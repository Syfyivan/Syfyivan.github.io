# Agent 双版本笔记：结构冻结与审查记录

核对日期：2026-10-23。交付为两篇独立、全文可读的 Hexo 单页文章。

## 1. 修订基线与目录冻结

基线为本次对话最后核实后的完整四章笔记，以及用户认可的五步组织方式。两篇覆盖相同机制，章节组织不同。

- 系统版：运行原理 → 上下文、检索与记忆 → 任务编排与可靠执行 → 验收、实现与选型。
- 五步版：角色与模块 → 主干五步 → 跨步骤编排与保障 → 验收与评估 → 实现、选型与观测。
- 目录权威文件：`outline.json`。正文权威文件：`sections.md`。
- 每篇包含全部 26 个机制块，各出现一次。发布产物直接包含正文，阅读不依赖另一篇或动态加载。
- 相同机制使用相同语义锚点。跨节联系以锚点引用，避免编号变化产生错误关联。

## 2. 术语与责任冻结

- Runtime 是整体软件责任集合；内部统一采用六个模块名：循环控制模块、上下文管理模块、模型接入模块、工具管理与执行模块、状态与持久化模块、事件与输出模块。
- 运行记录表示数据对象；运行状态只表示生命周期字段。预算、权限、等待对象和工具记录分别保存。
- 继续、等待、终止表示控制流；completed、failed、cancelled 表示本文应用层的终止结果。
- 上下文是当前输入；Memory 是信息维护机制；其数据称为记忆记录。
- 通用调用标识不设置伪统一 API 字段。Responses、Chat Completions、Claude 与 MCP 分别保留原始字段。
- 每项动作在详细正文中有唯一模块归属。主干表从 Runtime 整体视角给出输入输出，模块表解释内部责任。

## 5. 局部和全篇复核

- 局部：检查各块第一段引入的对象、并列维度、处理顺序和最后产物；每个标题覆盖所在块完整内容。
- 全篇：核对运行记录／状态、生成状态／运行终止／业务验收、工具调用 ID／业务幂等键等含义在全部使用位置一致。
- 章节承接：四章版通过信息、执行和控制依赖串联；五步版逐步交接，跨轮机制集中在后续章节。
- 内容完整性：两篇各含 26 个机制，语义锚点不重复，交叉引用有效，原始 API 字段保留。
- 整体与局部：主干仅给输入输出，内部机制在相应主题展开一次；表格用于字段或责任映射。

## 6. 用追问验收正文

1. 谁决定当前内容、谁转换成 API 请求？上下文管理模块选择，模型接入模块序列化。
2. 谁认出工具调用、谁执行？循环控制按协议项分派，工具管理与执行模块检查并调用真实入口。
3. 结果怎样回到原请求？按具体 API 标识与保存的映射关联；重复结果去重，未知归属报错。
4. 参数正确是否意味着可执行？语法、Schema、业务授权与执行条件分别检查。
5. 当前运行因何继续或结束？lifecycle 表给出待处理工作、等待、取消、错误和预算的明确条件。
6. 恢复怎样处理已发生但未记账的外部操作？使用稳定操作键、执行端幂等和状态查询，保留未知结果。
7. 文档和记忆怎样更新？保留来源和版本，明确替代关系，并处理派生索引与摘要。
8. 最终成功依据什么？实际产物与外部状态按验收条件检查，缺少证据保留未验证结论。
