怎么配合纸质资料看

网站负责“翻译资料”，Word 负责“考场原文定位”

资料里的话很密，容易看成概念堆叠。复习时不要先背，先按下面四步把每一节还原成“它在解决什么问题”。

1先找资料标题按 Word 里的章标题找，例如“3.3 负载均衡”“4.3 数据分库分表”，不要靠段落编号。
2再找纸上关键词每节都给出一两个能在纸质资料上扫到的关键词，用它快速确认位置。
3看人话解释把资料句子翻译成“问题、方案、代价”，看懂以后再回到原文。
4最后连到题目每节都标出能支持哪些选择题、简答题或设计题，考场才知道翻哪里。

记忆链路和资料的对应关系

这些链路不是额外背诵材料，而是把 Word 资料中分散的章节压缩成四条翻找路线。看链路时，按右侧章节回到纸质资料找原文。

高并发链路

链路含义：请求量变大以后，先扩计算能力，再减少同步等待和重复访问。

对应资料：3.1 计算层的软件架构技术挑战 → 3.3 负载均衡 → 4.4 数据缓存 → 3.4 消息队列 → 3.5 分布式服务框架。

纸上找：“TPS/QPS”“高性能集群”“负载均衡”“缓存的作用”“异步通信”“服务治理”。

对应题目：选择题 1，大型电商网站架构进化；综合应用题 1，计算层高性能、高扩展、高可用。

数据变大链路

链路含义：单库单表扛不住以后，先拆读写，再拆数据；拆完以后必须解决路由、事务和查询复杂度。

对应资料：4.1 数据驱动的软件架构演化 → 4.2 数据读写与主从分离 → 4.3 数据分库分表 → 分库分表引起的问题。

纸上找：“单机 MySQL”“读写分离·复制延迟”“垂直拆分、水平拆分”“水平切分的路由过程”“跨节点 Join”。

对应题目：选择题 6，客户端分片；简答题 4、5；综合应用题 2，数据层快速稳定访问。

高可用链路

链路含义：高可用不是机器不坏，而是坏了能发现、能切换、能恢复，并尽量不中断服务。

对应资料：1.2 质量属性中的健壮性/可用性 → 4.2 主备/主从/主主复制 → 3.3 负载均衡 → 3.5 集群容错、服务发现/注册 → Docker 与 Kubernetes 调度。

纸上找：“故障转移”“主备复制”“主从复制”“Failover/Failback/Failfast”“服务注册表”“Replication Controller”。

对应题目：简答题 3、4；综合应用题 1 的高可用部分；支付设计题的主备和副本思路。

数据正确链路

链路含义：支付、订单这类业务不能重复扣款、不能读到旧状态，所以要限制重复请求、状态流转和数据分布。

对应资料：3.5 幂等性概念与解决方案 → 4.2 复制延迟及关键业务读主机 → 4.3 同组数据跨库问题、分布式事务问题、扩容与迁移日志。

纸上找：“幂等性”“状态机控制法”“写操作后的读操作指定发给数据库主服务器”“同组数据跨库问题”“更新操作日志”。

对应题目：设计题 2、3，支付子系统一致性；综合应用题 2 的关键数据读写策略。

判断自己看懂资料的标准

任意翻到一节，都能回答三句话：这节解决什么问题？资料给了什么方案？这个方案带来什么复杂度或易错点？能说出这三句，就不用死背整段原文。

资料逐节导读

按 Word 资料顺序看：每一部分到底在讲什么

下面的“资料位置”就是你纸质资料里要找的标题；“纸上找”是更快的定位关键词；“看不懂时”是把原文翻译成考试能用的话。

1.1 系统体系结构概述

资料位置：1 系统体系结构的内涵及要点 → 1.1 系统体系结构概述。

纸上找：“架构 = 构件 + 连接件 + 拓扑结构 + 约束 + 质量”。

这部分讲什么：架构不是某一段代码，而是系统由哪些部分组成、这些部分怎么连接、整体要满足哪些约束和质量。

看不懂时：把“构件”理解成模块或服务，把“连接件”理解成接口、协议、消息、调用关系，把“拓扑”理解成它们连成的整体形状。

对应考点：分层系统的构件/连接件、软件架构定义、设计题开头的系统结构说明。

1.2 SA 作用、质量属性与 4+1 视图

资料位置：1 系统体系结构的内涵及要点 → 1.2 系统体系结构概述。

纸上找：“SA 作用”“架构师的关注点”“部分软件质量因素及其对策”“4+1 视图模型”。

这部分讲什么：软件架构用来沟通、复用和记录关键决策；架构师关注质量属性；4+1 视图把系统从不同角度讲清楚。

看不懂时：质量属性就是“系统好不好用、快不快、稳不稳、安不安全”。4+1 视图可以理解成设计题模板：用例、逻辑、开发、进程、物理。

对应考点：质量属性选择题、ATAM/效用树可借用这一节、MVC 设计题里的 4+1 视图组织。

1.2 中间件

资料位置：1 系统体系结构的内涵及要点 → 1.2 → 系统=服务集群+中间件、软件中间件的作用、中间件分类。

纸上找：“屏蔽异构性、实现互操作、共性凝练和复用”。

这部分讲什么：中间件夹在应用和底层系统之间，把通信、集成、事务、消息、服务管理这类公共能力抽出来。

看不懂时：把中间件理解成“不同系统之间的公共翻译层和公共服务层”。它让业务系统少关心操作系统、网络、协议、平台差异。

对应考点：简答题“软件中间件的作用”、消息中间件、分布式服务框架。

2.1 软件设计模式概述

资料位置：2 软件设计模式基础 → 2.1 软件设计模式概述。

纸上找：“创建型模式、结构型模式、行为型模式、J2EE 模式”“开闭原则”。

这部分讲什么：设计模式是局部设计经验，目标是让代码更好扩展、更容易复用、更少耦合。

看不懂时：不要逐字背每个模式，先记分类：创建型管“怎么创建对象”，结构型管“怎么组合对象”，行为型管“对象怎么协作”。

对应考点：MVC、观察者/发布订阅、事件系统风格、设计模式分类。

2.1 常见模式：单例、工厂、适配器、代理、观察者

资料位置：2 软件设计模式基础 → 创建型/结构型/行为型模式。

纸上找：“单例模式”“工厂模式”“适配器模式”“代理模式”“观察者模式”。

这部分讲什么：这些模式分别解决唯一实例、对象创建、接口不兼容、访问控制/增强、一对多通知的问题。

看不懂时：观察者就是资料里最接近“发布订阅/事件系统”的点；代理可以顺手理解缓存、日志、权限这类非业务增强。

对应考点：事件系统选择题、MVC/表示层弱关联、发布订阅和消息代理的理解。

3.1 计算层的软件架构技术挑战

资料位置：第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战。

纸上找：“计算复杂性”“应用从集中走向分布式”“服务治理”“TPS、QPS”。

这部分讲什么：计算层关注请求处理能力。用户和业务变多后，单体应用会走向业务拆分、服务化、治理和扩展。

看不懂时：把它看作“为什么要从一个应用拆成很多服务”。拆分以后性能、容量、安全、降级、上线下线都要治理。

对应考点：大型电商架构演进、综合题计算层、高性能/高扩展/高可用定义。

3.3 负载均衡

资料位置：第三章：计算机软件架构技术 → 3.3 负载均衡。

纸上找：“DNS 负载均衡、硬件负载均衡、软件负载均衡”“轮询、加权轮询、Hash”。

这部分讲什么：单服务器有性能上限，负载均衡就是增加任务分配器，把请求分给多台服务器。

看不懂时：地理级用 DNS，集群级可用 F5，机器级常见 Nginx；算法就是“按什么规则把请求发给谁”。

对应考点：电商演进选择题、综合应用题计算层、高并发入口层设计。

3.4 消息队列

资料位置：第三章：计算机软件架构技术 → 3.4 消息队列。

纸上找：“MOM”“发布订阅”“事件驱动”“时间解耦、空间解耦”。

这部分讲什么：消息队列让系统通过消息通信，不必所有调用都同步等待，常用于异步、削峰、解耦。

看不懂时：时间解耦是双方不必同时在线；空间解耦是发送方不必知道接收方在哪；异步是发出后先不阻塞主流程。

对应考点：事件系统风格、消息中间件、综合题中的异步处理。

3.5 分布式服务框架

资料位置：第三章：计算机软件架构技术 → 3.5 分布式服务框架。

纸上找：“服务订阅发布、服务路由、集群容错、服务调用、幂等性”。

这部分讲什么：服务拆多以后，需要框架处理注册发现、路由、容错、调用协议、序列化、配置和重复请求问题。

看不懂时：把一次调用想成：消费者找服务地址 → 路由选实例 → 调用失败要不要重试 → 写操作要防重复副作用。

对应考点：微服务设计、支付幂等性、综合题计算层服务治理。

3.5 微服务、API 网关、服务发现与注册

资料位置：第三章 → 3.5 → 微服务的定义、服务集成、服务发现、服务注册、数据去中心化。

纸上找：“API-网关方式”“消息代理方式”“客户端发现模式、服务端发现模式”。

这部分讲什么：微服务按业务拆小，网关负责统一入口，注册中心保存服务地址，发现机制帮助调用方找到可用实例。

看不懂时：API 网关像所有客户端的统一门面；服务注册表像地址簿；服务发现就是查地址并选一个健康实例。

对应考点：刷脸支付多终端统一接口、微服务集成方式、服务发现和负载均衡。

Docker 与 Kubernetes 调度

资料位置：第三章后半部分 → Docker 引擎、Docker VS VM、Docker 调度工具、K8S、POD 调度。

纸上找：“Docker 是 C/S 结构”“Swarm、Mesos、Kubernetes”“Pod、Label、Replication Controller”。

这部分讲什么：容器让应用部署更轻量，调度系统负责把容器放到合适机器上运行，并处理扩容、健康检查和故障迁移。

看不懂时：Docker 解决“打包和运行环境”，Kubernetes 解决“很多容器放到哪些机器、坏了怎么拉起、怎么找到服务”。

对应考点：综合题计算层高可用、扩容、容器调度相关表述。

4.1 数据驱动的软件架构演化

资料位置：4 数据层的软件架构技术 → 4.1 数据驱动的软件架构演化。

纸上找：“单机 MySQL”“Memcached+MySQL+垂直分离”“MySQL 主从读写分离”“分库分表+水平拆分”。

这部分讲什么：数据层的演化主线是单机数据库扛不住后，先缓存，再读写分离，再分库分表，再考虑 NoSQL/集群。

看不懂时：数据层所有技术都围绕三个压力：数据太多、索引太大、读写请求太多。

对应考点：电商架构演进、数据层综合题、缓存和分库分表出现的原因。

4.2 数据读写与主从分离

资料位置：4 数据层的软件架构技术 → 4.2 数据读写与主从分离。

纸上找：“读写分离·复制延迟”“主备复制”“主从复制”“主主复制”“数据集中集群、数据分散集群”。

这部分讲什么：通过复制和多节点提高读性能、可用性和容灾能力，但会带来复制延迟、故障切换和数据冲突。

看不懂时：主备偏备份，备机平时不服务；主从可让从机读；主主两边都能写但最容易冲突；关键业务写后读要读主库。

对应考点：数据集中/分散集群区别、对称/非对称集群、支付一致性设计。

4.3 数据分库分表

资料位置：4 数据层的软件架构技术 → 4.3 数据分库分表。

纸上找：“垂直拆分、水平拆分”“客户端分片”“垂直切分更偏业务拆分，水平切分更偏技术性能指标”。

这部分讲什么：分库分表就是把数据拆开，降低单库单表压力。拆法分垂直和水平，访问时必须能路由到正确分片。

看不懂时：垂直是按业务或字段拆，例如 User、Pay、Commodity；水平是同结构按行拆，例如 User0、User1。拆完以后事务、Join、排序分页会变难。

对应考点：客户端分片选择题、垂直/水平分表简答题、支付系统数据一致性。

4.4 数据缓存

资料位置：4 数据层的软件架构技术 → 4.4 数据缓存。

纸上找：“本地缓存、分布式缓存、反向代理缓存、CDN 缓存”“FIFO、LFU、LRU”“缓存穿透、并发、雪崩、热点”。

这部分讲什么：缓存把热点数据放到更快、更近的位置，减少数据库或后端服务压力。

看不懂时：先分清缓存位置：应用内是本地缓存，独立 Redis/Memcached 是分布式缓存，Nginx/Varnish 是反向代理缓存，离用户近的是 CDN。

对应考点：缓存清理策略选择题、缓存问题简答题、综合题热点访问优化。

资料本身需要注意的地方

这份 Word 的计算层和数据层够用，但表示层正文很弱：目录里有“5 表示层的设计基础”，正文里没有完整内容。因此视觉流程、Bootstrap、MVC 与三层 C/S 比较、ATAM 效用树、管道-过滤器、SPMD/Master-Worker/预测执行这些点，只靠原资料不太好查。最小修改建议是在 Word 最后一页加“2020C 弱覆盖补充”，不要重写主体资料。

一、多项选择题

1. 大型电商网站的架构进化

2. MVC 风格与三层 C/S 风格异同

3. 对称集群与非对称集群的主要区别

资料位置：资料未直接出现“对称/非对称集群”；可参考第三章：计算机软件架构技术 → 3.3 负载均衡（多服务器共同服务），以及第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离（主备复制、主从复制、主主复制、数据集中/分散集群）。

答题要点：对称集群中各节点地位基本相同，通常都可以对外提供同类服务，任务可通过负载均衡分配到任意可用节点，典型目标是提高吞吐、扩展性和容错性。非对称集群中节点角色不同，常见形式是主备、主从、调度节点/工作节点，主节点负责写入、调度或状态决策，备/从节点负责备份、读请求或故障接管。主要区别是节点角色是否等价、请求是否能发给任意节点、故障切换和一致性处理复杂度不同。

4. 数据集中集群与数据分散集群区别

资料位置：第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离 → 数据集群 → 数据集中集群、数据分散集群、集中 VS 分散。

答题要点：数据集中集群也就是一主多备/从，数据写入只能到主机，读操作可以根据主备或主从架构灵活安排；复杂点在于多通道复制、一致性检查、主机状态判断和故障后重新选主。数据分散集群由多个服务器共同存储数据，每台服务器负责一部分数据，同时备份一部分数据；复杂点在于数据分配算法、均衡性、容错性和扩容迁移。集中式适合数据量不大、机器数量不多的场景；分散式适合数据量巨大、集群规模大的场景。

5. 垂直分表与水平分表比较

资料位置：第四章：数据层的软件架构技术 → 4.3 数据分库分表 → 分库分表的基本定义（垂直拆分、水平拆分）、切分方法（垂直切分、水平切分及优缺点）、水平切分的路由过程与分片维度。

答题要点：垂直分表按业务或字段维度拆分，一张表按业务含义、冷热程度、字段访问频率拆成结构不同的多张表，重点是业务边界清晰和职责拆分。优点是拆分规则明确、便于动静/冷热分离、管理简单；缺点是跨表 Join 和事务变复杂，仍可能受单业务库瓶颈限制。水平分表按行拆分，依据哈希、时间等分片规则把同结构数据分散到多个表或库中，每张表结构相同、只保存一部分数据。优点是降低单表数据量、提升负载能力和稳定性；缺点是跨分片 Join、排序、分页、分布式事务和扩容迁移困难。共同问题包括分布式事务、跨节点 Join、合并排序分页和多数据源管理。

6. 缓存可能带来的问题

资料位置：第四章：数据层的软件架构技术 → 4.4 数据缓存 → 数据缓存的基本清洗策略 → 缓存的问题（数据一致性、缓存穿透、缓存并发、缓存雪崩、缓存热点）。

答题要点：缓存会带来数据一致性问题，即缓存与数据库或源数据之间可能不同步。缓存穿透指大量查询不存在的 key 导致请求绕过缓存直达数据库，可通过缓存空值、校验非法请求等方式缓解。缓存并发指热点 key 失效时大量请求同时访问数据库并回写缓存，导致应用和数据库压力突增。缓存雪崩指缓存服务器重启或大量缓存同一时间失效，后端数据库瞬时承压。缓存热点指极少数热点数据被高并发访问，缓存服务器本身压力过大。

1. 早期某宝网：单服务器 Web 访问能力与 MVC 设计

资料位置：1 系统体系结构的内涵及要点 → 软件架构设计的模型（4+1 视图模型）；2 软件设计模式基础 → J2EE 模式（MVC 模式）；第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战（单机、扩展性、性能指标）；第四章：数据层的软件架构技术 → 单机 MySQL（缓存、主从读写分离演进背景）和 4.4 数据缓存。

答题框架：

用例视图：用户通过浏览器完成注册登录、商品浏览/搜索、商品详情、购物车、下单、支付入口、物流查询等核心用例。早期系统可先保留核心交易链路，非核心功能如直播购物、复杂推荐可弱化或异步化。

2. 全球 10 亿用户可用的支付子系统：保障数据一致性的架构

资料位置：1 系统体系结构的内涵及要点 → 部分软件质量因素及其对策（性能、安全性、健壮性/可用性）；第三章：计算机软件架构技术 → 3.5 分布式服务框架 → 幂等性；第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离（复制延迟、主备/主从/主主、数据集群）；第四章 → 4.3 数据分库分表（客户端分片、支持事务的分布式数据库、分布式事务问题、同组数据跨库问题）。

设计理念：支付子系统优先保证正确性和一致性，再在一致性边界内做性能和扩展。入口层采用 API 网关和负载均衡接入全球用户，但核心支付写操作必须路由到确定的支付分区或账户分片。每个分片内部采用主/Leader + 多副本结构，核心写入只到主节点或 Leader，并通过同步复制、事务日志或共识机制确认后再返回成功。关键读请求读主节点，非关键查询可读从节点或缓存。

数据组织：按用户账户、商户、订单号或支付流水进行分库分表，同一笔支付强相关的数据尽量落在同一分片，利用本地事务获得强一致性。确实跨库的场景使用分布式事务、TCC/事务消息或支持事务的分布式数据库，并保留支付流水、状态机和对账机制。“第四章：数据层的软件架构技术 → 4.3 数据分库分表 → 同组数据跨库问题”这一处原则很关键：同组数据尽量放在同一台数据库服务器上，以便使用本地事务和自治能力。

一致性保障理由：第一，写操作单点归属到主节点或分片 Leader，避免多主并发写冲突。第二，支付请求带全局唯一流水号/订单号，用去重表或唯一索引实现幂等，防止重复付款、重复扣款。第三，支付状态按状态机推进，只允许合法状态转移。第四，跨库更新时使用分布式事务或可靠消息，失败后可重试、补偿和对账。第五，对主从复制延迟保持保守策略，支付后的关键读直接读主，避免“刚写完读不到”的问题。第六，对账和审计日志用于发现和修复最终不一致。

   ├─ 支付链路可追踪
   └─ 异常交易可定位、可审计、可回放

改进策略：如果评审发现性能风险，优先检查负载均衡、热点数据缓存、数据库索引、读写分离、异步化和分库分表方案。若可用性不足，增加主备/主从、自动倒换、健康检查、故障转移和灾备。若一致性风险高，收紧支付核心链路，关键读写走主节点，使用幂等、状态机、分布式事务/事务消息、同组数据同分片和对账补偿。若安全风险高，增加统一网关鉴权、加密、签名、防重放、限流和审计。若测试结论与评审风险不一致，应以风险场景补充压力测试、故障注入测试、一致性测试和安全测试；风险关闭前不应贸然上线核心支付链路。

四、综合应用题：刷脸支付人脸验证服务系统

1. 计算层如何实现高性能、高扩展、高可用

资料位置：第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战；3.3 负载均衡；3.4 消息队列（通信模型、MOM、异步通信）；3.5 分布式服务框架（集群容错、服务调用、API 网关、消息代理）；Docker 调度工具（容器调度、扩容、故障转移）。

答题要点：单机层面，对人脸检测、特征提取、比对算法做性能优化，使用线程池、连接池、本地缓存、批处理或硬件加速，减少不必要的 I/O 和序列化。服务设计为无状态或少状态，便于水平扩展。负载均衡层面，全球接入可用 DNS 做地理级调度，区域内使用 F5/LVS/Nginx 等集群级和机器级负载均衡，结合健康检查、加权轮询、负载最低优先或响应时间优先算法。高可用层面，多实例部署，服务注册发现，失败自动切换，关键服务多副本，容器编排系统负责拉起、扩容和故障迁移。消息处理层面，核心 2 秒验证链路保持同步短路径，日志、风控分析、模型更新、通知和离线训练等放入消息队列异步处理，提高主链路吞吐并实现解耦。

2. 数据层如何提供快速、稳定的数据访问

资料位置：第四章：数据层的软件架构技术 → 数据层非功能需求与架构技术；4.2 数据读写与主从分离（读写分离、复制延迟、数据集中/分散集群）；4.3 数据分库分表（定义、操作时机、解决方案、垂直/水平切分、路由）；4.4 数据缓存（缓存类型、清洗策略、缓存问题）。

答题要点：分库分表方面，人脸模板、用户身份、设备、交易验证流水等数据按业务做垂直拆分；用户人脸模板和验证流水按用户 ID、区域或哈希做水平拆分，降低单库单表压力。对全球海量用户，可采用数据分散集群以获得更好的可伸缩性，并用分片路由定位用户数据。主从分离方面，核心写入如注册人脸模板、更新账户状态写主库，查询和非关键读取走从库；刚写后的关键读必须读主库，避免复制延迟造成读不到最新数据。缓存方面，对热点用户特征、设备配置、风控规则、会话令牌等使用 Redis/Memcached 等分布式缓存；对静态资源和模型配置可结合 CDN/反向代理缓存。缓存设计要处理一致性、穿透、并发、雪崩和热点问题，比如缓存空值、互斥重建、过期时间随机化、热点 key 拆分和限流。

3. 如何为多终端提供友好、快捷展示

资料位置：资料未直接命中表示层细节；可弱参考 1 系统体系结构的内涵及要点 → 部分软件质量因素及其对策（易用性：统一风格界面、定制）；目录中的“5 表示层的设计基础”；第三章：计算机软件架构技术 → 3.5 分布式服务框架 → API 网关方式。

答题要点：多终端包括手机端、POS 机、自助设备等，应通过统一 API 网关提供一致接口，同时按终端能力适配页面和交互。异步内容加载方面，先加载验证主流程必需内容，如摄像头授权、取景框、提示语和验证按钮，非关键内容如广告、帮助、活动、历史记录延后加载；网络慢时展示轻量页面和明确状态反馈。自适应适配方面，根据屏幕尺寸、摄像头能力、系统版本、网络状态和输入方式选择布局与交互，保证按钮、提示、取景区域在不同设备上清晰可用。为了满足 2 秒应答，应减少首屏资源体积，缓存静态资源，本地预校验图像质量，将复杂分析放到后端或异步链路，并在失败时给出快速重试路径。
