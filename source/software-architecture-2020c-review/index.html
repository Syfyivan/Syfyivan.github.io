1. 软件架构：不是功能清单，而是系统的组织方式

核心理解：资料里的“构件、连接件、拓扑、约束、质量”看起来抽象，本质是在问：这个系统由哪些大块组成，这些大块怎么协作，哪些规则不能破坏，最后要达到什么质量。

资料怎么拆：构件可以是模块、服务、数据库、缓存、队列；连接件可以是 HTTP、RPC、消息、数据库连接；拓扑就是谁调用谁、谁依赖谁；约束是只能相邻层调用、只能主库写、必须鉴权；质量是性能、可用性、安全性、一致性。

举个例子：电商系统不是只写“商品、订单、支付”。架构层要写：浏览器/客户端通过网关进入，商品服务、订单服务、支付服务拆开，热点商品走缓存，订单消息异步通知，支付写主库并保证幂等。

易错点：不要把架构写成“用了 Java、用了 MySQL”这种技术清单。语言和数据库只是实现选择，架构要说明结构和质量目标。

答题用法：本系统采用分层/分布式架构，由入口层、业务服务层、数据层和中间件组成；各层通过接口、RPC 或消息连接；为满足性能/可用性/一致性，分别采用负载均衡、缓存、消息队列、主从复制等机制。

2. 质量属性：考试设计题真正想考的“为什么这么设计”

核心理解：质量属性不是功能，而是功能运行时的表现。一个支付系统“能付款”是功能；“两秒内付款、不能重复扣款、机器坏了不丢单”才是质量属性。

资料怎么拆：性能对应响应时间、TPS、QPS，可用性对应故障发现和故障切换，安全性对应鉴权和加密，可维护性对应模块拆分和文档化，可扩展性对应加机器或拆服务后系统能继续增长。

举个例子：刷脸支付题里“2 秒应答”是性能，“全球 10 亿用户”是扩展性，“支付不能错”是一致性/正确性，“人脸数据不能泄露”是安全性。

易错点：不要只写“系统要高性能、高可用”。要写实现手段，例如高性能靠负载均衡、缓存、异步；高可用靠多副本、健康检查、Failover；一致性靠幂等、事务、主库读写、对账。

答题用法：质量目标包括性能、可用性、一致性、安全性和可扩展性。性能通过负载均衡和缓存实现；可用性通过多实例、健康检查和故障切换实现；一致性通过幂等、状态机、主库读写和补偿对账实现。

3. 中间件：把分布式系统的公共麻烦抽出去

核心理解：中间件不是某一个产品名，而是一类位于应用和底层系统之间的软件。它的价值是让业务不用重复处理通信、异构、集成、事务、消息、服务治理这类公共问题。

资料怎么拆：“屏蔽异构性”是隐藏操作系统、语言、协议、数据库差异；“互操作”是让不同系统能合作；“共性凝练和复用”是把重复能力做成统一组件。

举个例子：消息队列是消息中间件，解决异步通信；API 网关是服务入口中间件，解决统一入口、鉴权、限流；分库分表中间件解决路由到哪个库表。

易错点：不要把中间件等同于“开发工具”。资料里明确说中间件在应用软件和系统软件之间，是为分布式应用提供公共服务的一类软件。

答题用法：中间件位于应用软件和系统软件之间，主要作用是屏蔽异构性、实现互操作、抽取共性能力复用，从而降低分布式系统开发复杂度，提高可靠性、可用性和集成能力。

4. 4+1 视图：设计题不会写时的骨架

核心理解：4+1 视图不是要你画五张复杂图，而是让你从五个角度说清楚系统。它特别适合设计题，因为设计题通常没有唯一答案，关键是结构完整。

资料怎么拆：用例视图写用户要完成什么；逻辑视图写系统有哪些模块/对象/服务；开发视图写代码模块怎么组织；进程视图写运行时调用、同步/异步、并发；物理视图写部署在哪些服务器或节点。

举个例子：早期淘宝单服务器题：用例是浏览商品、下单、支付；逻辑是 View/Controller/Model；开发视图是 Web、Service、DAO、Domain；进程视图是浏览器到 Web 容器再到数据库；物理视图是一台服务器上部署 Web、应用、数据库和缓存。

易错点：MVC 只是逻辑/表示层设计，不等于完整系统架构。三层 C/S 更偏部署和分层，4+1 可以把两者放到不同视角里说明。

答题用法：用例视图描述核心用户场景；逻辑视图采用 MVC/服务模块划分；开发视图按 Web、Service、DAO、Domain 组织；进程视图说明请求链路和同步异步；物理视图说明服务器、数据库、缓存部署。

5. 负载均衡：多机器之前必须先有分配规则

核心理解：负载均衡不是“多买几台服务器”这么简单。多台服务器能不能共同工作，取决于谁来分配请求、怎么分配、坏机器怎么剔除。

资料怎么拆：DNS 负载均衡适合地理级调度，但缓存导致更新慢；硬件负载均衡性能强但贵；软件负载均衡灵活便宜，常见如 Nginx。算法里轮询追求平均，加权轮询考虑机器能力，负载最低看当前压力，性能最优看响应时间，Hash 保持同类请求稳定。

举个例子：用户访问刷脸支付服务时，DNS 先把用户导向附近机房，机房入口再用负载均衡把请求发到健康的识别服务实例。

易错点：负载均衡解决的是入口请求分发，不直接解决数据库一致性。支付不能错还要靠幂等、主库读写、事务和对账。

答题用法：入口层采用多级负载均衡，地理级由 DNS 调度，集群级/机器级由 F5、LVS 或 Nginx 分发，结合健康检查和加权轮询/最小连接/响应时间优先算法提高吞吐和可用性。

6. 消息队列：把“不必立刻做完”的事从主流程拿走

核心理解：消息队列的核心是异步和解耦。它不是为了让系统更复杂，而是为了让发送方和接收方不用同时等待彼此。

资料怎么拆：同步调用是调用方等结果；异步调用是先发出去，之后再处理结果。时间解耦是不必同一时间在线，空间解耦是不必知道对方地址。发布订阅是一个事件可以被多个订阅者消费。

举个例子：下单成功后，扣库存和生成订单可能是主流程；发短信、写日志、推荐更新、统计分析可以发消息异步处理，不阻塞用户。

易错点：消息队列不保证业务天然正确。异步后会有重复消费、顺序、丢失、最终一致性问题，所以支付这类核心链路要谨慎使用，或配合幂等和事务消息。

答题用法：非关键流程通过消息队列异步化，削峰填谷并降低服务耦合；生产者只负责发送消息，消费者异步消费；关键业务需配合幂等、重试、补偿和监控。

7. 分布式服务框架：服务拆开后的交通系统

核心理解：服务一多，真正困难的不是“写服务”，而是服务地址怎么找、调用怎么发、失败怎么处理、配置怎么统一。

资料怎么拆：服务订阅发布解决注册发现；服务路由决定调用哪个实例；集群容错决定失败后重试还是快速失败；服务调用区分同步、异步、并行；协议和序列化决定数据怎么传；配置中心负责运行时参数。

举个例子：订单服务调用库存服务时，不应该写死某台机器 IP，而是从注册中心发现库存服务实例，通过路由选一个，调用失败时按 Failover 或 Failfast 策略处理。

易错点：Failover 适合读操作或幂等写操作；非幂等写操作不能随便重试，否则可能重复扣款或重复创建订单。

答题用法：业务拆分后使用分布式服务框架，提供服务注册发现、服务路由、集群容错、同步/异步/并行调用、多协议序列化和统一配置，提升服务治理能力。

8. 幂等性：支付题最核心的正确性知识点

核心理解：幂等性不是“不会失败”，而是失败重试或重复请求时，业务结果不能重复变化。一次付款请求来一次或来三次，都只能扣一次钱。

资料怎么拆：查询天然幂等，因为不会改数据；新增通常不幂等，因为多执行会多插入；基于主键的非计算式更新较容易幂等；计算式更新如余额减一不幂等。解决方案包括锁、全局唯一 ID、去重表、版本号、状态机。

举个例子：用户连续点三次支付按钮，系统收到三次同一个订单号的支付请求。数据库用订单号或支付流水号做唯一约束，第一次成功，后两次查到已处理就直接返回成功或处理中，不再扣款。

易错点：“重试”不是问题，问题是不加幂等的重试。分布式系统一定会有重试，所以幂等是保护业务正确性的基本设计。

答题用法：支付请求携带全局唯一流水号，落去重表或唯一索引；支付状态按状态机推进；重复请求直接返回已有结果；失败场景通过日志、补偿和对账保证最终一致。

9. 微服务、API 网关、服务发现：拆服务后的入口和地址簿

核心理解：微服务是把业务按功能拆成小服务；API 网关是所有客户端的统一入口；服务发现是运行时找到服务实例。

资料怎么拆：点对点调用简单但会失控；API 网关可以统一接口、安全、监控、限流、格式转换；消息代理适合异步集成；服务注册表保存服务实例地址；客户端发现由调用方选实例，服务端发现由负载均衡器代选。

举个例子：刷脸支付有手机、POS、自助设备多个终端。终端不应该分别适配所有后端服务，而是统一进 API 网关，再由网关转到人脸验证、风控、支付、账户等服务。

易错点：API 网关不是业务服务本身，核心业务逻辑仍应在后端服务里。网关主要处理非业务公共能力和统一入口。

答题用法：多终端统一接入 API 网关，由网关完成鉴权、限流、协议适配和路由；后端微服务注册到注册中心，调用方通过服务发现获取健康实例，实现动态扩缩容和故障剔除。

10. 读写分离与复制延迟：性能和一致性的交换

核心理解：读写分离让主库负责写、从库负责读，能提高读性能；复制延迟说明从库数据可能落后主库。

资料怎么拆：主从集群里每台机器存全量业务数据，主机写，从机读。写入主库后复制到从库需要时间，如果立刻读从库，可能读不到刚写的数据。资料给了三个办法：写后读主库、读从失败再读主、关键业务全走主。

举个例子：用户刚注册完账号，马上登录。如果登录读从库，而从库还没同步新账号，就会提示账号不存在。正确做法是注册后的关键读走主库。

易错点：不要在支付、订单、账户余额等关键链路里无脑读从库。读写分离提高性能，但会牺牲强一致读。

答题用法：普通查询走从库提升读性能；写后立即读取、支付状态、账户余额等关键业务读写全部指向主库，避免复制延迟导致读取旧数据。

11. 分库分表：拆数据以后最难的是路由和一致性

核心理解：分库分表不是越早越好，而是在单库单表的数据量、索引、吞吐达到瓶颈后，把数据拆开分担压力。

资料怎么拆：垂直拆分按业务或字段拆，像 User、Pay、Commodity 分到不同库；水平拆分按行拆，表结构相同，数据按哈希、时间等规则分散。客户端分片是在应用/JDBC/ORM 里做路由，代理分片是在应用和数据库之间加代理。

举个例子：用户表按 user_id 哈希拆成 16 张表。查询某个用户时，先用 user_id 算出分片，再去对应表查。若按手机号查但手机号不是分片键，就可能要查多个分片。

易错点：分库分表会带来跨库事务、跨库 Join、排序分页、扩容迁移问题。答题时不能只写优点，还要写这些代价。

答题用法：按业务做垂直拆分，按用户 ID/订单号做水平拆分；通过分片规则路由到具体库表；同组强相关数据尽量放同一分片，减少跨库事务和跨库 Join。

12. 缓存：性能提升来自“更快”和“更近”，风险来自“不一致”

核心理解：缓存就是把热点数据副本放在访问更快的位置。它能减少数据库压力，但副本意味着可能和源数据不一致。

资料怎么拆：本地缓存和应用同进程，最快但不能共享；分布式缓存独立部署，多个应用共享；反向代理缓存放在应用服务器前；CDN 缓存放到离用户更近的边缘节点。清理策略 FIFO 看进入时间，LFU 看使用次数，LRU 看最近访问时间。

举个例子：商品详情页访问量很大，可以把商品基础信息放 Redis，把图片和 JS/CSS 放 CDN。用户访问时先命中缓存，减少数据库和应用压力。

易错点：缓存不是银弹。缓存穿透是查不存在的 key 打到数据库；缓存并发是热点 key 失效后大家一起查库；缓存雪崩是大量 key 同时失效；缓存热点是单个热点 key 压垮缓存节点。

答题用法：热点数据使用本地/分布式/反向代理/CDN 缓存提升访问性能；通过过期时间、LRU/LFU/FIFO 等策略管理空间；通过缓存空值、互斥重建、过期时间随机化、限流和热点拆分处理缓存问题。

知识点讲解

先把概念翻成人话，再回到资料原文

下面这些是 2020C 里最容易“看见词但不懂意思”的知识点。每个知识点都按“它是什么、为什么会出现、资料怎么看、考试怎么写”来讲。

1. 软件架构

一句话：软件架构是在系统层面决定“有哪些部分、怎么连接、要满足什么质量”。

为什么出现：系统小的时候写功能就行；系统大了以后，性能、安全、扩展、维护都不是某个函数能解决的，必须先设计整体结构。

资料怎么看：看到“构件、连接件、拓扑结构、约束、质量”，先把术语对应到具体对象。构件是模块/服务，连接件是调用/接口/消息，拓扑是连接关系，约束是规则，质量是性能、可用性等目标。

考试怎么写：答设计题时先说架构目标，再按构件、连接、部署、质量属性展开。

2. 质量属性

一句话：质量属性就是系统“好不好”的不同维度，例如快不快、稳不稳、安不安全、好不好维护。

为什么出现：功能正确不等于系统可用。支付系统能扣款只是功能；不重复扣、两秒内返回、故障能恢复，才是架构要保证的质量。

资料怎么看：性能对应集群、缓存、异步；安全对应防火墙、加密、单一入口；可用性对应集群、灾备、故障转移。

考试怎么写：遇到“质量属性/ATAM/效用树”，就把目标拆成性能、可用性、一致性、安全、可扩展、可维护。

3. 中间件

一句话：中间件是夹在应用和底层系统之间的公共能力层。

为什么出现：分布式系统里有不同语言、系统、网络、协议和数据源。如果每个业务都自己处理通信、事务、消息、服务发现，会重复且容易错。

资料怎么看：“屏蔽异构性”就是隐藏不同平台差异；“互操作”就是让不同系统能协作；“共性凝练和复用”就是把大家都要用的能力抽出来。

考试怎么写：简答题先写位置，再写三大作用：屏蔽异构性、实现互操作、共性能力复用。

4. 4+1 视图

一句话：4+1 视图是从五个角度描述同一个系统。

为什么出现：一个系统给用户、开发者、部署人员、运维人员看的重点不一样，所以不能只画一张图。

资料怎么看：用例视图讲用户场景；逻辑视图讲类、对象、接口和模块；开发视图讲代码和模块组织；进程视图讲运行时进程通信；物理视图讲部署到哪些机器。

考试怎么写：设计题不知道怎么组织时，直接按这五块写，尤其适合 MVC/早期电商网站设计题。

5. 负载均衡

一句话：负载均衡就是把请求分给多台机器，避免一台机器被打满。

为什么出现：单服务器再优化也有上限。用户变多后，需要多台服务器一起提供服务，还要有一个“分配器”决定请求发给谁。

资料怎么看：DNS 负责地理级分流，F5/LVS 偏集群级，Nginx 常做机器级；轮询是平均发，加权轮询是按能力发，Hash 是让同类请求尽量去同一台。

考试怎么写：电商演进和综合题计算层，都可以写“入口层使用负载均衡，结合健康检查和合适算法”。

6. 消息队列 / MOM

一句话：消息队列让系统通过消息间接通信，不必所有流程都同步等待。

为什么出现：下单后发短信、写日志、更新推荐不一定要卡住主流程。放进消息队列后，主流程可以先返回，其他服务慢慢消费。

资料怎么看：时间解耦是不必同时运行；空间解耦是不必知道对方在哪里；发布订阅是一条消息可以通知多个订阅者。

考试怎么写：看到异步、削峰、解耦、事件驱动，就往消息队列/MOM/发布订阅上靠。

7. 分布式服务框架

一句话：分布式服务框架负责让很多服务能被注册、发现、路由、调用和容错。

为什么出现：服务拆多以后，调用方不可能手写所有服务地址，也不能每次失败就让业务代码自己处理。

资料怎么看：服务订阅发布解决“服务在哪里”；服务路由解决“选哪个实例”；集群容错解决“失败后怎么办”；序列化和协议解决“怎么传数据”。

考试怎么写：综合题计算层可以写“服务注册发现 + 路由 + 集群容错 + 同步/异步/并行调用”。

8. 幂等性

一句话：幂等性是同一个操作执行一次或多次，业务结果都一样。

为什么出现：网络抖动、用户重复点击、MQ 重复消费、RPC 重试都可能让同一请求到达多次；支付场景如果不幂等，就可能重复扣款。

资料怎么看：查询天然幂等；新增通常不幂等；基于唯一流水号、去重表、版本号、状态机可以把不幂等操作变得可控。

考试怎么写：支付设计题一定写唯一流水号/订单号、去重表或唯一索引、状态机控制、失败重试和补偿。

9. 微服务、API 网关、服务发现

一句话：微服务是按业务拆小，API 网关是统一入口，服务发现是动态找服务地址。

为什么出现：业务复杂后，一个大系统太难改、难部署、难扩容；拆成小服务后，又需要统一入口和动态寻址。

资料怎么看：API 网关处理统一接口、安全、限流、监控；注册中心像服务地址簿；客户端发现是调用方自己查地址，服务端发现是先到负载均衡器再转发。

考试怎么写：多终端、微服务集成、统一接口时，写 API 网关；动态实例、扩容和健康检查时，写服务注册发现。

10. 读写分离与复制延迟

一句话：读写分离是主库写、从库读；复制延迟是主库写完后，从库还没来得及同步。

为什么出现：多数系统读多写少，把读请求分给从库能减轻主库压力。但复制不是瞬间完成，所以会出现刚写完读不到。

资料怎么看：关键业务“写后读”要读主库；读从库失败再读主库；非关键读可以走从库。

考试怎么写：支付、注册、订单状态这类关键链路，写完后的读操作必须读主库，不能盲目读从库。

11. 分库分表

一句话：分库分表是把一个太大的库或表拆成多个库或表。

为什么出现：数据量太大、索引太大、单实例吞吐到瓶颈时，单库单表会拖慢查询和写入。

资料怎么看：垂直拆分按业务或字段拆，结构可能不同；水平拆分按行拆，结构相同但数据分散。拆完以后一定会遇到路由、事务、Join、排序分页、扩容迁移问题。

考试怎么写：比较题写“垂直偏业务拆分，水平偏性能扩展”；设计题写“同组数据尽量同分片”。

12. 缓存

一句话：缓存是把常用数据放到更快、更近的位置，减少后端压力。

为什么出现：热点数据反复查数据库很浪费，缓存能减少 I/O 和数据库访问。

资料怎么看：本地缓存快但不能共享；分布式缓存可共享；反向代理缓存离应用近；CDN 缓存离用户近。FIFO 看进入时间，LFU 看使用次数，LRU 看最近使用时间。

考试怎么写：缓存问题要能解释一致性、穿透、并发、雪崩、热点；清理策略题记住 FIFO/LFU/LRU/过期时间。

4.3 数据分库分表

这部分讲什么：分库分表就是把数据拆开，降低单库单表压力。拆法分垂直和水平，访问时必须能路由到正确分片。

2. MVC 风格与三层 C/S 风格异同

3. 对称集群与非对称集群的主要区别

资料位置：资料未直接出现“对称/非对称集群”；可参考第三章：计算机软件架构技术 → 3.3 负载均衡（多服务器共同服务），以及第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离（主备复制、主从复制、主主复制、数据集中/分散集群）。

答题要点：对称集群中各节点地位基本相同，通常都可以对外提供同类服务，任务可通过负载均衡分配到任意可用节点，典型目标是提高吞吐、扩展性和容错性。非对称集群中节点角色不同，常见形式是主备、主从、调度节点/工作节点，主节点负责写入、调度或状态决策，备/从节点负责备份、读请求或故障接管。主要区别是节点角色是否等价、请求是否能发给任意节点、故障切换和一致性处理复杂度不同。

4. 数据集中集群与数据分散集群区别

资料位置：第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离 → 数据集群 → 数据集中集群、数据分散集群、集中 VS 分散。

答题要点：数据集中集群也就是一主多备/从，数据写入只能到主机，读操作可以根据主备或主从架构灵活安排；复杂点在于多通道复制、一致性检查、主机状态判断和故障后重新选主。数据分散集群由多个服务器共同存储数据，每台服务器负责一部分数据，同时备份一部分数据；复杂点在于数据分配算法、均衡性、容错性和扩容迁移。集中式适合数据量不大、机器数量不多的场景；分散式适合数据量巨大、集群规模大的场景。

5. 垂直分表与水平分表比较

资料位置：第四章：数据层的软件架构技术 → 4.3 数据分库分表 → 分库分表的基本定义（垂直拆分、水平拆分）、切分方法（垂直切分、水平切分及优缺点）、水平切分的路由过程与分片维度。

答题要点：垂直分表按业务或字段维度拆分，一张表按业务含义、冷热程度、字段访问频率拆成结构不同的多张表，重点是业务边界清晰和职责拆分。优点是拆分规则明确、便于动静/冷热分离、管理简单；缺点是跨表 Join 和事务变复杂，仍可能受单业务库瓶颈限制。水平分表按行拆分，依据哈希、时间等分片规则把同结构数据分散到多个表或库中，每张表结构相同、只保存一部分数据。优点是降低单表数据量、提升负载能力和稳定性；缺点是跨分片 Join、排序、分页、分布式事务和扩容迁移困难。共同问题包括分布式事务、跨节点 Join、合并排序分页和多数据源管理。

6. 缓存可能带来的问题

资料位置：第四章：数据层的软件架构技术 → 4.4 数据缓存 → 数据缓存的基本清洗策略 → 缓存的问题（数据一致性、缓存穿透、缓存并发、缓存雪崩、缓存热点）。

答题要点：缓存会带来数据一致性问题，即缓存与数据库或源数据之间可能不同步。缓存穿透指大量查询不存在的 key 导致请求绕过缓存直达数据库，可通过缓存空值、校验非法请求等方式缓解。缓存并发指热点 key 失效时大量请求同时访问数据库并回写缓存，导致应用和数据库压力突增。缓存雪崩指缓存服务器重启或大量缓存同一时间失效，后端数据库瞬时承压。缓存热点指极少数热点数据被高并发访问，缓存服务器本身压力过大。

1. 早期某宝网：单服务器 Web 访问能力与 MVC 设计

资料位置：1 系统体系结构的内涵及要点 → 软件架构设计的模型（4+1 视图模型）；2 软件设计模式基础 → J2EE 模式（MVC 模式）；第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战（单机、扩展性、性能指标）；第四章：数据层的软件架构技术 → 单机 MySQL（缓存、主从读写分离演进背景）和 4.4 数据缓存。

答题框架：

用例视图：用户通过浏览器完成注册登录、商品浏览/搜索、商品详情、购物车、下单、支付入口、物流查询等核心用例。早期系统可先保留核心交易链路，非核心功能如直播购物、复杂推荐可弱化或异步化。

逻辑视图：采用 MVC。View 是 HTML/CSS/JS 页面和模板，负责展示商品、订单、购物车等页面；Controller 接收 HTTP 请求，做参数校验、会话处理和路由分发；Model 包含商品、用户、订单、支付记录等领域对象，以及 Service/DAO 对业务规则和数据库访问的封装。

开发视图：按模块拆分为 Web/Controller、Service、DAO、Domain、View 模板、Static 静态资源、配置和日志模块。这样可以在单服务器内保持清晰边界，为以后拆成分布式服务留下接口。

进程视图：浏览器请求进入 Web 容器或 Nginx，静态资源由 Nginx 直接返回，动态请求进入 Controller，再调用 Service、DAO 和数据库。日志、消息通知、推荐更新等非关键流程可异步处理，避免阻塞交易主流程。

物理视图：一台服务器上部署 Web 服务器、应用服务、数据库和本地缓存。单机优化包括：启用 HTTP 静态资源缓存与压缩；数据库建索引、SQL 优化、连接池；使用本地缓存缓存热点商品、分类、配置；减少重复 I/O；合理配置线程池；把图片、CSS、JS 等静态内容交给 Nginx 或反向代理缓存处理。这样能在单服务器条件下尽量提高吞吐和响应速度。

2. 全球 10 亿用户可用的支付子系统：保障数据一致性的架构

资料位置：1 系统体系结构的内涵及要点 → 部分软件质量因素及其对策（性能、安全性、健壮性/可用性）；第三章：计算机软件架构技术 → 3.5 分布式服务框架 → 幂等性；第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离（复制延迟、主备/主从/主主、数据集群）；第四章 → 4.3 数据分库分表（客户端分片、支持事务的分布式数据库、分布式事务问题、同组数据跨库问题）。

设计理念：支付子系统优先保证正确性和一致性，再在一致性边界内做性能和扩展。入口层采用 API 网关和负载均衡接入全球用户，但核心支付写操作必须路由到确定的支付分区或账户分片。每个分片内部采用主/Leader + 多副本结构，核心写入只到主节点或 Leader，并通过同步复制、事务日志或共识机制确认后再返回成功。关键读请求读主节点，非关键查询可读从节点或缓存。

数据组织：按用户账户、商户、订单号或支付流水进行分库分表，同一笔支付强相关的数据尽量落在同一分片，利用本地事务获得强一致性。确实跨库的场景使用分布式事务、TCC/事务消息或支持事务的分布式数据库，并保留支付流水、状态机和对账机制。“第四章：数据层的软件架构技术 → 4.3 数据分库分表 → 同组数据跨库问题”这一处原则很关键：同组数据尽量放在同一台数据库服务器上，以便使用本地事务和自治能力。

一致性保障理由：第一，写操作单点归属到主节点或分片 Leader，避免多主并发写冲突。第二，支付请求带全局唯一流水号/订单号，用去重表或唯一索引实现幂等，防止重复付款、重复扣款。第三，支付状态按状态机推进，只允许合法状态转移。第四，跨库更新时使用分布式事务或可靠消息，失败后可重试、补偿和对账。第五，对主从复制延迟保持保守策略，支付后的关键读直接读主，避免“刚写完读不到”的问题。第六，对账和审计日志用于发现和修复最终不一致。

效用树示例：

支付子系统总体效用
├─ 性能
│  ├─ 高峰期支付请求 TPS/QPS 达标
│  └─ 95/99 分位响应时间满足业务目标
├─ 可用性
│  ├─ 单机/单节点故障后自动切换
│  └─ 机房或区域故障时核心支付能力不中断或可降级

│  ├─ 同一订单重复请求不重复扣款
│  ├─ 账户余额、订单状态、支付流水一致
│  └─ 跨库交易失败时可补偿、可对账
├─ 安全性
│  ├─ 未授权请求不能发起支付
│  ├─ 关键数据传输和存储加密
│  └─ 防重放、防篡改、防刷接口
├─ 可扩展性
│  ├─ 用户和交易量增长时可增加服务节点
│  └─ 数据容量增长时可扩容分片
└─ 可维护/可观测性
   ├─ 支付链路可追踪
   └─ 异常交易可定位、可审计、可回放

改进策略：如果评审发现性能风险，优先检查负载均衡、热点数据缓存、数据库索引、读写分离、异步化和分库分表方案。若可用性不足，增加主备/主从、自动倒换、健康检查、故障转移和灾备。若一致性风险高，收紧支付核心链路，关键读写走主节点，使用幂等、状态机、分布式事务/事务消息、同组数据同分片和对账补偿。若安全风险高，增加统一网关鉴权、加密、签名、防重放、限流和审计。若测试结论与评审风险不一致，应以风险场景补充压力测试、故障注入测试、一致性测试和安全测试；风险关闭前不应贸然上线核心支付链路。

四、综合应用题：刷脸支付人脸验证服务系统

1. 计算层如何实现高性能、高扩展、高可用

资料位置：第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战；3.3 负载均衡；3.4 消息队列（通信模型、MOM、异步通信）；3.5 分布式服务框架（集群容错、服务调用、API 网关、消息代理）；Docker 调度工具（容器调度、扩容、故障转移）。

答题要点：单机层面，对人脸检测、特征提取、比对算法做性能优化，使用线程池、连接池、本地缓存、批处理或硬件加速，减少不必要的 I/O 和序列化。服务设计为无状态或少状态，便于水平扩展。负载均衡层面，全球接入可用 DNS 做地理级调度，区域内使用 F5/LVS/Nginx 等集群级和机器级负载均衡，结合健康检查、加权轮询、负载最低优先或响应时间优先算法。高可用层面，多实例部署，服务注册发现，失败自动切换，关键服务多副本，容器编排系统负责拉起、扩容和故障迁移。消息处理层面，核心 2 秒验证链路保持同步短路径，日志、风控分析、模型更新、通知和离线训练等放入消息队列异步处理，提高主链路吞吐并实现解耦。

2. 数据层如何提供快速、稳定的数据访问

资料位置：第四章：数据层的软件架构技术 → 数据层非功能需求与架构技术；4.2 数据读写与主从分离（读写分离、复制延迟、数据集中/分散集群）；4.3 数据分库分表（定义、操作时机、解决方案、垂直/水平切分、路由）；4.4 数据缓存（缓存类型、清洗策略、缓存问题）。

答题要点：分库分表方面，人脸模板、用户身份、设备、交易验证流水等数据按业务做垂直拆分；用户人脸模板和验证流水按用户 ID、区域或哈希做水平拆分，降低单库单表压力。对全球海量用户，可采用数据分散集群以获得更好的可伸缩性，并用分片路由定位用户数据。主从分离方面，核心写入如注册人脸模板、更新账户状态写主库，查询和非关键读取走从库；刚写后的关键读必须读主库，避免复制延迟造成读不到最新数据。缓存方面，对热点用户特征、设备配置、风控规则、会话令牌等使用 Redis/Memcached 等分布式缓存；对静态资源和模型配置可结合 CDN/反向代理缓存。缓存设计要处理一致性、穿透、并发、雪崩和热点问题，比如缓存空值、互斥重建、过期时间随机化、热点 key 拆分和限流。
