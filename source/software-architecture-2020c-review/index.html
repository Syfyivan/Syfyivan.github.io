理解与记忆链路

先看懂“问题怎么一步步变大”，再记每个方案

这门课不是一堆零散名词。它的主线是：系统规模变大以后，单机、单库、同步调用都会遇到瓶颈，于是架构开始分层、拆分、缓存、异步、复制和分片。

1先问问题用户多了、请求多了、数据多了、机器会坏、数据不能错。
2再找方案负载均衡、缓存、消息队列、服务框架、主从、分库分表。
3再看代价复制延迟、一致性、跨库查询、缓存雪崩、服务治理复杂度。
4最后会答题选择题抓概念边界，简答题写定义和区别，设计题按层组织。

高并发链路

单服务器扛不住 → 先做单机优化 → 加负载均衡把请求分给多台服务器 → 用缓存减少重复读数据库 → 用消息队列把非关键流程异步化 → 用分布式服务拆业务。

记忆句：高并发先分流，再缓存，再异步，再拆服务。

数据变大链路

单库单表变慢 → 读写分离缓解读压力 → 主从复制带来复制延迟 → 分库分表降低单库单表数据量 → 水平切分需要路由 → 跨库事务和 Join 变复杂。

记忆句：数据大了要拆，拆了就要路由，路由后事务和查询会变难。

高可用链路

机器一定会故障 → 主备/主从保存副本 → 负载均衡和服务注册发现健康节点 → 集群容错失败切换 → 容器调度负责拉起和扩容。

记忆句：高可用不是不坏，而是坏了能发现、能切换、能恢复。

数据正确链路

支付、订单不能重复或错乱 → 幂等防重复请求 → 状态机限制状态流转 → 关键读写走主库 → 同组数据尽量同分片 → 日志、补偿、对账处理异常。

记忆句：正确性靠幂等、状态机、主库读写、同组同分片和对账。

边看网站边翻资料

每一章只抓三个东西：问题、方案、代价

1.1/1.2 系统体系结构概述

先看懂：架构不是代码细节，而是构件、连接件、拓扑、约束和质量。质量属性靠结构设计来支撑。

记住：架构 = 构件 + 连接件 + 拓扑结构 + 约束 + 质量。中间件 = 屏蔽异构性、实现互操作、共性凝练和复用。

答题用：中间件作用、质量属性、4+1 视图、设计题开头的质量目标。

2.1 软件设计模式概述

先看懂：设计模式是在局部设计里降低耦合、提高复用。观察者模式解释发布订阅，MVC 解释表示层的分工。

记住：观察者/发布订阅强调触发和通知；MVC 强调 Model、View、Controller 分离。

答题用：事件系统、MVC 设计、设计模式分类。

3.1 计算层的软件架构技术挑战

先看懂：计算层解决“请求处理能力”的问题。规模变大后，要从集中应用走向分布式服务。

记住：高性能看响应时间、TPS、QPS；高扩展靠垂直扩展和水平扩展；高可用看故障和恢复。

答题用：设计题里的计算层总述、高性能/高扩展/高可用定义。

3.3 负载均衡

先看懂：负载均衡本质是把请求分给多台机器，解决单服务器性能上限。

记住：DNS 简单但更新慢；硬件强但贵；软件便宜灵活但性能一般。算法有轮询、加权轮询、负载最低、性能最优、Hash。

答题用：高并发入口层设计、负载均衡选择题、综合题计算层。

3.4 消息队列

先看懂：消息队列不是为了多一个组件，而是为了异步、削峰、解耦。

记住：同步通信耦合紧；异步通信并行度高。时间解耦是不必同一时间运行，空间解耦是不必知道对方在哪里。

答题用：消息中间件、事件驱动、发布订阅、异步处理设计。

3.5 分布式服务框架

先看懂：服务拆多以后，要有人负责注册、发现、路由、容错、治理和调用。

记住：请求链路可以想成：API 网关 → 服务发现/注册中心 → 服务路由 → 服务调用 → 集群容错 → 数据层。幂等解决重复请求副作用。

答题用：微服务、API 网关、服务治理、支付/订单的幂等性。

4.2 数据读写与主从分离

先看懂：数据库压力大时，把读写分散到不同节点；但复制不是瞬间完成，所以会有延迟。

记住：主备简单但备机不服务；主从能读扩展但有复制延迟；主主都能写但冲突复杂。关键业务写后读要读主库。

答题用：主备/主从区别、复制延迟、数据集中/分散集群。

4.3 数据分库分表

先看懂：分库分表解决单库单表数据量和访问压力过大的问题。

记住：垂直切分偏业务拆分，水平切分偏性能扩展。客户端分片可在应用层、JDBC、ORM 中实现。拆分后麻烦是事务、Join、排序分页、扩容迁移。

答题用：垂直/水平分表比较、客户端分片、支付数据一致性设计。

4.4 数据缓存

先看懂：缓存把热点数据放到更快、更近的位置，减少后端压力。

记住：缓存类型有本地、分布式、反向代理、CDN。清理策略有 FIFO、LFU、LRU、过期时间。问题有一致性、穿透、并发、雪崩、热点。

答题用：缓存简答题、清理策略选择题、设计题里的热点访问优化。

2020C《软件架构与中间件》逐题定位与解析

说明：下面每道题的“资料位置”都按纸质资料里的章节标题写，不需要再换算段落编号。复习时先读上面的理解链路，再用逐题解析练翻找和答题。

一、多项选择题

1. 大型电商网站的架构进化

答案：A B C

资料位置：第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战（计算复杂性、应用从集中走向分布式、业务拆分、服务治理、扩展性、高可用性）；第三章 → 3.3 负载均衡；第四章：数据层的软件架构技术 → 数据层非功能需求与架构技术、4.4 数据缓存。

解析：大型电商网站面对用户和业务扩展，典型演进路线是通过负载均衡利用多台服务器能力，通过缓存缓解热点访问和数据库压力，通过分布式服务拆分业务并提高扩展性。把 Java 全部改成 C++ 不是架构演进的通用手段，只是实现语言替换，不能直接解决架构扩展问题。

2. 事件系统风格特点

答案：A C D

资料位置：2 软件设计模式基础 → 行为型模式 → 观察者模式（发布-订阅/模型-视图、抽象耦合、触发机制）；第三章：计算机软件架构技术 → 3.4 消息队列（MOM 形式：发布订阅、事件驱动）；第三章 → 3.5 分布式服务框架 → 微服务架构的服务集成 → 消息代理方式。

解析：事件系统/发布订阅的核心是发送者和接收者解耦，事件触发者不必知道有哪些订阅者，构件通过事件发布、注册、订阅建立联系。选项 B 说执行顺序取决于订阅先后，这不是事件系统风格的必然语义，尤其在异步事件和消息系统中通常不能依赖订阅顺序。

3. 过滤器对数据执行的变换

答案：A B C

资料位置：资料未直接系统讲“管道-过滤器”风格；可弱参考 2 软件设计模式基础 → 行为型模式 → 访问者模式的注意事项（出现“过滤器”），以及第三章：计算机软件架构技术 → 3.4 消息队列 → 队列管理器功能（过滤、规则引擎）。基础架构风格知识需要补在资料旁边。

解析：过滤器的本质是对输入数据流做转换，可以增加额外数据、删减输入数据，也可以把多个来源的数据合并后输出。保存数据属于存储/持久化职责，不是过滤器“变换数据”的典型操作。

4. 分层系统的架构元素

答案：A B

资料位置：1 系统体系结构的内涵及要点 → 1.1 系统体系结构概述（架构共性：构件、连接件、物理分布、约束、质量；SA 构件和连接件定义）；第三章：计算机软件架构技术 → 3.4 消息队列 → OSI 模型的七个层次及其功能。资料未直接展开“分层系统风格”。

解析：分层系统的构件是各层内部的模块或构件，连接件通常是层间调用接口、协议或交互约束，HTTP 这类协议可作为连接件例子。分层拓扑一般是相邻层依赖或受限跨层，不是星型结构。分层是逻辑组织方式，不要求物理部署必须集中，完全可以跨机器或跨地点部署。

5. 并行范式类型

答案：A B C D

资料位置：1 系统体系结构的内涵及要点 → 1.1 系统体系结构概述（并行处理机结构、流水线结构）；第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战（计算模式的变革：单机多核、众核、分布式计算）；第三章 → 3.5 分布式服务框架 → 服务调用（并行调用）。资料未直接出现 Master-Worker、SPMD、预测执行。

解析：Master-Worker、SPMD、流水线和预测执行都属于常见并行/并发计算范式。Master-Worker 用主节点分派任务给工作节点，SPMD 是单程序多数据，流水线把处理拆成连续阶段，预测执行通过提前执行可能路径提升吞吐或降低等待。

二、简答题

1. 软件中间件的作用

资料位置：1 系统体系结构的内涵及要点 → 1.2 系统体系结构概述 → 系统=服务集群+中间件、软件中间件的作用、中间件意义、中间件分类。

答题要点：中间件位于应用软件和系统软件之间，用于屏蔽底层操作系统、网络通信、平台和接口差异，为分布式应用提供公共服务。其核心作用可概括为：屏蔽异构性、实现互操作、凝练和复用共性能力。进一步展开，可以写为：降低分布式系统开发复杂度，管理通信和资源共享，提高高可靠性、高可用性和灵活性，支持应用集成、消息通信、服务集成、数据集成和业务共性抽象。

2. MVC 风格与三层 C/S 风格异同

资料位置：2 软件设计模式基础 → 2.1 软件设计模式概述 → J2EE 模式（MVC 模式）；1 系统体系结构的内涵及要点 → 软件架构设计的模型（4+1 视图模型）；第三章：计算机软件架构技术 → Docker 引擎 / Docker 架构（C/S 结构示例）。资料未直接展开 MVC 与三层 C/S 的比较。

答题要点：二者都体现分离关注点和降低耦合的思想，都有利于维护、扩展、复用和多人协作。MVC 把应用划分为 Model、View、Controller：Model 封装业务数据和业务逻辑，View 负责展示，Controller 处理输入并协调模型和视图。三层 C/S 通常划分为表示层、业务逻辑层、数据访问/数据层，强调客户端、应用服务器、数据库服务器之间的逻辑或物理部署关系。差异在于，MVC 更偏设计模式或应用内部结构，尤其常用于表示层/交互层；三层 C/S 更偏系统架构和部署结构。MVC 可以运行在三层 C/S 的某一层或跨层实现，二者不是同一维度的完全替代关系。

3. 对称集群与非对称集群的主要区别

资料位置：资料未直接出现“对称/非对称集群”；可参考第三章：计算机软件架构技术 → 3.3 负载均衡（多服务器共同服务），以及第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离（主备复制、主从复制、主主复制、数据集中/分散集群）。

答题要点：对称集群中各节点地位基本相同，通常都可以对外提供同类服务，任务可通过负载均衡分配到任意可用节点，典型目标是提高吞吐、扩展性和容错性。非对称集群中节点角色不同，常见形式是主备、主从、调度节点/工作节点，主节点负责写入、调度或状态决策，备/从节点负责备份、读请求或故障接管。主要区别是节点角色是否等价、请求是否能发给任意节点、故障切换和一致性处理复杂度不同。

4. 数据集中集群与数据分散集群区别

资料位置：第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离 → 数据集群 → 数据集中集群、数据分散集群、集中 VS 分散。

答题要点：数据集中集群也就是一主多备/从，数据写入只能到主机，读操作可以根据主备或主从架构灵活安排；复杂点在于多通道复制、一致性检查、主机状态判断和故障后重新选主。数据分散集群由多个服务器共同存储数据，每台服务器负责一部分数据，同时备份一部分数据；复杂点在于数据分配算法、均衡性、容错性和扩容迁移。集中式适合数据量不大、机器数量不多的场景；分散式适合数据量巨大、集群规模大的场景。

5. 垂直分表与水平分表比较

资料位置：第四章：数据层的软件架构技术 → 4.3 数据分库分表 → 分库分表的基本定义（垂直拆分、水平拆分）、切分方法（垂直切分、水平切分及优缺点）、水平切分的路由过程与分片维度。

答题要点：垂直分表按业务或字段维度拆分，一张表按业务含义、冷热程度、字段访问频率拆成结构不同的多张表，重点是业务边界清晰和职责拆分。优点是拆分规则明确、便于动静/冷热分离、管理简单；缺点是跨表 Join 和事务变复杂，仍可能受单业务库瓶颈限制。水平分表按行拆分，依据哈希、时间等分片规则把同结构数据分散到多个表或库中，每张表结构相同、只保存一部分数据。优点是降低单表数据量、提升负载能力和稳定性；缺点是跨分片 Join、排序、分页、分布式事务和扩容迁移困难。共同问题包括分布式事务、跨节点 Join、合并排序分页和多数据源管理。

6. 缓存可能带来的问题

资料位置：第四章：数据层的软件架构技术 → 4.4 数据缓存 → 数据缓存的基本清洗策略 → 缓存的问题（数据一致性、缓存穿透、缓存并发、缓存雪崩、缓存热点）。

答题要点：缓存会带来数据一致性问题，即缓存与数据库或源数据之间可能不同步。缓存穿透指大量查询不存在的 key 导致请求绕过缓存直达数据库，可通过缓存空值、校验非法请求等方式缓解。缓存并发指热点 key 失效时大量请求同时访问数据库并回写缓存，导致应用和数据库压力突增。缓存雪崩指缓存服务器重启或大量缓存同一时间失效，后端数据库瞬时承压。缓存热点指极少数热点数据被高并发访问，缓存服务器本身压力过大。

三、设计题

1. 早期某宝网：单服务器 Web 访问能力与 MVC 设计

资料位置：1 系统体系结构的内涵及要点 → 软件架构设计的模型（4+1 视图模型）；2 软件设计模式基础 → J2EE 模式（MVC 模式）；第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战（单机、扩展性、性能指标）；第四章：数据层的软件架构技术 → 单机 MySQL（缓存、主从读写分离演进背景）和 4.4 数据缓存。

答题框架：

用例视图：用户通过浏览器完成注册登录、商品浏览/搜索、商品详情、购物车、下单、支付入口、物流查询等核心用例。早期系统可先保留核心交易链路，非核心功能如直播购物、复杂推荐可弱化或异步化。

逻辑视图：采用 MVC。View 是 HTML/CSS/JS 页面和模板，负责展示商品、订单、购物车等页面；Controller 接收 HTTP 请求，做参数校验、会话处理和路由分发；Model 包含商品、用户、订单、支付记录等领域对象，以及 Service/DAO 对业务规则和数据库访问的封装。

开发视图：按模块拆分为 Web/Controller、Service、DAO、Domain、View 模板、Static 静态资源、配置和日志模块。这样可以在单服务器内保持清晰边界，为以后拆成分布式服务留下接口。

进程视图：浏览器请求进入 Web 容器或 Nginx，静态资源由 Nginx 直接返回，动态请求进入 Controller，再调用 Service、DAO 和数据库。日志、消息通知、推荐更新等非关键流程可异步处理，避免阻塞交易主流程。

物理视图：一台服务器上部署 Web 服务器、应用服务、数据库和本地缓存。单机优化包括：启用 HTTP 静态资源缓存与压缩；数据库建索引、SQL 优化、连接池；使用本地缓存缓存热点商品、分类、配置；减少重复 I/O；合理配置线程池；把图片、CSS、JS 等静态内容交给 Nginx 或反向代理缓存处理。这样能在单服务器条件下尽量提高吞吐和响应速度。

2. 全球 10 亿用户可用的支付子系统：保障数据一致性的架构

资料位置：1 系统体系结构的内涵及要点 → 部分软件质量因素及其对策（性能、安全性、健壮性/可用性）；第三章：计算机软件架构技术 → 3.5 分布式服务框架 → 幂等性；第四章：数据层的软件架构技术 → 4.2 数据读写与主从分离（复制延迟、主备/主从/主主、数据集群）；第四章 → 4.3 数据分库分表（客户端分片、支持事务的分布式数据库、分布式事务问题、同组数据跨库问题）。

设计理念：支付子系统优先保证正确性和一致性，再在一致性边界内做性能和扩展。入口层采用 API 网关和负载均衡接入全球用户，但核心支付写操作必须路由到确定的支付分区或账户分片。每个分片内部采用主/Leader + 多副本结构，核心写入只到主节点或 Leader，并通过同步复制、事务日志或共识机制确认后再返回成功。关键读请求读主节点，非关键查询可读从节点或缓存。

数据组织：按用户账户、商户、订单号或支付流水进行分库分表，同一笔支付强相关的数据尽量落在同一分片，利用本地事务获得强一致性。确实跨库的场景使用分布式事务、TCC/事务消息或支持事务的分布式数据库，并保留支付流水、状态机和对账机制。“第四章：数据层的软件架构技术 → 4.3 数据分库分表 → 同组数据跨库问题”这一处原则很关键：同组数据尽量放在同一台数据库服务器上，以便使用本地事务和自治能力。

一致性保障理由：第一，写操作单点归属到主节点或分片 Leader，避免多主并发写冲突。第二，支付请求带全局唯一流水号/订单号，用去重表或唯一索引实现幂等，防止重复付款、重复扣款。第三，支付状态按状态机推进，只允许合法状态转移。第四，跨库更新时使用分布式事务或可靠消息，失败后可重试、补偿和对账。第五，对主从复制延迟保持保守策略，支付后的关键读直接读主，避免“刚写完读不到”的问题。第六，对账和审计日志用于发现和修复最终不一致。

3. 基于 ATAM 的支付子系统效用树与改进策略

资料位置：资料未直接出现 ATAM/效用树；可用 1 系统体系结构的内涵及要点 → 质量属性、架构对策、测试与评审、4+1 视图模型；第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战（性能、响应时间、并发、TPS/QPS、扩展性、高可用性）；第三章 → 3.5 分布式服务框架 → 幂等性；第四章：数据层的软件架构技术 → 读写分离、数据集群、数据缓存相关风险。

效用树示例：

支付子系统总体效用
├─ 性能
│  ├─ 高峰期支付请求 TPS/QPS 达标
│  └─ 95/99 分位响应时间满足业务目标
├─ 可用性
│  ├─ 单机/单节点故障后自动切换
│  └─ 机房或区域故障时核心支付能力不中断或可降级
├─ 一致性/正确性
│  ├─ 同一订单重复请求不重复扣款
│  ├─ 账户余额、订单状态、支付流水一致
│  └─ 跨库交易失败时可补偿、可对账
├─ 安全性
│  ├─ 未授权请求不能发起支付
│  ├─ 关键数据传输和存储加密
│  └─ 防重放、防篡改、防刷接口
├─ 可扩展性
│  ├─ 用户和交易量增长时可增加服务节点
│  └─ 数据容量增长时可扩容分片
└─ 可维护/可观测性
   ├─ 支付链路可追踪
   └─ 异常交易可定位、可审计、可回放

改进策略：如果评审发现性能风险，优先检查负载均衡、热点数据缓存、数据库索引、读写分离、异步化和分库分表方案。若可用性不足，增加主备/主从、自动倒换、健康检查、故障转移和灾备。若一致性风险高，收紧支付核心链路，关键读写走主节点，使用幂等、状态机、分布式事务/事务消息、同组数据同分片和对账补偿。若安全风险高，增加统一网关鉴权、加密、签名、防重放、限流和审计。若测试结论与评审风险不一致，应以风险场景补充压力测试、故障注入测试、一致性测试和安全测试；风险关闭前不应贸然上线核心支付链路。

四、综合应用题：刷脸支付人脸验证服务系统

1. 计算层如何实现高性能、高扩展、高可用

资料位置：第三章：计算机软件架构技术 → 3.1 计算层的软件架构技术挑战；3.3 负载均衡；3.4 消息队列（通信模型、MOM、异步通信）；3.5 分布式服务框架（集群容错、服务调用、API 网关、消息代理）；Docker 调度工具（容器调度、扩容、故障转移）。

答题要点：单机层面，对人脸检测、特征提取、比对算法做性能优化，使用线程池、连接池、本地缓存、批处理或硬件加速，减少不必要的 I/O 和序列化。服务设计为无状态或少状态，便于水平扩展。负载均衡层面，全球接入可用 DNS 做地理级调度，区域内使用 F5/LVS/Nginx 等集群级和机器级负载均衡，结合健康检查、加权轮询、负载最低优先或响应时间优先算法。高可用层面，多实例部署，服务注册发现，失败自动切换，关键服务多副本，容器编排系统负责拉起、扩容和故障迁移。消息处理层面，核心 2 秒验证链路保持同步短路径，日志、风控分析、模型更新、通知和离线训练等放入消息队列异步处理，提高主链路吞吐并实现解耦。

2. 数据层如何提供快速、稳定的数据访问

资料位置：第四章：数据层的软件架构技术 → 数据层非功能需求与架构技术；4.2 数据读写与主从分离（读写分离、复制延迟、数据集中/分散集群）；4.3 数据分库分表（定义、操作时机、解决方案、垂直/水平切分、路由）；4.4 数据缓存（缓存类型、清洗策略、缓存问题）。

答题要点：分库分表方面，人脸模板、用户身份、设备、交易验证流水等数据按业务做垂直拆分；用户人脸模板和验证流水按用户 ID、区域或哈希做水平拆分，降低单库单表压力。对全球海量用户，可采用数据分散集群以获得更好的可伸缩性，并用分片路由定位用户数据。主从分离方面，核心写入如注册人脸模板、更新账户状态写主库，查询和非关键读取走从库；刚写后的关键读必须读主库，避免复制延迟造成读不到最新数据。缓存方面，对热点用户特征、设备配置、风控规则、会话令牌等使用 Redis/Memcached 等分布式缓存；对静态资源和模型配置可结合 CDN/反向代理缓存。缓存设计要处理一致性、穿透、并发、雪崩和热点问题，比如缓存空值、互斥重建、过期时间随机化、热点 key 拆分和限流。

3. 如何为多终端提供友好、快捷展示

资料位置：资料未直接命中表示层细节；可弱参考 1 系统体系结构的内涵及要点 → 部分软件质量因素及其对策（易用性：统一风格界面、定制）；目录中的“5 表示层的设计基础”；第三章：计算机软件架构技术 → 3.5 分布式服务框架 → API 网关方式。

答题要点：多终端包括手机端、POS 机、自助设备等，应通过统一 API 网关提供一致接口，同时按终端能力适配页面和交互。异步内容加载方面，先加载验证主流程必需内容，如摄像头授权、取景框、提示语和验证按钮，非关键内容如广告、帮助、活动、历史记录延后加载；网络慢时展示轻量页面和明确状态反馈。自适应适配方面，根据屏幕尺寸、摄像头能力、系统版本、网络状态和输入方式选择布局与交互，保证按钮、提示、取景区域在不同设备上清晰可用。为了满足 2 秒应答，应减少首屏资源体积，缓存静态资源，本地预校验图像质量，将复杂分析放到后端或异步链路，并在失败时给出快速重试路径。
