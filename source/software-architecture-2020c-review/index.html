一、多项选择题

1. 大型电商网站的架构进化

答案：A B C

资料位置：P112-P125（计算层挑战、高性能、高扩展、高可用、垂直/水平扩展），P127-P145（负载均衡），P117-P120（应用从集中走向分布式、服务治理），P363-P366（数据缓存），P295（数据层架构技术）。

解析：大型电商网站面对用户和业务扩展，典型演进路线是通过负载均衡利用多台服务器能力，通过缓存缓解热点访问和数据库压力，通过分布式服务拆分业务并提高扩展性。把 Java 全部改成 C++ 不是架构演进的通用手段，只是实现语言替换，不能直接解决架构扩展问题。

2. 事件系统风格特点

答案：A C D

资料位置：P092-P098（观察者/发布订阅，抽象耦合、触发机制、异步注意事项），P157（MOM 形式包含发布订阅、事件驱动），P216-P217（通过队列和订阅主题实现发布订阅、用消息中间件解耦服务）。

解析：事件系统/发布订阅的核心是发送者和接收者解耦，事件触发者不必知道有哪些订阅者，构件通过事件发布、注册、订阅建立联系。选项 B 说执行顺序取决于订阅先后，这不是事件系统风格的必然语义，尤其在异步事件和消息系统中通常不能依赖订阅顺序。

3. 过滤器对数据执行的变换

答案：A B C

资料位置：资料未直接系统讲“管道-过滤器”风格；弱命中 P108（出现“过滤器”），P168（消息代理可做过滤）。基础架构风格知识需要补在资料旁边。

解析：过滤器的本质是对输入数据流做转换，可以增加额外数据、删减输入数据，也可以把多个来源的数据合并后输出。保存数据属于存储/持久化职责，不是过滤器“变换数据”的典型操作。

4. 分层系统的架构元素

答案：A B

资料位置：P004-P007（架构共性：构件、连接件、物理分布、约束、质量；构件和连接件定义），P152（OSI 七层是分层思想例子）。资料未直接展开“分层系统风格”。

解析：分层系统的构件是各层内部的模块或构件，连接件通常是层间调用接口、协议或交互约束，HTTP 这类协议可作为连接件例子。分层拓扑一般是相邻层依赖或受限跨层，不是星型结构。分层是逻辑组织方式，不要求物理部署必须集中，完全可以跨机器或跨地点部署。

5. 并行范式类型

答案：A B C D

资料位置：P004（并行处理机、流水线结构），P113（单机多核、众核、分布式计算模式），P199（并行调用）。资料未直接出现 Master-Worker、SPMD、预测执行。

解析：Master-Worker、SPMD、流水线和预测执行都属于常见并行/并发计算范式。Master-Worker 用主节点分派任务给工作节点，SPMD 是单程序多数据，流水线把处理拆成连续阶段，预测执行通过提前执行可能路径提升吞吐或降低等待。

二、简答题

1. 软件中间件的作用

资料位置：P019-P022。

答题要点：中间件位于应用软件和系统软件之间，用于屏蔽底层操作系统、网络通信、平台和接口差异，为分布式应用提供公共服务。其核心作用可概括为：屏蔽异构性、实现互操作、凝练和复用共性能力。进一步展开，可以写为：降低分布式系统开发复杂度，管理通信和资源共享，提高高可靠性、高可用性和灵活性，支持应用集成、消息通信、服务集成、数据集成和业务共性抽象。

2. MVC 风格与三层 C/S 风格异同

资料位置：P027（MVC 属于 J2EE/表示层设计模式），P023（4+1 视图可用于架构描述），P228/P235（C/S 结构例子，Docker Client/Server）。资料未直接展开 MVC 与三层 C/S 的比较。

答题要点：二者都体现分离关注点和降低耦合的思想，都有利于维护、扩展、复用和多人协作。MVC 把应用划分为 Model、View、Controller：Model 封装业务数据和业务逻辑，View 负责展示，Controller 处理输入并协调模型和视图。三层 C/S 通常划分为表示层、业务逻辑层、数据访问/数据层，强调客户端、应用服务器、数据库服务器之间的逻辑或物理部署关系。差异在于，MVC 更偏设计模式或应用内部结构，尤其常用于表示层/交互层；三层 C/S 更偏系统架构和部署结构。MVC 可以运行在三层 C/S 的某一层或跨层实现，二者不是同一维度的完全替代关系。

3. 对称集群与非对称集群的主要区别

资料位置：资料未直接出现“对称/非对称集群”；可参考 P127-P145（负载均衡下多服务器共同服务），P300-P313（主备、主从、主主复制），P315-P317（集中/分散数据集群）。

答题要点：对称集群中各节点地位基本相同，通常都可以对外提供同类服务，任务可通过负载均衡分配到任意可用节点，典型目标是提高吞吐、扩展性和容错性。非对称集群中节点角色不同，常见形式是主备、主从、调度节点/工作节点，主节点负责写入、调度或状态决策，备/从节点负责备份、读请求或故障接管。主要区别是节点角色是否等价、请求是否能发给任意节点、故障切换和一致性处理复杂度不同。

4. 数据集中集群与数据分散集群区别

资料位置：P315-P317。

答题要点：数据集中集群也就是一主多备/从，数据写入只能到主机，读操作可以根据主备或主从架构灵活安排；复杂点在于多通道复制、一致性检查、主机状态判断和故障后重新选主。数据分散集群由多个服务器共同存储数据，每台服务器负责一部分数据，同时备份一部分数据；复杂点在于数据分配算法、均衡性、容错性和扩容迁移。集中式适合数据量不大、机器数量不多的场景；分散式适合数据量巨大、集群规模大的场景。

5. 垂直分表与水平分表比较

资料位置：P324-P327（分库分表定义、垂直/水平拆分），P341-P345（垂直/水平切分及优缺点），P346-P347（水平切分路由和分片维度）。

答题要点：垂直分表按业务或字段维度拆分，一张表按业务含义、冷热程度、字段访问频率拆成结构不同的多张表，重点是业务边界清晰和职责拆分。优点是拆分规则明确、便于动静/冷热分离、管理简单；缺点是跨表 Join 和事务变复杂，仍可能受单业务库瓶颈限制。水平分表按行拆分，依据哈希、时间等分片规则把同结构数据分散到多个表或库中，每张表结构相同、只保存一部分数据。优点是降低单表数据量、提升负载能力和稳定性；缺点是跨分片 Join、排序、分页、分布式事务和扩容迁移困难。共同问题包括分布式事务、跨节点 Join、合并排序分页和多数据源管理。

6. 缓存可能带来的问题

资料位置：P366-P367。

答题要点：缓存会带来数据一致性问题，即缓存与数据库或源数据之间可能不同步。缓存穿透指大量查询不存在的 key 导致请求绕过缓存直达数据库，可通过缓存空值、校验非法请求等方式缓解。缓存并发指热点 key 失效时大量请求同时访问数据库并回写缓存，导致应用和数据库压力突增。缓存雪崩指缓存服务器重启或大量缓存同一时间失效，后端数据库瞬时承压。缓存热点指极少数热点数据被高并发访问，缓存服务器本身压力过大。

三、设计题

1. 早期某宝网：单服务器 Web 访问能力与 MVC 设计

资料位置：P023（4+1 视图），P027（MVC 属于表示层/J2EE 模式），P112-P125（单机/扩展/性能指标），P363-P366（缓存），P293（单机 MySQL、缓存与主从演进背景）。

答题框架：

用例视图：用户通过浏览器完成注册登录、商品浏览/搜索、商品详情、购物车、下单、支付入口、物流查询等核心用例。早期系统可先保留核心交易链路，非核心功能如直播购物、复杂推荐可弱化或异步化。

逻辑视图：采用 MVC。View 是 HTML/CSS/JS 页面和模板，负责展示商品、订单、购物车等页面；Controller 接收 HTTP 请求，做参数校验、会话处理和路由分发；Model 包含商品、用户、订单、支付记录等领域对象，以及 Service/DAO 对业务规则和数据库访问的封装。

开发视图：按模块拆分为 Web/Controller、Service、DAO、Domain、View 模板、Static 静态资源、配置和日志模块。这样可以在单服务器内保持清晰边界，为以后拆成分布式服务留下接口。

进程视图：浏览器请求进入 Web 容器或 Nginx，静态资源由 Nginx 直接返回，动态请求进入 Controller，再调用 Service、DAO 和数据库。日志、消息通知、推荐更新等非关键流程可异步处理，避免阻塞交易主流程。

物理视图：一台服务器上部署 Web 服务器、应用服务、数据库和本地缓存。单机优化包括：启用 HTTP 静态资源缓存与压缩；数据库建索引、SQL 优化、连接池；使用本地缓存缓存热点商品、分类、配置；减少重复 I/O；合理配置线程池；把图片、CSS、JS 等静态内容交给 Nginx 或反向代理缓存处理。这样能在单服务器条件下尽量提高吞吐和响应速度。

2. 全球 10 亿用户可用的支付子系统：保障数据一致性的架构

资料位置：P018（性能/安全/健壮性对策），P203-P207（幂等性和重复交易问题），P295-P299（读写分离、复制延迟和关键业务读主机），P300-P317（主备、主从、主主、集中/分散数据集群），P331-P337（分片、支持事务的分布式数据库），P354-P355（分布式事务、同组数据跨库问题）。

设计理念：支付子系统优先保证正确性和一致性，再在一致性边界内做性能和扩展。入口层采用 API 网关和负载均衡接入全球用户，但核心支付写操作必须路由到确定的支付分区或账户分片。每个分片内部采用主/Leader + 多副本结构，核心写入只到主节点或 Leader，并通过同步复制、事务日志或共识机制确认后再返回成功。关键读请求读主节点，非关键查询可读从节点或缓存。

数据组织：按用户账户、商户、订单号或支付流水进行分库分表，同一笔支付强相关的数据尽量落在同一分片，利用本地事务获得强一致性。确实跨库的场景使用分布式事务、TCC/事务消息或支持事务的分布式数据库，并保留支付流水、状态机和对账机制。资料 P355 的原则很关键：同组数据尽量放在同一台数据库服务器上，以便使用本地事务和自治能力。

一致性保障理由：第一，写操作单点归属到主节点或分片 Leader，避免多主并发写冲突。第二，支付请求带全局唯一流水号/订单号，用去重表或唯一索引实现幂等，防止重复付款、重复扣款。第三，支付状态按状态机推进，只允许合法状态转移。第四，跨库更新时使用分布式事务或可靠消息，失败后可重试、补偿和对账。第五，对主从复制延迟保持保守策略，支付后的关键读直接读主，避免“刚写完读不到”的问题。第六，对账和审计日志用于发现和修复最终不一致。

3. 基于 ATAM 的支付子系统效用树与改进策略

资料位置：资料未直接出现 ATAM/效用树；可用 P013-P018（质量属性和架构对策），P014（测试与评审），P023（架构视图），P121-P125（性能、响应时间、并发、QPS/TPS、扩展性、高可用性指标），P203-P207（幂等性），P295-P299/P315-P317/P366-P367（数据与缓存相关风险）。

效用树示例：

支付子系统总体效用
├─ 性能
│  ├─ 高峰期支付请求 TPS/QPS 达标
│  └─ 95/99 分位响应时间满足业务目标
├─ 可用性
│  ├─ 单机/单节点故障后自动切换
│  └─ 机房或区域故障时核心支付能力不中断或可降级
├─ 一致性/正确性
│  ├─ 同一订单重复请求不重复扣款
│  ├─ 账户余额、订单状态、支付流水一致
│  └─ 跨库交易失败时可补偿、可对账
├─ 安全性
│  ├─ 未授权请求不能发起支付
│  ├─ 关键数据传输和存储加密
│  └─ 防重放、防篡改、防刷接口
├─ 可扩展性
│  ├─ 用户和交易量增长时可增加服务节点
│  └─ 数据容量增长时可扩容分片
└─ 可维护/可观测性
   ├─ 支付链路可追踪
   └─ 异常交易可定位、可审计、可回放

改进策略：如果评审发现性能风险，优先检查负载均衡、热点数据缓存、数据库索引、读写分离、异步化和分库分表方案。若可用性不足，增加主备/主从、自动倒换、健康检查、故障转移和灾备。若一致性风险高，收紧支付核心链路，关键读写走主节点，使用幂等、状态机、分布式事务/事务消息、同组数据同分片和对账补偿。若安全风险高，增加统一网关鉴权、加密、签名、防重放、限流和审计。若测试结论与评审风险不一致，应以风险场景补充压力测试、故障注入测试、一致性测试和安全测试；风险关闭前不应贸然上线核心支付链路。

四、综合应用题：刷脸支付人脸验证服务系统

1. 计算层如何实现高性能、高扩展、高可用

资料位置：P112-P125（计算层挑战、性能/扩展/高可用指标），P127-P145（负载均衡类型、典型架构、算法），P153-P164（通信模型、MOM、异步通信），P198-P199（集群容错和同步/异步/并行调用），P215-P216（API 网关、消息代理），P243-P265（容器调度、扩容、故障转移）。

答题要点：单机层面，对人脸检测、特征提取、比对算法做性能优化，使用线程池、连接池、本地缓存、批处理或硬件加速，减少不必要的 I/O 和序列化。服务设计为无状态或少状态，便于水平扩展。负载均衡层面，全球接入可用 DNS 做地理级调度，区域内使用 F5/LVS/Nginx 等集群级和机器级负载均衡，结合健康检查、加权轮询、负载最低优先或响应时间优先算法。高可用层面，多实例部署，服务注册发现，失败自动切换，关键服务多副本，容器编排系统负责拉起、扩容和故障迁移。消息处理层面，核心 2 秒验证链路保持同步短路径，日志、风控分析、模型更新、通知和离线训练等放入消息队列异步处理，提高主链路吞吐并实现解耦。

2. 数据层如何提供快速、稳定的数据访问

资料位置：P295（数据层非功能需求与架构技术），P298-P299（读写分离与复制延迟），P315-P317（数据集中/分散集群），P319-P347（分库分表定义、时机、方案、垂直/水平切分、路由），P363-P367（缓存及缓存问题）。

答题要点：分库分表方面，人脸模板、用户身份、设备、交易验证流水等数据按业务做垂直拆分；用户人脸模板和验证流水按用户 ID、区域或哈希做水平拆分，降低单库单表压力。对全球海量用户，可采用数据分散集群以获得更好的可伸缩性，并用分片路由定位用户数据。主从分离方面，核心写入如注册人脸模板、更新账户状态写主库，查询和非关键读取走从库；刚写后的关键读必须读主库，避免复制延迟造成读不到最新数据。缓存方面，对热点用户特征、设备配置、风控规则、会话令牌等使用 Redis/Memcached 等分布式缓存；对静态资源和模型配置可结合 CDN/反向代理缓存。缓存设计要处理一致性、穿透、并发、雪崩和热点问题，比如缓存空值、互斥重建、过期时间随机化、热点 key 拆分和限流。

3. 如何为多终端提供友好、快捷展示

资料位置：资料未直接命中表示层细节；弱相关 P018（易用性对策：统一风格界面、定制），P001（目录提到表示层设计基础），P215（API 网关统一对外接口）。

答题要点：多终端包括手机端、POS 机、自助设备等，应通过统一 API 网关提供一致接口，同时按终端能力适配页面和交互。异步内容加载方面，先加载验证主流程必需内容，如摄像头授权、取景框、提示语和验证按钮，非关键内容如广告、帮助、活动、历史记录延后加载；网络慢时展示轻量页面和明确状态反馈。自适应适配方面，根据屏幕尺寸、摄像头能力、系统版本、网络状态和输入方式选择布局与交互，保证按钮、提示、取景区域在不同设备上清晰可用。为了满足 2 秒应答，应减少首屏资源体积，缓存静态资源，本地预校验图像质量，将复杂分析放到后端或异步链路，并在失败时给出快速重试路径。
