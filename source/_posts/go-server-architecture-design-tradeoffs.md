架构设计不是画复杂图，也不是把所有流行词堆到系统里。架构的核心是在约束里做取舍：哪些地方要强一致，哪些地方能最终一致；哪些链路要低延迟，哪些可以异步；哪些模块现在该拆，哪些应该继续留在单体里。

好的架构能解释“为什么这样设计”。差的架构通常只说“大家都这么做”。

## 架构设计先问什么

设计系统前，先问清楚：

- 业务目标是什么；
- 核心用户路径是什么；
- 峰值流量多少；
- 数据规模会怎么增长；
- 哪些操作不能错；
- 哪些功能可以降级；
- 团队有多少人维护；
- 未来最可能变化的地方在哪里。

这些答案会直接影响设计。小团队、低流量、需求快速变化时，清晰单体往往比微服务更合适。高流量、多团队、边界稳定时，微服务才更有价值。

## 必须掌握的知识点

### 分层架构

一个实用的服务端分层：

```text
handler / transport
  -> application service
  -> domain
  -> repository / client
```

handler 处理协议，application service 编排流程，domain 表达业务规则，repository/client 访问外部依赖。

分层的目的不是制造目录，而是隔离变化：

- HTTP 改 RPC，不影响业务规则；
- MySQL 换 PostgreSQL，不影响 service；
- 通知从同步改异步，不影响任务状态机；
- 测试业务逻辑时可以替换依赖。

### 领域边界

领域建模要围绕业务概念，而不是数据库表。

比如订单系统里，核心概念可能是：

- 用户；
- 商品；
- 库存；
- 订单；
- 支付；
- 履约；
- 退款；
- 通知。

每个概念都有自己的生命周期和规则。服务拆分时，优先按这些业务能力划边界，而不是按接口文件或表名拆。

### 一致性取舍

不是所有数据都需要强一致。

需要强一致的例子：

- 余额扣减；
- 库存不能超卖；
- 权益不能重复发放；
- 支付状态不能乱跳。

可以最终一致的例子：

- 通知发送；
- 搜索索引；
- 统计报表；
- 用户最近活动；
- 推荐特征。

强一致通常意味着更高耦合和更低吞吐；最终一致需要补偿、重试和状态可见性。架构设计要把这个取舍说清楚。

### 事件驱动和状态机

事件驱动适合解耦系统。例如订单创建后发出 `OrderCreated`：

- 库存服务扣减库存；
- 通知服务发消息；
- 风控服务做检查；
- 数据服务写宽表。

但事件驱动需要配合状态机。否则多个消费者各自修改状态，很容易混乱。

状态机的价值是规定合法流转：

```text
created -> paid -> shipped -> completed
created -> canceled
paid -> refunded
```

任何状态变化都要能解释来源、触发条件和失败补偿。

### 容量设计

架构设计不能只画逻辑图，还要估算容量：

- 日活、峰值 QPS；
- 读写比例；
- 数据增长量；
- 单用户热点；
- 数据库连接数；
- Redis key 数量和内存；
- MQ 消息量和消费能力；
- 下游服务延迟预算。

容量估算不需要一开始完全准确，但要能暴露关键瓶颈。比如订单创建峰值 2000 QPS，库存扣减和支付回调就不能靠单点串行逻辑硬扛。

## 演进路线

一个稳妥路线通常是：

1. 清晰单体：先把业务跑通，边界写清楚；
2. 模块化单体：内部按领域拆包，禁止跨层乱调；
3. 抽出独立服务：只拆边界稳定、扩展需求明确的模块；
4. 补治理能力：服务发现、限流、熔断、trace、发布系统；
5. 事件驱动：把非核心链路异步化；
6. 持续复盘：根据真实瓶颈调整，而不是按想象重构。

过早微服务会把学习成本变成线上成本。服务数量上去了，通信、观测、部署、数据一致性都会变复杂。

## 练习方式

为一个订单系统写设计文档：

- 背景和目标；
- 核心用户路径；
- 服务边界；
- 数据表；
- API 和 RPC；
- 缓存策略；
- MQ 事件；
- 状态机；
- 一致性方案；
- 降级策略；
- 监控指标；
- 容量估算；
- 已拒绝的方案和理由。

写设计文档时，重点不是图多，而是每个选择都有理由。
