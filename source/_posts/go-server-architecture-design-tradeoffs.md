架构这块最容易写虚。画几张图、堆几个词，看起来像回事，但一问“为什么现在要这么做”，就露馅。

我现在更愿意把架构理解成一组取舍记录：为什么拆，为什么不拆；哪里强一致，哪里最终一致；哪里同步返回，哪里丢到消息里慢慢做。

## 先问约束

设计之前先把这些问题写下来：

- 现在有多少流量；
- 团队几个人维护；
- 哪条链路最不能出错；
- 哪些功能可以慢一点；
- 数据会涨到什么量级；
- 未来最容易变的是哪块；
- 出问题时能不能接受人工补偿。

没有这些约束，架构图很容易变成想象力比赛。

## 单体不是原罪

如果业务还在变，团队也不大，清晰单体往往比微服务舒服。

我会先做模块化单体：

```text
handler
service
domain
repository
client
```

目录不是重点，边界才是重点。handler 不写业务，repository 不做流程编排，domain 里放状态和规则。等边界稳定了，再把某一块抽成服务。

过早拆服务，最后很容易得到一堆小仓库和一堆跨服务调用，问题没少，排障成本先涨了。

## 领域边界别按表切

订单、库存、支付、通知，这些是业务能力。不要因为有一张表，就立刻给它拆一个服务。

一个服务应该能说清楚自己负责的事实是什么：

- user-service：用户身份和资料；
- product-service：商品信息；
- inventory-service：库存变化；
- order-service：订单生命周期；
- payment-service：支付结果；
- notification-service：通知投递。

边界清楚以后，接口和数据归属才会清楚。

## 一致性要分等级

不是所有数据都值得强一致。

余额、库存、支付、权益发放，这些错了很难补，应该谨慎设计。

通知、搜索索引、报表、推荐特征，短暂延迟通常可以接受，用消息和补偿更合适。

这个判断要写进设计文档里。否则后面每个人都会按自己的理解改，系统会慢慢长歪。

## 状态机比口头约定可靠

只要业务有状态，就应该画出合法流转。

```text
created -> paid -> shipped -> completed
created -> canceled
paid -> refunded
```

状态机能帮你发现很多问题：取消后还能不能支付，支付后退款走哪条链路，消息重复来时应该忽略还是报错。

## 设计文档怎么写

我会用这种结构：

- 背景；
- 目标和不做什么；
- 关键链路；
- 服务边界；
- 数据表；
- 接口；
- 消息事件；
- 缓存策略；
- 状态机；
- 失败和补偿；
- 监控；
- 被拒绝的方案。

“被拒绝的方案”很重要。它能告诉后面的人：这个坑不是没人想到，而是当时权衡后没选。

## 一个练习

给订单系统写一份设计文档，不写代码也行。重点是把每个选择讲清楚：

- 为什么库存要强一致；
- 为什么通知可以异步；
- 为什么订单服务不直接改支付表；
- 为什么先做单体或为什么要拆服务；
- 回滚时会遇到什么数据兼容问题。

能把这些说清楚，比背多少架构名词更有用。
