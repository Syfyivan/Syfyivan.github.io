## AI 观察

### 1. MCP 的关键变化不是“多了几个功能”，而是协议层把会话责任还给应用

Claude 日报提到 MCP `2026-07-28` 版本的无状态核心、MCP Apps、Tasks、认证加固和弃用策略。MCP 官方说明进一步给出了工程影响：去掉协议层的初始化握手和 `Mcp-Session-Id` 后，远程请求可以落到任意服务实例，普通 HTTP 负载均衡就能工作；工具结果还可以携带 `ttlMs`、`cacheScope`，trace context 也有了明确的传递位置。

这不是把所有应用都变成无状态，而是把“协议隐式保存的状态”变成“业务显式携带的句柄”。购物车、浏览器、长任务等状态仍然存在，只是要通过 `basket_id`、`browser_id` 或 task handle 进入业务参数和可观测链路。对 agent 来说，这让状态更容易审计、重放和跨实例传递；对实现者来说，也意味着旧版依赖 sticky session 或实验性 Tasks API 的客户端需要认真做迁移，而不是只改一个版本号。

### 2. 开放权重争论最终会落到“能否测试、能否撤回、谁承担失控成本”

Claude 日报引用了 Anthropic 的 X 帖文。Anthropic 在正式立场中明确表示不主张一刀切禁止开放权重模型，同时主张对足够强的开放和闭源模型都做发布前安全测试，并把芯片、工业化蒸馏和高风险能力作为更具体的治理对象。Axios 的二级报道也交叉确认了“反对 blanket ban、支持定向控制”的政策边界。

工程上可以把这场争论翻译成一张供应商与运行时矩阵：模型权重是否可取得，数据是否能留在本地，安全策略能否更新，调用是否能被审计，出现高风险行为后能否撤销，以及模型升级会不会改变业务输出。所谓“开放”带来的是可控性和迁移能力，但不自动带来安全；所谓“托管”带来的是集中治理，但也把可用性、价格和供应商策略变成外部依赖。

### 3. 模型安全能力的增长，正在把验证从加分项变成上线门槛

Anthropic 的 Mythos Preview 研究称，模型能够在隔离环境中发现并构造复杂漏洞利用链，并强调要通过 scaffold、容器隔离、人工复核和协调披露来控制风险。这个结论来自模型提供方自己的研究，不能直接当作独立基准，但它给工程团队的信号很清楚：agent 的“完成”不能只看生成了代码，还要看是否在受控环境中验证、留下可复现证据，并且没有越过授权边界。

## 前端 / 服务端 / 客户端工程观察

### 前端：MCP Apps 让工具 UI 进入产品安全面

MCP Apps 允许服务端提供交互式 HTML，由宿主在 sandboxed iframe 中渲染；工具可以提前声明 UI 模板，使宿主能够预取、缓存和做安全审查。前端团队需要把它当作新的第三方运行时边界：检查 iframe 权限、消息来源、资源加载、用户确认和 UI 触发的工具调用是否都走同一条审计链。

验收也应从“截图像不像”升级为“状态、网络和授权是否可证明”。对于 agent 操作浏览器或业务页面，至少固定采集 console、network、关键 DOM/组件状态、错误截图和最终业务断言，避免把渲染问题、接口问题和模型问题混在一起。

### 服务端：无状态协议降低了路由复杂度，却提高了业务状态设计要求

MCP 官方建议的普通 round-robin、按 `Mcp-Method` 路由、结果缓存和 trace 传播，会减少 sticky session 与共享会话存储的运维负担。但长任务和多轮交互必须由显式 handle、幂等状态机和持久化记录承接。服务端应验证 handle 的租户、权限、过期时间和当前状态，拒绝把一个用户的任务句柄当成另一个用户的能力凭证。

Tasks 从核心能力转为扩展也提醒我们：扩展 API 的生命周期要独立管理。升级前要检查旧版 `tasks/list`、错误码、认证 issuer 校验和 SDK 支持矩阵；发布后要能从一次工具调用追到 agent、MCP client、网关、服务实例和下游依赖。

### 客户端：移动端和桌面端更像“任务控制面”，不是聊天气泡

当 agent 可以运行长任务、等待审批、跨设备继续工作，客户端首先要呈现的不是一段流式文本，而是任务状态、最后提交的版本、当前所需权限和可回滚动作。断线恢复时要区分“请求未送达”“服务端已受理”“动作已完成但回执丢失”三种状态，避免用户重复点击造成双写。

客户端还要显示证据：改了哪些文件、执行了哪些检查、哪个检查失败、谁批准了哪个版本。旧审批卡片、过期 task handle 和重复恢复是今天值得优先做的故障演练。

## 值得跟进的动作

1. 给 MCP client/server 做一次 `2025-11-25` 到 `2026-07-28` 的兼容性盘点，重点核对会话、Tasks、认证 issuer、错误码、JSON Schema 和 SDK 支持。
2. 为每个 agent 任务定义最小完成证明：变更摘要、命令与结果、版本或 commit、未验证项、所需人工批准和可撤销动作。
3. 在前端建立 MCP Apps 的安全清单，覆盖 iframe 隔离、消息校验、网络权限、工具调用确认、缓存范围和可观测性。
4. 在服务端演练 round-robin、断线、重复提交、过期句柄、模型回退与下游超时，确认重试幂等且能从 trace 还原全链路。
5. 对开放权重和托管模型各选一个真实任务，记录数据边界、许可证、延迟、单位成本、升级策略、安全测试和退出方案，不用“开源/闭源”一个标签替代评估。
