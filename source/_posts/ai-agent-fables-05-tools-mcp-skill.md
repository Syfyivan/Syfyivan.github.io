## 三段故事

工具行来了个新学徒，叫阿器。他很会判断该怎么办活，也能把量地、补锁、算料的步骤说得头头是道。可真要量一块地、动一笔钱、开一扇门，他不能凭感觉自己硬上。老掌柜教他一个规矩：自己不会、或不该亲手干的事，就开一张**领用单**——写清要哪件工具（比如卷尺）、怎么用。把单子交到柜台，柜台的人照单去用工具，量完把结果（“三丈二尺”）写在回执上递回来。阿器拿着这个准数，再接着算下一步。话，终于变成了动作。

可阿器很快烦了：东街那家工具行用木牌领、西街那家用口令领，每换一家就得重学一套领法。老掌柜讲起“统一柜台的规矩”：守这规矩的工具行，都按同一格式把自家东西挂到柜台上——**能借去干活的工具**、**能查阅的资料**、还有**现成的领用模板**。阿器只要学一次“怎么对接统一柜台”，全城守规矩的工具行就都能借，新开一家也立马会用。

后来阿器发现，有些活儿不是靠一件工具，而是靠一整套配好的“工具包”，收在高处架上。布包封皮先写着一句话：这包是干嘛的、什么时候该用它；翻开，里面是一张分步说明，还夹着几样配好的小器具和一张配方纸。平时只扫一眼封皮，用得上才取下翻开细看，几百个包摆着也不占脑子。老掌柜还从柜台后摸出一串钥匙分门别类挂好：只能看的随便拿，动钱动料的得先报一声、有人点头，真正危险的先到后院“试做间”里演一遍；谁借了什么全记在登记簿上，钥匙只给这一趟、办完就收回。

## 揭晓概念

这个故事讲的是：**工具调用、MCP 和 Skill**。

阿器是模型。开领用单、交柜台执行、再把结果回填，是 tool calling。统一柜台的规矩，是 MCP。架上那种带封皮的整套工具包，是 Skill：把说明、资源和脚本打包成 Agent 可按需加载的能力。那串钥匙、后院的试做间、墙上的登记簿，则是权限、沙箱与安全边界。

## 准确定义

这一讲有三个核心概念：tool calling、MCP、Skill。下面每个都讲透——不止给一句定义，还说清它为什么这么设计、配一个能直接感受的小例子、再划一道边界。

**Tool calling（工具调用）**

一句定义：让模型提出结构化的工具调用请求，再由应用程序执行工具，并把执行结果返回给模型。

为什么这么设计：模型本质上只会生成文本，它没有手，也不擅长精确计算和读实时数据。与其逼它"凭印象"硬算，不如让它输出一段结构化的"调用意图"，把真正的执行交给外部系统。这一步把"会判断"和"会执行"拆开了。

一个具体例子：你问"东京现在几点"，模型不会自己算时区，而是产出一个结构化调用——形如 `{"name": "get_time", "arguments": {"tz": "Asia/Tokyo"}}`。应用真的去读系统时间，拿到 `2026-06-28 21:30`，把这段结果写回消息历史，模型再用自然语言答复你。从头到尾，模型没碰过钟。

边界与延伸：tool calling 本身不是 Agent——它只是一次"模型开单、外部执行、结果回填"的往返。模型给出 tool call 也不代表动作一定发生：执行不执行、安不安全，全在应用侧。你平时感受到的"AI 帮我查了天气、换算了汇率"，背后就是这一来一回。

**MCP（Model Context Protocol，模型上下文协议）**

一句定义：一套开放协议，规定 AI 应用如何和外部的工具、数据源统一对接，而不必为每个都重写一套。

为什么这么设计：没有标准时，N 个应用要接 M 个工具，就得写 N×M 套专用胶水代码，接口五花八门、难复用。标准化之后变成 N+M：写一次客户端能接所有守协议的服务器，写一个服务器能被所有守协议的客户端复用。

一个具体例子：类比 USB——以前每种设备配一种插口，有了 USB 标准，一个口插鼠标、键盘、硬盘都行。MCP 里，一个 Agent 可以同时连"文件系统 server""数据库 server""某个线上服务 server"，它们都按同一套约定把能力挂出来，Agent 学一次对接，全都会用。

边界与延伸：MCP 不是某个工具，也不是某个模型，更不替你判断工具安不安全——它只定义"怎么插、怎么通信"。把它当成"一个产品"或"插件市场"，就理解偏了；它的价值在"统一接法"。

**Skill（技能 / Agent Skill）**

一句定义：把完成某类任务所需的说明、资源和脚本，打包成一个 Agent 可以按需加载的能力单元。

为什么这么设计：Agent 可以拥有几百种能力，但上下文窗口有限、还按 token 花钱。Skill 用"渐进式披露"化解矛盾：平时每个 Skill 只占一句描述，要用到才把完整内容展开。

一个具体例子：一个"PDF 填表"Skill，平时在模型眼里只是一行 `name + description`（量级在几十 token），完整说明和随附脚本可能上千 token。命中任务时才把正文加载进来——于是架上摆几百个 Skill 也不撑爆窗口，因为常驻的只是"封皮"。

边界与延伸：Skill 不是一段提示词，也不是又一个插件；它的核心价值是把"固定套路 + 上下文管理"一起打包好。一个 Skill 内部可以调用好几个工具。

## 历史过程

早期聊天模型主要生成文本。随着应用复杂度上升，开发者需要模型查数据库、读文件、调 API、运行命令，于是 function calling / tool calling 变成重要能力。OpenAI 的工具调用文档把流程描述成多步：请求模型、模型给出工具调用、应用执行、返回工具结果、模型继续回答或继续调用。

2024 年后，Agent 工程开始更重视标准化上下文和工具接入。Anthropic 推出 MCP，让不同数据源和工具能以更统一的方式暴露给模型应用。到 2025 年，MCP 稳定规范更新到 2025-11-25；2026 年的路线图和候选版继续推进传输可扩展性、权限和扩展机制。同时 Anthropic 的 Agent Skills 把“说明 + 资源 + 脚本”打包成可加载能力。它们解决的问题不同：MCP 更偏连接协议，Skill 更偏能力组织。

## 常见误解

第一，工具调用不是 Agent 的全部。一次工具调用仍然可能只是单轮问答，Agent 还需要循环、状态、停止条件和监督。

第二，MCP 不是“万能插件市场”。它定义连接方式，不替你判断工具是否安全、权限是否合理、结果是否可信。

第三，Skill 不是简单提示词。好的 Skill 应该包含任务说明、操作步骤、必要资源、脚本和边界。

## 小练习

给“查天气并提醒出门带什么”设计一个工具：

1. 工具名叫什么？
2. 输入参数有哪些？
3. 输出应该是什么结构？
4. 哪些权限必须限制？
5. 如果工具失败，模型应该怎么继续？
