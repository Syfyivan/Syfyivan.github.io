## 一、先看完整服务端版图

一套复杂活动通常不是一个 HTTP 服务完成的。

```text
C 端页面 / 端内容器
  -> C 端 API：登录、参数、协议和入口编排
  -> 领域服务：业务规则、状态机、事务和幂等
  -> MySQL / KV / Cache：资产、流水、配置和热点状态
  -> MQ / 权益服务：发奖、通知和异步收尾

运营后台
  -> BFF：配置聚合、格式转换、权限和文件入口
  -> 领域服务：配置校验、持久化和运行时规则

定时任务
  -> 聚合全站数据、筛选达标用户、补偿失败记录
  -> 调用领域服务，不复制一套业务规则

事件函数
  -> 消费评论、发帖、阅读等行为事件
  -> 校验活动状态和任务规则
  -> 写入积分或任务结果
```

这套系统里至少存在五类完全不同的数据：

| 数据类型 | 例子 | 一致性要求 |
| --- | --- | --- |
| 业务配置 | 卡池、阶段阈值、任务规则 | 发布时严格校验，运行时可缓存 |
| 用户资产 | 卡片实例、抽卡机会、权益 | 不能重复增加或扣减，强审计 |
| 业务流水 | 抽卡、赠卡、机会变更、发放记录 | 需要幂等键和可回放 |
| 聚合数据 | 全站总积分、参与人数 | 通常接受最终一致性 |
| 外部副作用 | 发奖、通知、发券 | 本地事务无法直接覆盖，需要可恢复状态机 |

后面所有难点，本质上都来自这五类数据的边界不同。

## 二、集卡抽卡：从接口到资产状态机

### 2.1 先把业务对象分清楚

集卡活动里容易混淆的概念有四个：

```text
卡片定义 card
  描述卡图、名称、稀有度和配置权重

卡片实例 card_instance
  用户真实拥有的某一张卡，有唯一实例 ID 和展示编号

聚合持有量 asset_count
  某用户拥有某种卡多少张，用于快速查询

资产流水 asset_flow
  为什么增加或减少、交易对手是谁、变化后数量是多少
```

如果只存 `user_id + card_id + count`，抽卡展示没有问题，但赠卡时会立刻遇到困难：到底送的是哪一张？编号是否随转移保留？两个分享链接是否锁定了同一份资产？客服如何追踪一张卡的来源和去向？

因此真实资产必须落到实例粒度，聚合数量只是查询加速视图，不能反过来充当唯一事实源。

### 2.2 API 层应该薄到什么程度

C 端 API 负责：

- 校验登录态和基础参数；
- 限制抽卡次数只能是支持的值，例如单抽或十连；
- 生成或透传请求幂等标识；
- 调用领域 RPC；
- 把领域模型转换成前端需要的字段；
- 补充图片裁剪、展示配置等非核心信息。

它不应该在 API 层循环十次单抽，也不应该自己计算概率、扣机会或拼接资产。

一个可讲的接口形态是：

```text
DrawRequest
  activity_id
  draw_count       // 只允许 1 或 10
  request_id       // 一次业务请求的幂等标识

DrawResponse
  request_id
  duplicate
  remaining_chance
  draw_items[]
  drop_items[]
```

其中 `duplicate` 不是报错，而是告诉调用方：这次返回来自已有业务结果的重放。

### 2.3 抽卡机会为什么要用余额表加流水表

最简单的机会模型是一个 `remaining_count`。但它无法很好回答：机会来自哪个任务、为什么扣了十次、重复消息有没有多加、客服如何恢复。

更完整的模型是：

```text
机会余额表
  granted_count
  consumed_count
  balance = granted_count - consumed_count

机会流水表
  flow_id
  activity_id
  user_id
  delta
  source_type
  source_id
  after_balance
```

发放机会时，先查询 `flow_id`：

- 已存在且业务参数一致，直接返回旧余额；
- 已存在但用户、活动、增量或来源不同，判定幂等键冲突；
- 不存在，才更新累计发放并写流水。

扣减机会时，不先查询余额再更新，因为两个并发请求可能同时读到余额充足。应该把条件和更新放到同一条语句：

```sql
UPDATE draw_chance
SET consumed_count = consumed_count + :cost
WHERE activity_id = :activity_id
  AND user_id = :user_id
  AND granted_count - consumed_count >= :cost;
```

`affected_rows = 0` 表示余额不足或账户不存在。这样余额校验和扣减是一个原子动作。

### 2.4 一个经常被忽略的幂等冲突

幂等不是“看见相同 request_id 就返回成功”。还要确认这次请求与原请求的业务语义一致。

例如第一次请求是：

```text
request_id = abc
draw_count = 1
```

第二次却是：

```text
request_id = abc
draw_count = 10
```

如果系统只按 request_id 查到旧记录并返回，就会把一次单抽结果伪装成十连结果。更稳妥的做法是把活动、用户、请求次数、来源等关键字段纳入冲突检查。

这类问题很适合作为面试追问，因为它能区分“会加唯一索引”和“真正理解幂等语义”。

### 2.5 概率为什么分两层

卡池采用两层概率更容易维护：

```text
第一层：命中稀有度
R / SR / SSR / SP

第二层：在该稀有度内部按权重命中具体卡片
```

如果所有卡片直接放到一个大权重池里，每新增或删除一张卡都可能改变整个卡池的概率；使用双层结构，运营可以先稳定稀有度分布，再只调整同档卡片的相对权重。

服务端保存的是整数概率基数和整数权重，避免浮点累计误差。配置发布前需要校验：

- 稀有度概率之和是否等于概率基数；
- 启用稀有度下是否至少有一张可命中卡；
- 权重是否为正；
- 保底目标稀有度是否真的存在；
- 卡片定义是否重复或为空。

### 2.6 大保底和十连保底不是一件事

大保底关注的是跨请求历史：连续若干抽没有命中目标稀有度后，下一抽强制命中。

十连保底关注的是本次批次：如果十次结果都低于某个稀有度，替换最后一张为符合条件的卡。

两者一起存在时，需要明确执行顺序和计数变化：

1. 每一抽先判断是否触发历史保底；
2. 正常更新历史保底计数；
3. 完成十次后检查整批是否已有高稀有度；
4. 如果批次保底替换最后一张，还要同步修正对应的保底计数语义。

实际实现可以从抽卡历史推导“距离上次目标稀有度已经抽了多少次”，这样不需要额外维护一份容易漂移的计数器。代价是历史查询成本，需要用索引和查询范围控制。

### 2.7 十连为什么必须在一个主事务里

一次十连的主事务至少包含：

```text
查询是否已有相同 request_id 的结果
  -> 原子扣减十次机会
  -> 读取或推导保底状态
  -> 生成十次命中
  -> 分配十个实例编号
  -> 写十个卡片实例
  -> 写十条抽卡记录
  -> 写独立掉落判定记录
  -> 更新聚合持有量与资产流水
  -> 提交
```

如果任何一个主步骤失败，事务整体回滚。不能出现“机会扣了十次，只写入八张卡”的中间状态。

请求重放发生在扣机会之前：如果已经存在同一请求的抽卡记录，就按 `draw_index` 重建结果并返回，不再次扣机会。

### 2.8 活动结束后的重试为什么比较特殊

活动时间校验不能简单放在函数第一行，然后所有请求一律拒绝。

考虑下面的时间线：

```text
23:59:59  用户抽卡成功，服务端已提交
00:00:01  客户端因为网络超时重试相同 request_id
```

活动虽然已经结束，但这次重试应该允许读取并返回 23:59:59 已经提交的结果；只有不存在历史结果的新请求才应该被活动结束规则拒绝。

因此正确顺序是：

```text
先查幂等结果
  -> 有结果：允许回放
  -> 无结果：检查活动是否仍可写
  -> 允许时才创建新业务结果
```

这个模式同样适用于机会发放、权益发放和订单提交。

### 2.9 卡片编号：唯一性、连续性和性能不能同时免费获得

卡片展示编号按“活动 + 卡片类型”独立递增，例如某种卡从 `NO.000001` 开始。

早期方案可以在事务里锁住该卡当前最大的实例编号，然后分配下一段连续区间。它逻辑直观，但热门卡会把所有并发抽卡集中到同一行或同一索引尾部，形成热点锁。

后来更稳妥的方案是独立计数器表：

```text
serial_counter(activity_id, card_id, next_seq)
```

一次十连里同一张卡命中 `k` 次，就原子预留一个长度为 `k` 的号段。业务事务再使用这个号段写实例。

这里必须接受一个取舍：如果号段已经预留，但后续业务事务回滚，编号可能出现空洞。对于展示序列，通常“全局不重复、单调递增”比“绝对无空洞”更重要。

面试官如果问为什么不用数据库自增 ID，答案是：自增 ID 可以保证全表唯一，但这里要求按每个活动和卡片类型独立编号，且一次批量抽卡需要预留连续号段，语义不同。

### 2.10 六位编号溢出不是把格式改成七位就结束

`%06d` 表示至少六位，不代表最多六位。编号达到一百万以后，字符串会自然变成七位。

服务端编号本身不会截断，但下载卡图或分享海报中的固定文字区域可能放不下。后续处理方式是根据数字位数切换到更宽的渲染样式，同时重新计算昵称与编号之间的安全间距。

这件事有两个可以讲的工程点：

1. 容量边界不仅存在于数据库字段，也存在于海报模板、埋点字段和前端布局；
2. 不能把“发了多少张卡”和“某一种卡的编号到了多少”混为一谈，因为编号是按卡片类型分别递增的。

这项后续治理属于团队服务端工作，面试时必须区分自己参与联调或风险发现的部分，不要据为个人独立实现。

### 2.11 赠卡为什么在创建分享时就锁定实例

赠卡语义是“我把自己的一张卡放进一个待领取链接，谁先领取归谁”。

创建分享时就应该：

1. 清理同用户、同卡片已经过期的赠卡锁；
2. 检查至少有一个可转移实例；
3. 选择一个具体实例；
4. 把实例从 `HELD` 更新为 `LOCKED`，绑定 transfer_id；
5. 创建 `AVAILABLE` 状态的转移单；
6. 生成随机分享令牌，对数据库只保存令牌哈希。

提前锁定可以避免用户用同一张卡生成多个分享链接，也避免分享创建以后自己又把卡消耗掉。

分享令牌只存哈希的原因和密码类似：数据库泄漏或日志误打时，攻击者不能直接拿原值领取资产。查询时对用户提供的 token 做同样哈希再匹配。

### 2.12 赠卡领取如何处理并发

领取事务需要同时完成：

```text
确认转移单仍是 AVAILABLE
  -> 校验不是赠送者自己领取
  -> 把锁定实例的 owner 改成领取者
  -> 更新赠送者和领取者聚合持有量
  -> 写两条方向相反的资产流水
  -> 条件更新转移单 AVAILABLE -> COMPLETED
```

最后一步必须带状态条件。两个用户同时领取时，只有一个请求能够把 `AVAILABLE` 更新成 `COMPLETED`；失败的一方重新读取状态，得到“已经被领取”，而不是再转移一次实例。

取消或过期时，需要把仍处于 `LOCKED` 的实例恢复为 `HELD`，否则资产会永久冻结。

### 2.13 求卡为什么不能在创建时锁卡

求卡语义不同：创建者并没有那张卡，他只是发布一个“我缺这张卡”的挂账单。此时系统不知道哪位好友会响应，也不能锁定别人的资产。

所以创建求卡只保存目标 card_id、创建者和过期时间。好友响应时才：

1. 检查求卡单仍可用；
2. 检查响应者是否有可转移实例；
3. 如果产品要求“送出后自己至少保留一张”，校验持有量至少为 2；
4. 锁定并转移响应者的具体实例；
5. 写双方资产流水；
6. 条件完成求卡单。

赠卡是“先锁资产，再等领取”；求卡是“先挂需求，响应时再锁资产”。这两个状态机不能为了复用代码强行合并成完全相同的流程。

### 2.14 为什么还要保留聚合数量

既然实例表是事实源，为什么不每次都 `COUNT(*)`？

因为图鉴页可能一次查询几十种卡，每张都实时 count 会放大数据库压力。可以保留聚合数量作为查询加速，但写路径必须保证它与实例变化在同一事务中更新，或者允许从实例表重建和校准。

资产流水中的 `after_count` 可以帮助审计：如果聚合量漂移，可以从最近流水和实例状态判断哪条路径出现问题。

### 2.15 集齐后领奖为什么采用两阶段状态机

用户集齐一套卡以后，可以兑换另一套抽奖机会。这里跨越两个系统：

- 本地卡片资产在 MySQL；
- 抽奖机会可能在另一个缓存、消息或领域系统。

单个数据库事务无法覆盖外部系统，所以真实实现拆成两阶段：

```text
Phase A：本地事务
  校验完整卡套
  -> 每种卡占用一个具体实例
  -> 写 pending 兑换记录
  -> 提交

Phase B：提交后履约
  pending / failed -> granting
  -> 使用稳定幂等键发放抽奖机会
  -> 成功：completed
  -> 失败：failed，可重试
```

被占用的卡仍然属于用户、仍可在图鉴展示，但不能再赠送或响应求卡。这样用户能看到收集成果，同时同一张卡不会重复参与兑换。

### 2.16 配置改变以后，重试使用哪一份配置

假设 Phase A 已经占用了 28 张卡，准备发 3 次抽奖机会；随后运营把配置改成了 1 次。

重试不能重新读取当前配置，否则同一笔已经承诺的兑换会被改写。Phase A 应当把目标抽奖 ID、发放次数和已占用实例保存到持久化记录中，Phase B 只使用记录里的快照。

这是一类通用原则：

> 对已经发生的业务承诺，重试依据持久化事实，而不是重新读取可变配置。

### 2.17 granting 状态卡死怎么办

如果进程把状态改成 `granting` 后宕机，记录会一直看起来“处理中”。

真实实现可以给 granting 设置超时：超过一定时间仍未完成，就允许新的 worker 重新领取执行权。外部发放接口必须有稳定幂等键，这样旧 worker 即使稍后恢复，也不会重复发放。

此外，错误信息写数据库前要按字段长度截断，而且应按 Unicode 字符截断，避免多字节字符被切坏，导致连“记录失败原因”这一步也失败。

### 2.18 随机掉落为什么提交后再履约

抽卡随机掉落是“抽到卡以后额外判定是否掉奖品”，它不应该改变卡片结果。

主事务中可以保存：

- 每次抽卡是否命中掉落；
- 命中的奖品 SKU；
- 独立的 drop_record_id；
- 当前状态，例如 won。

真实发奖放在主事务提交后执行。原因是外部权益系统失败时，不能回滚已经成功的抽卡和卡片资产。

```text
抽卡主事务成功
  -> 卡片结果对用户永久成立
  -> 尝试发放额外奖品
     -> 成功：completed
     -> 库存不足：stock_empty
     -> 其他可恢复错误：pending_compensation
```

每个掉落记录绑定稳定的外部 win_id。用户重放原请求或服务端补偿任务重试时，继续使用相同 win_id，不再创建第二笔奖品。

### 2.19 为什么既需要用户请求重放，也需要服务端补偿任务

只依赖用户重放 request_id 不可靠：用户可能看到抽卡结果后直接离开，再也不会发起同一请求。

所以服务端还需要分页扫描可恢复状态：

```text
won / granting / stock_empty / pending_compensation
```

补偿任务按主键游标批量处理，限制单批最大数量；某条记录失败时记数并跳过，不让一条坏数据阻断整个批次。

### 2.20 记录分页为什么不只用时间戳

抽卡和发奖记录可能在同一秒创建多条。如果只用 `create_time < last_time` 翻页，同一秒的数据可能重复或遗漏。

更稳定的游标是复合游标：

```text
(create_time, record_id)
```

排序和下一页条件同时使用时间与唯一 ID：

```sql
WHERE create_time < :cursor_time
   OR (create_time = :cursor_time AND record_id < :cursor_id)
ORDER BY create_time DESC, record_id DESC
LIMIT :limit_plus_one;
```

多查一条可以判断 `has_more`，再裁剪成页面大小。

### 2.21 抽卡链路失败矩阵

| 失败位置 | 已经发生什么 | 应该怎么处理 |
| --- | --- | --- |
| 参数或卡池校验失败 | 无业务写入 | 直接拒绝 |
| 机会不足 | 条件更新未命中 | 返回余额不足 |
| 概率配置无法命中 | 主事务未提交 | 整体回滚并报警配置 |
| 实例或记录写失败 | 主事务未提交 | 机会扣减一起回滚 |
| 客户端超时但事务已提交 | 结果已经成立 | 相同 request_id 重放 |
| 掉落发奖失败 | 卡片已提交 | 标记补偿，不回滚抽卡 |
| 赠卡领取并发失败 | 另一请求已完成 | 返回已领取状态 |
| 集齐发机会失败 | 卡片已占用、记录 pending/failed | 相同请求重试 Phase B |
| 活动结束后旧请求重试 | 旧记录存在 | 允许回放，不允许新写 |

### 2.22 抽卡高频追问

#### 为什么 request_id 不能由服务端每次重新生成

因为客户端重试需要携带同一个业务标识才能读取旧结果。如果每次重试都生成新 ID，服务端会把它当成新抽卡。

#### 数据库唯一索引和代码幂等检查有什么区别

代码检查可以返回友好的旧结果和冲突原因；唯一索引是并发情况下的最终防线。两者都需要。

#### 为什么十连不是十次 goroutine 并发调用

十连是一个业务动作，需要一次扣减、批次保底和整体结果。并发单抽只能提升调用速度，却破坏了事务和保底语义。

#### 为什么掉落不放进抽卡事务

本地事务无法覆盖外部权益系统。把外部 RPC 放进长事务还会延长锁时间，并且外部超时会回滚已经确定的卡片结果。

#### 允许编号有空洞会不会有问题

展示编号的核心约束是不重复和单调，不是财务凭证式连续。为了无空洞把外部或长业务事务绑进编号分配，代价更大。

#### 赠卡为什么不直接对 count 做减一和加一

因为卡片有实例编号和流转历史。只改 count 会丢失具体实例，无法避免同一张卡被多个分享同时使用。

#### 为什么赠卡创建时锁卡，求卡创建时不锁

赠卡创建者拥有并承诺了一份资产；求卡创建者只是声明需求，不知道未来由谁提供资产。

#### 集齐兑换为什么不在一个接口里同步完成

对外仍然可以是一个接口，但内部必须承认本地占用与外部发机会无法形成一个数据库事务，因此要使用可恢复状态机。

#### 如果发机会成功但写 completed 失败怎么办

重试使用同一个下游幂等键。即使再次调用发机会，下游也只能产生一次结果；本地随后补写 completed。

#### 如何验证没有重复发卡

检查请求级唯一索引、机会流水、实例唯一索引、序列计数器、资产流水和重放测试；并发测试要覆盖相同 request_id、不同 request_id 抢同一余额和两个用户抢同一赠卡。

## 三、进度解锁：实时行为和全站聚合怎样共存

### 3.1 业务链路

进度解锁活动把用户行为积分汇总成全站进度：

```text
签到 / 阅读 / 分享 / 回答问题
  -> 用户个人积分
  -> 排名或积分明细
  -> 离线聚合全站总分
  -> 写入总分快照
  -> C 端读取快照
  -> 根据阶段阈值展示图片、视频或跳转内容
```

这个项目的难点是：用户个人行为需要及时反馈，但全站总分不能在每次打开页面时实时扫描。

### 3.2 阶段为什么做成配置

阶段配置至少包含：

```text
phase_id
target_score
description
material_type
image / long_image / video
schema
fallback
```

后台保存前要校验阶段阈值严格递增、素材类型与必填字段匹配、跳转协议合法、旧客户端遇到新字段时仍能退化展示。

服务端只返回当前分数和每个阶段是否完成，前端按照配置渲染。这样更换主题和素材不需要重写服务端规则。

### 3.3 为什么全站总分走离线快照

如果页面请求实时聚合所有用户明细，访问量会直接转化成数据库扫描量。

真实实现由离线任务拿当前排行榜或积分列表，按统一比例归一化后求和，再叠加配置中的保底积分，写入一个按活动和进度组件区分的 KV 快照。

C 端读取路径变成常数复杂度：

```text
GET progress_score_key
  -> 解析整数
  -> 遍历少量阶段配置
  -> current_score >= target_score
```

对于这一类进度条，C 端不再为了展示进度额外统计全量报名人数，避免缓存缺失时打到热点报名表。

### 3.4 为什么写快照时取 max

活动解锁进度通常只前进不后退。离线任务可能并发执行，旧批次也可能晚于新批次完成。

因此写入时使用短锁，并比较：

```text
stored = max(existing, calculated)
```

这样旧任务不会把已经解锁的阶段覆盖回未解锁。

但这也有明确边界：如果业务允许删除违规内容后回退总分，就不能简单取 max，需要定义撤销语义、版本号或可重算事实表。面试时要先问清产品规则。

### 3.5 保底积分为什么重算，不累加 delta

保底积分是当前总分计算公式的一部分：

```text
total = sum(user_scores) + guaranteed_score
```

它不是每次任务执行都加一次的奖励。如果任务重复运行时做 `total += guaranteed_score`，就会不断膨胀。

正确方式是每轮从当前事实重新计算目标值，再用受控规则写快照。

### 3.6 快照缺失应该返回 0 还是报错

这取决于业务容错。

真实实现可以把 KV 不存在视为 0，并打告警；其他 KV 错误则返回失败。这样新活动在第一次离线任务执行前不会直接打不开页面，但监控能发现快照尚未产出。

如果阶段解锁涉及真实权益，而不是纯展示，就应更保守：快照缺失不能被解释为用户没有资格，也不能直接发奖，需要查询权威状态或暂停操作。

### 3.7 随机掉落为什么需要独立阈值状态

用户积分达到多个阈值时，可以触发不同次数的掉落。服务端为每个用户保存：

```text
triggered_thresholds = {
  100: true,
  300: true
}
```

请求进入后先获取用户级短锁，读取当前积分和已触发阈值，只为新增跨过的阈值增加抽奖次数。

这里的扩展追问是：如果一次命中多个阈值，前两个奖已经抽完，第三次失败，怎样避免重试时重复发前两个？

更强的设计是把每个阈值做成独立执行记录：

```text
(activity_id, user_id, threshold) -> pending / executing / completed / failed
```

按阈值记录进度，而不是只在全部完成后保存一个布尔集合。这个属于进一步的平台化设计，不应冒充原项目已经完整实现。

### 3.8 多抽为什么既要限制配置，也要限制运行时请求

运营后台只允许有限的多抽次数，例如 3、5、10，避免出现任意大循环。

但配置校验不等于运行时安全。C 端请求仍需要：

- 校验请求次数不超过配置；
- 一次性校验和扣减机会；
- 为每次抽奖生成独立记录；
- 明确部分失败是否允许；
- 对外返回稳定顺序。

如果底层抽奖系统暂时只支持单抽，可以在领域服务内部受控循环，但必须先固定业务批次 ID 和机会扣减语义，不能把循环放到前端。

### 3.9 签到怎样进入统一积分任务

签到请求需要校验：

- 活动、用户和任务组件是否合法；
- 当前任务类型是否确实支持签到；
- 当天次数是否达到 daily_limit；
- 活动期总次数是否达到 total_limit。

用户级锁保护同一时刻的两个签到请求。通过后更新个人总分、每日计数、累计次数和累计签到分数。

日期必须使用明确的业务时区，不能依赖服务器本地时区，否则跨机房或容器配置变化会导致“今天”不一致。

### 3.10 进度解锁失败矩阵

| 失败 | 影响 | 处理 |
| --- | --- | --- |
| 离线聚合失败 | 总分暂时停留在旧快照 | 告警、重跑，不影响用户个人任务 |
| 旧任务晚完成 | 可能覆盖新分数 | 高水位或带版本 CAS |
| KV 首次不存在 | 页面尚无快照 | 返回 0 并告警，视业务决定是否展示 |
| 配置阈值无序 | 阶段判断错误 | 发布前拒绝 |
| 签到并发 | 可能重复加分 | 用户锁 + 状态校验 |
| 随机掉落部分失败 | 可能重复触发 | 按阈值执行记录和幂等抽奖 ID |
| 旧客户端不认识新素材 | 页面无法展示 | 可选字段、默认素材和版本降级 |

### 3.11 进度解锁高频追问

#### 为什么不用数据库定时 `SUM`

可以，但要看明细规模、索引、执行频率和对在线库的影响。离线读取已经存在的排名结果通常成本更稳定。

#### 最终一致性会不会让用户觉得任务没加分

个人积分可以实时返回，全站总进度使用快照。产品上要区分“我的贡献”和“全站进度”，并说明刷新延迟。

#### 为什么要加锁，直接 SET max 不行吗

普通 GET + SET 不是原子操作。可以使用支持原子 max 的脚本、CAS 或数据库条件更新；如果存储能力有限，才用短锁保护读改写。

#### 锁过期但任务还没执行完怎么办

锁 TTL 要覆盖正常执行时间，并监控超时。更严格的实现使用带 owner token 的锁，释放时只删除自己持有的锁，避免删掉后来 worker 的锁。

#### 为什么进度只增不减

这是产品规则，不是通用技术真理。如果违规内容撤销需要扣分，就要改变高水位模型，保留可重算明细和版本化聚合。

## 四、自动徽章发放：批处理、幂等和有效期

### 4.1 两条入口，一套规则

徽章发放有两条入口：

```text
自动路径
  离线任务筛选积分达标用户
  -> 统一领域发放接口

批量路径
  运营上传表格
  -> BFF 转发文件地址
  -> 领域服务下载、解析和校验
  -> 统一领域发放接口
```

入口只决定用户从哪里来，真正的分组、重复判定、下游发放和有效期处理必须共用一套领域逻辑。

### 4.2 为什么有两级拆批

自动任务可能一次筛出很多用户。真实链路中，离线任务先按较大的批次调用领域 RPC；领域服务再按下游接口限制拆成更小的批次。

例如：

```text
离线任务：每 500 个用户一次领域 RPC
领域服务：每 50 个用户一次下游发放
```

两级拆批解决不同问题：第一层控制调用方内存、超时和 RPC 包大小；第二层适配下游批量接口和失败定位。

### 4.3 实际分组键为什么比文档多一个字段

设计文档常写按“徽章 ID + 有效期”分组。最终代码还把展示标题纳入分组：

```text
(user_title, title_text, valid_days)
```

因为同一个徽章标识如果配了不同展示标题，仍然不能安全合并为一次下游请求。文章和面试应以最终代码为准，而不是背早期方案。

### 4.4 活动幂等和全局权益不是同一层

自动发放使用活动维度的幂等键：

```text
(activity_id, user_id, user_title)
```

它回答的是：“这个活动是否已经因为达标给过这个用户这枚徽章？”

下游账号系统回答的是：“这个用户现在是否已经拥有这枚徽章？到期时间是什么？”

同一个用户可能在不同活动中获得同一徽章，因此不能只用 `user_id + badge_id` 阻止所有活动。反过来，同一活动也不能重复刷新有效期。

### 4.5 为什么预过滤失败时不能直接放弃整批

离线任务在调用领域服务前可以批量检查活动幂等标记，减少无效 RPC。

如果这次预过滤查询失败，真实实现选择继续把原用户列表交给领域服务，而不是直接丢弃。原因是预过滤只是优化，最终幂等仍由领域层和下游保证。

这是“fail-open”与“fail-closed”的一个好例子：

- 对权益重复风险，后面还有可靠幂等防线，预过滤失败可以继续；
- 对压测是否会写入正式资源，没有后续安全防线时必须 fail-closed。

### 4.6 有效期到底怎么续

本次发放先计算：

```text
candidate_end = now + valid_days
```

如果用户没有徽章，就新增到 `candidate_end`；如果已经存在：

- `old_end >= candidate_end`：视为重复，不缩短；
- `old_end < candidate_end`：修改为 candidate_end。

这不是简单的 `old_end += valid_days`。后者会让重复执行不断叠加有效期，破坏幂等。

如果产品明确要求“从旧到期时间继续续 N 天”，就需要另一套清晰语义和独立幂等记录，不能悄悄改变通用接口。

### 4.7 下游批量接口部分成功怎么办

下游可能返回三类用户：

- 新增成功；
- 已经存在；
- 发放失败。

领域服务先默认整批成功，再用失败列表和已存在列表覆盖每个用户的状态。对于“已存在”的用户，继续查询当前到期时间，决定是重复还是需要延长。

如果整个批量 RPC 失败，代码会把这一批降级为逐用户调用，缩小失败范围，避免一个异常用户拖垮整批。

这种降级会增加 RPC 数量，所以只应在批量失败时触发，并配合超时、重试上限和日志采样。

### 4.8 表格为什么由领域服务解析

如果 BFF 和领域服务分别解析文件，可能出现字段规则不一致。实际设计让 BFF 只负责上传和转发，领域服务作为唯一解析者，统一校验：

- 必须存在 user_id、徽章 ID、展示名、有效期等表头；
- 空行跳过；
- 缺少必填字段记录行级失败；
- 用户 ID 和有效期必须合法；
- 发放失败后补查账号是否存在；
- 返回原始行号和明确原因。

一行错误不应该让整份文件失败。响应中保留 `fail_rows`，运营修正失败行后可以重新上传。

### 4.9 重复用户行怎么处理

同一文件里可能多次出现同一个用户。这里首先要明确产品语义：

- 如果完全相同，应去重；
- 如果徽章或有效期不同，不能只按 user_id 去重；
- 如果同一用户同一徽章但配置冲突，应返回冲突行，而不是随机采用第一条。

真实代码为了把下游失败映射回表格，会保存用户到首行的索引。进一步的平台化实现可以把行唯一键设计为 `(row_index, user_id, badge_id)`，完整保留每一行结果。

### 4.10 KV 幂等标记写失败怎么办

一种危险情况是：下游徽章已经发放成功，但写活动幂等标记失败。

下次任务可能再次调用下游。好消息是下游查询和“只延长不缩短”的语义仍能避免重复实体；坏消息是会增加调用量，并可能把结果判定成 duplicate。

更强的方案是使用持久化发放记录表，先写 pending，再调用下游，最后 completed；KV 只做快速过滤。是否值得引入，取决于权益价值、规模和审计要求。

### 4.11 徽章失败矩阵

| 失败 | 当前可用策略 | 更强方案 |
| --- | --- | --- |
| 自动筛选任务重跑 | 活动幂等键过滤 | 持久化批次记录 |
| 预过滤 KV 失败 | 继续交给领域层 | 熔断并延迟重试 |
| 整批下游 RPC 失败 | 降级单用户 | 失败队列 + 限速补偿 |
| 部分用户失败 | 返回用户级状态 | 自动重试可恢复错误 |
| 用户不存在 | 批量补查账号 | 上传前预校验 |
| 徽章已存在 | 查询到期时间 | 统一权益状态查询 |
| 幂等标记写失败 | 下游再次判重 | DB 状态机 + KV 加速 |

### 4.12 徽章高频追问

#### 为什么不让离线任务直接调用账号服务

这样自动任务和批量工具会各复制一套幂等、分组、有效期和错误处理。领域接口是统一规则边界。

#### 为什么批量失败要逐用户重试

用于隔离坏用户或下游局部问题。但要限制触发条件和并发，不能把每次正常批量都退化成 N 次 RPC。

#### 活动幂等记录的 TTL 应该多长

至少覆盖该活动授予的有效期和可能的补偿窗口。若审计要求长期保留，应使用持久化记录而不是只依赖 TTL KV。

#### 为什么重复状态不一定是失败

幂等重放和权益已存在都是可预期业务结果。把它们与系统错误分开，调用方才能正确统计和重试。

#### 一万用户怎么发

调用侧去重并分大批，领域层按下游上限分小批；控制 RPC 超时和并发；保存用户级结果；失败批次可断点续传，而不是一次请求阻塞到结束。

## 五、多仓服务重构：代码目录必须服从运行边界

### 5.1 重构范围

活动服务长期演进后，六个仓库承载了八类玩法或基础能力：抽奖、签到、排行、投票、任务、表单、徽章和运营配置。

旧结构的主要问题是：

- 公共仓不仅有模型和基础设施，还混入具体业务 Service；
- 一个入口同时处理协议、业务、数据库、缓存、消息和兜底；
- 两条产品线的相似玩法写在同一大分支；
- 所有仓都依赖公共仓，业务代码放进去会放大改动和发布影响。

### 5.2 六个仓库的目标职责

```text
C 端 API
  HTTP 协议、登录、参数、入口编排

运营 BFF
  后台配置聚合、展示转换和文件入口

领域服务
  核心业务规则、事务、状态机和运行时配置

离线任务
  周期计算、批量筛选和补偿

事件函数
  行为事件消费与积分计算

公共层
  稳定模型、表定义、基础设施和无业务方向工具
```

### 5.3 领域模块内部怎样分层

```text
handler
  参数校验、协议转换

service
  依赖组装、能力查找、调用用例

strategy / business
  按玩法和业务线选择实现

workflow
  业务流程编排

repository
  事务性数据访问

post
  事务提交后的异步动作

router
  新旧实现灰度路由
```

依赖方向必须单向：handler 不直接写数据库，repository 不反过来调用 service，post 不决定主事务结果。

### 5.4 为什么不能把所有业务代码都搬到领域仓再直接 import

这是一次真实的返工点。

从代码目录看，把公共业务代码统一搬到领域仓很合理；但领域仓本质上是独立部署的 RPC 服务，其他仓库不能像普通 Go library 一样链接它的内部实现。

正确边界是：

- 需要跨进程复用的能力，定义稳定 RPC 契约；
- 只属于调用方的编排，留在调用方；
- 真正无业务方向的模型和基础设施，才放公共层；
- 不为了“消除重复”破坏发布和故障隔离。

这个教训可以概括为：

> 代码复用边界必须同时匹配编译、部署、发布和故障边界。

### 5.5 为什么保留 v1 和 v2 并存

一次性替换多个仓库的所有调用链，回滚成本太高。迁移采用：

```text
定义模块事实源和兼容契约
  -> 建立 v2 骨架
  -> 选择一条最小主链路试点
  -> v1 / v2 结果对比
  -> 按活动类型或流量灰度
  -> 观察稳定性
  -> 清理该模块 v1
```

不是等所有模块都完成后再统一删除 v1，而是每个模块全量稳定后尽快清理，避免双轨代码无限增长。

### 5.6 兼容性不能只比较返回 JSON

迁移验证至少包含：

| 维度 | 要比较什么 |
| --- | --- |
| API | 字段、默认值、空值和顺序 |
| 错误 | 错误码、错误语义、重试建议 |
| DB | 表、事务、写入条数和唯一键 |
| Cache | key、TTL、回源和失效行为 |
| MQ | topic、payload、发送时机和重复语义 |
| 外部 RPC | 调用次数、参数、超时和副作用 |
| 异步收尾 | 发奖、通知、补偿是否遗漏 |

很多重构事故不是主返回值变了，而是旧路径多写了一条缓存、少发了一条消息，或者错误码让客户端改变了重试行为。

### 5.7 灰度路由应该放在哪里

灰度路由最好集中在入口或统一 router 中，根据活动类型、白名单或比例选择 v1/v2。

不要在业务函数内部到处写：

```text
if flag { new logic } else { old logic }
```

分散开关会让一次请求部分走新、部分走旧，难以回滚和比较。

### 5.8 重构怎样量化

如果没有线上业务指标，不要编造“性能提升多少”。可以使用工程指标：

- 大文件行数和职责数量下降；
- 新功能修改仓库数减少；
- 公共仓业务依赖减少；
- v1/v2 差异告警数量；
- 灰度回滚时间；
- 单模块测试和构建时间；
- 同类活动接入周期。

### 5.9 重构高频追问

#### 为什么不是加一个工厂模式解决 if/else

工厂只能改善对象创建，不能解决仓库职责、运行边界、事务和副作用混杂。

#### 为什么不建一个全新的 v2 仓库

会引入双份基础设施、协议和发布链路，迁移面更大。先在现有领域仓按模块建立清晰结构，更容易灰度。

#### 如何防止 v2 变成另一套大泥球

明确依赖方向、模块契约、目录准入和 Phase Exit Criteria；新功能默认只进入 v2；模块稳定后及时删除旧路径。

#### 重构最大风险是什么

不是编译失败，而是隐藏副作用丢失、错误语义变化、缓存键不兼容和灰度无法快速回滚。

## 六、高流量活动压测：隔离比 QPS 更先

### 6.1 压测覆盖什么

一次大型活动压测覆盖七类入口：

1. 首屏组件聚合；
2. 活动配置读取；
3. 报名写入；
4. 报名查询；
5. 任务行为提交；
6. 答题；
7. 抽奖。

内部还会经过进度、资格、数据库、缓存、消息和发奖系统。不能把“七个 HTTP 接口”误解成全部系统边界。

### 6.2 压测标记为什么只允许从 Header 进入

压力标记需要在网关、HTTP 上下文、RPC metadata、数据库和缓存客户端中持续透传。

把标记放在 query 中容易被业务参数处理、日志改写或转发时丢失；因此专用压力环境只接受固定 Header，并拒绝 query 中的压力标记。

### 6.3 fail-closed 的两层守卫

入口守卫同时验证环境和标记：

```text
专用压力环境
  只有携带正确压力标记的请求才能进入

其他环境
  任何携带压力标记的请求都拒绝
```

这样既防止压力环境收到无标请求写入正式数据，也防止压力请求误打到普通测试环境或线上。

领域服务还要再次确认 metadata 没有在 RPC 中丢失。安全约束不能只依赖最外层网关。

### 6.4 影子表为什么不等于物理隔离

数据库中把表名路由为 `_stress`，只能保证数据命名空间不同。它们仍可能共享：

- 同一数据库集群的 CPU 和 IO；
- 同一连接池；
- 同一 Redis 或 KV 集群；
- 同一消息集群；
- 相同热点 key 的物理分片。

因此还需要压力平台硬上限、自动停压阈值和资源 owner 的容量确认。没有这些结论时，只能从极小 QPS 的 smoke 开始。

### 6.5 副作用怎样隔离

| 副作用 | 压测处理 |
| --- | --- |
| 数据库写 | 影子表 |
| 缓存写 | 独立 key / namespace |
| 消息 | 影子 topic 或禁止发送 |
| 发券、发权益 | mock / no-op |
| 站内信和通知 | no-op |
| 真实书架写 | 不纳入服务端压测 |

任意一层识别不了压力标记时，都应该停止，而不是尝试写默认资源。

### 6.6 为什么业务断言比 HTTP 200 更重要

真实压测中遇到过两类问题：

1. 网关返回 HTTP 成功，但响应体是业务参数错误，请求根本没有进入核心领域逻辑；
2. 上游接受了压力请求，下游服务因为不允许压力流量而拒绝，导致业务链没有走完。

所以每个接口都需要业务断言：

```text
报名后能查询到影子报名状态
任务后影子积分发生正确变化
答题后次数和记录匹配
抽奖后库存、次数和中奖记录一致
所有正式资源和真实副作用保持不变
```

### 6.7 UV 怎样换算 QPS

不能用总 UV 直接除以活动时长。需要考虑：

```text
资源位曝光
  * 页面打开率
  * 峰值集中系数
  * 每次页面触发的接口数
  * 任务参与率
  * 人均任务次数
  * 人均抽奖次数
```

读接口和写接口的比例不同，首屏多个请求还会在短时间内同时发生。流量模型应该拆到接口级别，再加安全系数。

### 6.8 为什么分阶段放量

推荐顺序：

```text
单请求准入
  -> 1 QPS smoke
  -> 单接口读压测
  -> 单接口写压测
  -> 异步链路验证
  -> 混合业务场景
  -> 目标档位
```

每个写场景都要单独证明隔离，不能因为“加书架任务通过”就默认报名、答题和抽奖也安全。

### 6.9 实际结果应该怎么说

在单机、小规格测试环境中，多数核心接口在约数百 QPS 下保持较稳定的延迟，部分读取和抽奖接口达到约 500 QPS 时成功率保持完整；任务与答题的混合场景曾出现约 97% 的业务成功率，暴露出参数和下游准入问题。

这不能写成“完整通过两千万 UV 容量验证”。更准确的结论是：

- 获得了核心接口的阶段性容量数据；
- 验证了部分影子路由和副作用隔离；
- 发现了 HTTP 成功但业务失败、下游拒绝压力流量等问题；
- 为正式上线提供风险依据，但异步消费者和真实下游容量不在本轮结论中。

### 6.10 立即停压条件

- 任何正式表、正式缓存 key 或真实消息出现变化；
- 压力标记在任一层丢失或改变；
- 请求进入错误环境；
- 影子表缺失后发生默认回退；
- P99、错误率、慢 SQL、锁等待或连接池超过阈值；
- 共享资源影响线上；
- Pod OOM、重启或健康检查失败。

### 6.11 压测高频追问

#### 影子表是不是绝对安全

不是。它隔离数据名，不隔离物理资源，也不自动覆盖缓存、消息和外部权益。

#### 为什么错误标记要拒绝，而不是当普通请求处理

普通处理可能把压力数据写入正式资源。安全边界不确定时必须 fail-closed。

#### 成功率 97% 算不算通过

取决于 SLA 和失败原因。业务参数错误或下游拒绝说明场景没有完整执行，不能把 97% 包装成容量通过。

#### 为什么不一直压到系统崩溃

目标是验证目标流量和安全余量，不是破坏共享测试环境。超过停压阈值会污染容量结论并影响其他团队。

#### 如何证明压测没有污染线上

压测前记录正式资源基线；压测中抽样 SQL、缓存、消息和下游调用；压测后再次核对正式资源无变化，并保留 request_id、trace 和 owner 结论。

## 七、事件消费写放大：当前时间和事件时间必须分开

### 7.1 问题是怎样形成的

社区帖子事件可能延迟或被 MQ 重放。旧逻辑只检查帖子创建时间是否落在活动窗口内。

于是出现下面的路径：

```text
活动已经结束
  -> 历史帖子事件被重放
  -> 帖子创建时间当时合法
  -> 仍然对活动列表做 fanout
  -> 获取分布式锁
  -> 查询报名和帖子详情
  -> 写积分详情和大对象诊断数据
```

虽然用户已经不可能继续参与，系统仍然消耗 RPC、锁、缓存和存储资源。

### 7.2 当前时间和事件时间回答不同问题

- 当前时间判断：这个活动现在是否还允许处理新副作用；
- 事件时间判断：这条内容在当时是否属于活动有效期。

两者都通过才应该继续。只看事件时间，会让过期活动永久接受历史重放；只看当前时间，又可能破坏明确允许的离线补算场景。

### 7.3 为什么需要双层保护

第一层放在活动 fanout 之前，避免为已结束活动创建 goroutine、加载帖子详情和抢锁。

第二层放在具体社区帖子处理器中，防止未来存在其他调用入口绕过 fanout。

```text
入口层：尽早削减无效工作量
处理器：保护业务不变量
```

### 7.4 为什么不能只清理运行时配置

运营清理配置可以快速止血，但存在时间差，也不能阻止未来同类重放。

系统必须把活动生命周期当成自己的业务边界。配置负责“哪些活动启用功能”，活动状态负责“现在是否允许产生副作用”，两者不能互相替代。

### 7.5 无效详情为什么使用确定性采样

所有无效事件都保存完整诊断详情，会产生新的写放大；完全不保存，又失去排障能力。

实现使用活动、用户、帖子和失败原因计算稳定哈希桶，只保存配置比例的无效详情：

```text
bucket = hash(activity_id, user_id, post_id, reason) % 100
save = bucket < sample_percent
```

确定性采样的好处是：同一条重放事件始终得到相同决定，不会每次重放都随机产生一份新记录。

有效帖子仍默认保存；无效帖子只有调试开关打开或命中采样才保存。

### 7.6 为什么还要裁剪存储结构

运行时校验可能需要完整帖子对象，但持久化排障通常只需要归因字段、状态、主题、字数和图片标记。

因此运行时详情和存储详情使用不同结构，写入前转换为紧凑模型，避免把正文预览和大量重复字段长期保存。

### 7.7 结果怎样讲

可以确认的工程效果是：活动结束后的重放事件会在进入 fanout、锁、报名 RPC 和大对象写入之前被拦截；无效诊断详情由全量写改为可控采样，并缩小了单条数据体积。

如果没有准确资源监控，不能编造“CPU 下降多少”或“节省多少存储”。

### 7.8 FaaS 高频追问

#### 为什么消费者必须假设消息会重复

消息系统通常提供至少一次投递，消费者超时、重平衡和人工回放都会产生重复。业务写入需要幂等。

#### 为什么不直接丢弃所有晚到消息

有些业务允许补算。需要按活动类型明确迟到窗口和补算模式，而不是写死所有事件一律丢弃。

#### 双层 guard 会不会重复

重复的是判断，不是职责。入口优化资源，处理器守住业务不变量，能抵抗未来新入口。

#### 确定性采样有什么缺点

小样本活动可能碰巧没有命中；需要允许临时调高采样率或打开定向调试，并控制开关时长。

## 八、跨项目看一致性和幂等

### 8.1 四种一致性模型

| 场景 | 模型 | 原因 |
| --- | --- | --- |
| 抽卡机会与卡片实例 | 本地强事务 | 必须一起成功或失败 |
| 卡片与外部掉落奖品 | 主结果强一致，副作用最终一致 | 外部系统不在本地事务内 |
| 全站进度 | 最终一致快照 | 允许短暂延迟，换取读稳定 |
| 徽章发放 | 用户级幂等 + 可重试 | 批量中允许部分成功 |

### 8.2 五层幂等

```text
入口幂等
  request_id / batch_id

业务流水幂等
  flow_id 唯一且校验业务参数

状态迁移幂等
  WHERE status = expected_status

外部副作用幂等
  stable win_id / grant_key

补偿任务幂等
  扫描未完成状态，重复执行不产生第二份资产
```

只说“加了唯一索引”通常还不够。面试官真正想知道的是：重复发生在什么层、旧结果怎样重建、冲突怎样区分、外部系统怎样保证只执行一次。

### 8.3 锁、CAS 和唯一索引分别解决什么

| 手段 | 解决的问题 | 不能替代什么 |
| --- | --- | --- |
| 分布式锁 | 减少同一用户/资源并发进入 | 不能替代最终幂等 |
| 条件更新 CAS | 保证状态只能从预期值迁移 | 不能保存完整审计 |
| 唯一索引 | 并发下最终防重复 | 不能提供友好重放结果 |
| 业务流水 | 解释变化来源和结果 | 不能单独阻止并发 |

最可靠的实现通常组合使用，而不是选择一个万能方案。

## 九、面试官继续追问时怎么组织回答

每个问题按照五步回答：

```text
业务不变量
  -> 失败或并发场景
  -> 数据和状态设计
  -> 恢复与观测
  -> 自己的所有权边界
```

例如“赠卡如何避免一张卡被两个人领走”：

> 业务不变量是一张具体实例只能转移一次。创建赠卡时先把实例从 held 锁成 locked；领取时在一个事务里转移 owner、写双方流水，并用 `available -> completed` 条件更新竞争最终领取权。两个用户并发时只有一个条件更新成功；另一方返回已领取。取消和过期会释放 locked 实例。前端只负责展示状态，最终正确性由服务端实例状态和 CAS 保证。

这比回答“我们加了锁”完整得多。

## 十、所有权怎样如实表达

这些服务端内容并不是全部由一个人独立完成。

可以明确讲的个人工作包括：自己实际负责的进度解锁全栈链路、徽章自动与批量发放能力、多仓重构中的具体模块、压测隔离准备，以及事件消费写放大修复。

集卡活动的完整服务端抽卡引擎、资产状态机和后续热点锁治理主要由服务端同事完成；如果自己的职责是前端所有权、接口对齐、联调验收和线上问题协作，就应该这样说。可以深入解释服务端原理，但不能把理解能力伪装成代码所有权。

一段合适的表达是：

> 集卡活动的前端由我独立负责，服务端核心抽卡和资产规则由后端同事实现。我在接口契约、异常状态、真机联调和结果验收中深入理解了这套链路，所以能够解释请求幂等、卡片实例、赠求卡状态和动画降级为什么这样设计；如果问到我亲自完成的服务端工作，我会重点展开进度解锁、徽章发放、重构迁移、压测隔离和事件写放大治理。

## 十一、两分钟服务端总述

> 我在实习中不只做过活动页面，也参与并负责过多类活动服务端能力。对复杂活动，我会先区分配置、用户资产、业务流水、聚合数据和外部副作用，再为不同数据选择一致性模型。
>
> 例如集卡抽卡里，单抽和十连由服务端统一处理。机会使用累计发放、累计消耗和幂等流水管理；十连在一个主事务里完成机会扣减、保底、卡片实例、编号、抽卡记录和资产流水。赠卡创建时锁定具体实例，求卡在好友响应时才选择实例；集齐后兑换抽奖机会因为跨系统，拆成占用卡片和幂等发机会两个可恢复阶段。随机掉落则在抽卡提交后履约，失败进入补偿，不回滚已经确定的卡片。
>
> 我亲自负责过进度解锁和徽章发放等服务能力。全站进度通过离线聚合写快照，C 端常数时间读取；徽章把自动达标和运营批量工具统一到领域接口，处理分组、活动幂等、有效期和用户级失败结果。我还参与多仓重构和高流量活动压测，把协议、领域、离线任务和事件函数的职责拆开，并通过新旧链路对比和全链路压力标记控制迁移与上线风险。
>
> 我认为这些项目最有价值的地方，不是用了多少中间件，而是我能把业务不变量转成事务、状态机、幂等键、补偿和可观测证据，再明确哪些结果是个人技术动作、哪些是团队业务成果。
