上一篇分清了 workflow 和 agent，也列了五种基础模式。这一篇把常见的编排模式摊成八种讲细。为了不被术语绕晕，全程用同一套比喻：**把每个 agent 当成公司里的一个人，模式的区别只是“这家公司怎么分活”。**

## 八种模式速查

| 模式 | 一句话比喻 | 子任务怎么定 | 拓扑 |
| --- | --- | --- | --- |
| Orchestrator-Worker | 项目经理临时拉人 | 运行时动态 | 星形（主管→子 agent） |
| Pipeline / Chaining | 工厂流水线 | 固定顺序 | 线性 |
| Parallel fan-out | 同时派发的快递 | 固定、独立 | 星形、并行 |
| Map-Reduce | 分头数人头再汇总 | 数量动态 | 扇出 + 聚合 |
| Hierarchical | 公司组织架构图 | 分层动态 | 树形 |
| Debate / Voting | 专家评审会 / 陪审团 | 多方共识 | 网状、多轮 |
| Evaluator-Optimizer | 作者和编辑反复改稿 | 循环 | 成对、环形 |
| Routing | 医院分诊台 | 按类别 | 分支 |

## 1. Orchestrator-Worker：项目经理临时拉人

一个中心“编排者”接到任务，**运行时**才决定拆成哪些子任务、派给几个工人，最后汇总。Anthropic 的研究系统就是它：主管（Opus 4）分析查询、定策略、派生 3–5 个子 agent（Sonnet 4），各自带独立上下文并行探索，再回传给主管合成；不够就再派。

- **适合**：复杂、开放、**子任务无法预先确定**的活——深度研究、范围可变的多文件改代码。
- **不适合**：需要全程共享上下文、agent 间强依赖的活；而且极贵。

## 2. Pipeline / Prompt Chaining：工厂流水线

把任务拆成**固定顺序**的步骤，上一道工序的产物流到下一道，工序间可加程序化“质检闸门”。用延迟换准确率，因为每一步都更聚焦、更简单。

- **适合**：能干净拆成固定步骤的可预测任务，比如“先写大纲（过校验）→ 再写全文”“先生成文案 → 再翻译”。
- **不适合**：步骤无法预知、或串行延迟受不了的场景。

## 3. Parallel fan-out：同时派发的快递

把**互相独立**的子任务拆开，在多个 LLM 上并发跑，再用程序合并。和编排者的区别是：这里的分工通常是**预先定好**的，不是临场决定的。

- **适合**：提速 + 关注点分离，比如把内容安全审查与主回答并行，互不拖慢。
- **不适合**：子任务彼此依赖、或结果难合并。

## 4. Map-Reduce：分头数人头再汇总

fan-out 的特化版，明确两阶段。**Map**：把大任务切成 N 份并行处理（N 常常运行时才定）；**Reduce**：把所有结果聚合成最终答案。LangGraph 用 `Send` API 动态扇出、用 state reducer 安全合并并发结果。

- **适合**：对大量条目的“易并行”工作——批量总结多文档、把宽搜索分到多个来源、批量打分打标。
- **不适合**：分片之间需要互相看到对方；reduce 步骤本身也可能成瓶颈或丢细节。

## 5. Hierarchical：公司组织架构图

多层监督——顶层主管协调若干中层主管，每个中层再带一队工人（“主管的主管”，树形）。上层可以审查下层的多样输出、在错误向上传播前过滤掉。研究指出**树形拓扑对故障/异常 agent 最有韧性**，因为高层能做错误恢复。

- **适合**：能按领域拆开的超大任务（如“研究团队”+“写作团队”）。
- **不适合**：监督层越多，协调开销和延迟越大，简单任务下杀鸡用牛刀。

## 6. Debate / Voting：专家评审会、陪审团

多个独立 agent 各自给答案；多轮中每个 agent 看到别人上一轮的回答、据此批判和更新自己，几轮后收敛到共识。更简单的“投票”变体跳过辩论，只把同一问题跑很多遍取多数。无需训练、对黑盒模型也能用。

- **适合**：提升事实准确性和推理质量、减少幻觉，数学/策略推理尤其有效。
- **不适合**：成本——M 个 agent × R 轮把调用量翻好几倍，还可能“自信地一起错”，几轮后边际收益递减。

## 7. Evaluator-Optimizer：作者和编辑反复改稿

一个 LLM（生成器）产出结果，第二个 LLM（评审）对照标准打分并给具体反馈，生成器据此修订，循环到评审满意。和辩论的区别：两个角色**不对称**（产出 vs 评判），且是**串行精修**而非并行求共识。

- **适合**：有清晰评估标准、迭代能切实改善、且模型反馈接近人类批评的任务——文学翻译、复杂搜索、要过检查的代码。
- **不适合**：缺乏客观标准、评审分不清好坏时，只会徒增成本，还可能反复横跳。

## 8. Routing：医院分诊台

第一步先给输入分类，再导向若干专门 agent 之一，每个有自己定制的提示和工具。关注点分离——每类输入得到为它优化的处理，而不是一个通用提示包打天下。前提是分类要可靠。

- **适合**：输入类别清晰、各需不同处理；也用于成本优化（简单问题走小模型、难的走大模型）。
- **不适合**：类别边界模糊、分类器不可靠时，误分类会级联。

## 两组最容易混的对比

把读者最容易混的两对单独拎出来：

- **编排者 vs 流水线**：项目经理临时拉人 vs 工厂流水线。一句话——**流水线的步骤是写死的，编排者是看了任务才临时决定派谁、派几个。**
- **辩论 vs 评审循环**：陪审团（平等、并行、投票）vs 作者和编辑（不对等、串行、改稿）。辩论是多方求共识，评审循环是两角色顺序精修。

## 一句话总结

八种模式不是要你背全，而是给你一张“分活的地图”：任务可预测就流水线，要分类就路由，要提速且独立就并行/分而治之，要质量就辩论或评审循环，**真正开放、步骤无法预知的，才上 orchestrator-worker**。真实系统几乎都是这些模式的组合——下一篇先讲它们共同的引擎：上下文隔离。
