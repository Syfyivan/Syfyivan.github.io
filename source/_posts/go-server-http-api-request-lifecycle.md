写后端最容易从一个路由开始：

```go
POST /tasks
```

但这个路由背后其实有一条挺长的路：网关、服务进程、中间件、handler、service、数据库、缓存、下游服务，最后再把响应吐回去。HTTP 这一站，我想先把这条路看清楚。

## Handler 不应该太重

我比较喜欢把 handler 当成“协议适配层”。它做这些事就够了：

- 取参数；
- 做基础校验；
- 拿到当前登录用户；
- 调 service；
- 把业务错误翻译成 HTTP 响应。

业务规则别堆在 handler 里。否则以后换 RPC、补定时任务、加 MQ 消费入口时，同一套业务逻辑就要复制几遍。

一个简单分层就够用：

```text
handler -> service -> repository/client
```

不复杂，但能挡住很多混乱。

## 状态码要稳定

状态码不用玩得很花。关键是稳定。

- 参数错：`400`
- 没登录：`401`
- 没权限：`403`
- 资源不存在：`404`
- 重复提交或状态冲突：`409`
- 被限流：`429`
- 服务内部错误：`500`
- 下游不可用：`503`

对外响应也尽量统一：

```json
{
  "code": "TASK_NOT_FOUND",
  "message": "任务不存在",
  "request_id": "req_123"
}
```

内部日志可以很细，对外错误别把数据库、Redis、RPC 的细节直接露出去。

## 中间件放横切逻辑

中间件适合做这些事：

- request id；
- 访问日志；
- panic recovery；
- 鉴权；
- 限流；
- CORS；
- 指标；
- trace 传播。

中间件不要偷偷写业务。比如“订单能不能取消”这种规则，应该待在 service 里，而不是藏在某个 middleware。

## 超时比想象中重要

没有超时的接口，平时看不出问题；下游一慢，就开始堆 goroutine、堆连接、堆内存。

HTTP server 自己要有 read/write/idle timeout；调用数据库、Redis、RPC 时也要带 context。入口层最好从一开始就把 request-scoped context 往下传，不然后面补会很别扭。

## 幂等不要靠运气

客户端会重试，网关会重试，用户会连点两次。创建订单、支付回调、扣库存、发权益，这些接口都要考虑幂等。

常见做法不复杂：

- 客户端传幂等 key；
- 数据库加唯一约束；
- 状态机判断是否已经处理；
- 记录请求处理结果。

重点是别把“应该不会重复”当成设计。

## 一个练习

写一个任务 API：

- 注册登录；
- 创建任务；
- 修改任务；
- 完成任务；
- 分页列表；
- 统一错误响应；
- request id 和访问日志；
- 鉴权中间件；
- 每个请求带超时。

先用 `net/http` 或一个轻量框架都行。这里练的是入口层边界，不是框架熟练度。
