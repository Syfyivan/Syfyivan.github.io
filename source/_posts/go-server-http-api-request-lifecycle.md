服务端的第二站是 HTTP 与 API。很多人第一次写后端，是从“注册一个路由，返回一段 JSON”开始的。但真正的 API 设计远不止 handler 函数：一个请求进入系统后，会经历网关、负载均衡、路由匹配、中间件、鉴权、参数校验、业务处理、下游调用、错误映射和响应返回。

学 HTTP 与 API 的目标，是把“会写接口”升级成“能设计稳定的入口层”。

## 请求链路长什么样

一个典型请求大概是这样：

```text
Client
  -> DNS / CDN / LB
  -> Gateway
  -> Go HTTP Server
  -> Middleware
  -> Handler
  -> Service
  -> DB / Cache / RPC / MQ
  -> Response
```

在这个链路里，handler 只是入口层的一小段。真正需要设计的是边界：

- 哪些错误返回 4xx，哪些返回 5xx；
- 请求体大小有没有限制；
- 鉴权失败是否继续打到业务层；
- 下游超时时对用户返回什么；
- 同一个创建请求重试时会不会重复写数据；
- 日志、指标和 trace id 在哪里注入。

## 必须掌握的知识点

### HTTP 方法和状态码

常见约定是：

- `GET` 查询资源，不应产生副作用；
- `POST` 创建资源或提交动作；
- `PUT` 整体替换；
- `PATCH` 局部更新；
- `DELETE` 删除资源。

状态码也要有一致语义：

- `400` 参数错误；
- `401` 未登录；
- `403` 无权限；
- `404` 资源不存在；
- `409` 状态冲突或重复提交；
- `429` 触发限流；
- `500` 服务内部错误；
- `503` 依赖不可用或服务降级。

状态码不需要炫技，但必须稳定。调用方一旦依赖你的错误语义，频繁变化会造成联调和线上问题。

### 参数校验和统一错误响应

参数校验要尽早发生，最好在进入业务逻辑前完成。比如分页大小、必填字段、枚举值、时间范围、ID 格式都属于入口层责任。

统一错误响应可以类似：

```json
{
  "code": "TASK_NOT_FOUND",
  "message": "任务不存在",
  "request_id": "req_123"
}
```

内部日志可以记录详细错误栈，对外响应只暴露可理解、可处理的信息。

### 中间件链路

中间件适合放通用逻辑：

- request id 注入；
- 访问日志；
- panic recovery；
- 鉴权；
- 限流；
- CORS；
- 指标统计；
- trace 传播。

不要把业务逻辑塞进中间件。中间件应该回答“这个请求能不能进入业务层”和“如何记录入口层信息”，而不是决定订单状态或库存扣减。

### 超时和连接管理

HTTP 服务端至少要关注：

- read timeout；
- write timeout；
- idle timeout；
- 请求 body 大小；
- 下游 client timeout；
- 连接池大小。

没有超时的服务，在依赖卡住时会慢慢耗尽 goroutine、连接和内存。服务端稳定性很多时候不是“永不失败”，而是“失败时能快速释放资源”。

### 幂等设计

接口重试是常态。网络抖动、客户端超时、网关重试都会让同一个请求被处理多次。

需要重点做幂等的场景：

- 创建订单；
- 支付回调；
- 扣库存；
- 发放权益；
- 消息消费回调；
- 文件上传确认。

常见做法是使用幂等 key、唯一约束、状态机和请求记录表。不要只靠“客户端不会重复点”这种假设。

## Go 里的分层建议

一个简单但够用的结构是：

```text
handler  ->  service  ->  repository / client
```

handler 负责协议：

- 解析 request；
- 校验参数；
- 调用 service；
- 把业务结果映射成 HTTP response。

service 负责业务：

- 检查权限；
- 组织事务；
- 调用多个 repository 或 client；
- 决定状态流转。

repository/client 负责外部依赖：

- 数据库；
- Redis；
- RPC；
- MQ；
- 第三方 HTTP API。

这样做的好处是：HTTP 只是入口协议，将来换成 RPC、定时任务或 MQ 消费时，核心业务逻辑还能复用。

## 练习方式

写一个任务管理 API：

- 用户注册、登录；
- 创建任务、更新任务、完成任务；
- 分页查询任务列表；
- 统一错误码；
- request id 和访问日志；
- 鉴权中间件；
- 每个请求都有 context timeout；
- 用测试覆盖参数错误、未登录、资源不存在、重复提交。

不要急着上复杂框架。可以先用标准库 `net/http` 或轻量框架实现，重点是把入口层边界写清楚。
