## 一、故事正文

九境修到末了，青萝以为终于要学最玄妙的法术，长老却把她带回了最小的那间静室，案上只摆着一卷未写完的代码。长老说：“前八境你学的是理念、是体系、是会审，是远远地看一座宗门。今日是收官，要落到你**手上的规矩**——高质量编程。名不正则术不灵，一行代码若起错了名、用错了手，再好的设计也会塌。”

长老先指着卷上一句 `if (j == 1)`，又另写一句 `if (1 == j)`。青萝不解，二者岂非一样？长老道：“一样，却不一样。你若哪天手一抖把 `==` 写成了 `=`，`if (j = 1)` 编译器照样放行，错得无声无息；可 `if (1 = j)` 编译器立刻喝止，因为常量不能被赋值。把常量放左边，是让机器替你把关。”他又指另一句 `if (i > 5000)`，问这 5000 是什么。青萝答不上来。长老摇头：“这叫**魔数**。该写成 `if (i > MAX_NUM)`，名字一出，意义自明，别人读得懂，你改得动。”

接着长老传她「**命名的规矩**」。变量要用名词，函数要用动词；类名、函数名用大写字母开头，变量用小写开头，常量全大写加下划线；静态变量加前缀 `s_`，不得已的全局变量加 `g_`，类的数据成员加 `m_`，循环计数就用 `i`、`j`、`k`。青萝照着把一卷乱名一一正过来，果然神清气朗。

长老话锋一转，说起最凶的两样东西。“你向天地**借**了一块内存——用 `malloc` 或 `new`，便欠下一笔，用完必须用 `free` 或 `delete` 如数归还。借了不还，这块内存就再也回不来，这叫**内存泄漏**；每调一次函数丢一块，初时无事，终有一日系统内存耗尽，程序猝死。”青萝悚然。长老又道：“更险的是，你还了内存，手里那根指针却没松开。`free` 只销毁内存，不销毁指针；指针地址照旧，指的却是一堆垃圾——这便是**野指针**。它不是 `NULL`，`if (p != NULL)` 拦不住它，它会乱指一气，祸及四邻。对策只有一句：释放之后，**立即把指针置为 `NULL`**。”

青萝把这两条抄在掌心。她忽然懂了，所谓收官，不是更高的术，而是更稳的手。

## 三、概念正解

### 3.1 代码风格：两个例子

- **常量放比较式左边**：把 `if (j == 1)` 写成 `if (1 == j)` 更优秀，可防止把 `==` 误写成 `=`。`if (p = NULL)` 编译器认为合法，但 `if (NULL = p)` 会被编译器指出错误，因为 `NULL` / 常量不能被赋值。
- **用符号常量替魔数**：`if (i > MAX_NUM)` 优于 `if (i > 5000)`。`5000` 这类**魔数**意义不明、难维护，应定义为有描述性名称的常量。

### 3.2 命名规则（Windows 程序命名规则）

- **匈牙利命名法**：在标识符前加上反映其类型的前缀。
- 变量名用**名词**或“形容词+名词”；全局函数名用**动词**或“动词+名词”；类的成员函数只用**动词**（被省略的名词就是对象本身）。
- 用正确的反义词组命名互斥意义的变量或相反动作的函数。
- **大小写约定**：类名和函数名用**大写字母开头**的单词组合；变量和参数用**小写字母开头**；常量**全用大写字母，用下划线分割单词**。
- **前缀约定**：静态变量加 `s_`；不得已的全局变量加 `g_`；类的数据成员加 `m_`（避免与成员函数参数同名）；可为标识符加反映软件性质的前缀以防冲突。
- 循环计数变量用 `i`、`j`、`k`、`l`、`m`。
- 不要仅靠大小写区分相似标识符；尽量不要出现与标识符完全相同的局部变量和全局变量。

### 3.3 函数处理规则

- 参数书写要**完整**（写类型也要写参数名）；函数**没有参数时用 `void` 填充**；参数命名恰当、顺序合理。
- 参数若是**指针且仅作输入**，应在类型前加 `const`，防止指针在函数体内被意外修改。
- 输入参数若以值传递方式传对象，宜改用 **`const &`** 传递，省去临时对象的构造与析构，提高效率。
- 参数个数尽量控制在 **5 个以内**。
- **不要省略返回值的类型**；函数名与返回值类型在语义上不可冲突。
- **不要将正常值和错误标志混在一起返回**：正常值用输出参数获得，错误标志用 `return` 语句返回。
- 为支持链式表达等灵活性，原本无返回值的函数可附加返回值；在函数“出口处”检查 `return` 语句的正确性和效率。

### 3.4 文件结构

- **定义文件**有三部分：开头的版权与版本声明、对头文件的引用、程序的实现体（数据和代码）。
- **版权和版本声明**含：版权信息；文件名称、标识符、摘要；当前版本号、作者/修改者、完成日期；版本历史信息。
- **头文件结构**：
  - 用 `ifndef`/`define`/`endif` 结构产生预处理块，**防止头文件被重复引用**。
  - `#include <filename.h>` 引用**标准库**头文件（从标准库目录搜索）；`#include "filename.h"` 引用**非标准库**头文件（从用户工作目录搜索）。
  - 头文件中**只存放“声明”而不存放“定义”**；不提倡在头文件中出现 `extern int value` 这类全局变量声明。

### 3.5 程序的版式

- **空行**：每个类声明、每个函数定义结束后加空行；函数体内逻辑密切相关的语句间不加空行，其它地方加空行分隔。
- **代码行**：一行只做一件事（只定义一个变量或只写一条语句）；`if`、`for`、`while`、`do` 等语句自占一行，执行语句不得紧跟其后，**不论多少都要加 `{}`**；尽可能在定义变量的同时初始化（**就近原则**）。
- **对齐**：`{` 和 `}` 独占一行、位于同一列，与引用它们的语句左对齐；`{}` 内代码块在 `{` 右边数格处左对齐。
- **长行拆分**：代码行最大长度宜控制在 **70 至 80 个字符**以内；长表达式在低优先级操作符处拆分，操作符放新行之首；修饰符 `*` 和 `&` 应**紧靠变量名**（如 `int *x, y;`，此处 `y` 不会被误解为指针）。
- **注释**：注释是“提示”而非文档，不可喧宾夺主；代码本身清楚就不必加注释（如 `i++; // i 加 1` 多余）；边写边注释、改代码同时改注释保证一致；注释应准确易懂、避免缩写；注释放在代码上方或右方，**不可放在下方**。
- **类的版式**：两种方式——“以数据为中心”（private 数据在前）与“以行为为中心”（public 函数在前）；建议采用**以行为为中心**，因为用户最关心接口。

### 3.6 表达式

- 运算符较多时，**用括号确定操作顺序**，避免依赖默认优先级。
- 不要编写太复杂的复合表达式，也不要有多用途的复合表达式（如 `d = (a = b + c) + r;`）。
- 不要把程序表达式与数学表达式混淆：`if (a < b < c)` 是数学写法，在程序里**并不**表示 `if ((a<b) && (b<c))`，而成了费解的 `if ((a<b) < c)`。

### 3.7 if 语句：四类变量与零值比较（重点）

| 变量类型 | 标准写法 | 说明 |
| --- | --- | --- |
| 布尔变量 flag | `if (flag)` / `if (!flag)` | **不可**与 TRUE/FALSE 或 1/0 比较，`if (flag == TRUE)`、`if (flag == 1)` 都是不良风格 |
| 整型变量 value | `if (value == 0)` / `if (value != 0)` | 用 `==` / `!=` **直接与 0 比较**；不可写 `if (value)` 模仿布尔 |
| 浮点变量 x | `if ((x >= -EPSINON) && (x <= EPSINON))` | **不可**用 `==` / `!=` 与任何数字比较（浮点有精度限制），转化为 `>=` / `<=`，`EPSINON` 是允许误差 |
| 指针变量 p | `if (p == NULL)` / `if (p != NULL)` | 用 `==` / `!=` 与 `NULL` 比较；可写 `if (NULL == p)` 防止误写成 `if (p = NULL)` |

`if/else/return` 组合应把 `if (condition) return x; return y;` 改写为 `if (condition) {return x;} else {return y;}`，或更简练的 `return (condition ? x : y);`。

### 3.8 for 循环控制变量

- **不可在 for 循环体内修改循环变量**，防止循环失去控制。
- 建议循环控制变量采用**半开半闭区间**写法：`for (int x = 0; x < N; x++)` 优于 `for (int x = 0; x <= N-1; x++)`。

### 3.9 内存管理（重点）

**三种内存分配方式**：

1. **静态存储区**：编译时分配，整个运行期间存在，如全局变量、`static` 变量。
2. **栈**：执行函数时局部变量在栈上创建，函数结束自动释放；分配内置于指令集，**效率高但容量有限**。
3. **堆（动态内存分配）**：运行时用 `malloc`/`new` 申请，由程序员用 `free`/`delete` 释放；**生存期自定、灵活，但问题也最多**。

**常见内存错误及对策**：

- 内存分配未成功却使用：使用前检查指针是否为 `NULL`；参数指针在函数入口用 `assert(p != NULL)`，自行申请用 `if (p == NULL)` 防错。
- 分配成功但未初始化就引用：内存缺省初值无统一标准，**无论何种方式创建数组都要赋初值**。
- 越过内存边界：如数组下标“多 1 / 少 1”，for 循环次数易错导致越界。
- **内存泄漏**：忘记释放内存；`malloc` 与 `free`（`new` 与 `delete`）**使用次数必须配对相同**，否则必有错误。
- **释放后继续使用**：return 误返回栈内存指针/引用；或释放后未将指针置 `NULL`，导致产生**野指针**。

**野指针**：不是 `NULL` 指针，是指向“垃圾”内存的指针。`free`/`delete` 只释放内存、不销毁指针，p 释放后地址不变（非 `NULL`），`if (p != NULL)` 起不到防错作用。成因有二：①指针变量未初始化（缺省值随机，乱指）；②指针被 `free`/`delete` 后未置 `NULL`。对策：申请后立即查是否 `NULL`、数组与动态内存赋初值、申请释放配对、**释放后立即置 `NULL`**。

### 3.10 const 的魅力与编程规则

- `const` 可修饰函数的参数、返回值乃至函数定义体，被修饰者受强制保护，预防意外变动，提高健壮性。**只能修饰输入参数**（修饰输出参数会使其失去输出功能）。
- 输入参数用“指针传递”时加 `const` 防止指针被改动；非内部类型参数 `void Func(A a)` 效率低（产生临时对象），改 `void Func(A &a)` 提高效率，但引用传递可能改变实参，故最终用 **`void Func(const A &a)`**。
- **Java 编程规则**：类名首字母大写、字段/方法/对象首字母小写；包名全小写；为每个类考虑置入 `main()` 测试代码；让一切尽可能 `private`；避免“魔术数字”应创建常数；警惕“巨大对象综合症”“分析瘫痪”“过早优化”。

## 五、考点卡

- **判断题抓手**：
  - “头文件中可以存放定义。”——错，头文件只放声明不放定义。
  - “`malloc` 与 `free` 不必次数相同。”——错，必须配对相同，否则内存泄漏。
  - “释放内存后 `if (p != NULL)` 能防止野指针。”——错，p 释放后地址非 `NULL`，该判断失效，须立即置 `NULL`。
  - “浮点变量可以用 `==` 直接与 0 比较。”——错，浮点有精度限制，须用 `EPSINON` 范围比较。
- **选择题抓手**：看到 `s_`/`g_`/`m_` → 命名前缀规则；看到 `ifndef`/`define`/`endif` → 防止头文件重复引用；看到 `<>` 与 `""` → 标准库 vs 非标准库头文件；看到“栈/堆/静态存储区” → 三种内存分配方式。
- **填空题抓手**：
  - 内存分配方式有三种：从 **静态存储区** 分配、在 **栈** 上创建、从 **堆**（动态）上分配。
  - `malloc`/`new` 申请的内存必须用 **`free`/`delete`** 释放，且次数必须 **配对相同**。
  - 释放内存后应立即将指针设置为 **`NULL`**，防止产生 **野指针**。
  - 函数参数个数尽量控制在 **5** 个以内。
- **简答题答题骨架**：“什么是内存泄漏与野指针，如何防范？”——①定义内存泄漏（忘记释放，调用一次丢一块，终致内存耗尽）；②定义野指针（指向垃圾内存的非 NULL 指针，`if (p != NULL)` 无效）；③野指针两大成因；④对策四条（申请后查 NULL、赋初值、申请释放配对、释放后立即置 NULL）。
- **设计题答题骨架**：给一段代码做编程规范评审——逐项检查命名（前缀/大小写/魔数）、函数（参数数/const/void/返回值）、版式（`{}`/对齐/初始化）、if 与 0 比较（四类）、内存（配对/置 NULL），指出问题并给出修正写法。

## 六、小试炼

1. **（判断）** `if (flag == TRUE)` 是判断布尔变量的推荐写法。
   参考答案：错。布尔变量标准写法是 `if (flag)` / `if (!flag)`，不可与 TRUE/FALSE 或 1/0 比较。**为什么**：TRUE 的具体值依实现而定，直接比较不可靠且属不良风格。

2. **（选择）** 为防止头文件被重复引用，应使用哪种结构？
   A. `try/catch/finally`　B. `ifndef/define/endif`　C. `for/while/do`　D. `public/private`
   参考答案：B。**为什么**：`ifndef/define/endif` 预处理块是防止头文件重复引用的标准手段。

3. **（填空）** 浮点变量 x 与零比较不能写 `if (x == 0.0)`，应转化为 `if ((x >= ______) && (x <= EPSINON))`。
   参考答案：`-EPSINON`。**为什么**：浮点有精度限制，须在允许误差 `EPSINON` 范围内判断。

4. **（简答）** 简述三种内存分配方式及各自特点。
   参考答案：①静态存储区——编译时分配，运行期间始终存在（全局变量、static）；②栈——函数局部变量自动创建/释放，效率高但容量有限；③堆——运行时 `malloc`/`new` 申请、`free`/`delete` 释放，灵活但问题最多。**为什么**：这是内存管理的基础分类，考点高频。

5. **（设计）** 指出 `int* foo(A a) { int x; if(x==NULL){} ...; free(p); return p; }` 中的规范问题。
   参考答案要点：值传递对象应改 `const A &a`；局部变量 `x` 未初始化就使用（就近初始化）；整型/指针与 0/NULL 比较混用，应分清四类；`free(p)` 后 `p` 未置 `NULL` 即返回，产生野指针；返回值类型与命名应一致、不返回栈内存指针。**为什么**：综合考查命名、函数、版式、if 比较、内存五大块。

## 七、易错点

- 把“声明”和“定义”混为一谈：头文件**只放声明不放定义**，别把函数体或变量定义写进 `.h`。
- 把四类 if 比较搞混：布尔用 `if (flag)`、整型用 `== 0`、浮点用 `EPSINON` 范围、指针用 `== NULL`，**四类各不相同**，最易在浮点和布尔上失分。
- 以为 `free` 后指针就安全：`free`/`delete` 只释放内存、**不销毁指针**，必须**立即置 `NULL`**，否则成野指针，`if (p != NULL)` 拦不住。
- 把内存泄漏和野指针混为一谈：泄漏是“借了不还”（忘记 `free`），野指针是“还了不松手”（释放后继续用）。
- 只记故事不写术语：答题要落到“魔数、匈牙利命名法、`ifndef/define/endif`、`const &`、半开半闭区间、内存泄漏、野指针”等课件原词。
