缓存最容易让人产生错觉：把 Redis 加上，系统就快了。实际上，缓存不是更快的数据库，而是一份有代价的副本。它能提升读性能、保护数据库、降低延迟，但也会带来一致性、失效、热点和故障降级问题。

学缓存时要先问一个问题：这份数据可以短暂不一致吗？如果答案是否定的，就不要轻易缓存，或者要设计更强的同步机制。

## 缓存在链路里的位置

典型读链路：

```text
HTTP/RPC
  -> Service
  -> Cache
  -> Database
```

缓存命中时直接返回，未命中时查数据库，再写回缓存。这个模式叫 cache-aside，也是业务系统里最常见的模式。

它看起来简单，但每一步都有坑：

- 缓存未命中时会不会大量请求同时打到数据库；
- 数据更新后缓存怎么失效；
- 缓存里存空值还是不存；
- 热点 key 会不会打爆单个 Redis 分片；
- Redis 不可用时系统是失败还是降级。

## 必须掌握的知识点

### Cache-aside

读流程：

1. 先读缓存；
2. 命中则返回；
3. 未命中读数据库；
4. 把数据库结果写缓存；
5. 返回结果。

写流程常见做法是：

1. 先写数据库；
2. 再删除缓存。

为什么不是“先删缓存再写库”？因为删完缓存后，如果还没写库，另一个请求可能读到旧数据库值并重新写入缓存，导致旧数据长期存在。

为什么不是“写库后更新缓存”？因为复杂对象更新容易丢字段，也可能在并发写入时把旧值覆盖进缓存。删除缓存更简单，下一次读再重建。

### 一致性是概率问题

缓存和数据库很难做到绝对强一致。常见策略包括：

- 先写库再删缓存；
- 删除失败后重试；
- 通过 MQ 广播缓存失效；
- 设置合理 TTL；
- 对关键数据短 TTL 或不缓存；
- 对强一致读直接查库。

不要把缓存一致性描述成“永远一致”。更准确的表达是：在什么时间窗口内可能不一致，业务是否接受，如何修复。

### 穿透、击穿、雪崩

缓存穿透：请求的数据根本不存在，每次都打到数据库。解决方式包括空值缓存、布隆过滤器、参数校验。

缓存击穿：热点 key 过期瞬间，大量请求同时查库。解决方式包括互斥重建、逻辑过期、热点 key 永不过期加后台刷新。

缓存雪崩：大量 key 同时过期，数据库压力骤增。解决方式包括 TTL 加随机抖动、分批预热、限流和降级。

### Redis 数据结构

Redis 不只是 string：

- string：简单对象、计数器、分布式锁；
- hash：用户资料、配置对象；
- list：简单队列；
- set：去重集合；
- zset：排行榜、延迟任务、按时间排序；
- stream：轻量消息流。

数据结构选错，会让后续查询和维护很难。比如排行榜用 zset 天然合适，用 string 拼 JSON 就会很笨重。

### 分布式锁要谨慎

Redis 锁常见问题：

- 锁没有唯一 value，释放时误删别人的锁；
- 业务执行超过锁过期时间；
- 续租失败；
- 拿不到锁时没有降级路径；
- 依赖锁保证强一致，但没有补偿机制。

分布式锁适合降低并发冲突，不适合当作唯一正确性保障。真正关键的唯一性和扣减逻辑，仍然要落到数据库约束、乐观锁或状态机上。

## 练习方式

给任务系统加 Redis 缓存：

- 缓存任务详情；
- 缓存用户资料；
- 更新任务后删除任务缓存；
- 对不存在的任务写短 TTL 空值缓存；
- 给缓存 TTL 加随机抖动；
- 对热点任务详情加互斥重建；
- 模拟 Redis 不可用时直接查库并打降级日志。

练习时不要只看延迟下降，也要观察数据库 QPS、缓存命中率、错误率和降级次数。
