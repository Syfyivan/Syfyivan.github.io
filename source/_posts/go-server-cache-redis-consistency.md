缓存这东西很诱人：加一层 Redis，接口立刻快一截。但我现在会先问一句：这份数据脏几秒，业务能不能接受？

如果不能接受，就别轻易缓存。缓存不是数据库的替身，它只是一个会过期、会丢、会和数据库短暂不一致的副本。

## 先从旁路缓存开始

最常见的读法是：

```text
读 Redis
  -> 命中就返回
  -> 未命中查数据库
  -> 写回 Redis
```

写法一般是：

```text
先写数据库
再删缓存
```

我会优先用“删缓存”，而不是“更新缓存”。因为真实业务对象经常不是一个字段，更新缓存很容易漏字段，也容易在并发场景下把旧值写回去。删掉之后让下一次读重建，简单一点。

## 一致性别说满

缓存和数据库很难一直同步。比较诚实的说法是：允许多久不一致，怎么缩短窗口，出问题怎么补。

常用办法：

- 缓存设置 TTL；
- 写库后删缓存；
- 删除失败要重试；
- 关键数据短 TTL；
- 强一致场景直接查库；
- 通过 MQ 广播缓存失效。

这里没有银弹。不同业务能接受的不一致窗口不一样。

## 三个老坑

缓存穿透：请求的数据根本不存在，每次都打到数据库。可以缓存空值，或者用布隆过滤器先挡一下。

缓存击穿：热点 key 正好过期，一堆请求同时查库。可以互斥重建，或者逻辑过期后后台刷新。

缓存雪崩：一大片 key 同时过期。TTL 加随机抖动是很朴素但有效的办法。

这些词看起来像八股，但线上真会遇到。尤其是热点 key，压测时不造出来，上线后才第一次见就很狼狈。

## Redis 数据结构别乱选

string 最通用，但不是所有东西都该塞 JSON。

- 用户资料：hash 可能更方便局部更新；
- 排行榜：zset；
- 去重集合：set；
- 简单计数：string；
- 延迟任务：zset 或更合适的队列系统；
- 消息流：stream 可以玩，但别替代正经 MQ。

选结构时想清楚以后怎么查、怎么删、怎么过期。

## 分布式锁少用一点

Redis 锁能用，但不要迷信。锁过期、业务超时、释放错锁、续租失败，这些都要考虑。

我更愿意把它当成“降低并发冲突”的工具，不把它当业务正确性的最后防线。关键约束还是尽量落到数据库条件更新、唯一约束、状态机这些地方。

## 一个练习

给任务系统加缓存：

- 任务详情走 cache-aside；
- 用户资料走缓存；
- 更新任务后删除缓存；
- 不存在的任务缓存一个短 TTL 空值；
- 热点任务加互斥重建；
- Redis 挂掉时降级查库并打日志。

做完以后看三组数：数据库 QPS、缓存命中率、接口 P95。只看平均延迟，很容易把问题看漏。
