## AI 观察

### 1. 用户说“变慢了”，首先要拆成速度、额度和任务复杂度

今天群里的反馈很有代表性：有人说修 3 个 bug 花了约 12 分钟，有人回忆自己用 `max` 起手通常要更久，也有人在额度用尽后切换 Spark。它们都是真实的使用感受，但不是同一个指标。

“变慢”至少可能来自四层：模型首 token 延迟变长，工具调用或 CI 变慢，模型在更高推理档位消耗更多 token，或者任务本身进入了更多探索、测试和回退步骤。如果把这些都压成一个“模型速度”，产品团队就无法判断应该扩容推理服务、优化工具链、降低默认 effort，还是改进任务拆解。

更麻烦的是，速度和额度是耦合的。官方 Codex 定价页明确说明，速度配置会增加适用模型的 credit 消耗，因此会更快用完包含额度；同一页面还写明，本地消息与云端对话共享五小时窗口，并可能叠加周限额。也就是说，用户感知到的“快一点”可能换来“更早触顶”，而“切小模型”可能延长可用时间，却改变结果质量和工具行为。

这解释了为什么额度页面不能只显示一个百分比。用户真正需要的是：当前任务使用了哪个模型和 effort，消耗了哪一个窗口，预计何时恢复，是否还有周限额，切换到哪个模型会怎样，以及当前任务能不能安全地从中断点继续。

### 2. 额度不是一个数，而是一组带作用域的预算

今天的飞书讨论里，“5 小时限制”和“一周限制”被放在同一句话里，正好暴露了预算模型的复杂性。官方页面给出的模型表按本地消息 / 5 小时展示额度，并提醒可能存在额外周限额；Spark 则有单独的使用限制，且官方说明它会随需求调整。

因此，agent 平台至少要区分：账号或工作区、模型、入口（本地 / 云端 / code review）、时间窗口、速度档位、任务类型和计费方式。一个“还剩 30%”的数字，如果没有这些维度，几乎无法指导行动：它可能是当前五小时窗口的剩余比例，也可能是周限额；可能只对应一个模型，也可能和多个 agentic 功能共享。

这也是为什么群里会出现“本地还是一周限制”“下次重置是什么时候”的疑问。它们未必表示产品规则互相矛盾，更可能是不同入口的状态展示没有把窗口和作用域说清楚。官方状态页过去也记录过一次 Codex 额度消耗异常：部分账号受到滥用与欺诈防护系统的错误限流影响。那是已解决的历史事件，不能直接解释今天的体验，但足以说明“额度消耗异常”需要服务端证据，而不是靠用户截图猜测。

### 3. 模型回退的关键不是“换一个”，而是告知代价并保住任务状态

当用户从 GPT 切到 Spark，或者从高能力模型切到更轻的模型，系统实际做了三件事：改变推理能力，改变延迟和成本，改变额度消耗速度。若客户端只显示一个模型名称，用户无法知道任务是否会重新规划、已有上下文是否保留、工具权限是否变化、之前生成的补丁是否仍然有效。

官方对 GPT-5.6 Terra 和 Luna 的更新强调了价格性能改善，并说明订阅价格与配额预算保持不变，只是 Terra 和 Luna 的使用会消耗更少 credit。这个信号很重要：模型更高效，不等于用户突然获得无限额度；产品可以用效率改善“延长任务续航”，却仍然需要清晰展示预算边界。

一个可用的回退策略应该把模型切换写入任务事件：`fallback_requested → policy_checked → context_compacted → model_switched → resumed → result_verified`。如果切换发生在修改文件之后，恢复点应指向最后一个已验证的补丁，而不是重新从最初提示开始。对于代码任务，模型回退还应保留测试结果、工具调用和未完成的检查清单。

## 前端 / 服务端 / 客户端工程观察

### 前端：把“慢”和“没额度”展示成两套不同的解释

agent 页面可以先建立一个最小的任务状态面板：

| 用户看到的现象 | 应展示的可观测状态 | 下一步动作 |
| --- | --- | --- |
| 首字慢、持续生成 | 模型、effort、首 token 延迟、排队时间 | 等待或切换速度档位 |
| 工具调用慢 | 工具名、调用耗时、重试次数、外部系统 | 查看工具或取消当前步骤 |
| 额度快用完 | 当前窗口、周窗口、预计重置、预算消耗 | 切小模型、购买 credit 或等待 |
| 切到 Spark / 轻量模型 | 回退原因、能力差异、上下文保留情况 | 接受回退或暂停任务 |
| 任务中断 | 最后成功事件、恢复点、是否可安全重试 | 从恢复点继续 |

进度条之外，前端还应给出“这次任务为什么用了这么多”的摘要：模型输出 token、工具调用次数、测试轮数、缓存命中情况和是否启用了更高速度档位。不要把模型供应商、计费窗口和任务阶段混成一张模糊的仪表盘。

### 服务端：预算决策要可解释，重试要可证明安全

服务端应在每次 agent turn 开始时生成预算快照，至少绑定：`task_id`、用户 / 工作区、入口、模型、effort、速度档位、预算窗口、额度消耗、代码版本和工作区版本。每一次限流、回退、重试和恢复都写入事件，而不是只返回一个 `429` 或“请稍后再试”。

重试尤其需要证据链。模型调用超时不代表工具没有副作用；额度页面刷新失败也不代表额度没有消耗；切换模型前的上下文压缩也不应丢掉最后一个可验证产物。服务端要区分“请求未发出”“请求已执行但回执丢失”“请求失败且可安全重试”三种状态，并为外部写操作绑定幂等键。

可以把任务状态设计成：

`created → running → waiting_for_tool → budget_warning → fallback_pending → resumed → verifying → delivered`

如果在 `budget_warning` 阶段决定切换模型，系统应该先完成策略检查，再确认当前工作区和测试状态，最后恢复任务；而不是让客户端自行拼接一条新提示，导致上下文、权限和成本记录断裂。

### 客户端：本地、云端、IDE 和移动端应观察同一个任务

Codex app 官方介绍把多 agent 并行、线程隔离、worktree 和长任务协作放在核心位置。这说明客户端的任务单位已经不是“一轮聊天”，而是可持续观察的工作对象。桌面端、IDE、CLI 和移动端可以是不同的控制面，但应该共享 `task_id`、模型、预算、审批、恢复点、变更摘要和验证结果。

客户端还应明确标注当前任务属于本地执行还是云端执行，额度是共享窗口还是独立窗口，模型回退是否由用户触发，以及当前配置来自个人、项目还是工作区策略。特别是当用户从本地 GPT 切到 Spark 时，要让他知道这是额度策略触发的回退、手动选择，还是服务端负载保护，而不是用“模型不可用”一概带过。

### 前端 / 服务端 / 客户端的共同边界：不要用体验样本冒充系统指标

“修 3 个 bug 花了 12 分钟”是一个任务样本，不是模型的 P95；“有人觉得 GPT 变慢”是体验信号，不是全局故障；“一周限制还在”是账号界面观察，也不是所有计划的统一规则。产品应该在界面和日志中同时保留样本级证据与聚合级指标，避免把个别用户的窗口、模型或地区配置外推到整个系统。

## 值得跟进的动作

1. 给每个 agent 任务增加预算卡片：当前模型、effort、速度档位、五小时窗口、周窗口、已消耗 credit、预计重置时间和可用回退选项。
2. 建立统一的“变慢”诊断字段，至少拆出排队、首 token、工具、CI、模型生成、测试和人工审批耗时，并在客户端显示对应解释。
3. 设计模型回退协议：记录触发原因、能力差异、上下文压缩结果、恢复点和验证命令；回退不能等价于新开一个聊天。
4. 对额度刷新、重试和外部写操作使用幂等键，验证“已执行但回执丢失”时不会重复创建 PR、重复发消息或重复修改文件。
5. 在本地、云端、IDE 和移动端统一任务事件模型，让用户能从任意入口看到同一个任务的预算、审批和恢复状态。
6. 为高 effort / Fast / Spark 等不同档位建立小型回归基准：记录质量、延迟、token、credit、工具调用和恢复成功率，避免只用主观速度做选型。
