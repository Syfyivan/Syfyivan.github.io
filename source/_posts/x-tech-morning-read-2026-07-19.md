## AI 观察

### 1. 模型竞争已经从“谁更强”扩展到“谁能稳定供给”

今天最值得注意的 X 信号，不是又一张榜单，而是 Anthropic 对 Claude Fable 5 订阅策略的重新安排：从 7 月 20 日起，Max 和 Team Premium 计划按标准周额度的 50% 包含 Fable 5；Pro 和 Team Standard 则改为使用额度，并获得一次性的 100 美元额度。可以直接看 [Claude 官方 X 帖文](https://x.com/claudeai/status/2078302415804379218)，再对照 [Simon Willison 对原帖的记录](https://simonwillison.net/2026/Jul/18/claude-make-fable-5-permanent/) 和 [The Decoder 的交叉说明](https://the-decoder.com/anthropic-slashes-claude-fable-5-limits-in-max-and-team-premium-and-pushes-pro-users-toward-api-pricing/)。

这件事的工程含义比套餐新闻更重要：当模型进入长时间、多轮工具调用和大上下文工作流后，产品约束不再只有模型质量，还包括推理成本、可用容量、每周额度和高峰期的服务稳定性。Anthropic 的 [Fable 5 页面](https://www.anthropic.com/claude/fable) 也把它定位为适合长时间、异步、复杂编码工作的模型，并明确说明了安全路由和 30 天数据保留等边界。

因此，团队在选模型时不应只记一个“最强模型”标签，而要同时记录：任务成功率、每个任务的 token 消耗、峰值排队/限流行为、失败后是否能恢复，以及套餐或 API 政策变化时的替代路径。

### 2. 评测的重点正在从“能不能写代码”转向“这份改动是否值得合并”

今天公开侧出现了一个很实用的工程信号：[Cognition 的 FrontierCode Leaderboard](https://cognition.com/frontiercode) 把 `mergeability` 作为核心问题：维护者是否真的愿意合并这份 PR。它把正确性、测试质量、范围控制、代码风格和仓库规范放在同一套评测里，还把查阅原始 PR 等“带答案的网络来源”视为不公平使用并归零。

这比单纯比较 pass@1 更接近真实团队工作。一个 agent 能通过测试，只能说明它完成了某个局部约束；它是否尊重现有架构、有没有扩大改动范围、测试是否足够、是否留下难以维护的接口，才决定这份结果能不能进入主分支。

### 3. X 帖文适合观察方向，不能单独承担规格和计费事实

本轮的 X 内容再次证明一个读法：官方账号的帖子很适合回答“产品在向什么方向调整”，例如 Fable 5 在订阅体系里如何分层；但具体额度、套餐、价格和安全边界，需要回到官方产品页、帮助中心或可复现的 API 文档。

同样，OpenAI 的 [Codex Security 插件上手页](https://openai.com/daybreak/codex-security-plugin/) 说明的是当前操作入口：可以在 Desktop Codex 中添加插件，也可以通过 Codex CLI 对代码目录发起扫描。至于它覆盖哪些漏洞类别、是否适合接入团队 CI，仍然应该以实际插件行为、权限和扫描报告为准，不能只根据社交平台上的宣传语扩大结论。

## 前端 / 服务端 / 客户端工程观察

### 前端：agent 需要可观察的真实页面，而不是只看生成出来的源码

[Chrome 团队在 I/O 2026 的 WebMCP 与 agentic web 说明](https://developer.chrome.com/blog/chrome-at-io26) 把前端的变化说得很清楚：浏览器不只是承载页面，也开始为 agent 提供理解和操作 Web 的能力。对前端团队而言，真正需要补齐的不是“再写一个生成组件的 prompt”，而是把页面的运行时状态暴露出来：DOM、console、network、性能、可访问性、关键业务状态和截图回归，都应该能被工具读取和复核。

这也解释了为什么“代码生成成功”经常不等于“页面交付成功”：agent 可能写出了看起来正确的 JSX，却没有处理真实数据、错误态、移动端布局、焦点顺序或 hydration 边界。前端项目可以把验收拆成三层：源码静态检查、浏览器运行时检查、用户路径回归；高风险页面至少要保留一份可复现的截图和网络证据。

### 服务端：长时 agent 的核心是状态、幂等和审计

[OpenAI 对 Codex 安全运行方式的说明](https://openai.com/index/running-codex-safely/) 将沙箱、审批、网络策略和 agent-native telemetry 放在同一套控制面里：低风险动作可以流畅执行，高风险动作必须显式停下来；同时记录 prompt、审批、工具调用、工具结果和网络策略决定。

这套思路适用于所有服务端 agent，而不只是一款产品。一个能运行数小时、跨多个工具和子任务的 agent，服务端至少要有：

- 可恢复的任务状态，而不是只保留一条最终回复；
- 带幂等键的工具调用和结果投递，避免重试造成重复写入；
- 清晰的权限边界，能回答“谁授权了这次动作”；
- 可检索的事件链，能从结果反查 prompt、工具、网络和人工审批。

如果这些数据不存在，问题发生后只能看到“失败了”，却无法解释它为什么失败、是否已经产生外部副作用、重跑是否安全。

### 客户端：从聊天壳转向 agent 的控制面

桌面端和移动端正在承载越来越多的控制职责：启动任务、查看进度、审批高风险操作、恢复中断会话、展示扫描证据，以及在无障碍模式下完整表达状态。这个方向与 OpenAI 的安全说明一致：审批和沙箱共同定义了 agent 的实际行为边界，而不是由聊天窗口里的自然语言单独决定。

客户端设计上，最容易遗漏的是“中间状态”：任务已启动但尚未有结果、工具调用被拦截、结果生成但尚未投递、连接断开后正在恢复、恢复后是否可能重复执行。对这些状态做明确建模，比再加一个“正在思考”的动画更能提升可用性和信任感。

## 值得跟进的动作

1. 给模型选型表增加容量和恢复维度：记录限流、等待时间、任务成本、失败重试、结果投递和替代模型，而不只记录基准分数。
2. 在现有 agent 评测中加入“可合并性”检查：范围是否收敛、测试是否覆盖、是否遵循仓库约定、是否能被维护者直接 review。
3. 为前端高风险页面建立 `source → runtime → user path` 三段式验收，至少保留 console、network、截图和关键业务状态的证据。
4. 为服务端工具调用补齐幂等键、审计事件和恢复语义；先用“投递失败后重启”“连接中途断开”“审批后重试”三类故障演练验证。
5. 在客户端把任务状态、审批状态、恢复状态和副作用提示做成一等信息，并为屏幕阅读器和纯文本输出保留完整表达路径。
