## 三段故事

木匠铺收到一张修车单。学徒先绕着车看一圈：轮子歪了，车轴松了，少了两颗钉。他拿起小本子写下先修哪里，再去工具架拿锤子和钉子。敲完以后，他不急着交差，而是推着车走一段，看看还会不会晃。

车还是有点偏。学徒又停下来，重新看车轮，发现不是钉子的问题，而是垫片太薄。他去仓库换垫片，再试一次。这样看一回、做一步、再检查一回，直到车能平稳走直，才把修车单盖上完成章。

后来铺子生意多了，师傅怕学徒乱跑，就定了规矩：每件活最多试几轮；贵重工具要师傅点头；每一步都要记账；修不好要早说，不许硬装会修。工坊不是让学徒永远绕圈，而是让他在可控范围里把事情做完。

## 揭晓概念

这个故事讲的是：**Agent Loop 与运行框架**。

学徒看车，是观察当前状态。写下先修哪里，是计划。拿工具做一步，是行动。推车检查，是读取结果。反复几轮直到盖章，是 Agent Loop。师傅定的轮数、工具权限、记账和求助规则，就是 Agent 的运行框架，也常被叫作 harness 或 runtime。

## 准确定义

这一讲有三个概念值得讲透：**Agent Loop**、**运行框架（harness / runtime）**、**停止条件与预算（stopping condition / budget）**。其余像 plan、observe、trace，理解成“循环里的一个动作或一份记录”即可，不必单独展开。

**Agent Loop**，一句话是：系统围绕目标反复执行“观察、计划、行动、读取结果、判断是否继续”的工程结构，而不是某个固定标准。为什么要绕圈，而不是一次答完？因为在真实环境里，你做完一步才知道结果对不对——第一次行动的结果会改变下一步该做什么，硬要一口气想到底就是盲猜。把“想”和“做”拆成多轮，模型才能拿真实反馈纠正自己。举个能直接感知的例子：让 Agent 修一段报错的代码，第 1 轮读报错信息→改一行→重新运行；运行又报出一个新错→第 2 轮再读再改，直到跑通。每一轮都是一次“observe→act→observe”。如果只允许一次（普通聊天就是这样），模型只能凭想象一次改完，改错了也没有第二次机会。要分清边界：Agent Loop 不等于“模型自己反复想”——那是 chain-of-thought，纯内部推理，循环里没有任何一步真去外部世界拿结果；Agent Loop 的关键恰恰是每轮都有一步真的去跑代码、查数据库、调 API。你平时能感知到的“为什么 Agent 比 chatbot 慢”“它怎么会自己发现做错了”，根源都在这里：它在等真实结果回来。这就是故事里学徒“看一回、做一步、再检查一回”的那股劲。

**运行框架**，一句话是：它不是模型本身，而是让模型能作为 Agent 运作的系统层，负责保存状态、执行工具、限制权限、控制成本、记录 trace、决定什么时候让人类确认。为什么需要它？因为模型只会输出文本——哪怕它写出“我要调用某个工具”，那也只是一串字；它自己不会真的去执行，不会记得上一轮发生了什么，不会知道已经花了多少钱，更不会拦住自己。这些全靠外面包一层程序来做：把模型的文本翻译成真实动作，再把真实结果喂回去，顺手在边上立好护栏。一个具体例子：同一个模型，套上不同 harness，行为天差地别——能读写文件、跑命令、连续循环的编码 Agent，和只能一问一答的网页聊天框，背后可以是同一个模型，差别几乎全在 harness。再具体到数字：“最多 10 轮”“单次工具调用超时 30 秒”“写文件前要人确认”，这些规则模型一条都管不了，全是 harness 设的。边界上要分清：harness 不是 prompt（prompt 是说给模型听的话，harness 是包住模型的程序），也不是某个框架花哨功能的总和。你能直接感知的现象——“为什么换个壳、同一个模型突然变强或变弱”“为什么 Agent 跑到一半会停下来问你要不要继续”——后者就是 harness 在踩刹车。这正是师傅定的那套规矩：工具权限、记账、求助，都长在框架里，不在学徒脑子里。

**停止条件与预算**，一句话是：决定循环何时结束的规则——可能是任务达成（盖章），可能是撞到轮数或成本上限（budget），也可能是判定修不好、该求助。为什么必须有？因为模型不一定知道“够了”：没有停止条件，一个卡住的 Agent 会一直绕圈，反复试同一个无效动作，把时间和成本烧光。budget 是兜底——就算判断不出成功还是失败，到了上限也强制停。来算一笔账：假设每轮工具调用花 ¥0.5、平均 3 秒，设上限 20 轮，那么最坏情况也就 ¥10、约 1 分钟封顶，这就是 budget 给你的可预测边界；没有它，一个陷入死循环的 Agent 半夜能替你烧掉成百上千轮。边界上最容易被忽略的是：停止条件不只是“成功了就停”，更难也更重要的是“失败了也要停下来、并说清楚为什么”——对应故事里那句“修不好要早说，不许硬装会修”。你能感知的现象：Agent 有时跑到一半说“我尝试了若干次仍未解决”然后主动停下，那不是它认怂，而是停止条件在保护你不被无限消耗。

把三者连起来：Agent Loop 提供“反复试”的能力，停止条件与预算决定“试到哪儿为止”，运行框架则把这一切管住、记下、必要时交还给人。没有这些边界，Agent 很容易从“自动帮忙”变成“自动闯祸”。

## 历史过程

早期 AI 系统也有规划和行动，只是多数运行在规则明确的封闭环境里。大语言模型出现后，模型能用自然语言解释目标、拆任务、选择工具，于是“语言模型 + 工具 + 循环”成了新的工程路线。

2022 年的 ReAct 论文把 reasoning 和 acting 交错起来：模型一边形成推理轨迹，一边采取动作并读取外部反馈。2024 年后，Agent 工程开始从“写一个循环”走向“给循环加护栏”：Anthropic 区分了 workflow 和 agent，提醒开发者优先选择简单、可组合、可测试的结构；OpenAI Agents SDK 这类工具也把轮次（turns）、工具（tools）、任务交接（handoffs）、护栏（guardrails）、会话（sessions）和轨迹记录（tracing）做成现成的工程模块。

到 2025-2026 年，前沿实践更强调 harness 或 scaffold（脚手架）：它不是模型本身，而是让模型能作为 Agent 运作的系统层，负责输入处理、工具编排、状态、审批和观测。换句话说，今天评价一个 Agent，不能只问“模型聪不聪明”，还要问“循环怎么跑、工具怎么管、失败怎么停”。

这段历史说明：Agent 不是突然出现的新魔法，而是搜索、规划、工具调用、软件运行时和评测系统合在一起后的新形态。

## 常见误解

第一，Agent Loop 不是越长越好。循环越长，成本、延迟和错误累积越明显，必须有预算和停止条件。

第二，ReAct 不是让模型把所有想法都暴露给用户。它的核心是“推理和行动交错”，实际产品里还要区分内部轨迹、审计日志和用户可见解释。

第三，运行框架不是装饰层。真正决定 Agent 是否可靠的，往往是工具权限、状态管理、失败恢复和人类确认。

## 小练习

给“帮我整理一篇长文并发布草稿”设计一个最小循环：

1. 每一轮要观察什么？
2. 能调用哪些工具？
3. 哪些动作必须人工确认？
4. 最多循环几轮？
5. 什么情况要停止并报告失败？
