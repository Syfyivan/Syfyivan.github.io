## AI 观察

### 1. agent 的竞争单位，正在从“回答得像不像”变成“任务能不能跑完”

OpenAI 在 6 月的公开研究中把 Codex 使用描述为更长的委托任务：截至 2026 年 5 月，超过 70% 的用户曾让它完成预计人工需要一个多小时的工作；非开发者用户也在快速增加。Anthropic 对 Claude Code 的回顾则把重点放在终端、代码库上下文和工具调用的组合上。

这两类材料不能证明某个模型在今天一定更强，却共同指向一个工程变化：模型能力只是 agent 的一个环节，真正决定交付质量的是任务拆解、上下文装载、工具权限、失败恢复和最终验证。把“生成了一份补丁”当成“任务完成”，会漏掉最昂贵的后半程。

### 2. 长任务越有价值，审计和中止就越不能缺席

OpenAI 的 Codex 安全说明把边界、人工批准、受控环境和遥测放在同一套部署叙事里。对使用者而言，最值得借鉴的不是某个厂商的具体实现，而是把 agent 的状态拆开：计划、执行、产物、验证、外部副作用和最终批准不应共用一个 `success`。

尤其是云端或后台运行的长任务，用户可能只在数小时后看到结果。此时必须能回答：它读过什么、改过什么、运行过哪些命令、哪些动作需要批准、验证是否真的通过、发生超时后是否可能重试两次。没有这些记录，所谓“自动化”只是把风险从交互界面藏到了后台。

### 3. “没有当天热点”也是一个可交付结论

今天的飞书窗口没有日报，X 检索页也没有稳定展开可复核单帖。对晨读来说，这不是必须用传闻填满版面的缺口，而是一个关于信息质量的观察：搜索入口证明检索发生过，不证明某位作者在当天说过某句话；群名和关键词命中也不证明日报已经发布。

因此今天的主题从“追一条热点”转向“把事实、线索和推论分层”。这种写法慢一点，却更适合技术判断：读者可以知道哪些内容可以直接行动，哪些需要继续观察，哪些只是工程上的合理推论。

## 前端 / 服务端 / 客户端工程观察

### 前端：让长任务的状态成为界面的一等公民

AI agent 的前端不应只有一个旋转图标和一句“处理中”。至少要把排队、规划、等待用户批准、工具执行、生成产物、验证中、失败可重试和需要人工接管区分开。对于多小时任务，还要展示最后同步时间、当前执行阶段、最近一次可审计事件和取消是否立即生效。

React 在 2026 年 2 月宣布 React、React Native 和 JSX 等项目转入由 Linux Foundation 承载的 React Foundation，技术治理也单独讨论。这个变化的直接价值不在于替某个框架下结论，而在于提醒前端团队：基础设施的所有权、技术治理、发布节奏和应用层使用体验是不同层次。做 agent UI 时，也应把“界面显示的状态”和“后端真正承诺的状态”分开建模。

### 服务端：把 agent loop 变成可恢复、可追责的状态机

服务端至少需要区分 `task_id`、`attempt_id`、`context_version`、`tool_call_id`、`approval_id`、`artifact_id` 与 `verification_id`。同一任务被重试时，不能因为多了一次网络超时就重复发送邮件、重复创建资源或重复写入生产数据。

一个可落地的最小链路可以是：`planned → running → awaiting_approval → executing → verifying → completed`；异常进入 `failed`、`cancelled` 或 `unknown`，而不是一律回到 `running`。对于“执行成功但回执丢失”，应保留对账状态和幂等键，让系统能查询事实后再决定是否补偿。

### 客户端：跨端能力要共享事实，不要共享错觉

Apple 的 Xcode 26.3 说明把 Claude Agent、Codex 等 agent 直接放进开发工具，并强调 agent 可以理解项目、调用内置工具、构建和运行测试。Android 近期则在推进开发者验证、有限分发账号和高级安装流程，时间线已经进入 2026 年 8 月的全球发布阶段。

两件事看似一个讲 AI、一个讲分发安全，实际都在提醒客户端团队：能力进入用户设备后，权限、状态和发布策略必须可见。桌面 IDE 里“测试通过”不等于 App 已经发布；Android 的“可以侧载”也不等于“已完成开发者验证”。客户端应明确区分本地构建、测试包、签名包、商店提交、分发可用和线上行为。

### 共同观察：证据链比工具品牌更稳定

前端负责把状态显示清楚，服务端负责把状态记录清楚，客户端负责把状态同步并在边界处拦截。无论使用 Codex、Claude Code 还是其他 agent，最终都应能从一条任务记录追溯到：输入上下文、模型与工具配置、变更产物、验证命令、人工批准、发布动作和线上结果。

这也解释了为什么今天不需要硬凑 X 热点。真正值得带回团队的不是“大家都在讨论哪个模型”，而是下一次讨论模型时，能不能拿出同一套可比较的任务、权限、验证和回滚证据。

## 值得跟进的动作

1. 给一个真实的 agent 长任务补齐状态字段：任务阶段、最后同步时间、当前工具调用、审批状态、产物链接、验证结果和取消结果。
2. 做一次故障演练：在工具调用超时、客户端重启、网络恢复和回执丢失四种情况下，确认任务是否会重复产生外部副作用。
3. 对前端、服务端、客户端分别写出“完成”的定义：页面显示完成、服务端状态完成、测试通过、签名包生成、商店可见和线上生效必须分开。
4. 把 X 观察转成可追溯队列：保留原帖 URL、作者、发布时间、抓取时间和原文快照；没有这些字段的搜索摘要只作为待核验线索。
5. 继续观察 Android 2026 年 8 月开发者验证相关变化，提前检查应用注册、有限分发账号和高级安装流程是否影响现有测试与交付链路。
6. 如果团队要比较 Codex 与 Claude Code，固定同一组仓库、权限、上下文、测试和回滚条件，不用一次主观体验替代可重复评估。
