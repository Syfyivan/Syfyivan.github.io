> 承上：上一章阿戍守住了名册和钥匙。这一章，老门卫要把“自己人能动什么”的规矩钉死——这事第五讲提过头，到了守城这儿更是性命攸关。

老门卫解下腰间一串岗位牌，一块块分派。“守东门的，只给东门的钥匙，别的门一概碰不着。盘查的，只能看、不能拿。”有人嫌麻烦：“都是自己人，给我一把万能钥匙多省事。”老门卫瞪他:“万能钥匙一旦被人骗去、被人夺去，整座城就没了——给的权越大，丢的时候越惨。”

他又立了三条:“**动大事得请示**——开城门、动府库这种，必须主将点头，单凭一道命令不算数。**拿不准的先去演武场试**——新阵法、没把握的动作，先在围墙里头演一遍，别拿真城门冒险。**坏了要能退**——万一搞砸了，得能退回到出事前的样子，别一锤子砸死。”

## 概念揭晓

老门卫这套，是把第五讲 05.5 的工具安全，放到“安全治理”的高度再钉一遍——因为注入（09.1）一旦得手，能造成多大破坏，全看这道防线。

“各岗只配该配的钥匙”，是**最小权限（least privilege）**：每个 Agent / 工具只拿完成任务所必需的最小权限，绝不发万能钥匙。

“动大事得请示”，是**审批 / 人类在环**：高风险、不可逆的操作执行前必须有人确认。

“拿不准的先去演武场试”，是**沙箱（sandbox）**：在隔离环境里先跑、先验证，不直接碰生产。

“坏了要能退”，是**回滚（rollback）**：保留可恢复的良好状态，出事能退回去（呼应第七讲 07.5）。

## 本章目录

- 为什么权限是注入的“最后一道闸”。
- 最小权限：把破坏面压到最小。
- 审批：把不可逆动作交给人。
- 沙箱与回滚：让试错和失误可承受。
- 小练习：给一个 Agent 设权限闸。

## 权限是注入的最后一道闸

09.1 说过：注入很难被彻底堵死，模型总可能被诱导“想做坏事”。这时真正兜底的，是**它有没有权限把坏事做成**。

- 被注入要它“删库”，但它根本没有删除权限 → 坏事做不成。
- 被诱导去转账，但转账要人工审批 → 卡在人这一关。

所以权限设计不是“锦上添花”，而是安全的**最后一道闸**：假设上游防线都可能被突破，靠最小权限和审批把破坏面压到可承受。这种“假设会被攻破、层层设防”的思路，叫纵深防御。

## 最小权限：压到最小

落地几条：

- 按任务、按角色拆权限，别给一个 Agent “通吃”的权。
- 只读和写入分开（第五讲）：读的放宽、写的从严。
- 权限可按需授予、可吊销、可限时。
- 定期审视：有没有谁攒了一身用不到的权限（权限蔓延）。

一句话：一个 Agent 能造成的最大破坏，等于它手里权限的上限。把上限压低，事故的天花板就低。

## 审批：不可逆动作交给人

不是所有动作都该让 Agent 自动完成。要区分：

- **可逆、低风险**：读数据、生成草稿——可自动。
- **不可逆、高风险**：删数据、转账、对外发布、批量操作——执行前要人确认。

审批的价值，是在“自动化的效率”和“不可逆的风险”之间放一个人。哪些动作要审批，应该按“出错的代价”来定，而不是图省事全自动。

## 沙箱与回滚：让失误可承受

再严的防线也挡不住所有失误，所以要让“失误的代价”可承受：

- **沙箱**：不确定的操作先在隔离环境跑，验证没问题再上生产；生产环境的破坏被挡在外面。比如让 Agent 执行自己生成的代码，就把它放进一个没有网络访问、只能读写临时目录、碰不到生产数据库的容器里跑——就算这段代码被注入污染、想去删生产数据或外传文件，也够不着真正的系统。沙箱这样设计，本质就是把“试错的代价”提前框死在一个赔得起的范围里。
- **回滚**：用版本控制、备份、可恢复的状态，让“退回出事前”随时可行。

有了这两样，你才敢放手让 Agent 多做事——因为就算它搞砸，也能收场。这把第七讲的“回滚”和这一讲的安全连成了一条线。

## 常见误区

第一，光想着“怎么防住注入”，却给 Agent 配了大权限——防线一破就是大事故。

第二，图省事发万能钥匙、长期大权限 key。方便一时，风险常在。

第三，高风险不可逆操作也全自动，没有审批、没有回滚，出事无法收场。

## 小练习

一个运维 Agent，能：查看日志、重启服务、删除数据库、修改线上配置。

1. 这四样各属于什么风险等级？哪些该只读、哪些该写入受限？
2. 哪些必须人工审批？哪些该先在沙箱验证？
3. 假设它被间接注入诱导去“删库”，你的哪道闸能兜住？
