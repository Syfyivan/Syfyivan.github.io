> 承上：上一章阿行第一次自己办成了事。这一章，老向导泼冷水：照着界面办事，栽跟头的花样多得很。

老向导掏出一张“常栽清单”，一条条讲给阿行。

“一、**路标挪了位**。你记着‘提交’的铃在右上角，可这家驿站重新摆过台子，铃挪到了左下——你照老位置一按，按了个空，或按错了别的。二、**半路杀出拦路的**。你正要填表，忽然蹦出来个收过路费的、发广告的，把你要点的东西挡住了，你一头撞上去。三、**看不见的暗格**。台面上看着办完了，可有个抽屉里的章还没盖、有个状态没刷新，你以为成了，其实没成。四、**有些门压根没把手**。设计这门的人没给摸路的人留记号，你瞎子摸象，怎么都找不到该按哪。”

## 概念揭晓

老向导这张清单，是操作图形界面的 Agent（UI Agent / Computer Use）最常见的失败模式。

“路标挪了位”，是**坐标漂移 / 界面变化**：UI 一改版、分辨率一变、元素一挪位，按记忆点的坐标就全错。界面是会变的，硬记坐标极其脆弱。

“半路杀出拦路的”，是**弹窗与意外干扰**：广告、cookie 同意框、登录弹窗、权限请求，会突然挡住目标元素，把 Agent 带偏。

“看不见的暗格”，是**隐藏状态 / 异步未完成**：界面看着“好了”，但后台还没处理完、某个状态没刷新、某步其实没成功——Agent 误以为完成。

“门没把手”，是**可访问性（accessibility）差**：界面对程序不友好（没有可读的元素标签、纯图片按钮、动态渲染），Agent 难以稳定识别和定位。

## 为什么界面操作这么脆

界面是给“人”设计的，不是给“机器照坐标点”设计的。人有强大的容错：弹窗挡住了会随手关掉，按钮挪了位一眼又找到。Agent 没有这种天然的鲁棒，于是：

- 界面一点点变化，它就可能全乱。
- 它对“意外情况”（弹窗、报错、加载慢）的处理远不如人灵活。

这就是为什么 Computer Use 看 demo 很惊艳、上真实复杂场景却频频翻车——和第八讲 08.1“demo 不算评测”一脉相承。

## 四种典型失败

- **坐标漂移**：依赖绝对坐标或固定布局，一改版就废。一个具体例子：同一个页面，换个分辨率、或把系统缩放从 100% 调到 125%，按钮的像素坐标就全变了，照老坐标去点必然落空。更稳的是靠“理解界面语义”定位（找“那个写着提交的按钮”），而不是死记位置。
- **弹窗干扰**：要能识别并处理意外弹窗（关闭、同意、跳过），否则会卡死或误点。
- **隐藏状态**：别只看“界面显示完成”，要等异步真完成、要校验最终状态（这单真的提交了吗）。
- **可访问性差**：纯图片按钮、无标签元素让识别变难。界面若能提供良好的可访问性信息，Agent 会稳得多。

## 怎么让 UI Agent 更稳

- **靠语义而非坐标**：尽量基于“元素是什么”来定位，而不是“在哪个像素”。
- **预案处理意外**：把常见弹窗、登录、加载等待写进流程。
- **每步校验**：动作后确认界面真的变成了预期状态，再走下一步。
- **小步 + 可回退**：一步步来，错了能退（10.4 的状态恢复）。
- **能 API 就别点界面**：有接口的优先用接口，界面操作留给“没有别的办法”的场景——它更脆、更慢、更贵。

## 失败要可观测、可恢复

UI Agent 几乎一定会遇到没见过的界面和意外。所以不是追求“永不出错”，而是让出错可被发现、可被收拾（第八、九讲）：

- 每一步截图留痕，出错能回放定位（第八讲 trace）。
- 关键步骤设确认和校验，别让错误悄悄累积。
- 高风险动作人工把关、可回滚（第九讲）。

把“它会失败”当成前提去设计，比假装“它不会失败”要安全得多。

## 常见误区

第一，照 demo 里的顺滑想象真实场景。真实界面有弹窗、改版、慢加载，脆得多。

第二，靠死记坐标。界面一变就全错，要靠语义定位。

第三，只看“界面显示成功”就当完成，不校验真实最终状态。

## 小练习

你让 Agent 在某购物网站“下单并付款”。

1. 这条流程里，坐标漂移/弹窗/隐藏状态各可能在哪一步咬你？
2. 哪一步必须“校验真实状态”而不能只看界面提示？
3. 如果能用网站的 API，你还会选界面操作吗？为什么？
