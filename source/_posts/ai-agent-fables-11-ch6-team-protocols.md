> 承上：上一章阿筹学会了算多 Agent 的账。这一章，老把头把压箱底的东西交给他——一支队能不能长久靠谱，靠的不是某次的好手气，是一套人人都守的规矩。

老把头递给阿筹一本薄册子，封面写着“队规”。

“一支队，”他说，“**活儿怎么切**得有数——切到谁都能照着干、又能各自验收的份上，不能切得稀碎、也不能一坨甩给一个人。**各组干到哪了，得有个对法**——别等到合拢那天才发现你往东他往西，要时时对暗号、同步进度。**撞车了听谁的**——两组结论打架、抢同一处地盘，得有说法，不能现吵。**最后交活，得拿出凭据**——不是嘴上说‘干完了’，是拿出验收过的、对得上要求的成果。”

“记住，”老把头合上册子，“英雄靠手气，队伍靠规矩。”

## 概念揭晓

老把头这本队规，是把多 Agent 从“能跑”做到“长久靠谱”的**团队工程协议**——也是这一讲从技术模式回到工程纪律的收束。

“活儿怎么切”，是**任务切分（decomposition）**：把大任务拆成边界清晰、可独立完成、可独立验收的子任务（呼应第七讲 SDD 的 tasks、11.1 的分工）。切得好，分工才顺。

“各组干到哪了得有个对法”，是**状态同步**：Agent 之间要共享必要的进度和状态，避免“各跑各的、最后对不上”。注意要和 11.3 的隔离平衡——同步“必要的进度”，而非“全部上下文”。

“撞车了听谁的”，是**冲突处理**：当 Agent 结论矛盾、争抢同一资源时，要有裁决机制（投票、协调者拍板、或升级给人）。

“交活要拿出凭据”，是**交付证据（verifiable deliverable）**：交付的不是“我说做完了”，而是经过验证、对得上要求的成果（第七讲可验证完成、第八讲评测、11.4 对抗验证，在这里汇合）。

## 为什么多 Agent 需要团队规矩

一群很能干的 Agent 凑在一起，未必比一个 Agent 强——如果它们各跑各的、互相覆盖、结论打架、没人能说清谁对，结果可能是“更贵的混乱”。

把它和人的团队类比就很清楚:一群高手，没有清晰的分工、对齐和交付标准，照样一盘散沙。多 Agent 工程的核心，正是把“一群 Agent”变成“一支队”——靠协议，而不是靠每个 Agent 单独发挥。这也是“AI 工程”区别于“调一个模型”的地方。

## 切分、同步、冲突、交付

- **切分**:子任务边界清晰、可独立验收。切分质量直接决定整队效率（11.1、11.3）。
- **同步**:共享必要的进度/状态，但守住隔离（11.3），别退回“共享一切”。
- **冲突**:预先定好“矛盾了怎么裁”——多数共识（11.4）、协调者拍板、或升级给人（第十讲信任边界）。
- **交付**:每个子任务和整体，都要有“算完成”的可验证标准和证据（第七、八讲）。

这四件事，就是把零散的 Agent 协作，钉成一套可重复、可审计的工程流程。

## 多 Agent 工程 = 把前十讲拢到一起

走到这里，会发现多 Agent 工程几乎用上了前面每一讲:

- 每个 Agent 是一个会用工具、会循环的个体（五、六讲）。
- 它们靠上下文工程和隔离运转（三、四、十一讲）。
- 产出靠评测和对抗验证守质量（八、十一讲）。
- 整体靠安全边界和最小权限兜底（九讲）。
- 对人靠可见、可控、可交付（七、十讲）。

所谓“AI 工程”，就是把这些拢到一起，让一群 Agent 可靠地完成一个工程。它是这门课前十讲的汇流。

## 简单优先:别为分工而分工

最后回到第 11.1 的告诫，也是 Anthropic、OpenAI 都反复强调的:**先用最简单的方案，能不拆就不拆。**

多 Agent 是强力但昂贵、复杂、难调的工具。只有当任务真的大到、杂到单 Agent 扛不动，且拆分收益明显大于协调成本时，才上多 Agent。把它当成“需要时才请的施工大队”，而不是“显得专业的默认配置”。
