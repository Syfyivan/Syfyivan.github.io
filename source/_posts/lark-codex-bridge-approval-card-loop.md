今天碰到一个很典型的桥接器事故：我在飞书里点了“同意执行”，界面上看起来没有效果，随后话题里还开始不断出现新的审批卡。直觉上像是按钮没被收到，但真正查下来，问题并不在按钮。

按钮点击已经生效了。审批记录里已经写入了决策时间，状态也从 `pending` 变成了 `running`。真正出错的是后面的两段逻辑：

1. 桥接器在审批通过后，会先发一条“已同意执行，开始处理”的状态通知；
2. 这条通知发送失败后，异常没有被隔离，导致真正的执行链被中断；
3. 同时，全局搜索/轮询又把桥接器自己发出的审批卡扫了回来，当成新的用户请求；
4. 新请求又生成新审批卡，于是出现了“审批卡套审批卡”的自循环。

这篇复盘不记录内部群、用户 ID 或具体业务内容，只记录这个问题对本地 AI Agent 桥接器有用的工程教训。

## 现象：点了同意，但像没点

从用户视角看，问题有三个信号：

- 点击“同意执行”后，飞书里没有出现预期的处理进展；
- 审批记录却显示这个请求已经进入 `running`；
- 话题里不断出现新的审批卡，每一张卡都引用上一张卡的内容。

这类问题很容易被误判成“飞书卡片按钮回调没触发”。但如果只盯着按钮回调，就会错过真正的因果链。

更准确的判断是：**按钮事件到了，状态也更新了，但后续通知失败把执行流程打断了；随后轮询机制又把自己发出的卡片误识别成用户消息。**

## 根因一：通知不该成为审批事务的一部分

原来的审批处理大概是这个形状：

```text
更新审批状态为 running
发送“已同意执行，开始处理”
开始执行真实任务
发送最终结果
```

这里最危险的是第二步。状态通知只是用户体验层面的反馈，它失败了不应该阻止真实任务继续执行。但之前实现里通知是一个普通 `await`，如果飞书接口因为消息格式、权限或目标会话约束返回错误，整个审批流程就会抛异常。

这次就是这样：审批状态已经落盘，但通知发送失败，真实执行没有继续往下走。于是用户看到的是“点击没反应”，系统内部看到的是“请求已经 running”。

修复方式是把通知从事务链里拆出去：

```text
更新审批状态为 running
best-effort 发送状态通知，失败只记日志
开始执行真实任务
best-effort 发送最终状态，失败只记日志
```

也就是说，通知可以失败，但不能让审批流停在半路。对这类自动化系统来说，状态通知是旁路，状态机推进才是主路径。

## 根因二：桥接器读回了自己发出的卡片

第二个问题更隐蔽。桥接器为了防止实时事件漏掉，会有轮询和全局搜索兜底。这个设计本身是合理的：如果 WebSocket 或事件订阅短暂抖动，轮询还能把群里的有效请求补回来。

但这次配置里允许搜索 `app` sender，也就是允许处理由应用账号发出的消息。这个能力是为了支持“某个应用帮人润色后转发请求”的场景。问题在于，桥接器自己发出的审批卡也是 `app` sender。

审批卡里面又包含了原始请求摘要、风险类型、请求 ID，以及“同意执行 / 取消执行”的提示。更糟的是，卡片引用的原始请求里本来就有 `review`、`MR`、`帮忙看下` 这类触发词。于是搜索兜底路径看到这张卡时，会觉得它也是一条新的可处理请求。

结果就是：

```text
用户请求 -> 审批卡 A
轮询读到审批卡 A -> 审批卡 B
轮询读到审批卡 B -> 审批卡 C
...
```

这个问题不是“轮询错了”，而是轮询缺少一个更基本的边界：**桥接器自己生成的控制消息不能再进入业务处理入口。**

## 修复：给控制面消息建隔离层

这次修复加了一个明确的审批消息过滤策略，专门识别几类不应该进入业务处理的消息：

- 已删除或已撤回的消息；
- 自己发出的 `interactive` 卡片；
- 标题和内容符合审批卡结构的消息；
- 包含“请求 ID”“同意执行 / 取消执行”“同意发送 / 取消发送”等控制面语义的卡片文本。

这个策略接到了三个入口：

- 实时消息入口；
- 普通群消息轮询入口；
- 全局搜索候选过滤入口。

按钮点击事件本身不走这条过滤，所以真正的 `card.action.trigger` 仍然可以被处理。被拦掉的是“卡片作为一条普通消息再次被处理”的路径。

同时，sender policy 也补了一条规则：当前 bot 的 `app_id` 和 `open_id` 都要视为 self sender。之前只按 open_id 识别自己，在应用消息场景里不够。

## 恢复动作

现场恢复分了几步：

1. 停掉桥接器，防止继续发卡；
2. 撤回已经生成的嵌套审批卡；
3. 把事故留下的嵌套审批记录标记为 `cancelled`，避免后续文本命令误触发；
4. 修复过滤策略和通知失败处理；
5. 补回归测试；
6. 重启服务，检查健康端点、队列状态和原话题里是否还有未撤回卡片。

这里还有一个额外的小坑：恢复服务时发现 LaunchAgent 仍指向旧的根目录入口，而当前包入口已经移动到子包目录。于是补了一个根目录 wrapper，让旧的 LaunchAgent 路径和新的包结构兼容。这个不属于审批卡事故的根因，但属于“恢复路径必须可重复”的一部分。

## 为什么之前没发现

这件事不是今天才坏，而是今天才凑齐了触发条件。它需要几个条件同时成立：

- 审批卡功能已经存在；
- 全局搜索/轮询兜底开启；
- 搜索 sender 类型允许 `app`；
- 桥接器自己发出的卡片能被搜索结果读回来；
- 卡片内容里包含足够像用户请求的触发词；
- 审批通过后的状态通知刚好失败；
- 通知失败又没有被隔离。

之前的验证主要覆盖了这些路径：

- 服务能启动；
- 实时 @ 消息能被处理；
- 普通审批卡能发出；
- 按钮回调能到达；
- 健康检查和基础测试通过。

这些都是“正向路径”。它们能证明系统可用，但不能证明系统不会处理自己生成的控制消息，也不能证明通知失败不会影响状态机。

更具体地说，当时漏了三类测试：

1. **自消息回收测试**：把桥接器自己发出的卡片塞回轮询/搜索结果，看它会不会被当成新请求。
2. **通知失败测试**：模拟飞书发送状态通知失败，检查审批流是否还能继续执行。
3. **跨入口一致性测试**：实时事件、普通轮询、全局搜索三条入口应该共享同一套控制面过滤策略，而不是各自判断。

这也是很多 Agent 桥接器容易踩的坑：只测“用户输入 -> 模型执行 -> 回复输出”，没有测“系统自己的输出会不会被系统再次读回”。一旦系统同时有事件订阅、搜索兜底、审批卡、自动回复，这个问题就会从理论风险变成真实事故。

## 这次留下的原则

这次修完后，我给自己留了几个更明确的规则。

第一，控制面消息和业务消息必须分层。审批卡、进度卡、系统提示、trace 标记都属于控制面，不能靠“看起来不像请求”来避免被处理。

第二，通知失败不能阻断状态机。用户可见通知可以失败，执行状态不能因此卡在半路。

第三，兜底机制要有负边界。轮询和全局搜索是为了补漏，不是为了把所有可见消息都重新解释一遍。

第四，健康检查不等于语义正确。`/healthz` 只能证明进程活着、端口可用、依赖大体正常；它证明不了“不会自循环”。

第五，恢复路径也要被验证。服务能不能重启、LaunchAgent 指向哪里、旧入口是否还存在，这些都应该算在事故恢复完成标准里。

## 最后

这次事故表面上是“飞书按钮没反应”，实际是一个很典型的 Agent 系统边界问题：系统既会读消息，又会发消息；既有实时事件，又有轮询补偿；既有用户请求，又有控制卡片。只要没有把这些消息类型分清楚，系统就可能把自己的控制面输出当成新的业务输入。

今天的修复不只是让这次卡片不再循环，而是补上了一条更重要的边界：**Agent 可以观察世界，但不能无条件地相信自己刚刚写进世界的东西。**
