系统上线后，最怕的不是报错，而是报错了不知道从哪儿查。

可观测性这部分，我会把它当成服务端的“现场记录”。请求从哪里进来，在哪个服务慢了，哪次 RPC 失败了，哪条消息堆住了，都得留下线索。

## 日志要能串起来

日志不是越多越好。能派上用场的日志，至少能回答：

- 这是哪个请求；
- 影响哪个用户或业务对象；
- 失败在哪个依赖；
- 花了多久；
- 错误是什么。

我会尽量打结构化日志，比如 JSON。字段不用一开始很多，但 request_id、trace_id、user_id、业务 id、error、latency 这些最好有。

一个常见问题是每一层都打 error，最后同一个错误刷出十几行。更好的做法是：底层包装错误，入口边界统一记录。

## 指标看趋势

日志适合查单个问题，指标适合看整体有没有变坏。

服务端至少要看：

- QPS；
- 错误率；
- P95/P99 延迟；
- 数据库连接池；
- Redis 命中率；
- RPC 下游错误率；
- MQ 堆积。

平均延迟容易骗人。一次慢请求对平均值影响不大，但用户看到的是卡住的那一次，所以 P95、P99 更有参考价值。

## Trace 看一条请求走哪儿了

微服务一多，光靠日志搜 request id 会很累。Trace 能把一次请求的路径串起来：

```text
gateway
  -> task-service
    -> user-service
    -> db query
    -> redis
```

慢在哪里，一眼能看个大概。尤其是“用户说偶尔很慢”的问题，trace 比纯日志好用很多。

## 告警要能让人行动

告警太多，最后大家都会忽略。

我更愿意按用户影响来设：

- 下单接口 5xx 超过阈值；
- P95 延迟持续升高；
- MQ 堆积超过消费能力；
- 数据库连接池耗尽；
- 缓存命中率突然下降。

“CPU 高”不是没用，但它通常只是线索，不一定直接代表用户受影响。

## 一个练习

给任务系统补观测：

- 入口生成 request id；
- 日志统一 JSON；
- handler 记录接口、状态码、耗时；
- RPC 调用记录下游和耗时；
- MQ 消费记录 message id；
- metrics 记录 QPS、错误率、P95；
- trace id 从 HTTP 传到 RPC，再传到 MQ。

然后故意造几个问题：数据库慢查询、Redis 挂掉、MQ 消费失败。别追求“永远不坏”，先练到坏了以后几分钟内能找到方向。
