系统上线后一定会出问题。可观测性的目标不是让系统不出错，而是在出错时能尽快回答三个问题：影响了谁，问题在哪里，为什么发生。

单体应用里，一个错误可能还能靠本地日志排查。微服务化之后，请求跨越网关、多个服务、数据库、缓存、MQ 和第三方依赖，如果没有统一的日志、指标和链路追踪，排障会变成猜谜。

## 可观测性在链路里的位置

可观测性应该覆盖整个请求生命周期：

```text
Gateway
  -> API service
  -> RPC service
  -> DB / Redis / MQ
  -> Consumer
  -> Downstream
```

每一层都要留下信号：

- 日志回答发生了什么；
- 指标回答整体是否异常；
- trace 回答一次请求经过哪里；
- 告警告诉人什么时候需要行动。

## 必须掌握的知识点

### 结构化日志

日志不是随手 `fmt.Println`。生产日志应该是结构化的，至少包含：

- timestamp；
- level；
- service；
- request_id；
- trace_id；
- user_id 或核心业务 id；
- error；
- latency；
- upstream/downstream；
- message。

好的日志不是越多越好，而是能检索、能关联、能解释。

错误日志尤其要避免两种问题：

- 每一层都打同一个错误，导致噪声巨大；
- 只打 `failed`，没有任何业务上下文。

推荐做法是底层包装错误，上层在边界处统一记录。

### 指标

指标看整体趋势。常见服务指标包括：

- QPS；
- 错误率；
- 延迟 P50/P90/P95/P99；
- 当前 goroutine 数；
- CPU、内存；
- 数据库连接池；
- Redis 命中率；
- MQ 消费延迟和堆积；
- RPC 下游错误率。

延迟不要只看平均值。平均值会掩盖长尾问题。用户感受到的往往是 P95、P99。

### 链路追踪

Trace 用来串起一次请求。它通常包含：

- trace id：一次完整请求；
- span id：一次子调用；
- parent span：调用关系；
- tags：服务名、接口名、错误、耗时。

当一个请求很慢时，trace 能告诉你时间花在哪里：

```text
gateway 20ms
task-service 600ms
  user-service 80ms
  db query 480ms
  redis 5ms
```

没有 trace，你只能在多个服务日志里手动搜索 request id，效率会低很多。

### 告警

告警不是把所有异常都发出来。好的告警应该满足：

- 代表真实用户影响；
- 有明确阈值；
- 有处理建议；
- 有负责人；
- 能区分紧急程度。

比起“CPU 高于 80%”，更有价值的告警是：

- 下单接口 5xx 超过 2% 持续 5 分钟；
- P95 延迟超过 800ms；
- 支付回调 MQ 堆积超过 10000 条；
- 数据库连接池耗尽；
- 缓存命中率突然下降。

### SLO 思维

SLO 是服务目标，比如：

- 99.9% 请求成功；
- P95 延迟低于 300ms；
- 消息 5 分钟内消费完成。

有了 SLO，就能判断问题是否真的影响服务目标，也能决定是否需要停止发布、扩容或降级。

## 常见反模式

### 只在出错时才想起来加日志

日志和指标应该在开发阶段就设计好。上线后再补，往往已经错过最需要证据的时间。

### 日志里没有业务 id

没有 user id、order id、task id 的日志，很难和真实问题关联。排查时只能靠时间范围和错误文本猜。

### 告警太吵

告警太多会让人麻木。每一条告警都应该能触发明确行动，否则它只是噪声。

## 练习方式

给任务系统补可观测性：

- 每个入口请求生成 request id；
- 日志统一输出 JSON；
- handler 记录接口、状态码、耗时；
- RPC 调用记录下游、错误、耗时；
- MQ 消费记录消息 id 和消费结果；
- 指标记录 QPS、错误率、P95 延迟；
- trace id 贯穿 HTTP、RPC 和 MQ；
- 设计三个告警：错误率、延迟、MQ 堆积。

然后主动制造问题：数据库慢查询、Redis 不可用、MQ 消费失败。看看能不能在 5 分钟内定位根因。
