前面的项目文章解决“我应该怎么讲”。这篇解决另一个问题：面试官不接受第一层答案，继续追问时怎么办。

它不是背诵题库。每组问题都沿同一条推导链展开：

```text
业务不变量
  -> 并发和失败场景
  -> 权威数据源
  -> 事务边界
  -> 跨系统幂等与补偿
  -> 观测和恢复
  -> 所有权边界
```

公开版本使用泛化名称。涉及没有在原项目中完整落地的增强方案，会明确使用“如果重新设计”。

## 一、怎样使用这份手册

不要一次背完。每个项目按四轮训练：

1. 只看问题，用 30 秒回答；
2. 再看回答核心，补齐缺失层次；
3. 让另一个人从“继续追问”里随机选一题；
4. 最后在白纸上画数据、状态和调用链。

如果一个答案只能在看到文章时说出来，就还不算掌握。

## 二、所有项目共用的回答骨架

### Q1：你为什么认为这是一个难项目？

不要回答“技术栈陌生”或“页面很多”。

回答核心：

> 难点来自多个业务不变量同时存在。例如结果以服务端为准、用户资产不能重复、动画和外部权益允许失败、活动又要支持高流量和配置变化。我先把这些不变量拆成状态、事务和异步边界，再选择实现方式。

继续追问：哪个不变量最容易被破坏？失败以后用户看到什么？

### Q2：你做的技术动作和业务结果有什么关系？

回答核心：

```text
技术动作 -> 直接工程效果 -> 业务能力 -> 团队业务结果
```

例如离线快照让高流量页面读稳定，进而支撑活动运行；不能说一个 KV 方案直接创造了千万 UV。

### Q3：如果只能讲一个决策，你讲什么？

选择能同时体现业务理解和技术取舍的决策：

- 抽卡：业务结果和展示动画解耦；
- 进度：实时个人反馈和全站离线聚合拆开；
- 徽章：两种入口统一到领域发放能力；
- 重构：代码边界服从运行和发布边界；
- 压测：隔离证据优先于 QPS；
- MQ：当前活动状态和事件发生时间分开判断。

### Q4：你怎么证明不是 AI 替你做的？

回答核心：

> Agent 扩大了代码检索、候选实现和历史比较范围；我定义业务不变量、审查代码证据、选择方案、设计实验并完成最终验收。最关键的取舍都能说明依据和被拒绝的替代方案。

### Q5：哪些部分不是你做的？

直接说边界，并立刻切回自己的工作：

> 核心抽卡引擎由服务端同事负责，我独立负责活动页前端，并参与接口、异常状态和联调验收。我的个人服务端所有权主要在进度解锁、徽章、具体重构模块、压测隔离和 MQ 治理。

## 三、集卡抽卡项目：十八组连续追问

### Q1：为什么抽卡结果必须以服务端为准？

回答核心：机会扣减、概率、保底、库存和资产都属于服务端权威状态。客户端只展示结果。

继续追问：如果客户端动画失败怎么办？

> 保存服务端结果并降级展示，不重新请求抽卡。

### Q2：为什么单抽和十连使用同一个引擎？

回答核心：它们共享机会、概率、保底、资产和记录语义。十连是一个批次，不是前端循环十次单抽。

继续追问：十连事务包含什么？

> 幂等重放、机会扣减、十次命中、实例与编号、抽卡记录、资产流水和掉落判定。

### Q3：request_id 如何实现幂等？

回答核心：事务开始先按活动、用户和 request_id 查询历史记录，有则重建旧结果；没有才校验活动状态并扣机会。

继续追问：同一个 request_id 一次单抽、一次十连怎么办？

> 不能只返回旧结果，还要校验业务参数一致，否则属于幂等键冲突。

### Q4：为什么活动结束后还允许某些请求？

回答核心：结束后拒绝新写，但相同 request_id 的已提交结果应允许回放，避免用户在边界时刻成功扣机会却拿不到结果。

### Q5：机会为什么不是一个 remaining_count？

回答核心：累计发放、累计消耗加流水能解释机会来源、扣减原因和重放结果。

继续追问：怎么原子扣减？

```sql
UPDATE chance
SET consumed = consumed + :cost
WHERE granted - consumed >= :cost;
```

### Q6：唯一索引、分布式锁和条件更新有什么区别？

- 唯一索引：并发下最终防重复；
- 分布式锁：减少并发进入；
- 条件更新：保证状态只能从预期值迁移。

它们不能互相完全替代。

### Q7：概率为什么分稀有度和同档卡片两层？

回答核心：稳定稀有度分布，新增同档卡只调整档内权重，运营更容易维护和预算。

继续追问：配置如何校验？概率和为固定基数、每档至少一张、权重为正、保底目标存在。

### Q8：十连保底和历史大保底如何同时工作？

回答核心：每一抽先处理历史保底，批次完成后检查是否已有目标稀有度；如果十连保底替换最后一张，还要修正历史保底计数语义。

### Q9：为什么卡片要实例化？

回答核心：赠卡、求卡、编号和流转审计需要知道具体是哪一张。`user + card + count` 不能表达实例所有权。

### Q10：为什么还需要聚合数量？

回答核心：图鉴一次查询多种卡，实时 count 实例成本高。实例是事实源，聚合量是同事务维护的查询加速视图。

### Q11：赠卡为什么创建时就锁卡？

回答核心：分享链接代表一份已经承诺的资产，必须防止同一实例生成多个链接或被用户另行消耗。

继续追问：取消和过期怎么办？把仍锁定的实例恢复为 held。

### Q12：求卡为什么不在创建时锁卡？

回答核心：求卡人并不拥有目标卡，也不知道哪个好友响应。响应时才校验并转移对方实例。

### Q13：两个用户同时领取同一赠卡怎么办？

回答核心：实例转移、双方流水和 transfer 状态在事务中处理；最后以 `available -> completed` 条件更新竞争，只有一个成功。

### Q14：分享 token 为什么只存哈希？

回答核心：原 token 是领取凭证，数据库或日志泄漏后不能让别人直接领取。

### Q15：集齐兑换为什么是两阶段？

回答核心：本地卡片在数据库，抽奖机会属于外部系统。Phase A 占用卡片并写 pending；Phase B 用稳定幂等键发机会，成功 completed，失败可重试。

继续追问：配置改变怎么办？使用 Phase A 保存的承诺快照，不重读当前配置。

### Q16：发机会成功、本地 completed 写失败怎么办？

回答核心：重试沿用相同下游幂等键，下游不重复发；本地补写完成状态。

### Q17：随机掉落为什么在抽卡提交后发奖？

回答核心：外部权益失败不能回滚已经确定的卡片，且外部 RPC 不应延长本地事务锁时间。

继续追问：用户不重放请求怎么办？服务端扫描可恢复状态主动补偿。

### Q18：编号计数器为什么允许空洞？

回答核心：展示编号要求不重复、单调，不要求财务式连续。预留号段后业务回滚可能留下空洞，换来并发性能和简单事务边界。

## 四、进度解锁项目：十二组连续追问

### Q1：为什么不用实时 SUM？

回答核心：页面 UV 会放大全量聚合成本，总进度允许短暂延迟，因此离线聚合写快照，C 端常数时间读取。

### Q2：用户刚做完任务为什么看不到总进度立即变化？

回答核心：区分个人实时反馈和全站最终一致进度。接口立即返回本次个人得分，全站进度按刷新周期更新。

### Q3：为什么快照使用 max？

回答核心：产品定义解锁后不回退，max 防止旧任务晚完成覆盖新进度。

继续追问：异常高值怎么办？写入前做范围、增幅和来源校验；max 不解决输入可信度。

### Q4：如果违规内容撤销需要减分呢？

回答核心：不能继续使用单调高水位，需要版本化聚合、可重算明细或正负流水。

### Q5：保底积分为什么不是 delta？

回答核心：它是总分公式项，每轮目标值重算；delta 会随任务重跑反复累加。

### Q6：离线任务并发怎么办？

回答核心：使用原子 max、CAS 或带 owner token 的短锁。简单 GET+SET 不是原子操作。

### Q7：锁过期后旧 worker 释放新锁怎么办？

回答核心：锁 value 保存 owner token，释放时比较 token，只删除自己的锁。

### Q8：快照不存在返回 0 还是报错？

纯展示可以返回 0 并告警；涉及真实权益时不能把缺失解释成无资格，应查权威状态或暂停操作。

### Q9：不同任务积分单位不一致怎么办？

回答核心：在进入目标进度和阈值判断前统一归一化，配置和接口使用业务单位，历史存储细节封装在适配层。

### Q10：随机掉落一次跨多个阈值，中途失败怎么办？

如果重新设计：每个阈值建立独立执行记录 `pending/executing/completed/failed`，不要全部完成后才保存一个集合。

### Q11：为什么多抽只允许有限值？

回答核心：控制请求时长、QA 组合、前端布局和库存预算；运行时仍要再次校验。

### Q12：这套能力怎样复用？

回答核心：阶段、素材、保底、签到、掉落和多抽全部配置化；服务端返回统一阶段和动作模型，不绑定单场文案。

## 五、批量权益发放：十二组连续追问

### Q1：为什么自动和名单发放必须共用领域接口？

回答核心：用户来源不同，但分组、幂等、有效期、失败和下游调用规则相同。

### Q2：为什么有两级拆批？

任务层控制请求体、执行时间和进度；领域层适配下游批量上限和部分失败。

### Q3：分组键是什么？

回答核心：至少包含徽章 ID、展示名和有效期。所有影响下游批量参数的字段都必须一致。

### Q4：活动幂等和全局权益有什么区别？

活动幂等回答“该活动是否发过”；全局权益回答“用户现在是否已有这枚徽章以及何时到期”。

### Q5：预查重失败为什么继续？

回答核心：预查重是性能优化，后面还有领域幂等和下游已有权益；直接丢用户会漏发。

### Q6：有效期如何计算？

```text
candidate = now + valid_days
new_end = max(old_end, candidate)
```

不能 `old_end += valid_days`，否则重复任务不断膨胀。

### Q7：整批超时是否全部失败？

不是。超时只说明调用方没拿到响应。重试前依赖幂等或查询下游最终状态。

### Q8：批量 RPC 整体失败为什么降级单用户？

用于隔离坏用户和缩小失败范围，但要限制并发、超时和触发条件。

### Q9：一行错误为什么不整批失败？

运营批量工具需要可恢复性。正确行继续，错误行返回行号、原值和原因。

### Q10：用户不存在为什么失败后再查？

大多数用户合法，发放前查全部会增加一次大 RPC；只对失败用户补查更经济。

### Q11：下游成功、活动幂等 KV 写失败怎么办？

当前下游已有权益能阻止实体重复，但会增加调用和审计缺口。如果权益价值高，应增加持久化 grant_record 状态机，KV 只做加速。

### Q12：一万用户如何断点恢复？

如果平台化：持久化 batch_id、item 状态和 cursor；批次可分页执行，只重试失败项，避免一个同步请求跑到底。

## 六、多仓重构：十二组连续追问

### Q1：为什么不是整理目录？

回答核心：目标是让编译、部署、发布和故障边界与代码职责一致。

### Q2：为什么公共仓不能放业务 Service？

所有仓都依赖公共仓，业务逻辑会放大升级和发布影响。公共层只保留稳定模型与基础设施。

### Q3：为什么领域仓不能直接 import？

它是独立 RPC 服务，不是 library。跨进程复用必须走协议。

### Q4：为什么保留 v1？

用于结果对比和快速回滚；模块稳定后应尽快删除，避免永久双轨。

### Q5：灰度路由放在哪里？

集中入口或 router，只选择一次版本，避免请求内部一半新、一半旧。

### Q6：读路径怎么比较？

可以双算但只返回主路径，比较字段、排序、空值和错误。

### Q7：写路径为什么不能直接双写？

可能重复产生数据库、消息和权益副作用。应使用测试数据、请求回放或受控影子资源。

### Q8：如何证明行为不变？

比较 API、错误码、DB、缓存、MQ、外部 RPC 和异步后置，不只比较返回 JSON。

### Q9：枚举映射为什么危险？

成功值相同并不代表其他值相同。必须逐枚举断言 duplicate、failed 等状态。

### Q10：为什么不用新建 v2 仓库？

会复制基础设施和发布链路，迁移范围更大。现有领域仓内部模块化更容易渐进切换。

### Q11：什么时候删除 v1？

全量、稳定观察、无差异告警、回滚窗口结束以后；按模块删除，不等所有模块一起。

### Q12：重构效果怎么量化？

看修改仓库数、公共业务依赖、legacy 行数、差异告警、回滚耗时、测试和接入周期；没有数据不编造性能百分比。

## 七、高流量压测：十二组连续追问

### Q1：为什么隔离先于 QPS？

压力数据污染正式表或触发真实发奖，比接口报错更严重。

### Q2：为什么只接受 Header 标记？

入口统一处理并透传 RPC metadata，避免 query 被业务跳转、普通参数和代理误用。

### Q3：为什么两层 fail-closed？

API 保护正常入口，Domain 防止绕过 API 直连；任一层识别不清都拒绝。

### Q4：影子表为什么不够？

只隔离数据名，仍共享数据库 CPU、IO、连接池、锁和其他缓存/消息资源。

### Q5：怎样证明压力标没有丢？

用同一 request_id 串 API、RPC、SQL、KV 和下游 trace，抽样检查标记和值一致。

### Q6：HTTP 200 为什么不算成功？

响应体可能是业务错误，甚至入口短路。需要解析业务码并做写后查询。

### Q7：业务断言有哪些？

报名可查询、任务积分变化、答题记录正确、抽奖机会/库存/中奖记录一致，正式副作用为零。

### Q8：UV 怎么换 QPS？

按页面打开率、峰值集中、接口数、参与率、人均任务和抽奖次数拆到接口，不能平均除总时长。

### Q9：为什么从 1 QPS 开始？

先证明路由和副作用隔离，再验证容量；错误设计在 1 QPS 已能发现，不需要先制造大量污染。

### Q10：97.77% 为什么不能说基本通过？

失败可能说明场景没完整执行，也未满足 SLA；必须分类根因而不是用总量稀释。

### Q11：500 QPS 能支撑多少 UV？

不能直接换算。它只是单接口、单机、特定流量模型下的阶段结果。

### Q12：为什么不压到崩溃？

目标是验证业务目标和余量，不是破坏共享环境。达到停压阈值就停止。

## 八、MQ 写放大：十组连续追问

### Q1：活动结束后为什么还会收到消息？

至少一次投递、积压、重试、重平衡和人工回放都会产生晚到消息。

### Q2：事件时间和当前时间有什么区别？

事件时间判断当时是否合法；当前时间判断现在是否仍允许产生新副作用。

### Q3：为什么跳过返回 nil？

结束活动是正常业务状态。返回 error 会让 MQ 继续重试。

### Q4：为什么需要两层 guard？

fanout 前减少资源，处理器内部守住不变量，防未来新入口绕过。

### Q5：为什么删配置不够？

配置清理有延迟、缓存和人为遗漏；生命周期必须由消费者自己判断。

### Q6：锁为什么解决不了？

锁只防同一消息并发，不判断这条消息是否应该处理。

### Q7：为什么确定性采样？

同一重放事件每次得到相同决定，不会普通随机那样多次命中并制造新写。

### Q8：采样键为什么包含 reason？

同一内容不同失败原因可以独立观测，但存储覆盖语义要明确。

### Q9：为什么运行时 DTO 和存储 DTO 分开？

校验需要丰富字段，长期排障只需关键归因；直接存运行时对象会放大体积和耦合。

### Q10：如果业务需要结束后补算怎么办？

增加显式 backfill 模式、时间范围、限流、dry-run、幂等 namespace 和审计，不放开普通在线消费者。

## 九、十道现场白板题

### 白板 1：画十连抽事务

必须画出：幂等查询、条件扣机会、概率/保底、编号、实例、抽卡记录、资产流水、提交后掉落履约。

### 白板 2：画赠卡状态机

```text
HELD -> LOCKED -> HELD(new owner)
             \-> HELD(original owner) on cancel/expire
```

同时画 transfer：AVAILABLE -> COMPLETED / CANCELED / EXPIRED。

### 白板 3：画集齐兑换两阶段

本地事务占卡与 pending；提交后领取 grant slot；外部幂等发机会；completed/failed；超时 worker 接管。

### 白板 4：写机会扣减 SQL

重点是条件更新和 affected_rows，不要写先 SELECT 再 UPDATE。

### 白板 5：设计进度快照

画用户行为、个人积分、离线聚合、KV 快照和 C 端读取，并注明最终一致性和快照更新时间。

### 白板 6：设计批量权益表

如果要求增强方案：batch、item、grant_record 三层，包含状态、幂等键、错误、重试次数和 cursor。

### 白板 7：画 v1/v2 灰度

入口 router 一次选择版本；读路径可双算；写路径不直接双写；开关回滚。

### 白板 8：画压力标传播

Header -> HTTP context -> RPC metadata -> DB/KV/MQ/downstream；每层标 fail-closed 和证据。

### 白板 9：画 MQ 生命周期 guard

配置活动列表 -> current state filter -> fanout -> handler second guard -> event-time validation -> idempotent write。

### 白板 10：从 UV 推 QPS

写出假设、公式和安全系数；面试官更看重推导过程，不要求猜中真实数字。

## 十、从项目跳到 MySQL 的十道题

### Q1：联合索引顺序怎么定？

按等值条件、范围条件和排序设计，同时看选择性和真实查询；不能机械把高选择性放最前。

### Q2：唯一索引能否替代幂等表？

只能防重复写，不能保存旧结果、冲突参数和业务状态。

### Q3：什么情况下会死锁？

并发事务以不同顺序锁多行。统一锁顺序、缩短事务、捕获死锁并安全重试。

### Q4：默认隔离级别对项目有什么影响？

需要能解释快照读、当前读、行锁和幻读；具体行为以数据库实现为准。

### Q5：为什么外部 RPC 不放数据库事务里？

延长锁时间、外部超时不可控、事务无法回滚外部副作用。

### Q6：大表分页为什么不用 OFFSET？

深分页扫描成本高；使用主键或复合游标 seek pagination。

### Q7：如何设计资产流水？

业务键、delta、after_balance、source、counterparty、时间和唯一 flow_id。

### Q8：计数器如何避免热点？

独立计数器、号段预分配、分片或异步聚合；根据是否允许空洞选择。

### Q9：如何在线加唯一索引？

先清理重复数据，评估锁和 DDL 能力，灰度校验，准备回滚和写入兼容。

### Q10：事务成功但响应丢失怎么办？

客户端重试相同幂等键，服务端重建旧结果。

## 十一、从项目跳到 Redis/KV 的八道题

### Q1：缓存和数据库一致性怎么办？

先明确权威源。常见是写 DB 后删除缓存，结合重试、消息或版本号；不存在万能强一致。

### Q2：分布式锁为什么要 token？

防止锁过期后旧 owner 删除新 owner 的锁。

### Q3：锁续期怎么做？

定期续租并校验 owner；进程停止后最终过期。业务仍需幂等。

### Q4：热 key 怎么处理？

本地缓存、分片、批量、降频、异步聚合和读副本，先通过监控确认热点。

### Q5：缓存穿透、击穿、雪崩区别？

不存在 key 高频查询、热点 key 失效、批量 key 同时失效；分别用空值/布隆、互斥回源、随机 TTL 等。

### Q6：为什么 KV 幂等标记不能作为唯一审计？

TTL、淘汰和写失败会丢历史；高价值权益需要持久化记录。

### Q7：原子脚本有什么风险？

执行时间长会阻塞、脚本与集群能力不兼容、返回类型和版本难维护。

### Q8：namespace 是否等于物理隔离？

不是，仍共享 CPU、内存、网络和分片热点。

## 十二、从项目跳到 MQ 的八道题

### Q1：至少一次投递是什么意思？

消息可能重复，消费者必须幂等；不能假设 exactly once。

### Q2：如何设计消费幂等键？

优先使用上游 event_id；没有时使用能唯一表达业务动作的组合键。

### Q3：顺序消息如何保证？

同一业务键路由到同一分区并单分区有序；全局有序成本高。

### Q4：消息积压怎么办？

先判断生产突增还是消费变慢；扩容消费者、优化慢依赖、限流和分批回放。

### Q5：死信队列怎么处理？

记录失败原因、人工或自动修复后按原幂等键重放，不直接丢弃。

### Q6：数据库写和发消息如何一致？

事务消息、outbox 或本地事件表加可靠投递；不能普通事务提交后无保护地发 MQ。

### Q7：消费成功但 ack 失败怎么办？

消息会重投，因此消费副作用必须幂等。

### Q8：什么时候不应该自动重试？

参数永久错误、业务已关闭或不满足规则；应记录并确认消费，避免毒消息无限循环。

## 十三、从项目跳到 RPC 的六道题

### Q1：超时和失败有什么区别？

超时结果未知，不能断言下游未执行；失败也要区分可重试和永久错误。

### Q2：什么时候可以自动重试？

只读或有稳定幂等键的请求；有副作用且无幂等时不能盲目重试。

### Q3：如何避免重试风暴？

指数退避、抖动、重试预算、熔断和服务端限流。

### Q4：为什么接口要返回用户级结果？

批量调用可能部分成功，调用方需要只重试失败项。

### Q5：IDL 新增字段如何兼容？

新增 optional 字段和默认行为，不复用已有字段编号，不让旧服务依赖新字段必填。

### Q6：跨仓为什么走 RPC 而不是 import？

独立服务的运行、发布和故障边界需要协议隔离。

## 十四、从项目跳到 Go 的八道题

### Q1：goroutine 泄漏怎么发生？

阻塞 channel、无退出条件、下游调用无 context；使用取消、超时和可观测计数。

### Q2：context 应该传什么？

取消、deadline 和请求级 metadata；不要塞可选业务参数或大对象。

### Q3：map 并发安全吗？

普通 map 不是；使用锁、sync.Map 或单 goroutine 所有权，根据访问模式选择。

### Q4：如何限制批处理并发？

信号量或固定 worker pool，结合 context、错误收集和下游限额。

### Q5：defer 在循环里有什么风险？

直到函数返回才执行，可能积累资源；把单次逻辑封装成函数。

### Q6：panic 怎么处理？

入口边界 recover、记录 stack 并返回明确错误；不能用 recover 掩盖普通业务错误。

### Q7：interface nil 有什么坑？

接口包含具体类型和 value；内部 typed nil 时接口本身不等于 nil。

### Q8：如何测试并发代码？

可注入时钟/随机数/依赖，使用 barrier 控制时序，跑 race detector，并验证业务不变量而非只看无报错。

## 十五、十个故意质疑你的问题

### 1. “你这个方案不就是加个 Redis 吗？”

回答：Redis 只是实现介质，核心是选择最终一致快照、定义权威源、处理任务乱序和快照缺失。

### 2. “批量发放直接 for 循环不行吗？”

回答：for 循环没有解决分组、部分成功、超时未知、幂等和运营恢复。

### 3. “重构没有性能收益，为什么要做？”

回答：目标是降低变更影响和发布耦合；用修改仓库数、回滚时间和接入周期衡量。

### 4. “影子表都有了，你为什么还这么谨慎？”

回答：缓存、消息、权益和物理资源仍共享，表隔离只覆盖一层。

### 5. “活动都结束了，删配置不就行了？”

回答：配置清理是运维动作，有延迟和缓存；消费者必须自行守生命周期。

### 6. “这些服务端方案不是你写的，你为什么讲？”

回答：明确区分理解与所有权；集卡服务端用于解释联调边界，个人服务端项目另有明确提交。

### 7. “你是不是把 AI 的答案背下来了？”

回答：说明一个实际取舍、被拒绝方案和真机/日志/代码证据，证明能独立判断。

### 8. “如果重新做，你会全部上状态机框架吗？”

回答：先看复杂度。显式枚举和受控迁移够用时不引入额外框架；跨系统长流程才考虑更强编排。

### 9. “你怎么证明业务结果是你的贡献？”

回答：不独占业务结果，说明自己的技术动作怎样支撑能力和稳定性。

### 10. “你现在记不清具体实现怎么办？”

回答：坦白不记得具体常量，回到确定的不变量和方案边界，不现场编造。
