这是 AI Town 课程的最后一讲。

前六讲我一直在拆 AI Town 的内部机制：Convex 调度怎么驱动世界、单线程 step 怎么保护状态、历史回放怎么省数据库、异步 LLM 怎么不阻塞主循环、记忆怎么写进向量再召回。每一讲都是在回答"它是怎么做的"。

但课程读到这里，真正的问题其实换了一个：**当我自己去做一个 Agent 产品时，AI Town 这套东西哪些该照搬，哪些该扔掉？**

AI Town 是一个很完整的样板，但它毕竟是为"像素小镇 + 自主社交 NPC"这个具体场景写的。如果不加分辨地整套搬到客服、协作工具或者虚拟社群上，很容易把它的"特例"也搬过去，最后被根本不属于你场景的复杂度拖死。

所以这一讲我不贴大段代码，更像一篇架构随笔：把前六讲的经验抽象成几条迁移取舍原则，最后给一张"该留 / 该换"的清单。

## 先分清楚：什么是骨架，什么是皮肤

读源码时有一个判断标准我一直在用：**这段设计是为了解决"任何多 Agent 系统都会遇到的问题"，还是为了解决"像素小镇这个具体场景"的问题？**

前者是骨架，迁移时要留；后者是皮肤，迁移时要换。

AI Town 的代码其实已经帮我们把这两层分得比较干净了。它的 `convex/` 目录里有一个很说明问题的分层：

- `convex/engine/` —— 通用引擎层，里面是 `abstractGame.ts` 和 `schema.ts`，完全不知道"小镇""角色""对话"是什么；
- `convex/aiTown/` —— 游戏层，`game.ts` 才把抽象引擎具体化成一个有玩家、有对话、有地图的世界；
- `convex/agent/` —— Agent 层，负责记忆、对话生成这些和 LLM 打交道的部分。

这个分层本身就是迁移指南。`engine/` 是骨架，`aiTown/` 里大部分是皮肤，`agent/` 介于两者之间。下面我按这个思路展开。

## 值得照搬的五件事

### 一、可靠调度：别用常驻循环驱动世界

这是第二讲讲过的，但放到迁移视角里它的价值更明显。

很多人做 Agent 产品的第一版，都会写一个 `while (true)` 加 `sleep` 的循环来推进任务。单机能跑，但一进 serverless、一上多实例、一遇到部署重启，就会出现进程被回收、循环中断、多实例并跑、失败后不知道从哪恢复这些问题。

AI Town 的做法是把"下一次什么时候继续"变成一个持久化的调度任务，用 `ctx.scheduler` 安排未来的 step。世界的推进不依赖某个进程永远活着，而依赖调度记录还在。

这一条几乎是无条件照搬的。任何需要"长期运行、可恢复、可能跨多实例"的 Agent 系统，都该把推进逻辑建在可靠的调度 / 队列 / 工作流引擎上。你不一定要用 Convex，但一定要有一个"持久化的下一步"。

### 二、单线程权威状态：让核心状态只有一个写入者

这是整套设计里我最想让你带走的一条。

`convex/engine/abstractGame.ts` 里的 `AbstractGame` 把它表达得很清楚：外部世界只能往 `inputs` 表里塞输入，真正改世界状态的只有 `runStep` 这一个串行入口。`runStep` 里先 `loadInputs` 把这一批输入读出来，然后在内存里连续 tick，最后算出 diff 一次性写回。

这意味着同一个 world 的状态在语义上只有一个写入者。用户点击、NPC 移动、LLM 回复、记忆写入，全都先变成 input，再由引擎串行裁决。没有两个异步函数同时写同一条记录，没有慢 LLM 覆盖新状态，没有乱序，没有半更新。

迁移时这一条几乎可以原样保留，只是"world"换成你的业务实体：一个客服会话、一份协作文档、一个工作流实例。只要这个实体会被多个来源并发修改，"外部提交事件 + 内部串行消费"就值得用。

AI Town 还配了一个细节值得一起搬走：`engine` 表里的 `generationNumber`（见 `convex/engine/schema.ts`）。每次 step 提交时它自增，`applyEngineUpdate` 会校验 `expectedGenerationNumber` 是否匹配。这样一个过期的"旧闹钟"重新唤醒时，会发现 generation 对不上而直接退出，不会去搅乱一个已经被新任务接管的世界。任何"定时任务 + 可能重复触发"的系统都需要这种乐观版本号。

### 三、服务端权威 + 前端回放：把写入频率和渲染频率解耦

第四讲讲过历史回放。迁移视角下，它的本质是一句话：**服务端低频写权威状态，前端高频渲染连续表现。**

AI Town 的引擎可以按 `tickDuration = 16`（约 60fps）在内存里推进，但不会每个 tick 都写库；它把一段时间内的位置变化攒成历史 buffer，step 结束时一起存（这就是 `serializedWorld` 里的 `historicalLocations`，以及 `convex/engine/historicalObject.ts` 那套编码）。前端拿到的是一小段轨迹，自己在本地插值回放，看起来就很平滑。

只要你的产品是"服务端有权威状态、前端要连续表现"，这个模式就能借鉴：数据大屏的曲线、协作文档里别人的光标、机器人路径回放、实时看板。

但要记住它的适用边界：历史回放只适合**数值型、连续型、可插值**的状态。位置、进度、速度可以；"是否已付款""订单是否取消"这种语义离散、不能插值的状态不行。迁移时别把它无脑套到所有字段上。

### 四、快慢分层：让慢思考离开主循环

第五讲的核心。游戏循环要快、要确定、要可恢复；LLM 调用慢、不稳定、会超时会失败。两者性格相反，绝不能混在一个同步流程里。

AI Town 把 Agent 行为拆成两层：同步的 `Agent.tick`（跟着引擎跑，只做"我在哪、有没有到目标、当前操作完没完成"这种轻判断）和异步的 operation（凡是 LLM、embedding、向量检索、总结，都丢给一个 Convex action 去跑，`convex/aiTown/agentOperations.ts`）。

关键边界是：**异步操作的结果不直接改世界，而是回头再提交一个 input**，由引擎在下一次 step 里决定它还算不算数。一句话概括就是"智能体可以异步思考，但状态机必须同步裁决"。

这条对真实 Agent 产品几乎是刚需，而且要搬得更狠。真实产品里慢操作不只有 LLM，还有工具调用、检索增强、外部 API、人工审核。所有这些慢操作都该走"异步执行 + 结果回灌成事件"的路子，而不是让它们在主流程里同步等待。AI Town 还限制一个 Agent 同时只能有一个进行中的 operation，这个"单飞"约束在真实产品里同样能避免一堆乱序覆盖的 bug。

### 五、记忆生命周期：难点不是向量库，而是写召忘

第六讲反复强调过：Agent memory 的难点从来不是"加个向量数据库"，而是整条生命周期——什么时候写、写什么、怎么召回、怎么注入、怎么遗忘和纠错。

`convex/agent/schema.ts` 把这条经验固化进了 schema：`memories` 表存的不是原始聊天记录，而是带 `importance`（重要性）、`lastAccess`（最近访问）、`data`（区分 relationship / conversation / reflection 三类来源）的结构化记忆；`memoryEmbeddings` 单独存向量并建 `vectorIndex`；还有一张 `embeddingsCache` 用 `textHash` 缓存 embedding，避免重复算同样的文本。

这套结构是可以直接照搬的设计语言：摘要而非全文、结构化字段配合向量、重要性和时间参与排序、embedding 结果缓存。换成客服就是用户画像和历史工单，换成协作工具就是团队知识沉淀，骨架完全一样。

## 它的特例：做产品时要换掉的几样

照搬完骨架，接下来是更重要的判断——哪些是 AI Town 为它自己的场景写的，到了你的产品里要换掉。

### 像素游戏世界本身

这是最明显的皮肤。`convex/aiTown/` 里大量东西是为"二维小镇"服务的：`worldMap.ts` 的地图、`movement.ts` 的寻路、`location.ts` 的坐标、`maps` 表、玩家的 `x/y` 位置。这些在客服、协作工具里根本不存在。

迁移时这一整层基本是删掉重写的。但注意：删的是"二维空间"这个具体模型，留的是它套在 `engine/` 之上的方式。你要做的是用自己的领域模型（会话、文档、工单）去填 `Game extends AbstractGame` 这个位置，而不是连引擎一起扔。

### tick 模拟这种连续时间推进

AI Town 是个**仿真**：它需要每 16ms 推一个 tick，让角色平滑地走、让世界连续地动，所以 `game.ts` 里设了 `tickDuration = 16`、`maxTicksPerStep = 600`，一个 step 内部要空跑几百个 tick。

但绝大多数 Agent 产品不是仿真，是**事件驱动**。客服会话没事的时候应该完全静止，不需要每秒推 60 帧；它只在"用户发消息""LLM 回复到了"这种事件发生时才需要前进一步。

所以迁移时，连续 tick 循环通常要换成纯事件驱动的 step：没有输入就不调度、不推进，有输入才唤醒。`AbstractGame` 的 `inputs → step → diff` 这个骨架可以留，但内部那个"为了仿真而存在的高频 tick 空转"对你多半是负担。把 `maxTicksPerStep` 降到 1、让 step 由事件触发，往往就够了。

### 和 Convex 的强绑定

AI Town 的可靠性很大程度上是 Convex 给的：`mutation` 的事务性、`scheduler` 的持久化、`action` 承接副作用、`query` 的实时订阅、内置 `vectorIndex`。这套东西很顺手，但它是一个具体技术选型。

迁移到自己的栈时，你要保留的是**这些语义**，而不是 Convex 这个名字：

- 一个有事务保证的"确定性状态写入"边界（对应 mutation）；
- 一个持久化的"下一步调度"机制（对应 scheduler，可以是消息队列、Temporal、cron+幂等任务）；
- 一个隔离副作用的"外部调用"边界（对应 action）；
- 一个能做实时推送的读侧（对应 query 订阅，可以是 WebSocket、SSE）；
- 一个向量检索能力（任意 vector DB）。

把 AI Town 读成"必须用 Convex"是误读；把它读成"任何 Agent runtime 都需要这五种能力，Convex 恰好一站式提供"才是对的。

## 把抽象映射到常见 Agent 产品

同一套骨架，套到不同产品上长什么样？我列四个常见场景。

**AI 客服**：用户消息变成 input，会话状态机就是单线程 step，LLM 回复走异步 action 再回灌成 input，客户画像和历史工单走 memory 检索，前端聊天流用流式/回放呈现。这里几乎是 AI Town 骨架的最直接映射，只是去掉了地图和移动。

**多人协作工具**：用户编辑操作进 input log，文档状态由引擎串行应用（这其实就是 OT/CRDT 的另一种表述），AI 辅助编辑是异步 operation，历史版本就是 replay / diff，团队知识进 vector memory。单线程权威状态在这里尤其值钱，它天然解决并发写冲突。

**游戏 NPC**：这是和 AI Town 最像的场景，几乎可以整套留下——世界模拟用 step loop，NPC 轻决策用 `Agent.tick`，复杂对白用 LLM action，角色经历进 memory，客户端动画用历史回放。这种场景下连 tick 模拟都可能要保留。

**虚拟社群 / 多智能体沙盒**：本质就是 AI Town 去掉像素皮肤的版本——一群 Agent 持续自主交互、产生关系、积累记忆。这里要留的恰恰是被很多人当成"游戏专属"的那些东西：持续运行的世界、`participatedTogether` 这种关系图（见 `convex/aiTown/schema.ts`）、长期记忆。

可以看出，越靠近"自主、持续、多体"，要保留的 AI Town 成分越多；越靠近"被动、事件触发、单会话"，要换掉的越多。这条轴能帮你判断自己的产品该从 AI Town 抄多少。

## 三层 schema 给的"状态分层"启发

最后我想专门讲讲三个 `schema.ts`，因为它们其实在教一件比代码更重要的事：**怎么给 Agent 系统的状态分层。**

把三层放在一起看：

- **引擎状态**（`convex/engine/schema.ts`）：`engines` 表只存 `currentTime`、`processedInputNumber`、`generationNumber`、`running` 这几个字段，`inputs` 表存输入队列。这一层只关心"时间推到哪了、输入处理到第几条、当前是第几代"，完全不知道业务是什么。它是**控制平面**。
- **游戏 / 业务状态**（`convex/aiTown/schema.ts`）：`worlds` 表用一个文档装下所有 players / conversations / agents 这些**热状态、频繁变、需要被引擎独占**的东西；同时把不常变的拆出去——`maps`、`playerDescriptions`、`agentDescriptions` 各自一张表；还有一组 `archived*` 表，专门存"引擎不想再管、但 UI 和 Agent 还想看"的冷数据。这是**业务平面**。
- **Agent / 记忆状态**（`convex/agent/schema.ts`）：`memories` + `memoryEmbeddings` + `embeddingsCache`，这是引擎主循环之外的**知识平面**，按需检索，不参与每一步的状态推进。

这个分层的启发是清晰的：

1. **控制状态和业务状态要分开。** 调度、版本号、输入游标这些是引擎自己的事，不要和业务字段混在一张表里。
2. **热状态和冷状态要分开。** 频繁变、要被引擎独占的状态尽量集中（AI Town 极端到塞进一个 world 文档，方便单线程加载和保存 diff）；不常变的描述、地图拆出去；已经结束的、引擎不再关心的归档掉。
3. **主循环状态和知识状态要分开。** 记忆不该在每个 step 里被同步读写，它是异步检索的知识层，独立于状态机的推进节奏。

迁移时，哪怕你完全不用 Convex，这三条分层原则也照样成立。先想清楚自己系统里的控制平面、业务平面、知识平面各是什么，再去选存储，往往比直接照抄表结构更有用。

## 一张"该留 / 该换"清单

把上面的判断浓缩成一张表，迁移时可以直接对照：

```text
┌────────────────────────┬──────────┬──────────────────────────────────┐
│ AI Town 的做法          │ 迁移建议 │ 原因 / 替换方式                  │
├────────────────────────┼──────────┼──────────────────────────────────┤
│ 持久化调度驱动 step     │ 留       │ 任何长跑系统都需要可恢复的下一步 │
│ 单线程权威状态 + input  │ 留       │ 并发写冲突的通用解法             │
│ generationNumber 版本号 │ 留       │ 处理过期任务 / 重复触发          │
│ 服务端低频写 + 前端回放 │ 看情况   │ 仅适合数值型、可插值的连续状态   │
│ 快慢分层(tick / action) │ 留并加强 │ 所有慢操作都该异步 + 回灌事件    │
│ 单 Agent 单 operation   │ 留       │ 避免乱序覆盖                     │
│ 记忆生命周期 + 结构化   │ 留       │ 难点是写召忘，不是向量库本身     │
│ 三层 schema 状态分层    │ 留(原则) │ 控制 / 业务 / 知识三平面分离     │
├────────────────────────┼──────────┼──────────────────────────────────┤
│ 像素地图 / 移动 / 坐标  │ 换       │ 你的领域模型替换这一层           │
│ 高频 tick 仿真          │ 换       │ 多数产品是事件驱动，不是仿真     │
│ 强绑定 Convex           │ 换       │ 留语义，换实现                   │
│ world 单文档塞全部状态  │ 看情况   │ 状态大时要拆，AI Town 是小状态   │
└────────────────────────┴──────────┴──────────────────────────────────┘
```

判断口诀其实就一句：**凡是解决"多 Agent / 长跑 / 并发 / 不确定 LLM"的，留；凡是解决"二维小镇 / 连续仿真 / Convex 选型"的，换。**

## 收尾：这门课的主线

七讲下来，如果只让我留一句话，那就是第一讲就说过、到这一讲反而更确信的那句：

**AI Town 真正值钱的不是像素小镇，而是它把不确定的 LLM 装进了一个确定的系统。**

回顾整条主线：

- 第一讲，我们看清它是一套 Agent 基础设施，不是游戏 demo；
- 第二讲，scheduler 让世界可靠续跑，而不是靠常驻进程；
- 第三讲，单线程 step 让核心状态只有一个写入者；
- 第四讲，历史回放让服务端低频写、前端高频动；
- 第五讲，异步 LLM 让慢思考离开主循环，结果回灌成 input；
- 第六讲，记忆生命周期把对话压成摘要、存进向量、按需召回；
- 这一讲，我们把前六讲抽象成迁移真实产品时的取舍。

这套设计最聪明的地方，是它从头到尾**没有把 LLM 放在系统中心**。LLM 只是一个会产生文本和建议、慢而不可靠的异步组件；真正的中心是状态机、事件流和调度。正因为中心是确定的，那个不确定的 LLM 才能被安全地接进来。

如果你要做自己的 Agent 产品，建议先把 `convex/engine/` 这层骨架读懂，再决定 `aiTown/` 那层皮肤长什么样。骨架几乎可以照搬，皮肤一定要重画。

这门课到这里就结束了。希望你以后再看到任何"AI + 某某界面"的炫酷 demo 时，会下意识地把 UI 拿掉，去问一句：它底下的状态机、事件流、调度和记忆，到底是怎么搭的？
