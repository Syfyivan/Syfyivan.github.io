学代理工具之前，先别急着看配置。配置只是把流量送到不同路径，真正要理解的是：一次请求本来会怎么走。

很多“代理连不上”的问题，其实不是代理协议坏了，而是 DNS、TCP、TLS、HTTP、系统代理设置、TUN 路由里的某一段出了偏差。把路径拆开之后，问题会清楚很多。

## 一次请求不是一个动作

你在浏览器里输入：

```text
https://example.com/articles/1
```

它大致会变成这样：

```text
URL
  -> 找到域名 example.com
  -> DNS 解析出 IP
  -> 选择传输层：TCP 或 QUIC
  -> 建立安全层：TLS
  -> 发送 HTTP 请求
  -> 收到 HTTP 响应
  -> 浏览器继续加载 CSS、JS、图片、字体
```

这不是严格的实现流程图，因为浏览器会缓存 DNS、复用连接、预连接、并发加载资源，也可能通过 HTTP/3 走 QUIC。但对排障来说，这张图够用：每一段都有自己的输入、输出和失败方式。

## DNS：先把名字变成地址

浏览器和大多数应用不会直接连接 `example.com` 这个字符串。它需要先知道目标 IP。

DNS 做的事可以先理解成：

```text
example.com -> 93.184.216.34
```

但真实 DNS 比这复杂：可能有 CNAME 跳转，可能同时返回 IPv4 的 A 记录和 IPv6 的 AAAA 记录，结果会被缓存，缓存多久由 TTL 影响。更重要的是，谁来解析 DNS，会影响代理规则后面能看到什么。

比如一个代理客户端要按域名分流，它就希望知道“这个 IP 是哪个域名解析来的”。如果某个应用绕过系统 DNS 自己解析，或者浏览器启用了独立的 DoH，代理客户端看到的上下文就可能不同。

## TCP：可靠字节流

如果请求走 HTTP/1.1 或 HTTP/2，底层通常是 TCP。TCP 给上层提供的是“可靠、有序的字节流”。上层不用自己处理丢包重传、乱序重排和流量控制这些细节。

可以先把 TCP 想成一根可靠管道：

```text
客户端 socket <==== 字节流 ====> 服务端 socket
```

这根管道有几个排障关键词：

- 端口：HTTP 常见 80，HTTPS 常见 443，但服务可以用别的端口；
- 连接建立：客户端要能到达目标 IP 和端口；
- 超时：连接超时通常说明路径、路由、防火墙、目标服务可达性有问题；
- 复用：HTTP/2 会在一条连接里跑多个 stream，所以“请求慢”不一定等于“新建连接慢”。

代理工具里的 HTTP 代理、SOCKS 代理、CONNECT 隧道，本质上都要处理这些连接。

## QUIC：跑在 UDP 上的新传输层

HTTP/3 不再直接跑在 TCP 上，而是跑在 QUIC 上。QUIC 使用 UDP 承载数据，但它不是“无状态随便发包”。QUIC 自己实现了连接、加密、拥塞控制、多路复用和丢包恢复。

这对代理排障有一个直接影响：同一个网站，HTTP/2 和 HTTP/3 的网络路径可能表现不同。TCP 443 能通，不代表 UDP 443 一定通。某些网络环境会限制 UDP，某些代理入口也未必完整支持 QUIC。

所以看到“浏览器访问慢，但关掉 HTTP/3 后好了”时，不要急着说网站坏了。它可能只是 UDP/QUIC 这条路径出了问题。

## TLS：保护内容，不保护所有元数据

HTTPS 的安全性来自 TLS。TLS 的目标是让客户端和服务端之间的数据具备机密性、完整性和身份认证能力。简单说：

```text
TCP/QUIC 负责运送
TLS 负责加密和验证
HTTP 负责表达请求和响应
```

TLS 保护的是连接里的应用数据。没有中间人解密时，代理通常不能看到完整 URL、header 和 body。它可能只能看到目标 IP、端口、部分握手信息，以及在未被加密隐藏时的 SNI。

这就是为什么 MITM 调试要额外安装并信任本地 CA。MITM 不是普通代理的必需步骤，而是主动改变 TLS 信任边界的调试手段。

## HTTP：应用层语义

HTTP 关心的是资源和动作：

```text
GET /articles/1 HTTP/1.1
Host: example.com
Accept: text/html
```

响应里有状态码、响应头和 body：

```text
HTTP/1.1 200 OK
Content-Type: text/html
```

HTTP 的关键点是“语义”。`GET`、`POST`、状态码、缓存、重定向、header、cookie 都属于这一层。代理如果不开 MITM，通常无法读取 HTTPS 里的完整 HTTP 内容；如果是普通 HTTP 明文流量，代理就能直接看到并修改。

## 代理工具插在哪些位置

现在把代理工具放回图里：

```text
应用
  -> DNS
  -> 系统代理 / 本地端口 / TUN / 透明代理
  -> 规则引擎
  -> 直连或代理出口
  -> 目标服务
```

不同工具和模式插入的位置不同。

系统代理更靠近应用层：应用愿意遵守系统代理设置，流量才会进来。

TUN 更靠近网络层：应用不知道代理存在，操作系统路由把 IP 包送进虚拟网卡。

透明代理和路由器方案更靠近网络出口：局域网设备可能完全不知道流量被接管了。

这几种方式没有绝对高级低级，只有适合不适合。系统代理简单清楚，TUN 覆盖面大但排障复杂，透明代理适合整网接管但最难定位。

## 排障时先问四个问题

第一，域名是谁解析的？

如果 DNS 不在代理工具控制范围内，域名规则、fake-ip、按域名选择出口都可能失效。

第二，流量有没有进入代理客户端？

系统代理模式下，不遵守系统代理的应用可能直接出去了。TUN 模式下，路由表、权限、IPv6、回环地址都可能影响接管。

第三，规则命中了什么？

规则引擎通常是按顺序匹配。命中的第一条规则，可能不是你以为的那条。

第四，出口到目标是否可达？

入口没问题、规则也没问题，不代表出口没问题。出口的 DNS、TLS、UDP、远端路由、服务端状态仍然可能失败。

## 一个最小心智模型

不要把代理工具理解成“开关”。更准确的模型是：

```text
接管流量 -> 补足上下文 -> 匹配规则 -> 选择出口 -> 观察结果
```

接管失败，工具根本看不见请求。

上下文不足，规则就可能匹配不到。

规则顺序错，流量会走错出口。

出口不可达，入口看起来再正常也没用。

观察能力差，问题只能靠猜。
