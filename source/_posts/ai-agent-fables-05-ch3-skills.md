> 承上：上一章阿器学会了对接统一柜台、借单件工具。这一章他发现，有些活儿不是靠一件工具，而是靠一整套配好的“工具包”。

阿器接了个没干过的活：给铜器做旧。他不知从何下手。老掌柜从高处架上取下一个布包：“这是‘铜器做旧’的整套，平时收着不占地方，要用才取。”

布包封皮上先写着一句话：这包是干嘛的、什么时候该用它。阿器一看就知道“这次该用它”。翻开，里面是一张分步说明：先用什么、再用什么、注意什么；说明里还夹着几样配好的小器具和一张配方纸，照着用就行。

“妙就妙在，”老掌柜说，“你平时不用记住这一整套，架上摆着几百个这样的包也不占你脑子。你只要扫一眼封皮，判断这次用不用得上；用得上，再取下来翻开细看。”

## 概念揭晓

架上这种“带说明书的工具包”，就是 **Skill（技能 / Agent Skill）**：把完成某类任务需要的说明、资源和脚本，打包成一个 Agent 可以按需加载的能力单元。

包的几样东西，对应 Skill 的结构：

- 封皮那句“是干嘛的、何时用” = **SKILL.md 的元信息**：一段简短描述，让 Agent 据它判断“这次该不该用这个 Skill”。
- 翻开后的分步说明 = **SKILL.md 正文**：完成任务的指引、步骤、注意事项。
- 夹着的小器具和配方纸 = **随附的脚本和资源（scripts / resources）**：可执行的工具、参考文件、模板等。

“平时只看封皮、用到才翻开细看”，是 **渐进式披露（progressive disclosure）**：不一次把所有细节塞进上下文，而是先给一句摘要，需要时才加载完整内容。这直接呼应第三、四讲——上下文是有限、要花钱的预算。

## Skill 和单个工具的区别

一个**工具**（05.1）通常是一个原子动作：算一次、查一次、写一次。一个 **Skill** 更像“一套做法 + 配套资源”：它可能内部用到好几个工具、附带脚本和参考资料，封装的是“怎么把某类任务做好”的整套知识。

打个比方：工具是“一把卷尺”，Skill 是“一整套量地放线的活计，连步骤带配方”。当某类任务反复出现、又有固定套路时，把它沉淀成 Skill，比每次都现教模型怎么做要可靠得多。

## 渐进式披露为什么关键

如果把几百个 Skill 的全部细节都塞进模型的上下文，窗口立刻爆掉，关键信息也被淹没（第三、四讲反复说的坑）。

渐进式披露解决这个矛盾：平时每个 Skill 只占“一句封皮描述”，Agent 扫一眼就能判断相关不相关；只有真正要用的那个，才把完整说明和资源加载进来。于是“能力可以很多，上下文却不被撑爆”。这是 Skill 设计里最聪明的一点。

算笔账就直观了：一个 Skill 的封皮描述可能只有几十 token，完整的 SKILL.md 正文加资源可能上千 token。如果架上有几百个 Skill，全展开就是几十万 token，窗口当场爆掉；只摊开封皮，几百个加起来也才一两万 token，扫一遍毫无压力。"先看封皮、用到才翻开"省下的，正是这个量级的差距。

## SKILL.md 该写什么

一个好的 Skill 说明，重点不在堆细节，而在让 Agent“正确地用对地方”：

- **什么时候用、什么时候别用**（最重要，决定它会不会被正确触发）。
- 完成任务的清晰步骤。
- 需要哪些输入、产出什么。
- 随附脚本/资源怎么调用。
- 常见坑和边界。

你会发现，这和 04.1 的“委托单”、05.4 的“工具说明牌”是同一种素养：把意图和用法写清楚，让执行者照着就能做对。

## Skill、工具、MCP 怎么配合

三者是不同层次、互相配合的：

- **工具**：单个原子能力。
- **MCP**：让工具和数据源以统一方式接入的协议（统一柜台）。
- **Skill**：把“完成某类任务的说明 + 资源 + 脚本”打包成按需加载的能力单元，内部可以调用工具。

一个成熟的 Agent，往往同时拥有：一堆通过 MCP 接入的工具，加上一架按需取用的 Skill。这套组合，正是第六讲 Harness 要统一编排的。

## 常见误区

第一，把 Skill 当成“插件”或“又一个工具”。它更像“带说明书的整套做法”，核心价值是把套路和上下文管理打包好。

第二，把所有细节一股脑写进去、还要求常驻上下文。那就丢了渐进式披露的意义。

第三，SKILL.md 只写“怎么做”，不写“何时用/何时不用”。结果它要么不被触发，要么被乱用。

## 小练习

下面几件事，判断更适合做成“一个工具”还是“一个 Skill”：

1. “把一段文字翻译成英文。”
2. “按公司规范，把一份需求文档拆成 spec、计划和任务清单。”（多步、有固定套路、带模板）
3. “查询某个城市此刻的天气。”
