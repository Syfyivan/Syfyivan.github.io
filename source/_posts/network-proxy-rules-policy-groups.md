代理工具真正核心的能力不是“代理”，而是“分流”。

分流的意思是：同一台设备上的不同请求，可以按域名、IP、端口、协议、进程、网络类型、规则集等条件走不同路径。

```text
请求上下文
  -> 规则引擎
  -> DIRECT / REJECT / 某个代理 / 某个策略组
```

理解规则引擎，比背某个客户端的配置格式更重要。

## 规则要先拿到上下文

一条规则能不能匹配，取决于代理客户端当时知道什么。

常见上下文包括：

- domain：目标域名；
- ip：目标 IP；
- port：目标端口；
- network：TCP、UDP、ICMP；
- process：发起连接的进程；
- inbound：流量从哪个入口进来；
- protocol：HTTP、TLS、QUIC 等可识别协议；
- rule-set：外部规则集；
- geosite / geoip：域名或 IP 分类数据库。

这里有一个关键点：不是所有入口都天然能拿到同样的上下文。

HTTP 代理请求通常带域名。

SOCKS 请求可以带域名，也可以带 IP。

TUN 一开始看到的是 IP 包，需要依赖 DNS 关联、fake-ip、嗅探或规则集补充域名信息。

透明代理在网关上处理流量，进程名通常拿不到，因为进程在另一台设备上。

所以一条规则在本机系统代理模式下能生效，不代表放到路由器透明代理里也能生效。

## 规则通常按顺序匹配

很多工具的规则是从上往下匹配，命中第一条后就停止。

简化一下：

```text
1. DOMAIN-SUFFIX,example.com,PROXY
2. IP-CIDR,10.0.0.0/8,DIRECT
3. MATCH,DIRECT
```

如果请求命中第一条，就不会继续看后面的兜底规则。

这解释了很多问题：

- 兜底规则太靠前，后面的精确规则永远没机会；
- REJECT 规则误伤，后面的 PROXY 规则不会生效；
- 规则集顺序不同，同一个域名走不同出口；
- IP 规则先命中，域名规则没有发挥作用。

排障时不要只问“有没有这条规则”。要问“它前面有没有更早命中的规则”。

## 域名规则和 IP 规则不是一回事

域名规则适合表达业务意图：

```text
*.example.com -> PROXY
```

IP 规则适合表达网络归属：

```text
203.0.113.0/24 -> DIRECT
```

它们都常用，但边界不同。

域名可能解析到多个 IP，CDN 还会按地区、网络、时间返回不同地址。一个 IP 也可能承载很多域名。

所以不要把“某个 IP 属于这个网站”当作永久事实。除非你控制这个网络段，否则 IP 规则更适合粗粒度判断，域名规则更适合表达应用层目标。

## 策略组不是 UI 按钮

策略组看起来像几个按钮：

```text
自动选择
故障转移
手动选择
直连
某个地区
```

但从规则引擎看，它是一个运行时决策器。规则命中策略组后，策略组再决定真正的出口。

常见策略包括：

- select：手动选择；
- url-test：周期性测速，选延迟更低的可用出口；
- fallback：当前出口不可用时切换下一个；
- load-balance：在多个出口之间分摊；
- chained proxy：一个代理再通过另一个代理拨出。

这就是为什么“规则命中了 PROXY”还不够。你还要看 PROXY 策略组当前选中了谁。

## 测速不等于真实体验

自动策略组经常使用一个测试 URL 来判断延迟或可用性。

这有用，但不能迷信。

测速 URL 只证明“这个出口访问这个 URL 的表现”。它不一定代表：

- 出口访问你的目标站点也快；
- UDP/QUIC 可用；
- TLS 握手正常；
- DNS 调度一致；
- 长连接稳定；
- 高并发时仍然稳定。

所以自动选择适合日常可用性，不适合作为所有问题的唯一解释。遇到具体目标异常，还是要看该目标自己的连接日志。

## DNS 规则和路由规则可能是两套

一些工具里，DNS 也有规则。

DNS 规则决定某个域名用哪个上游解析，路由规则决定连接走哪个出口。这两套规则应该配合，而不是互相打架。

常见冲突包括：

- 目标域名用本地 DNS 解析，但连接走远端出口，CDN 调度不匹配；
- 代理节点域名也走需要代理的 DNS，导致启动循环；
- fake-ip 生效了，但连接没有进入对应代理入口；
- DNS 规则命中一个结果，路由规则又按 IP 命中另一条路径。

看到“规则没问题但就是慢”，不要忘了检查 DNS 规则。

## 写规则的简单原则

第一，先粗后细还是先细后粗，要有意识。通常更精确、更危险的规则应该放前面，兜底放最后。

第二，能用域名表达业务，就别过早写死 IP。

第三，规则集不是越多越好。规则越多，越要知道来源、更新频率和顺序。

第四，保留日志可解释性。看到一条请求时，应该能知道它命中了哪条规则、哪个策略组、哪个出口。

第五，不要把 REJECT 当作默认优化。拒绝规则会改变应用行为，误伤时很难定位。

## 一次分流的完整问题

排障时按这几个问题走：

```text
1. 请求有没有进入代理入口？
2. 代理拿到了域名还是只有 IP？
3. DNS 是否和路由规则配套？
4. 第一条命中规则是哪条？
5. 规则动作是出口，还是策略组？
6. 策略组当前选中哪个真实出口？
7. 真实出口到目标是否可达？
```

这比“复制一份别人规则”更可靠。
