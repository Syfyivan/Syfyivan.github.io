MQ 最开始吸引我的点是“解耦”。后来发现，解耦只是表面，麻烦的是可靠性：消息会不会丢，会不会重复，会不会乱序，消费失败怎么补。

所以学 MQ，不是学会 `producer.Send()` 就结束了。

## 什么时候值得异步

适合丢到 MQ 里的，通常是这些：

- 发通知；
- 写审计日志；
- 更新搜索索引；
- 同步数据到别的系统；
- 做统计；
- 触发后续非核心流程。

不适合随便异步的，是主链路里必须立刻给用户结果的事。比如订单有没有创建成功、支付状态是不是已经确认，这些不能只靠“消息后面会处理”糊过去。

## 至少一次投递意味着会重复

业务系统里很常见的是“至少一次”。意思是系统尽量不丢消息，但可能重复投。

所以消费者要幂等。可以用：

- message id；
- 业务唯一键；
- 消费记录表；
- 数据库唯一约束；
- 状态机判断。

比如通知消息重复来了两次，不能真的给用户发两条一样的短信。支付成功消息重复来了，也不能重复发权益。

## 重试要有出口

消费失败后可以重试，但不能无限快速重试。否则下游本来就慢，你还一直补刀。

我会给消费失败准备这几样东西：

- 重试次数；
- 退避时间；
- 最后进入死信；
- 失败原因能查；
- 有人工补偿或脚本补偿入口。

死信队列不是“垃圾桶”，它更像待处理工单。每一条死信都应该能解释为什么没处理掉。

## 顺序只在需要的地方做

全局顺序很贵，也很少真的需要。更多时候需要的是同一个业务对象内部有顺序。

比如同一个订单：

```text
created -> paid -> shipped
```

可以把同一个 order_id 路由到同一个 partition。代价是这个 key 上的并行度会下降，所以别一上来就要求所有消息都严格有序。

## Outbox 很值得练

一个经典坑：数据库写成功了，消息发送失败了。

比较稳的做法是 outbox：

```text
事务里：
  写业务表
  写 outbox_events

后台 worker：
  扫未发送事件
  发 MQ
  标记已发送
```

这样至少能保证“业务变化”对应一条可重试的事件。它不华丽，但很实用。

## 一个练习

把“创建任务后发通知”改成异步：

- 创建任务时写 task；
- 同事务写 outbox event；
- worker 发送 `TaskCreated`；
- notification consumer 消费；
- 用 task_id 或 message_id 去重；
- 失败后重试，超过次数进死信。

然后故意让消费者失败、让 MQ 暂时不可用、让同一条消息重复投。能把这些情况处理完，才算这篇真的学完。
