消息队列的价值不是“把消息发出去”，而是把系统从同步调用改造成可缓冲、可重试、可解耦的异步链路。它常用来处理通知、日志、积分、库存、搜索索引、数据同步等不必阻塞主请求的工作。

但 MQ 也会把问题换一种形态：同步失败变成异步失败，直接返回错误变成消息堆积，函数调用一次变成至少一次投递。学 MQ 的重点是可靠性，而不是会调用 SDK。

## MQ 在链路里的位置

典型链路：

```text
API
  -> Service 写数据库
  -> 发送消息
  -> Consumer 异步处理
  -> 下游服务或数据库
```

比如创建任务后发送通知：

- 主接口只负责创建任务；
- 通知通过消息异步发送；
- 消费失败可以重试；
- 通知服务故障不会阻塞任务创建。

这就是异步解耦。

## 必须掌握的知识点

### 基本模型

无论是 Kafka、RocketMQ、RabbitMQ，核心概念都类似：

- producer：生产消息；
- broker：存储和转发消息；
- topic：消息主题；
- partition/queue：并行和顺序的基本单位；
- consumer：消费消息；
- consumer group：同一组内分摊消费；
- offset：消费进度。

理解这些概念后，再看不同 MQ 的实现差异会容易很多。

### 投递语义

常见语义有三种：

- 至多一次：可能丢，但不重复；
- 至少一次：不轻易丢，但可能重复；
- 恰好一次：语义复杂，通常依赖具体系统能力和业务配合。

业务系统里最常见的是至少一次。所以消费者必须幂等。不要假设一条消息只会被消费一次。

幂等方式包括：

- 消息唯一 ID；
- 业务唯一键；
- 消费记录表；
- 数据库唯一约束；
- 状态机判断。

### 重试和死信

消费失败不能无限快速重试，否则会造成下游雪崩。需要：

- 重试次数限制；
- 退避策略；
- 死信队列；
- 人工补偿入口；
- 失败原因记录。

死信队列不是垃圾桶，而是“需要人工或补偿流程介入”的消息集合。

### 顺序消息

顺序消息不是全局顺序，而通常是局部顺序。比如同一个订单的事件要按顺序处理：

```text
OrderCreated -> OrderPaid -> OrderShipped
```

做法是把同一个订单 ID 路由到同一个 partition/queue。代价是并行度下降，热点订单可能拖慢同一分区。

所以只有真正需要顺序的业务才做顺序，不要默认所有消息都要严格排序。

### Outbox Pattern

最经典的问题是：数据库写成功了，但消息发送失败怎么办？

如果直接在事务外发消息，会出现：

- 业务数据已提交；
- 消息没发出去；
- 下游永远不知道这次变化。

Outbox 的思路是：在同一个数据库事务里写业务数据和 outbox 记录，然后由后台 worker 扫描 outbox 表发送消息，发送成功后标记已发送。

```text
transaction:
  insert task
  insert outbox_event

worker:
  read unsent events
  publish to MQ
  mark sent
```

这样至少能保证“业务变更一定有一条待发送事件”。

## 练习方式

把任务创建后的通知改成异步：

- 创建任务时写 task 表；
- 同事务写 outbox_event 表；
- 后台 worker 扫描 outbox；
- 发送 `TaskCreated` 消息；
- notification consumer 消费消息并发送通知；
- 用 message id 或 task id 做幂等；
- 消费失败进入重试，超过次数进入死信。

然后主动制造故障：

- MQ 暂时不可用；
- 消费者处理超时；
- 同一消息重复投递；
- 下游通知服务失败；
- 消息堆积。

能处理这些情况，才算真正理解 MQ。
