> 承上：上一章阿筹把对抗验证的规矩立全了。这一章，老把头把账本拍在他面前：这么多人、这么多道核对，值不值，得算。

阿筹的队越拉越大,核对越加越多,他正得意“稳了”，老把头指着账本:“你看，人头翻了三倍，工钱也翻了三倍；活儿是分头干了，可光是各组之间对接、传话、等齐，又搭进去不少功夫。上回有一组中途出岔，整件活返工重来，那一趟的料钱全打了水漂。”

“分头干能快，这没错，”老把头说，“可不是人越多越划算。多一个人多一份嚼用，多一道交接多一处可能出错。你得算清楚:这一趟，分工省下的工期，抵不抵得上多花的工钱和多担的乱子。”

## 概念揭晓

老把头这本账，是多 Agent 绕不开的**成本与延迟**——它把前面几讲反复出现的“算账”意识，抬到了系统层面。

“人头翻倍、工钱翻倍”，是**token 与调用成本**：每多一个 Agent、每多一道评审/验证，都是额外的模型调用和 token 消耗。多 Agent 常常比单 Agent 贵好几倍。

“分头干能快”，是**并行收益**：相互独立的子任务并行跑，能显著缩短总时长——这是多 Agent 提速的主要来源。

“对接、传话、等齐搭进去的功夫”，是**协调开销**：Agent 之间的交接、汇总、互相等待，本身要花时间和 token，人越多越明显。

“一组出岔、整件返工”，是**失败与重跑成本**：环节越多，出错概率越高；一处失败可能拖累全局，重跑很贵。

## 多 Agent 为什么常常更贵

一个直觉但重要的事实:多 Agent 通常比单 Agent **贵得多**。Anthropic 的多 Agent 研究就提到，多 Agent 系统消耗的 token 可达单次对话的十几倍。原因：

- 每个 Agent 各有自己的提示词、上下文、来回调用。
- 评审、验证、共识（11.4）都是额外的调用。
- 协调者要理解、拆解、汇总，自身也很费。

所以“拆成多 Agent”不是免费的高级感，而是用更高的成本换更高的质量或更短的时延。这笔交换值不值，要具体算。

## 并行收益从哪来、到哪为止

并行是多 Agent 提速的核心，但它有上限：

- 只有**相互独立**的子任务才能真正并行；有依赖的（A 的输出是 B 的输入）只能串行。
- 并行的总时长≈最慢的那条链，不是所有任务之和——所以一个特别慢的子任务会拖住全局。
- 拆得越碎，协调开销越大，可能把并行省下的时间又吃回去。

理想情况是“少数几个粗粒度、相对独立的子任务并行”，而不是“拆成上百个小块互相等待”。

## 协调开销:人越多越明显

多 Agent 的隐藏成本，大半在协调:

- 交接、汇总要花 token 和时间。
- 等待最慢的 Agent（同步点）会拖慢整体。
- Agent 越多，出错和不一致的概率越高，处理这些又要花成本。

这正是“三个和尚没水喝”的工程版:协调成本会随 Agent 数量超线性增长。所以要克制拆分，别为分工而分工（呼应 11.1）。

## 怎么把账算划算

- **先问值不值**:单 Agent + 好提示能不能解决？能就别上多 Agent（11.1）。
- **粗粒度拆分**:少数几个独立子任务，而非过度细分。
- **按价值配验证**:高风险产出才上多重对抗验证（11.4），低风险的别过度核对。
- **设预算和上限**:给整个流程设 token / 时间预算和重试上限，防止失控烧钱（呼应第八讲 08.6 的预算告警）。
- **盯端到端指标**:像第八讲 08.3 那样，把完成率和成本/延迟放一起看，而不是只看“做得多周全”。

## 常见误区

第一，以为多 Agent“分头干”一定更快——有依赖时并不能并行，协调还会拖后腿。

第二，无视成本，层层叠加评审/验证/共识，把账烧爆。

第三，不设预算和重试上限，一处反复失败重跑，悄悄烧掉大笔 token。

## 小练习

一个多 Agent 流程:1 个协调者 + 5 个并行检索 + 1 个写作 + 2 个验证。

1. 哪些环节能真正并行，哪些必须串行？
2. 这套大概比“单 Agent 做同样的事”贵几倍？贵在哪？
3. 如果要砍成本，你会先砍哪一环？怎么不太掉质量地砍？
