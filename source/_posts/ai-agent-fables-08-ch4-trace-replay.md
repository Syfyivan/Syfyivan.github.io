> 承上：上一章阿评想看清选手办事的全过程，却发现凭记忆复盘太难。这一章，老裁判带他去看角落里那套录像设备。

考核场每个角落都架着录像。老裁判带阿评进了回放间。

“一场考核，我们不只记个结果，”老裁判调出一场，“每一步都分段记下来：他这一步干了什么、用了多久、成没成。他每次去借工具、工具回了什么，也都记着。要是几个选手合伙办一件事，谁把活儿交给谁、在哪一步交的，一清二楚。”

“最有用的是，”老裁判把录像倒回某一帧，“出了岔子，我能精确回到那一步重看，不用猜。看多了，我把大家常栽的跟头归了类——‘忘了上一步结论的’‘工具用错的’‘绕圈出不来的’——攒成一本图鉴。下回一看苗头，就知道是哪一类。”

## 概念揭晓

老裁判这套录像，就是 AI 系统的**可观测性（observability）**核心——**trace（追踪）与回放**。

“每一步分段记下来”，是 **span**：一次 trace 由许多 span 组成，每个 span 记录一个步骤（一次模型调用、一次工具调用、一段处理）的输入、输出、耗时和状态。

“每次借工具、工具回了什么”，是 **tool call 记录**：把 Agent 的每次工具调用及其结果完整留痕。

“谁把活儿交给谁”，是 **handoff**：多 Agent 协作时，任务在 Agent 之间的交接记录（第十一讲会展开）。

“精确回到那一步重看”，是 **replay（回放）**：能重现一次执行的完整过程，用于复盘和调试。

“把常栽的跟头归类成图鉴”，是**失败归类（failure taxonomy）**：把失败模式整理成有限的类别，便于识别、统计和针对性改进。

## 为什么 Agent 必须可观测

Agent 是多步、带工具、有随机性的系统。当它出错时，光看最终结果，你根本不知道是哪一步、为什么坏的——是检索漏了？工具调错了？上下文丢了？还是模型判断偏了？

没有 trace，排查 Agent 故障就像隔着布袋打老鼠。有了 trace，每一步都留痕、可回放，问题定位从“猜”变成“查”。可观测性不是锦上添花，而是让 Agent 可被调试、可被改进的前提——这也是第六讲 Harness 的重要一环。

## 一条 trace 里有什么

一条完整 trace 通常包含：

- **每个 span**：步骤类型、输入、输出、耗时、成功/失败。
- **模型调用**：提示词、返回、token 用量。
- **工具调用**：调了哪个工具、参数、结果、错误。
- **决策点**：它为什么选这一步（如果能记录推理）。
- **交接（handoff）**：多 Agent 时谁接了谁。

举个具体例子，一次“查订单”的 trace 摊开大概长这样：span 1 是模型调用，把用户问句解析成意图，耗时 0.4s；span 2 是工具调用 `query_order(id="A 123")`，耗时 0.1s，结果为空；span 3 又是模型调用，它读到空结果，回了句“查不到该订单”。把这三段一串，你立刻看出问题在 span 2——订单号里多了个空格，工具其实没查对，根本不是“订单不存在”。**单看最后那句结论你只会怪模型；看 span 才知道错在参数。** 这就是为什么要按步骤分段记录，而不是只存一个总输入总输出。

## 回放：把“为什么错”变成可查

回放让你能回到任意一步重看，甚至改一个条件重跑，看结果会不会不同。它的价值：

- **定位**：精确找到出错的那一步。
- **复盘**：理解失败的因果链，而不是只看症状。
- **验证修复**：改完之后，拿同样的输入回放，确认真的修好了（接回归集）。

这把 08.1 的“回归”和 08.3 的“轨迹评测”落到了可操作的工具上：有了 trace 和回放，过程才真正可评、可调、可守。

## 失败归类：从救火到改进

零散地修单个 bug，永远在救火。把失败归类，才能系统改进：

- 统计哪类失败最多（如“上下文丢失”占 40%），优先治大头。
- 给每类失败配套针对性的检测和对策。
- 把每一类做成评测项，进回归集，防止复发。

失败图鉴让团队从“又出了个怪问题”进化到“这是第 3 类失败，我们有标准处置”。这是质量从手忙脚乱走向工程化的标志。

## 常见误区

第一，只存最终结果，不存过程。出了错无从查起。

第二，有 trace 却从不回放、不归类——日志堆成山，洞察是零。

第三，把每次失败当孤立事件救火，不沉淀成类别和回归项，于是反复踩同一个坑。

## 小练习

你的 Agent 这次没能完成任务。手里有完整 trace：

1. 你会先看哪几个 span 来定位问题？
2. 假设发现是“某次工具调用返回了错误、它却没处理”，这属于哪一类失败？
3. 修完之后，你会把什么加进回归集，防止它复发？
