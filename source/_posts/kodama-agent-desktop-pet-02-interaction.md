上一篇讲了 Kodama 的事件入口：飞书 bridge 通过 SSE 推事件，本地 Codex/Claude Code 通过 hook 推事件，renderer 统一展示。

这一篇讲真正花时间的地方：桌宠 UI。

我一开始以为桌宠 UI 的核心是“能显示”：宠物图案、状态气泡、事件面板。实际开发下来，最难的是“不打扰”：

- 宠物不能太大。
- 透明窗口不能挡住其他 App。
- 鼠标不能离宠物很远也被命中。
- 气泡不能盖住宠物。
- 气泡不能跑出屏幕。
- 面板不能遮住输入框。
- 配置入口必须容易找到。
- 左键、右键、拖动、点击气泡都不能互相冲突。

桌宠不是网页里的一个组件。它浮在整个系统桌面上，所以每一个像素、每一次命中都会影响用户正在做的事情。

## 第 1 个问题：宠物太大

最早的版本按窗口高度铺满模型。效果就是宠物很可爱，但完全不可用：它会挡住飞书、浏览器、编辑器，尤其在右下角时占用太多可点击区域。

后来加了两层控制：

1. Electron 窗口大小：很小、小、中、大。
2. 模型内部缩放：`petScale`。

窗口大小决定桌宠最多占多少屏幕空间；模型缩放决定图案在窗口里多大。

```js
const DEFAULT_UI_SETTINGS = {
  petScale: 0.72,
  petOpacity: 0.82,
  hitboxScale: 0.35,
  triggerMode: 'right',
};
```

这里有一个细节：不能只缩放图案，不缩小窗口。因为 Electron 的透明窗口虽然看不见，但仍然可能参与鼠标命中。窗口太大时，即使图案看起来小，用户也会感觉“鼠标还没碰到宠物，它就被点到了”。

所以窗口尺寸和 hitbox 必须一起控制。

## 第 2 个问题：透明不等于不存在

Electron 透明窗口最容易让人误会的一点是：透明区域在视觉上不存在，但在鼠标系统里仍然可能存在。

Kodama 的策略是默认 click-through：

```js
win.setIgnoreMouseEvents(true, { forward: true });
```

也就是默认不吃鼠标，让鼠标穿透到下面的飞书、浏览器或编辑器。只有当鼠标进入“可交互区域”时，renderer 才通知 main process：

```js
window.pet.setIgnoreMouse(false);
```

鼠标离开后再恢复：

```js
window.pet.setIgnoreMouse(true, { forward: true });
```

`forward: true` 很关键。没有它，窗口忽略鼠标后就收不到 mousemove，也就不知道鼠标什么时候又回到了宠物身上。

这类桌面悬浮 UI 的核心不是“做透明”，而是“透明时仍能保持最小必要感知”。

## 第 3 个问题：可点击区域不能等于模型 bounds

Live2D 或 GIF 模型的 bounds 往往比可见主体大。比如图案周围有透明边距，或者模型资源本身留了安全区。

如果直接用 `model.getBounds()` 判断鼠标是否在宠物上，命中区域会非常大。用户鼠标距离图案还有一段距离，也会触发桌宠。

所以 Kodama 又做了一层 interactive bounds：

```js
function interactivePetBounds() {
  const b = petBounds();
  const width = b.width * uiSettings.hitboxScale;
  const height = b.height * uiSettings.hitboxScale;
  const centerX = b.x + b.width / 2;
  const centerY = b.y + b.height * 0.66;

  return {
    x: centerX - width / 2,
    y: centerY - height / 2,
    width,
    height,
  };
}
```

这里 `hitboxScale` 默认只有 0.35。也就是说，真实可点区域是视觉模型 bounds 的一小块，主要集中在宠物主体上，而不是透明外框。

后来用户希望“左键可以穿透，只用右键触发”。于是加了 `triggerMode`：

- 右键模式：左键尽量不影响正常工作，右键打开配置。
- 左键模式：左键可拖动/触发。
- Alt/Command + 左键：作为显式拖动兜底。

这一步学到的点是：

> 桌宠的命中区域应该服务于“我想操作它”这件事，而不是服务于图片资源的几何边界。

## 第 4 个问题：怎么移动桌宠

桌宠不能固定在一个位置。用户会把它拖到角落、边缘、飞书窗口旁边，甚至希望它可以半露在屏幕边上。

最早的拖动是窗口级别的：

```js
window.pet.move(e.screenX - lastX, e.screenY - lastY, petBounds());
```

main process 里再更新 BrowserWindow 的 position。

后来遇到一个问题：如果按窗口边界 clamp，宠物永远不能贴到角落，因为透明窗口比可见宠物大。用户看到的是“明明还能往右放，为什么不让我拖了？”

解决方法是用“可见宠物 bounds”参与 clamp，而不是用窗口 bounds。也就是说，允许透明窗口出屏幕，只要可见宠物主体仍然留在屏幕里。

```text
窗口可以部分出屏幕
但 visible pet bounds 不能完全离开 workArea
```

这是桌宠类 UI 和普通窗口最大的差异之一：普通窗口要保证窗口完整可见，桌宠只需要保证可交互主体可找回。

## 第 5 个问题：气泡离宠物太远

最早气泡固定在窗口顶部，用户看到的是：宠物在下面，气泡在很远的上面。视觉上像两个无关元素。

于是加了 `bubbleCorner`：

- `near`：跟随宠物附近。
- `auto`：自动选远离宠物的角落。
- `top-left/top-right/bottom-left/bottom-right`：固定角落。

同时加了 `bubbleGap`，让用户能控制气泡和宠物之间的距离。

但“贴近宠物”不能简单写成：

```text
top = pet.y - bubble.height - gap
```

因为会遇到很多边界：

- 宠物在屏幕顶部，上方放不下。
- 宠物在屏幕底部，下方放不下。
- 气泡有多条，高度超过上下空间。
- 宠物在角落，气泡应该自动往屏幕内侧翻。

所以后面变成了区域选择。

## 第 6 个问题：气泡不能盖住宠物

这是一次很典型的 UI bug：气泡栈高了以后，旧逻辑只是把气泡 clamp 回屏幕可见区域。结果气泡确实没出屏幕，但它被硬塞到了宠物身上。

旧逻辑大概是：

```text
先算 aboveTop
如果放不下，就 clamp 到屏幕内部
```

问题是 clamp 只保证“在屏幕里”，不保证“不和宠物相交”。

后来改成四个候选区域：

```text
above：宠物上方
below：宠物下方
right：宠物右侧
left：宠物左侧
```

每个区域都有自己的宽高、可用空间和偏好位置。算法会优先选择能完整放下气泡的区域；如果完整放不下，就选择可用高度最大的区域，并给气泡栈设置 `max-height`，让它内部滚动。

核心变化是：

```text
不要先定位再 clamp
而是先选择不会和宠物相交的区域
```

这也是很多浮层定位问题的通用经验。tooltip、popover、context menu 都一样：真正的约束不是“不能出屏幕”这一条，而是多个矩形之间的关系。

## 第 7 个问题：配置面板不能藏起来

桌宠的配置一开始藏在右键菜单里，结果用户找不到。

后来加了事件 / 配置面板，并把它放进 tray menu 和右键入口：

- 右键宠物或气泡：打开面板。
- 菜单栏 Kodama：打开“事件 / 配置面板”。
- 面板顶部可拖动，用来移动桌宠。

面板里放了这些设置：

- 图案大小。
- 透明度。
- 点击范围。
- 左键/右键触发。
- 气泡位置。
- 面板位置。
- 气泡间距。
- 窗口大小。

这些设置不是“锦上添花”。对于桌宠来说，它们是可用性的基础。不同屏幕尺寸、不同 App 布局、不同用户对误触的容忍度都不一样。

尤其是透明度和触发方式组合起来以后，可以得到一种很舒服的模式：

```text
宠物半透明
左键穿透
只有右键才打开配置 / 交互
```

这样它更像一个环境提示，而不是挡在桌面上的 App。

## 第 8 个问题：悬浮摘要不能变成第二张大卡片

气泡上又加了 hover 摘要。目的不是重复气泡正文，而是让用户知道“这个会话到底在干什么”。

第一次实现时摘要太贪心：标题、cwd、最近三轮、更新时间、跳转目标都展示。结果高度太高，反而挡住原气泡和页面。

后来收敛成：

- 标题：取最近用户请求或 session 标题。
- 内容：只展示最近两条 user/assistant 摘要。
- 不展示完整路径。
- 不展示更新时间。
- 不展示跳转目标。
- 位置锚定在原气泡下方居中，而不是跟着鼠标点跑。

这里的经验是：

> hover 不是详情页。hover 只回答一个问题：这个东西大概是什么？

如果用户想深入，就点击气泡打开会话，或者点分享生成网页快照。

## 第 9 个问题：面板和气泡也要分层

桌宠里至少有四层：

```text
pet canvas / gif       z-index: 1
accessory layer        z-index: 4
bubble                 z-index: 10
event panel            z-index: 30
hover tip              z-index: 45
```

层级太低，气泡会被宠物盖住；层级太高，hover 又会挡住配置面板。每个元素都要知道自己是什么：

- 宠物主体是背景角色。
- 气泡是提醒。
- 面板是主动操作界面。
- hover 是临时解释。

这也是为什么不能把所有东西都做成一个大浮层。桌宠 UI 的信息层级必须清楚，否则用户会觉得“哪里都能点，哪里都挡”。

## 小结：桌宠 UI 的核心不是可爱，是克制

这一阶段的主要修正包括：

1. 默认缩小宠物，并让大小可配置。
2. 默认 click-through，只在真实 hitbox 内接管鼠标。
3. hitbox 独立于模型 bounds，避免透明边距误触。
4. 拖动按可见主体 clamp，而不是按透明窗口 clamp。
5. 气泡从固定位置改成 near/auto/corner。
6. 气泡定位按可用区域选择，避免覆盖宠物。
7. 常驻气泡加忽略按钮，事件面板加 tabs。
8. hover 摘要改成短提示，不做详情页。

这套 UI 最终不是最炫的，但它开始接近一个真实可用的桌面伴随工具。
