服务端学习最后一定要落到项目。只看知识点会觉得都懂，一做系统才会发现：事务边界在哪里，缓存什么时候失效，消息为什么重复，RPC 超时怎么设，日志怎么串，发布怎么回滚。

推荐做一个“用户、商品、库存、订单、支付、通知”的小型业务系统。它规模可控，但覆盖了服务端最核心的问题。

## 为什么选这个项目

这个系统天然包含：

- 用户身份和权限；
- 商品查询和缓存；
- 库存扣减和并发控制；
- 订单状态机；
- 支付回调幂等；
- MQ 异步通知；
- RPC 服务拆分；
- 数据库事务；
- 可观测性；
- 发布和故障降级。

它不需要复杂 UI，也不依赖特别新奇的技术，但足够训练真实后端能力。

## 第一阶段：清晰单体

先不要急着拆服务。第一版做清晰单体：

```text
handler
  -> service
  -> repository
```

功能包括：

- 用户注册登录；
- 商品列表和详情；
- 创建订单；
- 查询订单；
- 取消订单；
- 支付回调；
- 通知记录。

这一阶段重点是：

- 目录结构清晰；
- handler 不写业务规则；
- service 组织流程；
- repository 只访问数据库；
- 错误码统一；
- 基础测试齐全。

如果单体都写不清楚，拆成微服务只会更乱。

## 第二阶段：数据库和事务

设计核心表：

- users；
- products；
- inventory；
- orders；
- order_items；
- payments；
- outbox_events；
- operation_logs。

关键事务：

- 创建订单：写订单、写订单明细、冻结库存、写操作日志；
- 支付成功：更新支付状态、更新订单状态、写 outbox；
- 取消订单：释放库存、更新订单状态、写日志。

库存扣减要处理并发。可以先用数据库条件更新：

```sql
update inventory
set available = available - ?
where product_id = ? and available >= ?
```

受影响行数为 0 时，说明库存不足。

## 第三阶段：缓存

适合缓存：

- 商品详情；
- 商品列表；
- 用户基础资料；
- 库存读模型。

不适合直接依赖缓存保证正确性的：

- 真实库存扣减；
- 支付状态；
- 订单最终状态。

缓存策略：

- 商品详情使用 cache-aside；
- 商品更新后删除缓存；
- 热点商品加随机 TTL；
- 不存在商品写短 TTL 空值；
- Redis 不可用时降级查库。

缓存的目标是提升读性能，不是替代数据库正确性。

## 第四阶段：消息队列

引入 MQ，把非核心链路异步化：

- 订单创建后发通知；
- 支付成功后发权益；
- 订单状态变化后写搜索索引；
- 操作日志异步汇总；
- 数据分析事件异步上报。

使用 outbox pattern：

1. 业务事务内写订单和 outbox；
2. worker 扫描 outbox；
3. 发布消息；
4. 标记发送成功；
5. 消费者幂等处理。

重点练习重复消息、消费失败、死信队列和补偿。

## 第五阶段：微服务拆分

当单体边界清晰后，再拆成：

- user-service；
- product-service；
- order-service；
- payment-service；
- notification-service。

拆分原则：

- 每个服务拥有自己的数据；
- 服务之间通过 RPC 或事件通信；
- 不跨服务直接查库；
- 每个 RPC 都有超时；
- 读请求可以有限重试；
- 写请求依赖幂等和状态机；
- trace id 全链路传递。

order-service 是核心编排者，但不要让它变成所有业务的垃圾桶。支付、通知、商品能力应该留在自己的服务内。

## 第六阶段：可观测和生产化

补齐生产能力：

- 结构化日志；
- metrics；
- trace；
- 错误率告警；
- P95 延迟告警；
- MQ 堆积告警；
- Dockerfile；
- docker compose；
- 健康检查；
- 优雅退出；
- 灰度发布和回滚演练。

然后做故障演练：

- Redis 挂掉；
- 数据库慢查询；
- payment-service 超时；
- MQ 消费失败；
- notification-service 不可用。

每次演练都写复盘：用户影响、发现方式、根因、恢复手段、后续改进。

## 完成标准

项目完成不是代码写完，而是你能从一个订单请求开始讲清楚：

- 请求进入哪个接口；
- 经过哪些 service；
- 写了哪些表；
- 哪些操作在事务里；
- 哪些数据进缓存；
- 发了哪些消息；
- 下游失败如何处理；
- 重复请求如何幂等；
- 日志和 trace 怎么查；
- 指标异常时如何告警；
- 新版本如何灰度和回滚。

能讲清楚这些，就说明服务端知识已经从零散点变成了系统能力。

## 继续扩展

完成基础版后，可以继续加：

- 秒杀库存；
- 优惠券；
- 退款；
- 多仓库存；
- 读写分离；
- 分库分表；
- 搜索服务；
- 风控服务；
- 后台运营系统。

但不要一开始就加。先把主链路做稳，再逐步增加复杂度，这才是服务端学习最踏实的节奏。
