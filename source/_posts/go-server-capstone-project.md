前面每一篇都是拆开学。最后还是得做一个项目，把这些东西重新拧在一起。

我会选一个小型订单系统：用户、商品、库存、订单、支付、通知。它不新鲜，但够实用。数据库事务、缓存、MQ、幂等、RPC、状态机、观测、部署，都会自然冒出来。

## 第一版先做单体

先别急着微服务。第一版只做一个清晰单体：

```text
handler -> service -> repository/client
```

功能不用太多：

- 用户注册登录；
- 商品列表和详情；
- 创建订单；
- 查询订单；
- 取消订单；
- 支付回调；
- 通知记录。

这一版重点是边界。handler 不写业务，service 管流程，repository 管数据访问。能把单体写清楚，后面拆服务才有依据。

## 数据库先把事实存对

可以先有这些表：

- users；
- products；
- inventory；
- orders；
- order_items；
- payments；
- outbox_events；
- operation_logs。

创建订单时，至少要在一个事务里写订单、订单明细、冻结库存、操作日志。库存扣减可以先用条件更新：

```sql
update inventory
set available = available - ?
where product_id = ? and available >= ?
```

影响行数为 0，就是库存不足。别在代码里先查库存再扣，那样并发下很容易出问题。

## 缓存只放读模型

适合缓存：

- 商品详情；
- 商品列表；
- 用户基础资料；
- 库存展示值。

不适合只靠缓存保证正确性：

- 真实库存；
- 支付状态；
- 订单最终状态。

缓存负责快，数据库负责准。这个边界别混。

## MQ 处理旁路事情

订单创建后，可以异步做：

- 发通知；
- 写审计；
- 同步搜索索引；
- 发数据分析事件；
- 触发后续履约流程。

这里用 outbox 会比较稳：业务事务里写 outbox，后台 worker 负责发消息。消费者按 message id 或业务 id 做幂等。

## 后面再拆服务

单体边界清楚以后，可以拆成：

- user-service；
- product-service；
- order-service；
- payment-service；
- notification-service。

拆完要补的不是“更多仓库”，而是：

- RPC 超时；
- 有限重试；
- trace 透传；
- 服务降级；
- 消息幂等；
- 每个服务拥有自己的数据。

如果这些没补，微服务只是把简单问题变成分布式问题。

## 最后补生产化

项目做到这里，还差最后一层：

- 结构化日志；
- metrics；
- trace；
- 错误率告警；
- P95 告警；
- MQ 堆积告警；
- Dockerfile；
- docker compose；
- 健康检查；
- 优雅退出。

然后故意造故障：Redis 挂、数据库慢、payment-service 超时、MQ 堆积。每次写一段复盘：影响是什么，怎么发现，怎么恢复，下次怎么避免。

## 做到什么程度算够

能从“创建订单”这个请求开始，讲清楚：

- 进哪个接口；
- 调哪些 service；
- 写哪些表；
- 哪些操作在事务里；
- 哪些数据进缓存；
- 发哪些消息；
- 重复请求怎么处理；
- 下游超时怎么办；
- 日志和 trace 怎么查；
- 怎么灰度，怎么回滚。

能讲到这个程度，这个项目就不是玩具了。它不一定大，但已经把服务端最常见的坑走了一遍。
