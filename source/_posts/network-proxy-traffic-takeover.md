代理客户端想处理请求，第一步不是“选节点”，而是先看见流量。

看不见流量，规则再复杂也没用。不同代理模式的本质区别，就是它站在网络路径的哪个位置接管流量。

## 系统代理：应用主动把请求交给你

系统代理是最容易理解的模式：

```text
应用
  -> 操作系统代理设置
  -> 127.0.0.1:本地代理端口
  -> 代理客户端
  -> 直连或转发
```

浏览器、很多桌面应用、命令行工具可以读取系统代理设置，然后把 HTTP、HTTPS 或 SOCKS 请求交给本地代理端口。

它的优点很明确：

- 轻量；
- 容易开关；
- 日志清楚；
- 对路由表影响小；
- 出问题时比较容易还原。

缺点也明确：它依赖应用配合。

有些应用不读系统代理，有些只读环境变量，有些自己实现 DNS 和连接逻辑，还有些只让 HTTP 走代理但 UDP 不走。系统代理模式下，这些流量可能绕过代理客户端。

所以“我开了系统代理，但这个 App 还是直连”，并不矛盾。系统代理不是系统强制网关，它更像一份应用可以遵守的约定。

## 本地端口：HTTP、SOCKS 和 mixed-port

很多客户端会启动本地端口：

```text
HTTP proxy:  127.0.0.1:7890
SOCKS proxy: 127.0.0.1:7891
Mixed port:  127.0.0.1:7892
```

HTTP 代理理解 HTTP 请求，也可以通过 CONNECT 建立隧道。

SOCKS 更低一层，常见 SOCKS5 可以表达目标地址、端口和认证信息，但它不理解 HTTP 语义。

mixed-port 是一些工具提供的便利入口：同一个端口同时接受 HTTP 和 SOCKS 请求。它让用户少记端口，但不改变底层协议差异。

排障时要确认应用实际连的是哪个端口。很多“代理没生效”只是应用填了旧端口，或者 HTTP/SOCKS 类型选错了。

## TUN：让操作系统把 IP 包送进来

TUN 模式会创建一个虚拟网络接口。你可以把它想成一张虚拟网卡：

```text
应用
  -> 操作系统路由表
  -> TUN 虚拟网卡
  -> 代理客户端用户态网络栈
  -> 规则判断
  -> 直连或转发
```

和系统代理相比，TUN 不依赖应用主动支持代理。只要路由把流量导进虚拟网卡，代理客户端就能看到更多流量。

这也是它的复杂来源：

- 需要系统权限；
- 需要正确设置路由；
- 要避免代理自己产生的连接再次回到 TUN，形成回环；
- DNS 要和 TUN 配合；
- UDP、IPv6、局域网、Docker、虚拟机都会影响路径；
- 日志里看到的可能先是 IP 包，而不是可读的 HTTP 请求。

TUN 适合“应用不支持系统代理，但我仍然想接管它”的场景。它不是更简单，而是覆盖面更大。

## Apple 平台里的虚拟网卡

iOS 和 macOS 上，很多网络工具依赖 Apple 的 Network Extension。`NEPacketTunnelProvider` 这类能力给应用扩展一个虚拟网络接口，应用扩展可以从 packet flow 里读取和写入 IP 包。

这解释了两个现象。

第一，iOS 上代理工具经常表现得像 VPN。不是它一定在做传统企业 VPN，而是系统把这类全局网络接管能力放在 VPN/Network Extension 模型里管理。

第二，后台运行、权限、配置安装、证书信任、系统弹窗都会影响体验。它不是普通桌面进程随便监听一个端口那么简单。

## 透明代理：设备不知道自己被接管了

透明代理通常发生在 Linux、OpenWrt、软路由或网关上：

```text
手机 / 电脑
  -> 家庭路由器
  -> 防火墙规则 / 策略路由 / TProxy
  -> 代理内核
  -> 直连或转发
```

客户端设备不需要配置代理，甚至不知道代理存在。网关通过防火墙规则或策略路由把流量导入代理程序。

这很适合统一管理一整个局域网，但排障成本也最高：

- 问题可能在客户端 DNS；
- 可能在网关 NAT；
- 可能在防火墙规则；
- 可能在策略路由；
- 可能在代理规则；
- 可能在上游出口；
- 还可能在某台设备的 IPv6 路径。

透明代理的心智模型不是“某个 App 开了代理”，而是“整个网络出口被改写了”。

## 三种模式怎么选

先看需求，不要先看功能表。

如果只是浏览器、终端和少数开发工具需要代理，系统代理或本地端口通常够用。

如果很多应用不支持代理，或者你要接管 UDP、游戏、桌面软件，TUN 更合适。

如果你要让一整个局域网共用策略，透明代理或路由器方案更合适。

如果你只是调试 HTTP API，系统代理加 MITM 往往比 TUN 更清楚。

## 常见误区

第一个误区：TUN 一定比系统代理高级。

不对。TUN 只是接管层更靠下，覆盖面更大。它带来的复杂度也更高。能用系统代理解决的问题，不一定要上 TUN。

第二个误区：开了全局代理就所有流量都代理了。

要看入口模式。系统代理下，不遵守系统代理的应用仍然可能直连。TUN 下，也要看路由和排除规则。

第三个误区：DNS 是另一个独立开关。

DNS 和入口接管必须配合。fake-ip、域名规则、节点域名解析都依赖 DNS 路径正确。

第四个误区：日志里没有请求就说明目标站点没访问。

更可能是流量没有进入当前代理入口。先确认入口，再看规则和出口。

## 排障时的第一张图

遇到问题先画这张图：

```text
应用
  -> 是否读系统代理？
  -> 是否连到本地端口？
  -> 是否被 TUN 路由接管？
  -> DNS 是否走代理客户端？
  -> 代理日志是否出现连接？
```

如果日志里没有连接，不要先改规则。先证明流量进来了。
