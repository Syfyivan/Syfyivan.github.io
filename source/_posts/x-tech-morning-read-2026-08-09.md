## AI 观察

### 1. 长任务的核心指标，是“回来以后还在不在同一条轨道上”

今天群里最值得留下的不是某个模型名，而是一个很具体的工作痛点：任务运行两三个小时，用户离开一段时间再回来，发现 agent 已经有很多地方没有遵循原指令。

这和一次回答是否漂亮是两种能力。长任务需要持续保持目标、约束、已做决策和待验证事项；它还要在上下文压缩、工具失败、子任务切换和中间产物更新后，继续知道哪些规则不能被“合理地”改写。OpenAI 对 GPT-5.6 的公开说明也把重点放在工具编排、长时工作流、程序化工具调用和多 agent 协作上，但厂商评测或产品宣称不能替代对自己仓库的回归测试。

因此，“指令遵循度”不应只在任务结束时凭感觉打分。更有用的做法是把硬约束、软偏好、当前阶段、已确认事实和待决策项分别记录，并在每个阶段切换时做一次短的状态回顾。

### 2. 重置按钮既是运营动作，也是基础设施的可观测性问题

群内关于额度重置的讨论，和 X 上 `@thsottiaux` 的相关帖子形成了同一条观察线：用户把“额度恢复”当成可以继续工作的基础设施事件，而不只是一个福利通知。X 截图显示一条帖子宣称已为付费的 ChatGPT Work 与 Codex 用户重置额度；同一线程里有人把这种周期性动作称为“performative reset”。第三方归档保存了这些文字并提供原帖链接，但其状态页同时显示“今天未检测到重置”以及更早的最后一次重置记录，这意味着“帖子存在”“平台执行”“某个账号实际看到额度恢复”不能合并为一个事实。

这和 Codex 开源仓库中的 [额度可见性 Issue](https://github.com/openai/codex/issues/33690) 是同一个工程问题的不同侧面：用户真正需要知道的不是“有没有一个 reset 按钮”，而是本次运行消耗了哪个产品、模型或任务的多少额度，什么时候恢复，是否和 Agent 共用池，以及长任务在即将耗尽时能否提前提醒。没有这些字段，用户会把服务端计费、产品运营和客户端显示混成“今天又重置了/又没重置”。

### 3. 图片摘要里的“官方确认”，必须回到原文和适用条件

群里还出现了两张风格统一的图片，分别把国行 Mac 的 Apple 智能与“阿里千问”或“豆包”联系起来，并写出 macOS 版本、登录账户、地区和数据隐私等条件。它们是值得跟进的群内线索，但不是官方页面本身。

本轮核验到的 Apple 中国支持页面，仍然明确记录了 Apple 智能的设备、地区限制，并将 Mac 上的外部模型扩展写作 ChatGPT；页面还写明中国大陆购买的受支持设备当前不可用，境外购买设备在中国大陆且 Apple 账户地区为中国大陆时也不可用。它们不能证明未来不会接入本地模型，也不能证明群图一定完全错误，但至少说明“苹果官方文档已确认国行 Mac 接入豆包/千问”目前不能作为已核验事实发布。

这类冲突本身很适合成为 AI 工程观察：模型生成的图表、截图转述和官方文档都可能包含部分真信息，但只有原始页面、版本、地区、账号与开关条件同时对上，才足以指导安装或发布决策。

## 前端 / 服务端 / 客户端工程观察

### 前端：把长任务的“偏航”暴露出来，而不是只显示处理中

长任务页面至少应展示当前阶段、最后一次状态同步、最近一次工具调用、正在遵循的约束摘要、待用户确认事项和验证进度。用户回来时，第一眼应该知道 agent 是在计划、执行、等待、恢复、验证还是已经偏航，而不是看到一个持续旋转的 loading。

对于上下文较长的任务，可以增加“约束回顾”或“阶段摘要”面板：哪些指令是硬约束，哪些已经完成，哪些被 agent 建议修改但尚未获批。这样用户能在中途纠偏，不必等两小时后通过 diff 猜测 agent 何时偏离。

### 服务端：把任务、上下文、额度和外部副作用拆成不同状态

服务端不要用一个 `success` 覆盖整个长任务。至少应区分 `task_id`、`attempt_id`、`context_version`、`instruction_digest`、`tool_call_id`、`quota_bucket`、`approval_id` 和 `verification_id`。每次上下文压缩或阶段切换，都应留下可比对的摘要和版本。

额度也需要独立的账本：记录产品、模型、运行、时间窗口、已消耗量、剩余额度、重置来源和生效回执。一个“重置已宣布”的事件，不能直接写成“额度已恢复”；应分别有 `announced`、`propagating`、`applied`、`visible_to_user` 和 `reconciled` 等状态。这样才有可能解释为什么 X 上的声明、后台账本和客户端显示会暂时不一致。

### 客户端：能力入口、地区条件和数据去向要能被验证

客户端展示一个“Apple 智能扩展”或“AI 助手”入口时，不能只依赖宣传图。应把实际生效的 macOS 版本、设备购买地区、Apple 账户地区、登录主体、扩展提供方和请求/附件去向显示在设置或诊断页里。对于 Beta 功能，客户端还要给出“未生效”“部分可用”和“请求已发出但等待服务”的可区分状态。

同样的原则适用于 Codex：额度条不能只显示一个百分比；至少要告诉用户这个百分比属于哪个产品池、按什么时间窗口计算、长任务是否会继续消耗、重置是自然恢复还是人工/运营事件。客户端越是把复杂状态压成一句话，用户越容易用错误的因果关系指导下一次任务。

### 共同观察：长任务的交付物是“结果 + 证据链”

今天的三条线索其实指向同一件事：长任务要有可恢复的上下文，额度事件要有可对账的账本，客户端 AI 能力要有可验证的适用条件。一个补丁、一个“已重置”提示或一张“官方确认”的信息图，都只能算中间产物。

真正可交付的结果应该能回答：任务依据的指令版本是什么，经历了哪些阶段，调用了哪些工具，消耗了哪个额度池，哪些外部动作已经发生，最后由哪条测试或官方页面完成验证。没有这条链，agent 的“完成”只是用户暂时没有发现问题。

## 值得跟进的动作

1. 给一个真实的两小时以上 Codex 任务加四个检查点：启动、上下文压缩后、关键工具调用后、最终验证前；每次记录硬约束、已完成项、偏航风险和下一步。
2. 做一次“中途离开再回来”的回归测试，比较不同阶段的指令遵循度，并把约束摘要、任务 diff、工具日志和最终测试结果放在同一份记录里。
3. 将额度事件做成可对账状态：`announced → propagating → applied → visible_to_user → reconciled`；不要把 X 帖子、服务端变更和客户端百分比当成同一个回执。
4. 为长任务增加高消耗预警，至少显示剩余额度、预计本次任务消耗、共享额度池、恢复时间和“继续/暂停/降级模型”的选择。
5. 对群内流传的 AI 功能图做最小核验：保存原图、发布者、原文链接、页面抓取时间、适用版本和地区；任何一项缺失，都只能进入待核验队列。
6. 继续观察 [X 的 AI/Codex 检索页](https://x.com/search?q=%28Codex%20OR%20%22Claude%20Code%22%20OR%20AI%29%20since%3A2026-08-09%20until%3A2026-08-10&src=typed_query&f=live) 是否出现可稳定打开的原始帖子；在此之前，不把搜索摘要、群截图或第三方转述写成产品承诺。
