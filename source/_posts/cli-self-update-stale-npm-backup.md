最近处理了一次 CLI 自更新问题。表面上看，它只是一个命令升级失败：

```text
self update -> npm install -g -> rename -> ENOTEMPTY
```

但真正值得记录的不是“删掉一个目录就好了”，而是这类修复应该怎么收口：什么时候可以自动清理，什么时候不能清理，什么时候可以重试，怎么写回归测试，怎么向 reviewer 证明这个修复不会误删用户机器上的其他目录。

这篇文章整理这次完整链路。为了适合公开博客，我会保留可复用的工程判断和验证方法，不展开内部仓库、人员、接口和平台链接。

## 先说结论

这次问题的根因是：npm 全局安装 CLI 时，会把旧包目录 rename 到同级的临时备份目录。如果一次安装被中断，或者 npm 上一次清理不完整，就可能留下一个形如：

```text
.<package-name>-xxxxxx
```

的残留备份目录。

下一次再执行 self-update 时，npm 又想把当前包目录 rename 到同名或类似的备份目录。如果目标目录已经存在且非空，就会报：

```text
ENOTEMPTY: directory not empty, rename '<global-package-dir>' -> '<stale-backup-dir>'
```

本机临时恢复很简单：确认它确实是 npm 生成的同级残留备份目录，删掉这个残留目录，然后重新安装目标版本。

代码层面的修复不能这么粗暴。最后采用的是一个窄口径策略：

1. 只处理 npm，不处理 pnpm 或其他包管理器。
2. 只处理输出里明确包含 `ENOTEMPTY` 的失败。
3. 只从 npm 的 `rename '<src>' -> '<dst>'` 错误里提取路径。
4. 要求 `src` 的 basename 必须是当前 CLI 包目录名。
5. 要求 `src` 和 `dst` 在同一个父目录下。
6. 要求 `dst` 的 basename 必须以 `.<package-name>-` 开头。
7. 要求 `dst` 真实存在，并且是目录。
8. 删除后只重试一次 install。

这样做的核心是：自动修复可以有，但必须把可删除范围压到足够小。否则一个“帮用户恢复升级”的功能，就会变成“根据错误输出删除文件系统路径”的高风险能力。

## 第一个问题：升级命令自己失败了

一开始只是想升级 CLI，然后看看能不能顺手给 CLI 提一个 MR。结果第一步就卡住：`self update` 没有成功，错误落在 npm 的全局安装阶段。

这类问题有一个容易误判的点：看到 `SELF_UPDATE_ERROR` 时，很容易先怀疑网络、registry、权限、版本号，或者当前 CLI 代码本身。但这次关键错误不是这些，而是 npm 在做目录 rename 时失败。

抽象一下错误形态：

```text
rename '<prefix>/lib/node_modules/<scope>/<package>'
  -> '<prefix>/lib/node_modules/<scope>/.<package>-xxxxxx'

ENOTEMPTY: directory not empty
```

这说明 npm 不是下载不到包，也不是没有权限写目录，而是目标备份目录已经存在且不为空。

本机恢复分三步：

1. 确认当前 CLI 的真实执行路径和全局安装目录。
2. 在同级目录里找到残留的 `.<package>-*` 备份目录。
3. 删除这个残留目录后，重新执行全局安装。

恢复后，CLI 能升级到目标版本。这解决了“我现在机器上能不能继续用”的问题，但还没有解决“下一位用户遇到同样问题会不会继续卡住”的问题。

## 第二个问题：不能把本机手工修复直接写成自动修复

手工修复时，人可以看路径、看目录名、看上下文，然后判断这是 npm 残留。程序不行。程序如果只根据 stderr 里的路径做 `rm -rf`，风险非常高。

所以这次修复最重要的不是“删除目录”，而是“证明这个目录可以删”。

最后把判断条件收得很窄：

```text
command 必须是 npm
  -> 输出必须包含 ENOTEMPTY
  -> 必须能解析出 rename src -> dst
  -> src basename 必须等于当前包目录名
  -> src 和 dst 必须同父目录
  -> dst basename 必须以 .<package>- 开头
  -> dst 必须存在且是目录
  -> 删除成功后才重试一次
```

这背后的原则是：恢复逻辑要匹配“已知故障形状”，而不是泛化成“安装失败就清理一下再试”。

比如下面这些情况都不应该自动处理：

- registry 或网络失败；
- npm 权限不足；
- 目标路径不在同级目录；
- 目标目录名不像 npm 备份目录；
- stderr 里没有明确的 `ENOTEMPTY rename`；
- 第二次 install 仍然失败。

尤其是最后一点很关键：重试只能证明“残留备份目录导致的第一次失败”被修复了，不能证明所有 install 失败都应该吞掉。如果第二次仍失败，就应该走原来的错误路径，把真实原因暴露出来。

## 第三个问题：新 clone 里测试和 lint 先失败了

修代码之外，还遇到一个很普通但很常见的问题：在新 clone 或新 worktree 里直接跑测试、lint、build，会因为依赖没有安装而失败。

这个问题本身不复杂，但它很容易污染判断。你本来是在验证 self-update 逻辑，结果看到测试命令失败，就可能误以为代码改坏了。

处理方式也很直接：

```text
先安装依赖
再跑定向测试
再跑 lint
再跑 build
```

这次以后，我对类似仓库会默认先确认三件事：

1. 当前 worktree 是不是刚创建的；
2. `node_modules` 是否存在；
3. 测试失败是环境缺失，还是业务断言失败。

这听起来很基础，但对节省排障时间很有效。

## 回归测试怎么写

这类 bug 最怕只在真实机器上手工复现，因为真实全局安装路径很容易污染用户环境，也很难在 CI 里稳定复现。

这次测试没有真的调用 npm 去改全局目录，而是用注入的 command runner 模拟 npm 行为：

1. 创建一个临时 global root。
2. 在里面放一个假的当前包目录。
3. 再放一个假的残留备份目录。
4. 第一次 install 返回 `ENOTEMPTY rename '<src>' -> '<dst>'`。
5. 断言代码删除残留目录。
6. 第二次 install 返回成功。
7. 最后 list 查询返回新版本。

测试关注几个关键断言：

```text
install 被调用了两次
残留备份目录已经不存在
最终 installedVersion 是目标版本
命令序列符合预期
```

这里的重点不是 mock 得多像 npm，而是把这条业务链路锁住：

```text
第一次失败
  -> 识别为可信 npm 残留备份目录
  -> 删除
  -> 只重试一次
  -> 成功后继续走原来的安装验证逻辑
```

如果以后有人把判断条件放宽，或者把“只重试一次”改成循环，这条测试就应该能提醒他：你正在改变这次修复最重要的安全边界。

## 代码评审里真正关注什么

这次 MR 的代码范围很小，只动了 self-update 服务逻辑和对应测试。但 reviewer 关注的重点不是“行数少不少”，而是 blast radius。

self-update 是 CLI 自己升级自己的通道。它一旦出问题，影响的不是某个普通业务命令，而是所有用户后续升级 CLI 的能力。所以即使 diff 很小，它也属于高敏感基础设施路径。

评审里比较关键的点有几个：

- 删除路径前有没有足够多的守卫条件；
- 是否只对 npm 生效，避免误伤 pnpm 等路径；
- 是否只匹配明确的 `ENOTEMPTY rename`；
- 是否要求源路径和目标路径同级；
- 是否要求目标目录符合 npm 备份命名；
- 是否存在无限重试风险；
- 第二次失败是否仍然保留原有错误路径；
- 测试是否覆盖首次失败、清理、重试、成功的完整链路。

结论是：实现可以合并，但由于它属于升级/发版基础设施，不能走自动 approve 或自动合并队列，需要人工 review 后手工合并。

这是这次“后面又遇到的问题”：不是代码又坏了，而是变更域本身触发了更高等级的合并门槛。这个判断是合理的。越靠近安装、升级、鉴权、发布、权限和清理文件系统的代码，越不应该只按 diff 行数评估风险。

## 怎么验证

这次验证分成四层。

第一层是本机恢复验证：清掉确认过的残留备份目录后，重新安装目标版本，确认 CLI 能继续升级和执行。

第二层是定向回归测试：

```text
node --test -r ts-node/register -r tsconfig-paths/register test/services/self_update/self_update.test.ts
```

它验证 self-update 相关测试整体通过，也包括新增的“残留备份目录清理后重试一次”场景。

第三层是静态和构建验证：

```text
npx eslint src/services/self_update/self_update.ts
npm run build
git diff --check
```

这里分别覆盖风格/静态问题、项目构建、空白字符和补丁格式问题。

第四层是 MR 侧验证：MR 包含 2 个变更文件、2 个提交，检查项全部通过，没有失败 check。reviewer 给出的结论是逻辑合理、测试充分，但由于 self-update 属于基础设施路径，需要人工合并。

## 后续调研里的几个工具链坑

这次 self-update 修复之后，还继续做了一轮相邻 CLI 能力的接口规格调研。那一段不适合在公开博客里展开内部接口细节，但有几个通用经验值得保留。

### 文档抓取失败时，不要一直撞同一扇门

当文档正文抓取因为登录态或 token 过期失败时，继续反复拉同一个接口通常没有意义。更好的做法是快速切换证据源：

```text
文档搜索结果
  -> API 元数据
  -> 代码引用
  -> 服务树或仓库线索
  -> 最小可验证 spec
```

目标不是“非得把某篇文档拉下来”，而是“找到足够可靠的 source of truth”。

### 搜索工具有查询长度限制时，短关键词比长句更稳

内部搜索或文档搜索经常会对 query 长度、分词方式、权限范围有隐性限制。长句看起来更精确，实际可能更容易失败。

更稳的做法是拆成短关键词：

```text
不要一次搜完整需求描述
改成搜核心名词、接口名、页面名、状态名
```

先用短词把范围找出来，再进入具体文档或接口详情。

### API 元数据不要假设 JSON 形状

调 API 平台元数据时，最容易犯的错误是先写 `jq`，默认返回一定是数组或某个字段结构。现实里，同一个平台不同方法、不同版本、不同错误态的 JSON 形状可能不一致。

更稳的顺序是：

```text
先看 raw payload
再确认字段层级
最后再写提取脚本
```

这能避免把“解析脚本错了”误判成“平台没有这个接口”。

### 活跃 MR 分支旁边做调研，要用独立 worktree

如果当前分支已经在处理一个 MR，就不要把相邻调研、spec 草稿、实验脚本都塞进去。最省心的做法是从主干新建 worktree：

```text
active MR worktree: 只放当前修复
spec/research worktree: 只放调研文档
```

这样后续无论是继续实现、丢弃调研、还是单独提交文档，都不会污染正在 review 的修复分支。

## 可复用的原则

这次最有价值的不是某几行代码，而是几条可以复用的工程原则。

第一，自动恢复逻辑一定要有精确的故障形状。不要因为“重试一下可能会好”就吞掉所有失败。

第二，涉及文件删除时，路径校验要比你第一反应更保守。命令、错误码、路径关系、目录名模式、文件类型，最好都校验。

第三，重试要有上限。一次重试通常是在处理已知 transient 或已知残留问题；无限重试是在制造新的故障模式。

第四，测试应该复现因果链，而不是只覆盖最后结果。这里要验证“失败、清理、重试、成功”，而不是只验证函数最后返回成功。

第五，基础设施路径不能只看 diff 大小。安装、升级、权限、发布、文件系统清理这些路径，即使只改几十行，也应该按高影响面处理。

第六，调研和实现要隔离。尤其是一个分支已经进入 MR 后，旁边的探索最好放进独立 worktree，不要把不相关上下文带进 review。

第七，验证要分层：本机恢复、定向测试、静态检查、构建、MR checks、人工 review，各自证明不同的事情。

## 最后

这次修复看起来像一个 npm 小坑，但它其实是一个很典型的工程问题：真实故障来自工具链边缘状态，修复需要进入用户机器的文件系统，验证又必须避免污染真实全局环境。

这类问题的好修复不是“尽量聪明”，而是“尽量窄”：

```text
只识别已知故障
只清理可信残留
只重试一次
只在测试里模拟危险环境
把剩下的不确定性交还给原错误路径
```

越靠近基础设施，越要少一点魔法，多一点边界。
