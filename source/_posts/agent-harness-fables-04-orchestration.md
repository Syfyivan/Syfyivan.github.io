镇上要办集市。

如果每年流程都一样，镇长会贴一张固定清单：

先租棚子，再分摊位，再贴告示，再收摊费。

但今年不一样。桥坏了，商队改道，雨季提前，铁匠铺还突然要办比赛。

镇长只好请一位总管现场拆任务：谁去查桥，谁去问商队，谁去改路线，谁去通知摊主。

这就不是照着清单走了，这是现场编排。

## 概念揭晓

这篇章要揭开的，是第 06 讲里“如何组织过程”的那一层：**不是所有事情都该交给单轮临场发挥，有些任务应该先被编成脚本，再稳定执行**。

故事里的“固定清单”对应简单、稳定、重复的执行方式；“总管临场拆任务”对应编排层，也就是 Orchestration。它关心的不是模型会不会想，而是**一条任务到底该怎么被拆、怎么被派、怎么被验收、怎么被继续推进**。

这也是从 ReAct 走向 Orchestration 的分水岭：前者让模型自己在脑子里转，后者把流程的骨架先落到代码里，再让模型在需要判断的地方出场。

## ReAct 先把路跑起来

最早的做法，是让模型自己扮演循环本身：想一步、做一步、看一步，再回到下一步。这个模式很灵活，适合边界模糊、探索性强、流程未定的任务。

它的问题也很明显：**流程重量全压在模型每一轮的临场发挥上**。一旦某一步理解偏了，后面整条链路都可能歪；而且你很难复盘到底错在了哪一步。

所以 ReAct 能跑起来，但不一定适合长期稳定交付。它更像“先把路试出来”，而不是“把路修成可以反复跑的系统”。

## Skill 与 Dynamic Workflow 的分水岭

这部分最重要的判断是：**Skill 交给模型结构，Workflow 交给代码结构**。

Skill 更像说明书，优点是灵活、轻、好组合；缺点是路径每次都可能不同，稳定性要靠模型自己把握。

Dynamic Workflow 更像脚本，优点是阶段顺序、并行、循环、分支都被代码钉死，稳定、可复放、可审计；缺点是前期要先把流程想清楚。

可以把它简单理解为：

- 想要探索性和临场应变，先用 Skill。
- 想要阶段清晰、可验收、可反复执行，就把它编成 Workflow。

这不是二选一，而是不同任务对应不同层级的结构。

## 深度研究这类任务为什么适合编排

源文用“深度研究”做例子，是因为这类任务的结构很典型：

- 先快速理解问题。
- 再拆成若干子课题并行研究。
- 然后汇总、审改、再验证。

这种任务有三个特征：

1. 阶段分明。
2. 每一阶段都有验收标准。
3. 需要多轮迭代，而不是一次回答就结束。

这正是编排最擅长的地方。模型可以负责每一步的判断和生成，但流程的顺序、并行方式、回炉条件，最好由代码固定下来。

## `agent(taskPrompt, verificationPrompt?)` 这道门

源文里一个很关键的设计点，是把“干活”和“验收”拆开。一个调用负责产出，另一个调用负责把关。

可以把它理解成两道门：

- `taskPrompt` 让模型完成当前子任务。
- `verificationPrompt` 让模型判断这份结果有没有过线。

这样做的好处是，重试逻辑被关进调用内部了。外层脚本只管编排阶段，不需要每次都写一堆 `for retry` 的样板代码。

这其实就是把“反复做到合格”内化成了一个稳定部件，而不是散落在流程里的临时代码。

```text
阶段编排 -> 子任务调用 -> 内部自我修正 -> 验收通过 -> 进入下一步
```

## 代码和模型分别负责什么

如果把这类工作流拆开，最容易看清的是职责分工：

- 代码负责阶段顺序、并行、循环、分支、次数上限。
- 模型负责搜索、规划、写作、判断、改写。

也就是说，**骨架是代码，血肉是模型**。代码保证流程不丢步，模型在被显式调用的地方贡献智能。

这也解释了为什么编排不是“把模型关起来”，而是“让模型只在真正需要它的地方出现”。这样一来，流程更稳定，成本也更容易控制。

## 一个工作流的解剖

源文把一个成熟的工作流拆成了好几个常见部件。你可以把它记成一张检查表：

- Trigger：什么任务会启动这条线。
- Planner：先把问题拆开。
- State：把进度和结果落盘。
- Workers：并行做子任务。
- Evaluator：判断结果过不过线。
- Loop / Branch：什么时候继续、什么时候分叉。
- Stop / Resume：如何暂停和续接。
- Repeatability：如何保证下次还能重放。

这组部件的价值在于，它把“会做任务”变成“会组织任务”。这就是 Orchestration 真正落地的地方。

## 让人留在 Loop 里

长一点的任务，最怕无人值守地跑偏。源文强调，人不应该只在最后验收，而要在关键岔路留得进来。

常见做法有两种：

- 工作流主动问人：比如方向不清、取舍不明、需要业务判断时先停下来。
- 用户主动插入：循环中定期读取新的 steering 信息，及时改方向。

这类设计的核心不是“人工介入越多越好”，而是**在真正需要人裁决的节点上，把人放进来**。这样既不会把流程做成黑箱，也不会让每一步都被打断。

## 视频生成为什么也适合同一套结构

源文最后拿视频生成做了第二个例子，很说明问题。做视频并不只是“生成一段内容”，它通常也有很清楚的阶段：

- 写脚本。
- 定角色。
- 拆分镜。
- 并行生成画面和配音。
- 剪辑成片。
- 最后做质量校验。

这说明 Dynamic Workflow 不是只适用于研究任务。只要一个任务有清晰阶段、可验收标准、并且会重复执行，它就很适合被编排。

换句话说，**不是所有事都要写成 Workflow，但凡你已经在反复手工串这些阶段，基本就值得把它编成脚本。**
