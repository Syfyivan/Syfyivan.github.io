前几篇把桌宠通知、气泡、会话跳转、分享入口和设置面板都串起来了。但真正开始日常使用以后，一个更关键的问题会马上出现：

> 我到底在哪里看 bridge 和机器人刚刚做了什么？

桌宠气泡适合提醒人“有事发生了”，但它不适合承担完整审计。Agent 跑一次任务，背后至少有飞书消息、触发判断、owner 确认、Codex/Claude 执行、过程事件、最终回复、token 用量、失败原因和分享链接。如果这些信息只散在飞书消息、终端日志、JSONL 和桌宠气泡里，用户一定会觉得系统不可信。

所以这一篇记录的是 Bridge 任务详情页的设计：它不是把日志文件换个皮肤，而是把“机器人任务”整理成可以阅读、可以定位、可以分享、可以排错的控制面板。

## 为什么气泡不够

桌宠最开始的目标是提醒：

- 飞书机器人收到消息。
- 本地 Agent 开始工作。
- 有 permission prompt 需要确认。
- 某个 Codex/Claude session 完成。

这些都适合做成气泡。但很快会遇到几个问题。

第一，气泡内容必须短。桌宠如果把完整思考过程都堆在屏幕上，就会遮挡正文、输入框和桌宠本体。提示应该是“一眼知道有事”，不是“在屏幕右边开一个日志终端”。

第二，气泡会被忽略、关闭、错过。哪怕后来把气泡改成常驻、手动忽略，用户也仍然需要一个地方回看历史。

第三，气泡无法解释触发链路。比如用户问“为什么这个 review 没开始”，答案可能不是 Codex 没运行，而是：

- 这条消息没有显式 at 机器人。
- 当前群不在轮询白名单里。
- 进入了 owner 确认卡，但还没点同意。
- reviewer follow-up 识别过宽，被另一个机器人回复误触发。
- bridge 收到了任务，但运行后端返回 keychain 或权限错误。

这些原因不应该靠猜，也不应该让用户翻终端日志。任务详情页要把它们变成可见状态。

## 任务详情页的最小模型

我把 Bridge 任务页拆成两层：

1. 左侧是任务列表，用于快速定位最近任务。
2. 右侧是任务详情，用于还原一次任务的完整生命周期。

一个任务至少要有这些字段：

```text
taskId       任务唯一 ID
source       lark / local / hook
backend      codex / claude / custom
runtime      exec / stream / relay
sandbox      workspace-write / read-only / unknown
cwd          任务执行目录
chatId       飞书会话 ID
messageId    飞书消息 ID
senderId     触发人 ID
status       running / waiting / done / failed
tokens       本轮用量
startedAt    开始时间
updatedAt    最近更新时间
endedAt      结束时间
requestText  原始请求
finalText    最终回复
events       过程事件
```

这些字段看起来普通，但它们对应的是用户真正会问的问题：

- 这是谁触发的？
- 是哪个群里的？
- 它有没有跑起来？
- 它跑的是 Codex 还是别的后端？
- 它为什么停住了？
- 它最后回复了什么？
- 我能不能跳回原始飞书会话？
- 我能不能把这次过程分享给别人？

所以详情页不是“日志浏览器”，而是一个把技术事实翻译成产品状态的界面。

## 列表不是日志流

我最开始容易犯的一个错，是把任务列表做成事件列表：收到一条事件就显示一条。

这样看起来很实时，但问题很大。一次任务可能产生十几条事件：

```text
created
accepted
permission_prompt
stdout
tool_call
reply_draft
task_done
```

如果每条都出现在列表里，用户会看到很多重复项。真正应该做的是聚合：同一个 `taskId` 下的事件合并成一张任务卡。

任务卡只显示摘要：

```text
收到，请下一位继续。
完成 · codex · exec · 4 事件
/var/folders/...
06/16 14:18:54
```

右侧详情再展开所有字段和过程。这样左侧负责“找任务”，右侧负责“看过程”。

## “收到，请下一位继续” 是什么

开发时我看到一个任务标题是“收到，请下一位继续。”，这很容易让人误解：为什么机器人没做事，只回了一句协议话术？

这个文案来自联调 relay 场景。两个机器人互相协作时，需要一个很轻量的交接协议：

```text
收到，请下一位继续。
```

它的含义不是“用户主动说了这句话”，而是“当前 relay 轮次完成，轮到下一个参与者”。任务页如果只显示 `requestText` 或 `finalText`，就会让这个协议消息看起来像普通用户对话。

所以详情页里必须展示上下文字段：

- `source=lark`
- `context=chat:oc_xxx`
- `runtime=exec`
- `messageId=om_xxx`
- `senderId=ou_xxx`
- `events=4`

这样用户才知道它是一轮 bridge 任务，而不是某个神秘消息从天上掉下来。

## 任务分享和会话分享不是一回事

这里踩过一个产品概念坑：任务页分享和会话分享很像，但不能混为一谈。

任务分享适合分享一条 bridge 任务：

- 这个任务是谁触发的。
- bridge 怎么判断。
- Agent 做了什么。
- 最终返回了什么。
- 是否失败、失败在哪一步。

会话分享适合分享一整段协作过程：

- 我让菌子和另一个机器人联调。
- 两边机器人来回说了几轮。
- 中间谁提了问题、谁给了上下文。
- 最终是否收敛。

也就是说，任务页是“单次执行记录”，会话页是“多轮交互故事”。

如果用户点击桌宠气泡上的“分享”，它需要根据事件类型选择：

- `taskId` 明确时，分享任务详情。
- `sessionId` 或 `chatId + message range` 明确时，分享会话。
- 只有本地 transcript 时，先生成可读 HTML，而不是打开 JSONL。

这也是为什么不能直接把 `kodama-agent-transcript.xxxxxx.jsonl` 用系统默认应用打开。JSONL 是机器记录，不是分享产物。用户要的是可阅读的页面。

## Bridge 是事实源，Kodama 是入口

我给桌宠加任务入口时，最重要的边界是：Kodama 不应该重新实现 bridge 的任务数据库。

合理链路是：

```text
bridge
  /healthz
  /pet/events
  /pet/state
  /tasks
  /tasks/:id
  /sessions/share

Kodama
  气泡提醒
  摘要面板
  任务页窗口
  跳转和分享按钮
```

Bridge 已经知道任务的真实状态。Kodama 只负责把入口放到用户看得到的地方。

这样设计有两个好处。

第一，避免双写状态。任务状态只在 bridge 里维护，桌宠重启后可以重新拉取，不会出现“桌宠显示完成但 bridge 还在跑”的分裂状态。

第二，便于排查。用户问“为什么 Bridge 离线”，桌宠只需要探测 `/healthz` 或 `/pet/state`，而不是猜测网络状态。用户问“为什么任务没开始”，任务页直接展示触发门槛和事件。

## 详情页应该展示什么过程

我希望任务过程不要只是 raw log，而是结构化事件。

比较理想的过程列表是：

```text
14:18:27  created           收到飞书消息
14:18:28  route_matched     命中 codex profile
14:18:28  approval_required 需要 owner 确认
14:18:41  approval_accepted owner 已确认
14:18:42  runner_started    Codex exec 启动
14:18:52  reply_ready       生成飞书回复
14:18:54  task_done         已发送
```

这比“stdout 一大坨”更接近用户脑子里的问题。用户真正想知道的是“卡在哪一步”，不是每个内部函数打印了什么。

当然，底部仍然可以留一个原始事件 JSON 折叠区。它给开发者兜底，不应该成为默认阅读方式。

## 排查 review 没开始

这次开发过程中还遇到一个相邻问题：用户在飞书里发了 MR 信息，为什么 review 没开始？

这个问题不能直接动代码，因为用户说“先不要做动作，我想先看看这个 MR 的实现”。正确做法是只读排查：

1. 找到对应飞书会话和消息。
2. 确认 bridge 是否收到事件。
3. 确认消息是否满足触发条件。
4. 确认是否进入 owner 确认或 reviewer 自动化分支。
5. 确认是否被群白名单、mention 模式或安全规则拦住。
6. 只给出原因，不帮用户点 approve、不触发 review。

这个例子说明任务详情页里需要一个“触发判定”区域。它可以写清楚：

```text
触发结果：未启动 review
原因：消息未包含显式 review 指令 / 未 @ 机器人 / 当前群未启用该 profile
下一步：需要在原话题中 @机器人 并给出 MR 链接
```

否则用户只能看到“没反应”，而不知道系统到底是安全拦截、权限失败，还是根本没收到消息。

## 这页的设计原则

这次做 Bridge 任务详情页，我总结了几条原则。

第一，任务页要回答“发生了什么”，不是展示“程序打印了什么”。

第二，任务、会话、transcript 是三个不同实体。任务可以属于会话，transcript 可以作为证据，但用户点击分享时要拿到的是可读页面。

第三，触发失败也应该是一种结果。没有启动不是空状态，而应该有原因。

第四，桌宠只做入口。真正的任务事实应该由 bridge 暴露。

第五，任何自动化 review、owner 确认、bot-to-bot relay 都必须在任务详情中展示安全边界，否则用户会以为机器人“乱接管”。

做完这页以后，桌宠才从“有提醒的小玩具”变成“能回到现场的 Agent 控制面”。
