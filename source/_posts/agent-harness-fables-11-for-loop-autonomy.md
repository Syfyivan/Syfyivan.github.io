城里有一座钟楼。最早的时候，守夜人每隔一小时爬上去看一眼街道：东门没事，西市没事，河桥没事。他看完就下楼，等下一次钟响再上去。

后来城变大了。守夜人光靠眼睛不够，就在钟楼里放了地图、巡逻册、信鸽笼和小仓库。他每次上楼，不只是看一眼，还会记录哪里修过、哪里要复查、哪些街巷该交给别的巡夜人。有人回来汇报时，只交一张摘要，不把整夜的脚印都倒进钟楼。

再后来，师傅给钟楼加了几道机关：开门前先检查名单，派人前先看预算，遇到贵重仓库要等城主盖章，巡逻结束要写入档案。钟楼不再只是“每小时看一次”的木头循环，而是会分工、会记账、会停手、会求助的城防系统。

## 概念揭晓

这个故事讲的是 Agent Loop 的进化。

第一段里的守夜人，只是一个浅循环：定时观察，做一点动作，然后等待下一轮。第二段里的地图、巡逻册、信鸽和小仓库，对应计划、外部记忆、子任务隔离和中间结果落盘。第三段里的机关，对应 middleware、审批、预算、限流、错误恢复和持久化。

所以本章要讲的不是“循环本身有多神秘”。最小 Agent Loop 甚至可以写成一个 `while` 或 `for`。真正的差距在于：这个循环有没有计划工具、有没有上下文治理、有没有可插拔扩展点、有没有人类监督、有没有跨会话的记忆和恢复能力。

## 本章目录

- 最小循环：模型反复决定是否调用工具，直到停止。
- 浅循环与深循环：同一个骨架，为什么产品能力差很多。
- Deep Agents：把计划、文件系统、子代理和长程记忆预装进 Harness。
- Middleware：在模型调用和工具执行之间插入可测试的工程逻辑。
- 生产级扩展点：摘要、审批、重试、限流、脱敏、fallback。
- 前沿观察：从反应式任务走向更持久的自治系统。
- 三次进化：浅循环、深循环、自治循环。

## 最小循环：普通代码也能写出来

Agent Loop 的最小形态并不复杂。它大概就是：

```python
messages = [{"role": "user", "content": user_input}]

for _ in range(max_turns):
    response = model.call(messages, tools=tools)
    messages.append(response)

    if not response.tool_calls:
        break

    for call in response.tool_calls:
        result = run_tool(call)
        messages.append({"role": "tool", "content": result})
```

这段代码表达的规则很朴素：模型如果发出工具调用，外壳就执行工具，把结果放回消息；模型如果没有发出工具调用，就把这一轮当成最终回答。

它的价值在于把一次性回答变成多步行动。但它的问题也很明显：上下文会越来越长，工具结果会挤占空间，模型可能忘记原始目标，失败后可能在同一组动作里打转。如果只停留在这段代码，Agent Loop 很快会从“自动推进”变成“自动放大错误”。

## 浅循环与深循环

浅循环只依赖模型当前上下文。任务短的时候，它看起来很灵；任务一长，就容易出现三类问题。

第一类是上下文溢出。工具输出、网页全文、测试日志和中间思考不断堆进消息列表，真正重要的目标、约束和最新证据反而被挤远。

第二类是目标遗忘。模型一开始知道要修车，转了几圈以后却开始只盯着某个螺丝，忘了最终验收是“车能不能平稳走直”。

第三类是无限振荡。模型在搜索、读取、修改、测试之间来回绕，却没有预算、停止条件或外部裁判告诉它该收手。

深循环不是换了一个更玄的循环，而是在同一骨架上加四类支撑：详细但可控的系统指令、显式计划工具、外部文件或状态作为记忆、子任务隔离和汇总。LangChain 的 Deep Agents 官方文档也把这类能力拆成任务规划、文件系统、上下文管理、子代理和人类审批等组件。

## Deep Agents：把四根柱子预装好

Deep Agents 可以理解成一种预装好的 Agent Harness。它不是只给你一个 `while`，而是把长程任务常用的支柱打包好：

- **任务规划**：内置类似 `write_todos` 的计划工具，让模型把多步任务显式写成可跟踪清单。
- **虚拟文件系统**：让中间材料、草稿、摘要和状态可以落到外部存储，而不是全塞在上下文窗口。
- **上下文管理**：对历史、工具结果和长期材料做摘要、搬运、缓存或按需加载。
- **子代理**：把重任务交给独立上下文窗口处理，只把最终报告交回主循环。
- **人类在环**：在高风险动作前暂停，等待人类审批、修改或拒绝。

这里最容易被低估的是计划工具。它不一定真的“执行”什么，甚至可以是 no-op；但它强迫模型把任务状态显式写下来。对长任务来说，显式计划本身就是一种上下文工程：它把“我接下来要做什么”从模型隐含状态变成可检查、可恢复、可更新的外部状态。

子代理也不是为了显得热闹。它的核心价值是上下文隔离。主代理不用吞下子任务的几十轮中间过程，只需要拿回压缩后的结论。这样主循环保持清醒，子循环负责深入。

## Middleware：给循环装可插拔机关

如果只把 Agent Loop 写成模型调用和工具执行，工程师很快会问：我能不能在模型调用前压缩历史？能不能在工具执行前做审批？能不能在工具失败后重试？能不能按成本切换模型？能不能在返回用户前做脱敏？

Middleware 就是为这些问题准备的扩展点。LangChain 当前文档把 middleware 描述为定制 agent harness 的核心机制：每个 middleware 处理一个关注点，挂在 agent loop 的合适位置，并且可以和其他 middleware 组合。

可以把它想成 Web 服务里的中间件：请求进来前可以鉴权、限流、改写；响应出去前可以记录、审计、包装。Agent Loop 里也是一样，只不过“请求”变成了模型调用和工具调用，“响应”变成了模型输出、工具结果和最终答案。

常见插入点可以分成两类：

- **节点式钩子**：整个任务开始前、每次模型调用前、模型调用后、整个任务结束后。
- **包裹式钩子**：包住一次模型调用或一次工具调用，可以短路、重试、缓存、限流或替换。

这件事的重要性在于，它把“提示词里劝模型小心点”变成了“运行时确定执行的工程逻辑”。

## 生产级扩展点

一个真实可用的循环通常会装上这些机关。

**摘要与上下文搬运**：当消息历史接近窗口上限时，压缩旧材料，保留最近关键步骤和任务目标。LangChain 的预置 middleware 文档里就有 SummarizationMiddleware 这类组件。

**人类审批**：数据库写入、发邮件、删除文件、花钱调用服务，都不该只靠模型自己判断。Human-in-the-loop middleware 可以在指定工具调用前中断，让人类批准、编辑或拒绝。

**重试与 fallback**：生产环境会遇到限流、超时、模型失败和工具偶发错误。重试、备用模型和调用次数限制应该是运行时策略，而不是散落在每个工具里的临时 `try/catch`。

**工具限流与模型预算**：循环越长越贵。模型调用次数、工具调用次数、单工具频率、总 token 预算，都应该有硬边界。

**脱敏和防护**：PII、密钥、内部路径和用户隐私不能只依赖模型“不要说”。应该在上下文进入模型前或工具结果回填前做确定性处理。

这些扩展点共同说明一件事：深循环不是“更会想”，而是“更会被管理”。

## 前沿观察：从反应式走向自治式

Feishu 原文还讨论了 Claude Code 相关的前沿工程观察，例如更复杂的查询引擎、记忆分层、后台守护、周期性刷新、云端规划卸载、防蒸馏和终端渲染优化。这里要特别划边界：这些内容来自原文作者对公开技术分析和工程现象的整理，不应当当成 Anthropic 官方公开 API 或已发布功能。

即使不把具体名称当事实，这些方向背后的趋势仍然值得学习。

第一，循环的边界正在变长。早期循环只活在一次会话里；更进一步的系统会跨会话保留状态，甚至在用户不盯着的时候继续维护项目知识。

第二，记忆会从“把历史塞回上下文”转向“索引 + 按需加载”。常驻上下文只放轻量指针，真实材料在文件、数据库或历史日志里按需检索。

第三，规划会从本地临时思考转向可卸载的工程服务。复杂任务可以让更强模型、更长上下文或云端运行时处理，再把计划交回执行循环。

第四，界面和体验也会成为循环的一部分。流式 token 如何渲染、进度如何展示、失败如何回放、审批如何打断，都影响 Agent 是否真的可用。

这意味着自治系统不是“一个模型一直自己跑”。它更像一个带记忆、带调度、带权限、带人类刹车、带长期维护机制的运行时。

## 三次进化

可以把 Agent Loop 的演进分成三层。

**第一层：浅循环。** 模型在循环里调用工具，工具结果回填，直到模型停止。它适合短任务，也适合教学，但不适合长时间无人看管。

**第二层：深循环。** 在同一个循环里加入计划、外部记忆、上下文压缩、子代理、权限和 trace。它能处理数十步任务，适合代码、研究、排障、写作等复杂工作。

**第三层：自治循环。** 循环不再只属于一次对话，而是跨会话、跨时间、跨环境持续维护状态。它可能监听事件、周期性检查、在空闲时整理记忆、把复杂规划交给更强运行时，同时在关键动作前等待人类确认。

初学者不要一上来追第三层。正确顺序是先写清楚最小 loop，再补工具契约，再补上下文和记忆，再补 middleware，最后再考虑自治。

## 今天的练习

拿一个你希望 Agent 完成的长任务，例如“修一个测试失败并写总结”。先不要写完整产品，只写这三层：

1. 最小 loop：最多几轮，每轮能调用哪些工具，什么时候停止。
2. 深循环支撑：计划放哪里，中间材料放哪里，子任务是否隔离。
3. middleware：哪些工具要审批，失败怎么重试，预算怎么限制，哪些内容要脱敏。

如果这三层说不清楚，说明你还不是在设计 Agent，而是在期待模型自己补齐运行时。
