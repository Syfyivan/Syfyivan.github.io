## AI 观察

### 1. “反模板”不是审美口号，而是一个可执行的质量过滤器

今天的日报选了一个很具体的工具：[`anti-slop`](https://github.com/miqdadbadjuber/anti-slop) 把 UI 生成中的模板化风险拆成规则、活力方向、功能完整性和交付门禁。公开 README 明确说它不是固定配色或固定布局的风格指南，而是要求每个视觉技术通过“服务什么目的”的检查；`DESIGN.md` 负责品牌和方向，`antislop.md` 负责过滤，`AGENTS.md` 或同类入口文件负责按任务路由。

这套分工很值得借鉴：模型可以生成代码，但不能凭空发明产品方向；规则可以阻止常见坏味道，但不能代替设计判断；入口文件可以控制加载范围，但不能把“文件被读过”当成“结果通过”。真正的交付门槛应当是：方向存在、技术选择有理由、交互真的可用、不同状态能工作，并且最后留下检查结果。

### 2. Skill 的最小闭环应当是“路由—执行—门禁”，而不是“安装成功”

`anti-slop` 的公开文件把 `antislop.md` 定义成按需加载的核心规则，又把 UI 规则作为可选的增量 Skill；这比把几百行提示词永久塞进每个会话更容易维护。它还把 During 和 After 分成两种使用模式：一种在构建过程中约束产出，另一种先审计、等人工选定问题后再修改。

我的工程推论是，任何团队 Skill 都应该能回答三个问题：

1. 什么任务会触发它，哪些任务明确不触发？
2. 它执行时改变了什么输入、工具权限和检查步骤？
3. 它以哪份报告、测试或人工确认作为通过依据？

如果只能回答“它能让模型写得更像某种风格”，却不能指出触发条件和失败证据，那它还是一段经验，不是可验收的工程能力。

### 3. 群里的“假客户端”和“重置体验”提醒了配置层级的风险

Codex 群今天有人询问为什么客户端只能自定义模型、账号信息无法切换，也有人讨论重置卡、额度和不同模型的价格体感。这些内容不能证明某个客户端是“假的”，也不能证明官方服务发生了统一故障；但它们暴露了一个常见诊断问题：用户看到的入口、当前使用的模型、登录身份、计费提供方和实际请求路径，可能不是同一层。

公开的 [Claude Code 配置文档](https://code.claude.com/docs/en/settings) 也体现了类似的层级：托管、命令行、项目、本地和用户配置可能共同影响最终行为；[权限文档](https://code.claude.com/docs/en/permissions) 进一步说明拒绝规则、询问规则和允许规则有明确的优先级。对任何 Agent 客户端都应采用同样的拆分：显示配置来源、最终生效值、运行环境和最近一次验证时间，而不是只给一个“当前模型”的字符串。

## 前端 / 服务端 / 客户端工程观察

### 前端：把“设计方向”和“反模板检查”做成两条状态链

前端工作台可以把一次 UI Agent 运行展示成两列：左侧是 `DESIGN.md` 提供的方向、用户选择的能量/节奏/动效目标；右侧是 `antislop.md` 或项目规则发现的风险、实际交互检查和 Delivery Gate 结果。这样用户能区分“没有方向”“有方向但实现偏离”和“实现符合方向但功能未完成”。

公开规则中特别值得落地的是功能完整性和韧性检查：按钮要真的工作，页面要覆盖空态、加载态、错误态、响应式和键盘操作。前端不要只显示一个绿色的“AI 检查通过”，至少应能打开对应页面、测试步骤、截图或录屏，并把“规则未触发”与“规则触发后通过”分开。

### 服务端：把规则加载和交付门禁变成可追踪事件

服务端可以为一次 Agent 交付记录 `task_id`、`attempt_id`、`rule_bundle_version`、`design_digest`、`entry_file`、`builder_run_id`、`review_run_id`、`evidence_id` 和 `stop_reason`。规则加载失败、参考文件缺失、工具执行失败、人工拒绝和最终验证失败应当是不同事件，不能都压成一条“生成失败”。

这也是 [Claude Code 配置的项目作用域](https://code.claude.com/docs/en/settings) 对后端设计的启发：团队共享的设置可以进入版本控制，本地实验配置则不应悄悄改变所有人的结果。规则包、提示词、模型、权限模式和依赖版本最好都有摘要；同一个任务重试时，要能看出到底是输入变了、规则变了，还是运行环境变了。

### 客户端：不要让“能看到入口”代替“真的按该配置运行”

客户端应该至少显示四层状态：当前界面选择、最终解析后的配置、实际请求使用的模型/提供方，以及最后一次成功验证的版本和时间。遇到“只能自定义模型”这类问题时，用户可以沿着这条路径检查是登录身份、组织策略、客户端版本、远端能力还是自定义网关造成的，而不是依赖截图猜测。

对于移动端或远程控制入口，还要把“在哪里操作”和“代码实际在哪里执行”分开。官方 [Claude Code 工作方式说明](https://code.claude.com/docs/en/how-claude-code-works) 将本地、云端和 Remote Control 视为不同执行环境，同时说明终端、IDE、桌面、网页和 CI/CD 是不同交互入口。这个边界对 Codex、Claude Code 以及内部 Agent 工作台都适用：客户端是控制面，不等于执行面。

### 共同观察：AI 交付的最小单位是“结果 + 反证路径”

今天的材料最后都指向同一个工程习惯：不要只存模型生成的结果，要保存别人推翻它所需的最短路径。页面需要实际交互和不同状态的证据，服务需要规则版本和事件链，客户端需要最终配置、执行环境和版本信息，Skill 需要固定输入、检查规则和失败报告。

## 值得跟进的动作

1. 选一个经常生成 UI 的项目，建立三文件最小试验：`DESIGN.md` 提供方向，入口文件按 UI 任务路由，`antislop.md` 或等价规则负责过滤；先在一个脱敏页面上记录通过与失败原因。
2. 将规则包纳入版本控制并做摘要校验，记录 `rule_version`、`design_version`、`model`、`provider`、`permission_mode` 和 `runtime`，避免“同一个提示词”在不同环境下被误认为同一个实验。
3. 给前端交付门禁补 5 个固定检查：空态、加载态、错误态、窄屏布局和键盘操作；每一项都输出可打开的证据，不用一个总分掩盖缺项。
4. 给服务端补齐 Agent 生命周期事件：`requested → routed → built → reviewed → verified → published`，并让重试具备幂等键和明确的停止原因。
5. 给客户端增加“配置来源 / 最终生效值 / 执行环境 / 最近验证”面板，用它复现群内关于模型切换、账号身份和额度重置的体验问题；先做单账号、单版本、单任务对照，不把群内感受直接升级为全局结论。
6. 继续观察[当天 AI X 检索页](https://x.com/search?q=%28Codex+OR+%22Claude+Code%22+OR+%22AI+agent%22%29+since%3A2026-08-13+until%3A2026-08-14&src=typed_query&f=live)以及前端、服务端、客户端三个入口；只有能回到作者、正文、发布时间和上下文时，才把 X 线索升级为事实。
