<div class="csf-key-note">上一讲我们承认了一件事：Excel 和文本文件总有撑不住的那天。这一讲我们就来认识那个"撑得住"的东西到底长什么样——它的世界里只有一种形状：<b>表</b>。把现实里的一本书、一个用户，正确地拆进"一张表的一行"，是你和数据库打交道的第一个、也是最重要的基本功。今天不写一行 SQL，我们先把脑子里的那张表画清楚。</div>

## 🎯 这一讲你会学到什么

- 什么是**关系模型**：为什么数据库几乎只用"表"这一种结构来装一切。
- **表 / 行 / 列**到底分别是什么，用人话讲清它们的关系。
- 列要有**数据类型**：为什么"价格"和"书名"不能混着存。
- **主键（primary key）**是什么，为什么每一行都需要一个"身份证号"。
- **NULL** 是什么——它不是 0，也不是空字符串，而是"不知道 / 没有"。
- **模式（schema）**：一张表"长什么样"的设计图。
- 一个能力：拿到任何一个现实事物，你能开始想"它该是哪张表的哪一行、哪几列"。

<div class="csf-note">这一讲的产出不是代码，是<b>一张你亲手画在纸上的表</b>，外加一句你能讲给别人听的"为什么"。听起来简单，但这正是后面所有 SQL 的地基。地基歪一寸，楼能塌一丈。</div>

## 🛠 跟我做

### 先认人：表、行、列 <span class="csf-b csf-core">必读</span>

关系模型这个名字听着高大上，其实它的核心朴素得让人意外：**所有数据都摆成一张二维表格**。就像 Excel 那样，有横排、有竖列。我们先把三个词对上号。

<div class="csf-legend">📊 <b>表（table）</b>：一类事物的集合。比如"所有的书"放一张 <code>books</code> 表。<br>↔️ <b>行（row）</b>：表里的一条记录，代表"一个具体的东西"。一行就是一本具体的书。<br>↕️ <b>列（column）</b>：一种属性 / 字段。比如"书名"是一列，"价格"是一列。<br>🔑 <b>主键（primary key）</b>：能唯一认出某一行的那一列，相当于这一行的身份证号。</div>

我们用一张迷你书店的表来感受一下。下面这张表，每一**行**是一本书，每一**列**是这本书的一个属性：

| id | title | author | price | stock |
|----|-------|--------|-------|-------|
| 1 | 小王子 | 圣埃克苏佩里 | 28.00 | 12 |
| 2 | 活着 | 余华 | 35.00 | 0 |
| 3 | 三体 | 刘慈欣 | 59.00 | 7 |

读这张表，你应该能立刻翻译成人话：

- 这是一张装"书"的表。表里现在有 **3 行**，就是 3 本书。
- 每本书有 **5 列**信息：编号、书名、作者、价格、库存。
- 第 2 行那本《活着》，<code>stock</code>（库存）是 0——它在册，但卖光了。

<div class="csf-why">💡 <b>为什么非得是表？</b> 因为表这种"行 × 列"的形状有个巨大的好处：每一行的结构完全一样，每一列的含义完全固定。这种"整齐"换来的，是机器可以飞快地按列筛选、按行查找、跨表拼接。上一讲文本文件的混乱，本质就是因为它没有这种强制的整齐。关系模型用一点点"必须先想清楚结构"的代价，换来了后面无穷的便利。</div>

### 每一列都有"类型" <span class="csf-b csf-key">重点</span>

注意看上面的表：<code>title</code>（书名）装的是文字，<code>price</code>（价格）装的是数字，<code>stock</code>（库存）装的是整数。这不是巧合——**数据库里每一列都必须事先声明它只装哪种数据**，这叫**数据类型**。

为什么这很重要？想象一下：如果"价格"这一列允许有人填进"二十八元"这三个字，那你以后想算"全店书的总价"就彻底没戏了——机器没法把"二十八元"和 35.00 相加。**类型，就是数据库帮你提前挡住脏数据的第一道门。**

入门阶段你只要先认识几种最常见的类型：

<div class="csf-legend">🔢 <b>整数（INTEGER）</b>：库存、数量、id。没有小数点。<br>💰 <b>小数 / 实数（REAL）</b>：价格、重量这种带小数的。<br>📝 <b>文本（TEXT）</b>：书名、作者、地址，任何文字。<br>📅 <b>日期时间</b>：下单时间、注册时间（后面的讲会细说存法）。</div>

<div class="csf-note">⚠️ 先说明一句：<b>SQLite 就是我们这门课要用的那个具体的数据库软件</b>（一个小巧、装起来很省事的数据库，后面会带你装、带你用）。它在类型上比较"宽松"——意思是，即使你某一列说好了只装数字，它也不太拦着你往里塞文字，不会立刻报错。听起来好像很方便，但这容易让你养成"列里什么都能塞"的坏习惯，到了别的数据库就会出问题。所以<b>哪怕软件不严格，你自己心里必须严格</b>：设计表时就把每一列装什么想清楚。养成"先定类型"的习惯，换别的数据库（MySQL、PostgreSQL 这些）时才不会摔跤。</div>

### 主线动手练：为迷你书店画一张 `books` 表 <span class="csf-b csf-core">必读</span>

现在轮到你了。**关掉一切代码工具，拿出纸笔，或者打开一块白板。这一步千万别让 AI 替你画——画表的过程就是你建立"用表思考"直觉的过程，AI 替你画了，长本事的就是它不是你。**

按下面四步走，把它真的画出来：

```text
第 1 步：确定这张表装什么 → 装"书"，表名就叫 books。

第 2 步：列出每本书你关心哪几个属性（=列）：
        id（编号）、title（书名）、author（作者）、
        price（价格）、stock（库存）。

第 3 步：给每一列标上数据类型：
        id     → 整数 INTEGER
        title  → 文本 TEXT
        author → 文本 TEXT
        price  → 小数 REAL
        stock  → 整数 INTEGER

第 4 步：圈出哪一列当主键 → 圈住 id。
        （为什么是 id 不是 title？先猜，下面揭晓）
```

画完后，你的纸上应该长这样（这就是这张表的**模式 / schema**——它的设计图）：

```text
表 books
┌────────┬─────────┬──────────┬──────┐
│ 列名   │ 类型    │ 说明     │ 主键 │
├────────┼─────────┼──────────┼──────┤
│ id     │ INTEGER │ 书的编号 │  ★   │
│ title  │ TEXT    │ 书名     │      │
│ author │ TEXT    │ 作者     │      │
│ price  │ REAL    │ 价格     │      │
│ stock  │ INTEGER │ 库存数量 │      │
└────────┴─────────┴──────────┴──────┘
```

<div class="csf-note">🗣 <b>最后一步，也是最关键的一步：开口讲。</b> 找个同学、室友，或者就对着 AI，用半分钟讲清楚一句话：<b>"为什么我用 id 当主键，而不是用书名当主键？"</b> 如果你能把这句讲明白，这一讲你就真的学到手了。下面我们就来攻这个问题。</div>

### 主键：为什么需要一个"身份证号" <span class="csf-b csf-core">必读</span>

主键，就是**能唯一认出某一行**的那一列。给你一个主键值，数据库就能精确锁定到唯一的一行，不多不少。

先猜一下：上面的 <code>books</code> 表，**能不能用书名 <code>title</code> 当主键？** 先在心里给个答案和理由，再往下看。

<div class="csf-key-note">揭晓：<b>不能。</b> 主键有两条硬要求——<b>唯一</b>，而且<b>最好永不改变</b>。书名两条都踩雷：<br>① <b>会重复</b>：世界上同名的书太多了，《活着》也许有好几个版本、几个出版社，书名一撞，数据库就分不清你说的是哪一行。<br>② <b>会变</b>：书可能再版改名、副标题调整。一旦书名变了，所有"靠书名指向这本书"的地方就全断了。<br>而 <code>id</code> 不一样：它是我们自己造的一个纯编号，天生不重复，而且一旦给某本书发了 1 号，就永远是 1 号，绝不更改。这就是为什么几乎所有表都会专门加一列 id 当主键。</div>

这个判断力极其重要，因为它是后面**所有表关系的地基**。后面几讲你会学到，让"订单"指向"哪本书"，靠的就是把书的 <code>id</code> 写进订单表里。如果 id 会变会重复，整个关系网就会崩塌。

<details class="csf-fold"><summary>细究：自然键 vs 代理键，以及"复合主键"<span class="csf-b csf-skim">细究 · 可跳读</span></summary>
像书名、身份证号这种"现实里本来就有"的标识，叫<b>自然键（natural key）</b>；像我们自己造的 id 这种"专门为做主键而生、本身没现实含义"的，叫<b>代理键（surrogate key）</b>。<br>初学阶段的稳妥默认：<b>优先用代理键 id</b>。因为现实里的"唯一标识"常常没你想的那么唯一、那么稳定（手机号会转让、邮箱会换、身份证号也有极少数历史问题）。<br>另外，主键不一定只能是一列：有时要用<b>两列合起来</b>才能唯一确定一行（比如"班级 + 学号"），这叫<b>复合主键（composite key）</b>。这个概念先知道有这回事就行，后面讲多表关系时会自然用到。</details>

### NULL：第三种"值"，意思是"不知道" <span class="csf-b csf-key">重点</span>

最后认识一个新手特别容易栽的概念：**NULL**。

假设进了一本新书，作者一栏暂时还没查到。这时 <code>author</code> 这一格该填什么？填空字符串 <code>""</code>？填 0？都不对。正确答案是 **NULL**——它表示**"这里没有值 / 我们还不知道"**。

<div class="csf-note">务必分清这三者，它们是<b>三件不同的事</b>：<br>• <code>0</code> → 一个确定的数字，比如库存是 0（明确卖光了）。<br>• <code>""</code>（空字符串）→ 一个确定的、长度为零的文字。<br>• <code>NULL</code> → <b>压根没有值</b>，"不知道 / 不适用"。<br>《活着》库存是 0，意思是"我确切知道它有 0 本"；而新书作者是 NULL，意思是"我还不知道作者是谁"。这俩天差地别。</div>

为什么现在就提 NULL？先说一件你以前可能没人讲过的事：**在数据库里，每做一次比较（比如"这本书的价格是不是等于 50"），机器都会给出一个判断——要么"成立"，要么"不成立"。** 你可以把它想成机器在心里点头或摇头。

而 NULL 有个反直觉的脾气：**只要比较的某一边是 NULL，这个判断既不算成立、也不算不成立**——机器既不点头也不摇头，干脆"不表态"。

举个例子：你想"找出价格 ≠ 50 的书"。那些价格是 NULL（还没标价）的书，<b>不会</b>被算进来——因为机器认为"我都不知道这本书多少钱，没法判断它等不等于 50"，于是直接不表态、把它排除在外。这个坑后面查询时会专门踩，今天你只要先记住一句话：**NULL 是"不知道"，不是"零"，也不是"空"。**

## 💡 自己复述一遍

合上屏幕，用一句话把这一讲讲给自己听。比如：

<div class="csf-note">"关系模型就是把一类事物装进一张<b>表</b>，每<b>一行</b>是一个具体的东西，每<b>一列</b>是它的一个属性、且有固定<b>类型</b>；每行靠一个<b>主键</b>（最好用永不重复、永不更改的 id）来唯一标识；而 <b>NULL</b> 表示'不知道'，跟 0 和空字符串都不是一回事。"</div>

讲不顺也没关系，回头再看一眼上面那张 <code>books</code> 表，对着它讲一遍。能对着表讲清楚，比背定义有用得多。

## 🔧 翻车现场

<div class="csf-card"><b>翻车 1：拿"会重复或会变"的东西当主键。</b><br>典型错误：用书名、用手机号、用邮箱、用用户昵称当主键。<br>后果：哪天两条数据撞了名，或者用户改了手机号，整张表的"身份"就乱了，所有指向它的地方一起出错。<br>解法：默认加一列纯编号 <code>id</code> 当主键。记住主键的两条铁律——<b>唯一 + 永不改变</b>。</div>

<div class="csf-card"><b>翻车 2：把"没有值"填成 0 或空字符串。</b><br>典型错误：作者没查到就填 <code>""</code>，价格还没定就填 0。<br>后果：以后你分不清"价格真的是 0 元"还是"还没定价"；统计时会把这些假数据一起算进去，结论全歪。<br>解法：真的不知道，就用 <b>NULL</b>。让"未知"诚实地保持未知。</div>

<div class="csf-card"><b>翻车 3：一列里塞好几样东西。</b><br>典型错误：搞一列叫 <code>info</code>，里面塞"余华 / 35元 / 库存7"。<br>后果：你又退回到了上一讲文本文件的泥潭——没法单独按价格筛、按作者查。<br>解法：<b>一列只装一件事</b>。能拆成独立属性的，就拆成独立的列。</div>

<div class="csf-card"><b>翻车 4：列的类型想当然。</b><br>典型错误：价格列里混进"35元""免费"这种文字。<br>后果：以后求和、比大小、排序全部失灵。<br>解法：设计时就把每列类型钉死，价格就是数字（REAL），单位"元"放在显示的时候再加，别存进数据里。</div>

## ✅ 自检三问

1. 用你自己的话说：**行**和**列**分别代表什么？在 <code>books</code> 表里，"《三体》"是行还是列？"price"呢？
2. 主键必须满足哪两条要求？据此解释：为什么"手机号"通常不适合当用户表的主键？
3. <code>stock = 0</code> 和 <code>author = NULL</code>，含义有什么本质区别？如果把一个"还没查到的作者"错填成空字符串，将来可能踩什么坑？

<div class="csf-note">三问都能不看上文答出来，就可以进下一讲。卡在哪一问，就回到对应小节再读一遍——尤其是第 2、3 问，是后面最容易出错的地方（程序里的错误、毛病，业内一般叫 bug，以后你会经常听到这个词）。</div>

给你换个场景，自己独立画一张表（同样：先纸笔，别让 AI 代画，画完再让 AI 帮你挑毛病）：

<div class="csf-card">🎯 为一个"<b>图书馆的读者</b>"设计一张 <code>members</code> 表。<br>要求：<br>① 至少包含 4 列，自己想清楚要哪些属性（提示：编号、姓名、注册日期、借书数量……）。<br>② 给每一列标上数据类型。<br>③ 选出主键，并写一句话说明<b>为什么选它、为什么不选姓名</b>。<br>④ 故意留一个"可能为 NULL"的列，并说明它在什么情况下会是 NULL。<br>进阶（选做）：再想一想，如果以后要记录"谁借了哪本书"，你觉得这条信息该放进 <code>members</code> 表，还是 <code>books</code> 表，还是……需要一张新表？把你的直觉写下来——后面讲多表关系时，回来对照。</div>

<div class="csf-note">🤖 <b>AI 的正确用法：</b> 画完之后，把你的表丢给 AI，让它<b>当审查员</b>："帮我看看这张表的主键选得对不对？有没有哪列类型不合适？哪列将来可能出问题？"——让 AI 挑你的毛病、和你辩论，而不是让它替你从零生成一张表。<b>判断力是练出来的，不是抄出来的。</b></div>

## 📦 复制带走

<div class="csf-card">📦 <b>本讲要点</b><br>1. <b>关系模型 = 一切皆表</b>：表装一类事物，行是一条具体记录，列是一个属性，每列有固定<b>类型</b>。<br>2. <b>主键是身份证号</b>：唯一、且最好永不改变；默认用自造的 id，别拿书名/手机号这种会重复会变的当主键。<br>3. <b>NULL ≠ 0 ≠ 空字符串</b>：NULL 是"不知道 / 没有"，别用 0 或 "" 假装它有值。<br>4. <b>schema 是设计图</b>：动手写 SQL 之前，先在脑子里（或纸上）把表长什么样想清楚——这是后面所有操作的地基。</div>
