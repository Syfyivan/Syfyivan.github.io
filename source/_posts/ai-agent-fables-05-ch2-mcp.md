> 承上：上一章阿器学会了开领用单借工具。可他很快烦了：东街那家工具行用木牌领、西街那家用口令领、城外那家还要画押——每换一家，他就得重学一套领法。

阿器抱怨连连，老掌柜笑了：“早年就是这么乱。后来大家立了个统一柜台的规矩，谁守这规矩，借起来就一个样。”

这规矩说：任何一家工具行，只要按统一格式把自家东西挂到柜台上，来借的人就能用同一套办法对接。柜台上挂三类东西：**能借去干活的工具**（用了会产生动作和结果）、**能查阅的资料**（拿来读、不改东西）、以及**现成的领用模板**（别人写好的标准单子，照着改就能用）。

“于是阿器你不用再为每家重学，”老掌柜说，“你学一次‘怎么对接统一柜台’，全城守规矩的工具行就都能借。新开一家行，只要它也守规矩，你立马就会用。”

## 概念揭晓

这套“统一柜台的规矩”，就是 **MCP（模型上下文协议，Model Context Protocol）**：一个开放标准，规定了 AI 应用怎么和外部的工具、数据源统一对接，免得每接一个都要重写一套。

它的角色分两边：

- **客户端（client）**：来借东西的一方，通常嵌在 AI 应用 / Agent 里。
- **服务器（server）**：挂出能力的一方，把某个系统（数据库、文件、某个 SaaS、某个工具）按 MCP 格式暴露出来。

服务器主要挂三类东西：

- **tools**：模型可以调用、会产生动作的工具（呼应 05.1 的工具调用）。
- **resources**：可读取的数据/上下文（拿来当资料用，类似第四讲的“资料”）。
- **prompts**：预置好的提示模板，供客户端取用。

## MCP 解决什么乱象

没有统一标准时，每个 AI 应用要接一个新数据源或新工具，都得专门写一套对接代码——接十个工具写十套，接口五花八门，难复用、难维护。这就像阿器为每家工具行重学一套领法。

MCP 把这件事标准化：定义一套通用的“怎么发现能力、怎么调用、怎么传数据”的协议。于是“写一次客户端，接所有守协议的服务器”“写一个服务器，被所有守协议的客户端复用”成为可能。生态因此能快速长大——这正是它近年迅速普及的原因。

## 客户端、服务器、三类能力

- **客户端**在 AI 应用里，负责“去发现有哪些能力、按需调用、把结果交给模型”。
- **服务器**包住某个具体系统，把它的能力按 MCP 格式挂出来。
- 服务器挂的 **tools / resources / prompts** 分别对应“能做的动作 / 能读的资料 / 能取的模板”。

一个 Agent 可以同时连多个 MCP 服务器：一个连你的文件系统、一个连数据库、一个连某个线上服务——它们在模型眼里，都是“按统一规矩挂出来的能力”。

## MCP 不是工具本身

这是最常见的误解：MCP 不是某个工具，也不是某个模型，它是**让工具和模型对接的协议**（统一柜台的规矩），本身不干活。

类比：MCP 之于工具，有点像 USB 之于设备——它定义“怎么插、怎么通信”，但插上去的鼠标、键盘、硬盘各是各的功能。把 MCP 当成“一个工具”或“一个产品”，就理解偏了。它的价值在于“统一接法”，让生态可互通。

## 为什么标准化重要

回到第一讲的主线：能力来源是模型，可靠性和扩展性来自模型之外的安排。MCP 就是“之外的安排”里很关键的一块——它让 Agent 能以统一、可组合的方式接入越来越多的外部能力，而不必为每个能力重造轮子。

它也带来新的责任：统一接入意味着更要管好“哪些能借、谁能借、借了能干到什么程度”——这正是 05.5 权限与第九讲安全要接住的。

## 常见误区

第一，把 MCP 当成一个工具或模型。它是协议（接法），不是干活的东西。

第二，以为接了 MCP 就自动安全。统一接入反而更要管权限和边界。

第三，分不清 tools 和 resources。会产生动作、改状态的是 tool；拿来读、当资料用的是 resource。

## 小练习

判断下面几样，按 MCP 该挂成 tool、resource 还是 prompt：

1. “在数据库里新增一条订单。”
2. “这份公司风格指南，供模型写文案时参考。”
3. “一段写好的‘代码评审’标准提问模板。”
