> 承上：第十讲走到岔路口，阿行望着一座灯火通明的城，说那像是一大群人各司其职、合伙办大事。老向导说，那是会分工的城邦。这一讲就进城了。新学徒阿筹要跟着老把头，学怎么带一支工队。

阿筹一开始什么都想自己干：探路、采料、施工、记账、验收，一肩挑。结果一桩跨城的大工程下来，他累垮了，活还样样半生不熟。

老把头把他叫来:“傻小子，这种活儿，从来不是一个人扛的。”他把工队分了组：探路的只管探路，采料的只管采料，施工的各守一摊，账房专管算账，还有专门挑错验收的。“各干各的擅长的，”老把头说,“几摊还能同时开工，比你一个人从头干到尾，又快又好。”

阿筹不服:“可这么多人，不更乱吗？”老把头笑:“分工是本事，把分了工的人拢到一处不出乱子，是更大的本事——这正是你接下来要学的。”

## 概念揭晓

老把头分组干活的道理，就是**多 Agent（multi-agent）**系统的出发点：用多个各有专长、可并行、上下文相互隔离的 Agent，去完成单个 Agent 扛不动的复杂任务。

“各干各擅长的”，是**专家角色（specialization）**：让每个 Agent 专注一类子任务（检索、写代码、审查、规划），各自的提示词、工具、上下文都为这件事优化。

“几摊同时开工”，是**并行（parallelism）**：相互独立的子任务可以同时跑，缩短总时长。

“各守一摊、互不搅和”，是**上下文隔离（context isolation）**：每个 Agent 只看自己该看的，避免互相干扰、也避免一个上下文被撑爆（第三、四讲的窗口预算）。

“拆开再拢到一处”，是**编排（orchestration）**：把分工的 Agent 组织起来、协调好，这是 11.2 的主题。

## 单 Agent 在哪撞墙

一个 Agent 把所有事一肩挑，会遇到几堵墙：

- **上下文爆掉**：一个超大任务的全部资料、工具、历史，塞不进一个窗口（第三讲）。
- **样样不精**：一个通用提示词很难同时把检索、编码、审查都做到最好。
- **串行太慢**：本可以并行的活，被迫一件件做。
- **难以审视**：一长串混在一起的推理，出错难定位（第八讲）。

把任务拆给多个专精的 Agent，正是对症下药：各自上下文更小更聚焦、各自更专业、能并行、过程更可观测。

## 多 Agent 的四个好处

- **分工专精**：每个 Agent 为一类活优化，质量更高。
- **上下文隔离**：各自只装自己那摊，窗口更省、更少互相污染。
- **并行提速**：独立子任务同时跑。
- **可组合、可审视**：像搭积木一样组合角色，每个角色的产出可单独评测（第八讲）。

这把前面几讲的能力（工具、上下文、评测、安全）抬到了“一群 Agent 协作”的层面，也就是“AI 工程”。

## 它不是越多越好

但要立刻泼一盆冷水（呼应第五讲“工具不是越多越好”）：多 Agent 会引入新的成本和复杂度——

- 多一个 Agent，多一份 token 和延迟。
- Agent 之间要交接、要同步，沟通本身就有开销和出错可能。
- 协调越复杂，越难调试、越容易“三个和尚没水喝”。

所以多 Agent 是一种**有代价的强力工具**，不是默认选项。这条权衡线会贯穿 11.5（成本）和整讲。

## 什么时候才该上多 Agent

一个实用的判断：当任务**真的大到、杂到单 Agent 扛不动**时才拆——

- 子任务之间**相对独立**，拆开收益大于协调成本。
- 不同子任务需要**明显不同的专长/工具/上下文**。
- 能**并行**，且并行带来的提速值得多花的钱。

反过来，能用“一个 Agent + 好的提示和工具”解决的，就别为了“显得高级”硬上多 Agent——简单往往更可靠（这也是 Anthropic《Building Effective Agents》反复强调的）。

## 常见误区

第一，一上来就堆一堆 Agent，以为越多越强。复杂度和成本会反噬。

第二，把本该一个 Agent 顺手做的事，硬拆成多角色，徒增交接开销。

第三，只看到分工的好处，看不到协调、成本、调试的代价。

## 小练习

下面三个任务，判断该用单 Agent 还是多 Agent：

1. “把一段文字翻译并润色。”
2. “调研一个行业：分头查 20 个来源、各自总结、再合成一份带引用的报告。”
3. “回答一个简单的产品使用问题。”
