这次问题表面上很简单：抽卡弹窗里应该先播放一段出卡动画，单抽展示一张卡，十连展示十张卡，然后再进入可交互的结果页。

但实际调试时，它变成了一个很典型的前端动效排障陷阱：同一个“看起来透明”的现象，背后可能是容器尺寸、Lottie 图片资源、离线资源路径、base64 格式、调试环境和状态切换时间共同造成的。

最后真正收敛下来的结论是：

```text
AnimaX 渲染 PNG base64 可以，JPEG base64 不行。
出卡 Lottie 里的卡图应该稳定注入 PNG data URL，并保持 data asset 的解析方式。
```

这篇文章把整个过程复盘一下。重点不是“某一行代码怎么改”，而是为什么这个问题会卡很久，以及以后遇到类似问题应该怎么拆。

## 背景：Lottie 不是普通图片

抽卡页的结果弹窗有两个阶段：

1. 出卡动画阶段：用 `animax-view` 播放 Lottie。
2. 结果展示阶段：用普通 Lynx 视图展示卡面、标题、按钮、轮播和翻卡交互。

普通结果页里的卡图使用的是平台的 `<image>` 组件。它能加载图片、触发错误回调，也能配合已有的图片降级和重定向逻辑。

但 Lottie 不一样。Lottie 文件里有自己的 `assets`，卡图需要被写进 Lottie JSON 的图片资源里。播放器内部怎么加载这些图片，不等同于普通 `<image>`。

这就是第一个关键误区：

```text
DOM 图片能显示，不代表 Lottie 内部图片也能显示。
```

## 第一次改法：把真实卡图 URL 注入 Lottie

最直观的实现方式是：抽到哪张卡，就把这张卡的图片 URL 注入到 Lottie 的 `assets[].p` 里。

思路没问题，问题在于运行环境。

在本地调试里，页面模板可能来自本地 dev server，但静态资源并不一定也从本地走。某些移动端调试环境会把资源路径重写成离线包或 CDN 兜底路径。

于是就出现了一个很迷惑的现象：

- 本地 URL 用 `curl` 看是 `200`。
- 设备运行时实际请求的离线/CDN URL 是 `404`。
- 普通 `<image>` 可能还能走自己的兜底逻辑。
- Lottie 内部的图片资源失败后，不一定给你一个清晰的错误。

更麻烦的是，原始 Lottie 里的图片本来就是透明占位图。真实图片加载失败时，画面不是“红叉”或者“加载失败”，而是仍然透明。

所以第一次改法的问题是：

```text
把 Lottie 内部图片资源当成普通图片资源处理了。
```

## 第二次改法：怀疑尺寸、层级和播放器容器

画面透明时，最容易先怀疑容器没尺寸。

这一步其实有价值。因为 Lynx 不是浏览器，`height: 100%`、绝对定位、视口高度这些细节都可能导致元素算不出尺寸。于是我们给 `animax-view` 明确设置宽高，并加了半透明背景来判断容器是否真的在屏幕上。

这个排查结论是：

```text
animax-view 容器是存在的，尺寸也是有的。
```

这一步排除了“容器没挂上”和“高度为 0”。但它没有解决问题，因为透明的是 Lottie 内部要画的卡图，不是外层元素。

这里的教训是：调试背景只能证明容器存在，不能证明 Lottie 内容渲染成功。

## 第三次改法：把卡图转成 base64 内嵌

既然外链资源不稳定，下一步就是把图片直接内嵌进 Lottie。

这方向是对的。Lottie 图片资源里常见的两个字段很关键：

```json
{
  "u": "",
  "p": "data:image/...",
  "e": 1
}
```

`p` 是图片地址或 data URL，`e` 表示它是嵌入资源。只要走 data URL，就不应该再依赖调试环境的离线资源路径、CDN 兜底、跨域策略和图片重定向。

但这里踩了第二个坑：为了控制体积，最开始生成的是 JPEG base64。

结果是：

```text
base64 确实内嵌了。
资源也不走外链了。
但 AnimaX 渲染 JPEG base64 仍然透明。
```

这也是最容易卡住的地方。因为从代码角度看，JSON 里确实有 `data:image/jpeg;base64,...`，`e` 也设置了，Lottie 也挂上了。直觉上会觉得“base64 方案已经生效了，为什么还透明？”

真正的问题是播放器兼容性：

```text
这个播放器链路下，PNG base64 能渲染，JPEG base64 不能稳定渲染。
```

所以“base64 不行”这个结论是不准确的。准确说法是：

```text
JPEG data URL 不行，PNG data URL 可以。
```

## 第四次干扰：按钮图片也变成 fallback

中间还出现过另一个现象：底部按钮图片不显示，变成了兜底文字按钮。

这个现象和出卡动画透明很像，但不是同一个层级的问题。

按钮是普通 `<image>`。它失败的原因是调试环境把本地静态资源重写到了离线/CDN 兜底路径，而这些新资源还没有发布到那条路径上，所以运行时加载失败，触发了代码里的 fallback。

这个问题提醒我们：调试环境里“模板来自本地”不等于“资源也来自本地”。

但它也造成了干扰。因为当按钮和 Lottie 都不显示时，很容易把所有问题归为“启动方式不对”或“资源路径不对”。

事实上，更准确的拆分是：

| 现象 | 直接原因 | 层级 |
| --- | --- | --- |
| 按钮图片变 fallback | 运行时资源路径走到未发布的离线/CDN 地址 | 普通图片资源 |
| Lottie 外链卡图透明 | Lottie 内部图片资源也依赖了不稳定外链 | Lottie 图片 asset |
| Lottie base64 仍透明 | JPEG data URL 不被播放器稳定渲染 | 图片编码兼容性 |

它们长得像，但不是一个 bug。

## 第五次干扰：兜底时间从 1.4 秒变成 8 秒

出卡动画播放完后，页面会切到结果态。为了防止播放器回调不触发，代码里有一个兜底定时器。

原本这个兜底接近动画时长，大约 1.4 秒。后来为了观察动画，它被临时拉长到 8 秒。

这个改动本身可以理解，但它放大了体感问题：

```text
如果 Lottie 内容透明，1.4 秒后还能进入结果页。
如果兜底变成 8 秒，用户会看到 8 秒空白动画态。
```

于是“动画透明”又被放大成了“页面卡住”“总数不显示”“结果不出现”。

这里还有另一个分支问题：十连动画阶段本来就没有渲染“恭喜获得 10 张卡”的 DOM 文案，这个文案只在后面的结果轮播态里出现。动画态透明，再叠加 8 秒兜底，就更像是整套结果 UI 都没出来。

## 为什么会卡这么久

这类问题最难的地方，不是某个知识点很深，而是多个变量同时给出同一种视觉结果：透明。

这次至少有六个变量混在一起：

1. `animax-view` 容器是否有尺寸。
2. Lottie 原始 asset 是否只是透明占位。
3. 外链图片在移动端播放器内部是否能加载。
4. 调试环境是否把静态资源重写到离线/CDN 路径。
5. base64 的 MIME 类型是 PNG 还是 JPEG。
6. 动画态到结果态的兜底时间是否过长。

任何一个失败，肉眼看到的都可能是“没动画”。

更糟的是，有些验证会给出误导性的半真结论：

- 普通图片能显示，不代表 Lottie 内部图片能显示。
- 本地资源 `200`，不代表设备运行时请求的资源也是 `200`。
- base64 已经写进 JSON，不代表播放器支持这种图片编码。
- 容器有红色背景，不代表 Lottie 内容已经渲染。
- 切到结果页正常，不代表出卡动画正常。

这些半真结论叠在一起，就会让排查路径来回摆动。

## 最终稳定方案

最后稳定的方向很明确：

1. 出卡 Lottie 不优先注入外链卡图。
2. 卡图映射使用内嵌 base64。
3. base64 使用 PNG，不使用 JPEG。
4. Lottie asset 保持 `u: ""`、`p: "data:image/png;base64,..."`、`e: 1`。
5. 为了控制包体，先降采样，再尝试 palette PNG 或量化压缩。
6. 单抽先验证一张卡，确认播放器能渲染，再扩展到 28 张全量卡面。

这里的体积取舍也要现实一点。PNG 肯定比 JPEG 大，但如果 180px 宽的 28 张卡图大约几 MB，作为验证方案是可以接受的。先证明渲染链路正确，再优化体积。

不要一上来同时做这些事：

- 换图片格式；
- 换资源路径；
- 改播放器参数；
- 改动画时长；
- 改结果态 UI；
- 改调试启动方式。

同时改太多变量，只会让下一次透明时不知道是谁导致的。

## 下次遇到类似问题，按这个顺序查

我会把这类问题拆成一个固定清单。

第一步，确认容器：

```text
给播放器容器加临时背景。
确认位置、宽高、层级都正确。
```

第二步，确认最小可渲染资源：

```text
不要先注入业务图。
先用一张已知可显示的 PNG data URL。
```

第三步，确认图片格式矩阵：

```text
PNG data URL 是否显示？
JPEG data URL 是否显示？
本地 URL 是否显示？
离线/CDN URL 是否显示？
```

第四步，确认 Lottie asset 字段：

```text
data URL: u=""，p=data URL，e=1
外链 URL: u/path 与 e 的语义要单独验证
```

第五步，确认调试环境真实请求：

```text
不要只看源码里的 src。
要看设备运行时最终请求的 URL。
```

第六步，控制状态切换：

```text
动画兜底时间不要随便拉长。
拉长可以用于观察，但要标注清楚，否则会把透明问题放大成页面卡住。
```

## 总结

这次问题卡住很久，本质上是因为它不是一个单点 bug，而是一串兼容性问题叠在一起。

最开始以为是外链资源问题，后来以为是容器尺寸问题，再后来以为 base64 也不行。最后才拆清楚：

```text
外链资源确实不稳定。
容器尺寸已经不是主因。
base64 方向是对的。
真正卡住 base64 方案的是 JPEG 编码。
PNG base64 才是当前播放器链路下更稳的选择。
```

这类动效问题最怕“看起来都一样”。透明、空白、没播放、没切态，在截图上很难区分。

真正有效的办法是一次只验证一个变量，用最小可复现资源把播放器链路先打通，再把业务资源、包体优化和交互状态一点点加回来。
