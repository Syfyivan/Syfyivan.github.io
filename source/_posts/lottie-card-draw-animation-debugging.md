这次问题表面上很简单：抽卡弹窗里应该先播放一段出卡动画，单抽展示一张卡，十连展示十张卡，然后再进入可交互的结果页。

但实际调试时，它变成了一个很典型的前端动效排障陷阱：同一个“看起来透明”的现象，背后可能是容器尺寸、Lottie 图片资源、离线资源路径、base64 格式、调试环境和状态切换时间共同造成的。

最后真正收敛下来的结论是：

```text
AnimaX 渲染 PNG base64 可以，JPEG base64 不行。
出卡 Lottie 里的卡图应该稳定注入 PNG data URL，并保持 data asset 的解析方式。
```

但这个结论是最后才得到的。中间真正耗时间的地方，不是“不知道 PNG 比 JPEG 稳”，而是每一步都有一套看起来成立的解释，而且这些解释都能解释一部分现象。

这篇文章把整个过程复盘一下。重点不是“某一行代码怎么改”，而是为什么这个问题会卡很久，为什么好几种改法都像是对的又像是错的，以及以后遇到类似问题应该怎么拆。

## 先说清楚：它到底复杂在哪里

如果只看最终修法，这个问题像这样：

```text
JPEG base64 不显示 -> 换成 PNG base64 -> 好了
```

这当然太简单了。真实问题更像这样：

```text
UI 状态机
  -> 决定当前显示 Lottie 动画态还是 DOM 结果态

Lottie JSON
  -> 原始图片 asset 是透明占位
  -> 运行时要把业务卡图注入进去

图片资源系统
  -> 普通 image 能走重定向、兜底、错误回调
  -> Lottie 内部 asset 不一定走同一套逻辑

调试环境
  -> 模板可能来自本地
  -> 图片却可能被改写到离线包/CDN 兜底路径

播放器兼容性
  -> data URL 看起来都叫 base64
  -> 但 PNG data URL 和 JPEG data URL 在播放器里不是同一个结果

临时调试改动
  -> 为了观察把兜底时间拉长
  -> 结果把“透明一瞬间”放大成“页面长时间空白”
```

这几个系统的边界同时交叉在一个弹窗里，所以它不是一个单点 bug。每个错误链路失败时，肉眼看到的都是同一个东西：透明、空白、没动画。

最折磨人的就是这一点：不同根因长得一样。

## 真正的业务状态机

抽卡结果不是单个视图，而是一个短状态机。

可以把它简化成这样：

```text
点击抽卡
  -> 得到抽卡结果
  -> 进入 reveal 动画态
  -> Lottie 播放完成，或者兜底 timer 到点
  -> 进入 DOM 结果态
```

单抽和十连又不完全一样：

```text
单抽：
  reveal Lottie
    -> 单张大卡 DOM
    -> 可下载 / 可翻卡 / 可看掉落

十连：
  reveal Lottie
    -> 横滑大卡轮播 DOM
    -> 单张卡详情、下载、掉落、关闭
```

这意味着“没看到东西”有很多解释：

- Lottie 根本没挂上；
- Lottie 挂上了，但没有尺寸；
- Lottie 有尺寸，但内部图片透明；
- Lottie 播放了，但很快切到结果态，所以肉眼没看到；
- Lottie 没触发完成回调，停在动画态；
- 结果态有文案，但动画态本来没有文案；
- 临时 timer 被拉长，导致透明态停留更久。

所以这不是“动画不显示”一句话能描述清楚的。更准确的问题应该拆成：

```text
现在停在哪个状态？
这个状态是否应该显示 DOM 文案？
播放器容器是否存在？
Lottie 内部 asset 是否被替换？
替换后的 asset 是否能被播放器解码？
完成回调或兜底 timer 是否能把状态推进？
```

只有把这些问题拆开，后面的证据才不会互相污染。

## 背景：Lottie 不是普通图片

抽卡页的结果弹窗有两个阶段：

1. 出卡动画阶段：用 `animax-view` 播放 Lottie。
2. 结果展示阶段：用普通 Lynx 视图展示卡面、标题、按钮、轮播和翻卡交互。

普通结果页里的卡图使用的是平台的 `<image>` 组件。它能加载图片、触发错误回调，也能配合已有的图片降级和重定向逻辑。

但 Lottie 不一样。Lottie 文件里有自己的 `assets`，卡图需要被写进 Lottie JSON 的图片资源里。播放器内部怎么加载这些图片，不等同于普通 `<image>`。

这就是第一个关键误区：

```text
DOM 图片能显示，不代表 Lottie 内部图片也能显示。
```

## 第一次改法：把真实卡图 URL 注入 Lottie

最直观的实现方式是：抽到哪张卡，就把这张卡的图片 URL 注入到 Lottie 的 `assets[].p` 里。

思路没问题，问题在于运行环境。

这个方案当时看起来非常合理，因为普通卡面本来就能显示。既然 DOM 结果态里的卡图能显示，那把同一张图塞进 Lottie，按理说也应该显示。

问题正出在“按理说”。

在本地调试里，页面模板可能来自本地 dev server，但静态资源并不一定也从本地走。某些移动端调试环境会把资源路径重写成离线包或 CDN 兜底路径。

于是就出现了一个很迷惑的现象：

- 本地 URL 用 `curl` 看是 `200`。
- 设备运行时实际请求的离线/CDN URL 是 `404`。
- 普通 `<image>` 可能还能走自己的兜底逻辑。
- Lottie 内部的图片资源失败后，不一定给你一个清晰的错误。

更麻烦的是，原始 Lottie 里的图片本来就是透明占位图。真实图片加载失败时，画面不是“红叉”或者“加载失败”，而是仍然透明。

所以第一次改法的问题是：

```text
把 Lottie 内部图片资源当成普通图片资源处理了。
```

这一步真正得到的结论不是“外链一定不行”，而是更窄的一句话：

```text
在当前调试链路里，不能假设 Lottie 内部外链 asset 和普通 image 使用同一套加载路径。
```

如果把这个结论说得太宽，就会误伤后面的判断。因为外链失败是一条真实链路，但它不是唯一链路。

## 第二次改法：怀疑尺寸、层级和播放器容器

画面透明时，最容易先怀疑容器没尺寸。

这一步其实有价值。因为 Lynx 不是浏览器，`height: 100%`、绝对定位、视口高度这些细节都可能导致元素算不出尺寸。于是我们给 `animax-view` 明确设置宽高，并加了半透明背景来判断容器是否真的在屏幕上。

这个排查结论是：

```text
animax-view 容器是存在的，尺寸也是有的。
```

这一步排除了“容器没挂上”和“高度为 0”。但它没有解决问题，因为透明的是 Lottie 内部要画的卡图，不是外层元素。

这里的教训是：调试背景只能证明容器存在，不能证明 Lottie 内容渲染成功。

这也是一个很典型的“局部证据”。它能证明一件事：

```text
播放器节点在屏幕上。
```

但它不能证明下面这些事：

```text
Lottie JSON 被成功解析。
Lottie 图片 asset 被成功替换。
替换后的图片被成功加载。
图片格式被播放器支持。
动画完成回调会被触发。
```

如果把“红底出现”误读成“播放器没问题”，排查就会走偏。

## 第三次改法：把卡图转成 base64 内嵌

既然外链资源不稳定，下一步就是把图片直接内嵌进 Lottie。

这方向是对的。Lottie 图片资源里常见的两个字段很关键：

```json
{
  "u": "",
  "p": "data:image/...",
  "e": 1
}
```

`p` 是图片地址或 data URL，`e` 表示它是嵌入资源。只要走 data URL，就不应该再依赖调试环境的离线资源路径、CDN 兜底、跨域策略和图片重定向。

但这里踩了第二个坑：为了控制体积，最开始生成的是 JPEG base64。

这一步为什么会这么容易踩坑？因为 JPEG 是一个很自然的工程选择。

卡图是照片/插画类资源，PNG 会更大，JPEG 更省体积。把 20 多张卡面塞进一个前端包里，第一反应当然是压成 JPEG。尤其当目标是“先让 Lottie 不依赖外链”时，JPEG base64 看起来是很合理的折中。

结果是：

```text
base64 确实内嵌了。
资源也不走外链了。
但 AnimaX 渲染 JPEG base64 仍然透明。
```

这也是最容易卡住的地方。因为从代码角度看，JSON 里确实有 `data:image/jpeg;base64,...`，`e` 也设置了，Lottie 也挂上了。直觉上会觉得“base64 方案已经生效了，为什么还透明？”

真正的问题是播放器兼容性：

```text
这个播放器链路下，PNG base64 能渲染，JPEG base64 不能稳定渲染。
```

所以“base64 不行”这个结论是不准确的。准确说法是：

```text
JPEG data URL 不行，PNG data URL 可以。
```

这里面还有一个更隐蔽的点：MIME 类型也不是装饰。

`data:image/jpeg;base64,...` 和 `data:image/png;base64,...` 都是 data URL，但播放器内部很可能走了不同的解码分支。普通浏览器能显示 JPEG，不代表这个播放器的 Lottie image asset 分支也支持 JPEG data URL。

这就是为什么最终结论必须说完整：

```text
不是“base64 方案不行”。
不是“尺寸不行”。
不是“外链不行之后只能放弃 Lottie”。
而是“当前 AnimaX/Lottie 图片 asset 链路下，PNG data URL 是可行路径，JPEG data URL 会透明”。
```

少说任何一半，都会让下一个人重新踩坑。

## 第四次干扰：按钮图片也变成 fallback

中间还出现过另一个现象：底部按钮图片不显示，变成了兜底文字按钮。

这个现象和出卡动画透明很像，但不是同一个层级的问题。

按钮是普通 `<image>`。它失败的原因是调试环境把本地静态资源重写到了离线/CDN 兜底路径，而这些新资源还没有发布到那条路径上，所以运行时加载失败，触发了代码里的 fallback。

这个问题提醒我们：调试环境里“模板来自本地”不等于“资源也来自本地”。

但它也造成了干扰。因为当按钮和 Lottie 都不显示时，很容易把所有问题归为“启动方式不对”或“资源路径不对”。

事实上，更准确的拆分是：

| 现象 | 直接原因 | 层级 |
| --- | --- | --- |
| 按钮图片变 fallback | 运行时资源路径走到未发布的离线/CDN 地址 | 普通图片资源 |
| Lottie 外链卡图透明 | Lottie 内部图片资源也依赖了不稳定外链 | Lottie 图片 asset |
| Lottie base64 仍透明 | JPEG data URL 不被播放器稳定渲染 | 图片编码兼容性 |

它们长得像，但不是一个 bug。

这一步卡人的地方在于，它是一个“相关但不同根”的问题。

它和出卡透明共享同一个上游风险：调试环境里的资源路径会被重写。

但它的失败位置不同：

```text
按钮失败在普通 image 资源加载。
Lottie 失败在播放器内部 image asset 加载。
JPEG base64 失败在播放器内部图片解码。
```

如果只看截图，它们都叫“不显示”。如果看系统边界，它们是三个层级。

## 第五次干扰：兜底时间从 1.4 秒变成 8 秒

出卡动画播放完后，页面会切到结果态。为了防止播放器回调不触发，代码里有一个兜底定时器。

原本这个兜底接近动画时长，大约 1.4 秒。后来为了观察动画，它被临时拉长到 8 秒。

这个改动本身可以理解，但它放大了体感问题：

```text
如果 Lottie 内容透明，1.4 秒后还能进入结果页。
如果兜底变成 8 秒，用户会看到 8 秒空白动画态。
```

于是“动画透明”又被放大成了“页面卡住”“总数不显示”“结果不出现”。

这里还有另一个分支问题：十连动画阶段本来就没有渲染“恭喜获得 10 张卡”的 DOM 文案，这个文案只在后面的结果轮播态里出现。动画态透明，再叠加 8 秒兜底，就更像是整套结果 UI 都没出来。

这类临时调试改动很常见，也很危险。

当一个 session 为了观察动画，把兜底时间拉长；另一个 session 正在判断“为什么结果文案不显示”；第三个现象又是 Lottie asset 透明，这三个信息合在一起，就会形成一个错误直觉：

```text
是不是结果页没渲染？
是不是状态没切？
是不是按钮挡住了？
是不是总数文案丢了？
```

但实际可能只是：

```text
状态还停在 reveal；
reveal 本来没有总数文案；
Lottie 内部图片又透明；
兜底时间还被拉长了。
```

所以调试动效时，临时参数必须被当成变量记录下来。否则它会把一个渲染问题伪装成状态机问题。

## 更真实的时间线

如果把过程按“当时相信什么、后来为什么推翻”写，会更接近真实调试。

### 阶段一：以为是外链资源问题

现象是 Lottie 透明，但 DOM 卡图能显示。

当时最合理的解释是：Lottie 内部图片走外链，而播放器的资源加载能力不如普通 image。这个方向是对的，因为运行时确实存在资源重写和 404。

但它不能解释后来的现象：即使把图片变成 base64，仍然透明。

所以外链问题是真的，但不是全因。

### 阶段二：以为是容器尺寸问题

Lynx 环境下，容器高度、绝对定位、视口单位都可能出问题，所以给播放器加明确尺寸和调试背景是必要的。

这一步排除了容器问题，却没有让动画出现。

所以尺寸问题是必须排查的疑点，但不是主因。

### 阶段三：以为 base64 方案也不行

base64 已经写进 Lottie JSON，外链依赖看起来也去掉了，但画面仍然透明。

这时很容易得出错误结论：

```text
AnimaX 不支持 base64 图片。
```

后来用 PNG base64 对照，才发现这个结论太粗了。真正不行的是 JPEG base64。

### 阶段四：以为启动方式又出问题

按钮图片 fallback、Lottie 透明、资源 URL 404 同时出现时，很容易重新怀疑 dev server 或 HDT 启动方式。

启动方式确实会影响资源路径，但对于已经内嵌的 base64 方案，启动方式不应该再决定图片是否能加载。于是问题又被收敛回播放器对 data URL 格式的支持。

### 阶段五：以为结果态文案缺失是同一个问题

十连动画态没有总数文案，结果态才有。再叠加 8 秒兜底，就像总数文案也坏了。

但这其实是 UI 状态设计和 Lottie 透明叠加出来的错觉，不是同一层 bug。

这个时间线说明：每次判断都不是完全错，而是只解释了一部分现象。问题卡住，是因为我们需要把“部分正确的解释”继续削窄，直到它只覆盖自己该覆盖的范围。

## 为什么会卡这么久

这类问题最难的地方，不是某个知识点很深，而是多个变量同时给出同一种视觉结果：透明。

这次至少有六个变量混在一起：

1. `animax-view` 容器是否有尺寸。
2. Lottie 原始 asset 是否只是透明占位。
3. 外链图片在移动端播放器内部是否能加载。
4. 调试环境是否把静态资源重写到离线/CDN 路径。
5. base64 的 MIME 类型是 PNG 还是 JPEG。
6. 动画态到结果态的兜底时间是否过长。

任何一个失败，肉眼看到的都可能是“没动画”。

更糟的是，有些验证会给出误导性的半真结论：

- 普通图片能显示，不代表 Lottie 内部图片能显示。
- 本地资源 `200`，不代表设备运行时请求的资源也是 `200`。
- base64 已经写进 JSON，不代表播放器支持这种图片编码。
- 容器有红色背景，不代表 Lottie 内容已经渲染。
- 切到结果页正常，不代表出卡动画正常。

这些半真结论叠在一起，就会让排查路径来回摆动。

真正拖慢进度的是这三类“半真结论”。

第一类是环境半真：

```text
本地模板加载成功。
```

这句话是真的，但它不能推出“所有静态资源都从本地加载成功”。

第二类是组件半真：

```text
普通 image 能显示。
```

这句话也是真的，但它不能推出“Lottie 内部 image asset 也能显示”。

第三类是格式半真：

```text
图片已经变成 base64。
```

这句话仍然是真的，但它不能推出“播放器支持这个 MIME 类型的 data URL”。

排查变慢，就是因为这些话都不是谎话。它们只是证明范围太小，而我们一开始把它们解释得太大。

## 这次真正应该沉淀的不是修法，而是验证矩阵

这类问题不能只记一个“以后用 PNG”的结论。因为下一次可能换成别的播放器、别的资源管线、别的调试环境。

更值得沉淀的是验证矩阵：

| 变量 | 要验证的问题 | 不能偷换成什么结论 |
| --- | --- | --- |
| 容器 | 节点是否存在、尺寸是否正确 | Lottie 内容一定没问题 |
| 原始 Lottie | asset 是否透明占位、图层是否引用正确 | 业务图一定注入成功 |
| 外链 URL | 设备最终请求是否 200 | 本地 curl 200 就够了 |
| data URL | `e:1`、`u/p` 字段是否符合播放器语义 | 只要是 base64 就一定能显示 |
| 图片格式 | PNG/JPEG/WebP 是否分别支持 | 浏览器支持等于播放器支持 |
| 状态机 | 当前是 reveal 还是 result | 页面没文案等于文案丢了 |
| timer | 兜底是否被临时拉长 | 停留久等于状态没切 |

这个矩阵比最终代码更重要。代码会变，播放器会变，但这种拆法可以复用。

## 相关知识点

这次问题背后牵涉的知识点不少。单独拿出来看，每个都不算特别难；难的是它们在一个动效链路里同时出现。

### 1. Lottie 的 image asset 是什么

Lottie 本质上是一份动画描述 JSON。它不只是“每一帧一张图”，而是包含图层、变换、关键帧、预合成、矢量图形和图片资源。

图片资源通常放在 `assets` 里。一个简化的 image asset 像这样：

```json
{
  "id": "i_0",
  "w": 258,
  "h": 360,
  "u": "",
  "p": "data:image/png;base64,...",
  "e": 1
}
```

几个字段很关键：

| 字段 | 含义 |
| --- | --- |
| `id` | 图层通过这个 id 引用图片 |
| `w/h` | 设计资源的宽高信息 |
| `u` | 资源目录或 URL 前缀 |
| `p` | 图片文件名、URL 或 data URL |
| `e` | 是否是嵌入资源，常见语义是 data URL 需要设为 `1` |

所以替换 Lottie 图片，不是随便把 JSON 里的字符串换一下就完了。你要确认：

```text
图层 refId 引用的是哪个 asset？
你替换的是不是这个 asset？
p/u/e 的组合是否符合播放器语义？
替换后的图片格式是否被播放器支持？
```

如果 refId 对不上，图片不会出现；如果 `e` 语义不对，播放器可能按外链去解析；如果图片格式不支持，结果仍然透明。

### 2. 透明占位图为什么会误导排查

很多设计导出的 Lottie 会先放一张 1px 透明图作为占位，然后运行时再替换。

这有一个副作用：失败时不会明显失败。

如果原始 asset 是透明图，那么真实图片没加载成功时，播放器仍然能正常播放动画，只是播放的是透明图片。视觉上就是：

```text
容器在。
动画也许在播。
但你什么都看不到。
```

这和“播放器没初始化”“容器没尺寸”“状态没切”长得非常像。

所以遇到透明问题时，要第一时间确认原始 asset 是不是透明占位。如果是，后面所有“没显示”的证据都要重新解释。

### 3. Data URL 不是一种格式

我们平时会粗略地说“转 base64”，但浏览器或播放器看到的不是“base64”三个字，而是一整个 data URL：

```text
data:image/png;base64,...
data:image/jpeg;base64,...
data:image/webp;base64,...
```

这里至少包含三层信息：

1. 资源是内嵌的，不是外链。
2. 资源 MIME 类型是什么。
3. 后面的内容用 base64 编码。

所以 `data:image/png;base64,...` 和 `data:image/jpeg;base64,...` 不是同一种资源。它们只是都用了 base64 这个编码方式。

这次最容易误判的点就在这里：

```text
JPEG base64 不显示
  != base64 不显示
  != data URL 不显示
  != Lottie 不支持内嵌图片
```

准确结论应该保留 MIME 类型：

```text
当前播放器链路支持 PNG data URL，但不稳定支持 JPEG data URL。
```

### 4. PNG、JPEG、WebP 的差别不能只看体积

前端工程里常见图片格式大概可以这样理解：

| 格式 | 特点 | 常见用途 | 这次链路里的风险 |
| --- | --- | --- | --- |
| PNG | 无损，支持透明，体积较大 | UI 切图、透明图、图标、需要精确边缘的图 | 包体可能变大 |
| JPEG | 有损，不支持透明，体积较小 | 照片、复杂插画 | 某些 Lottie 播放器的 data URL 分支可能不支持 |
| WebP | 压缩率好，可支持透明 | 现代 Web 图片 | 移动端/播放器兼容性要单独确认 |

正常网页里，JPEG 是很稳的格式。但这里不是普通网页图片，而是 Lottie 播放器内部 image asset。它是否支持某个格式，要看播放器实现。

所以格式选择不能只问：

```text
哪个体积小？
```

还要问：

```text
这个播放器的这个资源入口支持吗？
这个入口对 data URL 和外链 URL 支持是否一样？
这个入口对 PNG/JPEG/WebP 支持是否一样？
```

这也是为什么 PNG 体积大一些，但在这类动效链路里反而可能是更稳的第一选择。

### 5. Base64 会增加体积

base64 不是压缩算法。它只是把二进制数据编码成文本，方便放进 JSON、HTML 或 CSS。

代价是体积会变大，常见经验值是原始二进制体积增加约三分之一。

例如一张 100KB 的 PNG，变成 base64 文本后可能接近 133KB，再加上 `data:image/png;base64,` 这一段前缀。

所以内嵌 base64 的取舍是：

| 优点 | 缺点 |
| --- | --- |
| 不依赖外部资源请求 | 增大 JS/JSON 体积 |
| 避免离线/CDN 路径错误 | 无法单独缓存图片 |
| 避免某些跨域或重定向问题 | 更新任意图片都要更新包 |
| 对 Lottie 注入更可控 | 大量图片会影响解析和内存 |

这次选择 base64，不是因为它永远更好，而是因为它能把资源路径这个变量先拿掉。等播放器链路确认后，再考虑包体优化。

### 6. PNG 也可以压缩：降采样、调色板和量化

PNG 体积大，不代表只能接受原始大图。

常见优化手段有三类：

```text
降采样：把图片尺寸缩小，例如宽度从 360px 降到 180px。
调色板 PNG：把真彩色 PNG 转成 256 色以内的 indexed PNG。
量化压缩：用 pngquant 一类工具减少颜色数量并优化压缩。
```

对抽卡动效来说，Lottie 阶段的卡图通常不是最终可下载高清图。它只是在动画里飞出来、缩放、停留一小段时间。这个阶段可以接受更小尺寸。

更合理的策略是：

```text
结果态 DOM 卡图：用清晰图。
Lottie 动画态卡图：用降采样后的 PNG。
```

这样既能保证动画稳定，也不至于把包体推得太高。

### 7. 普通 image 和播放器内部图片不是一回事

普通 `<image>` 组件通常会接入平台图片能力，比如：

- 图片重定向；
- 降级图；
- 错误回调；
- 缓存；
- 解码优化；
- 不同设备的图片质量策略。

但 Lottie 播放器内部的 image asset 可能不走这些能力。它可能只是播放器自己解析 JSON，然后自己加载图片。

所以这两个结论不能互推：

```text
普通 image 能显示 -> Lottie 内部一定能显示
Lottie 内部不能显示 -> 普通 image 也一定不能显示
```

它们是两条不同的渲染链路。

这次排查里，结果态卡图正常，不能证明出卡动画 Lottie 里的卡图正常。底部按钮 fallback，也不能直接证明 Lottie 的 JPEG base64 有问题。必须按链路分开看。

### 8. 离线资源、CDN 兜底和本地 dev server 的关系

移动端页面调试经常有一个反直觉点：

```text
模板来自本地 dev server，不代表所有静态资源也来自本地 dev server。
```

有些调试环境为了模拟线上，会保留离线包、CDN 兜底、资源前缀重写等逻辑。于是你会看到：

```text
template.js 来自本地
image src 运行时被改写到离线/CDN 地址
```

如果这张图片是本地新增的，还没有发布到离线/CDN，那么本地文件存在、dev server 能返回 200，也不代表设备最终能拿到。

正确排查方式是看运行时最终 URL：

```text
源码里的 import 是什么？
打包后资源路径是什么？
设备 DOM 或日志里的最终 src 是什么？
这个最终 src 请求返回多少？
```

只看源码路径，会漏掉中间重写。

### 9. CORS 不应该被过早当成原因

前端资源加载失败时，很容易第一反应是 CORS。

但这次问题里，CORS 并不是最应该优先猜的原因。因为真实证据指向的是：

```text
离线/CDN URL 404
JPEG data URL 播放器不渲染
```

CORS 的典型特征是资源存在，但浏览器安全策略不允许读取。这里有些资源压根没有命中正确地址；另一些资源已经是内嵌 data URL，不再是跨域请求。

所以排查顺序应该是：

```text
先确认有没有请求。
再确认请求 URL 是否正确。
再确认 HTTP 状态码。
再确认 MIME/解码。
最后才看跨域策略。
```

不要用 CORS 解释所有图片问题。它太常见，也太容易误导。

### 10. 播放完成回调不能当作唯一状态推进

动效播放完之后，常见做法是监听播放器的完成回调，然后切到下一阶段。

但移动端播放器回调可能受很多因素影响：

- Lottie 没成功解析；
- 图片 asset 没加载；
- 播放器内部报错但没有抛到业务层；
- 页面切后台；
- 首帧卡住；
- 播放结束事件没有触发。

所以业务状态机通常还需要一个兜底 timer。

但 timer 也有副作用：如果它设置得太短，动画没播完就切走；如果设置得太长，透明态会停留很久。

更稳的做法是：

```text
正常路径：completion 回调推进。
兜底路径：略长于动画真实时长。
调试路径：可以临时拉长，但必须显式标记，避免影响其他问题判断。
```

这次 8 秒兜底就是一个例子。它不是根因，但会把根因放大。

### 11. 动效调试要区分“视觉问题”和“状态问题”

同样是“没看到结果”，可能有两类原因。

视觉问题：

```text
当前状态对了，但内容没画出来。
例如 Lottie asset 透明、图片格式不支持、层级被遮挡。
```

状态问题：

```text
内容能画，但状态没进入到对应阶段。
例如 reveal 没切 result、completion 没触发、timer 被改长。
```

这两个问题的排查方式完全不同。

视觉问题要查容器、图层、资源、解码、样式。

状态问题要查 state、effect、timer、回调、条件分支。

这次最大的混淆点就是：视觉问题导致 reveal 透明，timer 又让 reveal 停留更久，于是看起来像状态问题。

### 12. 最小复现比完整业务流更有价值

完整业务流里变量太多：

```text
抽卡接口
卡图映射
真实卡面
Lottie JSON
播放器
状态机
结果页
调试环境
```

要验证播放器是否支持 PNG data URL，不需要跑完整抽卡。

更好的最小复现是：

```text
一个最小 Lottie
一个 image asset
一个 1x1 或 10x10 PNG data URL
一个 animax-view
```

如果最小复现都不显示，业务代码不用看。

如果最小复现显示，再逐步加真实 Lottie、真实卡图、全量映射和业务状态机。

这就是调试复杂前端问题的基本原则：先拆掉业务，再验证技术边界。

## 最终稳定方案

最后稳定的方向很明确：

1. 出卡 Lottie 不优先注入外链卡图。
2. 卡图映射使用内嵌 base64。
3. base64 使用 PNG，不使用 JPEG。
4. Lottie asset 保持 `u: ""`、`p: "data:image/png;base64,..."`、`e: 1`。
5. 为了控制包体，先降采样，再尝试 palette PNG 或量化压缩。
6. 单抽先验证一张卡，确认播放器能渲染，再扩展到 28 张全量卡面。

这里的体积取舍也要现实一点。PNG 肯定比 JPEG 大，但如果 180px 宽的 28 张卡图大约几 MB，作为验证方案是可以接受的。先证明渲染链路正确，再优化体积。

不要一上来同时做这些事：

- 换图片格式；
- 换资源路径；
- 改播放器参数；
- 改动画时长；
- 改结果态 UI；
- 改调试启动方式。

同时改太多变量，只会让下一次透明时不知道是谁导致的。

更稳的落地顺序应该是：

```text
1. 用一张最小 PNG data URL 替换 Lottie 的一个 asset。
2. 确认播放器能显示这张图。
3. 再接入一张真实卡图的 PNG data URL。
4. 再生成全量卡图映射。
5. 再做降采样和量化压缩。
6. 最后恢复动画时长和结果态切换。
```

这样每一步只验证一个变量。

如果第一步都不显示，问题在播放器或 Lottie asset 字段。

如果第一步显示、第三步不显示，问题在真实图片转换。

如果第三步显示、全量不显示，问题可能在映射、体积或某一张图片。

如果全量显示但结果态异常，再去查状态机和 timer。

这才是可控的调试顺序。

## 下次遇到类似问题，按这个顺序查

我会把这类问题拆成一个固定清单。

第一步，确认容器：

```text
给播放器容器加临时背景。
确认位置、宽高、层级都正确。
```

第二步，确认最小可渲染资源：

```text
不要先注入业务图。
先用一张已知可显示的 PNG data URL。
```

第三步，确认图片格式矩阵：

```text
PNG data URL 是否显示？
JPEG data URL 是否显示？
本地 URL 是否显示？
离线/CDN URL 是否显示？
```

第四步，确认 Lottie asset 字段：

```text
data URL: u=""，p=data URL，e=1
外链 URL: u/path 与 e 的语义要单独验证
```

第五步，确认调试环境真实请求：

```text
不要只看源码里的 src。
要看设备运行时最终请求的 URL。
```

第六步，控制状态切换：

```text
动画兜底时间不要随便拉长。
拉长可以用于观察，但要标注清楚，否则会把透明问题放大成页面卡住。
```

第七步，避免多 session 互相改变量：

```text
一个 session 改资源注入。
一个 session 改动画时长。
一个 session 改结果态文案。

这些改动都合理，但如果没有同步，排查结论会互相污染。
```

动效调试尤其需要把临时改动写清楚：

```text
当前是否强制外链？
当前是否强制 base64？
当前 base64 是 PNG 还是 JPEG？
当前兜底 timer 是多少？
当前 Lottie 是否用了透明占位？
当前截图处于 reveal 还是 result？
```

这些信息缺一个，截图就很难解释。

## 总结

这次问题卡住很久，本质上是因为它不是一个单点 bug，而是一串兼容性问题叠在一起。

最开始以为是外链资源问题，后来以为是容器尺寸问题，再后来以为 base64 也不行。最后才拆清楚：

```text
外链资源确实不稳定。
容器尺寸已经不是主因。
base64 方向是对的。
真正卡住 base64 方案的是 JPEG 编码。
PNG base64 才是当前播放器链路下更稳的选择。
```

这类动效问题最怕“看起来都一样”。透明、空白、没播放、没切态，在截图上很难区分。

真正有效的办法是一次只验证一个变量，用最小可复现资源把播放器链路先打通，再把业务资源、包体优化和交互状态一点点加回来。
