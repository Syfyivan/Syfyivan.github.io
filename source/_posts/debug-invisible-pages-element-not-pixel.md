起因很小。我在用一套跨端渲染框架——就是那种「自己画 UI」的引擎,类比 Lynx、React Native、Flutter——还原一张 Figma 设计稿。还原嘛,总会出问题:这块颜色不对、那块错位、按钮点了没反应。

但真正卡住我的,不是「出问题」这件事本身,而是**出了问题,我没有任何手段去调试它**。

我得先说清楚这种「没法调试」到底有多难受,因为后面所有的努力都是冲着它去的。一张截图能告诉我「这个按钮比设计稿低了大概 4 个像素」,但它**永远不会告诉我这 4 像素是怎么来的**:是这个元素自己多了一截 `margin`?是父容器的 `align-items` 没对齐?是文字的 `line-height` 把它撑下去了?还是——更要命的——我盯着的这个东西,**根本就不是**我以为的那个元素,只是恰好画在了那个位置上?截图是一张「拍扁了的光栅图」,它丢掉了页面里所有的**身份、状态和因果**:每个像素属于谁、那个元素现在是什么状态、它为什么长这样。你拿着一张丢掉了一切结构信息的图,去反推一个结构问题,本质上是在猜。

而我习惯的 Web 调试,F12 一开,元素选中、盒模型高亮、computed 样式一列、控制台一看——问题在哪一目了然。换到真机上的引擎页面,这套全没了。这篇文章,就是我顺着「为什么没了、怎么把它找回来」这条线,一路挖到底的记录。全程只讲通用原理,你把「Lynx」换成任何一个自渲染引擎,结论都成立。

## 一、第一个反直觉:为什么现成的自动化工具「看不进去」

我的第一反应是:Appium、Airtest 这些 UI 自动化都很成熟了,直接拿来驱动不就完了?

挖进去才发现,行不通,而且不通的原因很深——它藏在这些工具「**到底是怎么找到一个控件的**」里。

先看 Appium 这一类「基于控件树」的工具。它本身不直接操作屏幕,而是去调操作系统提供的自动化后端:在 Android 上是 UiAutomator2,在 iOS 上是 XCUITest。这些后端能力的来源,是操作系统维护的一棵**无障碍树 / 原生视图树**——为了让读屏软件、辅助功能能工作,系统会把界面上每一个原生控件(一个 `Button`、一个 `TextView`、一个 `UIImageView`)登记成树上的一个节点,每个节点带着它的边界框、文字、内容描述。Appium 找元素,就是在这棵树上按 id、按文字、按 xpath 去查。这套机制对**原生 App** 非常好使,因为原生 App 的每个按钮、每个文本,本来就是一个真实的系统控件,天然在树上。

现在关键来了:**一个自渲染引擎,根本不走系统的控件这条路。**

为了跨端一致和性能,这类引擎的做法是:向系统只申请**一整块画布**(通常就是一个 `View` / `UIView`,或者一块用 Skia、用自研渲染器直接绘制的纹理),然后页面里所有的 `<view>`、`<text>`、`<image>`,**全部由引擎自己在这块画布上画出来**。这些元素是引擎内部「场景树 / 影子树」里的对象,它们从生到死**都没有变成过任何一个系统原生控件**。

后果是致命的:在操作系统的无障碍树里,你这整个花花绿绿的页面,**只对应一个叶子节点**——那块画布。系统知道「这里有一块 LynxView / RN 的容器」,但对里面那几十个元素**一无所知**。Appium 在树上查来查去,只能查到那一块容器,查不到容器里的任何东西。

<div class="dbg-note">有人会说,无障碍不是也能透出一部分语义吗?是的,有些框架会为了读屏,把<strong>少量</strong>关键文本桥接进无障碍树。但那是为「可访问性」服务的、残缺的、按需的子集,远不是你调试需要的那棵「带几何、带样式、带层级」的完整元素树。指望它来做精确自动化,等于指望从门缝里看清整个房间。</div>

那 Airtest 这种「截图找图」的呢?它绕开了控件树,直接在屏幕像素里做图像匹配。这条路确实能「看见」画出来的东西,但它有两个洗不掉的硬伤。第一,**脆**:换个分辨率、换个机型的像素密度、来个深色模式、页面里有动态内容或动画,匹配就飘了。第二,也是更本质的——它给你的是**一个像素坐标,带着零语义**。它能告诉你「屏幕上 (320, 540) 这里长得像那个按钮」,但它说不出这是哪个元素、它叫什么、现在是什么状态、为什么在这。我要调的是「为什么不对」,而它只能回答「在哪」,问错了问题。

<div class="dbg-key">把这一节收束成一个结构性的结论:通用自动化工具的位置,决定了它的天花板。它们站在 <strong>App 外面、操作系统这一层</strong>往里看;而自渲染引擎为了跨端和性能,<strong>刻意绕过了系统的控件层</strong>,自己闷头画。一个在外面、一个把门关上了自己玩——它俩天然就不在一个频道上。这不是工具不够努力,是架构上隔了一堵墙。</div>

## 二、核心原则:按「元素」操作,不按「像素」

既然站在外面、隔着系统看不进去,那唯一的出路就是:**别从外面看,从引擎内部问。**

好消息是,现代渲染引擎大多在自己内部内置了一个「调试代理」,而且它对外讲的,是一套你很可能已经熟悉的协议——**CDP(Chrome DevTools Protocol)**,也就是你按 F12 时浏览器背后跑的那套东西。通过这条内部通道,你能拿到引擎眼里的**真相**,而不是屏幕外面的猜测:完整的元素树、每个元素**真实的几何盒模型**、计算之后的样式、运行时的状态。

有了这条通道,「可靠地点一下」就不再是「在截图上量个坐标点下去」,而是一套有讲究的流程。我把它拆开,一步步说**每一步为了防住什么**:

1. **`DOM.getDocument` 拿到文档树根节点。** 这是后面一切查询的起点。
2. **`DOM.querySelector` 用选择器定位目标。** 注意,我们从一开始就用「这是哪个元素」来锚定,而不是「屏幕哪个位置」。
3. **`DOM.scrollIntoViewIfNeeded` 把它滚进可视区。** 一个在视图外、还没真正布局的元素,你去取它的坐标,要么取不到,要么取到的是垃圾。先确保它真的被布局、被画出来了。
4. **`DOM.getBoxModel` 取它的盒模型,算中心点。** 盒模型返回的是四组四边形(content / padding / border / margin 各一圈)。优先取 content 框的中心;如果这个元素太小或内容为空、content 框退化了,就退一步取 border 框的中心。这里取到的是引擎的「逻辑坐标」——记住这个词,第四节它是主角。
5. **`DOM.getNodeForLocation` 用刚算出的坐标反查,确认命中的就是它。** 这一步是整套流程的灵魂。它在做的是「命中测试」(hit-testing):问引擎「(x, y) 这个点,最上层盖着的是哪个节点?」如果答案不是我们的目标——可能它被一个浮层盖住了、可能它其实在屏幕外、可能页面刚刚变了——那就**当场报错,绝不把这一下点出去**。
6. **派发输入(同一坐标的 press 和 release)。** 校验通过了,才真正点下去。

<div class="dbg-note"><strong>第 5 步为什么是灵魂?</strong>因为「算出一个坐标」和「这个坐标点得到目标」是两件完全不同的事。坐标可以算得很对,但元素被遮挡、被移动、还没布局好,你照着点就是点空。区别「可靠」和「玄学」的,就是这一步肯不肯老老实实先反查、再下手。它返回「这里没有任何节点」时,正确的反应是<strong>停下来报错</strong>,而不是「先点了再说」。</div>

把这一节钉死成一句:**坐标只来自盒模型,绝不来自截图。** 至于为什么连「拿截图量个坐标」都不行——不只是因为截图会过期,更因为截图像素和引擎逻辑坐标之间,隔着一层你绝对不该自己去碰的换算。这就是下一节、也是整件事里最容易翻车的地方。

## 三、最大的澄清:CDP 是「协议」,不是「能力」

我卡了很久的一个误区是这样的:「浏览器 F12 又能点又能查,为什么换到真机上的引擎页面就这么费劲?难道这条调试通道**没有** CDP 吗?是不是它根本不支持这些操作?」

把底层翻清楚之后我才意识到,这个问题问错了。要解开它,必须先把**两件被我混在一起的事**拆开。

**第一件事:传输(谁来搬运消息)。** CDP 说到底是一种消息格式——一套类似 JSON-RPC 的协议,有很多「域」(DOM、CSS、Input、Page、Runtime……),你发命令、它回结果、它推事件,通常跑在一条 WebSocket 上。但这些消息数据,得有人从你的电脑搬到设备上去。这个「搬运工」可能是一根 USB 线(通过端口转发建一条隧道),也可能是一座无线调试桥。**搬运工是「哑」的**——它不理解消息内容,只负责把帧原样转过去。所以,这根管子**从不缺 CDP**,它压根不关心搬的是不是 CDP。

**第二件事:应答端(谁收到命令真去干活)。** 你发 `DOM.getBoxModel`,得有个东西真的去算这个元素的盒模型再回给你。这个「应答端」是谁,才是一切差异的根源:

- 当你连的是**浏览器 / WebView**,应答的是 Blink/V8 内置的那套 DevTools 后端。这是一套**成熟到近乎完整**的实现,维护了很多年,你能想到的 DOM/CSS/Input/Page 方法它基本都有,行为也稳定。
- 当你连的是**自渲染引擎的视图**,应答的是引擎**自己重新实现、编进运行时里的一个 CDP 子集**。它把 CDP 的调用,映射到引擎自家的那套 DOM、布局系统、JS 虚拟机上。因为是重写的,它**只实现了一部分方法**,而且年轻、会随版本变化,某些方法在新版本才有、某些行为在不同平台还不一样。

<div class="dbg-key">于是「网页里随便操作、引擎页面却处处是坑」的真相浮出来了:<strong>同一套协议、同一根管子,但两头接的是两个成熟度天差地别的应答端。</strong>浏览器那头是「完整版」,引擎那头是「子集版」。不是没有 CDP,是 CDP 的<strong>另一头</strong>是个还在长身体的部分实现。</div>

而且引擎这一头还多一道坎:输入。你发的逻辑坐标,在引擎里不会像浏览器那样直接喂给一个统一的事件管线,而是要被**转换成平台原生的手势事件**(Android 的 `MotionEvent`、iOS 的 `UIEvent` 触摸序列)再派发出去。这一步转换,引擎在内部替你做了,而它做这步转换的方式,正是下一节第一个坑的来源。

想透了这一层,后面所有的「难」就都不再是玄学,而是一个个能定位、能各个击破的具体问题。

## 四、六个坑,逐个说清「到底是什么在作怪」

把一次点击,从你敲下命令、一路穿到引擎真的派发出一个触摸事件,中间会踩到六类坑。它们叠在一起,就是「这东西很难写好」的全部真相。我一个个讲透它的成因和解法——你会发现,**六个里有五个,防御都是纯代码、跟有没有真机毫无关系**。

**坑一:坐标换算,你千万别自己做。** 这是翻车最多的地方,成因在上一节埋了:逻辑坐标到屏幕上真正的触摸点,中间隔着一层平台相关的换算。具体有多绕?在 Android 上,引擎收到你的逻辑坐标后,会**乘以屏幕像素密度**,再去构造 `MotionEvent` 派发;在 iOS 上,它要把点**换算到 key window 的坐标系**里再合成触摸;如果是全屏模式,还要先**减掉这块视图在屏幕上的原点偏移**。这些换算,引擎在内部**已经替你做了**。所以如果你拿到盒模型坐标后,自作聪明又做一次 DPR/缩放换算,结果就是**换算了两遍**,点位必然飘掉。解法因此极其反直觉但极其简单:**什么都别算**,盒模型给你什么逻辑坐标,你原样喂回去,换算是引擎的活。——这也正是「坐标只能来自盒模型、不能来自截图」的根:截图是物理像素,你想用它就必须自己换算,一换就错。

**坑二:布局是会漂的,坐标读出来那一刻就可能过期。** 引擎的布局是响应式、异步的:一次滚动、一批数据回来、一帧动画,都会触发重新布局。这意味着你 `getBoxModel` 读到的坐标,是**某一个瞬间的快照**,几毫秒后它就可能不作数了。解法是两层:第一,**绝不缓存坐标**,每次操作都重新读盒模型;第二,更狠一点——在真正派发输入**之前的最后一刻,再用 `getNodeForLocation` 复检一次命中**,把「读坐标」到「点下去」之间那条缝压到最小,中途页面变了就中止。我自己实现时,这条复检救了很多「校验时还在、点的时候已经跳走」的场景。

**坑三:双线程,你得知道自己在跟谁说话。** 这类引擎为了不让繁重的 JS 逻辑卡住渲染,常把活动拆到两个线程/两个 VM 上:一个主线程跑布局和渲染,一个后台线程跑业务 JS(有的引擎甚至是两个独立 JS 虚拟机)。后果是,有些 CDP 域只在某个线程上有意义——比如你在后台线程求值一段 JS 去读页面状态是对的,但有一类调试器/性能相关的方法只在主线程上才支持。如果你不区分,把命令发错线程,它就**默默失败**或报一个你看不懂的错。解法是:在接口里把「线程」做成一个显式参数,读 UI 状态走后台、调试器类走主线程,别让它默认踩雷。

**坑四:输入是时序敏感的合成手势,不是两条孤立的指令。** 一次「点击」在系统看来,是「在很短的时间和很小的位移内,一次按下紧跟一次抬起」。如果你的按下和抬起,是作为两条**互不相干、中间还隔了一段延迟**的消息发过去的,手势识别器可能把它**识别成长按**,或者干脆丢弃。双击更娇气:第二次点必须落在系统认定的「双击间隔」之内,否则就被当成两次独立单击。解法是:把一组输入(按下、抬起,或双击的四条)**作为一个流、背靠背地一次性发出**,保证它们的时序紧凑;双击的间隔做成可调,识别器不认就调它。

**坑五:传输栈的失败模式特别多,得分层报错。** 从「驱动器」到「引擎」,中间这条链特别长:设备没插好/没连上调试桥、连上了但 App 没打开调试开关、开关开了但页面没打开、页面打开了但你选错了会话……任何一环断了,表象都是「点不动」。如果你只笼统地抛一句「失败」,排查就是大海捞针。解法不在协议、在工程:**把每一环单独探测、分层报错**——「没发现设备」「发现设备但没有会话」「有会话但不是目标页」要是三个不同的错,直接告诉你卡在第几环。

**坑六:没有稳定的选择器,因为页面侧根本没给你。** 自渲染、尤其是机器生成的页面,经常既没有测试标记、也没有语义化的 id,你想 `querySelector` 都无从下手。这个坑的解法是两条腿走路:**治本**是推动页面侧给关键可交互元素挂上稳定的测试标记——这是投入产出比最高的一件事,加一个标记,定位就从「猜」变成「查」;**兜底**是当你拿不到标记时,退而用「按可见文字去搜索」来定位,代价是同一段文字出现多次时会有歧义,需要靠出现顺序或上下文再消歧。

<div class="dbg-note">通看一遍你会发现一个规律:难,不难在 CDP 协议本身,而难在「<strong>部分实现的引擎应答端 + 原生手势派发 + 双线程 + 易漂的坐标 + 又长又脆的传输栈 + 缺失的选择器</strong>」这六样东西<strong>叠在一起</strong>,每一样都有自己独立的失败方式。但反过来看也正是好消息:这六样里,真正非得有一台真机才能验证的,只有「引擎到底有没有把触摸正确派发出去」这一件运行时行为;其余五样的防御,全是你在没有任何设备的情况下,纯靠代码就能写对、写死的。</div>

## 五、插曲:认真聊聊 D2C——它能做什么,又为什么不可能完美

要讲清楚我那个工具最大的用处,得先把它的上游——D2C——讲透。

**D2C(Design-to-Code,设计转代码)**,就是输入一张 Figma 这类的设计稿,直接输出可用的前端代码。这件事这两年随着大模型起来,落地了一批工具,确实能让你「还原设计稿」时一开始就少出很多错。但只要你认真用过,就会撞上它们一条诚实的、也无法回避的声明:**做不到 100% 还原。** 要理解后面为什么需要一个「验证器」,先得理解它为什么做不到。

**根本原因:「设计稿 → 代码」这步转换,本质是有损的。** 一张设计稿是「拍扁的结果」——它只描述了「最终长这样」,却**没有描述意图**。举几个具体的:两个元素之间空了 16 像素,这到底是父容器的 `gap`、还是某个元素的 `margin`、还是绝对定位硬算出来的?设计稿不知道,但代码必须二选一,选错了,一改动就崩。一排卡片,是该用弹性布局自动排、还是绝对定位一个个摆?设计稿没说,而这决定了它在不同屏宽下会不会正确伸缩。系统状态栏、刘海、安全区这些只有真机上才存在的东西,设计稿里压根没有,只能估。更别说为了让生成的代码结构合理,工具常会把设计稿里一些纯包装的图层**合并或删掉**——于是**生成代码里的节点,和设计稿里的图层,根本不是一一对应的**。这些不确定性加在一起,就是那 1% 到 N% 的「不像」,而且它**消不掉**,因为信息在源头就丢了。

理解了「为什么难」,再看市面上的 D2C 工具,你会发现它们大致分成**两种架构形态**,各有取舍:

- **本地 agent 形态。** 在你本地跑一个多阶段流程:解析设计稿 → 给每个图层打标注 → 按你的项目约定生成代码,直接写进你的工程目录。它通常**专精某一个框架**,懂这个框架的写法、复用你项目里已有的组件和设计 token,产物拿来就能用,改动成本小。代价是要配本地环境和若干 token。
- **云端平台形态。** 你把设计链接提交给一个云端服务,它在云上构建,完事你下载一个产物包,再迁移进项目。好处是**通用、零本地环境、覆盖面广**;代价是产物比较「通用」、需要你做迁移适配,而且通常**不暴露中间过程**。

<div class="dbg-note"><strong>这里藏着一个对「验证」至关重要的概念:中间表示。</strong>好的 D2C 工具,在「生成代码」之前会先产出一份<strong>带标注的设计树</strong>——每个节点上挂着它对应的设计图层 id、布局语义(横排还是竖排、间距多少)、以及样式。这份东西才是「设计真源」。它的价值在于:它是连接「设计图层」和「最终代码」的桥,既能用来追溯,理论上也能用来做验证——你可以拿真机渲染出来的页面,去和这份标注树逐项对。云端形态往往把它藏起来,本地形态更可能把它吐出来,这一点后面会变成关键。</div>

还有一个常被忽略的细节:**设计 token**。成熟的设计系统不会让你写死 `color: #FF0000`,而是写 `color: 主色`——这个「主色」就是一个 token,背后才是具体色值。好的 D2C 会把样式表达成「token + 兜底值」的形式(类似 `{主色, fallback: #FF0000}`),既保留了设计系统的语义,又给了一个万一 token 对不上时的退路。但这也带来一个隐患:当 token 文件缺失、或匹配不唯一时,工具只能**退化成硬编码那个兜底值**,于是生成的颜色虽然「看起来对」,却和设计系统的语义脱了钩——这又是一处「肉眼难发现、但确实不对」的地方,正是需要验证器去抓的。

最后说一句**专用 vs 通用**的取舍,因为它直接影响产物质量。专精某个框架的 D2C,会懂这个框架的「脾气」。拿开源的跨端框架 Lynx 举例:它默认的布局协议和 Web 的 flex 并不完全一样、对 `z-index` 这类层级控制的支持也和浏览器有出入、列表的间距还得用框架自己的属性而不是 CSS 的 `gap`。一个**专用** D2C 知道这些,生成出来就是地道的、能跑的代码;一个**通用** D2C 不懂,产物往往是「看着像、但一上真机就布局错乱」,你得手工返工。这也解释了:为什么针对你正在用的框架,专用工具往往比通用平台更省事。

## 六、于是,D2C 天生需要一个「验证器」

讲完 D2C,最关键的一句话来了:**这些工具,无论哪种形态,都只管「生」,生完不会回头看真机到底像不像、哪里不像。** 它把代码交付给你,任务就算结束了。

可「还原」这件事真正的难点,恰恰在交付之后:它到底像不像设计稿?不像的话,是哪个元素、差在文案、颜色、字号还是位置?——这个活**没人接**。而它需要的能力,正好是前四节那套东西:一个能进引擎、能读到真机上 DOM、盒模型、计算样式的驱动器。**生成是一个问题,验证是另一个完全不同的问题,而后者一直空着。**

补上它,一个闭环就成立了:

```
设计稿
   │  D2C 工具生成代码 ——「生成」,它擅长的
   ▼
页面代码 ──► 真机打开
   │            │  驱动器:读真机上每个元素的文字 / 颜色 / 字号 / 盒模型,
   │            │          逐项对比设计稿(或那份标注树)给的期望值
   │            ▼
   │         差异报告:哪块文案不对、哪块颜色不对、哪块尺寸/可见性不对
   └────回灌修正◄┘ ——「验证 + 反馈」,驱动器擅长的
```

但这里有个**真实存在的硬骨头**,我得诚实地讲:**生成的代码,通常不会把设计图层的 id 带回到运行时的元素上。** 也就是说,真机上跑着的那个 DOM 节点,和设计稿里那个图层之间,**没有一个机器能直接读到的锚点**。这导致「自动对齐」并不轻松——你只能退而求其次,用几条启发式去配:有人工映射时用映射、没有时按可见文字去猜哪个对哪个、再不行就只能标「对不上」。纯图标、无文字的容器,往往就只能落到「对不上」,得人工补。**这不是偷懒,是信息在生成那一步就断了**;最干净的根治办法,其实是让 D2C 在生成代码时,顺手把设计图层 id 透传成一个稳定的测试标记——一行小改动,就能把「靠猜的模糊对齐」变成「精确的逐项 diff」。

<div class="dbg-key"><strong>生成和验证,是两个不同的问题,且天然互补。</strong>生成侧负责把设计变成代码,验证侧负责把「像不像稿」从一句模糊的吐槽,变成一份能逐项核对的 diff。这里还有个小而关键的工程细节:做样式对比前,得先把值<strong>归一化</strong>——颜色 <code>#f00</code> 和 <code>#ff0000</code> 是同一个色,不该报成差异;<code>16px</code> 和 <code>16PX</code> 也是。不归一化,你的报告会被一堆假差异淹没,没人会看。</div>

这,就是我最后动手写的那个东西:一个薄薄的驱动层,把第二节那套「定位 → 盒模型 → 命中校验 → 点击」的铁律,连同「读结构、读样式、对着设计稿比对」的能力,封装成一组稳定、自带校验闭环的函数。它不和任何 D2C 工具竞争——恰恰相反,它接在所有 D2C 的下游,补上它们都缺的那半块。它要解决的,从头到尾就是我开篇那句话:**还原出问题之后,我终于有办法去调试它了。**

## 七、没有真机,怎么先把代码验对?

写这个工具的全程,我手上一直没有一台能连进来的设备。但「没设备」不该成为「逻辑也写不对」的借口——这两件事,可以也应该分开。

诀窍是把风险**分层**。仔细想,一次操作要穿过四层:① 你自己写的驱动逻辑(算坐标、走命中校验的分支、按正确时序发输入)→ ② 你和协议之间的契约(方法名对不对、参数结构对不对)→ ③ 传输(消息有没有被搬到设备)→ ④ 引擎运行时(引擎收到后有没有真的去命中、去派发)。这四层里,**③和④确实只能上真机验,但①和②,完全可以在没有任何设备的情况下离线验死。**

怎么验?写一个**假的 CDP 应答端**(mock),手工喂给它罐头响应——「查这个元素,返回这个盒模型」「这个坐标,命中/不命中」——然后去断言你的驱动逻辑在各种情况下的行为:中心点算对了吗?content 框退化时有没有正确地退到 border 框?命中校验失败时,是不是真的**一条输入指令都没发出去**?双击是不是真的凑齐了四条、间隔也对?把这些分支用断言一个个钉死。

<div class="dbg-note"><strong>这样做的回报,不只是「测了个心安」。</strong>它把「你自己写的那部分」确定性地验到死,从而把剩余的不确定性<strong>精确地隔离</strong>到「传输 + 引擎」这两块真·只能上真机的地方。这意味着等设备到位的那一刻,你需要 debug 的范围,已经从「整条又长又黑的链路」缩小到了「最后两层」。在没有设备的日子里,这是你能为「将来那次真机联调」做的、回报最高的准备——你不是在干等,你是在提前把雷区缩小到只剩两格。</div>

## 📦 复制带走

<div class="dbg-card"><strong>📦 复制带走</strong><br>① 自渲染引擎为了跨端和性能,<strong>刻意绕过系统控件层自己画</strong>,所以它对操作系统是个黑盒——基于控件树或截图的通用 UI 自动化,从架构上就看不进去。<br>② 正确姿势是按<strong>元素</strong>(走引擎内部调试协议,拿真实几何)操作,不按<strong>像素</strong>(截图);其中「点之前先做命中反查」是可靠与玄学的分界线。<br>③ <strong>CDP 是协议、不是特权</strong>:管子只负责搬运,真正的难,难在引擎那个「重写的、部分实现的应答端」,外加输入要转成原生手势。<br>④ 六个坑里,五个的防御是<strong>纯代码</strong>、跟有没有真机无关;真正只能真机验的,只有「引擎有没有把触摸正确派发」这一件。<br>⑤ D2C「设计转代码」本质<strong>有损</strong>(设计稿丢了意图),做不到 100% 像稿;它分本地 agent 型和云端平台型,专精某框架的往往比通用平台更出活。<br>⑥ D2C 只管「生成」,不管「验证」;而生成代码常不带回设计图层锚点,所以验证要靠启发式对齐——补上这半块,才是「设计稿 → 已验证页面」的完整闭环。<br>⑦ 用<strong>假应答端</strong>离线验逻辑,把剩余风险隔离到「传输 + 引擎」两层——没设备时,这是回报最高的准备。</div>

## 🚀 留个思考

下次你再遇到一个「截图看着不对、但你说不出为什么不对」的页面,先别急着对着像素较劲。先问自己一句:**我能不能拿到它的「元素真相」?** 能,问题就从猜谜变成了逐项核对;不能,那把这条通道打通——往往才是真正该做的第一步。很多时候,我们以为难的是「修这个 bug」,其实真正难的、也真正值得先解决的,是「让自己能看见这个 bug」。
