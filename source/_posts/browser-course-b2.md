> 这是一条支撑整条主线的**底座分支**。主线里反复出现「浏览器进程」「渲染进程」「主线程」「合成线程」——这些词能成立，全靠操作系统提供的进程、线程、内存、调度这些基础机制。这条分支把那个底座讲清楚，你再回头看主线里的进程模型，就会从「记住有这么个说法」变成「知道它为什么必须这样」。

<p class="bc-sec lead">一句话结论</p>

操作系统给每个程序分配**进程**做隔离的资源容器、用**线程**做真正被 CPU 调度的执行单元、用**虚拟内存**给每个进程一份独占内存的假象。浏览器的多进程架构、渲染进程里的单线程模型、站点隔离带来的内存开销，全都是这三样机制的直接推论。

<p class="bc-sec">理解原理</p>

### 第一步：进程——隔离的资源容器

**进程（process）** 是操作系统分配资源的基本单位。每个进程有自己独立的地址空间、文件描述符、权限边界。关键在「独立」二字：一个进程崩溃，不会直接拖垮另一个进程，因为它们的内存互不可见。

这正是浏览器多进程架构的地基。主线节点一、节点七讲过 Chromium 把浏览器进程、渲染进程、网络服务、GPU 进程分开——**之所以能靠「分进程」实现崩溃隔离和安全隔离，正是因为操作系统保证了进程间地址空间互不可见。** 站点隔离把不同站点放进不同进程，一个渲染进程被攻破也读不到别的进程内存，这条安全保证的底层依据就是进程隔离。

### 第二步：线程——真正被调度的执行单元

**线程（thread）** 是 CPU 调度的基本单位。一个进程里可以有多个线程，它们**共享**这个进程的地址空间（同一片堆内存、同样的全局变量），但各自有独立的执行栈和寄存器状态。

「共享地址空间」是双刃剑：

- 好处：线程间通信便宜，直接读写同一块内存就行，不像进程间要专门的 IPC。
- 坏处：多个线程同时读写同一份数据，会有**数据竞争（race condition）**，得靠锁等同步手段保护，这也是多线程编程复杂的根源。

回到主线节点九：为什么 JS 是单线程？因为把 JS 和 DOM 操作放在同一个主线程上，就**天然不存在多线程数据竞争**——DOM 永远只有一个线程在动，心智负担极低。代价是长任务会卡住这唯一的线程。而节点十一里栅格化、合成放到别的线程（合成线程），正是把不碰 DOM 的重活挪出主线程，用多线程换吞吐、又避开对 DOM 的竞争。

<div class="bc-call bc-bonus"><span class="bc-tag">加分细节</span><strong>进程 vs 线程，一句话抓住本质</strong><br>进程是「资源分配的单位」，线程是「CPU 调度的单位」。进程之间隔离、崩溃互不影响、通信贵；线程之间共享进程资源、通信便宜、但要防数据竞争。浏览器的取舍就是沿这条轴展开的：跨站点用进程（要隔离和安全），渲染内部用多线程（要通信效率和并行）。能用这一句话统领两者，比分别背定义清楚得多。</div>

### 第三步：虚拟内存——每个进程都以为自己独占内存

**虚拟内存（virtual memory）** 是操作系统给每个进程的一个假象：每个进程都觉得自己拥有一整片连续、独占的地址空间，从 0 开始编号。实际上这些**虚拟地址**要经过硬件 MMU（内存管理单元）和操作系统维护的**页表**，翻译成真实的**物理地址**。

这套机制一石多鸟：

- **隔离**：进程 A 的虚拟地址和进程 B 的虚拟地址，即使数值相同，也映射到不同的物理页——所以进程天然读不到彼此内存。这就是第一步「进程隔离」在内存层面的实现原理。
- **超额使用**：物理内存不够时，不常用的页可以换到磁盘（换页 / swap），让程序用起来像有很多内存。
- **按需分配**：内存按**页（page）** 为单位管理，用到才真正映射物理页。

主线节点七说「站点隔离让 Chrome 吃内存」，底层原因就在这里：每多一个渲染进程，就多一套独立的地址空间和页表、多一份自己的堆和缓存，物理内存占用自然上去。这是「安全靠进程隔离」必须付的代价。

### 第四步：用户态与内核态——一道保护墙

程序跑在**用户态（user mode）**，权限受限，不能直接碰硬件和关键资源。要读文件、发网络包、创建线程，都得通过**系统调用（system call）** 请操作系统在**内核态（kernel mode）** 代劳。这道墙保证了一个普通程序不会随便搞坏整个系统。

主线里每一次「网络服务发包」「渲染进程读缓存文件」，落到最底层都是一次次系统调用穿过这道墙。系统调用有开销（要切换特权级),所以高性能程序会想办法减少不必要的系统调用——这也是理解很多 I/O 优化的起点。

### 汇总：主线里的每个「进程/线程」都能在这里找到根

进程给隔离、线程给调度与并行、虚拟内存实现隔离并制造独占假象、用户态/内核态划出权限边界。浏览器的多进程隔离、单线程 JS、多线程渲染、以及「安全换内存」的取舍，全是这套机制的推论。

<p class="bc-sec">主线整理</p>

```text
操作系统要同时跑很多程序，还要互不干扰
        ↓ 用「进程」做资源与隔离的容器
进程：独立地址空间 / 崩溃隔离 / 通信要 IPC
        ↓ 进程内要并行、要高效通信，用「线程」
线程：共享地址空间被 CPU 调度 / 通信便宜但有数据竞争
        ↓ 隔离和独占假象怎么实现？虚拟内存
虚拟内存：虚拟地址经页表映射到物理地址，进程互不可见
        ↓ 普通程序不能乱碰硬件，划一道墙
用户态/内核态 + 系统调用：受控地请操作系统代劳
        ↓
推论：浏览器多进程隔离、单线程 JS、多线程渲染、安全换内存
```

<p class="bc-sec">设计取舍</p>

**进程隔离 vs 线程共享**：进程用「地址空间隔离 + 昂贵的 IPC」换来崩溃与安全隔离；线程用「共享地址空间 + 数据竞争风险」换来高效通信和并行。浏览器跨站点选进程（要隔离），渲染内部选多线程（要效率），是同一根轴上按需求分别取点。

**虚拟内存**：用「地址翻译的开销 + 页表内存」换来了进程隔离、内存超额使用和按需分配三大好处。代价是多一层间接、换页时有性能抖动，以及每个进程都要维护自己的页表（多进程时累加成可观开销）。

**用户态/内核态分离**：用「系统调用要切换特权级的开销」换来了系统的安全和稳定——一个崩溃的程序困在用户态，搞不垮内核。代价是频繁 I/O 的程序要为系统调用开销买单，催生了各种批量化、异步化的 I/O 优化。

<p class="bc-sec">面试回答</p>

操作系统这套机制正好是主线里那些进程线程说法的底座。进程是资源分配和隔离的单位，每个进程有独立地址空间、互相看不到内存，一个崩了不影响别的——浏览器能靠分进程做崩溃隔离和站点隔离安全，就是因为操作系统保证了进程隔离。线程是 CPU 调度的单位，一个进程里多个线程共享地址空间，通信便宜但会有数据竞争要加锁。所以 JS 设计成单线程，是把 JS 和 DOM 放一个主线程上天然没有数据竞争，代价是长任务卡住这条线程；而栅格化合成放到别的线程，是把不碰 DOM 的重活挪出去换并行。隔离的底层实现靠虚拟内存：每个进程以为自己独占一整片地址空间，虚拟地址经页表映射到物理地址，两个进程数值相同的地址也映射到不同物理页，所以互不可见。这也解释了为什么站点隔离让 Chrome 吃内存——每多一个进程就多一套地址空间、页表和堆。最后还有用户态内核态的墙，程序想读文件发网络包都得走系统调用请内核代劳，保证普通程序搞不垮系统,但系统调用有开销,所以有各种 I/O 优化。

<p class="bc-sec">常见追问</p>

**进程和线程的区别？**（校招必考）
进程是资源分配的基本单位，有独立地址空间，隔离性好、崩溃互不影响、通信要 IPC 较贵。线程是 CPU 调度的基本单位，同进程内线程共享地址空间，通信便宜、可并行，但有数据竞争需要同步。一句话：进程管隔离，线程管调度。

**为什么浏览器要用多进程架构？**（校招常问，连主线）
为了稳定和安全。分进程后一个页面崩溃不拖垮整个浏览器；站点隔离把不同站点放进不同进程，靠进程地址空间隔离保证一个进程被攻破也偷不到别站点数据。代价是内存开销上升。

**虚拟内存是什么，解决什么问题？**（校招常问）
给每个进程一份独占连续地址空间的假象，虚拟地址经页表和 MMU 映射到物理地址。它实现了进程间内存隔离、支持物理内存超额使用（换页）、支持按需分页。是进程隔离在内存层面的实现基础。

**多线程为什么容易出 bug？单线程 JS 怎么规避的？**（校招常问，连主线）
多线程共享地址空间，多个线程同时读写同一数据会产生竞态，要靠锁同步，容易死锁或漏加锁。JS 单线程让 DOM 只有一个线程操作，天然无竞态，心智简单，代价是长任务阻塞。重活交给不碰 DOM 的 Worker/合成线程并行。

**什么是系统调用，为什么有开销？**（回答出来加分）
用户态程序请操作系统在内核态执行特权操作（读文件、发包、建线程）的接口。开销来自用户态到内核态的特权级切换和上下文保存。频繁 I/O 会积累开销，因此有批量、异步、零拷贝等优化。

**协程/用户态线程和内核线程有什么不同？**（通常不需要主动展开）
内核线程由操作系统调度，切换要进内核、开销较大。协程是用户态自己调度的轻量执行流，切换不进内核、开销小，适合海量并发 I/O。但协程需要配合非阻塞 I/O，且不能真正利用多核（需配合多线程）。
