想要的不是一个“所有数值翻倍”的补丁，而是四个可以组合的方向：画家成长、更多时代事件、丰富的工会经营，以及汉化。

这篇记录设计方案。**成长、时代、经营三个玩法 Mod 尚未完成实现；汉化只进入部分文本预览阶段。** 原版中已经确认的机制见[上一篇](/game-mod-research/painters-guild-mechanics/)。

## 1. 画家成长：让培养出现取舍

原版有学习、天赋、教学、三级晋升与旅行。新增内容应当让玩家决定“怎样培养”，而不只是更快填满同一条进度条。

第一阶段可以设计“进修机会”：年轻画家面对不同路线，选择专注创作、学习授课或外出见习。收益与代价同时写清楚，例如训练期间无法接单、需要支付费用，而不是无代价地增加全部属性。

第二阶段再建立长期师徒关系。关系应绑定稳定的人物标识，不能只记人物在数组中的位置，因为解雇或死亡会改变数组顺序。教学可以保留原版的邻接条件，再增加师徒熟悉度或专长传递。

第三阶段才考虑传承：当大师退休或去世，曾经培养的学生、留下的手稿或代表作继续影响工会。这需要新增持久状态，并处理导师外出、关系中断和后代继承，工作量明显大于调整学习公式。

**首个可验收版本**：一个可选择的成长事件，选择产生不同结果，资金不足时不会错误扣费，保存后能恢复结果，读档不会再次领取同一份收益。

## 2. 跨时代事件：让 1620 年后的年份有意义

原版历史事件表在 1620 年的总结之后没有继续安排内容。可以沿着日期调度入口，增加后续事件，但“多几个弹窗”还不等于有了新玩法。

一个事件至少包含：

| 信息 | 用途 |
| --- | --- |
| 稳定 ID 与适用年代 | 保证能追踪、能存档、能升级 |
| 前置条件与触发频率 | 避免无关事件刷屏 |
| 事件文本与选项 | 让玩家理解取舍 |
| 即时效果或持续效果 | 真正改变经营处境 |
| 完成记录与持续时间 | 防止读档重复发奖或效果永不结束 |

第一版可以先放入几个**明确标为虚构经营事件**的场景：新的收藏者希望长期订购、年轻学徒组织作品展示、工坊需要适应新的审美需求。先验证事件系统，再为巴洛克及更晚时代补充经过独立查证的历史节点。

涉及真实历史时，要分清“确有其事的背景”和“为了游戏设计的效果”。某次真实事件发生过，不代表给工会增加某个百分比收入就是历史事实。

更晚时代还需要同步检查画家来源、画风、赞助人结构与经济量级，否则年份虽然走远了，人物和市场仍停在原地。

**首个可验收版本**：在 1620 年之后的新日期触发一项新事件，两种选项能产生不同结果，完成后存档、退出、读档不会重复触发。还要检查从事件日期前的旧存档继续推进，以及直接载入日期已过的存档时采用什么规则。

## 3. 工会经营：在接单之外增加长期决策

原版已有货币、声望、工资、招聘和扩建。这些是经营扩展的基础，不必马上重新制作建筑系统。

可以先尝试三个内容：

- **赞助合同**：接受一段时间的稳定收入，同时承担交付要求；拒绝则保留自由接单能力。
- **展览筹备**：预先投入资金与画家时间，完成后提升知名度；不是点一下就拿奖励。
- **学徒预算**：把短期现金流换成长期人才培养，和成长 Mod 联动。

第一版只选一种合同做完整闭环：签约、扣费或预付款、记录要求、检查到期、履约或违约结算。先完成一条链，比同时放入许多只有标题的功能更有价值。

**首个可验收版本**：合同状态可以存档；同一周期只结算一次；人员离开后不会留下无法完成的任务；关闭经营模块时，对未完成合同有明确处理规则。

## 4. 汉化：作为独立可选模块

汉化尽量只改变显示文字和字体，不改变原版经济与触发条件，也不把原版事件改写成我们设想的新机制。

首批范围是四个主菜单标签与二十一组事件标题、正文。后续再覆盖人物属性、商店、招聘、存读档和包含人名、金额的动态提示。

新增的玩法事件需要稳定文本键，避免中文内容与逻辑条件混在一起。内部使用的物品名、类名、保存字段仍保持稳定，只翻译面向玩家的文字。否则把程序用来比较的物品名称翻成中文，可能连带破坏行为判断。

**首个可验收版本**：中文能正常显示；最长文本不遮住按钮；悬停和重新打开界面不回退成乱码；切换语言不改变存档数据。详见[汉化实验](/game-mod-research/painters-guild-localization/)。

## 5. 为什么不能分别做四个 SWF 然后依次安装

这款游戏的主要内容集中在同一个 `GameData.swf`。如果四个 mod 都直接提供完整替换文件，后装的文件可能把前一个 mod 的修改覆盖掉。

计划采用“一个构建入口、多个可选补丁”的方式：读取同一份经校验的原版副本，按启用配置组合修改，最后生成一个游戏文件。它仍是离线补丁方案，不是已经存在的官方插件加载器。

存档扩展也应共享一个明确的版本约定，例如下面这份**拟定结构**：

```json
{
  "modData": {
    "schemaVersion": 1,
    "growth": {"relationships": []},
    "events": {"completedIds": []},
    "guild": {"contracts": []}
  }
}
```

旧存档没有 `modData` 时应能初始化默认值；模块关闭、重新启用和未来升级时，不能随意删除其他模块的字段。汉化不需要更改这些业务数据。

## 6. 实施顺序和当前边界

1. **原版往返验证**：导出、无改动编译、启动、新游戏、保存、读取。现在只到启动主菜单。
2. **部分汉化预览**：验证修改文字、字体处理和补丁可恢复性。
3. **单个事件闭环**：让事件实际触发、选择并持久化；随后验证 1620 年后的触发。
4. **成长与经营小模块**：各实现一个完整玩法，再验证组合。
5. **长期内容扩展**：补充事件、培养路线、合同类型和更晚时代。

组合验证至少覆盖：原版、仅汉化、每个玩法单独启用、三个玩法与汉化全部启用。保存与读取还要跨这些组合检查，不能只测试“全开时启动成功”。

桌面 Mod 和[现有网页版](/painters-guild/)保持两条实现路线。桌面侧研究得到的规则可以写成文章，也可以启发网页版设计；但不能把修改 SWF 的补丁当作 JavaScript 网页扩展直接安装。
