## 一、故事正文

青萝最近接了一桩委托：替宗门炼一件「传讯阵盘」，能在山门各殿之间收发讯息。她编码极快，三日便交了初版。可执律师姐试用时一皱眉：改个殿名，整盘失灵；想多接一座偏殿，竟要把传讯逻辑、阵纹绘制、储灵格全推翻重炼。一连返工五次，青萝熬得双眼通红，阵盘还是一碰就散。

她不服气，把卷宗抱去找长老：「我代码没写错啊，每一处都跑得通，为什么一改就崩？」

长老没看代码，先要了她的**设计**文档——结果青萝拿不出来。她是想到哪写到哪，根本没画过蓝图。长老叹道：「问题不在炼器，在**软件设计**。你这盘子，模块之间**耦合**太紧，一个模块直接伸手去改另一个模块肚子里的数据；每个模块**内聚**又太低，一个模块里塞了绘阵、传讯、存储三件不相干的事。改一处便动全身，这叫牵一发而动全身。」

长老在石壁上写下一句课件原话：**软件设计是把软件需求转换为软件表示的过程，是将用户需求准确转化为软件系统的唯一途径**。他说，好作品不是「炼」出来的，是先把**蓝图（设计）**画好、再照图施工得来的。设计分两步走：先做**高层次设计（软件体系结构设计）**，把需求转成数据结构和系统结构，定义子系统以及它们之间的通信或接口；再做**详细设计**，细化出每个模块的数据结构和算法，给写代码的人一份清晰的规范说明。

「你跳过了画蓝图这一整段，」长老说，「所以你不是在设计，是在赌。」他让青萝记住设计的**两条基本原则**：始终**以质量为目标**、**设计越简单越好**；以及那条贯穿全章的指导思想——**降低模块耦合度，提高模块内聚性**。

青萝又问：耦合和内聚，到底有没有尺子量？长老说有——耦合从松到紧分**七级**，内聚从低到高也分**七级**，模块独立性越好，耦合越低、内聚越高。她这才明白，那五次返工，不是手慢，是蓝图缺位。这一日她没再碰阵盘，先把传讯阵盘的体系结构图画了出来。

## 三、概念正解

### 3.1 软件设计的含义与两个阶段

**软件设计**是软件开发的重要阶段之一，是把**软件需求转换为软件表示**的过程，也是将用户需求准确转化为软件系统的**唯一途径**。它处于软件工程的**技术核心位置**。设计分两个阶段：

| 阶段 | 别名 | 基本任务 |
| --- | --- | --- |
| **高层次设计** | 软件体系结构设计 | 将软件需求转化为**数据结构**和软件的**系统结构**，定义子系统及它们之间的**通信或接口** |
| **详细设计** | —— | 对结构表示细化，得到详尽的数据结构和算法，对所有的类详尽描述，给程序员一份**清晰的规范说明**；即考虑技术上如何实现已设计好的体系结构 |

### 3.2 软件设计的目标与评价标准

**设计目标**：确保软件在**总体结构、外部接口、主要部件功能分配、全局数据结构以及各主要部件之间的接口**等方面的合适性、完备性，从而以**较低的成本**开发出**较高质量**的软件系统。

**评价标准**分三类（软件设计评价可转化为对**软件系统设计模型**的评价）：

1. 以**源系统**作为标准来度量设计模型（实体空间的间接标准），关键词：设计的合理性、专家、用户代表。
2. 以**分析模型与设计模型的一致性**作为标准。
3. 以**目标系统的角度（即软件产品质量属性）**检验系统设计，产品质量标准就是**形式空间的标准**。

### 3.3 设计基本原则：低耦合、高内聚

两条**基本原则**：设计过程中始终**以质量为目标**展开，**设计越简单越好**。指导思想（贯穿全章）：**降低模块耦合度、提高模块内聚性**——这正是衡量**模块独立性**的两把尺子。模块独立性越好，耦合越低、内聚越高。

**耦合七级**（从松到紧，独立性从高到低，越往后越差）：

| 耦合 | 含义（越靠后越坏） |
| --- | --- |
| **非直接耦合** | 模块间无直接关系，独立性最强（最好） |
| **数据耦合** | 模块间通过参数传递**数据** |
| **特征耦合** | 传递的是**数据结构**（整个记录），但只用其中一部分 |
| **控制耦合** | 传递的是**控制信息**（标志、开关），一个模块控制另一个的逻辑 |
| **外部耦合** | 多个模块访问同一**外部环境/全局变量**（受限格式） |
| **公共环境耦合** | 多个模块访问同一**公共数据环境**（公共内存、共享文件） |
| **内容耦合** | 一个模块**直接访问或修改另一个模块的内部数据/代码**，耦合最紧（最坏） |

**内聚七级**（从低到高，独立性从低到高，越往后越好）：

| 内聚 | 含义（越靠后越好） |
| --- | --- |
| **偶然内聚** | 模块内各部分毫无关系，凑在一起（最差） |
| **逻辑内聚** | 把逻辑上相似的功能放一起，由参数决定执行哪个 |
| **时间内聚** | 因同一时间执行而放一起（如初始化） |
| **过程内聚** | 各部分按特定**顺序/过程**执行 |
| **通信内聚** | 各部分使用**同一输入数据或产生同一输出数据** |
| **信息内聚** | 各部分操作同一**数据结构**，各有独立入口 |
| **功能内聚** | 模块内所有部分**协同完成单一功能**，内聚最高（最好） |

记忆口诀：耦合要「松」（追求非直接、数据耦合，远离内容耦合），内聚要「专」（追求功能内聚，远离偶然内聚）。

### 3.4 面向对象（OO）设计的技术原则

| 原则 | 课件要点 |
| --- | --- |
| **开闭原则** | 软件实体对**扩展开放、对修改关闭**；「开」指功能扩展开放，「闭」指原有代码修改封闭 |
| **单一职责原则** | 一个类只有**一个引起它变化的原因**；若有多个动机改变一个类，应拆成多个类各负一责 |
| **里氏代换原则** | 任何**基类**可以出现的地方，**子类**一定可以出现；尽量从抽象类继承而非具体类 |
| **依赖倒置原则** | **抽象不应依赖细节，细节应依赖抽象**；要针对**接口**编程，而不是针对**实现**编程 |
| **接口隔离原则** | 根据客户需求不同，为不同客户端提供不同的服务 |
| **合成复用原则** | 在新对象里使用已有对象作为其一部分，通过**委派**复用已有功能（优先组合/聚合，而非继承） |
| **最少知识原则**（迪米特法则） | 一个对象应当对其他对象有**尽可能少的了解** |

### 3.5 软件体系结构

软件体系结构为软件系统提供**结构、行为和属性的高级抽象**，由**构件、连接件**及指导集成的模式与约束组成。

**模型分类**：结构模型（以构件、连接件刻画结构，侧重整体结构）、框架模型（针对特定问题建结构）、动态模型（研究系统「大颗粒」行为，如重新配置）、过程模型（研究构造系统的步骤）、功能模型（一组功能构件按层次组成，下层向上层提供服务）。

**体系结构分类**：

| 类型 | 特点 |
| --- | --- |
| **单用户体系结构** | 整个系统运行在一台计算机上，一个用户占用全部资源，不共享交换数据（最早最简单） |
| **C/S（客户机/服务器）** | 用户操作模块在**客户机**，数据存在**服务器**数据库 |
| **B/S（浏览器/服务器）** | 用户界面通过**浏览器**实现，极少事务逻辑在前端，**主要事务逻辑在服务器端**；是对 C/S 的一种改进 |
| **中间件多层分布式** | 客户端表示层 + 中间业务逻辑层 + 数据库服务器，三层或多层；把客户和资源分开、**降低服务器负载**，不同组件可用不同语言实现 |

多层分布式设计要点：**安全性、稳定性、易维护、快速响应、系统扩展灵活**；以高性能、高可靠性、高安全性、高扩展性和可管理为原则。

### 3.6 设计模式

**设计模式**让人们更简单方便地**复用成功的软件设计和体系结构**。**四个基本要素**：①模式名称（描述模式的问题、解决方案和效果）；②问题（描述应在何时使用）；③解决方案（描述组成部分之间的关系、职责和协作方式）；④效果（描述应用效果及应权衡的问题）。

**作用**：在工程小组成员间提供通用语义；方便复用成功设计与体系结构；有助于做出有利于系统复用的选择；帮助设计者更快更好完成系统设计。

**三大类（23 种经典模式）**：

| 分类 | 说明 | 常见模式 |
| --- | --- | --- |
| **创建型模式** | 抽象了**实例化过程**，使系统独立于对象如何被创建、组合、表示 | 抽象工厂、生成器、工厂方法、原型、单件 |
| **结构型模式** | 用继承机制组合接口或实现，描述如何**组合对象**实现新功能 | 适配器、桥接、组合、装饰、外观、享元、代理 |
| **行为型模式** | 涉及**算法和对象间职责的分配**，还描述对象/类之间的通信模式 | 职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者 |

**UML** 是一种直观化、明确化、构建和文档化软件系统产物的**通用可视化建模语言**。可先用 UML 建模再编写代码，从一开始就保证系统结构合理；用协作图、组件图分别做硬件、软件设计，用状态图、序列框图描述系统流程细节。

### 3.7 软件设计优化

- **模块设计**：模块划分合适、模块间有一定独立性；功能与接口定义正确；数据结构定义正确；模块内数据流和控制流定义正确。
- **接口设计**：用户接口、硬件接口、软件接口、通信接口都要正确全面，并描述各接口功能、关系及**可测试性**。
- **详细设计**：为每个模块确定算法、数据结构、接口细节，并设计一组测试用例。采用**结构化设计方法**——控制结构一般采用**顺序、选择、循环**三种结构；尽量减少 GOTO 语句；使用**单入口单出口**控制结构；用**自顶向下逐步求精**方法。优点是可读性、可维护性好；缺点是增加存储容量和运行时间（约 **10%-20%**）。
- **详细设计工具**：流程图、伪码、IPO 图（输入加工输出图，说明每个模块的输入/输出数据和数据加工）、PAD 图（问题分析图，用二维树形结构表示控制流，易转程序代码）、判定表（适合描述逻辑条件比较复杂的过程）。
- **界面设计**：保持一致性、有自助功能、易懂、易用、规范、有帮助设施、美观协调、独特性、快捷方式组合、错误保护。

### 3.8 典型系统与数据库设计质量

- **J2EE**：利用 Java 2 平台简化企业解决方案的体系结构，分客户层、Web 层、业务逻辑层、企业信息系统层；常用前端控制器、数据访问对象（DAO）、值对象、截取过滤器、会话面、视图帮助器等模式。
- **.Net**：是 **3 层系统**——UI 层（表示层，离用户最近）、业务逻辑层（承上启下，处于数据访问层与表示层中间）、数据层（实现对数据表的增删改查 CRUD）。
- **数据库设计质量**：分数据层、业务层、表示层；**数据字典**是对数据的**数据项、数据结构、数据流、数据存储、处理逻辑、外部实体**等进行定义和描述，目的是对数据流程图中各元素做出详细说明；数据字典存储各种模式及相应映象，是数据收集与分析所获得的**主要成果**，使信息描述准确以确保系统正确工作，有助于数据的进一步管理和控制。

## 五、考点卡

- **判断题抓手**：
  - 「耦合越高越好。」错——要**降低耦合**，内容耦合最坏、非直接耦合最好。
  - 「内聚越高越好。」对——功能内聚最高最好。
  - 「B/S 是对 C/S 的一种改进。」对（课件原话）。
  - 「软件设计只有详细设计一个阶段。」错——分高层次设计和详细设计两阶段。
- **选择题抓手**：
  - 看到「数据结构、系统结构、子系统、接口」→ 高层次（体系结构）设计；看到「算法、规范说明、给程序员看」→ 详细设计。
  - 看到「对扩展开放、对修改关闭」→ 开闭原则；「一个引起类变化的原因」→ 单一职责；「基类能出现的地方子类也能出现」→ 里氏代换；「针对接口而非实现编程」→ 依赖倒置；「对其他对象了解尽可能少」→ 最少知识原则。
  - 看到「抽象工厂、单件、原型」→ 创建型；「适配器、装饰、代理、外观」→ 结构型；「观察者、策略、命令、迭代器」→ 行为型。
- **填空题抓手**：
  - 软件设计的指导思想是**降低模块耦合度**、**提高模块内聚性**。
  - 耦合从松到紧：非直接、数据、特征、控制、外部、公共环境、**内容**耦合。
  - 内聚从低到高：偶然、逻辑、时间、过程、通信、信息、**功能**内聚。
  - 设计模式三类：**创建型、结构型、行为型**。
- **简答题答题骨架**（简述如何提高软件设计质量）：①以质量为目标、设计越简单越好；②降低耦合、提高内聚（模块独立性）；③遵循 OO 设计原则（开闭、单一职责、里氏、依赖倒置、接口隔离、合成复用、最少知识）；④选合适的体系结构；⑤复用设计模式；⑥结构化详细设计（三结构、单入单出、自顶向下）。
- **设计题答题骨架**（给一个系统做设计优化）：①划分模块，保证模块独立性；②检查耦合级别，把控制/公共环境/内容耦合改为数据/非直接耦合；③检查内聚级别，把偶然/逻辑内聚提升到功能内聚；④选体系结构（单用户/C/S/B/S/多层分布式）；⑤套用设计模式；⑥用流程图/伪码/IPO/PAD/判定表描述详细设计；⑦建数据字典。

## 六、小试炼

**题 1（判断）**：模块之间耦合越紧密，系统越容易维护。
参考答案：错。耦合越紧，改一处动全身，越难维护。设计要**降低耦合**。为什么：内容耦合（最紧）会让模块直接改彼此内部数据，独立性最差。

**题 2（选择）**：下列耦合中**最松（最好）**的是：
A. 内容耦合　B. 公共环境耦合　C. 控制耦合　D. 非直接耦合
参考答案：D。非直接耦合模块间无直接关系，独立性最强；内容耦合最坏。

**题 3（填空）**：软件设计分为两个阶段：______ 设计（软件体系结构设计）和 ______ 设计。
参考答案：高层次；详细。

**题 4（选择）**：「任何基类可以出现的地方，子类一定可以出现」描述的是哪条原则？
A. 开闭原则　B. 里氏代换原则　C. 单一职责原则　D. 依赖倒置原则
参考答案：B。里氏代换原则。

**题 5（简答）**：简述设计模式的四个基本要素。
参考答案：①模式名称（描述模式的问题、解决方案和效果）；②问题（描述应在何时使用）；③解决方案（描述设计组成部分之间的关系、职责与协作方式）；④效果（描述应用效果及使用模式应权衡的问题）。

**题 6（设计）**：青萝的传讯阵盘「改一处动全身」，请给出三条改进设计的方向。
参考答案示例：①把模块从内容耦合降为数据耦合，模块间只通过参数传数据、不直接改别人内部；②把「绘阵+传讯+存储」拆开，让每个模块功能内聚，单一职责；③对外定义清晰接口、针对接口编程（依赖倒置），并先用 UML 画体系结构图再编码。

## 七、易错点

- 把**耦合方向**和**内聚方向**记反：记住「耦合越低越好、内聚越高越好」，模块独立性是它俩的共同目标。
- 把**七级耦合/七级内聚的顺序**背乱：耦合「非直接→数据→特征→控制→外部→公共环境→内容」（越靠后越坏）；内聚「偶然→逻辑→时间→过程→通信→信息→功能」（越靠后越好）。
- 把**高层次设计**和**详细设计**搞混：前者出系统结构与接口，后者出算法与规范说明。
- 把**设计模式三类**张冠李戴：创建型管「怎么造对象」、结构型管「怎么拼对象」、行为型管「对象怎么协作/分派职责」。
- 只背故事不背术语：答题必须落到「耦合、内聚、开闭原则、体系结构、设计模式、数据字典」这些课件原词。
- 把 B/S 和 C/S 关系说反：B/S 是对 C/S 的**改进**，主要事务逻辑在**服务器端**。
