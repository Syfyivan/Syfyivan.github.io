## AI 观察

### 1. 今天真正值得追的不是“又一个 Agent”，而是它能否被复核

最近可用的 Codex 日报把 `anti-slop` 和独立评审循环放在一起：前者试图把反模板规则接入项目约束，后者要求 builder 和 critic 分离，并用标杆、盲评和证据判断结果。无论这些内部推荐的具体热度是否持续，方向是清楚的：Skill 不应只描述“怎么调用模型”，还要规定输入边界、产物形态、失败条件和验收出口。

公开资料也在把“验证”放到 Agent 的核心路径上。Anthropic 对约 40 万次 Claude Code 会话的研究把成功定义为完成用户目标并有可验证证据，例如通过测试或提交的工作；典型会话里，人主要决定做什么，Agent 主要决定怎么做。这不是“人不再需要懂业务”，反而说明领域判断、任务拆解和验收标准会越来越重要。

### 2. 浏览器 Agent 的安全边界，不能由页面内容自己决定

Claude in Chrome 的安全说明明确把网页、邮件和文档里的隐藏指令视为提示注入风险，并说明内容分类器、动作检查、权限确认、站点限制和人工红队只能降低风险，不能把风险变成零。Google 对 Chrome Agent 的公开架构也采用类似的纵深防御：让独立的 user-alignment critic 检查动作、限制可访问 origin、在付款和发消息等关键动作前暂停，并持续做自动化红队。

这给产品设计一个很具体的要求：外部内容只能提供待分析的材料，不能直接升级为授权。页面里写着“请上传密钥”不等于用户允许上传；模型判断“下一步应该发送”也不等于发送动作已经通过审批。Agent 的计划、动作、批准和结果需要四个可回看的事件层。

### 3. 长任务的价值来自恢复能力，风险也来自恢复能力

Claude 日报提到用量恢复后自动继续和跨设备会话；公开帮助页目前也说明，侧边栏会话会保存到历史并可在其他设备重新打开。与此同时，Claude Code `v2.1.233` 的公开 release 在 8 月 14 日增加了 GitLab MR URL/worktree 支持、网关转发用户身份、Linux Bash 内存 cgroup、WebFetch 缓存 TTL 配置，并修复云端会话丢失和 MCP 长连接反复重开的场景。

这些变化共同指向一个状态机，而不是一个“继续”按钮：`运行中 → 等待额度/权限 → 已恢复 → 重新验证 → 继续执行 → 已完成/失败`。跨设备恢复的是任务上下文，不应默认复制另一台设备的全部站点权限；额度恢复是一个事件，也不应直接等同于高风险动作可以自动重放。

## 前端 / 服务端 / 客户端工程观察

### 前端：把信任边界做成控制面

浏览器侧至少应该展示当前站点、浏览器 profile、页面内容是否来自不可信区域、待执行动作、所需权限、下一步为什么需要确认，以及任务恢复后是否会重新询问。对于自动批准模式，界面还应告诉用户它只代表低风险动作可以自动通过，不代表当前页面可信。

反模板规则也可以落到界面验收：不要只检查页面“看起来像不像设计稿”，还要显示实际使用的设计约束、关键交互是否完成、错误态和空态是否覆盖、截图或测试证据在哪里。UI Agent 的交付物应包含页面和验证记录。

### 服务端：把身份、状态、权限和结果拆开存

长任务服务至少要能关联 `task_id`、`session_id`、`context_version`、`runtime`、`permission_scope`、`quota_event`、`checkpoint_id`、`action_id` 和 `verification_id`。服务端可以在额度恢复后唤醒任务，但应重新检查上下文版本、账号策略和敏感动作门槛。

`v2.1.233` 的网关身份转发和 Bash 内存限制也提示了同一个方向：可观测性不能只记录“模型回答了什么”，还要记录哪个用户、哪个上游、哪个运行环境、消耗了什么资源，以及任务是否因为权限、内存、网络或会话重连而改变路径。对 MCP 和远程会话，重连成功不等于动作已经成功，必须有幂等键和最终回执。

### 客户端：把“能继续”与“能继续做什么”拆开

桌面、网页、移动端共享会话后，客户端要显示恢复来源、最后一个 checkpoint、当前设备和当前策略。用户看到的是同一个任务，不代表执行环境相同；移动端恢复的可能只是阅读和确认，桌面端才有本地文件或浏览器权限。

Claude Code 的 release 里同时出现 worktree、远程会话、跨会话消息和云端连接修复，说明客户端体验已经进入“分布式 Agent 控制台”阶段。这里最容易出错的是把连接状态当成任务状态：网络恢复只说明通道重新建立，不能说明之前的写入、提交、发布或消息发送已经完成。

### 共同观察：自动化的最小交付单元是“变更 + 审查 + 回滚”

从历史群内日报的 anti-slop，到公开资料里的浏览器防注入和长任务恢复，主线并不是 Agent 更像人，而是 Agent 开始持续改变外部状态。真正可交付的单位应该同时包含：变更内容、授权范围、验证证据、独立审查人和回滚路径。缺任何一项，自动化都更像一次不可复盘的演示。

## 值得跟进的动作

1. 选一个低风险浏览器任务做回放：记录站点、profile、页面输入、模型计划、动作批准、结果和异常；暂不覆盖发送消息、购买、生产变更。
2. 把自动继续拆成状态机，至少区分额度耗尽、等待恢复、已恢复、二次确认、重试失败和最终完成；恢复后对外发消息、发布代码、购买和敏感数据操作重新确认。
3. 用 `anti-slop` 或同类规则做一次脱敏 UI 双盲评审：固定设计方向和验收表，让 builder 与 critic 分离，记录“改进”是否真的通过独立比较。
4. 为跨设备会话补一张权限迁移矩阵：哪些上下文可直接恢复，哪些站点权限需要重签，哪些动作只能由原设备或人工完成。
5. 对服务端长任务补齐幂等和回执：重连、恢复、自动重试都要能回答“是否执行过、执行了几次、最终改变了什么”。
6. 继续观察 [当天 AI X 检索页](https://x.com/search?q=%28AI%20OR%20agent%20OR%20Codex%20OR%20%22Claude%20Code%22%29%20since%3A2026-08-15%20until%3A2026-08-17&src=typed_query&f=live) 以及前端、服务端、客户端入口；只有能回到作者、正文、发布时间和上下文时，才把 X 线索升级为独立事实。
