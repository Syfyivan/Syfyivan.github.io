## AI 观察

### 1. “会写”正在变成一个有输入门槛的工程步骤

今天 Codex 群的日报把重点放在 `human-writing`：写作前先判断材料够不够，写作中保留事实与个人判断，写作后再检查重复、报告腔和常见模型句式。公开仓库也明确把流程拆成材料核准、推进和中文表达三部分，并提供检查脚本。这个 Skill 的价值不在于让模型“更像人”，而在于把写作任务从一句模糊要求变成一条可检查的流水线。

群内日报还建议拿一段脱敏周报做双盲改写：数字、结论和链接不变，只比较读感。这是一个很小但很实用的评测设计。它把“我觉得更自然”拆成事实保真、信息密度、句式重复和读者盲评几个维度，也提醒我们：内容 Skill 同样需要回归样本，不应只靠作者当场满意。

### 2. Agent 的权限体验，正在从“安全开关”变成工作流吞吐量

Codex 群里有人反馈，手机 App 里大事小情都要求批准，一分钟的任务可能弹出好几次审批；另一条消息则说 Mac 客户端语音聊天长时间停留在思考状态后自动退出，而网页端正常。这些是两位群友在窗口内报告的体验，不足以证明所有设备、账号或版本都有同样问题，但它们指向同一类产品矛盾：代理越能做事，权限、网络、状态恢复和前后台切换越会成为实际吞吐量的一部分。

Claude 群合刊引用的 X 帖子把这条线延伸到 Auto mode、跨会话消息与 Managed Agents。由于 X 正文本轮无法稳定展开，本文不把“8 月 14 日起默认启用”或“已面向哪些平台推出”当成独立核验事实；可以确认的是，公开 CLI 文档仍把权限模式、允许/禁止工具和权限提示作为一等配置，公开 changelog 也记录了跨会话消息滞留、会话恢复和长任务稳定性方面的修复。工程上，安全模式不是一个二元开关，而是任务成本、可审计性和用户注意力的联合约束。

### 3. 质量控制的对象，从代码扩展到表达和上下文

今天两份日报看似一个讲中文写作，一个讲 Claude Code 的 Agent 能力，实质上都在处理“模型知道什么、应该保留什么、什么时候需要停下来确认”。`human-writing` 把材料门槛和事实核准放在前面；Claude Code changelog 则显示，精确字符串替换、工作区信任提示、网关额度警告、跨会话消息和 Remote Control 恢复都在持续被产品化。

这意味着 AI 工作流的验收不能只看最终产物。至少要同时看输入是否足够、硬约束是否被保留、工具副作用是否经过批准、上下文是否可恢复、结果是否能回到原始证据。对写作是“数字和链接有没有被改写”，对代码是“变更和测试是否对应”，对客户端则是“状态是否能解释”。

## 前端 / 服务端 / 客户端工程观察

### 前端：把“等待审批”和“长任务恢复”做成可读状态

手机端频繁审批和 Mac 端语音长时间思考后退出，首先是状态表达问题。界面不应只显示一个转圈，而应区分：正在执行、等待权限、网络重连、后台恢复、上下文压缩、工具失败、需要用户输入和已完成待验证。每次审批最好带上动作、目标、风险和允许范围，用户才能判断是批准一次、允许同类动作，还是暂停任务。

对于长任务，前端还应保留最近一次状态摘要、最后一次工具调用、当前约束和恢复入口。用户离开后再回来，第一屏应能回答“Agent 现在在哪一步”和“我批准它继续会发生什么”，而不是让用户重新阅读完整对话。

### 服务端：把审批、上下文、额度和结果分成可对账事件

服务端可以把一次运行拆成 `task_id`、`attempt_id`、`context_version`、`instruction_digest`、`tool_call_id`、`approval_id`、`quota_bucket` 和 `verification_id`。审批事件不要直接等价于工具成功；额度公告不要直接等价于额度到账；会话发出消息也不要直接等价于对方已经消费。

更稳妥的状态链可以是：`requested → classified → waiting_approval → approved/denied → executed → verified`。额度或运营事件则至少区分 `announced → propagating → applied → visible_to_user → reconciled`。有了这些中间状态，才能解释为什么用户看到的是“反复审批”“网页正常但 App 退出”或“日报说已更新但客户端仍显示旧状态”。

### 客户端：稳定性和权限策略必须按入口、版本与网络路径拆开

群内关于语音聊天的反馈不能直接归因于模型，也不能直接归因于 Mac 客户端。需要记录客户端版本、设备型号、网络路径、前后台切换、会话时长、最后一个服务端事件和是否发生上下文压缩，再与网页端同一账号、同一任务做对照。否则“网页正常、App 失败”只是现象，不是根因。

同样，Auto mode 或任何“减少确认”的入口都应该显示当前权限模式、允许范围、管理员策略和降级原因。公开文档里已经有 `--permission-mode`、允许/禁止工具和权限提示等概念；客户端若把它们压成一个按钮，用户就很难知道一次批准是临时授权、项目级规则还是组织级策略。

### 共同观察：AI 产品需要交付“结果 + 证据链”

今天的输入从中文 Skill 到跨会话 Agent，再到移动端语音故障，表面上分散，底层却是同一个问题：系统能否把自己的状态、边界和依据交给用户检查。好看的改写需要原稿对照，自动执行需要审批记录，客户端恢复需要事件日志，安全能力宣称需要原始帖子和适用条件。

当证据链断掉时，模型写得越顺、权限点得越快、界面显示得越简洁，用户反而越容易误判系统已经完成了什么。AI 工具的下一个竞争点，可能不是再增加一个入口，而是让每个入口都能解释自己的状态。

## 值得跟进的动作

1. 取一段 300 字脱敏周报做双盲改写：锁定数字、结论、链接和段落顺序，分别评估事实保真、信息密度、重复度与读者盲评；把原稿、改写稿和检查结果保存成回归样本。
2. 给一个两小时以上的 Agent 任务增加四个检查点：启动、上下文压缩后、关键工具调用后、最终验证前；每次记录硬约束、已完成项、待审批动作和偏航风险。
3. 对手机端频繁审批做一次最小复现：固定账号、设备、网络、任务和权限模式，记录审批次数、间隔、动作类型及网页端对照，不要先把问题归因到模型能力。
4. 对 Mac 语音问题采集可脱敏的客户端版本、会话时长、前后台事件、网络重连和最后服务端事件；若能复现，再比较网页端和 App 端的同任务行为。
5. 在客户端把权限状态、上下文版本、额度窗口和恢复状态放到诊断面板；把“已宣布”“正在传播”“已生效”“用户可见”分开显示。
6. 继续观察 [当天 AI / Codex / Claude Code X 检索页](https://x.com/search?q=%28Codex%20OR%20%22Claude%20Code%22%20OR%20AI%29%20since%3A2026-08-10%20until%3A2026-08-11&src=typed_query&f=live) 和 [当天前端 / JavaScript 检索页](https://x.com/search?q=%28React%20OR%20JavaScript%20OR%20frontend%29%20since%3A2026-08-10%20until%3A2026-08-11&src=typed_query&f=live)。只有能回到原帖、作者、时间和上下文时，才把 X 线索升级为产品事实。
