这篇文章只讲一次高流量活动的服务端压测和隔离准备。

项目模型面向千万级 UV，压测覆盖首屏、配置、报名、任务、答题和抽奖等七个 HTTP 入口。我负责过服务端隔离改造、准入验证和压测材料，并参与执行；最终报告由测试和研发团队共同完成。

面试时不需要按改造日期背诵，而要讲清楚：为什么隔离先于 QPS、怎样证明业务真的执行、怎样给出不过度外推的容量结论。

## 一、十五秒怎么介绍

> 我负责过一个千万级 UV 目标活动的压测隔离和执行准备。压测覆盖七个核心接口，压力标记从 HTTP 一直透传到 RPC、数据库、缓存和消息；写请求进入影子表和隔离 key，发奖、通知等真实副作用被 mock 或拦截。压测获得了多个接口约 500 QPS 下的延迟数据，也发现了 HTTP 成功但业务失败和下游拒绝压力流量的问题。

## 二、默认两到三分钟主回答

> 这个项目面向千万级 UV，压测覆盖首屏、配置、报名、任务、答题和抽奖七个入口。我认为最大风险不是接口扛不住，而是压力标记在某一层丢失以后写到正式资源，甚至触发真实发奖。所以我的第一步不是加 QPS，而是建立完整隔离链。
>
> 压力标记从固定 Header 进入，经 API 上下文和 RPC metadata 透传到领域服务，再驱动数据库影子表、缓存 namespace 和消息或权益的 mock。专用压力环境缺标、未知标和 query 标全部 fail-closed；普通环境收到压力标也拒绝，领域服务直连还有第二层守卫。每个写场景先做正负 canary，确认 SQL 只落影子表、缓存 key 带 namespace、真实消息和权益为零，才允许放量。
>
> 我还把 HTTP 成功和业务成功分开。报名后要能查到影子报名，任务后积分和目标记录要一致，抽奖后机会、库存和记录要匹配。真实执行中，多个读和抽奖接口在约 500 QPS 下延迟稳定；任务与答题混合场景只有约 97.77% 成功，暴露出参数和下游准入问题，因此不能宣布整套系统容量通过。
>
> 这个项目让我形成的核心判断是：影子表只隔离数据名，不隔离物理 CPU、IO 和连接池；HTTP 200 也不证明业务链完整。一个可信的压测结论必须同时包含流量模型、隔离证据、业务断言、性能指标和明确的未覆盖边界。

## 三、面试官真正会听什么

| 面试官的判断 | 你要给出的证据 |
| --- | --- |
| 是否有安全意识 | 两层 fail-closed、影子资源、真实副作用为零 |
| 是否理解压测 | UV 到接口 QPS 的拆解、逐场景准入和分阶段放量 |
| 是否理解业务成功 | HTTP 状态、响应体和写后查询三层断言 |
| 是否会解释结果 | 500 QPS、P99、97.77% 失败和未覆盖边界 |
| 是否有所有权 | 隔离改造、canary、证据核对和执行参与 |

## 四、为什么压测第一件事不是提高 QPS

活动链路包含：

```text
报名
任务发分
答题
抽奖机会
奖品库存
中奖记录
发券 / 发奖
站内信 / 通知
```

如果压力标记在某一层丢失，可能污染正式数据或发出真实权益。

所以顺序必须是：

```text
隔离设计
  -> 单请求准入
  -> 正负 canary
  -> 小流量 smoke
  -> 分接口放量
  -> 混合场景
```

## 五、压测方案的七个关键收敛点

### 收敛一：先处理领域侧数据和副作用隔离

第一轮改造让压力上下文进入领域服务，并让数据库访问根据上下文选择影子资源。同时对真实书架、发奖和通知等副作用增加压力场景分支。

这一版的重点是“写到哪里”和“哪些不能真的执行”。

### 收敛二：让 HTTP 入口和 RPC 全程保留压力上下文

API 入口读取固定 Header，把值写入请求上下文，并通过 RPC metadata 传给领域服务。

同一天把“开发真机影子联调”和“正式压力流量”拆成两种场景：

- 开发影子：允许部分真实读，用于功能联调；
- 压力场景：真实下游写必须为零。

两者不能共用一个模糊的 stress 布尔值。

### 收敛三：把压力上下文延伸到抽奖后置链路

抽奖不是一个同步函数结束。资格查询、库存、中奖记录和后置发奖可能经过二次 RPC 或异步逻辑。

这一阶段修复了压力上下文在后续调用中丢失的问题，避免入口带标、抽奖主链带标，但发奖阶段回到正式路径。

### 收敛四：错误环境和错误标记全部 fail-closed

守卫规则：

```text
专用压力环境
  缺标 -> 403
  未知标 -> 403
  query 标 -> 403
  正确 Header -> 允许

普通环境
  带任何压力标 -> 403
  无标 -> 正常业务
```

领域服务直连也有对应保护，不能只信 API 网关。

### 收敛五：影子表之后继续补齐缓存与共享资源边界

团队把压力守卫和业务分支整合，并继续把 DB handler 改为上下文感知。

随后发现：影子表已经生效，不代表缓存客户端自动带上压力 namespace。因此继续补缓存上下文透传。

### 收敛六：验证中间件、刷新和二次上下文不会丢标

一些中间件、缓存刷新或二次上下文创建会丢失 metadata。这一轮继续确保 Header 进入后，在整个 HTTP 链路中不会被 normalize 掉。

### 最终执行：从单请求准入到约 500 QPS

每个写场景先做单请求准入，再由压力平台放量。最终多个读和抽奖场景达到约 500 QPS；任务与答题混合场景暴露失败，需要进一步排查。

## 六、七个核心 HTTP 入口

| 场景 | 类型 | 主要验证 |
| --- | --- | --- |
| 首屏组件聚合 | 读 | 多组件聚合、进度和资格 |
| 活动配置读取 | 读 | 配置缓存和序列化 |
| 报名 | 写 | 幂等、报名表、通知拦截 |
| 报名查询 | 读 | 影子报名状态 |
| 任务行为提交 | 写 | 限次、积分和书架 mock |
| 答题 | 写 | 答案、积分、次数 |
| 抽奖 | 写 | 资格、库存、记录和发奖拦截 |

内部 RPC 不是独立 HTTP 压测入口，但必须在 trace 中确认被真实执行。

## 七、压力标记的传播

```text
HTTP Header
  -> API context
  -> persistent RPC metadata
  -> domain context
  -> DB router
  -> KV namespace
  -> MQ / external side-effect decision
```

### 为什么 query 标记被禁止

query 参数容易被：

- 业务参数绑定忽略；
- 跳转时复制；
- 日志或代理改写；
- 下游 RPC 丢失；
- 普通用户构造。

固定 Header 更容易被中间件统一处理。

## 八、两层 fail-closed

### API 层

验证运行环境、区域、集群和标记组合，不匹配立即终止。

### Domain 层

验证 RPC metadata。即使有人绕过 API 直连领域服务，错误压力请求仍不能写入。

为什么不是 fail-open？因为继续执行的最坏结果是真实发奖和数据污染，风险不可接受。

## 九、数据库隔离

压力请求通过 ORM 路由到：

```text
activity_xxx_stress
```

本轮准备了十余张影子表，覆盖报名、积分、目标、抽奖次数、库存和记录等。

### 禁止 fallback

如果影子表不存在，必须报错，不能自动回到正式表。否则“为了让压测继续”会直接污染线上数据。

### 影子表不是独立数据库

表名不同，但可能共享：

- 数据库实例；
- CPU / IO；
- 连接池；
- 锁和热点索引。

因此还需要平台限流和资源 owner 的容量结论。

## 十、缓存隔离

需要盘点所有写 key：

- 报名状态；
- 用户积分；
- 目标进度；
- 答题计数；
- 抽奖机会；
- 抽奖锁；
- 配置缓存；
- 参与人数。

每个 key 要么增加稳定 pressure namespace，要么证明本场景只读。

### 为什么只验证 Redis 不够

系统可能同时使用 Redis 和持久化 KV。两套客户端的上下文传播和 namespace 规则不同，都要抽样验证。

## 十一、副作用隔离

| 副作用 | 压力场景 |
| --- | --- |
| 真实加书架 | 不执行 |
| 书架状态检查 | 返回受控 mock |
| 权益 / 券 | mock 或 no-op |
| 站内信 / 通知 | no-op |
| 发奖消息 | 影子 topic 或禁止 |
| 真实消费者容量 | 不纳入本轮结论 |

为什么书架读也可能 mock？本轮目标是活动服务容量，如果把书架下游一起压入，无法区分瓶颈归属，而且下游可能不允许压力流量。

## 十二、单请求准入

一次写请求通过前，需要收集完整证据：

```text
HTTP 200 + 业务 success
API 日志有 pressure marker
Domain 日志 marker 相同
SQL 只出现影子表
KV key 有压力 namespace
真实下游 RPC 为 0 或受控 mock
真实表、正式 key、正式 topic 无变化
```

缺少任一关键证据，都不能开始放量。

## 十三、正负 canary

正向：

```text
专用环境 + 正确 Header -> 200，业务成功
```

负向：

```text
专用环境 + 缺标 -> 403
专用环境 + 未知标 -> 403
专用环境 + query 标 -> 403
普通环境 + 压力标 -> 403
Domain 直连缺标 -> RPC error
```

负向验证同样重要。只测“正确请求能通过”，不能证明错误请求会被拦截。

## 十四、业务断言

### 报名

写后查询影子报名状态；重复报名只产生一条有效记录。

### 任务

本次 added_score 正确；影子积分明细和目标记录一致；重复 request 不重复加分。

### 答题

答案处理、计数和积分进入影子资源。

### 抽奖

机会扣减、库存、中奖记录和返回结果一致；真实发奖为零。

为什么不只看 HTTP 200？有一次工具层返回成功，但业务体是参数错误，请求没有真正进入领域链路。

## 十五、UV 到 QPS

```text
峰值页面 UV
* 首屏接口数
* 峰值集中系数
= 首屏读 QPS

参与 UV
* 人均任务次数
* 峰值集中系数
= 任务写 QPS

抽奖人数
* 人均抽奖次数
* 连抽请求折算
= 抽奖 QPS
```

不能用活动总 UV 直接除以总秒数，因为大促流量会在资源位开放、任务刷新和开奖时集中。

## 十六、放量顺序

```text
1 QPS / 并发 1 / 数分钟
  -> 只读接口
  -> 报名写
  -> 单任务写
  -> 答题
  -> 抽奖
  -> 混合场景
  -> 目标档位
```

每阶段观察 P50/P99、错误率、CPU、内存、连接池、慢 SQL、锁等待、KV 延迟和消息水位。

## 十七、已确认的阶段容量结果

测试环境为单机、小规格实例。

### 首屏组件聚合

约 500 QPS，成功率 100%，P99 约 40ms。

### 活动配置读取

约 500 QPS，成功率 100%，P99 约 13ms。

### 报名

放量到数百 QPS 未见错误，但延迟随压力上升，需要保守评估拐点。

### 任务与答题混合

接近 500 QPS 时成功率约 97.77%，有数千次失败，不能判定通过。

### 抽奖

约 500 QPS，成功率 100%，P99 约 60ms。

## 十八、为什么 97.77% 不能算通过

要看失败原因：

- 如果是压力工具参数错误，请求没进入业务；
- 如果是下游拒绝压力流量，链路不完整；
- 如果是系统容量错误，说明目标未达成。

无论哪一种，都不能用 HTTP 总量稀释后说“基本通过”。

## 十九、下游拒绝压力流量

活动服务调用作者或书架类下游时，下游可能有 `onStressDeny` 安全策略。

处理选择：

1. 本轮目标不包含下游容量：在活动侧 mock，明确结论边界；
2. 需要联合压测：提前与下游 owner 建立准入、隔离和限额；
3. 不能为了跑通私自移除下游保护。

## 二十、HTTP 成功但业务失败

压力平台可能只把 HTTP 200 当成功。业务体可能是：

```json
{"code": 2, "message": "invalid params"}
```

因此压测脚本必须解析响应体并断言业务字段；必要时请求后查询影子状态。

## 二十一、立即停止条件

- 正式表出现压力数据；
- 正式缓存 key 变化；
- 正式消息或真实权益被触发；
- 压力标记在任一层丢失；
- 请求进入错误环境；
- 影子资源缺失却发生 fallback；
- P99、错误率或慢 SQL 超阈值；
- 实例 OOM、重启或健康检查失败；
- 共享资源影响其他流量。

## 二十二、通过标准

- 目标 QPS 达成；
- P99 和错误率满足预先约定 SLA；
- 业务断言通过，不是入口短路；
- 本轮涉及影子表有完整数据；
- 正式表和真实副作用为零；
- 缓存、消息和下游隔离有证据；
- 每轮保留 request_id、trace、SQL、KV 和 owner 结论。

## 二十三、为什么不能宣称完整容量通过

本轮没有覆盖：

- 真实发奖下游容量；
- 正式 MQ consumer；
- 全部离线任务；
- 多机正式规格；
- 完整目标 UV 的全链路混合模型。

因此结论只能是“获得阶段性接口容量数据并验证部分隔离”，不能说完整系统已通过千万级容量。

- 整体上线保障。

## 二十五、备用的完整口述版

> 我负责过一个千万级 UV 目标活动的服务端压测隔离和执行准备，覆盖首屏、配置、报名、任务、答题和抽奖七个 HTTP 入口。
>
> 我认为这类压测最重要的不是先把 QPS 打高，而是保证压力数据不会进入正式资源。所以我先设计压力标记从 Header 进入，经 API 上下文和 RPC metadata 透传到领域服务，再驱动数据库影子表、缓存 namespace 和副作用 mock。专用压力环境缺标、未知标和 query 标全部 fail-closed；普通环境带压力标也拒绝，领域服务直连还有第二层守卫。
>
> 推进时先完成领域侧数据和副作用隔离，再接 HTTP 入口、拆分开发影子与正式压力场景，并补抽奖后续链路的 metadata；随后增加正负 guard、数据库和缓存路由，并持续验证中间件后的标记保持。每个写接口都先做单请求准入，确认 SQL 只落影子表、KV 有 namespace、真实权益和消息为零，才进入放量。
>
> 最终首屏、配置和抽奖等接口在约 500 QPS 下表现稳定，P99 大约在十几到六十毫秒；任务与答题混合场景只有约 97.77% 成功，暴露出参数和下游准入问题。这个结果让我认识到 HTTP 200 不等于业务成功，影子表也不等于物理隔离。压测结论必须同时包含业务断言、隔离证据和未覆盖边界。

## 二十六、高频追问

### 为什么只允许 Header

便于入口统一处理和 RPC metadata 透传，避免 query 被普通业务、跳转或代理误用。

### 影子表是否安全

只隔离数据名，不隔离物理 CPU、IO、连接池和锁，还需要限流与 owner 结论。

### 为什么漏标直接 403

漏标继续执行可能写正式资源，风险不可接受。

### 怎么验证没有真实发奖

查下游调用 trace、正式中奖表、正式消息 topic 和权益记录基线，不只看代码分支。

### 为什么不压到系统崩溃

目标是验证业务目标和余量，不是破坏共享环境。达到停压阈值就应停止。

### 500 QPS 能支撑多少 UV

不能直接换算，要结合峰值集中度、接口触发次数和人均行为。文章中的 QPS 是接口阶段结果，不是完整 UV 结论。

### 成功率 97.77% 为什么不接受

因为失败场景未满足业务 SLA，而且部分请求可能根本没走完整业务链。

## 二十七、公开边界

- 隔离与放量阶段来自真实服务端改造和压测报告；公开版删除环境、标记值和内部工单。
- QPS 与 P99 使用近似量级；它们来自单机测试环境，不能外推为线上总容量。
- 最终报告和整体压测是团队成果，个人负责隔离准备、部分改造、证据核对和执行参与。
