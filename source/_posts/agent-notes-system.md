## 第一章：Agent Runtime 的运行原理

<a id="terms"></a>

### 1.1 系统角色与统一术语

Agent 系统让模型参与决定后续动作，由程序调用真实能力，并将取得的观察用于继续处理目标。理解系统时，先区分参与者，再区分它们操作的数据。

| 参与者 | 主要职责 | 交接关系 |
| --- | --- | --- |
| 应用 | 接收请求，认证用户，管理任务与会话，提供业务要求并展示结果 | 把任务和运行配置提交给 Runtime，消费运行事件与结果 |
| Agent Runtime | 承载模型调用、工具调度、运行记录和控制逻辑 | 协调内部模块，连接模型服务、工具和应用 |
| 模型 | 根据当前输入生成答复、动作请求或约定格式的内容 | 将生成结果返回模型接入模块 |
| 工具 | 根据参数执行操作，检查自身业务前提，返回实际结果 | 接受工具管理与执行模块的调用 |

这里的 Runtime 是一个软件职责集合。应用可以在进程内嵌入它，也可以调用独立服务。权限检查、资源调度和预算限制由程序作出决定；任务中的动作选择可以交给模型。

全文采用以下通用术语，后文保持同一含义。

| 术语 | 定义 |
| --- | --- |
| 任务 | 要完成的业务目标，以及适用要求和验收条件 |
| 会话 | 保存一组相关交互的容器 |
| 运行 | 针对任务启动的一次逻辑执行，可经历等待和恢复 |
| 运行记录 | 保存运行身份、进度、配置引用、待处理工作和已确认结果的数据 |
| 运行状态 | 运行记录中的生命周期字段 |
| 模型调用 | 向模型服务提交一次请求并处理其响应 |
| Agent Loop | 组织输入、模型生成、动作处理与反馈更新的循环过程 |
| 编排 | 规定执行单元之间的依赖、分支、执行者与结果交接的控制机制 |
| 协议 | 参与方约定的消息格式、关联规则与交互要求 |
| 上下文 | 当前模型调用实际使用的输入信息 |
| Memory | 保留、维护和取回既往信息的机制；其保存的数据称为记忆记录 |

这些名称用于本文的系统分析。接入具体产品时，需要把 API 的 `thread`、`turn`、`status` 等对象逐一映射到应用的数据模型；原始字段按该接口定义解释。

<a id="entry"></a>

### 1.2 运行入口与主干五步

应用收到并定位任务后，向 Runtime 提交任务目标、会话关联和运行配置。运行配置提供模型选择、工具范围、工作环境和权限策略等信息；实际字段取决于接入方式。Runtime 据此建立或加载运行记录，分配当前执行所需的资源。

下面从 Runtime 整体职责出发，用五步表示单轮主要处理。表中的输出就是下一环节的输入；内部责任由[模块协作](#modules)进一步确定。

| 步骤 | 主要输入 | 本步输出 |
| --- | --- | --- |
| 组装上下文 | 当前要求、运行记录、可用资料与输入预算 | 选定内容、工具定义和调用要求 |
| 调用模型 | 选定内容与调用要求 | 解析后的响应项、生成状态与协议标识 |
| 处理响应 | 模型响应与当前执行条件 | 答复、真实工具结果、错误或待处理请求 |
| 更新运行记录 | 本轮已确认信息与待处理事项 | 更新后的运行记录 |
| 决定下一步 | 更新后的记录、预算和外部控制信号 | 继续、等待或终止的决定 |

继续时回到输入组装；等待时保留关联请求与恢复入口；终止时向应用交回结果和终止原因。上述顺序是理解职责的骨架。实现中可以在生成响应时发布事件，也要在副作用发生前后写入恢复所需的数据；[运行记录](#record)和[恢复机制](#recovery)说明具体写入责任。

<a id="modules"></a>

### 1.3 Runtime 模块及协作

一次运行需要信息选择、接口通信、真实执行和状态维护。以下六个模块按这些责任划分，模块名在全文保持一致。

| 模块 | 自己完成的处理 | 对外输出 |
| --- | --- | --- |
| 循环控制模块 | 识别响应用途，分派后续工作，检查控制条件并决定流转 | 模型或工具调度、等待请求、终止决定 |
| 上下文管理模块 | 选择资料，组织来源与角色，控制输入预算 | 选定的本轮内容 |
| 模型接入模块 | 序列化接口请求，接收并归并事件，保留 API 字段 | 响应内容、生成状态或调用错误 |
| 工具管理与执行模块 | 管理工具定义与入口，检查调用条件，调度并收集实际执行 | 工具结果、拒绝原因或审批请求 |
| 状态与持久化模块 | 保存当前运行记录、交互历史和恢复数据 | 一致的记录视图及检查点 |
| 事件与输出模块 | 将已确认的进度、状态变化和结果转换成应用事件 | 可关联、可消费的输出事件 |

上下文管理模块决定提供哪些信息；模型接入模块将这些信息转换为指定 API 的请求。工具管理与执行模块接收循环控制模块分派的动作，把工具返回值交回后者。状态与持久化模块统一保存这些变化，事件与输出模块据此向应用报告。

六个模块表达的是软件责任，项目可以把多个责任放在同一个进程或组件中。判断边界是否清楚，要看输入、动作和结果归属是否明确。

### 1.4 模型调用与工具调用协议

入口与模块分工已经确定。接下来沿模型接入模块的边界，依次说明请求构造、流式接收、响应解释，以及工具调用与结果的关联。

<a id="request"></a>

#### 请求组成与对话状态传递

模型接入模块已经取得选定内容。它现在需要将内容映射到接口字段，并明确哪些信息由本次请求提供、哪些由服务端状态续接。

从用途看，请求可能携带指令与输入、工具定义、调用配置。是否出现以及是否必填，由具体 API 决定。按核对的 Claude Messages API `2026-10-21` 版文档，直接请求体中的 `model`、`max_tokens` 和 `messages` 是必需参数；`system` 与 `tools` 按需提供。工具定义中的参数结构约束（Schema）描述模型可生成的参数，执行代码保留在工具侧。[Claude Messages 接口](https://platform.claude.com/docs/en/api/messages/create)

对话状态传递有两种常见安排。客户端维护历史时，上下文管理模块选择本轮需要的历史，模型接入模块随请求重新发送。服务端保存状态时，客户端可以通过会话标识或前次响应标识续接，由服务端合成有效输入。

续接时仍需按接口要求提交当前输入及配置。OpenAI Responses 的 `previous_response_id` 用于关联前次响应；前次顶层 `instructions` 不会随该标识自动继承，需要继续生效时应再次提供。应用应明确每类信息由哪一端保存。[Responses 对话状态](https://developers.openai.com/api/docs/guides/conversation-state)、[指令续接规则](https://developers.openai.com/api/docs/guides/migrate-to-responses)

请求发出前，模型接入模块检查字段组合和模型能力是否相容，并记录实际模型及配置版本。接口不接受的字段组合属于调用错误；处理与重试规则集中在[恢复机制](#recovery)。

<a id="stream"></a>

#### 流式响应的归并与完成点

请求发送后，模型服务可以分批返回响应。模型接入模块先按响应项标识识别片段归属，再分别累积文字和工具参数，维护每项是否已经完成。

OpenAI Responses 的 `response.function_call_arguments.delta` 携带参数增量，`response.function_call_arguments.done` 标记参数流完成；工具名称与调用标识还要从相应调用项取得。参数完成事件只完成该部分数据的接收，运行层仍需检查对应项和响应的状态。[工具调用流式事件](https://developers.openai.com/api/docs/guides/function-calling)

工具管理与执行模块接收的是通过完整性检查的调用。模型接入模块遇到断流、未闭合参数或缺失完成信息时，记录不完整响应，并把错误交给循环控制模块。应用可以较早展示文字片段，但展示事件与可执行调用分别交接。

生成过程与工具执行可以在某些实现中重叠。无论采用哪种调度，单个工具动作都应具有已确认的名称、参数与关联标识；并发成立的条件见[依赖与并发](#orchestration)。

<a id="response"></a>

#### 响应内容、生成状态与参数校验

接入模块完成协议解析后，循环控制模块同时读取响应内容和生成状态。内容说明生成了什么，生成状态说明响应为何停止以及是否完整。二者共同决定哪些信息可继续处理。

在 Claude Messages 中，`stop_reason` 的 `end_turn` 表示自然结束，`tool_use` 表示工具使用请求，`max_tokens` 表示达到输出上限，`pause_turn` 表示服务端工具循环需要续接。`end_turn` 本身只描述响应结束。[Claude 停止原因](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

在 OpenAI Responses 中，循环控制模块从 `output` 中的 `type: "function_call"` 识别普通函数调用，并结合响应 `status` 检查完整性。`status: "incomplete"` 时可以读取 `incomplete_details.reason`，例如输出上限导致的 `max_output_tokens`。适配层保留这些原始字段，再给运行层提供对应结论。[OpenAI 结构化输出处理](https://developers.openai.com/api/docs/guides/structured-outputs)

答复文字、工具请求与其他协议项可能出现在同一响应中。结构化输出描述答复的格式要求，因此由答复解析逻辑校验；工具请求则按专门的协议项分派。

调用进入执行前，工具管理与执行模块完成三个检查：解析参数表示；按工具声明的 Schema 检查结构；检查业务、授权和执行条件。JSON 解析只确认语法，Schema 约束确认字段结构，实际操作条件由资源服务与[授权机制](#permissions)提供。

解析或 Schema 检查失败时，模块生成关联到该调用的具体错误，供模型修正。缺少用户输入时，循环控制模块通过约定的输入请求结构创建等待事项。等待对象与后续答复的关联在[状态流转](#lifecycle)说明。

<a id="correlation"></a>

#### 工具调用标识与结果关联

校验后的工具请求需要在执行期间保持身份，以便结果回到原请求。以下表格限定为普通自定义函数工具，字段直接沿用各 API 名称。

| 接口 | 调用请求 | 回传结果 |
| --- | --- | --- |
| OpenAI Responses | `function_call` 项的 `call_id`、`name`、JSON 字符串 `arguments` | `function_call_output` 项的相同 `call_id` 与 `output` |
| OpenAI Chat Completions | `tool_calls[].id`、`function.name`、`function.arguments` | 工具消息的 `tool_call_id` 与 `content` |
| Claude Messages | `tool_use` 块的 `id`、`name`、对象 `input` | `tool_result` 块的 `tool_use_id` 与 `content` |

Responses 调用项自己的 `id` 标识响应项，`call_id` 用于结果关联。Claude 的客户端工具结果通过后续 `user` 消息中的 `tool_result` 块提交，并遵守该接口的排列要求。[OpenAI 字段](https://developers.openai.com/api/docs/guides/function-calling)、[Claude 字段与排列](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

工具管理与执行模块保存待完成调用。结果返回时，先按标识定位原请求，检查所属运行，再标记结果已经收到。已接收结果的重复投递按事件标识去重；未知或跨运行的关联进入错误处理。结果归属以保存的映射为依据。

实际执行者还要明确。客户端工具由应用侧工具实现或其调用的服务执行；服务端托管工具由提供方执行，应用读取其结果或继续协议。调用标识解决结果关联，跨重试的业务去重见[幂等机制](#recovery)。

<a id="tools"></a>

### 1.5 工具接入、MCP 与 Skill

工具管理与执行模块先取得工具定义，再把工具名称映射到真实入口。定义说明用途、参数、前置条件、是否有副作用以及结果含义。执行入口可采用本地函数、命令行接口（CLI）子进程、HTTP/RPC 服务或 MCP 工具服务。

对于函数，执行器转换参数并收集返回值与异常；对于 CLI，执行器设置工作目录和环境，收集退出码及输出；对于远端服务，执行器处理请求身份、返回体和网络状态。底层业务服务在真正读写时维护自己的业务约束。

Model Context Protocol（MCP）将外部能力接入协议化。Host 是使用能力的应用，Client 是 Host 内的协议通信组件，Server 提供工具、资源或提示模板。按本文固定的 MCP `2025-06-18` 版本，Client 发送 `initialize` 协商版本和能力，确认后发 `notifications/initialized`，再使用服务端声明的能力。[MCP 生命周期](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)

`tools/list` 返回工具定义；`tools/call` 在 `params.name` 与 `params.arguments` 中携带调用。Host 保存模型调用标识与 MCP 请求的对应关系，JSON-RPC `id` 负责 MCP 请求响应配对。RPC 错误与工具结果里的 `isError` 分开处理。[MCP 工具协议](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

Skill 采用另一种扩展方式：它提供可复用的任务方法及资源。Agent Skills 规范要求目录至少包含带元数据与正文的 `SKILL.md`，还可包含脚本、参考材料和资产。宿主先发现技能，选择后加载所需内容；脚本仍通过执行工具运行。[Agent Skills 格式](https://agentskills.io/specification)

工具提供动作，MCP 提供连接约定，Skill 提供方法与材料。Skill 的文本影响上下文，宿主的工具接口与权限控制决定真实执行。技能加载可以发生在上下文准备或后续按需读取时。

<a id="browser"></a>

### 1.6 浏览器观察与元素定位

浏览器工具把页面状态转换成模型可用的观察，并将选定目标转换成浏览器操作。DOM、可访问性树、截图和提取文本是观察的不同表示：它们分别侧重结构、语义、视觉和阅读内容。

浏览器从页面语义生成可访问性树。该树与 DOM 具有不同组织目标，节点并非一一对应。工具可以选择其中适合交互的节点，为模型提供简短引用，并在内部保存实际定位信息。

Chrome DevTools Protocol（CDP）提供浏览器调试与控制接口。其中，`Accessibility.AXNode.nodeId` 标识 AX 节点，可选字段 `backendDOMNodeId` 关联 `DOM.BackendNodeId`。`DOM.resolveNode` 接收的参数名则是 `backendNodeId`。工具引用、AX 标识和 DOM backend 标识属于三个不同位置。[CDP 协议定义](https://github.com/ChromeDevTools/devtools-protocol/blob/7245ec551bc9d450170193456ab3965bb7e716cb/json/browser_protocol.json)

在 agent-browser `v0.39.1` 的 Chrome 路径中，Rust CLI 向常驻 daemon 发命令，daemon 通过 CDP 控制浏览器。元素引用映射项保存可选 backend 节点标识、角色、名称与 frame 等信息，再在相应浏览器目标中解析节点。该版本的 iOS Safari 路径采用 WebDriver，部署时需按所用后端判断。[版本说明](https://github.com/vercel-labs/agent-browser/blob/v0.39.1/README.md)、[元素实现](https://github.com/vercel-labs/agent-browser/blob/v0.39.1/cli/src/native/element.rs)

节点脱离文档、frame 改变或解析失败时，工具返回定位失效。重新观察后，还需检查目标名称、语义与业务身份，再决定是否操作。动作回执和新的页面状态交给后续判断，业务结果由[验收机制](#acceptance)检查。

浏览器会话可以隔离 Cookie 等客户端状态。多个会话访问同一服务端对象时，仍需按共享资源进行并发控制。

## 第二章：上下文、检索与记忆

第一章已经说明怎样执行模型请求。要让请求有用，还需要确定输入来自哪里、怎样取回、怎样在有限空间中组织。本章沿信息进入模型的路径展开。

<a id="context"></a>

### 2.1 信息关系与上下文组装

上下文管理模块操作的是信息的本轮使用视图。运行记录保存执行进度与待处理工作，历史记录保存消息和调用，外部资料保存文档与业务内容，记忆记录保存经维护的既往信息。这些数据可以相互关联，同一段历史也可以成为记忆来源。

组装时，模块接收当前要求、运行记录、资料范围和输入预算。它先保留当前目标、有效约束与必要执行信息，再选择与本轮决策相关的历史、工具结果、资料和记忆。选择依据包括任务关联、时效、来源和内容价值。

遇到冲突时，模块保留冲突双方及来源，让后续处理能够判断哪个版本适用。将过期推测直接改写成确定事实，会使后续动作失去依据。

选定内容还需要保留角色与来源。用户要求、系统指令、工具观察和检索资料分别以适当位置提交；历史工具请求与结果保持接口要求的关联。完成后，模块输出选定内容，模型接入模块负责序列化。

外部资料可以由程序预先取得，也可以经模型调用检索工具取得。两条路径最后都将实际取得的内容交给上下文管理；数据库里的位置或文件路径则作为后续读取入口。

<a id="budget"></a>

### 2.2 上下文预算与压缩

选定信息可能超过本轮输入容量。上下文管理模块先按目标模型的上下文限制和输出约束安排预算，再计算指令、工具定义、消息与资料的占用。涉及推理 token 的模型还要遵守其相应限制。

处理超额内容时，先移除无关和重复部分，再按资料价值选择截断、摘要、外置或分次读取。截断适合可局部读取的输出；摘要适合已较稳定的历史；外置适合需要保留完整内容但无需本轮全读的资料。

摘要过程接收待压缩区间及保留要求，生成目标、约束、已完成动作、证据位置和未完成事项的短记录。模块检查关键事项是否仍有对应，再与保留的近期交互组合并重新计数。检查失败时，保留原内容，缩小压缩范围或改用其他缩减方式。

原始记录按保存策略留存，摘要中保留回查引用。压缩须维持计划、推测、已执行和已验证之间的区别。无法容纳必要输入时，应拆分工作或明确报告限制。

摘要服务于模型理解。待审批的精确参数、操作标识与恢复位置保存在运行记录中，后续程序从这些结构化数据恢复执行。[上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

<a id="rag-index"></a>

### 2.3 RAG 入库与索引维护

检索增强生成（RAG）通过检索外部资料，为模型生成提供依据。入库是检索的前置准备，通常由资料变更触发或后台执行。它产出的索引供在线查询使用。

入库系统维护原文、内容块和索引的关联。原文按文档与版本保存；解析器提取标题、段落、表格和代码等结构；切分器按这些结构与长度约束生成内容块。每个块保存原文标识、版本、位置、所属范围和权限元数据。

块过大容易混入无关信息，块过小容易丢失约束。重叠可以保留边界连续性，也会增加重复。切分方式需要通过真实查询检验。

关键词检索通常建立倒排索引，记录词项出现在哪些块中，BM25 等方法结合词频、词项区分度和长度排序。向量检索先用 embedding 模型编码内容块，再建立相似度搜索结构；查询与资料必须使用兼容的表示空间和距离计算。

大规模向量搜索可以采用近似最近邻索引。图索引沿候选之间的连接探索，减少全量比较；搜索范围影响速度和召回率。向量保留检索特征，原文仍负责提供可回查内容。

文档更新时，系统生成新版本内容块与索引，确认可用后切换查询的当前版本。旧版本按历史策略保留或清理；删除或权限收回时，先阻止内容继续返回，再清理派生记录。这样查询结果才能对应明确的资料版本。

<a id="rag-query"></a>

### 2.4 查询构造、召回、重排与证据

在线查询从当前问题出发，使用入库形成的索引。查询构造器接收问题、已确定的任务范围、必要历史和可信过滤条件，输出检索文本与结构化限制。

规则或模型可以补全已知指代、拆分多个信息需求。程序校验结果是否保留实体、编号、版本、时间和否定条件，是否加入无依据事实。授权范围由系统提供，改写只在该范围内继续限定。校验失败时回退原查询；指代仍不清楚时请求澄清。

检索器执行关键词与向量查询，收集候选及其来源、版本、分数和排名。合并时先对齐内容标识，再去重和融合。不同检索分数未必可比，RRF 可以按各路排名累加贡献；采用哪种融合方式应由评估决定。[混合检索](https://www.elastic.co/docs/solutions/search/hybrid-search)

重排器接收问题与较小候选集合，进一步比较相关性。常见 cross-encoder 将问题和候选一起编码评分，计算成本通常高于比较预先编码的向量。它重排已有候选，未进入候选集的资料需要通过改进召回找回。[召回与重排](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

证据选择器再考虑覆盖、重复、版本和预算。高分但内容相同的块不能代替缺失的另一项条件；必要时补读相邻段落或原文。最终输出带来源和位置的证据，交给上下文管理。证据不足时输出不足原因，供下一轮检索或答复处理。

<a id="memory"></a>

### 2.5 Memory 的写入、维护与召回

Memory 的目标是使既往信息在后续交互中可用。会话内记忆支持当前交互连续性，跨会话记忆支持后续任务。原始历史、检索索引和提炼后的记忆分别承担留存、查找和复用职责。

在 LangGraph 的术语中，线程图状态与检查点支持短期记忆，独立 store 支持跨线程数据。这里的图状态包含消息和应用数据，与单一生命周期字段不同。[Memory 概念](https://docs.langchain.com/oss/python/concepts/memory)

写入过程从交互和工具证据提取候选，保存内容、来源、范围、时间及确认状态。维护逻辑判断候选是否值得保留、是否重复、是否与现有记录冲突，再决定新增、替换或保留为待确认内容。来源可追溯，并不自动说明陈述已经证实。

本轮结果可在记录更新时产生候选，同步或后台交给上述维护逻辑。同步方式较及时，后台方式减少当前延迟，但要核对来源在处理前是否已经变化。模型的提取结果经过确认规则后才成为相应状态的记忆。

纠错时，系统记录更正与替代关系，使旧记录失效，并更新引用旧内容的摘要、索引或其他记忆。删除同样需要处理派生内容，防止被删除事实从旧摘要中再次进入上下文。

召回器接收任务范围和当前问题，过滤当前有效且可访问的记忆，再选择相关记录，连同来源和不确定性输出给上下文管理。群、话题、项目和个人范围分别保存；群历史可建立索引，再从中提炼适合相应范围保留的决定与约束。

Memory 可以使用文件、关系存储或向量检索。RAG 负责检索与使用，Memory 负责信息生命周期；记忆可以采用 RAG 方式召回。此类应用层写入不会直接修改模型权重。

## 第三章：任务编排与可靠执行

信息供给解决每轮决策依据什么。本章进一步确定请求属于哪项工作、工作怎样组织，以及中断或失败后怎样继续。

<a id="routing"></a>

### 3.1 消息、任务、会话与运行路由

应用在创建或继续运行之前，先确定消息属于哪项任务。路由器接收发送者身份、消息标识、群或频道标识、回复关系，以及已有任务映射。

它优先读取显式任务标识、被回复消息的归属和话题绑定，并确认目标存在且发送者有访问权限。缺少明确关联时，才从允许访问的任务中产生候选，比较任务描述、最近活动和语义。无法区分时输出澄清请求。

路由结果确定任务与会话，并指明创建运行、向现有运行追加输入，或回答某个等待请求。应用持久化消息到这些对象的映射，利用外部消息标识去重，避免重复投递导致重复启动。

单一聊天接入通道可以通过这张映射表连接多个底层会话：发送到 Runtime 的请求携带已确定的会话标识，回传事件携带运行标识，再由应用投递回原消息空间。消息所属话题与底层会话是需要维护的关联。

路由决定工作归属，内容检索在该范围内寻找资料。同一会话有运行正在修改历史时，新输入采用排队、受控追加或打断规则，避免并发覆盖。只承担接入、映射和转发的 Bridge 属于应用协调层；描述项目时应说明底层 Loop 由哪个 Runtime 执行。

<a id="paradigms"></a>

### 3.2 Workflow、ReAct 与规划执行

任务已经定位后，需要确定控制路径由谁选择。Workflow 的主要依赖与分支由程序描述；Agent 允许模型根据观察动态选择动作。两者可以组合，例如程序限定阶段，模型处理阶段内的探索。

ReAct 原始方法交替生成语言推理轨迹与动作，并让动作取得的观察参与后续判断。它描述一种具体决策方式；Agent Loop 是执行机制，更宽泛。现代运行端可以借鉴其反馈结构，采用各自的工具协议。[ReAct 原论文](https://arxiv.org/abs/2210.03629)

Plan-and-Execute 将规划和执行分开：规划器输出步骤、依赖和预期结果；执行器返回实际产物与错误；规划器据此调整剩余计划。计划中的完成标记需要关联执行证据，前提变化后重新检查依赖。

审查阶段读取要求、产物和证据，输出具体缺口或通过结论，再由控制逻辑决定是否修正。能够用规则、测试或外部状态检查的条件，交给对应验收器。模型审查需要校准，修正过程仍受次数和预算约束。

这些方式规定工作如何组织，Runtime 提供执行它们所需的模型、工具和记录能力。多 Agent 是否参与，则由实际分工需要决定。

<a id="orchestration"></a>

### 3.3 依赖、并发与多 Agent 协作

编排面向多个执行单元之间的关系，执行单元可以是程序、检索、模型调用或 Agent Loop。编排记录每个单元的输入、输出、前置依赖、执行者、资源和完成条件。

调度器读取完成记录，找出依赖已满足的工作，再依据资源占用和并发限制启动。结果写回后重新检查下游依赖。分支选择由明确条件或指定模型判断产生，判断结果也保存到记录中。

并发需要检查数据与资源两方面：工作是否依赖另一项未完成结果，是否修改相同对象，是否共享可变会话状态，以及外部服务是否允许并发。隔离工作目录、分配写入所有权、使用锁或版本检查，可以分别处理相应冲突。

工具列表中同时出现多个调用，只说明模型提出多个动作。真正并行执行前，工具管理与执行模块仍需核对上述条件；存在依赖时按可执行顺序处理。

多 Agent 分工还需要为每个子任务确定目标、上下文范围、可用资源、输出格式和证据要求。主 Agent 调用子 Agent 时保留协调责任；控制权交接则将后续工作移交给指定执行者。并行结果由协调者检查冲突、重复和缺失，再形成下游输入。

增加执行者会增加信息传递、资源管理和结果合并成本。适合分工的任务应具有可区分的工作范围和可检查的子结果，其收益通过[系统评估](#evaluation)确认。

### 3.4 运行记录、状态流转与恢复

调度需要知道已经发生什么、还欠哪些结果。先确定记录结构，再定义流转条件，最后解释记录与外部操作之间的故障间隙。

<a id="record"></a>

#### 运行记录与持久化对象

状态与持久化模块接收模型响应、工具结果、错误和控制决定，将它们组织成当前运行记录。为保证后续判断读取相同事实，同一运行的更新应串行提交，或使用版本检查拒绝覆盖旧视图。

| 记录组成 | 需要保存的内容 |
| --- | --- |
| 身份与关联 | 运行、任务、会话和输入标识 |
| 生命周期 | 当前运行状态、轮次、等待或终止原因 |
| 执行控制 | 预算使用、取消请求、配置和权限策略引用 |
| 交互历史 | 模型响应项、工具请求、实际结果和错误 |
| 待处理工作 | 未完成调用、等待输入、审批对象、结果未知的操作 |
| 证据与产物 | 产物地址、版本、测试输出和外部结果引用 |

这里按数据用途划分，不要求每个实现使用完全相同字段。生命周期字段只表达运行阶段，预算和权限仍作为各自数据保存。消息数组可以承载交互历史，其余执行数据由运行记录的其他部分维护。

更新有明确的时机。模型调用和工具启动前记录必要的意图与标识；结果收到后保存对应事实；本轮处理结束时汇总进度、清理已经完成的待处理项，为下一步提供当前视图。这样第四步承担实际状态归并，执行前后的记录点则保留恢复证据。

检查点保存恢复所需的状态快照与执行位置；事件日志按顺序记录变化；产物存储保存实际文件和报告。只有产物引用时，还需保存可识别的版本，确认恢复时读到的是对应内容。

本轮值得保留的信息可以输出为 Memory 候选，交给[记忆维护](#memory)。该交接输出候选及来源，长期写入是否成立由相应维护规则决定。

<a id="lifecycle"></a>

#### 继续、等待与终止

循环控制模块读取当前运行记录后，决定继续、等待或终止。本文用 `queued`、`running`、`waiting`、`completed`、`failed`、`cancelled` 表达一套应用层生命周期；这些值用于说明设计，不代替任何产品的原始 `status`。

| 当前检查结果 | 控制动作 | 记录变化 |
| --- | --- | --- |
| 收到取消请求 | 停止接纳新工作，向可取消动作传播取消 | 记录未确认外部结果，最终标记 `cancelled` |
| 不可恢复错误或总预算耗尽 | 终止调度并返回原因 | 标记 `failed`，保存错误与剩余工作 |
| 有未解决的输入或审批请求 | 暂停对应工作，释放可释放资源 | 标记 `waiting`，保存等待对象 |
| 有依赖已满足且允许执行的工作 | 调度该工作或开始下一轮 | 保持 `running` |
| 模型响应完整结束、答复通过约定格式校验，且没有待处理工作 | 完成本次执行的收尾 | 标记 `completed`，保存输出与终止原因 |

继续、等待和终止描述控制流；`completed`、`failed`、`cancelled` 描述终止结果。等待状态保存尚未满足的条件，后续输入通过请求标识匹配，再恢复对应工作。

用户信息不足需要由约定工具或结构化信号形成输入请求，记录缺什么、由谁回答、恢复到哪里。接口返回一段问句后，应用也需要将其转换成这样的请求，才能提供可靠恢复入口。

生成停止原因参与上述检查，同时检查取消、时间和 token 等预算、待处理动作及任务规则。空输出、反复无进展或无法解释的响应进入明确错误处理。运行 `completed` 后，业务要求是否满足由[任务验收](#acceptance)给出独立结论。

<a id="recovery"></a>

#### 重试、检查点恢复与幂等

恢复机制处理程序记录与真实外部环境之间的差距。启动恢复时，执行器加载检查点、核对配置与产物版本、读取待处理动作，并查询结果未知的外部操作，之后才能选择后续工作。

框架的恢复单位影响哪些代码再次执行。LangGraph `1.2.16` 的 `interrupt()` 恢复会从所在节点开头重执行，节点内中断前的逻辑可能再跑一次。内存 checkpointer 只提供进程内保留，跨重启需要相应持久化后端。[对应版本代码](https://github.com/langchain-ai/langgraph/blob/1.2.16/libs/langgraph/langgraph/types.py)、[中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

错误处理先识别种类。暂时性网络或服务错误可在有限次数与总预算内退避重试；参数或输出错误交回对应处理者修正；权限和业务前提错误要求改变条件。持续重复调用、同类错误或目标状态无变化，可以触发无进展终止，记录实际触发依据。

产生副作用的操作需要单独设计幂等。应用在首次执行前保存稳定的逻辑操作键；后续重试沿用该键。执行端以该键识别同一操作，检查参数一致性，并将去重记录与实际变更可靠关联。模型协议的调用标识仍只负责请求结果关联。

外部操作成功而本地尚未保存结果时可能发生故障。恢复后先按操作键查询真实状态，或调用具有上述幂等保证的接口。超时只说明未及时收到结果；状态无法确认时保留未知结果，并进入进一步查询或人工处理。[幂等 API 与安全重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

取消通过执行组件向下传播，能够停止的范围由模型服务、进程和外部系统决定。已经提交的修改需要业务事务或补偿机制处理；本地运行记录需要如实保留这些结果。

<a id="permissions"></a>

### 3.5 身份、授权、隔离与审批

执行所需的授权从可信身份开始。应用认证请求主体，授权组件根据主体、资源和操作类型给出决定，工具执行端与资源服务在真实访问边界执行检查。

| 控制 | 输入依据 | 实际作用位置 |
| --- | --- | --- |
| 身份认证 | 登录态、令牌或其他可信凭据 | 应用入口及服务连接 |
| 资源授权 | 主体、资源范围、操作类型 | 检索、记忆与业务资源服务 |
| 工具策略 | 当前任务配置与授权范围 | 工具管理与执行模块 |
| 执行隔离 | 文件、进程和网络等限制 | 工具进程所在环境 |
| 人工审批 | 明确的待执行动作 | 审批记录与恢复入口 |

模型提供目标参数，程序再检查这些目标是否处于允许范围。检索和记忆过滤应在内容暴露给无权组件或模型前生效，避免以事后过滤代替访问控制。

审批记录绑定操作、目标、关键参数与必要版本条件。用户批准后，执行器核对当前动作是否仍符合该记录；目标或参数实质变化时重新判断。恢复时重新核对当前权限。

网页、文档和工具输出可以包含命令式文字。上下文保留其来源，执行边界继续使用可信授权依据。来源标签帮助解释内容，资源权限和执行隔离负责强制边界。[OWASP 提示注入防护](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

凭据按需要由执行环境提供，日志、模型输入与长期记忆只保留任务所需信息。具体授权强度按资源和操作决定，避免把全部工具统一处理成一种风险等级。

## 第四章：验收、实现与技术选型

前面三章建立了执行、信息和控制关系。最后从产物证据出发，检查系统效果，再决定采用哪些实现以及如何观察运行代价。

### 4.1 验收与效果评估

先判断单次任务是否满足要求，再把同一判断方法用于一组可重复执行的用例。

<a id="acceptance"></a>

#### 单次任务验收

验收器接收任务要求、实际产物及外部状态，逐项检查要求是否有证据支持。结果记录为通过、失败或证据不足，并关联检查条件和证据位置。

| 判断层次 | 成立依据 |
| --- | --- |
| 接口成功 | 请求被正常处理，响应完整性符合接口约定 |
| 运行完成 | 没有未处理执行工作，Runtime 按运行约定完成收尾 |
| 业务通过验收 | 实际产物与外部状态满足任务要求及约束 |

模型总结提供待核查声明，工具返回值提供动作结果，测试输出证明所覆盖条件。验收器根据证据能支持的范围给出结论；缺少某项关键证据时保留未验证状态。

验收可以在执行阶段结束后作为编排节点参与修正，也可以在整个运行终止后由应用触发。前者将缺口交给后续执行单元；后者需要继续处理时由应用创建后续运行。文章把验收放在执行机制之后介绍，是按知识依赖安排。

Agent 评价需要同时检查交互轨迹和环境中的实际结果，才能发现口头完成与真实完成之间的差异。[Agent 评估方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

<a id="evaluation"></a>

#### 评估集、检索指标与评估控制

单次验收形成可执行标准后，系统评估在一组用例上重复应用这些标准。用例来自真实请求、历史失败和人工边界设计；自动生成内容需要审核。每项用例保存必要历史、身份与资料范围、初始环境和预期判断。

路由用例标注正确任务或应澄清的条件；检索用例标注相关资料、版本及证据；执行用例检查目标、动作和恢复；端到端用例检查最终业务状态。真实常见任务与无答案、歧义、权限限制、重复投递和中断等失败用例共同组成覆盖范围。

计算检索指标前，固定评价单位为文档或内容块，固定资料版本和相关性标注。设相关单位集合为 R，前 k 个去重结果为 S_k，采用以下口径。

| 指标 | 本文采用的计算口径 |
| --- | --- |
| Recall@k | 命中的相关单位数除以 R 的大小 |
| Precision@k | 命中的相关单位数除以 k；不足 k 项的空位计为未命中 |
| Hit@k | 每个问题是否至少命中一项相关结果，再对问题平均 |
| MRR@k | 首项相关结果排名的倒数；前 k 项未命中记零，再对问题平均 |
| NDCG@k | 将分级相关性收益按位置折扣，再除以理想排序收益 |

无相关答案的用例另行评价拒答或澄清，避免零分母。多条件问题还需要检查证据覆盖；只命中一项的 Hit@k 无法说明全部条件已找到。标注不完整时，Recall 只反映已标注相关集合。[排序评估定义](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval)

开发集用于调整，测试集用于保留评价；按资料来源、任务或时间划分可降低近重复泄漏。固定或记录模型、提示词、工具、索引和环境版本。随机任务多次运行并报告波动，每次恢复规定的初始状态，避免前次产物或记忆使后续试验失真。

<a id="implementations"></a>

### 4.2 Framework、Harness、Runtime 与 SDK

已经明确职责和评价标准后，可以判断现成实现承担哪些工作。Framework 提供构建抽象与组件，Runtime 执行任务，SDK 提供程序入口。Harness 通常指模型周围的工具、上下文、执行环境与控制设施，具体边界由项目定义。

以下记录明确版本的能力，核对日期为 **2026-10-23**。表格用于定位接口与责任，性能比较需要另行评价。

| 实现与版本 | 核对到的接入能力 | 应用仍需确定的工作 |
| --- | --- | --- |
| LangChain 1.4.7、LangGraph 1.2.16 | `create_agent` 基于 LangGraph 构建 Agent；图执行支持状态与控制流 | 业务状态、节点边界、外部操作与验收 |
| OpenCode v1.19.4 | JS/TS SDK 可创建客户端，或同时启动服务和客户端 | 身份与任务关联、服务部署及业务授权 |
| Pi v1.4.0 | 模型 API、Agent core、Coding Agent 等分层组件 | 按所选组件补齐应用与隔离能力 |
| Hermes v0.22.4 | 消息网关、工具、记忆和 Skills 等集成能力 | 现成会话和存储设计与业务的适配 |
| DSH 提交 687f282e8625 | Cordis 插件化 Harness，该提交标记为 developer preview | 插件集成、兼容性和升级维护 |
| Codex 仓库 rust-v0.163.0 | TypeScript SDK 包装 CLI，以 JSONL 交换事件 | 业务上下文、任务管理和输出消费 |
| Claude Agent SDK Python v0.2.172 | 包装并运行 Claude Code CLI，提供会话与工具控制接口 | 业务工具、授权和部署环境 |

LangChain 与 LangGraph 存在具体实现关系：该版本 `create_agent` 返回编译后的 LangGraph 图。[LangChain 代码](https://github.com/langchain-ai/langchain/blob/langchain%3D%3D1.4.7/libs/langchain_v1/langchain/agents/factory.py) OpenCode 的 `createOpencode` 组织服务和客户端创建，已有服务则可单独连接。[OpenCode 代码](https://github.com/anomalyco/opencode/blob/v1.19.4/packages/sdk/js/src/index.ts)

Pi 该版本声明没有内置限制文件、进程、网络和凭据访问的权限系统，应另配所需隔离。[Pi 版本说明](https://github.com/earendil-works/pi/blob/v1.4.0/README.md) Hermes 与 DSH 的能力范围依据相应版本文档，完整系统和插件化底座带来不同集成成本。[Hermes](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/README.md)、[DSH](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/README.md)

Codex 的上述 TypeScript SDK 提供 `Thread.run()` 和 `runStreamed()`；另可使用 app-server 的线程、执行轮次与事件接口。不同 SDK 和接口各自有生命周期，按应用需要选择并映射。[版本化 SDK](https://github.com/openai/codex/blob/rust-v0.163.0/sdk/typescript/README.md)、[app-server](https://learn.chatgpt.com/docs/app-server) Claude Agent SDK 接入现有 Agent 运行能力，客户端模型 SDK 则提供直接模型 API 访问。[Claude SDK](https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.172/README.md)

开源范围应分别核对 SDK、运行端、工具、模型与托管服务的许可证和部署条件。某一部分的可见源码只支持对该部分的判断。

<a id="selection"></a>

### 4.3 技术选型的方法

选型先把需求转成可检查约束：任务类型、流程控制、运行时长、恢复、权限、多用户隔离、模型、部署环境和维护投入。根据这些约束决定需要完整系统、可嵌入运行组件，还是编排框架。

随后检查能力语义。恢复历史与恢复未完成动作需要不同数据；审批界面与可编程审批接口提供不同集成方式；工具行为提示与进程隔离产生不同保证。每项必需能力都应追问其保存什么、在哪里执行、失败怎样暴露。

用同一组任务、环境限制和验收标准比较候选，记录完成率、错误类型、人工介入、耗时、成本和维护工作。比较 Runtime 时尽量固定模型与工具；选择完整方案时可以采用各自配置，但要记录哪些因素发生变化。

最终选择记录写明关键约束、选中实现满足的能力、需要自建的部分，以及重新评价的触发条件。复用 Runtime 后，应用仍可自建路由、检索、Memory 和验收；自研的收益要与这些长期维护责任一起计算。

<a id="operations"></a>

### 4.4 性能、成本、缓存与可观测性

运行观测将问题定位到实际环节。追踪记录关联任务、运行、模型调用和工具调用，保存配置版本、资料版本、耗时、结果、错误与验收依据。敏感字段在进入普通日志前处理。

性能按排队、资料获取、检索、模型输入处理、输出生成、工具、重试和等待分解。串行阶段累积耗时，并行阶段受依赖路径和慢分支影响。首次反馈、首次有效结果和任务完成时间分别统计，再观察 P95 等尾部情况。

在常见自回归 Transformer 推理中，KV cache 保存已有 token 的注意力计算状态，供后续生成复用。跨请求前缀缓存进一步复用满足条件的相同前缀计算，减少重复输入处理。结果缓存则保存已经完成请求的输出，需要核对权限、资料版本和有效期。Memory 保存可复用信息及来源，服务于后续理解。[前缀缓存说明](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)

成本包括主模型、改写、摘要、重排、embedding、外部工具、运行环境及失败重试。单位成功任务成本用统计期总成本除以成功数量；没有成功任务时报告无法计算。减少输入或调用次数时，同时观察验收通过率与返工成本。

应用进度通过事件与输出模块交付。SSE 适合服务端推送，WebSocket 支持双向交互；业务事件的保留和重放由应用实现。可以为运行事件分配递增序号，客户端保存已处理位置，重连后补取并去重；日志缺口或过期时先加载当前状态快照，再接收后续事件。[SSE 事件机制](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

状态快照应带对应事件位置，避免补取时跳过变化。界面连接断开后，后台运行可以继续；界面通过明确终止事件更新运行展示，通过验收结果展示业务结论。
