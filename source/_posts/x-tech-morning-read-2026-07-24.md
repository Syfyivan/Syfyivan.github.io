## AI 观察

### 1. 语音正在从“把话转成 prompt”变成 Agent 的调度入口

OpenAI 的 X 帖子把 ChatGPT Voice 描述成桌面端能力：用户可以用声音控制电脑，并协调 ChatGPT Work 或 Codex 中的多个 Agent。官方文档进一步写明，Voice 可以启动独立线程、查看已有任务、发送后续指令，并把进度、阻塞和结果带回语音对话；它遵循被调度任务原有的权限，语音本身不会自动扩大权限。

Anthropic 同期也在更新 Claude 的语音模式。官方帮助页确认，Voice Mode 支持免提和按住说话两种交互，可以在同一会话中切换文字与语音，且上下文会延续。两边的共同变化不是“多一个麦克风按钮”，而是把 Agent 的控制面从输入框扩展到了实时会话：用户可以在走动、观察结果或等待长任务时继续发出方向调整。

但语音会放大一个旧问题：人类以为自己在“聊天”，系统实际上正在创建任务、消耗额度、调用工具和改变文件。客户端必须持续回读 `正在执行什么、由谁授权、预计会产生什么副作用`，否则语音的低摩擦会把误操作也变得低摩擦。

### 2. 多 Agent 的价值不在“同时跑”，而在可观察、可暂停、可接管

OpenAI 文档将 Voice 与 Codex 任务连接起来，Anthropic 的公开材料则把 Agent 工作描述为持续的上下文、工具和验证过程。把它们放在一起看，下一阶段的核心对象不再是单轮回答，而是一个能被用户随时打断和重新指挥的任务集合。

这要求 Agent runtime 至少暴露任务 ID、当前阶段、最近一次工具调用、等待原因、预算/额度消耗和下一步动作。多个 Agent 同时运行时，还要明确哪些工作共享文件、哪些工作只读、谁有权合并结果。否则“我让它们并行处理”只是在服务端制造更多无法解释的并发。

今天 Codex 群里关于重置卡、模型疑似降级、图像生成失败和网页卡顿的讨论，正好说明了这一点：用户首先感知到的是额度和状态，却通常看不到计量口径、路由原因、重试策略和服务端证据。没有可读的运行回执，用户只能把产品行为解释成“玄学”。

### 3. Agent 进入工程链后，验证回路比生成能力更决定交付质量

Anthropic 7 月 22 日的文章把验证回路定义为“检查结果，必要时修复，再次检查”的迭代过程，并建议把反复执行的人工检查写成 skill、接到 GitHub Actions 或 PR 流程中。微软早期大规模部署 Claude Code 与 Copilot CLI 的研究也提醒我们：采用和合并 PR 数量的提升，不等于交付价值已经被证明；研究者明确把 merged PR 作为代理指标，而不是最终价值。

这给“语音驱动多 Agent”补上了一个必要条件：语音只能降低发起和跟进任务的成本，不能替代确定性检查、运行时观测和人工判断。一个成熟的 Agent 交付链应让模型在回答“完成了”之前，拿出构建、测试、日志、截图、权限和差异审查等证据；缺少证据时，最诚实的结果是 `需要人工确认`，而不是更顺滑的语音播报。

## 前端 / 服务端 / 客户端工程观察

### 前端：语音界面要做成“任务控制台”，不是一个会说话的输入框

前端应把语音会话和任务列表绑定起来，至少展示：当前任务、执行阶段、工具调用、等待审批、额度/预算、失败原因和停止按钮。用户说“继续”时，系统要能告诉他继续的是哪个任务；用户说“停一下”时，必须明确是暂停语音、暂停当前 Agent，还是停止所有副作用。

对多 Agent 场景，建议在每个任务旁边显示工作区、分支或文件范围，以及“只读/可写/需要审批”的权限状态。客户端还要提供文字回放、可复制的命令和错误详情，因为语音适合导航，不适合承载长日志、路径、堆栈和精确参数。

### 服务端：把语音 turn、Agent task 和外部副作用拆成三层状态

服务端不要用一条 `conversation.status` 覆盖所有生命周期。至少分成：语音连接是否活跃、Agent 任务是否运行、外部动作是否已提交。语音断开不代表任务失败，任务完成也不代表部署成功；如果用户在语音中重复说“再来一次”，服务端必须用 `task_id + action_id` 或等价幂等键避免重复扣费、重复发消息、重复写文件或重复发布。

对于额度和路由问题，回执应能携带模型/路由、计量窗口、请求时间、重试次数和 request ID；对于图片生成或远程控制这类长任务，还要把 `queued`、`running`、`waiting_for_device`、`rate_limited`、`failed_but_retryable` 和 `delivered` 区分开。否则前端只能把不同故障统一显示成“正在努力”。

### 客户端：真正的 Agent 体验是“设备反馈闭环”

桌面端、移动端和模拟器都不是单纯的输出屏幕，而是 Agent 的传感器和执行面。语音启动 Codex 后，客户端要把构建日志、测试结果、页面截图、模拟器状态、权限弹窗和用户审批回传给 Agent；Agent 的每一步也要能被用户暂停、接管或回滚。

无障碍尤其值得单独验收：语音输入、屏幕阅读器、键盘操作和可见状态必须表达同一套任务事实。不要只测试“能不能说话”，还要测试噪声环境、打断、切换文字输入、麦克风权限拒绝、后台任务继续运行、网络断开恢复，以及语音与文本同时操作时的竞态。

## 值得跟进的动作

1. 给语音驱动的每个任务建立可读回执：任务 ID、权限、阶段、工具、预算、阻塞原因和下一步动作。
2. 把 `voice turn`、`agent task`、`external side effect` 分成独立状态机，并为每个不可逆动作补充幂等键和审计记录。
3. 把构建、测试、日志、截图、接口结果和安全扫描接成验证回路；Agent 没拿到证据时，默认进入人工确认，而不是播报成功。
4. 为前端补齐语音场景验收：打断、重复指令、空结果、权限拒绝、额度耗尽、网络断开和多 Agent 并发。
5. 为客户端补齐设备反馈验收：桌面窗口、移动端远程连接、模拟器、真实设备、系统权限和可访问性输出要分别记录证据。
6. 对 Codex 群内的额度/重置、模型降级和图像生成失败，只收集账户类型、平台、时间、request ID、模型选择和复现步骤；在官方文档或状态页确认前，不把群内经验写成产品规则。
7. 对 Claude 群内关于“reset 时间显示上海”的讨论，优先验证本机时区、账户设置、网络出口和产品文案，再判断是否存在地理位置推断；不要凭一条界面提示推导隐私结论。
