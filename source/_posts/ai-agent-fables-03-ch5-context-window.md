> 承上：上一章阿册知道了这座楼怎么练成、有多博学。这一章，老馆长泼了盆冷水：再博学，它一次能摊在桌上同时看的纸条，也是有数的。

老馆长指着那张长桌：“管理员厉害，是因为他能一眼扫过桌上所有纸条。可桌子就这么大，一次能摊的纸条有上限。超了，旧的就得撤下去——撤下去的，它就看不见了。”

阿册不服气，想了个主意：把桌子换成大三倍的。老馆长摇头：“你以为摊的纸条翻三倍，工夫也翻三倍？不止。每张纸条都要和桌上其它每张两两对看——纸条翻三倍，对看的工夫差不多翻九倍。桌子能做大，但越大越费、越慢。”

后来阿册又栽了个跟头：他把一大摞资料一股脑全摊上去，以为“给得越多答得越好”。结果真正要紧的那张，淹没在一堆没用的纸里，管理员反倒看走了眼。

## 概念揭晓

那张“一次能摊多少纸条”的桌子，是**上下文窗口（context window）**：模型一次能同时处理的 token 数量上限。超出窗口的内容，模型“看不见”——要么被截断，要么得靠别的办法搬运（这正是第六讲 Harness 要解决的）。

“纸条翻三倍、对看的工夫翻九倍”，是注意力的**平方级成本**：标准注意力里，每个 token 要和所有 token 互相计算，开销大致随序列长度的平方增长。所以上下文越长，越慢、越贵、越吃显存。

“全摊上去反而看走眼”，是**长上下文的误区**：把窗口塞满不等于效果更好。无关内容会稀释注意力、淹没关键信息，模型还常对开头结尾更敏感、对中间内容容易“看丢”。

## 上下文窗口限制了什么

窗口决定了模型“一次能看见多少”。它同时框住了你的输入（提示词、资料、对话历史）和它的输出——全都算在这几千到几十万的 token 预算里。

一旦对话很长、资料很多，就会撞上窗口上限：早期内容被挤出去，模型“忘了”前面说过什么。这不是它“记性差”，而是桌子满了。理解这一点，你就懂了为什么长对话里它会前后矛盾，也懂了为什么要专门有人研究“怎么搬运上下文”。

## 为什么长上下文又贵又慢

标准注意力让每个 token 关注所有 token，计算量大致与长度的平方成正比：长度翻倍，注意力开销约翻四倍。于是：

- 更长的输入 → 更高的延迟和费用。
- 显存也吃紧，硬件成本上去。

近年有不少技术在优化这件事（让长上下文更便宜），窗口也越做越大；但“长就免费”仍然不成立。把上下文当成一份有成本的预算来花，是工程上的基本素养——这点第六讲（offloading、compaction）会专门展开。

## 塞满窗口为什么常常更差

新手最容易犯的错，是“反正窗口大，全塞进去”。问题有三：

- **稀释**：无关内容多了，真正关键的信息占比下降，注意力被分散。
- **中间易丢**：研究和实践都发现，模型常对上下文的开头和结尾更敏感，对正中间的内容容易“看丢”（俗称 lost in the middle）。
- **更贵更慢**：白白为没用的内容付 token 成本。

更好的做法是：只放真正相关、经过筛选的内容，把关键信息放在显眼位置。这正是第四讲“上下文工程”和 RAG 的用武之地。

## 窗口大不等于不要检索和记忆

有人觉得“窗口够大就不用检索了，全塞进去就行”。但即便窗口很大：

- 你的资料常常远超任何窗口（整个知识库、整个代码仓）。
- 全塞既贵又会稀释。
- 跨会话的长期记忆，靠窗口也留不住。

所以“大窗口”和“检索 + 记忆 + 上下文搬运”不是替代关系，而是配合关系。这条线会一路通到第四讲（RAG）和第六讲（Harness）。

## 常见误区

第一，把上下文窗口理解成“模型的总记忆”。它只是“一次能同时看见的量”，不是长期记忆。

第二，以为“给得越多越好”。无关内容会稀释和淹没关键信息，常常更差。

第三，以为窗口变大就万事大吉。长上下文有成本、有“中间易丢”，并不能取代检索与记忆。

## 小练习

假设你要让模型基于一份 500 页的手册回答问题，但窗口放不下整本：

1. 你会把整本塞进去，还是先检索出最相关的几页？为什么？
2. 关键的那几段，你会放在上下文的什么位置？
3. 如果要连续问很多轮，怎么避免对话历史把窗口占满？
