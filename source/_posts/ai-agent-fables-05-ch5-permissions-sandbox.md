> 承上：上一章阿器把工具说明牌都补清楚了。这一章，老掌柜话锋一转：工具会用还不够，能不能借、借了能干到什么程度，得有规矩。

老掌柜从柜台后摸出一串钥匙，分门别类挂好。

“工具分三等，”他说。“**只能看的**——量尺、放大镜，随便拿，看坏不了东西。**能动东西的**——开锁的、动钱箱的、改账本的，这些得先报一声、有人点头才给（动账之前还得说清要动多少）。**真正危险的**——比如要往真账本上落一大笔，先到后院那间‘试做间’里演一遍，没问题了再上真账。”

他又指了指墙上的登记簿：“谁借了什么、动了什么、什么时候，全记下来。出了岔子，照簿子一查就知道是哪一步。最要紧的——钥匙不外传，借工具的人只拿到这一趟用得着的那把，办完就收回。”

## 概念揭晓

老掌柜这套规矩，是把工具的**权限与安全边界**讲清楚——这是放 Agent 去“真办事”前必须想明白的事。

“只能看 vs 能动东西”，是**只读与写入的分级**：读取信息风险低，修改真实状态（改数据、动钱、发消息、删文件）风险高，要区别对待。

“动东西得先报一声、有人点头”，是**审批 / 人类在环（human-in-the-loop）**：高风险操作执行前，要有人确认。

“危险的先在试做间演一遍”，是**沙箱（sandbox）**：在隔离、可回滚的环境里先跑，不直接动真实的线上系统，把误伤挡在外面。

“谁借了什么全记下来”，是**审计（audit log）**：所有动作可追溯，出事能复盘、能定位。

“钥匙只给这一趟、办完收回”，是**最小权限与密钥边界**：只授予完成任务所必需的权限，密钥不泄露、不滥发、用完即收。

## 会用工具之后，安全才开始

前面几章让模型“能借工具办事”。但一旦它能动真实世界——改数据库、发邮件、转账、删文件——风险就完全不同了。一个判断失误或一次被诱导（第四讲的注入、第九讲的攻击），可能造成真实损失。

所以工具能力越强，越要把“能不能、谁批、出错怎么收场”想在前面。这章是从“工具会用”到“工具敢放出去用”的关键一跃，也是第九讲安全治理的前奏。

## 只读 vs 写入

第一刀，先按风险把工具切两类：

- **只读**：查信息、读文件、算东西——出错顶多是答错，可控。
- **写入 / 副作用**：改状态、动钱、对外发消息、删改文件——出错会造成真实、有时不可逆的后果。

对只读工具可以放得宽些；对写入工具，要默认从严：明确授权、必要时审批、留好回滚的余地。把这两类混为一谈，是很多事故的根源。

## 审批、沙箱、审计三道防线

- **审批**：高风险动作执行前，让人确认（“确定要把这 1000 条记录删掉吗？”）。把不可逆操作卡在人这一关。
- **沙箱**：在隔离环境里先跑、先验证，不直接动真实的线上系统；出问题能丢弃、能回滚，不伤真实数据。举个具体的：让 Agent 去执行一段会改动数据库的命令（也就是 SQL），先在一份真实数据的副本（一份一模一样的备份）上试跑，看它会动到多少条数据——本该改 3 条却报"影响 30000 行"，立刻就拦下了，真正的数据库毫发无损；又比如让一个写代码的 Agent 在一个临时的隔离小环境（叫"容器"）里跑测试，跑崩了直接把这个环境丢掉重来，外面真正的系统不受影响。
- **审计**：完整记录“谁、什么时候、用什么工具、做了什么、结果如何”。它不阻止事故，但让事故可复盘、责任可追溯。

三者配合：沙箱挡住大部分误伤，审批卡住高危动作，审计兜底可追溯。

## 最小权限与密钥边界

一条贯穿安全的原则：**只给完成任务所必需的最小权限。**

- 一个只需要读数据的 Agent，就别给它写权限。
- 密钥、令牌要妥善保管，不放进提示词、不写进日志、不随意下发；按需、限时、可吊销。
- 权限按任务、按角色隔离，别让一个 Agent 拿着“万能钥匙”。

权限越大，被误用或被攻击时的破坏面越大。最小权限是把破坏面压到最小的根本办法。

## 常见误区

第一，给 Agent 配工具时只想“能不能干成”，不想“干错了会怎样、谁来兜”。

第二，把读和写一视同仁，对写入操作不设审批和回滚。

第三，图省事给大权限、长期密钥。方便一时，风险长存。

## 小练习

你要给一个客服 Agent 配三样能力：查订单、给用户发退款、删除用户账号。

1. 这三样各属于只读还是写入？风险怎么排序？
2. 哪些需要人工审批？哪些该先在沙箱验证？
3. 你会怎么设置它的权限和密钥，体现“最小权限”？
