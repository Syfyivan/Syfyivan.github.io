数据库是大多数服务端系统的事实来源。接口可以重写，缓存可以失效，消息可以重放，但最终业务状态通常要落在数据库里。学数据库不能只学 SQL 语法，而要围绕三个问题：数据是否正确，查询是否稳定，结构是否能演进。

服务端工程里很多线上事故，本质都是数据库边界没想清楚：事务太大、索引缺失、状态字段混乱、重复写入、迁移不兼容、分页越翻越慢。

## 数据建模先于写代码

写业务接口前，先把核心实体和状态想清楚。以任务系统为例，至少会有：

- 用户表：谁拥有任务；
- 任务表：任务主体；
- 操作日志表：记录任务状态变化；
- 幂等请求表：避免重复创建；
- 可能还有标签、评论、附件等扩展表。

表设计不是把对象字段机械映射到数据库。它要回答：

- 什么字段必须唯一；
- 什么状态可以流转；
- 哪些字段用于查询；
- 删除是物理删除还是软删除；
- 是否需要审计创建人、更新人、时间；
- 数据增长后是否需要归档。

## 必须掌握的知识点

### 主键、唯一约束和状态字段

主键用于定位一行，唯一约束用于保护业务规则。比如订单号、用户邮箱、幂等 key，都不应该只靠代码判断是否重复，数据库约束才是最后防线。

状态字段要少而清晰。比如订单状态可以是：

```text
created -> paid -> fulfilled -> closed
created -> canceled
paid -> refunded
```

不要让状态随意跳转。状态机越清楚，事务、消息和补偿流程越容易设计。

### 索引不是越多越好

索引能加速查询，也会拖慢写入并占用空间。设计索引时要看真实查询模式。

常见原则：

- 高频过滤字段适合建索引；
- 联合索引要考虑最左匹配；
- 排序字段经常要和过滤字段一起设计；
- 低基数字段单独建索引价值有限；
- 查询只返回索引字段时可能走覆盖索引；
- 深分页会越来越慢，需要游标分页或基于索引的 seek。

比如任务列表常见查询是：

```sql
where user_id = ? and status = ?
order by created_at desc
limit 20
```

可以考虑联合索引：

```sql
(user_id, status, created_at)
```

但如果查询模式变化，索引也要重新评估，而不是凭感觉堆。

### 事务边界

事务保证一组数据库操作同时成功或失败。它适合保护本地一致性，比如：

- 创建任务；
- 写操作日志；
- 写 outbox 消息记录。

这些可以放进一个事务。

但不要把远程 RPC、HTTP 调用、MQ 发送放进数据库事务里。事务持有锁越久，系统吞吐越差，失败场景越复杂。

### 隔离级别和锁

服务端不一定一开始就深挖数据库内核，但必须理解：

- 并发更新同一行会产生锁竞争；
- 事务隔离级别影响读到的数据；
- 大事务会持有大量锁；
- `select for update` 能锁定行，但也可能造成等待；
- 乐观锁适合冲突不高的更新场景。

库存扣减、余额变更、状态流转这类逻辑，都要明确并发写入时怎么保证正确。

### Schema 迁移

线上数据库结构变更要向后兼容。一个稳妥流程通常是：

1. 先加新字段，允许为空；
2. 代码同时兼容新旧字段；
3. 后台回填历史数据；
4. 灰度切读新字段；
5. 确认稳定后删除旧字段。

不要在一次发布里同时改表、改写入、改读取、删旧字段。这样一旦回滚，数据和代码可能互相不兼容。

## 练习方式

给任务管理 API 接入 MySQL 或 PostgreSQL：

- 设计用户表、任务表、操作日志表；
- 为任务列表设计联合索引；
- 创建任务时使用事务写任务和日志；
- 加唯一约束保护幂等 key；
- 写一个迁移脚本给任务增加 priority 字段；
- 用压测观察有索引和无索引的查询差异。

重点不是把 ORM 用熟，而是理解 ORM 背后的 SQL、事务和索引。
