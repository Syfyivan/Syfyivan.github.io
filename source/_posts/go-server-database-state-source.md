接口写到最后，问题都会落到数据上。缓存可以删，消息可以重放，接口可以改，但数据库里的状态一旦乱了，修起来最麻烦。

所以这一站不急着背 SQL 细节，先把“数据怎么被正确地写进去，又怎么被稳定地查出来”想清楚。

## 表不是对象的影子

建表前先问几个问题：

- 这张表代表什么业务事实；
- 哪些字段能唯一确定一条记录；
- 状态有哪些合法流转；
- 哪些查询会特别频繁；
- 以后数据量大了怎么归档；
- 删除是真删还是软删。

比如任务系统，至少会有用户、任务、操作日志。创建任务时，任务表记录当前状态，操作日志记录“谁在什么时候做了什么”。这比只在任务表里改一个 status 更容易追溯。

## 约束要交给数据库一部分

有些规则不要只靠代码判断。

邮箱唯一、订单号唯一、幂等 key 唯一，这类规则最好有数据库唯一约束兜底。因为线上总会有并发，总会有重试，也总会有你没想到的入口。

状态也一样。比如订单从 `created` 到 `paid`，不能随便从 `canceled` 又跳回 `paid`。代码里要有状态机，数据库更新时也要带上旧状态条件。

```sql
update orders
set status = 'paid'
where id = ? and status = 'created'
```

影响行数为 0，就说明状态已经变了，不能假装成功。

## 索引跟着查询走

索引不是越多越好。写多了会拖慢写入，也会让维护变复杂。

我通常先列出真实查询：

```sql
where user_id = ? and status = ?
order by created_at desc
limit 20
```

再考虑联合索引：

```sql
(user_id, status, created_at)
```

如果列表页后面要翻很多页，就别只靠 offset 深分页。可以用上一页最后一条的时间或 id 做游标，查询会稳很多。

## 事务别包太大

事务适合保护本地数据库一致性。比如创建任务时：

1. 写任务；
2. 写操作日志；
3. 写 outbox 事件。

这三步可以放同一个事务里。

但远程 RPC、HTTP 调用、MQ 发送，不要塞进数据库事务。事务持锁时间越长，越容易拖慢整条链路。跨系统一致性后面用消息、状态机和补偿来处理。

## 迁移要给回滚留路

线上改表最怕“一步到位”。

更稳的节奏是：

1. 先加新字段，旧代码不受影响；
2. 新代码双读或双写；
3. 回填历史数据；
4. 灰度切到新字段；
5. 稳定后再清理旧字段。

这样就算中间要回滚，也不会出现旧代码读不了新数据的尴尬情况。

## 一个练习

给任务 API 接数据库：

- users；
- tasks；
- task_logs；
- idempotency_keys；
- 为任务列表建索引；
- 创建任务时用事务写任务和日志；
- 用唯一约束挡重复创建；
- 写一条迁移，给任务加 priority。

ORM 可以用，但别只看 ORM。把它生成的 SQL 打出来看一眼，很多问题会提前暴露。
