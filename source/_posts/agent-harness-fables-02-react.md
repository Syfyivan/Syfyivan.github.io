小镇有个送信人，名叫阿闻。镇长问他：“山那边今天会下雨吗？”

阿闻没有装作自己知道。他先走到回音井边，对井说：“请问山那边的天气。”井回了一张纸条：“小雨，气温 18 度，北风。”

阿闻拿着纸条回去，告诉镇长：“会下小雨，出门带伞。”

第二天镇长又问：“山那边和河对岸，哪里更适合晒谷子？”

这次阿闻没有跑两趟。他同时把两张问题纸投进回音井，等两张回信都上来，再比较湿度、风向和气温，最后才回答。

第三天问题更复杂：“三天后办集市，哪个地方更稳妥？”

阿闻先查天气，再查路况，再查摊位记录。每拿到一张回信，他都重新判断下一步要问什么。

## 概念揭晓

回音井就是工具。阿闻不是天气专家，但他知道什么时候该查天气、查哪个地方、查完怎么解释。

在 tool calling 里，模型做的是“决定要不要调用工具，以及带什么参数”。真正执行工具的是 Harness，也就是系统外壳。

一个完整流程大概是：

```text
用户提出问题
模型判断需要工具
模型产出 tool_call 和参数
Harness 执行工具
工具结果回到消息历史
模型基于结果继续回答或继续调用工具
```

OpenAI 的 function calling 文档把这件事拆得很清楚：模型可以生成工具调用，应用侧执行代码，再把工具输出交还给模型。模型不是直接控制世界，它是在写一张“请执行这个动作”的单子。

## 本章目录

- 单轮、并行、多轮：三种常见工具调用节奏。
- 工具契约：为什么工具说明比工具名字更重要。
- 调试方法：从 transcript 看模型为什么会选错工具。
- 小练习：删掉工具名，只靠描述判断工具能不能被正确使用。

## 单轮、并行、多轮

第一天是单轮：一个问题，一个工具调用，一个结果。

第二天是并行：同一轮里发出多个 tool call，等结果回来后一起比较。

第三天是多轮：后一个问题依赖前一个结果。Deep Research、代码修复、故障排查，常常都是这种形态。

这三种形态背后还是同一条线：Reason、Act、Observe。区别只是水车转了几圈，以及一圈里挂了几个水桶。

## 最容易误解的一点

工具不是模型的超能力。工具是合同。

合同写得烂，阿闻就会问错井。比如工具叫 `search`，描述只写“搜索东西”，模型就很难判断它能不能查实时资料、能不能查内部文档、返回的是摘要还是全文。

好合同应该写清楚：

- 什么时候用。
- 什么时候不要用。
- 参数必须是什么格式。
- 结果大概代表什么。
- 和相似工具的边界在哪里。

工具调优不是玄学，更多时候是在调合同。

## 今天的练习

拿一个你常用的工具定义，删掉工具名，只看描述和参数。问自己：一个新同事能不能仅凭这段说明正确使用它？

如果不能，模型大概率也不能。
