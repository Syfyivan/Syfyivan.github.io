## AI 观察

### 1. “主控 + 执行”不是多开几个 agent，而是拆开决策权

今天的《Codex 攻略日报》最值得留下的不是某一条提示词，而是角色边界：主控负责目标、范围、架构判断和验收证据；执行角色负责在边界内修改代码、运行命令和回传结果；高风险部分再交给复核角色。这样的拆分把“我觉得应该这样做”和“我已经验证这样做”分成了不同的产物。

这和 [Aegis 公开仓库](https://github.com/GanyuanRan/Aegis) 的自述方向相近：先建立基线，再要求证据，区分修复路径与旧路径退役，并让简单任务保持轻量。仓库还公开了一个自称受控的 A/B benchmark：相同 Codex 客户端、模型、推理档位、提示词、项目和工具策略下，只改变方法包投影。这个结果可以作为项目自己的实验记录，但不能直接外推成所有代码库、模型和团队的普遍收益。

工程上，主控并不一定要更“聪明”，它更需要拥有三种权力：拒绝未经证据支持的完成声明，要求执行角色补齐验证，以及在结果不满足边界时重新分派任务。执行角色也不应该拥有无限扩张范围的权力，否则“分工”只是把风险藏到另一个上下文里。

### 2. Skill 的价值在于把方法写成可检查的工作流

一个 Skill 如果只有“请认真完成任务”，很快会退化成风格提示；它真正有价值的部分应当能映射到检查项：任务目标是否明确，修改前基线是否存在，允许改动哪些目录，哪些命令可以执行，完成需要哪些证据，失败如何回退，旧路径何时退役。

因此，Skill 更像一个轻量的交付协议，而不只是 prompt 片段。它至少可以输出四类对象：

1. `Scope`：目标、非目标、允许触碰的边界。
2. `Plan`：角色、步骤、依赖和风险。
3. `Evidence`：diff、测试、日志、截图或可复现命令。
4. `Decision`：完成、阻塞、回退或需要人工选择。

这也解释了为什么日报把“主控只写目标和验收证据，再让执行角色实现，最后交回 diff、测试结果和风险”单独列为今日玩法。它降低了代理把“生成了代码”误报为“问题已解决”的概率，也让人类更容易在中途接管。

### 3. A2A 与 MCP 分别解决“找谁协作”和“能调用什么”

[A2A 官方说明](https://a2a-protocol.org/latest/) 明确把 A2A 定义为 agent-to-agent 的通信与协作协议：不同框架、平台和供应商的 agent 可以发现彼此、委派子任务、交换结果，同时不必暴露内部记忆、工具或实现细节。它还明确说明 A2A 不是 agent 开发框架，也不是工具调用协议。

[MCP 当前任务规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks) 则把长任务表示为带任务 ID 的持久状态机，允许请求方轮询和延迟取回结果。结合 MCP 的工具、资源和提示词模型，可以把它理解成 agent 与外部能力之间的连接层。

这两个协议放在一起看，边界很清楚：A2A 负责“把工作交给另一个 agent”，MCP 负责“让一个 agent 使用工具、资源或外部系统”。如果一个系统把两者都抽象成任意 JSON 转发，就会失去权限、超时、幂等、任务状态和责任归属。今天群里推荐的 A2A 接入文章，真正值得跟进的正是这条边界，而不是“再加一个协议”本身。

### 4. 证据闭环是多 agent 系统的共同语言

当角色变多，最容易丢的是上下文，最容易混淆的是责任。主控说“执行角色已经改了”，执行角色说“测试应该由主控判断”，最后人类只看到一段看起来合理的总结。这时，交付物必须从自然语言升级为证据包：

```text
task_id
scope_snapshot
baseline_commit
role_and_model
changed_files
tool_calls
test_commands_and_results
known_risks
rollback_point
final_decision
```

证据包不要求每个任务都写成审计报告。简单任务可以只保留目标、diff 和一条验证命令；跨文件重构、跨 agent 委派或会触碰外部系统的任务，才展开完整字段。关键是完成标准要与风险匹配，而不是所有任务都堆一套繁重流程。

## 前端 / 服务端 / 客户端工程观察

### 前端：把角色和证据变成可读的任务界面

前端不应只显示“Agent 正在工作”。如果当前任务有主控、执行和复核角色，界面至少要让用户看到：每个角色的目标、当前阶段、最近一次产物、等待什么，以及谁有权推进下一步。

一个轻量任务卡可以这样组织：

| 区域 | 应展示的内容 | 用户动作 |
| --- | --- | --- |
| 目标 | scope、非目标、验收条件 | 修改边界或确认目标 |
| 角色 | 主控、执行、复核及各自模型 | 查看责任和暂停角色 |
| 证据 | diff、测试、日志、截图、外链 | 打开证据或要求补证 |
| 状态 | 执行中、等待工具、待复核、阻塞、已交付 | 继续、重试、回退或接管 |
| 风险 | 未验证路径、权限变化、外部副作用 | 接受风险或转人工审批 |

对前端来说，最重要的交互不是“再开一个 agent”，而是“从哪个证据点继续”。当用户从桌面端切到浏览器或移动端时，应该看到同一个 `task_id` 和同一份验证状态，而不是一条孤立的摘要。

### 服务端：为委派、任务和副作用建立明确状态机

服务端应把角色协作建模成可追踪的状态迁移，而不是把每次委派当成普通聊天消息。例如：

`created → scoped → delegated → executing → evidence_submitted → reviewing → verified → delivered`

每个状态都要绑定任务 ID、父任务 ID、工作区或代码版本、角色、模型、工具权限、预算、输入输出摘要和时间戳。执行角色调用外部写接口时，还需要幂等键与外部回执；主控超时不应自动再次创建 PR、发送通知或修改配置。

A2A 只定义 agent 间的通信协作，并不替系统决定谁可以写数据库；MCP 的任务也不等于业务系统的最终完成状态。真正的服务端边界仍要由业务权限、审计记录、重试策略和人工审批补齐。

对长任务，建议至少区分三种结果：请求尚未产生副作用、请求已完成但回执丢失、请求失败且确认可以安全重试。只有第三种才适合无条件重试。第一种与第二种如果被混为“超时”，就会把协议层的可靠性问题变成业务层的重复写入。

### 客户端：本地、云端、IDE 和移动端共享控制面

OpenAI 的 [Codex 官方仓库](https://github.com/openai/codex)把 Codex CLI 描述为运行在本机终端的 coding agent，同时将 IDE、桌面和云端入口分开说明。入口可以不同，但任务控制面不应各自发明一套身份：任务 ID、角色、模型、权限、审批、变更摘要、验证结果和恢复点应该可跨端读取。

客户端还要把“观察”与“控制”区分开。移动端可以查看任务进度、批准低风险步骤或要求暂停，但不应因为一个简化按钮就默认获得本地文件、生产系统或外部写接口权限。桌面端执行本地命令时，应明确显示工作区；云端 agent 返回 patch 时，应明确显示它对应的提交和验证环境。

对 A2A 和 MCP 的接入，客户端还应显示调用链：这是委派给另一个 agent，还是调用一个工具；工具是只读还是有副作用；任务是否可轮询；失败后能否安全恢复。可解释的调用链比一个“已使用 MCP/A2A”的徽标更有用。

### 共同边界：不要把方法包、协议能力和产品承诺混为一谈

Aegis 的公开仓库、A2A 的协议说明和 MCP 的任务规范分别代表项目方法、通信标准和任务原语。它们能帮助我们设计系统，但不等于任何 Codex、Claude Code、IDE 或企业平台已经完整实现了相同的能力。尤其是“支持 A2A”不代表已经具备跨租户授权、幂等写入、可观测追踪和安全审批。

## 值得跟进的动作

1. 选一个两小时内能完成的真实代码任务，试跑“主控—执行—复核”三角色流程；只比较完成证据、返工次数和恢复成本，不先比较 prompt 长度。
2. 给每个 agent 任务增加最小证据包：范围、基线提交、修改文件、验证命令、结果、未解决风险和回退点。
3. 把 A2A 与 MCP 的边界写进内部设计：前者负责 agent 委派，后者负责工具与资源；为两条链路分别定义认证、权限、超时、幂等和审计字段。
4. 在前端任务卡上展示角色、状态、证据和副作用，提供“要求补证”“暂停”“从回退点继续”三个明确动作。
5. 在服务端先实现父任务 / 子任务关系和幂等回执，再扩大并行 agent 数量；没有任务归属和回执，更多并发只会扩大排错面。
6. 对 Aegis 或类似 Skill 做一次隔离试用：检查安装范围、默认激活方式、升级路径和验证脚本，不把第三方仓库 README 或自动安装命令直接视为组织规范。
