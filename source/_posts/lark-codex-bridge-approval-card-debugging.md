这次故障表面上很像“点了同意执行，但本机没有动”。真正查下来，结论反而更麻烦一点：**按钮生效了，任务也启动并完成了，只是所有可见通知都失败了**。

这类问题很容易误判。人看到的是聊天窗口里没有“已开始”“已完成”的回复，于是自然会认为按钮没有触发；但本机状态里已经有审批记录、子进程、完成时间和结果文本。一个自动化系统只要把“执行是否成功”和“通知是否成功”混在一起，就会让用户从 UI 上得到相反的事实。

这篇是一次脱敏复盘，只保留机制和工程教训，不放内部群 ID、用户 ID、私有仓库链接、日志路径或 token。

## 现象：同意按钮之后没有任何反馈

当时链路是这样的：

1. 群里有人发代码评审请求，并带了代码平台的 MR 链接。
2. 桥接器识别到这可能涉及 MR comment 或 approve，生成“需要确认本机操作”的审批卡。
3. owner 点击“同意执行”。
4. 聊天窗口里没有出现“已开始执行”，也没有最终 review 结果。

从用户视角看，这就是“没执行”。但本机侧的状态记录显示，审批已经从 `pending` 变成 `running`，随后 review 自动化记录也创建出来，最后还变成了 `done`。也就是说，问题不在按钮触发，而在反馈链路。

## 根因一：通知用的幂等 key 超过平台字段限制

桥接器每次发 IM 消息都会带一个 idempotency key，避免重试时重复发消息。问题出在 key 的生成方式太“诚实”：

```text
delegate-action-thread-<operation-id>-<action>-<count>-<uuid>
```

这串东西一拼就很长。实际失败的 key 长度超过 90 个字符，而 IM OpenAPI 对这个字段有长度和字符集约束。平台返回的是字段校验错误，结果是：

- “已同意执行，开始处理”的话题回复失败；
- 私聊兜底通知也失败；
- “执行完成”的最终通知也失败。

任务本身在跑，但所有用户能看到的状态都被同一个参数问题挡住了。

修复方式很直接：所有发消息的 `--idempotency-key` 在进入 CLI 前统一规范化。

- 只保留安全字符。
- 短 key 原样使用。
- 长 key 截断前缀，并追加短 hash。
- 最终长度控制在平台字段限制以内。

这个修复点最好放在统一的 `runCli` 包装层，而不是在每个调用点手工截断。因为消息发送入口很多，只修一个按钮回调，下一次 final reply、P2P fallback 或进度卡仍然可能踩中同一个坑。

## 根因二：执行状态和通知状态耦合过紧

还有一个隐藏问题：review 自动化完成后，桥接器会把结果回复到原话题。如果这一步失败，旧代码可能把整个 review 标成 failed。

这在语义上是不对的。对用户来说可以分成三件事：

- Agent 有没有启动；
- Agent 有没有完成 review；
- 结果有没有成功回写到 IM。

第三件事失败，不应该抹掉前两件事的事实。修复后，review 执行成功会先落 `done` 和 `resultText`；回写失败只记录 `replyError`，不再把已完成任务改成失败任务。

这条很重要，因为生产排障时我们需要回答的第一句话通常是“它到底有没有执行”。如果状态模型把执行失败和通知失败揉成一个字段，就只能继续猜。

## 根因三：普通委托卡和敏感操作卡不是一类卡

之前已经修过一次“卡片套卡片”：桥接器的轮询兜底会把自己发出去的审批卡、已删除消息、bot 自己的消息继续当成新委托处理，于是出现卡片里再生成卡片的循环。

那次修复做了三件事：

- 识别并跳过审批卡文本；
- 跳过已删除消息和 bot 自己发出的交互消息；
- 关闭普通委托草稿审批卡和轮询兜底，只保留明确的 review 自动化入口。

但这次出现的卡不是普通草稿卡，而是“敏感操作确认卡”。原因是 MR review 自动化理论上可能写 MR comment 或 approve，非 owner 发起时旧策略仍然要求 owner 确认。这在安全上说得通，但和“不要再发卡片”的体验目标冲突。

最终调整是：**非 owner 发起的 MR review 不再弹敏感操作卡，而是直接进入只读 review 模式**。

只读模式可以查 MR、读 diff、看评论和 CI 状态，然后在话题里回复结论；但禁止写 MR comment、approve、request changes、merge。owner 本人发起，或明确的人类转发授权场景，才保留可写 review/approve 能力。

这比“把审批全部关掉”更稳：不刷卡片，同时不把外部发起人的一句话升级成本机写代码平台的授权。

## 为什么之前没发现

这件事不是今天才做，而是之前已经做了很久，今天才暴露。原因主要有四个。

第一，之前验证关注的是“点击按钮后状态是否变化、Codex 是否启动”，没有把“话题里是否真的出现可见反馈”作为必测断言。状态机过了，但用户可见闭环没过。

第二，开发和手工测试里常用的是短 idempotency key。真实卡片回调里把 operation id、action、计数和 UUID 拼在一起，长度一下子超过平台限制。测试样本没有覆盖生产长度。

第三，通知失败被当成附属日志处理，没有在健康检查或任务摘要里突出展示。于是它不是“失败”，只是日志里一段很容易被忽略的 400。

第四，卡片套卡片和敏感操作卡属于两条策略链。前一次修的是“不要把自己发的审批卡再当成新委托”，这一次暴露的是“非 owner review 请求是否还应该发敏感确认卡”。表面都是卡片，实际不是同一个 bug。

## 这次补上的护栏

这次补了几条比较关键的护栏：

- 统一收口 IM 发送参数，所有 idempotency key 进入 CLI 前先规范化。
- review 执行结果和 IM 回写结果解耦，回写失败只记录 `replyError`。
- 非 owner MR review 改成只读模式，不再生成确认卡。
- owner / 明确授权转发的 review 仍可走写操作路径，但保留 CI、阻塞评论、状态确认等 approve 条件。
- 普通委托草稿卡继续关闭，卡片消息、删除消息、bot 自己的交互消息继续跳过。
- 排障时优先看本机审批存储、任务记录、子进程和最终结果文本，而不是只看聊天窗口有没有回复。

这类桥接器最怕的不是某个 API 偶发失败，而是用户看到的状态和机器真实状态不一致。以后类似链路的验收标准应该写成端到端闭环：

```text
用户点击 -> 本机状态 running -> 子进程存在 -> 任务完成 -> 结果落盘 -> 话题可见回复
```

中间任何一步失败，都要能单独标出来。只有这样，下一次看到“没反应”的时候，才不会把“没有通知”误判成“没有执行”。
