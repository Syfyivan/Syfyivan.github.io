这篇文章只讲进度解锁活动，不再把它和抽卡资产、徽章发放或压测混在一起。

需求最初被拆成约七人日的服务端工作：新增进度条类型、活动页进度查询、随机掉落、签到任务、保底积分和多抽配置。真正做完以后，它已经不只是一个进度条，而是一套连接运营配置、实时任务、离线聚合、奖品履约和前端展示的全栈能力。

公开版本删除了内部系统名称和精确活动数据，但保留真实时间顺序、技术取舍和后续修正。

## 一、十五秒怎么介绍

> 我负责过一套进度解锁活动的全栈交付。用户通过签到、分享和互动贡献积分，全站总积分达到阶段阈值后解锁图片、视频或跳转内容，同时支持随机掉落和多次抽奖。服务端没有在页面请求时实时扫描全量积分，而是通过离线任务聚合并写快照，让 C 端查询保持常数复杂度；需求后来继续沉淀成可配置能力，支撑了多场节点活动。

如果面试官感兴趣，再进入后面的时间线。

## 二、为什么它不是一个普通进度条

表面需求是：

```text
总积分达到 100 万 -> 解锁图片
达到 300 万 -> 解锁长图
达到 500 万 -> 解锁视频
```

服务端实际要解决：

- 阶段阈值和素材如何配置；
- 全站总分从哪里来；
- 用户刚完成任务时怎样及时看到个人反馈；
- 离线聚合延迟怎样解释；
- 多个任务重复回放会不会重复加分；
- 保底积分会不会被每轮任务重复累加；
- 随机掉落达到多个阈值时如何防重复；
- 三连、五连、十连如何保存配置并限制运行时；
- 签到怎样复用统一积分体系；
- 老活动和旧客户端如何不受新字段影响。

## 三、真实开发时间线

### 第一阶段：4 月下旬，先落最小主链路

第一轮先完成四件事：

1. 增加“奖励解锁型进度条”这一配置类型；
2. C 端能够根据活动和组件读取总分快照；
3. 离线任务能够聚合用户积分并写快照；
4. 增加随机掉落和多抽的最小运行入口。

这个阶段的目标不是一次支持所有素材，而是先证明：

```text
运营可以保存阶段配置
  -> 用户行为进入积分体系
  -> 离线任务生成总分
  -> 页面能读到总分和阶段状态
```

第一版之后立即补了两类保护：禁用的进度条不能被离线任务误处理；随机掉落配置中暂时不支持的阈值组合要在发布时拒绝，而不是运行到一半才失败。

### 第二阶段：4 月底到 5 月上旬，补齐存储和配置闭环

最小链路跑通后，问题从“能不能工作”变成“保存后会不会丢字段”。

这一阶段重点处理：

- 空数据表或缓存缺失时不要走错误的读取分支；
- 随机掉落的内部奖池必须跟随活动配置保存；
- 复制活动时，新旧奖池 ID 要正确映射；
- 多抽次数经过后台保存、领域转换和数据库以后不能丢失；
- 长图、视频、跳转卡片的必填字段要按素材类型校验。

这里有一个很典型的中台问题：前端已经出现了一个配置项，不代表它真的被端到端保存。要沿着：

```text
后台表单
  -> BFF 模型
  -> IDL
  -> 领域配置
  -> DB extra
  -> 再次查询回显
```

逐层核对。

### 第三阶段：5 月中旬，解决积分单位和任务接入

不同互动链路的积分历史上可能使用不同缩放单位。有的运行时按原始整数存储，有的排行榜为了精度放大一百倍。

如果签到直接加 10，离线排行榜却把 1000 理解为 10，就会出现：

- 实时接口显示增加 1000；
- 页面总分只增加 10；
- 随机掉落阈值又按另一种单位判断。

因此这一阶段明确了两套边界：

```text
任务配置和接口返回：业务展示单位
排名与部分历史存储：内部缩放单位
```

所有进入目标进度和随机掉落判断的分数先归一化。签到提交不再强制依赖并不存在的通用任务 ID，而是根据活动中的签到规则完成校验。

分享和答题任务也在这一阶段接入统一奖励链路，避免“页面显示完成，但奖励没有落地”。

### 第四阶段：5 月下旬，补图片奖品和展示动作

业务继续要求解锁图片奖品。服务端不仅返回图片 URL，还要返回前端应该展示什么操作：

- 实物奖：填写或查看地址；
- 优惠权益：领取、使用或已失效；
- 图片奖：保存图片；
- 其他奖品：仅展示。

这次扩展说明，奖品不能只返回 `prize_type + url`。前端如果自己推导动作，不同页面会出现不一致。更好的方式是服务端返回一个稳定的 `action_info`。

### 第五阶段：6 月以后，优化热点读和后续复用

相关活动规模放大后，又补了一项读路径优化：奖励解锁型进度条不需要每次都统计当前报名人数。

旧的通用进度条会在阶段完成时查询报名人数，但奖励解锁页面只关心总分和阶段状态。跳过无关统计后，C 端路径保持为一次 KV 读取加少量配置遍历。

这不是需求首版的一部分，而是上线和复用后根据访问模式做的收敛。

## 四、整体技术链路

```text
运营后台
  -> 配置阶段、素材、保底积分、随机掉落、签到、多抽
  -> BFF 转换并提交领域服务
  -> 领域服务校验并保存

用户实时行为
  -> 签到 / 分享 / 答题等任务入口
  -> 更新用户积分或排名记录
  -> 立即返回个人本次得分

离线聚合
  -> 读取当前用户积分集合
  -> 统一分数单位
  -> 求和并叠加保底积分
  -> 高水位写入总分快照

C 端读取
  -> 读取总分快照
  -> 遍历阶段配置
  -> 返回每个阶段是否完成和展示信息
```

## 五、阶段配置怎样设计

一个阶段至少包含：

```text
phase_id
target_score
description
material_type
image_url
long_image_url
video_url
schema
fallback_material
```

发布时验证：

- target_score 严格递增；
- 阶段 ID 不重复；
- 图片阶段必须有图片；
- 视频阶段必须有视频或允许的兜底素材；
- 跳转协议属于允许范围；
- 老活动没有新字段时仍使用默认值；
- 未启用的组件不进入离线聚合。

为什么阈值必须严格递增？如果两个阶段同分或后一个更小，页面很难解释当前阶段，运营也无法判断解锁顺序。

## 六、为什么不在页面请求时实时求全站总分

假设有数十万参与用户，每次页面打开都运行：

```sql
SELECT SUM(score) FROM user_score WHERE activity_id = ?;
```

即使有索引，访问峰值仍会把页面 UV 放大成聚合压力。进度条又不要求毫秒级精确，因此使用离线快照更合理。

读取变成：

```text
key = progress_total:{activity}:{component}
GET key
```

时间复杂度不随参与用户增长。

## 七、离线聚合怎么计算

伪代码：

```text
total = 0
for user in current_ranking:
    raw = parse(user.score)
    normalized = normalize(raw)
    total += normalized

if guaranteed_score_enabled:
    total += guaranteed_score

store_high_water(total)
```

这里有三个细节：

1. 单条分数无法解析时，不能静默跳过，否则总分会偏小；
2. 保底积分是公式项，每轮重算一次，不是 delta；
3. 写入需要防止旧任务覆盖新任务。

## 八、高水位写入为什么使用 max

离线任务可能并发或乱序：

```text
任务 A 算出 900 万，执行较慢
任务 B 稍后算出 1000 万，先写入
任务 A 最后才写
```

普通 SET 会让总分从 1000 万退回 900 万，导致阶段重新锁住。

因此第一版采用短锁保护：

```text
existing = GET key
stored = max(existing, calculated)
SET key stored
```

这个选择依赖产品规则“解锁后不回退”。如果产品要求违规内容删除后撤回进度，就需要版本化快照或从事实明细重算，不能继续使用 max。

## 九、锁的实现会被怎么追问

当前模型使用带 TTL 的短锁并进行有限次重试。面试官可能继续问：

### 锁到期后旧任务释放了新任务的锁怎么办

更强的锁应保存 owner token，释放时比较 token，只删除自己持有的锁。简单 `DEL lockKey` 在任务执行超过 TTL 时可能误删后来 worker 的锁。

这个是合理的扩展设计题。如果原代码没有 owner token，要说清楚现状与可以改进的地方，不要假装已经实现。

### 为什么不用原子脚本

如果 KV 支持脚本或 CAS，可以原子完成 max 写入，减少锁复杂度。选择短锁通常是因为当时已有存储封装和交付时间约束。

## 十、保底积分为什么不能累加

错误做法：

```text
每次离线任务：current += guaranteed_score
```

任务执行十次就会加十次。

正确做法：

```text
target = sum(real_user_score) + guaranteed_score
```

保底积分表示运营希望进度至少多出一段固定贡献，不是一笔重复发放的用户资产。

## 十一、随机掉落状态机

随机掉落可以配置成每次触发一次，或者按积分阈值触发。

阈值模式保存：

```text
triggered_thresholds: {
  100: true,
  300: true
}
```

一次请求：

```text
获取用户锁
  -> 读取当前积分
  -> 找到已达到但未触发的阈值
  -> 汇总 draw_times
  -> 增加对应抽奖机会
  -> 执行抽奖
  -> 保存阈值状态
```

### 可能被追问：中途部分失败怎么办

如果一次跨过三个阈值，前两个抽奖成功，第三个失败，而状态尚未保存，重试可能重复前两个。

更强方案是每个阈值一条执行记录：

```text
(activity, user, threshold)
pending -> executing -> completed / failed
```

这是从原实现推导的增强方向，适合设计题，不说成线上已经发生的事故。

## 十二、多抽配置为什么只允许有限值

后台限制 3、5、10 等固定值，而不是任意整数：

- 控制一次请求的最大执行时间；
- 便于前端布局和动画预设；
- 便于 QA 覆盖；
- 避免运营误配上百次抽奖；
- 底层库存与机会扣减可以预估。

运行时仍需要再次校验，不能信任配置或客户端。

## 十三、签到任务怎样处理限次

签到状态至少包含：

```text
daily_count[date]
total_count
total_score
```

请求流程：

```text
校验活动和任务类型
  -> 获取用户级锁
  -> 按业务时区读取今日计数
  -> 校验每日上限和活动总上限
  -> 更新用户积分
  -> 更新签到状态
  -> 返回本次增加和当前累计
```

为什么必须指定业务时区？服务器可能部署在不同时区，依赖本地时区会让“今天”在不同实例上不一致。

## 十四、开发中几个有价值的修正

### 1. 禁用组件仍被离线任务处理

修正：聚合前同时检查进度条类型和 enable 状态。

### 2. 多抽配置后台保存后丢失

修正：沿后台、IDL、领域模型、DB extra 和查询回显逐层补齐。

### 3. 签到强制要求通用 task_id

修正：签到由活动中的任务组件和签到规则定位，不要求不存在的外部任务 ID。

### 4. 互动分数单位不一致

修正：实时链路和离线聚合都进入统一归一化函数。

### 5. 图片奖只有 URL，没有动作语义

修正：服务端返回“保存图片”等 action_info。

### 6. C 端进度读取附带无关报名统计

修正：奖励解锁类型跳过报名人数热点查询。

## 十五、怎么验证

### 配置测试

- 阈值无序必须拒绝；
- 缺素材必须拒绝；
- 旧配置无新字段仍可读；
- 保存后再查询字段不丢失。

### 聚合测试

- 多用户求和正确；
- 分数缩放正确；
- 保底积分只加一次；
- 旧任务晚写不会回退；
- 缓存不存在时行为明确。

### 任务测试

- 同日重复签到达到上限；
- 跨日重新计数；
- 总次数达到上限；
- 两个并发请求只有一个成功。

### 随机掉落测试

- 未达到阈值不触发；
- 达到一个阈值只触发一次；
- 一次跨多个阈值次数正确；
- 已触发阈值不重复。

## 十六、业务结果怎么说

相关节点活动合计达到千万级曝光和数十万任务参与，说明进度解锁、任务和抽奖能够支撑大规模运营玩法。

不能说“因为我写了离线聚合，所以产生了这些 UV”。更准确的因果关系是：

> 我负责的配置、聚合和任务链路让玩法可以稳定运行并被后续活动复用；最终曝光和参与由内容、资源位、运营玩法和整条研发链路共同产生。

## 十七、两到三分钟口述版

> 我负责过一套进度解锁活动的全栈交付。业务上，用户通过签到、分享和互动贡献积分，全站总积分达到阶段阈值后解锁图片、长图、视频或跳转内容，同时支持随机掉落和多抽。
>
> 最大的服务端难点是总进度。它来自大量用户，不能每次打开页面都实时扫描。所以我把实时和聚合拆开：用户任务完成后实时更新个人积分并返回本次得分；离线任务周期性读取积分集合，统一不同互动链路的分数单位，求和后叠加保底积分，再写入按活动和组件区分的 KV 快照。C 端只读一次快照并遍历少量阶段配置，访问量增加时查询成本仍然稳定。
>
> 写快照时还要处理任务并发和乱序。因为产品定义解锁后不回退，我用高水位语义保存 max(existing, calculated)，避免旧任务把进度覆盖回去。阶段素材、阈值、随机掉落、多抽和签到都做成配置，并在发布时校验；旧活动没有新字段时保持默认行为。
>
> 这个需求不是一次写完。第一轮先跑通配置、离线聚合和 C 端读取，之后继续修正配置字段丢失、签到任务定位、积分单位、图片奖动作和热点报名统计。最后能力被多个节点活动复用。我认为这个项目最能体现的是，我不仅完成一个页面接口，而是把实时任务、最终一致聚合和运营配置组织成了一套可持续复用的能力。

## 十八、高频追问

### 为什么不用实时 SQL SUM

访问量会放大全表聚合成本，而总进度允许短暂延迟。离线快照使 C 端查询稳定。

### 离线任务延迟多久可以接受

由产品定义刷新周期。服务端记录快照更新时间、任务延迟和失败告警，页面可以显示“数据更新中”。

### KV 丢失怎么办

纯展示场景可以返回 0 并报警；涉及真实权益时不能仅凭缺失快照判定资格，要查询权威记录。

### 为什么 max 不会掩盖错误数据

它确实可能保留一次异常高值，所以需要写入前做上限、增幅和来源校验。max 只解决乱序，不解决输入可信度。

### 怎么防止离线任务重复执行

聚合是目标值重算，不是 delta；重复计算同一事实得到同一目标，高水位写入保持幂等。

### 随机掉落和主抽奖为什么分开

触发条件、幂等状态和展示入口不同。可以复用底层奖池，但不能混淆业务来源。

### 你个人负责到什么程度

我覆盖了后台配置、协议、领域逻辑、离线聚合和前端接入等多个环节，可以按提交和联调链路说明；业务效果属于团队共同结果。
