<div class="csf-key-note">你打开电脑，浏览器、音乐、微信、编辑器，几十个程序看起来都在<strong>同时</strong>跑。但你的 CPU 可能只有 8 个核——它怎么伺候得过来几十个程序？<br><br>先说清楚一个词：CPU 里负责真正干活的单元叫"核"（core），你可以把一个核理解成一个工人——一个工人同一时刻只能做一件事；8 核就是 8 个工人。买电脑时听到的"几核几核"，说的就是这个。这一讲里"核"会反复出现，记住这个比喻就够了。这一讲的答案会有点反直觉：很多"同时"其实是<strong>装出来的</strong>。CPU 切得太快，快到你的眼睛和感觉都被骗过去了。看懂这个"骗局"，你才真正理解了电脑为什么会卡、为什么多开会变慢。</div>

## 🎯 这一讲你会学到什么

上一讲我们讲了线程——一个进程里可以有"多个分身"同时干活。但这里藏着一个没说破的问题：如果你的电脑只有几个 CPU 核，那几十个进程、上百个线程，凭什么能"一起"动起来？

这一讲就来揭这个底。学完你会知道：

- **分时复用**：CPU 其实是在飞快地轮流执行各个程序，"同时"很大程度上是错觉。
- **时间片**：每个程序一次只能用 CPU 一小会儿，时间一到就被换下来。
- **上下文切换**：换人是有代价的，不是免费的。
- **调度器**：是谁在决定"下一个轮到谁"。
- **并发 vs 并行**：这俩词长得像，意思差很远，搞混了你会判断错很多事。
- **核数**：到底"能真正同时跑几个"，跟你电脑有几个核什么关系。

<div class="csf-note">这一讲我们会真的让电脑"忙起来"——写一个故意把 CPU 占满的小脚本，亲眼看着任务管理器里的曲线冲上去。别担心，它不会弄坏电脑，结束进程就回落了。</div>

## 🛠 跟我做

### 先猜一猜 <span class="csf-b csf-key">重点</span>

假设你的电脑有 8 个核。现在你写一个**永远停不下来的死循环**程序，让它拼命算、一刻不歇。运行它，然后打开任务管理器看 CPU 占用。

先别往下看，**在心里猜一个数**：

- 这一个死循环程序，会让 CPU 总占用冲到 100% 吗？
- 还是只占其中一部分？大概多少？

把你的猜测记下来，我们待会儿验证。

### 第一步：找到你的"任务管理器" <span class="csf-b csf-core">必读</span>

每个系统都有一个能看 CPU 实时占用的工具：

- **Windows**：按 `Ctrl + Shift + Esc` 打开任务管理器，点"性能"标签，看 CPU 那张图。右键 CPU 图，选"将图表更改为" → "逻辑处理器"，就能看到**每个核**单独的曲线。（这里的"逻辑处理器"你暂时可以当成"核"来看，点它看到的就是每个核的单独曲线；严格说两者有一点区别，后面会讲。）
- **macOS**：打开"活动监视器"（在"应用程序/实用工具"里，或用 Spotlight 搜 Activity Monitor），点"CPU"标签。再按 `Cmd + 2` 可以调出 CPU 历史窗口，看每个核。
- **Linux**：命令行敲 `top` 或 `htop`（`htop` 更直观，没装的话 `sudo apt install htop`）。`htop` 顶部那一排横条就是每个核。

先让它开着，眼睛盯着曲线。现在它应该是低低的、起起伏伏的。

### 第二步：写一个把 CPU 占满的死循环 <span class="csf-b csf-core">必读</span>

我们用 Python（前面的课装过了；没装的话，几乎任何语言都能写出等价的死循环）。新建一个文件叫 `busy.py`：

```python
# busy.py —— 一个故意停不下来的死循环
# 它什么有用的事都不干，只是疯狂地占着 CPU
while True:
    pass
```

就这么三行（注释不算）。`while True:` 表示"条件永远成立，一直循环"；`pass` 表示"什么也不做"。合起来就是：**一刻不停地空转**。这正是我们要的——一个不知疲倦、把 CPU 榨干的家伙。

<div class="csf-note">这段代码请你<strong>自己手敲一遍</strong>，别让 AI 替你生成。它短到没有任何理由偷懒，而亲手敲、亲眼看它跑起来的过程，才是这一讲真正的重点。</div>

接下来要在**这个文件所在的文件夹里**打开终端（也叫命令行，就是那个能敲命令的黑色/白色窗口）。怎么打开：

- **Windows**：打开 `busy.py` 所在的文件夹，点一下上方的地址栏，把里面的路径删掉，输入 `cmd` 再回车，就会在这个文件夹打开命令行；或者在文件夹空白处按住 `Shift` 再点右键，选"在此处打开终端"/"在此处打开 PowerShell 窗口"。
- **macOS**：在"访达"里右键 `busy.py` 所在的文件夹，选"服务" → "在文件夹中打开终端"（没看到这一项的话，先打开"终端"应用，输入 `cd ` 再把文件夹拖进窗口、回车，也能切到这个目录）。
- **Linux**：在文件管理器里右键文件夹空白处，多数系统有"在终端中打开"；或在终端里用 `cd 文件夹路径` 切过去。

终端打开后，敲下面这行回车：

```bash
python busy.py
```

如果运行后报错说版本太老，或者干脆提示找不到 `python` 这个命令，就把命令改成 `python3 busy.py` 再试一次（`python3` 是新版本，有些电脑上 `python` 还是很老的旧版，要用 `python3` 才行）。

运行后程序**不会有任何输出**，光标会停在那里——这是对的，它正忙着空转呢。现在马上去看任务管理器。

### 第三步：揭晓——一个死循环占了多少？ <span class="csf-b csf-key">重点</span>

回到你的猜测。你大概率会看到：

- **总 CPU 占用并没有冲到 100%**。在一台 8 核机器上，它通常只让总占用涨了 **十几个百分点**（大约 100% ÷ 8 ≈ 12.5%）。
- 但如果你看**单个核**的曲线，会发现**有一个核被顶到了接近 100%**，其它核还是悠闲的。

为什么？因为这个程序只有**一条执行线**（一个忙碌的线程），它一次只能待在**一个核**上拼命跑。其它 7 个核它够不着。所以"满了一个核",但"总盘子只占了八分之一"。

<div class="csf-why">这就是为什么有人说"我程序卡死了，可 CPU 才占 12%，明明还有余啊"——其实它的某一个核已经 100% 了，那条线已经堵死了，剩下的核帮不上它的忙。看总占用会骗你，要看单核。</div>

### 第四步：多开几个，看负载怎么铺开 <span class="csf-b csf-core">必读</span>

现在**再多开几个**同样的脚本。开几个新的终端窗口，每个都跑一遍 `python busy.py`（也可以复制成 `busy2.py`、`busy3.py` 分别跑）。

**先猜**：开 4 个死循环，8 核机器的总占用会变成多少？哪些核会忙起来？

开起来后再看：

- 每多开一个，总 CPU 占用就**再涨一截**（每个大约又是十分之一到八分之一）。
- 看单核曲线，你会看到**忙碌的核一个一个被点亮**——操作系统把这几个死循环**分派到了不同的核上**，让它们真正地并排跑。这就是后面要讲的"并行"。
- 如果你开的死循环数量**超过了核数**（比如 8 核开 12 个），那么核就不够分了，系统只能让几个程序**轮流**用同一个核——这时每个死循环分到的 CPU 就被摊薄了。

### 第五步：结束进程，看曲线回落 <span class="csf-b csf-core">必读</span>

观察够了就把它们都停掉：

- 在每个运行脚本的终端窗口里按 `Ctrl + C`，程序就会被中断。
- 关不掉的，可以在任务管理器/活动监视器里找到对应的 `python` 进程，右键"结束任务"/选中后点左上角停止。

看着 CPU 曲线**唰地落回**原来的低位。这说明：占用是这些进程实实在在"占"出来的，进程没了，CPU 就闲下来了。CPU 本身不累，它只是忠实地执行你交给它的活。

## 🔧 翻车现场

### 翻车一：把"并发"和"并行"当成一回事 <span class="csf-b csf-key">重点</span>

这是最经典、也最影响判断的混淆。两个词只差一个字，意思却不一样：

- **并发（concurrent）**：很多任务**都在推进中**，但靠的是一个核**飞快地轮流切**——任何一个瞬间其实只有一个在真跑。像一个厨师同时"照看"煎蛋、煮汤、烤面包：他在三口锅之间来回跑，不是真的长出三只手。
- **并行（parallel）**：很多任务**真的在同一瞬间一起跑**——靠的是**多个核**，一个核一个任务。像三个厨师各守一口锅，真的同时在做。

<div class="csf-note">一句话记牢：<strong>并发是"看起来同时"（一个核轮流切），并行是"真的同时"（多个核一起上）</strong>。单核也能并发，但单核做不到并行。</div>

为什么这事关你的判断？以后你会听到"用多线程加速"。如果你的任务是纯计算、又只有单核，那多开线程也快不了——因为它们还是在抢同一个核轮流跑，并没有真正并行。搞混这俩，你就会对"为什么加了线程还是不快"百思不得其解。

### 翻车二：以为单核也能"真正同时"跑两个程序 <span class="csf-b csf-core">必读</span>

很多人第一反应是："我电脑明明同时开着十几个程序啊，怎么会是假的？"

真相是：**单核 CPU 任一瞬间只在执行一条指令**。它给 A 程序跑几毫秒，"啪"切到 B 跑几毫秒，再切到 C……切换快到每秒成百上千次，你的眼睛根本分辨不出来，于是大脑认定"它们在一起动"。就像电影是一帧一帧的静止画面，放得快了你就看成了连续的动作。

所以"同时"是真的体验，但"同一瞬间一起跑"是错觉。**真正的同一瞬间一起跑，必须有多个核。**

### 翻车三：看到总 CPU 没满，就以为"还有富余、不会卡" <span class="csf-b csf-skim">可跳读</span>

前面动手时你已经见过了：一个死循环把某个核顶到 100%，但总占用才 12%。如果你只盯着总占用，会误判"资源充足"。**单线程的程序卡住时，瓶颈往往是某一个核满了，而不是总量满了。** 诊断卡顿，记得把图切到"按核显示"再看。

## 🚀 挑战

<div class="csf-note">这个挑战要你<strong>亲手做实验、亲眼下结论</strong>，别问 AI 要答案——它给的数字不一定对得上你这台机器。</div>

1. 先用前面的方法**查清楚你的电脑到底有几个核**（任务管理器/活动监视器里一般写着"内核"或"逻辑处理器"数）。注意：这里写的"内核"指的是 CPU 的物理核心数，别和操作系统的"内核（kernel）"搞混——它俩名字一样、意思完全是两码事，这里说的就是 CPU 有几个核。
2. **故意开到比核数多**：比如你是 8 核，就同时开 **10～12 个** `busy.py`。
3. 观察并记录：
   - 总 CPU 占用最高冲到了多少？是不是接近 100%？
   - 这时候你**动一动鼠标、切换一下窗口**，电脑是变卡了，还是依然顺滑？为什么？
4. 用一两句话写下你的结论：当"想跑的活"超过"核的数量"时，操作系统是怎么处理的，体验上有什么变化。

<details class="csf-fold"><summary>想再深一点：时间片、上下文切换和调度器到底是什么<span class="csf-b csf-skim">细究 · 可跳读</span></summary>
前面讲的"轮流切",背后其实有三个一直在干活的角色，知道了能帮你把整件事串起来。<br><br><strong>时间片（time slice）</strong>：操作系统不会让一个程序一直霸占 CPU，而是给它一小段使用时间（通常是几毫秒到几十毫秒）。时间一到，不管它干没干完，都得让出来排队。这保证了没有谁能把别人饿死——这也是为什么哪怕有个程序在死循环，你还能挪得动鼠标。<br><br><strong>上下文切换（context switch）</strong>：换人不是免费的。CPU 从 A 切到 B 时，得先把 A 干到一半的"现场"（寄存器里的值、执行到哪一行等等，上一讲提过这叫上下文）保存起来，再把 B 上次的现场恢复回来。这一存一取要花时间，纯属"管理开销"，并没有帮你多算一道题。所以切换太频繁反而会拖慢整体——这就是上下文切换的代价。<br><br><strong>调度器（scheduler）</strong>：是操作系统里专门决定"下一个 CPU 时间片轮到谁"的那段程序。它要权衡：让你正在交互的程序优先（你才不觉得卡）、别让某个程序一直排不上队、又别切得太勤白白浪费。它是这场"轮流游戏"的裁判。<br><br>把这三者连起来：<strong>调度器</strong>按一定规则，给每个就绪的程序发<strong>时间片</strong>，时间片用完就做一次<strong>上下文切换</strong>换下一个。几十上百个程序就这样在有限的几个核上轮着跑——这就是"一个 CPU 同时做几十件事"的全部秘密。
</details>

## 📦 复制带走

<div class="csf-card"><strong>这一讲，揣四件事走：</strong><br>1. <strong>"同时"很多是装的</strong>：一个 CPU 核同一瞬间只跑一件事，它靠飞快地轮流切换（分时复用 + 时间片）骗过你的感觉。<br>2. <strong>并发 ≠ 并行</strong>：并发是"看起来同时"（一个核轮流切），并行是"真的同时"（靠多个核）；单核能并发，但做不到并行。<br>3. <strong>核数决定真正的并行上限</strong>：8 核最多 8 件事真正同时跑；活儿超过核数，就只能轮流摊薄。<br>4. <strong>诊断卡顿要看单核</strong>：总 CPU 没满不等于不卡——单线程程序常常是某一个核已经 100% 了。</div>
