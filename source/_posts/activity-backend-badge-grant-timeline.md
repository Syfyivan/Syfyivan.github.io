这篇文章只讲自动徽章发放。

它看起来只是“给一批用户调用发徽章接口”，但真正上线需要同时处理自动达标、运营批量导入、活动级幂等、全局权益状态、有效期、部分失败、账号不存在、超时误报和后续复用。

我在这个项目中覆盖了后台配置、批量工具、领域接口、定时任务接入、联调和自测。面试的重点不是复述先后顺序，而是说明：为什么批处理不是一个 for 循环，以及我怎样把两种入口收敛成可靠的权益能力。

<!-- more -->

## 一、十五秒怎么介绍

> 我负责把积分达标自动发徽章和运营批量导入名单发徽章统一成一套领域能力。系统按徽章和有效期分组、分批调用下游，使用活动维度幂等避免定时任务重跑重复发放，同时处理已有徽章的有效期和逐用户失败结果。第一场活动验证后，这套能力继续被其他活动复用。

## 二、默认两到三分钟主回答

> 这个项目有两个入口：一条是离线任务筛选积分达标用户自动发徽章，另一条是运营上传名单批量发放。我的核心设计是让入口只负责找用户，所有分组、幂等、有效期和失败处理都进入统一领域接口，避免两条链各复制一套规则。
>
> 自动任务会重复执行，所以先使用活动、用户和徽章组成的业务键做预过滤，领域层再做最终判重；批量名单则由领域服务统一解析和逐行校验，一行错误不会阻断整份文件。进入发放主流程以后，用户按照徽章 ID、展示名和有效期分组，调用侧和领域侧做两级拆批，控制 RPC 包大小和下游批量上限。
>
> 下游返回的不是整批成功或失败，而是新增成功、已经存在和发放失败三类用户。我按用户返回状态；如果徽章已经存在，就查询旧到期时间，只在本次目标更晚时延长，避免定时任务重试把有效期不断累加。整批 RPC 失败时再降级到单用户调用，缩小失败范围；失败用户还会补查账号是否存在，让运营能够根据行号和原因修正名单。
>
> 这套能力首次验证后继续被其他活动复用。它最能体现的不是我会调用权益接口，而是我把批处理中的分组、幂等、部分成功、超时不确定性和运营恢复路径组织成了一套统一能力。

## 三、面试官真正会听什么

| 面试官的判断 | 你要给出的证据 |
| --- | --- |
| 是否理解批处理 | 两级拆批、用户级结果、失败不阻断整批 |
| 是否理解幂等 | 活动维度判重、下游已有权益、超时后的安全重试 |
| 是否有领域设计 | 自动和名单入口共用一套发放规则 |
| 是否考虑运营体验 | 行号、失败原因、账号不存在和可重新上传 |
| 是否做过真实维护 | 有效期膨胀、批量超时和共享表格兼容 |

## 四、为什么难点不在“调用一个 RPC”

如果只看成功路径：

```text
user_ids -> AddBadge -> success
```

真实问题包括：

- 定时任务每天跑，达标用户会被反复扫到；
- 用户可能已经从别的活动获得同一徽章；
- 重复调用是返回 duplicate，还是续期；
- 续期从现在算还是从旧到期时间算；
- 一批五十人里只有三个人失败怎么办；
- 整批 RPC 超时，实际下游可能已经成功；
- Excel 一行错误是否阻断所有用户；
- 同一文件里用户重复且配置冲突怎么办；
- 用户 ID 不存在时如何返回可理解的错误；
- 活动幂等标记写失败但下游已经成功怎么办。

## 五、你只需要记住的六个工程转折

### 转折一：先把自动和名单发放统一到领域层

第一版同时建立：

```text
积分达标 -> 定时任务 -> 发徽章

运营表格 -> 后台工具 -> 文件解析 -> 发徽章
```

这时已经意识到两条入口不能各写一套下游调用，所以抽出统一领域接口。

为了控制请求体和下游限制，第一版很快补了分批逻辑。

### 转折二：从整批返回收敛到用户级结果语义

这一阶段提交非常密集，说明真正困难的是“下游返回以后怎样解释”。

依次处理了：

- 每个用户的成功、已存在和失败状态；
- 一批部分成功时不能把整批当失败；
- 返回失败行及原始行号；
- 活动幂等键结构；
- 已有徽章的续期逻辑；
- 下游成功以后再写幂等标记；
- 取消不必要的逐用户预查询；
- 对失败用户补查账号是否存在；
- 减少 RPC 次数和冗余字段。

这个时间段最适合面试时回答“第一版哪里不完整”：不是核心接口完全不能用，而是批量场景的状态解释、续期和失败定位需要逐步收口。

### 转折三：统一奖励配置，并把查重变成可选优化

自动发放的阈值奖励配置被统一到同一个规则结构，避免后台、离线任务和领域服务各自理解不同字段。

定时任务增加批量预查重：已经有活动发放标记的用户，在进入领域 RPC 前过滤，减少无效调用。

但预查重只是优化。如果 KV 查询失败，任务仍会把用户交给领域层，因为最终幂等不能依赖这一步。

### 转折四：把页面、协议、领域、任务和验收串成完整交付

按照原始排期：

| 工作 | 估算 |
| --- | --- |
| 后台奖励配置 | 1 人日 |
| 批量工具页面 | 1 人日 |
| 批量服务端 | 2 人日 |
| 自动发放服务端 | 1 人日 |
| 通用领域接口 | 1 人日 |
| 联调 | 1 人日 |
| 自测 | 1 人日 |

合计约八人日。这里能说明我的所有权不只是一段后端函数，而是完整交付链路。

### 转折五：把成熟能力迁入 workflow / repository 架构

后续多仓重构时，徽章模块又经历：

```text
repository / workflow 抽离
  -> 模块装配
  -> v1/v2 路由
  -> 单元测试
  -> 隔离测试环境路径验证
```

过程中还修正过新旧模块状态枚举映射错误，说明重构验证不能只看能否编译。

这部分属于重构文章的主线，在这里作为能力后续演进说明。

### 转折六：针对重复执行和超时不确定性继续加固

上线复用以后，又发现两类真实风险：

1. 批量重复执行可能让有效期不断叠加；
2. 定时任务批量太大或超时设置不合理，会把“下游可能已执行”误报成失败。

后续修正了有效期目标计算，并调整定时任务的拆批、超时、重试和日志。还补充了共享表格入口与失败行测试。

这段后续维护很值得讲，因为它说明我不是只完成首次开发，也继续处理真实运行语义。

## 六、整体架构

```text
自动路径
  离线任务筛选达标用户
  -> 批量预查活动幂等标记
  -> 按大批调用领域服务

批量路径
  运营上传或选择表格
  -> BFF 转发文件地址和操作人
  -> 领域服务解析、校验、构造用户项

统一领域路径
  参数校验
  -> 按徽章配置分组
  -> 活动维度幂等检查
  -> 按下游上限拆小批
  -> 调用账号权益服务
  -> 处理成功 / 已存在 / 失败
  -> 写活动发放标记
  -> 返回逐用户结果
```

## 七、为什么统一领域接口是关键

如果自动任务直接调用下游，批量工具也直接调用下游，就会复制：

- 用户参数校验；
- 下游请求组装；
- 已有徽章处理；
- 有效期规则；
- 失败状态映射；
- 活动幂等记录；
- 日志和重试。

入口层只决定用户从哪里来，业务规则必须由领域层统一。

## 八、实际分组键

早期方案常写：

```text
(badge_id, valid_days)
```

最终代码实际使用：

```text
(badge_id, title_text, valid_days)
```

展示标题也会进入下游请求。如果同一 badge_id 配了不同 title_text，合并后无法决定使用哪个标题。

这是一个很好的“文档和代码不一致”案例：面试回答必须以最终实现为准，同时解释为什么多出一个字段。

## 九、两级拆批

自动任务可能收集大量达标用户，真实链路有两层：

```text
任务层：数百用户一批调用领域 RPC
领域层：数十用户一批调用下游权益 RPC
```

第一层控制：

- 单次领域 RPC 请求体；
- 任务执行时间；
- 批次进度和失败定位。

第二层适配：

- 下游接口最大用户数；
- 下游超时；
- 部分失败返回；
- 整批失败后的逐用户降级。

为什么不直接所有用户一次发？一次请求失败会失去全部进度，超时也更难判断实际执行到哪里。

## 十、自动任务的预查重

离线任务先批量读取：

```text
grant:{activity}:{user}:{badge}
```

已存在的用户不进入领域 RPC。

### 预查重失败怎么办

真实实现选择继续发送原用户列表，并记录 warning。

原因：

- 预查重只优化 RPC 数量；
- 领域层仍会做活动幂等检查；
- 下游已有权益也能返回已存在；
- 因为一次缓存故障直接不发徽章，会造成权益遗漏。

这是一种有后续防线的 fail-open。

## 十一、活动维度幂等

自动发放的幂等键：

```text
(activity_id, user_id, badge_id)
```

它表达：某用户是否已经因为这个活动获得过这枚徽章。

为什么不能只用 `(user_id, badge_id)`？同一个徽章可能被多个活动复用，不能让活动 A 阻止活动 B 的合法授予。

为什么批量工具可以使用特殊 activity_id？批量工具不是某个达标活动，可以使用独立渠道语义；但仍要区分它和自动任务，避免错误复用活动幂等规则。

## 十二、全局权益状态

活动幂等通过以后，用户仍可能已经拥有同一徽章。

下游批量接口返回：

```text
success_user_ids
exist_user_ids
fail_user_ids
```

领域服务先把整批标记为成功，再用 exist 和 fail 列表覆盖逐用户状态。

对于 exist 用户，继续查询现有到期时间，决定：

- 旧到期时间已经更晚：duplicate；
- 本次目标到期时间更晚：修改到本次目标。

## 十三、有效期为什么很容易写错

本次目标：

```text
candidate_end = now + valid_days
```

最终语义：

```text
new_end = max(old_end, candidate_end)
```

它只延长，不缩短，也不会在重复执行时不断累加。

### 错误方案一：old_end += valid_days

定时任务每天扫到同一用户，就每天续一遍，导致有效期膨胀。

### 错误方案二：直接覆盖 candidate_end

用户原本还有半年，本次只配置 30 天，会把权益缩短。

### 为什么后来还会修

早期实现和设计文档可能对“续期”理解不同。上线复用以后，重复执行场景让语义问题暴露出来，于是明确为只取更晚目标，而不是从旧到期时间累计。

## 十四、下游部分成功

一批用户中：

```text
45 人成功
3 人已存在
2 人失败
```

不能把整个 RPC 当成功，也不能把整批当失败。

领域结果按用户返回：

```text
user_id
status: SUCCESS / DUPLICATE / FAILED
fail_reason
```

调用方只重试 FAILED，不重试 SUCCESS 和 DUPLICATE。

## 十五、整批 RPC 失败为什么降级单用户

如果批量调用整体报错，可能是：

- 某个用户参数导致整批拒绝；
- 下游批量接口暂时异常；
- 网络错误；
- 超时但实际已执行。

代码会把该小批拆成单用户请求，缩小失败范围。

注意：超时场景重试仍必须依赖下游幂等或“已有徽章”查询，否则可能重复续期。这也是为什么不能使用累加型有效期。

## 十六、文件批量入口

文件必须包含：

```text
user_id
badge_id
title_text
valid_days
```

领域服务逐行：

1. 跳过空行；
2. 校验必填字段；
3. 解析正整数用户 ID；
4. 校验有效期范围；
5. 记录 Excel 原始行号；
6. 构造统一 badgeUser；
7. 调用同一领域主流程；
8. 把失败用户映射回原行。

为什么由领域服务解析，而不是 BFF？因为它是规则唯一事实源。BFF 只做文件入口和协议转发。

## 十七、一行错为什么不能整批失败

运营可能上传一万行，其中一行 user_id 写错。如果整份失败，运营要重新清洗和上传，系统也无法告诉他具体问题。

响应保留：

```text
line_num
user_id_raw
badge_id
title_text
valid_days_raw
reason
```

正确行继续发放，错误行可以单独修正。

## 十八、用户不存在怎么判断

下游“发放失败”不一定明确说明账号不存在。

真实实现只对失败用户再批量查询账号：

- 查不到：失败原因改成“用户不存在”；
- 能查到：保留下游失败原因。

为什么不在发放前查所有用户？会给每次批量增加一次大范围账号 RPC，而大多数用户本来合法。失败后补查更经济。

## 十九、同一文件的重复用户

需要区分：

- 完全相同的重复行：可以去重；
- 同用户不同徽章：必须分别处理；
- 同用户同徽章不同有效期：属于冲突配置，应明确规则；
- 同用户同徽章不同展示名：不能无声覆盖。

真实代码为了映射失败行，会保存用户对应的首行信息。更完整的批量平台可以把每一行作为独立 item_id，完整返回行级结果。

## 二十、下游成功但幂等标记写失败

失败链：

```text
下游徽章发放成功
  -> 写活动 KV 失败
  -> 定时任务下次再次扫到
```

第二次调用下游会看到权益已存在，并通过有效期规则避免实体重复。但会多一次 RPC，且活动侧审计不完整。

更强方案：

```text
DB grant_record
pending -> granting -> completed / failed
KV 只作为快速过滤
```

是否引入 DB 状态机取决于权益价值、规模和审计要求。原项目使用 KV 与下游状态组合，面试时要如实说明。

## 二十一、定时任务超时为什么可能是“假失败”

RPC 超时只说明调用方没有按时拿到响应，不证明下游没有执行。

因此后续修正包括：

- 控制每批用户数；
- 设置与下游耗时匹配的超时；
- 限制自动重试次数；
- 记录批次号、用户样本和状态计数；
- 再次执行依赖领域幂等和下游已有权益状态。

不能看到 timeout 就盲目重发所有用户。

## 二十二、共享表格入口的后续兼容

运营不一定上传本地 Excel，也可能提供在线表格链接。

后续能力需要处理：

- 链接指向文件还是表格；
- 一个文档含多个工作表时必须明确 sheet；
- 权限不足如何提示；
- 表头和本地文件保持同一规则；
- 链接歧义时 fail-closed，不能猜错工作表后直接发权益。

## 二十三、日志和观测

关键日志：

```text
activity_id
channel
badge_id
batch_no / batch_total
user_count
success / duplicate / failed count
failed user sample
downstream latency
prefilter skipped count
```

不要在高量日志里打印完整一万用户列表。保留数量和有限样本，失败结果通过结构化记录查询。

## 二十四、验证矩阵

### 自动路径

- 未达阈值不收集；
- 达阈值进入批次；
- 同一任务重跑不重复；
- 预查重失败仍进入领域层；
- 不同活动可发同一徽章。

### 批量路径

- 表头错误整份拒绝；
- 单行错误不影响其他行；
- 用户不存在有明确原因；
- 重复行规则确定；
- 多种徽章和有效期正确分组。

### 有效期

- 用户无徽章：新增；
- 旧到期更早：延长到 candidate；
- 旧到期更晚：不缩短；
- 重复任务：不持续膨胀。

### 部分失败

- 下游返回 fail 和 exist 列表；
- 整批失败降级单用户；
- 超时后重试不产生重复副作用。

## 二十五、业务结果与因果边界

第一场活动中，徽章入口达到数十万量级用户，资源位表现和报名转化较好；通用发放能力随后被其他活动复用。

正确表达：

> 我完成的自动与批量发放能力，保证达标用户能够稳定收到权益，并降低运营名单发放和后续活动接入成本。最终入口流量和转化由资源位、权益吸引力、内容和运营共同决定。

## 二十六、备用的完整口述版

> 我负责过一套积分达标自动发徽章能力，同时给运营提供批量名单工具。这个需求最初看起来只是调用账号侧接口，但真正难的是定时任务会重复执行、用户可能已经拥有同一徽章、一批用户可能部分成功，以及有效期不能因为重试不断累加。
>
> 我把自动任务和批量文件作为两个入口，统一进入领域发放接口。入口只负责筛选用户或解析文件，领域层按徽章 ID、展示名和有效期分组，再按下游限制拆批。自动任务先做活动幂等预过滤，但预过滤失败仍交给领域层，因为最终幂等不能依赖缓存优化。
>
> 下游返回新增成功、已存在和失败用户列表，我按用户返回结果。已有徽章会查询到期时间，只在本次目标更晚时延长，避免重复任务把有效期不断叠加。整批 RPC 失败时会降级成单用户调用；文件里一行错误不会阻断整批，而是返回行号和原因。失败用户还会补查账号是否存在。
>
> 这个项目从 2 月第一版到 3 月联调完成，之后又继续修正有效期膨胀、定时任务超时误报和共享表格兼容。它让我真正理解了批处理不是 for 循环，而是分组、幂等、部分结果、重试和运营可恢复性的一整套设计。

## 二十七、高频追问

### 为什么预过滤失败选择 fail-open

因为后面还有领域幂等和下游已有权益状态；直接放弃会漏发。它是性能优化，不是唯一正确性防线。

### 为什么压测标记丢失却要 fail-closed

因为那种场景继续执行可能污染真实数据，没有安全后盾。fail-open/closed 取决于失败后的业务风险。

### 一万用户如何避免接口超时

任务层大批、领域层小批；批次有编号和进度；控制并发与超时；失败批次可恢复，不用一个同步请求承载全部完成。

### 为什么 duplicate 不是 error

它是幂等重放或已有权益的正常业务状态，不应该触发无限重试和告警。

### 有效期为什么不从旧 end_time 再加 N 天

重复执行会不断膨胀。当前语义是保证权益至少持续到本次 candidate_end。

### 批量工具为什么不直接把逻辑放 BFF

领域规则会与自动任务重复，而且其他调用方无法复用。BFF 应保持入口和协议职责。

### 你怎么证明是自己完整负责

可以沿后台配置、批量页面、BFF 协议、领域接口、离线任务、联调和自测逐层说明，并用有效期、部分失败和超时修正证明自己持续负责。
