> 承上：上一章阿筹把各摊上下文划清了。这一章，老把头抛出一个更尖的问题：活儿干完了，凭什么说它对？

施工组拍胸脯:“我们干完了，保准没问题！”老把头不接茬,反问:“你自己说没问题，跟没说一样。”

他派了三拨人去对着干。“一拨**专门挑你的错**——你说装好了，他逐颗螺丝拧一遍。一拨**照图纸验收**——你交的活，对不对得上当初的要求。还有一拨最狠，**专门来拆台**——假装自己是想找茬的对头，使劲找你最薄弱的地方下手。”最后他定规矩:“一件要紧的活，得几拨人都点头、对得上，才算数；一拨说行不够。”

阿筹咋舌:“这么麻烦？”老把头:“越要紧的活，越要有人专门跟它对着干。自己夸自己，最不可信。”

## 概念揭晓

老把头派人“对着干”，是多 Agent 最有价值的用法之一:**对抗式验证（adversarial verification）**——用专门的 Agent 去质疑、检验另一个 Agent 的产出，而不是让它自说自话。

“专门挑错的”，是 **critic / reviewer（评审）**：一个 Agent 专门批评另一个的产出，找漏洞、提改进（呼应 11.2 的 critic 模式）。

“照图纸验收的”，是 **verifier（验证者）**：对照明确标准（第七讲的验收标准、第八讲的评测）判定产出合不合格。

“专门来拆台的”，是 **red team（红队）**：站在攻击者/找茬者的立场，主动去发现最薄弱处——尤其用在安全（第九讲）和健壮性上。

“几拨都点头才算数”，是 **consensus / 投票（共识）**：让多个独立 Agent 各自判断，多数一致才采信，单个声音不算数。

## 为什么自评不可信

第三讲讲过模型会一本正经地编、还常常过度自信（第二讲 02.5 的校准问题）。让产出它的 Agent 自己判断对错，等于让“可能在编的人”给自己背书——它倾向于说“我答得很好”。

这正是 LLM-as-judge 要警惕的偏差（第八讲 08.5）之一:模型容易被“我做得很完美”这类自我评价带偏。所以可靠性高的系统，把“产出”和“判定”交给**不同的、独立的** Agent，让判定方带着怀疑去挑刺，而不是替产出方圆场。

## 评审、验证、红队各管什么

- **评审（critic）**：开放式地找问题、提改进，适合打磨质量，常配合 11.2 的反思循环。
- **验证（verifier）**：对照硬标准判合格不合格，适合有明确验收标准的产出（代码能不能跑、格式对不对、事实对不对）。
- **红队（red team）**：主动攻击式地找最坏情况——能不能诱导它越界、能不能让它出安全事故（第九讲）。

三者层次不同:评审提质量，验证保底线，红队防灾难。要紧的系统三样都要有。

## 共识：多数对冲单点错误

单个 Agent（哪怕是验证者）也会错。共识机制用“多个独立判断 + 多数一致”来对冲:

- 让若干独立 Agent（或同一 Agent 多次独立运行）各自判断，取多数。
- 关键决定要求“几方对得上”才放行（呼应老把头“几拨都点头”）。
- 独立性很重要:如果几个判断者共享同样的偏见或上下文，它们会一起错，投票就失效。

这把第八讲“多视角验证”落到了多 Agent:用独立性和数量，压低“一致地错”的概率。

## 验证者要独立、要对抗

对抗式验证能不能起效，关键在两点:

- **独立**:验证者要有自己的视角、上下文、甚至不同的提示词/模型，别和被验方同源（否则一起犯同样的错）。
- **对抗**:验证者的任务是“找出它哪里不对”，而不是“确认它对”——默认怀疑，举证有罪，而非无罪推定。

一个被明确要求“尽力反驳这个结论、宁可错杀”的验证者，比一个温和的“看看对不对”的检查者，能挡住多得多的错误。

看一个具体的“一来一回”：产出方写了份报告，断言“某公司 2024 营收同比增长 20%”。一个独立的 verifier 被要求“别信它，自己去原始财报核对”，它翻到年报发现实际是 12%，于是打回：“营收增速对不上，年报第 X 页是 12%，请改并附出处。”产出方据此改成 12% 并补上引用，verifier 再核一遍才放行。关键在于这个 12% 不是产出方“自己再想想”想出来的——是一个**不同上下文、被要求挑刺**的 Agent 独立查出来的；要是让产出方自评，它多半会说“我引用的数据没问题”，因为它看的还是那份错资料。这就是“独立 + 对抗”为什么比“自评”能多挡一大截错误的原因。

## 常见误区

第一，让产出的 Agent 自己判断对错。它会替自己圆场。

第二，验证者和被验方同源、共享上下文，结果一起错。

第三，把验证者写成“确认它对”的姿态，而不是“尽力挑错”的对抗姿态。
