微服务不是把一个项目拆成很多项目。真正的微服务，是按业务能力拆出可以独立开发、独立部署、独立扩展的服务。拆分之后，最先遇到的不是“架构变高级了”，而是“本地函数调用变成了不可靠的网络调用”。

所以学习 RPC 与微服务，第一原则是：先解决失败，再谈扩展。

## 微服务改变了什么

单体里一次调用可能只是：

```go
user := userService.GetUser(id)
```

拆成微服务后，它变成：

```text
task-service
  -> user-service over network
```

这时会出现新问题：

- user-service 实例在哪里；
- 请求打到哪台机器；
- 下游是否健康；
- 调用超时怎么办；
- 是否可以重试；
- 重试会不会放大流量；
- 返回旧数据能不能接受；
- 下游挂了主流程是否降级。

这些就是服务治理。

## 必须掌握的知识点

### RPC 协议和 IDL

常见内部通信方式：

- HTTP JSON：简单、通用、调试方便；
- gRPC：基于 protobuf，性能好，IDL 明确，适合强类型内部服务；
- Thrift：跨语言、成熟，在一些公司内部体系常见；
- 自定义 RPC：通常依赖公司基础设施。

RPC 的核心不是“比 HTTP 快”，而是契约清晰。IDL 定义字段、类型、方法和兼容性规则。微服务之间最怕的是接口随意变化，下游悄悄崩掉。

兼容性基本原则：

- 新增字段要可选；
- 不要随意改字段含义；
- 不要复用已废弃字段编号；
- 删除字段要有灰度周期；
- 错误码要稳定。

### 服务发现与负载均衡

服务实例会扩缩容、重启、故障摘除。调用方不能写死 IP，需要服务发现。

基本流程：

```text
service instance -> registry
client -> registry -> instance list
client -> load balancer -> selected instance
```

负载均衡不仅是随机选一个实例，还要考虑：

- 健康检查；
- 权重；
- 同机房优先；
- 慢实例摘除；
- 连接池；
- 熔断状态。

### 超时

每个 RPC 都必须有超时。没有超时，下游慢会拖垮上游。

超时要按链路预算设计。比如用户请求总预算 800ms：

```text
入口处理 50ms
查用户 100ms
查任务 200ms
查缓存 50ms
聚合和响应 100ms
预留 300ms
```

不要每个下游都随手设 3 秒。链路越长，总延迟越容易失控。

### 重试

重试只适合可重试错误：

- 短暂网络错误；
- 连接重置；
- 下游临时 503；
- 幂等读请求。

不适合重试：

- 非幂等写请求；
- 参数错误；
- 权限错误；
- 明确业务失败；
- 已经接近总超时预算。

重试要有次数限制和退避。否则下游一慢，上游疯狂重试，会把局部故障放大成全站故障。

### 熔断、限流和降级

熔断：下游持续失败时，短时间内直接失败，避免继续打爆下游。

限流：控制入口或下游调用流量，保护系统容量。

降级：核心链路优先，非核心功能返回默认值或延后处理。

比如任务列表页，如果用户头像服务挂了，可以返回默认头像；但任务本身查不到，就不能假装成功。

### 服务拆分原则

不要按 controller 拆，也不要按表名拆。更好的拆分维度是业务能力和数据归属：

- user-service 管用户身份和资料；
- task-service 管任务生命周期；
- notification-service 管通知投递；
- billing-service 管账单和支付。

一个服务应该拥有自己的数据。跨服务直接查对方数据库，会让边界失效。

## 练习方式

把任务系统拆成三个服务：

- user-service：用户资料；
- task-service：任务创建、查询、状态流转；
- notification-service：异步通知。

要求：

- task-service 通过 RPC 查询用户；
- task-service 调 user-service 设置 100ms 超时；
- 对读请求设置有限重试；
- notification 通过 MQ 触发；
- 所有调用透传 trace id；
- user-service 故障时，任务主流程能明确失败或降级。
