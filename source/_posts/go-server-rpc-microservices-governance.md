微服务最容易被讲得很高级，但一落地，第一感受通常是：以前一个函数调用，现在变成了一次可能失败的网络请求。

所以我会先把微服务理解成“拆分以后如何处理失败”。扩展性、组织协作、独立部署都重要，但排在第一位的还是失败边界。

## 拆服务之前先问边界

不要按 controller 拆，也不要按表名拆。比较靠谱的拆法是按业务能力：

- user-service 管用户；
- task-service 管任务；
- notification-service 管通知；
- payment-service 管支付。

一个服务最好拥有自己的数据。跨服务直接查对方数据库，看起来省事，实际上边界很快就会烂掉。

## RPC 的重点是契约

gRPC、Thrift、HTTP JSON 都可以用。比协议名字更重要的是接口契约。

IDL 或接口文档要说清楚：

- 字段含义；
- 哪些字段可选；
- 错误码；
- 超时建议；
- 兼容规则。

接口一旦被别人依赖，就不要随便改字段含义。新增字段比修改字段安全，废弃字段也要留灰度期。

## 每个调用都要有超时

服务拆开后，链路会变长。一个入口请求可能要调三四个下游。每个下游都给 3 秒，最后用户可能等到天荒地老。

更实际的做法是先给整条链路一个预算。比如总共 800ms，那用户服务、任务服务、缓存、数据库各自能花多久，要心里有数。

超时不是随便填个数字，它是在分配用户能等待的时间。

## 重试会放大故障

读请求、短暂网络错误，可以有限重试。非幂等写请求就要非常小心。

下游已经慢了，上游再重试三次，流量可能瞬间翻倍。很多故障不是被第一次请求打崩的，是被重试打崩的。

重试至少要有：

- 最大次数；
- 退避；
- 总超时预算；
- 只对可重试错误生效；
- 写请求先确认幂等。

## 熔断、限流、降级别混着用

这几个词经常一起出现，但作用不同。

熔断是下游持续失败时，先别继续打它。

限流是保护自己或下游，别让流量超过承受能力。

降级是牺牲非核心体验，保住主链路。比如头像服务挂了可以给默认头像；订单查不到就不能假装成功。

## 一个练习

把任务系统拆成三个服务：

- user-service；
- task-service；
- notification-service。

要求：

- task-service 通过 RPC 查用户；
- RPC 调用带超时；
- 读请求最多重试一次；
- 通知通过 MQ 触发；
- trace id 贯穿 HTTP、RPC、MQ；
- user-service 挂掉时，task-service 的行为是明确的：失败、降级，或者返回部分结果，不要卡住。

拆完你会发现，微服务不是把代码切开那么简单。代码切开以后，治理能力也得一起补上。
