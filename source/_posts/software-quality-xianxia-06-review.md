## 一、故事正文

青萝接的这件委托快交付了。委托人要的是一面「传讯阵盘」，她照着卷宗一路炼下来，自觉用料扎实、阵纹工整，只想尽快封箱送出，换一份谢礼。

偏偏在山门口被执律师姐拦住。师姐管的就是「按流程把关、会审、监督」这一摊事。她说：「交付前要走一道**软件评审**。」青萝皱眉：「阵盘都炼好了，再开**会审**不是耽误工夫？我自己看过好几遍，没问题。」

执律师姐没动怒，只摊开青萝最早画的那份需求卷宗，又取来设计图，一行一行对：「委托人写的是『传讯三百里，可同时绑定五枚信符』，你的设计图上只留了**三枚**信符位。」青萝凑近一看，脸就白了——这不是阵纹画错，是**需求**到**设计**这一步就漏了，后面编码、刻纹全是顺着这个错往下走的。

师姐说：「你看，这个缺陷此刻挑出来，改设计图、补两枚信符位，半日的事。可你要是真封箱送了出去，委托人当场试阵发现信符不够，要退、要拆、要返工，还要赔信誉——同一个缺陷，**发现得越晚，纠正费用越高**。在需求阶段抓住是 1 倍力气，到了实际使用阶段，可能是它的几十倍、上百倍。」

青萝不服气：「那也只是这一处。」师姐摇头：「不止。**前一阶段的错误会导致后一阶段的工作结果中有相应的错误，而且错误会逐渐累积，越来越多**。你这阵盘的刻纹、调试，全是建在『漏了两枚信符位』这个错误设计上的——它不是一个点，是一条线。」

她当场叫来两位同门，凑成一个评审小组，把青萝的**需求说明、设计说明书、代码**摆上案，又取出一张早就备好的**缺陷检查表**：正确性、完整性、一致性、可追溯性……一项项核对。半个时辰后，案上多了三处问题：信符位漏了、传讯距离的描述前后不一致、还有一段刻纹没法对应到任何一条需求。

师姐提笔写下评审结论：「有条件接受——没有大缺陷，把这几处小缺陷修订后，可以通过。」青萝这才明白，**评审不是炼好之后多此一举的检查，而是把缺陷拦在交付之前、拦在它变贵之前的功夫**。她把阵盘抱回炼器房，半日就补好了那两枚信符位。

## 三、概念正解

### 3.1 为什么需要评审（三个角度）

课件从三个角度论证**软件评审**的必要性：

**从成本上衡量**：核心结论是「**缺陷发现得越晚，纠正费用越高**」。消除一个缺陷的相对成本随阶段急剧上升，课件给的倍数序列要背：

| 阶段 | 消除一个缺陷的相对成本 |
| --- | --- |
| 需求分析 | **1 倍** |
| 设计 | **3-6 倍** |
| 编码 | **10 倍** |
| 开发测试 / 系统测试 | **15-40 倍** |
| 实际使用（发布后） | **40-1000 倍** |

软件评审的重要目的，就是**尽早发现产品中的缺陷，减少大量的后期返工**。

**从技术上衡量**：**前一阶段的错误会导致后一阶段的工作结果中有相应的错误，而且错误会逐渐累积，越来越多**。错误的规格说明会带出错误的设计，错误的设计会带出错误的编码，最终成为不完善的软件产品。

**从效率上衡量**：评审让不同角色受益——开发工程师减少修订缺陷与测试调试的时间、提高编程效率；项目负责人缩短开发周期、减少维护费用、控制项目风险与质量问题；测试工程师可把更多精力放到测试用例设计上；维护人员维护工作减少、产品可维护性增强。

### 3.2 评审的内容（四类评审）

| 类型 | 定义 |
| --- | --- |
| **管理评审** | 由**最高管理者发起**，要求各部门对管理体系目前的状况进行评审，状况包括**适宜性、有效性、充分性**。对质量体系进行回顾和总结。 |
| **技术评审** | 对产品以及各个阶段的输出内容进行评估，目的是确保需求说明、设计说明书与最初的说明书**保持一致**，并按计划对软件进行了正确的开发。输出《技术评审报告》。 |
| **文档评审** | 评审需求、设计、代码、质量验证等文档。 |
| **过程评审** | 对软件开发过程的评审，通过对流程的监控，保证 **SQA 组织定义的软件过程在项目中得到遵守**，并保证质量方针更快更好地执行。 |

**评审对象（文档评审的范围）**：

- **需求评审**——《市场需求说明书》《产品需求说明书》《功能说明书》
- **设计评审**——《总体设计说明书》《详细设计说明书》
- **代码评审**——代码
- **质量验证评审**——《测试计划》《测试用例》

**文档评审检查列表**（要能列举）：正确性、完整性、一致性、可行性、有效性、可靠性、可追溯性、模块化、清晰性、易测性。

### 3.3 评审的方法（五种，按正式度排序）

课件给出五种评审方法，**从最不正式到最正式**排列：

**临时评审（Ad hoc review） → 轮查（Pass-round） → 走查（Walkthrough） → 小组评审（Group Review） → 审查（Inspection）**

其中**审查（Inspection）是最正式、最严格、最有效的评审方法**——这是本章最高频考点。审查、小组评审、走查的对比（记三个典型差异即可）：

| 对比项 | 审查 | 小组评审 | 走查 |
| --- | --- | --- | --- |
| 主持者 | 评审组长 | 评审组长或作者 | 作者 |
| 专门的评审角色 | 是 | 可能 | 否 |
| 检查表 | 是 | 是 | 否 |
| 准备 / 确认 | 有 | 有 | 无 |

**如何选择评审方法**：选择评审方法最有效的标准是——**对于最可能产生风险的工作成果，要采用最正式的评审方法**。例如核心代码失效后果严重，应采用**审查或小组评审**；一般代码则可采用临时评审、同桌评审等较随意的方法。

### 3.4 评审的技术

- **缺陷检查表**：列出容易出现的典型错误，是评审的一个重要组成部分。
- **规则集**：类似缺陷检查表，是业界通用规范或企业自定义规则的集合。
- **评审工具的使用**：如 NASA 开发的 **ARM（自动需求度量）**。
- **从不同角色理解**：不同角色对产品/文档的理解不一样。
- **场景**：按用户使用场景对产品/文档进行评审。

### 3.5 评审会议（准备 → 召开 → 结果）

**准备评审会议**：① 制定评审计划和评审时间（含评审检查点）；② 组建评审组（**选定评审组长非常重要**）；③ 准备评审材料；④ 发送审查包；⑤ 制定活动进程表。

**召开评审会议**：① 由评审员/作者进行演示或说明；② 评审员就疑惑处与作者沟通；③ 协调人或记录员完成会议记录（清楚简明、含缺陷分类）。注意事项：避免**人身攻击**、避免**无休止争论**、避免**偏离会议中心**、**鼓励所有人发言**。

**四种评审结果**（高频考点，要能区分）：

| 结果 | 含义 |
| --- | --- |
| **接受** | 评审内容不存在大的缺陷，可以通过。 |
| **有条件接受** | 不存在大的缺陷，**修订其中一些小缺陷后**可以通过。 |
| **不能接受** | 有较多缺陷，作者需修改并**重新评审**。 |
| **评审未完成** | 由于某种原因未能完成，还需后续会议。 |

评审结果还要**跟踪**（针对有条件接受、不能接受）与**分析**（有效性、效率和成本）。

### 3.6 如何实施成功的评审

- **主观因素**：对工程师进行评审培训使评审深入人心；预防个人冲突（避免有人身攻击倾向者加入）；将评审加入项目计划并分配足够资源；收集以前的评审数据了解哪种方法最有效；把评审列入个人时间表确保充分准备。
- **客观因素**：**异步评审**（共享文档、邮件评审）、**分布式评审**（视频会议）。

一句小结牢记：**评审过程越正式，评审的效率越高；审查是评审方法中最正式、最严格、最有效的。**

## 五、考点卡

- **判断题抓手**：「评审是软件炼好之后多此一举的检查」——错，评审目的是**尽早发现缺陷、减少后期返工**，越早越省。「走查是最正式的评审方法」——错，**审查（Inspection）** 才是最正式、最严格、最有效的。
- **选择题抓手**：看到「最高管理者发起、适宜性/有效性/充分性」→管理评审；看到「确保各阶段输出与最初说明书一致」→技术评审；看到「保证 SQA 定义的软件过程被遵守」→过程评审；看到「最正式/最严格/最有效」→审查；看到「ARM / 自动需求度量」→评审工具。
- **填空题抓手**：缺陷成本序列 **1 → 3-6 → 10 → 15-40 → 40-1000** 倍；五种方法按正式度：临时评审、轮查、走查、小组评审、**审查**；四种结果：接受、有条件接受、不能接受、评审未完成。
- **简答题答题骨架**：① 为什么评审（成本/技术/效率三角度）；② 四类评审定义；③ 五种方法及审查最正式；④ 四种评审结果。
- **设计题答题骨架**：给定一个交付物 → ① 判断风险高低，按「最可能产生风险用最正式方法」选评审方法；② 确定评审对象（需求/设计/代码/测试计划）；③ 准备缺陷检查表/规则集；④ 走准备-召开-记录会议流程；⑤ 给出四种结果之一并跟踪分析。

## 六、小试炼

**题 1（判断）**：缺陷在需求阶段发现和在发布后发现，纠正成本基本相同。
参考答案：错。为什么——课件明确「缺陷发现得越晚纠正费用越高」，需求阶段约 1 倍，发布后实际使用阶段可达 40-1000 倍。

**题 2（选择）**：五种评审方法中，最正式、最严格、最有效的是（ ）。
A. 临时评审　B. 走查　C. 小组评审　D. 审查
参考答案：D。为什么——课件小结直接点明审查（Inspection）是最正式、最严格、最有效的评审方法。

**题 3（填空）**：评审的四种结果是接受、______、不能接受、评审未完成。
参考答案：有条件接受。为什么——「不存在大缺陷，修订其中一些小缺陷后可以通过」即有条件接受，与「接受」「不能接受」区别在于是否需要修订小缺陷或重新评审。

**题 4（简答）**：简述选择评审方法的标准，并举例。
参考答案：选择评审方法最有效的标准是——对于最可能产生风险的工作成果，要采用最正式的评审方法。例如核心代码失效后果严重，应采用审查或小组评审；一般代码可采用临时评审、同桌评审等较随意的方法。

**题 5（设计）**：某团队要交付一个支付核心模块，请设计其评审方案。
参考答案要点：① 支付核心风险极高 → 采用最正式的**审查（Inspection）**；② 评审对象覆盖需求评审、设计评审、代码评审、质量验证评审（测试计划/用例）；③ 准备缺陷检查表与规则集，必要时用工具（如 ARM）；④ 走准备（组评审组、选评审组长、发审查包）—召开（演示、沟通、记录并分类缺陷）流程；⑤ 给出评审结果（接受/有条件接受/不能接受/未完成）并对有条件接受、不能接受的结果进行跟踪，分析有效性与成本。

## 七、易错点

- 把**四类评审**（管理/技术/文档/过程）和**五种方法**（临时/轮查/走查/小组/审查）混为一谈：前者是「评审什么内容」，后者是「用多正式的方式评审」，两个维度别串。
- 把**走查（Walkthrough）** 当成最正式的方法：最正式、最严格、最有效的是**审查（Inspection）**，走查由作者主持、无检查表、无准备无确认，反而较随意。
- 记不准**缺陷成本序列**：务必背 1 → 3-6 → 10 → 15-40 → 40-1000 倍，别只记「越来越贵」。
- 混淆**有条件接受**与**不能接受**：有条件接受是「小缺陷，修订后通过」；不能接受是「缺陷较多，改完要重新评审」。
- 只背故事不背术语：答题要落到「软件评审、缺陷成本、审查、四种评审结果、缺陷检查表」等课件原词。
