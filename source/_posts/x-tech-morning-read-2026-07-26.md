## AI 观察

### 1. “远程操作 Agent”首先是状态同步问题，不是再做一个聊天窗口

今天 Codex 群里的问题很具体：任务在电脑上跑，人已经离开桌面，收到消息后想用手机调整。群内有人提到原生远控、截图和设置里的“远程”入口。这只能说明真实使用需求正在出现，不能证明某个入口、套餐或网络条件已经对所有人开放。

但它揭示了 Agent 产品的下一道门槛：用户需要在另一个设备上知道任务到底处于什么状态，并能安全地接管。手机端不一定要复制完整终端，它至少要能显示任务 ID、当前阶段、最近一次工具调用、等待什么输入、哪些动作需要批准，以及最新一份验证证据。没有这些信息，所谓远程控制只是把“看不见的黑箱”搬到了另一块屏幕。

### 2. 语音、移动端和连接器把“理解”推进到了“代办”，权限回执必须跟上

Anthropic 7 月 23 日的公告显示，Voice Mode 已能使用 Opus、Sonnet 和 Haiku，并可触达已连接的 Gmail、Slack 等工具；用户可以在移动端、桌面端和 Web 使用，调用连接工具前 Claude 会请求许可。[公告](https://claude.com/blog/think-through-hard-problems-in-voice-mode) 的重点不只是语音质量，而是从讨论问题到执行动作的连续链路。

OpenAI 的发布说明也把 Chat、Work 和 Codex 放进同一桌面应用，并提到 Codex 的差异编辑、PR review、多仓库项目和更快的 computer use；Work 则可以在 Web 和移动端处理较长任务、连接应用和文件，并支持计划任务。[发布说明](https://help.openai.com/en/articles/6825453-chatgpt-release-notes) 这些能力共同指向一个变化：Agent 不再只交付一段文本，而是在跨入口、跨工具、跨时间地推进一件事。

因此，产品设计要把“允许它做什么”和“它刚刚做了什么”放在同一个确认回路里。一次授权应有范围、对象、有效期和撤销动作；一次执行应有输入、工具、结果和失败原因。否则用户会把“我听见它说完成了”误认为“系统已经完成并验证”。

### 3. Agent 的完成态必须允许“不确定”和“待接管”

OpenAI 状态页记录过一次 Codex Review 的错误升高事件，页面显示已恢复，但也提醒可用性指标是按聚合层级统计的，个体账户、套餐、模型和功能的体验可能不同。[状态页](https://status.openai.com/incidents/qw645fke) 对使用者的启发是：Agent 任务不能只用一个布尔值表示成功或失败。平台健康、任务执行、工具回执和业务验证是不同层次。

一个更诚实的状态集合应至少包含：`running`、`waiting_for_input`、`waiting_for_approval`、`tool_failed`、`succeeded_but_unverified`、`verified` 和 `handover_required`。其中 `succeeded_but_unverified` 很重要：命令返回成功，不代表页面、接口、构建产物或线上行为符合目标。

## 前端 / 服务端 / 客户端工程观察

### 前端：把 Agent 的“观察窗”做成结构化任务卡

手机或 Web 端不需要一开始就复刻终端，但要把不可缺的上下文结构化出来：仓库或工作区、任务目标、发起人、资源 owner、当前阶段、权限范围、最近动作、验证摘要、阻塞原因和最后更新时间。

交互上要区分三种动作：继续等待、补充信息、接管执行。审批按钮旁边要明确副作用，例如“写入分支”“创建 PR”“发布到环境”，而不是只显示“允许 Agent 继续”。对于断网和通知延迟，客户端应能在重新打开时从服务端重放任务状态，不能把一条过期的 toast 当成事实。

### 服务端：把远程接管建模为同一条 Agent Run 的新观察者

服务端不要为手机端再创建一条孤立会话。桌面终端、Web、手机和 CLI 应共享 `agent_run_id`，并由服务端维护事件序列：人发起了什么、Agent 调了什么工具、工具返回了什么、策略是否放行、验证跑到了哪一步、谁批准了不可逆动作。

每次接管都需要有并发控制和幂等语义。手机发出的“继续”不能和桌面发出的“重试”同时推进同一个副作用；过期的审批不能在网络恢复后自动生效；任务已经进入终态后，客户端重放消息也不能重复执行。对于长任务，心跳、租约、断线恢复和事件回放比聊天记录更重要。

另外，外部 Issue、PR、网页、文档和依赖包都应视为不可信输入。IssueTrojanBench 的预印本在受控实验中评估了 Cursor、Claude Code 和 Codex Desktop，报告称 66.5% 的恶意 Issue 能穿透其测试中的 Agent 与模型防线，并指出供应链类攻击尤其突出。[论文](https://arxiv.org/abs/2607.20759) 这是安全研究结果，不是生产事故率；但它足以说明：服务端不能把“来自项目里的文字”自动升级为高优先级指令。

### 客户端：多端不是多份 UI，而是同一责任链的不同观察窗

客户端之间要同步任务 ID、权限、审批状态、验证证据和接管人。用户在手机上看到“等待批准”，回到电脑后应看到同一个状态；用户在手机上撤销权限，桌面端正在等待的动作也应立即失效。

可以借鉴公开工程项目 Agent of Empires 的几个拆分方向：浏览器访问、移动优先的 Agent 状态展示、多仓库工作区、工作/等待/空闲状态识别，以及依靠 tmux 保持会话。[项目页](https://www.agent-of-empires.com/) 这些能力并不等于生产级安全方案，却说明远程 Agent 的体验核心是“会话持久化 + 状态可见 + 低风险接管”，而非简单地把终端画面缩小。

## 值得跟进的动作

1. 给每个 Agent 任务补齐责任链：发起人、授权人、资源 owner、最终接管人；缺一项就进入待确认状态。
2. 统一桌面、Web、手机和 CLI 的 `agent_run_id`，把工具调用、测试、扫描、截图、接口回执和部署结果挂到同一条证据链上。
3. 将任务状态拆为执行、等待输入、等待审批、工具失败、未验证成功和已验证成功，禁止用“请求已接受”冒充“业务已完成”。
4. 为跨端接管补上租约、幂等键、事件回放、审批过期和撤销权限测试，重点测断网、重复点击、设备切换和两个客户端同时操作。
5. 前端任务卡片明确显示副作用与验证结果；推送通知附带任务链接和最后证据，不只发送“已完成”。
6. 为 Issue、PR、文档、网页和依赖包输入增加不可信标记与对抗性回归，验证 Agent 会不会把外部内容当成高优先级系统指令。
7. 继续观察 X 的当天公开讨论，但在能定位到具体账号、具体帖子和原始上下文前，不把热榜摘要、转述或趋势页写成技术事实。
