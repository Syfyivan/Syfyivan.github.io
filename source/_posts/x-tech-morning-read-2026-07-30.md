## AI 观察

### 1. 记忆开始从“上下文技巧”变成 agent 的本地基础设施

今天的《Codex 攻略日报》把 [OptMem](https://github.com/VictorTaelin/OptMem) 作为“每日一个 Skill”。公开仓库能核对到它的定位：用一个 426-token prompt 和无依赖脚本，把长期记忆追加到本地日志，再通过可重建的摘要树控制每次唤醒的阅读预算；仓库页面当前显示 867 stars、51 forks。

这类工具的价值不在于“让模型记住一切”，而在于把记忆变成可检查的工程资产：哪些决策被记录、原文能否找回、摘要能否重建、坏记忆能否删除。对长项目和跨天自动化尤其如此。记忆一旦进入 agent 的输入链路，就应像配置和依赖一样有来源、版本和失效策略，而不能只靠模型在压缩后自行回忆。

### 2. 速度和地域正在成为同一个运行时选择

日报提到 Vercel AI Gateway 的区域推理能力；Vercel 的公开页面显示，7 月 29 日又增加了统一 fast mode：请求可以选择更快的 serving path，必要时回退到标准速度，并按请求记录速度相关计费。此前的区域推理还允许把请求固定到美国或欧盟，并返回实际服务地域。

这意味着模型调用配置不应只有 `model` 一个字段。至少还应显式记录 `region`、`speed`、fallback、数据保留策略和预算。交互式客户端可以优先低延迟，后台任务可以优先成本；敏感数据则必须在地域和 provider 约束不满足时失败，而不是静默漂移到另一个区域。

### 3. 供应链防护开始覆盖“模型会主动安装的东西”

GitHub 7 月 28 日的公开变更确认：GitHub Advisory Database 开始吸收 OpenSSF malicious-packages 仓库中的恶意包通告，覆盖 npm、PyPI 等更多生态，并可以通过 `type:malware` 过滤。日报把它转化成一个很实用的玩法：把脱敏后的 lockfile diff 交给 Codex，只核对包名相似度、维护者变化、首次发布时间和恶意包告警，不让 agent 直接执行安装。

这条边界值得扩大到 skills、MCP server、插件和脚本。agent 现在不仅消费依赖，还可能主动发现、下载和运行工具；“能安装”不应等于“能执行”。最小可行的防线是来源固定、权限隔离、网络出口受控、安装前扫描、执行后留痕，并为每次新增工具保留可回滚版本。

## 前端 / 服务端 / 客户端工程观察

### 前端：把 agent-facing UI 当成产品接口，而不是装饰层

当 agent 有持久记忆、fast mode、区域选择和工具调用时，前端需要把这些运行时状态展示出来：本次请求使用了哪个模型和区域、是否发生回退、记忆引用来自哪里、工具是否需要人工确认。对于嵌入式工具 UI 或 MCP Apps，还要把 iframe 隔离、消息来源、网络权限和工具调用确认纳入安全验收。

前端测试也应从“截图是否正确”扩展到“状态是否可证明”：固定采集 console、network、关键 DOM/组件状态、权限提示和最终业务断言。否则用户看到的“已完成”可能只是模型输出完成，实际工具调用仍然失败。

### 服务端：模型路由要变成带约束的策略，而不是一层 URL 转发

服务端应把 `region`、`speed`、provider、数据保留、预算和 fallback 作为策略字段落库或进入 trace。路由发生变化时，返回值必须能说明实际服务地域、实际模型和是否回退；不满足合规或租户约束时应该明确失败。长任务还需要显式的 task handle、幂等状态机和审计记录，不能把可靠性寄托在隐藏 session 上。

供应链方面，Dependabot 的恶意包数据可以成为 CI 的第一道筛选，但 agent 运行时仍要有沙箱、最小权限和出网控制。特别是“自动发现一个 MCP server 并运行其安装脚本”这类流程，应拆成发现、审查、批准、执行四个状态，任何一步都能停住。

### 客户端：从聊天窗口转向任务控制面

今天群内关于支付失败、银行卡请求未到银行和代理服务的讨论，属于个人经验，不能证明某个官方风控规则；但它提醒了一个客户端共同问题：用户看到的失败位置，往往不是实际失败边界。客户端应该区分“请求未发出”“网关拒绝”“provider 未接收”“工具执行失败”和“回执丢失”，并给出下一步动作。

对 Codex、Claude Code 或其他长任务 agent，客户端还要显示任务句柄、当前模型/速度/区域、最后一次成功动作、待审批权限和可回滚版本。断线重连后要能判断服务端是否已经受理，避免用户因为看不到状态而重复提交。

## 值得跟进的动作

1. 给 agent 的每次模型调用增加最小运行时记录：模型、区域、速度、provider、fallback、token/cost、trace 和数据保留策略。
2. 选一个真实项目试用 OptMem 或同类记忆工具，验证记录是否可追溯、摘要是否可重建、坏记忆是否可删除；不要只看“模型感觉更懂上下文”。
3. 在 CI 中启用或检查 Dependabot 的 malware alerts，配合 OpenSSF 数据做 lockfile 和新增 skill/MCP server 的安装前审查。
4. 把前端 agent 验收固定为 `observe → act → verify`：必须有 console、network、状态、权限和最终业务断言，而不仅是一张截图。
5. 做一次客户端断线与重复提交演练：覆盖未送达、已受理、已执行但回执丢失、审批过期和 fallback 发生五种状态。
6. 把内部群里关于支付、代理、额度和风控的个人经验整理为“待核验问题”，不要直接升级成产品规则或安全结论。
