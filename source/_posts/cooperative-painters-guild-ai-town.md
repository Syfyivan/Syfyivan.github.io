最近重新看了一个老游戏：`Painters Guild`，中文网页小游戏里叫《天才画家培养计划》。

它的原始玩法很清楚：玩家经营一家文艺复兴时期的画家协会，接顾客订单，安排画家作画、休息、进修、调色，赚到钱以后买家具、扩建房间、提升声望。Steam 页面把它归类为管理模拟，4399 的简介里也提到几个关键点：招聘和管理画家、拓展画廊、接受顾客绘画请求、画家疲劳后需要休息、家具和画作都会占据空间，并且多个画师可以合作创作同一幅画。

我觉得最值得学习的不是它的题材，而是它的小闭环：

```text
接订单 -> 分配画家 -> 作画 / 调色 / 休息 / 学习
  -> 交付作品 -> 获得金钱和声望
  -> 买家具 / 扩建 / 招募
  -> 接更难的订单
```

但如果只是照着做一遍，就还是一个单人调度游戏。真正有意思的改造，是把它从“一个玩家操作所有画家”变成“多个玩家各自扮演一个画家”。

也就是说，原作里玩家像工会老板，拖着每个画家到处干活；新版本里，每个玩家就是一个画家。大家共享同一个画室，面对同一批订单、同一个颜料库存、同一套家具和同一个工会声望。

## 一句话版本

这是一个多人协作画室经营游戏：

```text
玩家各自控制一名画家，在同一间工坊里协作接单、作画、调色、休息、学习和扩建。
订单来自顾客，也可以来自 AI 小镇里的居民。
完成后的作品会成为小镇世界的一部分，被摆进店铺、广场、住宅或展览空间。
```

它保留《画家工会》的经营骨架，但把核心体验从“我调度别人”改成“我们一起经营”。

## 为什么要改成多人

单人版的乐趣来自资源调度：谁去画，谁去睡，谁去调色，是否拒绝订单，钱先买床还是买画架。

多人版的乐趣来自协商和临场救火：

- 一个玩家快累倒了，但订单还有最后一段精修；
- 调色师发现颜料快没了，要不要先停下大画；
- 两个画家都想去画高价值订单，但普通订单马上超时；
- 有人专注赚钱，有人想提升声望，有人想练个人风格；
- 大项目需要三个人协作，谁打底，谁上色，谁收尾。

这类分工天然会产生对话：

```text
你先去睡，我来补最后 20%。
别接那个贵族肖像，我们颜料不够。
我速度快，我先打底，你等一下来精修。
这张挂到镇长办公室，声望应该会涨。
```

这比一个人拖动所有角色更适合放进 AI 小镇，因为 AI 小镇本身就是一个由角色、关系、地点和事件组成的世界。

## 核心循环

第一版可以保持非常简单：

```text
订单出现
  -> 玩家决定接受或拒绝
  -> 玩家站到画架旁进入作画
  -> 作画消耗颜料并增加疲劳
  -> 其他玩家可以加入同一幅画
  -> 作品完成后交付
  -> 获得金币、声望和 NPC 关系变化
  -> 购买家具、扩建画室、学习新技法
```

关键是不要让玩家只是在画架旁等进度条。每种工作状态都应该有轻量决策。

作画时可以选择：

- 快速推进：进度快，但质量波动更大；
- 稳定绘制：进度中等，质量稳定；
- 精修细节：进度慢，但提高最终质量上限；
- 迎合客户：更容易拿奖励，但降低个人风格成长；
- 坚持风格：可能惹客户不满，但提高艺术声望。

调色时可以选择：

- 大量混色：补充通用颜料；
- 精准配色：为某个订单生成加成颜料；
- 研究新配方：短期收益低，长期解锁风格。

休息时也可以有取舍：

- 小憩：恢复快，但不完全；
- 深睡：恢复彻底，但占用床位更久；
- 散步：恢复心情，顺便触发小镇事件。

## 玩家角色

不要让所有玩家只是“速度不同的画家”。每个画家应该有自己的专长和性格。

可以先做 6 种原型：

| 角色 | 擅长 | 弱点 |
| --- | --- | --- |
| 速写师 | 小订单、打底、赶工 | 精修能力弱 |
| 精修师 | 提高质量上限、名作收尾 | 作画速度慢 |
| 调色师 | 高效生产颜料、制作特殊颜料 | 直接作画收益低 |
| 社交画家 | 谈价格、争取延期、安抚顾客 | 技术成长慢 |
| 学院派 | 学习技法、解锁科技、指导新人 | 前期赚钱慢 |
| 策展人 | 布置展览、提升声望、安排作品落地 | 依赖已有作品 |

每个玩家只需要控制一个角色，但整个工会需要这些能力组合起来。

如果人数不足，可以用 AI 学徒补位。AI 学徒不应该比玩家聪明，而应该像可被指派的简单助手：去调色、去休息、帮忙打底、搬画架。这样单人也能玩，多人时又不会抢玩家的戏。

## 订单系统

订单最好按“复杂度”分层。

普通订单：

- 肖像；
- 店铺招牌；
- 小幅宗教画；
- 家庭纪念画。

中型订单：

- 餐厅壁画；
- 学校教学画；
- 节日海报；
- 商会宣传画。

大型订单：

- 教堂穹顶；
- 镇政厅壁画；
- 纪念碑草图；
- 全镇庆典展览。

每个订单包含这些字段：

```ts
interface Commission {
  id: string;
  requesterId: string;
  title: string;
  styleWanted: "portrait" | "religious" | "landscape" | "poster" | "abstract";
  phases: WorkPhase[];
  deadlineDays: number;
  paintCost: number;
  rewardCoins: number;
  rewardPrestige: number;
  relationshipImpact: Record<string, number>;
  placementTarget?: string;
}
```

订单可以拆成阶段：

```text
构图 -> 打底 -> 上色 -> 精修 -> 装裱 -> 交付
```

多人合作时，不是简单叠进度，而是让不同阶段吃不同技能：

- 速写师适合构图和打底；
- 调色师能降低上色消耗；
- 精修师负责最后质量；
- 社交画家可以在中途处理客户改需求；
- 策展人决定作品完成后放在哪里。

这样一幅画自然会变成小团队任务。

## 空间和家具

画室应该是一个有格子的 2D 空间。家具不是装饰背景，而是生产设施。

基础家具：

- 画架：承载订单；
- 床：恢复疲劳；
- 调色台：生产颜料；
- 书桌：学习技法；
- 仓库：提高颜料容量；
- 展示墙：展示作品，提高声望；
- 门口招牌：吸引更高价值客户。

空间限制很重要。它让玩家必须做经营选择：

```text
多放画架 -> 能同时接更多订单，但画家更累
多放床 -> 周转稳定，但产能降低
多放装饰 -> 声望更高，但挤占生产空间
扩建房间 -> 解决空间，但需要大量金币
```

这也是原作里很经典的地方：所有家具和画作都占空间，摆得下画板时多个画师可以共同创作。

## AI 小镇接入

如果后续放进 AI 小镇，最有价值的部分是“订单不再随机生成”，而是来自小镇居民的生活。

AI 小镇可以给画室提供这些输入：

- NPC 的职业、性格、预算、审美；
- 小镇最近发生的事件；
- NPC 之间的关系；
- 店铺、住宅、公共空间的装饰需求；
- 节日、竞选、纪念日、开业等场景。

例如：

```text
咖啡馆老板想要一幅新招牌，因为隔壁新开了一家甜品店。
镇长竞选前需要宣传肖像，但不希望看起来太傲慢。
一对居民结婚，想委托一幅纪念画。
学校老师希望画一张文艺复兴主题教学挂图。
广场节日快到了，需要多人合作完成大型壁画。
```

完成后的作品也不要只换成金币。它应该成为世界状态：

```ts
interface Artwork {
  id: string;
  title: string;
  authors: string[];
  style: string;
  quality: number;
  storyTags: string[];
  createdAtWorldTime: number;
  placedAt?: {
    locationId: string;
    x: number;
    y: number;
  };
}
```

作品挂进小镇以后，可以继续影响世界：

- 店铺人气上涨；
- 委托人的心情变好；
- 其他 NPC 评论作品；
- 某个画家因此出名；
- 工会声望提升；
- 后续出现相关订单。

这样“完成一幅画”就不只是结算动作，而是在小镇里留下痕迹。

## 系统架构

为了以后接 AI 小镇，最好从一开始就把它拆成三层。

```text
客户端
  - 玩家移动
  - 设施交互
  - 拖拽 / 点击 UI
  - 画作进度动画

工会模拟服务
  - 订单状态
  - 画家状态
  - 资源和家具
  - 多人同步
  - 时间推进

AI 小镇事件层
  - NPC 需求生成
  - 委托文本生成
  - 作品评价
  - 小镇位置落地
  - 记忆和关系更新
```

数据流可以这样走：

```text
AI 小镇事件
  -> 生成委托
  -> 工会订单池
  -> 玩家协作完成
  -> 产出 Artwork
  -> 写回小镇世界
  -> NPC 评价和关系变化
  -> 新事件继续生成
```

这个方向和 AI Town 的基础设施思路一致：核心世界状态由服务端模拟器串行推进，玩家和 AI 都只是提交输入。这样多人玩家、AI NPC、异步 LLM 结果不会在同一时间随便改状态。

## 最小可行版本

第一版不要急着做完整 AI 小镇。先验证多人画室是否好玩。

MVP 可以这样定：

1. 一个网页房间，支持 2 到 4 个玩家进入；
2. 每个玩家控制一名像素画家；
3. 画室里有画架、床、调色台、书桌；
4. 系统定时生成订单；
5. 玩家走到设施旁按键开始工作；
6. 作画消耗颜料，工作增加疲劳；
7. 多人可以协作同一幅画；
8. 完成订单获得金币和声望；
9. 金币可以买更多画架、床和装饰；
10. AI 小镇先只作为“订单文本生成器”，暂不做完整世界回写。

技术上可以用：

- Phaser 3 或 PixiJS 做 2D 客户端；
- Node.js / WebSocket 做多人同步；
- 服务端维护权威状态；
- 前端只做输入和表现；
- 后续再接 AI 小镇的 NPC 需求系统。

服务端 tick 可以非常简单：

```ts
function stepGuild(dt: number, guild: GuildState) {
  spawnCommissions(dt, guild);
  updatePainters(dt, guild);
  updateActiveArtworks(dt, guild);
  resolveDeadlines(guild);
  resolveCompletedCommissions(guild);
}
```

玩家输入也尽量事件化：

```ts
type PlayerInput =
  | { type: "move"; playerId: string; target: Point }
  | { type: "start_work"; playerId: string; stationId: string; mode: WorkMode }
  | { type: "stop_work"; playerId: string }
  | { type: "accept_commission"; commissionId: string }
  | { type: "buy_furniture"; itemId: string; position: Point };
```

核心原则是：客户端不直接改钱、声望、订单进度。客户端只提交输入，服务端统一结算。

## 第一版的乐趣判断

这个项目是否值得继续，不看内容量，而看下面几个问题：

- 玩家会不会自然分工？
- 玩家会不会互相催促和救场？
- 订单快超时时，是否会产生紧张感？
- 疲劳、颜料、床位、画架是否形成真实取舍？
- 完成一幅多人合作的大画时，是否有共同完成感？
- 作品挂进小镇后，玩家是否会记得“这是我们画的”？

如果这些成立，再接 AI 小镇才有意义。

如果这些不成立，直接加 AI NPC、记忆、世界事件，只会把系统变复杂，但不会让游戏更好玩。

## 可以超过原作的地方

《Painters Guild》的问题是中后期重复：接单、画、休息、升级，很快就进入稳定流水线。多人版本可以从几个方向补深度。

第一是关系：

画家之间可以有师徒、竞争、默契、嫉妒。多人合作越多，默契越高；长期抢同一类订单，可能形成竞争。

第二是市场趋势：

某段时间宗教画流行，下一段时间贵族肖像涨价。调色师和社交画家可以提前感知趋势。

第三是作品生命：

画作不是卖掉就消失。它会挂在小镇里，被 NPC 看见、讨论、收藏、转卖，甚至成为某个事件的线索。

第四是个人风格：

每个玩家可以形成自己的风格标签。客户可能点名某位画家，也可能因为风格冲突拒单。

第五是 AI 事件：

AI 小镇里的真实事件会变成订单来源。玩家不是服务随机顾客，而是在参与一个持续变化的小镇叙事。

## 结论

这个方案的重点不是复刻一个老 Flash 游戏，而是把它的经营闭环改造成一个适合多人和 AI 世界的模块。

`Painters Guild` 给了一个很好的骨架：

```text
有限空间 + 有限人力 + 疲劳 + 订单 + 声望 + 扩建
```

多人版本要加上的，是：

```text
玩家分工 + 协商 + 救场 + 共同作品 + 小镇影响
```

AI 小镇要加上的，是：

```text
有记忆的委托人 + 有地点的作品 + 有后果的评价 + 会延续的事件
```

如果能把这三层接起来，它就会从一个“经营画室小游戏”变成 AI 小镇里很自然的职业系统：玩家和朋友一起经营画室，AI 居民带着自己的故事来下单，而每一幅完成的画都会留在小镇里，成为大家共同生活过的证据。

## 可试玩原型

我先做了一个可以直接在博客里玩的原型：[共享画室](/painters-guild/)。

它目前支持两种模式：

- 不填服务器地址时，可以本地单人试玩；
- 启动 WebSocket 后端后，多名玩家可以进入同一个房间，各自认领一名画家。

后端可以直接放在阿里云 ECS 上跑，部署步骤见：[共享画室 WebSocket 后端部署](/docs/painters-guild-server-deploy.md)。
