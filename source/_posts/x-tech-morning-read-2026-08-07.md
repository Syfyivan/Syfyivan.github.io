## AI 观察

### 1. “临时会话消失”有时不是故障，而是产品契约没有被看见

今天群里对 Codex 侧边聊天的疑问，表面上是“为什么过一段时间不能继续”“聊天记录为什么清空”。公开的 OpenAI Codex Issue 给出了更清晰的背景：当前 `/side` 被描述为从主对话开启的 ephemeral fork，相关源代码把它定位为快速侧边提问；Issue 还明确把“让侧聊在重启、更新和重新加载后保留”列为 feature request，而不是把现状直接认定为偶发丢数据。

这两者的差别很重要。若一个功能本来就是临时上下文，用户需要的是醒目的生命周期提示、升级路径和“保存到主任务/转成 fork”的动作；若产品承诺持久化却丢记录，才应该按数据可靠性问题处理。把两者混成一个“AI 记性不好”的抱怨，会让前端、服务端和客户端都排错在错误的层次。

Anthropic 的官方 Claude Code cheatsheet 也采用类似的分层：`/btw` 是不加入主对话的快速侧边问题，session 拥有自己的会话历史，而项目记忆由 `CLAUDE.md` 跨 session 保留。不同产品的命令名称不必相同，但可以看出一个共同趋势：AI 工具正在把“对话”拆成主任务、短问答、分支和项目记忆几种不同生命周期。

### 2. 上下文不是一个总开关，而是一组有生命周期的资源

更实用的抽象不是“有没有聊天记录”，而是给上下文分层：

| 上下文层 | 典型用途 | 默认生命周期 | 应有的操作 |
| --- | --- | --- | --- |
| 主任务 | 持续执行、修改代码、跑验证 | 持久或可恢复 | 继续、暂停、恢复 |
| 侧边提问 | 查询当前进度、一次性解释 | 临时 | 关闭、丢弃、提升为分支 |
| Fork 分支 | 探索另一条实现路线 | 持久分支 | 对比、合并、归档 |
| 项目记忆 | 规则、约束和稳定背景 | 跨任务 | 查看、修改、审计 |

这张表也解释了今天群里“侧边问一次性问题，重要内容给主任务或文档”的经验：不是所有内容都应该进入主线程，但所有真正影响交付的决策都应有一个可恢复的落点。临时上下文可以低成本、低噪声；它不能承担唯一的需求、验收标准、权限批准或回滚依据。

### 3. 带用户身份的工具调用，把“回答问题”变成“代表用户行动”

Claude Code 群里的另一条讨论涉及读取个人消息、以用户身份给别人发消息，以及某次异常代发排查。这里不应把群内转述当成已证实的产品行为，但它提示了一个更普遍的 AI 工程问题：一旦 agent 能使用用户身份调用外部系统，安全边界就不再只是模型能不能生成正确文本，而是“谁授权、以谁的身份、向谁执行了什么动作、结果能否审计”。

因此，“能调用消息工具”至少要拆成四个独立状态：发现工具、通过权限检查、生成待执行动作、实际发送并获得回执。把这四步压缩成一个“工具可用”标记，用户就无法区分“没有权限”“动作未发送”“发送成功但回执丢失”和“发送后需要撤回或补救”。

### 4. 没有稳定 X 单帖，就不要用 X 的热闹替代证据

本轮 X 当日检索页可访问，但没有稳定展开可复核的单帖正文。这个结果本身也是来源质量信号：搜索入口证明“检索发生过”，不证明某个作者在当天说过某句话，更不证明一个产品变更已经发布。

所以本文把 X 留在来源窗口和后续追踪入口，不引用不可核验的作者观点、点赞量或所谓行业共识；关于 `/side`、`/btw`、session history 和项目记忆的事实，改由官方仓库、公开 Issue 与厂商文档支撑。晨读的价值不是每天都凑出一条 X 热点，而是让读者知道哪些信息已经核验、哪些仍然只是线索。

## 前端 / 服务端 / 客户端工程观察

### 前端：把“临时”做成可见、可操作的生命周期

侧边会话的入口附近应直接显示“临时”“不保证跨重启保留”或等价提示，并提供三个低摩擦动作：把结论发送到主任务、保存为文档/备注、提升为持久分支。关闭前不必每次弹出打断式确认，但当侧聊包含代码片段、决策或外部工具结果时，应给出轻量的保存建议。

前端还要区分上下文来源：哪些文本来自主任务，哪些来自侧聊，哪些是项目记忆，哪些是当前工具返回。这样用户才能判断一个回答为什么“知道这件事”，也才能在错误时删除错误来源，而不是盲目清空整个会话。

### 服务端：为会话、分支和副作用建立不同的状态机

会话服务不应只保存一张 `conversation` 表。至少需要区分 `thread_id`、`parent_thread_id`、`persistence`、`input_version`、`permission_context` 和 `side_effects`。临时侧聊可以落内存或短期存储，但要明确它的过期条件；持久分支必须有可恢复的记录；工具调用则要单独记录授权、执行、回执和幂等键。

外部消息发送尤其不能靠“模型输出了一段 JSON”来证明完成。一个可审计的最小链路是：`drafted → authorized → sent → acknowledged`，失败则进入 `rejected`、`unknown` 或 `needs-reconciliation`，而不是直接回到可重试状态。否则网络超时可能造成重复发送，或者用户以为没发成功而再次操作。

### 客户端：桌面、终端、IDE 和移动端共享同一份上下文事实

如果桌面端看到侧聊，终端看到 `/side`，移动端看到一个“临时问题”，三个入口必须共享会话类型、父任务、保存状态和最后一次同步时间。不能把本地列表里暂时消失解释成服务端数据已删除，也不能把一个仍在内存里的临时线程显示成“已保存”。

客户端切换模型或入口时，还应把上下文能力显示出来：是否能恢复、是否会触发压缩、是否继承项目记忆、是否保留工具授权。模型名称只是配置的一部分；真正影响结果的是上下文、工具和权限三者的组合。

### 共同边界：把“记忆”“日志”“产物”和“副作用”分开

一段对话记录不等于项目记忆；工具日志不等于外部动作成功；一份生成的补丁不等于已经合入；群内有人遇到过现象也不等于厂商发布了行为承诺。今天的材料很适合用来做一个小型验证矩阵：固定同一任务，分别测试侧聊关闭、应用重启、`/fork`、主任务保存和消息工具调用，记录每一步的可见状态与恢复结果。

## 值得跟进的动作

1. 在自己的 Codex/Claude Code 工作流里约定：侧聊只放一次性问题；任何需求、约束、验收结论、权限批准和回滚信息，都写入主任务、项目记忆或可追踪文档。
2. 为 agent 会话补一组最小字段：`session_kind`、`parent_id`、`persisted`、`expires_at`、`memory_scope`、`permission_scope` 和 `last_sync_at`，前端按这些字段展示生命周期。
3. 设计一次“重启与恢复”测试：主任务运行中开侧聊，分别关闭窗口、重启客户端、创建 fork，再检查哪些内容保留、哪些内容应当消失、用户是否得到明确提示。
4. 对所有带用户身份的消息、邮件、日历或文档工具，先实现草稿与审计，再开放实际发送；执行记录至少包含授权主体、目标、动作摘要、幂等键和回执。
5. 做一张“上下文层 × 客户端 × 工具权限”的兼容性矩阵，不用一句“这个入口不稳定”覆盖掉是临时语义、同步延迟、权限缺失还是服务端异常。
6. 继续观察 [X 当日 Codex/Claude Code/AI 检索页](https://x.com/search?q=%28Codex%20OR%20%22Claude%20Code%22%20OR%20AI%29%20since%3A2026-08-07%20until%3A2026-08-08&src=typed_query&f=live) 是否出现可稳定打开的原始帖子；在此之前，不把搜索摘要或截图当作产品变更证据。
