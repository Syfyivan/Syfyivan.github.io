王国里有一匹名马，跑得快，记路也准。商人买下它后，第二天就抱怨：“为什么它不能把货送到北城？”

老车夫问：“车厢呢？缰绳呢？货箱呢？路引呢？驿站呢？过桥要交的凭证呢？”

商人说：“我买的是名马。”

老车夫说：“那你得到的是速度，不是运输系统。”

## 概念揭晓

这篇章要揭开的，是第 06 讲里最基础也最容易被忽略的一层：**模型只是能力本体，模型之外还有一整套让它真的能干活的外壳**。

这里的“马”对应模型本身，负责推理、生成、判断；“车厢、缰绳、驿站”对应外面的工程结构，也就是我们今天说的 Harness。没有这层外壳，模型可以很强，但它还是更像一匹快马，不像一套能稳定运货的系统。

下面我会把这层外壳拆成几块：为什么换壳能提分、规则为什么要靠失败驱动、底层零件到底有哪些、长程任务为什么会把 Context 和调度一起拉进来，以及为什么今天的产品越来越像，但底层模型并不是唯一原因。

## 模型之外，究竟多了什么

第 06 讲里最核心的判断就是：**Agent = Model + Harness**。这不是一句口号，而是一种工程拆法。模型负责“想”，外壳负责“让想法变成可执行、可审计、可恢复的过程”。

在这个拆法里，外壳通常至少包含六类东西：

- 指令层：系统提示、项目说明、角色说明、子任务说明。
- 工具层：文件读写、命令执行、搜索、浏览、外部接口。
- 运行环境：文件系统、沙箱、浏览器、终端、权限边界。
- 编排层：任务拆分、子任务派发、并发、重试、回收。
- 纪律层：钩子、校验、审批、阻断危险动作。
- 观测层：日志、轨迹、计量、回放、复盘。

这也是为什么“换壳”有时比“等下一代模型”更有用。因为很多失败并不是模型本身不具备能力，而是它缺少合适的外壳去把能力稳稳落地。

## 为什么换壳能提分

源文里用了一个很直接的工程观察：同一个模型，换一套外壳，结果可以差很多。这里更稳妥的说法是，**在真实工程里，模型输出和最终体验常常被外壳拉开很大差距**。

差距通常来自三类地方：

1. 工具契约不清楚，模型不知道什么时候该用。
2. 上下文组织不合理，模型很快被噪音淹没。
3. 调度和恢复做得差，一旦跑长了就容易半路丢状态。

所以很多时候，工程师看到“模型今天怎么这么笨”，其实该先问的不是“模型坏了没有”，而是“外壳有没有把它应该知道的东西、应该做的动作、应该遵守的纪律都安排好”。

这个重心很重要：**当问题主要落在外壳里时，工程师今天就能改；当问题只落在模型权重里时，你只能等。**

## 棘轮原则：规则只为失败负责

源文里我最认可的一条标准是：好的项目规则，最好都能追溯回一次具体失败。换句话说，**规则不是凭感觉堆出来的，而是失败逼出来的**。

棘轮原则有两个方向：

- 失败发生后，把对应规则加进去，避免同样的坑再掉一次。
- 模型变强后，回头压力测试旧规则，能删的就删，不要把外壳养成垃圾抽屉。

这比“多写几条保险规则”更工程化。因为每一条规则都要回答一个问题：它到底是在防哪一次具体事故？如果答不上来，这条规则大概率只是让系统更重。

这也是我理解 Harness 的一种方式：**它不是装饰层，而是失败记忆的结构化沉淀**。

## 基础零件：文件系统、命令执行、沙箱、记忆、搜索、钩子

把外壳拆细，最常见的几块就是这些：

- 文件系统和 Git：让任务能落盘、能回滚、能对比。
- Bash：让模型可以借助现有脚本和命令完成通用操作。
- 沙箱：把危险动作关在边界里，不让它误伤环境。
- 记忆和搜索：让长任务不必把全部历史硬塞进上下文。
- 钩子：把关键纪律从“希望模型记住”变成“外壳强制执行”。

这些东西并不神秘，但它们共同决定了一个系统是不是“能跑很久”。模型只是在中间发挥智能，真正保证它不乱来、不失忆、不越界的，往往是这些朴素零件。

可以把它理解成一辆车的底盘、刹车、油箱、仪表盘和维修站。车再快，没有这些，也跑不远。

## 长程任务：Context 与调度的两条战线

源文把长程任务拆成了两条战线，这个拆法非常准确。

第一条是 Context 战线。任务一长，最先出问题的通常不是“不会想”，而是“装不下、记不住、越跑越乱”。常见解法有三种：

- 压缩旧上下文，腾出空间。
- 把大输出落盘，按需再取。
- 通过按需加载的能力树，把“可能需要”改成“现在才需要”。

第二条是调度战线。任务一长，另一个常见问题是“模型自己宣布做完了”。这时就需要：

- 用文件化的计划约束自己。
- 用重启式循环维持目标不丢。
- 把“判断做完没有”的角色和“产出结果”的角色分开。

这两条战线合在一起，才算真的接住长程任务。单纯加大上下文窗口不够，单纯让模型更聪明也不够。**长程任务本质上是外壳工程，而不是单轮生成工程。**

## 收敛正在发生

源文还有一个很重要的判断：现在很多产品长得越来越像，不是因为大家抄得整齐，而是因为它们在共同收敛到一套更稳定的外壳模式。

这个收敛至少有三层：

- 服务化：把常见的外壳能力做成可配置的底座，而不是每个团队从零手搓。
- 共演化：模型变强后，外壳不会消失，只会把重心移到下一层更难的问题上。
- 相似化：不同产品底层模型不一样，但文件系统、终端、沙箱、审批、子任务这些结构越来越接近。

这意味着什么？意味着外壳不是临时过渡件，而是一个独立工程方向。它会越来越像基础设施，也会越来越像产品。

## Skill 与 Hook 是落地把手

如果把第 06 讲再压缩一层，普通工程师真正能动手的把手，大致就是 Skill 和 Hook。

Skill 解决“能做什么”：

- 什么时候被发现。
- 触发后能用哪些工具。
- 应该注入哪些按需知识。

Hook 解决“必须怎么做”：

- 什么时候拦截危险动作。
- 什么时候做自动校验。
- 什么时候在退出前强制复核。

这两者一软一硬，刚好夹住中间那条执行链。Skill 让系统更能干，Hook 让系统更可靠。它们不是装饰，而是外壳里最容易被普通工程师直接改造的部件。
