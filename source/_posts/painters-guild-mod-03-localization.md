在成长、事件和经营之外，中文本地化也值得单独做成一个可选扩展。对这款 Flash / AIR 游戏来说，改掉英文只是第一步，中文字体、文本框宽度和动态字符串都需要检查。

当前是 **0.1 部分汉化候选**：四个主菜单标签、二十一组事件标题与正文已编译进候选 SWF，并完成重新导出检查。它不是完整汉化包，也尚未完成中文界面的运行验收。

## 1. 先选可核对的文本范围

首批菜单包括“新游戏、读取存档、设置、退出游戏”。事件部分包含欢迎说明、原作预设的历史消息，以及 1620 年的巴洛克时期总结。

文本与原作处理函数一一对应，翻译数据单独放在本地 `zh-CN.json` 中。准备脚本按函数定位标题与正文，再生成修改后的 ActionScript 类。每个替换位置必须唯一，找不到或出现多个匹配就停止，避免换一个版本后悄悄改错地方。

这批翻译中，个别引文使用了标注过的意译。历史消息保留原作叙述层面的含义，不把游戏文本当作已经核实的史料。新增历史内容时，需要另做历史资料核查。

## 2. 显示文字和程序内部名称要分开

原作会用字符串判断家具类型等行为。如果只做全局字符串替换，可能把逻辑条件使用的名称也改掉。

例如，一个名字既出现在界面，又被用来判断是否执行调色逻辑。只翻译其中一处，比较就可能失配。因此本次优先修改明确用于显示的赋值位置，不改内部物品标识、类名或存档键。

后续完整汉化最好把界面展示映射集中管理：程序内部继续使用稳定标识，面向玩家时再取中文文案。

## 3. 为什么需要处理字体

Flash 文本框可以使用嵌入字体。如果嵌入字体没有目标中文字形，简单替换成中文可能显示为空白。是否缺字需要逐个资源或界面验证，不能只凭游戏原本是英文就假定所有文本框都一样。

本次候选采用 Windows 系统字体方案：对目标文本框关闭嵌入字体，改用 `Microsoft YaHei`，同时设置默认格式和当前格式。这样兼顾后续再次给文本框赋值的情况。

下面是这次新写的字体处理函数的思路，省略具体类接入位置：

```actionscript
var format:TextFormat = field.getTextFormat();
format.font = "Microsoft YaHei";
field.embedFonts = false;
field.defaultTextFormat = format;
field.text = translatedText;
field.setTextFormat(format);
```

主菜单在赋值位置调用它；事件窗口在刷新标题与正文时调用它。这个方案只针对本次 Windows 环境，不包含字体文件，也没有证明其他系统会得到相同显示结果。

目前没有重新布局文本框。短中文标签可能更紧凑，但长事件、数字和人名混排仍可能溢出，因此不能把“已经设置字体”当成“排版通过验收”。

## 4. 构建过程和输入校验

补丁在独立调研目录中准备，不覆盖 Steam 安装文件。流程是：

```text
校验原始 SWF 的 SHA-256
  → 从本地导出结果定位文本
  → 生成修改后的 MainTimeline 与 NewEvent
  → 使用 JPEXS 依次替换两个类
  → 重新导出候选文件，检查文字与接入点
  → 在独立游戏副本中进行中文界面验收
```

两个类需要一起替换：事件类会调用主时间轴新增的字体函数。只安装一半不是受支持的组合。

编译使用 JPEXS 的 `-replace` 能力；工具将该能力标为实验性，因此即便编译成功也必须做运行测试。命令格式参考[官方命令行说明](https://github.com/jindrapetrik/jpexs-decompiler/wiki/Commandline-arguments)。

## 6. 下一轮应该怎样验收

先检查四个主菜单能否显示与点击，再进入新游戏，查看欢迎事件和最长的一组事件文字。事件按钮的悬停会改变说明区域，移出后又会恢复正文，这两个过程都要检查。

随后检查包含人名、金额和日期的内容，确认数字没有丢失、中文没有被截断。最后保存、退出、读档，并与未汉化副本比较同一状态，确保纯显示修改没有改变玩法数据。

正式安装说明应在这些检查通过后提供，并包含原始文件备份、版本识别和恢复步骤。当前只保留本地候选，不发布原版 SWF 或完整反编译脚本下载。
