这篇文章只讲一次事件消费写放大治理。

问题发生在社区帖子积分链路：活动已经结束，但历史帖子消息因为延迟或重放，仍然进入活动 fanout、分布式锁、报名查询、帖子详情读取和大对象诊断写入。

这个案例没有漂亮的业务增长数字，却很适合稳定性面试，因为它能体现问题定位、生命周期判断、止血与根治、采样和可观测性。面试时不需要复述提交时间，而要把因果链讲完整。

## 一、十五秒怎么介绍

> 我处理过一次 MQ 重放导致的写放大。旧链路只判断帖子创建时间是否在活动期，没有判断活动当前是否仍运行，所以活动结束后历史消息仍进入 fanout、Redis 锁、报名 RPC 和详情写。我在 fanout 前增加当前时间与状态检查，并在业务处理器内保留第二层 guard；同时把无效详情从全量写改成确定性采样，并裁剪存储字段。

## 二、默认两到三分钟主回答

> 这个问题发生在帖子积分消费者。活动已经结束，但历史消息因为延迟或重放仍在进入处理链。旧逻辑只校验帖子创建时间是否属于活动期，所以历史帖子本身是合法的；它没有校验活动当前是否仍运行，结果消息继续对活动列表 fanout，获取分布式锁、查询报名和帖子详情，并写入大对象诊断数据。
>
> 我先沿消息入口把完整调用链画出来，确认只让运营删除配置可以临时止血，却不能成为系统防线。代码上我做了两层保护：第一层在 fanout 前检查当前状态和时间，尽早避免 goroutine、锁和 RPC；第二层保留在社区帖子处理器内部，守住“不为结束活动产生新副作用”的业务不变量，防止未来新入口绕过。
>
> 同时我发现无效帖子也在全量保存详细诊断数据，所以把运行时校验结构和持久化结构分开，只保存归因需要的字段。有效帖子默认记录，无效帖子只有 debug 开启或命中确定性采样才保存。采样使用活动、用户、帖子和失败原因计算稳定哈希，同一条重放消息不会每次随机产生新的写入。
>
> 这次修复的直接效果是：过期活动在进入 fanout、锁、报名 RPC 和大对象写之前就被拦截。它没有业务增长指标，但能证明我不是只会修改局部代码，而是能沿消息链定位资源放大、区分事件时间与系统当前状态，并用守卫、采样和观测形成完整治理。

## 三、面试官真正会听什么

| 面试官的判断 | 你要给出的证据 |
| --- | --- |
| 是否会定位问题 | 从 MQ 入口追到 fanout、锁、RPC 和存储 |
| 是否理解消息语义 | 至少一次投递、延迟、重放和幂等 |
| 是否会做系统性修复 | 当前时间 guard、处理器二次保护、配置只止血 |
| 是否有成本意识 | 无效详情采样、紧凑 DTO 和指标控制 |
| 是否诚实归因 | 只说阻断路径，不编造 CPU 或存储下降比例 |

## 四、问题的完整调用链

```text
帖子变更 MQ
  -> 解析事件
  -> 获取所有可能消费帖子事件的活动 ID
  -> 批量读取活动配置
  -> 为每个活动并发 fanout
  -> 获取 活动+帖子 分布式锁
  -> 查询用户报名
  -> 延迟读取帖子详情
  -> 校验主题、字数、图片和状态
  -> 写用户帖子积分状态
  -> 写诊断详情
```

任何一层单看都合理，活动结束后整条链继续执行就形成无效成本。

## 五、为什么历史消息会在活动结束后出现

消息系统通常提供至少一次投递。晚到或重复可能来自：

- 消费者处理超时；
- 重平衡；
- 下游临时失败后重试；
- 人工回放；
- 历史积压恢复；
- 上游更新事件再次触发。

消费者必须把重复和延迟当成正常输入，而不是偶发异常。

## 六、旧逻辑为什么没有拦住

旧处理器检查：

```text
post.create_time 是否在 activity.start_time ~ end_time
```

历史帖子确实是在活动期间创建，所以通过。

但它没有问：

```text
time.now 是否仍在活动期
activity.status 是否仍允许产生新副作用
```

所以活动结束不影响历史事件重放。

## 七、事件时间和当前时间

### 事件时间

回答：这条内容在发生时是否属于活动。

### 当前时间

回答：系统现在是否还允许为这个活动执行任务和写入。

在线积分活动通常需要两者都成立：

```text
current_activity_running
AND event_happened_in_window
```

如果业务明确支持活动结束后的补算，则需要单独的 backfill 模式、时间窗口、限流和审计，不能让普通在线消费者无限接受旧消息。

## 八、一次完整的定位与修复闭环

### 发现阶段

从资源和日志症状看，活动结束后仍有帖子处理、锁和详情写。沿消息入口追踪后，发现过期活动仍存在于运行时配置列表，消费者又只校验帖子创建时间。

### 止血判断

移除或关闭运行时配置可以立即减少流量，但配置清理有延迟，也不能阻止未来同类问题。

因此配置清理只作为运维止血建议，代码修复必须独立成立。

### 根因修复

核心修复一次完成三组变化：

1. fanout 前增加活动当前状态与时间检查；
2. 社区帖子处理器增加第二层相同 guard；
3. 诊断详情增加采样和紧凑存储结构。

### 验证

单元测试覆盖：

- 运行中活动继续处理；
- 已结束活动不进入处理器；
- 非运行状态跳过；
- 有效帖子仍保存详情；
- 无效帖子按 debug 或 sample 决定；
- 相同事件采样结果稳定。

## 九、第一层 guard：fanout 之前

伪代码：

```text
for activity in activities:
    if !is_running_now(activity):
        continue

    spawn processor(activity)
```

尽早拦截避免：

- 创建 goroutine；
- 构造帖子详情 loader；
- sleep 等待主从同步；
- 获取 Redis 锁；
- 查询报名和帖子详情。

它主要解决资源效率。

## 十、第二层 guard：业务处理器内部

```text
CommunityPostProcessor.Process:
    if !is_running_now(activity):
        return nil
```

为什么看起来重复仍要保留？

- 未来可能出现不经过统一 fanout 的调用入口；
- 单元测试可能直接调用处理器；
- 重构时入口保护可能被移动；
- 处理器自己必须守住“不为结束活动产生副作用”的不变量。

第一层是资源优化，第二层是业务安全。

## 十一、活动状态如何判断

同时检查：

- activity.status 属于允许运行的状态；
- 当前时间不早于开始时间；
- 当前时间不晚于结束时间；
- 时区使用统一业务时区；
- 无时间配置时采用明确默认，而不是随意放行。

日志记录跳过原因：status_not_running 或 outside_running_period，便于区分配置问题和正常结束。

## 十二、为什么不返回 error

活动正常结束后跳过旧消息，是业务预期，不是系统故障。

如果返回 error，消息系统可能继续重试同一消息，反而放大流量。

应该：

```text
记录结构化 skip 日志
增加 skipped counter
返回 nil 确认消费
```

只有配置读取、存储或核心依赖真正失败时才返回 error。

## 十三、写放大不只来自有效数据

旧逻辑为大量无效帖子也保存完整诊断详情，包括：

- 标题和正文预览；
- 多组字数统计；
- 主题来源；
- 图片和封面字段；
- 帖子日志与详情的重复状态；
- 调试归因字段。

高重放量下，即使每条只有几 KB，也会形成明显存储和序列化成本。

## 十四、为什么不完全删除诊断详情

这些字段曾用于排查：

- 为什么某帖没有积分；
- 主题 ID 来自哪里；
- 字数按哪个字段计算；
- 删除或审核状态怎样变化；
- 帖子日志与详情不一致。

完全删除会让后续问题无法定位。

正确方向是：有效数据保留必要详情，无效数据受控采样。

## 十五、确定性采样

```text
bucket = FNV(activity_id:user_id:post_id:reason) % 100
save = bucket < sample_percent
```

为什么不使用普通 random？

同一事件每次重放都会重新随机，可能多次命中并产生多份写入。确定性哈希让相同业务键始终得到相同决定。

### 采样规则

- 有效帖子：默认保存；
- debug 开启：无效帖子全量保存；
- sample <= 0：无效帖子不保存；
- sample >= 100：无效帖子全量保存；
- 其他：按稳定桶采样。

## 十六、采样键为什么包含 reason

同一帖子可能先因字数不足失败，后来编辑后因缺图失败。

把 reason 加入哈希后，不同失败原因可以独立采样，有利于观察状态变化。代价是同一帖子可能保存多个原因版本，需要在存储 key 或覆盖语义中明确。

## 十七、运行时结构与存储结构分开

运行时校验需要丰富字段：

```text
标题、正文、多个字数来源、封面、主题、状态……
```

持久化排障只保留：

```text
activity_id / user_id / post_id
valid / score / reason
source / log_id / processed_at
expected_topic / actual_topics
word_source / effective_words / min_words
require_image / has_image
status / book_id
```

写入前转换成 compact DTO，避免直接序列化整个运行时对象。

## 十八、为什么配置清理不能替代代码

```text
配置：决定哪些活动启用该能力
活动状态：决定现在是否允许处理
```

配置可能：

- 清理延迟；
- 人工遗漏；
- 缓存旧值；
- 被误重新开启。

生命周期判断必须属于消费者自己的安全边界。

## 十九、锁为什么不能解决这个问题

分布式锁只避免同一活动和帖子被多个实例同时处理。

活动结束后每个不同帖子仍会获得自己的锁并执行。锁降低并发重复，不判断业务是否应该发生。

## 二十、消息幂等还需要什么

这次修复重点是活动生命周期和写量，但完整消费者还应考虑：

- 积分写入按 event_id 或业务键幂等；
- 更新事件覆盖旧状态，而不是重复累计；
- 删除事件撤销已有积分；
- MQ 重试不会重复报名或发奖；
- 处理结果可查询。

不能因为增加当前时间 guard 就宣称整个消费链路“exactly once”。

## 二十一、可观测性

建议指标：

```text
post_events_received
activities_considered
activities_skipped_not_running
activities_skipped_outside_window
processors_started
locks_acquired / lock_failed
details_saved_valid
details_saved_invalid_sampled
details_skipped_invalid
score_writes
```

按 activity_id、reason 和 event_source 做有限维度聚合，避免把 post_id 作为指标标签造成高基数。

## 二十二、结果怎么说

可以确认：

- 已结束活动在 fanout 前被过滤；
- 处理器内部有第二层保护；
- 无效详情由全量写变成配置化确定性采样；
- 存储 payload 缩小到必要归因字段；
- 不再依赖运营及时删除配置才能阻止同类路径。

不能确认：

- 精确 CPU 降幅；
- 精确 Redis 调用下降；
- 精确存储节省。

没有监控数据就不编造。

## 二十三、如果允许补算怎么办

不要删除在线 guard，而是增加显式 backfill 模式：

```text
backfill_job_id
allowed_activity_ids
event_time_range
max_qps
dry_run
idempotency_namespace
operator
```

补算使用独立入口、限流和审计，不与普通 MQ 消费混在一起。

这是合理扩展方案，不是原修复已经实现的部分。

## 二十四、备用的完整口述版

> 我处理过一次社区帖子 MQ 重放导致的写放大。活动已经结束，但历史帖子事件仍在消费。旧逻辑只校验帖子创建时间是否属于活动期，所以历史帖子合法；它没有校验活动当前是否还运行，结果消息继续对活动列表 fanout，获取 Redis 锁、查询报名和帖子详情，并写大对象诊断数据。
>
> 我先沿消息入口追踪完整链路，确认只让运营删配置可以止血，但不能成为系统防线。代码上我做了两层保护：第一层在 activity fanout 前检查当前状态和时间，尽早避免 goroutine、锁和 RPC；第二层保留在社区帖子处理器内部，守住业务不变量，防止未来新入口绕过。
>
> 同时我发现无效帖子也在全量写详细诊断信息，所以把运行时校验结构和持久化结构分开，存储只保留归因需要的字段。有效帖子默认保存，无效帖子只有 debug 开启或命中确定性采样才保存。采样用活动、用户、帖子和失败原因计算稳定哈希，同一条重放消息不会每次随机产生新写入。
>
> 这次提交同时补了生命周期、采样和测试。它没有业务增长数据，但直接阻止了过期活动继续进入 fanout、锁、RPC 和大对象写入。这个案例让我认识到，消息消费者不仅要判断事件当时是否合法，还要判断系统现在是否仍允许产生副作用。

## 二十五、高频追问

### 为什么消息会重复

至少一次投递、重平衡、超时、重试和人工回放都可能导致重复。

### 为什么跳过返回 nil

这是业务预期；返回 error 会让 MQ 再次重试。

### 两层 guard 是否冗余

入口 guard 优化资源，处理器 guard 保护不变量，职责不同。

### 为什么不用帖子 create_time

create_time 只说明事件当时合法，不能说明活动现在仍允许写入。

### 确定性采样的缺点

小样本可能恰好没有命中；需要临时 debug、按原因统计和可调整比例。

### 如何证明修复有效

单测覆盖活动状态和采样；运行时观察 skipped counter、processor 数和详情写入量；抽样确认过期活动没有锁、RPC 和存储调用。

### 你为什么不直接加一个活动 ID 黑名单

黑名单只解决当前活动，生命周期 guard 解决同类系统问题。
