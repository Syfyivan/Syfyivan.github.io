服务端学习不能停在“本地能跑”。真正的服务要在生产环境里稳定运行，能配置、能发布、能回滚、能观测、能压测、能在依赖故障时降级。部署运维就是把代码安全地变成线上服务的过程。

这一阶段的目标是建立生产意识：任何变更都要控制影响面，任何故障都要能恢复。

## 从本地到线上发生了什么

本地运行通常是：

```text
go run main.go
```

线上运行则涉及：

```text
build
  -> image
  -> config
  -> deploy
  -> health check
  -> traffic
  -> monitor
  -> rollback
```

每一步都可能出问题。比如镜像构建用了错误版本，配置缺失，数据库地址指错，健康检查过早通过，灰度流量太大，回滚时 schema 不兼容。

## 必须掌握的知识点

### 配置管理

配置应该和代码分离。常见配置包括：

- 数据库地址；
- Redis 地址；
- MQ topic；
- RPC 超时；
- 限流阈值；
- 功能开关；
- 密钥和 token。

配置要满足：

- 不同环境隔离；
- 敏感信息不进代码仓库；
- 变更可审计；
- 出错可回滚；
- 服务启动时校验必需配置。

不要在代码里写死生产地址，也不要把密钥放进配置文件提交。

### 容器化

容器化不是只会写 Dockerfile。服务端容器至少要关注：

- 多阶段构建，减小镜像体积；
- 非 root 用户运行；
- 健康检查；
- 优雅退出；
- 日志输出到 stdout；
- CPU 和内存限制；
- 镜像版本可追踪。

Go 服务优雅退出尤其重要。收到停止信号后，应该停止接收新请求，等待正在处理的请求完成，关闭数据库和 MQ 连接。

### 健康检查

健康检查通常分两类：

- liveness：进程是否还活着；
- readiness：是否可以接流量。

服务刚启动时，可能进程活着，但配置没加载好、数据库连接没建立、缓存预热没完成，这时 readiness 不应该通过。

也不要把健康检查设计得太重。如果每次健康检查都查数据库，可能在故障时进一步放大压力。

### 发布策略

常见发布方式：

- 滚动发布：逐批替换实例；
- 蓝绿发布：新旧两套环境切流；
- 灰度发布：先给一小部分流量；
- 金丝雀发布：用少量真实流量验证。

发布的核心是控制影响面。任何新版本都可能有 bug，所以要先让少量实例或少量用户验证，再逐步扩大。

### 回滚

回滚不是“重新发旧代码”这么简单。真正需要考虑：

- 旧代码是否兼容新数据库结构；
- 新版本写入的数据旧版本能不能读；
- 配置是否也要回滚；
- MQ 消息格式是否兼容；
- 缓存结构是否变化。

这也是为什么数据库迁移要拆步骤：先兼容，再切换，再清理。

### 压测和故障演练

压测要回答：

- 单接口极限 QPS；
- 核心链路容量；
- P95/P99 延迟；
- 数据库和缓存瓶颈；
- MQ 堆积速度；
- 扩容是否有效。

故障演练要回答：

- Redis 不可用怎么办；
- 数据库变慢怎么办；
- 下游 RPC 超时怎么办；
- MQ 消费堆积怎么办；
- 某个机房故障怎么办。

演练不是为了制造麻烦，而是提前知道系统会怎样失败。

## 练习方式

把任务系统生产化：

- 写 Dockerfile；
- 用 docker compose 启动 API、数据库、Redis、MQ；
- 支持环境变量配置；
- 增加 `/healthz` 和 `/readyz`；
- 支持优雅退出；
- 写启动时配置校验；
- 加一个限流配置；
- 模拟发布新版本和回滚；
- 压测任务创建和任务列表接口；
- 模拟 Redis 挂掉时降级查库。

完成后，你会发现“能跑”和“能上线”之间差了一整套工程能力。
