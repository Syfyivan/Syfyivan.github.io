## AI 观察

### 1. agent 一旦能被远程控制，核心问题就从“会不会做”变成“能做到哪里”

今天 Claude 群里最有价值的讨论不是某个模型排行榜，而是一个很具体的问题：电脑端通过 SSH 连接 devbox 后能新建任务，手机端却看不到同一个 session；群友继续比较 Codex remote control 的速度和能否连接多台设备。这说明 agent 产品已经从“在当前终端里聊天”变成“跨设备观察并接管一项持续工作的任务”。

远程控制会放大三类边界问题：任务究竟在哪台机器执行，当前账号拥有哪些文件和网络权限，以及手机上的“批准/继续”对应的是哪一个版本的任务。如果这些信息没有进入统一的任务状态，客户端显示的只是一个聊天窗口，用户却在操作一个可能修改代码、调用外部服务的后台进程。

OpenAI 对 Codex app 的公开介绍把多线程、并行 agent、worktree 和 diff 审阅放在同一套工作流里；移动端说明则把“查看进展、审阅结果、改变方向、批准下一步”描述成远程协作的基本动作。由此可以得到一个工程判断：远程控制不是简单把桌面 UI 缩小到手机，而是把任务、权限、证据和恢复点做成跨端协议。

### 2. 隔离的价值，是把“模型犯错”限制成“一个工作区里的失败”

Claude 日报把 v2.1.222 的 worktree 隔离扩展、SendMessage 权限分类和 Write 工具说明并列记录，方向很一致：限制 agent 的作用域，并让副作用对用户可见。版本页公开的说明还包括修复主仓库破坏性 git 命令绕过隔离、修复后台任务绕过工具限制等内容；这类变化比单纯增加一个快捷按钮更值得工程团队关注。

Anthropic 的 containment 工程文章把防御拆成运行环境、权限/监督以及外部攻击面，并强调文件系统边界和网络出口边界要一起设计。它给出的实际教训是：只要凭证没有进入沙箱，很多“模型、用户或攻击者试图取走凭证”的路径都会被环境层截断。对任何能接入 devbox、代码库或公司工具的 agent，这比“提示词里提醒它不要做危险操作”更可靠。

因此，隔离不是为了让 agent 变得不能用，而是为了让自动化可以更大胆地运行：任务可以在 worktree 或临时环境中继续，用户只需要在真正越过边界时介入。可用性和安全性在这里不是二选一，前提是边界由运行时强制执行，而不是只靠模型自觉。

### 3. Skill 和文档读写需求，暴露的是能力分发与权限治理问题

Codex 群里今天的两条消息分别问“有没有比较好的 Codex Skill 集合”和“Codex 接入飞书后能否直接读写改删文档”。它们看起来是教程需求，实质上对应 agent 进入团队环境后的两个关键问题：能力如何复用，外部写操作如何被授权和审计。

Skill 不应只是一个提示词仓库。它至少要声明允许访问的目录、工具和网络域名，写操作是否需要审批，完成需要哪些证据，以及失败如何恢复。飞书文档这类外部系统还要把“能读”与“能写、能删”分开建模，把操作者、目标文档、变更摘要和回执绑定到任务，而不是把一个通用的 MCP 或 API token 交给 agent。

这也回应了今天日报中对 SendMessage 权限分类的关注：当 agent 可以把任务派给另一个 session 时，权限检查不能只发生在最初创建任务的地方，分发、工具调用和外部写入都需要重新确认作用域。

## 前端 / 服务端 / 客户端工程观察

### 前端：远程控制界面要展示“状态 + 边界 + 证据”

手机端最重要的不是复刻桌面端所有按钮，而是让用户在很小的屏幕上判断当前动作是否安全。任务卡至少应该显示：执行设备或 devbox、工作区/worktree、当前 agent 和模型、最近一次工具动作、是否等待审批、最后验证到哪一步，以及继续操作会产生什么副作用。

“正在运行”不够用。前端应区分 `执行中`、`等待工具`、`等待审批`、`等待重新认证`、`可安全恢复`、`验证中` 和 `已交付`。如果移动端暂时看不到桌面端创建的 session，界面也应明确显示同步延迟、账号/工作区不一致，还是任务确实没有被服务端接收，不能用空列表制造“任务消失”的错觉。

### 服务端：任务必须有单一事实源，外部写操作必须幂等

服务端应把 `task_id`、执行环境、worktree、用户/工作区、模型、权限快照、最近成功事件和恢复点写进同一条任务状态流。桌面端、CLI、IDE 和手机端都读取这条状态，而不是各自维护一个本地 session 列表。

远程批准尤其需要幂等键：用户在手机上点了一次“继续”，网络超时后再次点击，服务端要能判断是重复确认、状态已推进，还是第一次请求根本没有送达。所有涉及飞书文档、代码推送、部署或其他外部写入的动作，都应返回“已受理/已执行/回执丢失/可安全重试”的明确状态。

### 客户端：多设备控制面不是消息同步，而是责任同步

今天群里的 devbox 和手机讨论，说明客户端要同步的不只是文本和通知，还包括任务责任：谁批准了哪一个动作，批准时看到的 diff 或计划是什么，执行在哪台设备，当前是否仍在同一个工作区，以及断线恢复会不会重复执行。

OpenAI 的公开说明把移动端定位为远程查看、审阅、改变方向和批准的入口，这些动作都应该指向同一个可审计的任务事件。对客户端实现而言，最小闭环可以是：`发现任务 → 查看范围 → 查看待执行动作 → 明确批准 → 观察执行 → 查看验证证据`。缺少最后一步，手机端只能证明“点过按钮”，不能证明“结果已交付”。

## 值得跟进的动作

1. 为 Codex/Claude Code 类任务定义一份跨端状态协议，至少包含 `task_id`、执行环境、worktree、权限快照、当前阶段、最后成功事件、恢复点和验证结果。
2. 给 Skill 增加权限和证据元数据：可读写目录、允许的网络域、外部系统操作、审批点、幂等要求、完成命令和回滚方式。
3. 选一个 devbox 远程控制场景做断线演练：桌面端创建任务、手机端发现任务、重复批准、切换设备、工具超时和从恢复点继续，都要留下可核验事件。
4. 把“读飞书文档”和“修改/删除飞书文档”拆成不同能力，先用只读任务验证身份、目标资源和回执，再为写操作增加人工确认、变更摘要和审计记录。
5. 在 agent 页面增加一块“为什么现在不能继续”的解释区，区分权限不足、任务不在当前工作区、设备离线、模型限流、外部工具失败和正在等待人工批准。
