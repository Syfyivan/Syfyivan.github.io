王国东边有一座旧城，城门口挂着三块木牌。第一块写着税册，第二块写着仓单，第三块写着巡夜记。每块牌子下面都站着一位抄写员，人人都说自己记得很清楚，人人也都只记得自己那一摊。

新来的总管第一次巡城时，发现同一件事被问了三遍。粮食为什么晚到，税额为什么改了，桥为什么还没修好，三位抄写员各自能翻出一页纸，却没人能说清这一页纸和前后一串争论有什么关系。

后来，国王让人把旧箱子里的信件、会记、批注和口头承诺都收拢起来。新的档案馆不只存纸，还给每张纸写来处、写负责的人、写什么时候该作废。城里的争吵并没有立刻消失，但至少下次再问“为什么”，有人能把前因后果一起翻出来了。

## 概念揭晓

这篇对应的是 [Harness 101：Company Brain](https://my.feishu.cn/wiki/OAagwqqaUi3bxwkHAjYc6TFsnoY)。

它讲的不是“给公司加一个更好搜的资料库”，而是给组织装一层能被带回决策现场的记忆基质。原文的核心分成三层：事实记忆、交互记忆、行动记忆。后两层不是附属品，而是让记忆真正进入协作和决策的关键。

## 公司为什么不是“有资料”就有记忆

最常见的错觉是：把文档、邮件、工单和消息接起来，就等于组织有了记忆。实际上，这通常只做到检索。

检索回答的是“哪段内容可能相关”。记忆回答的是“这件事在组织里意味着什么”。

同一句话，放在不同角色、不同时间、不同任务里，含义会变。客户说“我们可以下季度再说”，对销售可能是风险，对产品可能是优先级信号，对工程可能是交付窗口，对管理层可能是战略变化。只会找片段，不会解释含义，就还没有真正的组织记忆。

## 三层记忆的分工

原文把 Company Brain 拆成三层，不是为了起三个漂亮名字，而是为了把组织记忆拆到可实现的粒度。

| 层级 | 主要回答 | 典型内容 |
| --- | --- | --- |
| 事实记忆 | 发生了什么 | 客户承诺、负责人、配置、变更、来源 |
| 交互记忆 | 为什么这样决定 | 会议争论、折中方案、反对意见、条件 |
| 行动记忆 | 下一步怎么协同 | 推进、等待、确认、升级、停止 |

这三层对应的不是三类文本，而是三类任务。事实负责可追溯，交互负责可解释，行动负责可协调。

## 事实记忆要存什么

事实记忆最容易被误解成“把所有东西都收进来”。更稳妥的做法是把它当成带元数据的条目，而不是一段裸文本。

一个事实节点至少要有这些信息：

| 字段 | 作用 |
| --- | --- |
| `source` | 事实从哪里来，能不能回看原始证据 |
| `owner` | 谁对它负责，谁能确认它 |
| `timestamp` | 它是什么时候产生或更新的 |
| `permission` | 谁能看原文，谁只能看摘要 |
| `freshness` | 它现在还有效吗 |
| `confidence` | 系统对这条事实有多确定 |
| `relationship` | 它和哪些项目、承诺、风险相连 |
| `provenance` | 这条事实怎么进入系统、后来有没有被推翻 |

原文特别强调 provenance。没有来源链的事实，只是一条断言；有来源链的事实，才算可审计、可回放、可质疑。

## 交互记忆要保留什么

交互记忆保存的不是完整录音稿，而是决定是怎么长出来的。

重要的不是“谁说过什么”，而是“谁在什么条件下接受了什么结论”。会议里的一句“可以，但前提是法务签字”，邮件里的一句“先按这个折中方案走”，Slack 里的一句“先别排优先级”，都比一段压缩后的总结更接近真实决策。

这层最难的地方在于边界。不是所有话都该变成组织资产，不是所有私人犹豫都该公开，不是所有讨论都该对所有角色可见。好的交互记忆既要能重读过去，也要避免把组织变成一台无处不在的记录机器。

## 行动记忆怎样推动下一步

如果前两层只负责“存”和“懂”，那系统还只是档案馆。行动记忆的目标是把记忆变成下一步协同。

它更像一个协调层，不是一个固定流程引擎。固定流程要求路径明确：A 发生，B 执行。行动记忆面对的往往是路径不完整、owner 不明确、承诺有条件、风险在累积的局面。它要做的是把合适的人、证据和下一步带回现场。

常见的下一步不只是“执行”，还包括：

- 继续推进
- 等待确认
- 请求补证据
- 上报风险
- 暂停行动
- 重新询问原始决策人

这也是原文里最有价值的判断之一：有了行动记忆，组织不只是“记得住”，而是“知道该怎么继续走”。

## 一个最小可行的实现骨架

如果真要落地一个最小版本，顺序不该从聊天框开始，而该从记忆底座开始。

1. 先建 `event log`，所有输入都先做追加写入。
2. 抽取器不要直接写真值，先写 `claim`，保留证据和置信度。
3. 检索要同时用 embedding 和图谱遍历，前者找候选，后者补上下文。
4. 权限层要单独存在，别等上线后再补。
5. 动作路由先只做低风险建议，例如生成摘要、提醒待办、标记冲突、请求确认。

这个骨架对应的其实是一条 trust curve。先让系统能回放，再让它能解释，最后才让它能建议或动作。
