前面讲了多 Agent 怎么强。这一篇专门泼冷水：它很贵、有边界、有一堆反模式。Anthropic 反复强调一句原则——**能简单就别复杂，只在确实改善结果时才加复杂度**。这一篇帮你判断“值不值”。

## 先算账：多 Agent 有多贵

Anthropic 给的 token 量级对比，是最该记住的数字：

```text
普通聊天          ：基准 1×
单 agent（带工具）：约 4×   普通聊天的 token
多 agent 系统     ：约 15×  普通聊天的 token
```

> Agent 大约用掉聊天 4 倍的 token；多 agent 系统大约用掉 15 倍。

在 BrowseComp 评测上，他们还发现**单是 token 用量就解释了 80% 的表现差异**。换句话说，多 agent 强，很大程度上是“用钱堆出来的”——你是在拿成本换深度和把握。

所以截图里那个 `max-effort`、`60 agents` 不是日常配置，是“这个 PR 很重要，值得砸资源”时才开的档位。

## 收益从哪来：并行 + 隔离

代价之外，收益也实打实（第 01、04 篇的数据）：

- 内部研究评测，多 agent 比单 agent 高 **90.2%**；
- 复杂查询靠并行最多砍掉 **90%** 耗时（总耗时取最慢而非相加）；
- 上下文隔离让主 agent 不被噪音淹没。

**一句话权衡**：多 agent 用 15× 的 token 和更高的协调复杂度，换“单 agent 上下文根本装不下、或一个视角根本看不全”的任务能被做完、做好。

## 适合 / 不适合：一张判断表

| 适合多 Agent | 不适合多 Agent |
| --- | --- |
| 开放式、步骤无法预知（深度研究） | 步骤固定、可预测（用 workflow 更稳更省） |
| 信息量大、且大部分最终没用（海里捞针） | 信息少、一个上下文就装得下 |
| 子任务能并行、互相独立 | 强串行依赖，下一步要等上一步 |
| 需要多视角交叉验证 | 需要所有 agent 共享同一份实时上下文 |
| 任务价值高，付得起 15× 成本 | 对成本/延迟极敏感的高频小任务 |

Anthropic 自己的判断标准很直白：多 agent 适合“**广度优先、能切成互不依赖的并行块、且值得砸 token**”的查询；反过来，大多数写代码场景因为强依赖、要共享上下文，**并不适合**简单粗暴地拆多 agent。

## 反模式：真实踩过的坑

Anthropic 复盘里的翻车案例，每一个都值得贴墙上：

- **分工没说清 → 重复劳动**：一个子 agent 去查 2021 年芯片危机，另两个重复查 2025 供应链，谁也没分到该干的。**解药**：每个子 agent 必须有目标、输出格式、工具/来源指引、清晰边界。
- **不分轻重 → 杀鸡用牛刀**：给简单问题派 50 个子 agent、无限去找不存在的来源、互相干扰。**解药**：把“按复杂度分配工作量”写进提示——简单查询 1 个 agent，复杂的才 10+。
- **错误累积 → 小故障变灾难**：agent 有状态、非确定，早期小偏差会被后续放大。**解药**：验证（第 05 篇）+ 渐进部署。
- **协调与合成难**：并行产出一堆碎片，reduce/合成这一步本身可能丢细节或成瓶颈。**解药**：留专门的合成阶段，别指望“拼起来就行”。

## 并发不是无限的

“同时开很多 agent”也有物理上限：

- **并发数有上限**：同一时刻能跑的 agent 数受运行时/资源限制（常见十几个一批，做完一个补一个），不是你写 100 个就 100 个一起跑。
- **总数有上限**：编排框架通常设一个总量上限（防止失控循环），几百个就该重新想想是不是拆错了。
- **合成是瓶颈**：agent 越多，最后去重、排序、合成的负担越重。

## 一句话总结

多 Agent 是“用 15× 的 token 换深度和把握”的重武器：适合开放、海量、可并行、价值高的任务，不适合可预测、强依赖、要共享实时上下文、对成本敏感的活。上之前先问三句——**任务真的开放吗？拆得开吗？值这个钱吗？** 三个“是”才上，否则一个好 agent + 检索往往更对。
