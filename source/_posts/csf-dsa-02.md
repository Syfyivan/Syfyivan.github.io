<div class="csf-key-note">📍 <b>一句话点题：</b>数组和链表是装数据的两种"队形"。数组让所有人挨着站成一排，所以你能瞬间点到第 5 个人；链表让每个人手里牵着下一个人，谁也不用挨着站，所以队首插队特别快。<br>这一讲我们就把这两种队形在内存里到底长什么样、各自快在哪慢在哪，亲手写代码摸清楚。</div>

上一讲《复杂度直觉：大 O 是怎么估出来的》里，我们学会了用大 O 给一段代码的快慢"估个量级"。但你可能心里还有个疙瘩：**为什么"按下标取一个元素"是 O(1)，而"在开头插一个元素"却可能是 O(n)？** 这背后的真正原因，不在算法里，而在**数据是怎么摆在内存里**的。

这一讲我们就掀开盖子，看看数据在内存里到底怎么排队。这是整门课第一个真正的"数据结构"，往后的栈、队列、哈希、树，全都是从这两种排队方式长出来的。

## 🎯 这一讲你会学到什么

- **内存是什么样的**：为什么"连续"和"不连续"会带来天壤之别的速度。
- **数组**：为什么按下标访问能做到 O(1)（随机访问），又为什么在开头增删那么贵。
- **链表**：用"指针/引用"把节点一个个串起来，为什么开头插入能做到 O(1)，但按下标查找却要 O(n)。
- **一个关键澄清**：Python 的 `list` 其实**不是**链表，它是"动态数组"。这个误会坑过无数初学者。
- **怎么选**：拿到一个问题，怎么判断"该用数组还是链表"。

<div class="csf-note">⚠️ <b>开门见山的约定：</b>这一讲有一个手写单链表的练习，是这门课第一个"必须自己敲"的硬骨头。<b>请务必自己写</b>，写到能跑通、能打印出来为止。链表写错时那种"明明逻辑对了却打印不出来"的抓狂，是每个程序员的成人礼——让 AI 替你写，你就把这份成人礼跳过了，亏的是自己的判断力。AI 可以在你卡住后给你<b>讲解</b>，但第一版代码，自己来。</div>

## 🛠 跟我做

### 第一步：先在脑子里画出"内存"<span class="csf-b csf-core">必读</span>

你可以把内存想象成一条**超长的储物柜走廊**，每个柜子大小一样，从 0 号开始编号：0、1、2、3……每个柜子能放一个值。柜子的编号就叫**地址**。

这里要先认识一个角色：**CPU**。它就是电脑里负责算东西、干活的"大脑"，我们写的程序最终都是它在执行。这个大脑有个特异功能：**只要你报出柜子编号，它能瞬间走到那个柜子**，不管这个柜子是 5 号还是 500 万号，花的时间几乎一样。这就是所谓的"随机访问"——"随机"在这里不是"随便乱来"的意思，而是"任意位置都能一步到位"。

记住这个走廊的画面，下面所有快慢的解释，都能用它说清楚。

### 第二步：体会数组——"挨着站成一排"<span class="csf-b csf-key">重点</span>

**数组**的核心规则只有一条：**所有元素在内存里挨着放，占用一段连续的柜子。**

假设有个数组 `[10, 20, 30, 40]`，从 100 号柜子开始放（每个值占 1 个柜子）：

```text
柜子编号:  100   101   102   103
存的值:    10    20    30    40
下标:       0     1     2     3
```

现在问你：我想取下标为 2 的元素，CPU 怎么做？它不用一个个数过去，而是**直接算**：起始地址 100 + 下标 2 = 102 号柜子，一步到位。

<div class="csf-why">💡 <b>这就是 O(1) 随机访问的秘密：</b>因为元素是连续摆放的，第 i 个元素的地址 = 起始地址 + i × 每个元素的大小。<br>别被"× 每个元素的大小"吓到——在我们这个柜子的例子里，每个值正好占 1 个柜子，所以"大小"就是 1，地址就是 100 + 2×1 = 102，和前面"100 + 下标 2"算出来完全一样。<br>那为什么不直接写成"+ 下标"、非要乘一下？因为真实内存里，有的值占的格子多、有的占得少（比如一个大数字可能要好几个格子）。写成"× 大小"是为了通用：不管一个值占几个格子，这道乘加法都成立。<br>关键是：这就是一道乘加法，跟数组多长完全无关。数组有 4 个元素还是 400 万个元素，取第 i 个的耗时一模一样。所谓"按下标访问是 O(1)"，本质是"地址能直接算出来"。</div>

我们用 Python 的 `list` 先**体会**这个"按下标一步到位"的感觉（注意：这里只是借 `list` 来感受，后面会专门澄清它的真实身份）：

```python
arr = [10, 20, 30, 40]

# 按下标访问：不管 list 多长，这一步都是 O(1)
print(arr[0])   # 10
print(arr[2])   # 30
print(arr[-1])  # 40（Python 允许负数下标，-1 表示最后一个）
```

**先猜后做：** 在运行下面这段之前，先猜一下 `arr[2]` 会变成几？

```python
arr = [10, 20, 30, 40]
arr[2] = 99      # 把下标 2 的位置改成 99
print(arr)       # 你猜打印出什么？
```

<details class="csf-fold"><summary>揭晓答案<span class="csf-b csf-skim">细究 · 可跳读</span></summary>打印 <code>[10, 20, 99, 40]</code>。把下标 2 处的 30 改成了 99。<br><b>注意"改"和"增删"是两码事：</b>按下标"改值"也是 O(1)，因为它和访问一样，地址能直接算出来，走过去把柜子里的东西换掉就行，不影响其他柜子。真正贵的是"增"和"删"，下面马上讲。</details>

### 第三步：数组的痛点——"在开头插队"<span class="csf-b csf-key">重点</span>

数组按下标查改这么爽，代价在哪？代价在**增和删**，尤其是在**开头**。

回到柜子走廊。数组 `[10, 20, 30, 40]` 占着 100~103。现在我想在**最前面**插一个 5，让它变成 `[5, 10, 20, 30, 40]`。问题来了：100 号柜子已经被 10 占了，5 没地方站。

数组的规则是"必须连续"，所以唯一的办法是：**把 40、30、20、10 全部往后挪一个柜子**，腾出 100 号给 5。

```text
插入前:  100=10  101=20  102=30  103=40
挪动:    每个元素都往后搬一格
插入后:  100=5   101=10  102=20  103=30  104=40
```

如果数组里有 n 个元素，在开头插入就要挪动 n 个元素——这是 **O(n)**。删除开头同理，后面所有元素都得往前补位。

**先猜后做：** 下面用 `insert(0, ...)` 在开头插入，再用 `append(...)` 在末尾追加。你觉得哪个更费劲（对大数组而言）？

```python
arr = [10, 20, 30, 40]

arr.insert(0, 5)   # 在下标 0（开头）插入 5：后面元素都要往后挪
print(arr)         # [5, 10, 20, 30, 40]

arr.append(99)     # 在末尾追加 99：通常不用挪动别人
print(arr)         # [5, 10, 20, 30, 40, 99]
```

<details class="csf-fold"><summary>为什么末尾追加通常很便宜？<span class="csf-b csf-skim">细究 · 可跳读</span></summary>在开头插入要挪 n 个元素（O(n)）；在末尾追加不用挪任何人，所以通常是 O(1)。<br>说"通常"是因为：数组占的那段连续柜子是有限的，追加到塞满时，系统得另找一段更大的连续空间、把老数据整体搬过去，这一次搬运是 O(n)。但这种"扩容"很少发生，把它平摊到每一次追加上，平均仍然接近 O(1)。这个"偶尔贵一次、平摊下来很便宜"的概念叫<b>均摊复杂度</b>，现在有个印象即可，后面讲哈希时还会遇到。</details>

### 第四步：链表——"每个人牵着下一个人"<span class="csf-b csf-core">必读</span>

数组的麻烦根源是"必须连续"。**链表**换了个思路：**元素可以散落在内存的任意角落，不用挨着；每个元素额外记一个"下一个元素在哪"。**

链表里的每个元素，我们叫它**节点（Node）**。一个节点装两样东西：

1. `val`：自己存的值；
2. `next`：一个**指针 / 引用**，指向下一个节点（是谁牵着的下一只手）。

最后一个节点的 `next` 指向 `None`（空），表示"队伍到此为止，后面没人了"。

```text
[5 | →] ──→ [10 | →] ──→ [20 | →] ──→ [30 | None]
 头节点                                  尾节点(next 是 None)
```

<div class="csf-note">🔑 <b>"指针 / 引用"是什么？</b>你先别被这个词吓到。它就是"一张写着地址的便利贴"。节点 A 的 <code>next</code> 不是把节点 B 装在自己肚子里，而是贴了一张便利贴："下一个在 B 那儿"。想找下一个，照着便利贴走过去就行。Python 里这种"贴便利贴"的关系叫<b>引用</b>，效果和 C 语言的"指针"是一回事——都是"我手里攥着另一个东西的位置"。</div>

**链表为什么开头插入快？** 假设要在最前面插一个 0。我们只要：新建一个节点 0，让它的 `next` 指向原来的头节点 5，然后把"头"这个标记改成指向 0。**没有任何元素需要挪动**，改两根"便利贴"就完事——这是 **O(1)**。

但天下没有免费的午餐。**链表想取第 3 个元素，必须从头开始一个一个数过去**：从头节点出发，照着 `next` 走，走 3 步才到。它做不到数组那种"算地址一步到位"，因为节点散落各处，地址没法算。所以**链表按下标查找是 O(n)**。

这正好是数组的镜像：数组查得快、开头增删慢；链表开头增删快、查得慢。

### 第五步：亲手写一个单链表<span class="csf-b csf-core">必读</span>

下面是这一讲的硬核练习。**请你先自己写，写不出来再看我的版本。** 我们要实现：定义节点、在开头插入、遍历打印。

先想清楚结构，再动手。一个节点就是一个小盒子，装 `val` 和 `next`。

下面这段代码第一次出现了 `class`、`def __init__`、`self` 这三个词，它们对没碰过编程的人最唬人，所以我先用大白话把它们讲清楚，你再往下看代码就不慌了：

- **`class` 是"造盒子的图纸"。** 它本身不是一个盒子，而是一张图纸。按这张图纸，我们能造出很多个长得一样的盒子（也就是一个个节点）。这里我们给图纸起名叫 `Node`。
- **`def __init__` 是"造盒子时自动执行的装配说明"。** 每次照图纸造一个新盒子，这段说明就会自动跑一遍，负责把盒子里该放的东西摆好。`__init__` 前后那两个下划线是 Python 的固定写法，表示"这是造东西时自动调用的特殊方法"，照抄即可，不用纠结。括号里的 `val` 是你造盒子时递进去的值。
- **`self` 就代表"正在造的这一个盒子自己"。** 所以 `self.val = val` 的意思是：把你递进来的那个值（右边的 `val`），存进这个盒子自己的 `val` 格子里（左边的 `self.val`）。两个 `val` 一个是"递进来的料"、一个是"盒子上的格子名"，名字一样只是为了好记。

```python
class Node:
    def __init__(self, val):
        self.val = val      # 把递进来的值，存进这个节点自己的 val 格子
        self.next = None    # 指向下一个节点，默认还没接上，是 None
```

然后是链表本身。链表只需要攥住一个东西：**头节点 `head`**。顺着头节点的 `next`，就能摸到整条链。

```python
class LinkedList:
    def __init__(self):
        self.head = None    # 空链表，头是 None

    def push_front(self, val):
        """在开头插入一个值（头插），O(1)"""
        node = Node(val)        # 1. 造一个新节点
        node.next = self.head   # 2. 新节点牵住原来的头（关键：先接上后面）
        self.head = node        # 3. 把头标记改成新节点

    def print_all(self):
        """从头到尾遍历打印，O(n)"""
        cur = self.head         # 从头节点开始
        parts = []
        while cur is not None:  # 只要还没走到尽头
            parts.append(str(cur.val))
            cur = cur.next      # 关键：顺着便利贴走到下一个
        print(" -> ".join(parts) + " -> None")
```

最后那两行（`parts.append(...)` 和 `print(" -> ".join(...))`）也有几个新写法，挨个说一下，免得你"跑出来了却不懂为什么这么写"：

- **`str(cur.val)`** 是把节点里存的值转成"文字"。值有可能是数字（比如 `10`），而我们最后要把它们拼成一句话，所以先用 `str()` 把数字变成文字 `"10"`。
- **`parts`** 是一个"清单"（一开始 `parts = []` 就是个空清单），`parts.append(...)` 表示往这个清单的末尾添一项。遍历一圈下来，每个节点的值的文字都被攒进了 `parts`，比如变成 `["10", "20", "30"]`。
- **`" -> ".join(parts)`** 是把清单里的文字，用 `" -> "` 这个箭头当连接符，串成一整句话——`["10", "20", "30"]` 就被串成 `"10 -> 20 -> 30"`。最后再在末尾接上 `" -> None"`，打印出来就是 `10 -> 20 -> 30 -> None`，正好画出整条链。

<div class="csf-note">🧠 <b>停一下，盯住 push_front 的三行顺序。</b>第 2 步和第 3 步<b>绝对不能换序</b>。如果你先做第 3 步（<code>self.head = node</code>），原来的头就再也没人牵着了，后面整条链当场丢失。必须<b>先让新节点接住旧链，再移动头</b>。这是链表最经典的"接指针"陷阱，写之前就在心里过一遍。</div>

**先猜后做：** 我们依次头插 30、20、10，再打印。注意是"头插"——每次都插在最前面。你先猜打印结果是 `10 -> 20 -> 30` 还是 `30 -> 20 -> 10`？

```python
ll = LinkedList()
ll.push_front(30)
ll.push_front(20)
ll.push_front(10)
ll.print_all()      # 你猜是什么顺序？
```

<details class="csf-fold"><summary>揭晓答案 + 为什么<span class="csf-b csf-skim">细究 · 可跳读</span></summary>结果是 <code>10 -> 20 -> 30 -> None</code>。<br>因为每次都插在<b>开头</b>：先放 30（链是 30），再头插 20（变成 20→30），再头插 10（变成 10→20→30）。最后插进去的反而排在最前面——这种"后进先出"的味道，正是<b>下一讲"栈"</b>的影子，你已经提前摸到了。</details>

把上面 `Node`、`LinkedList` 和这段测试代码拼在一起，存成一个 `.py` 文件跑起来。如果你看到 `10 -> 20 -> 30 -> None`，恭喜，你亲手让数据在内存里串起来了。

<div class="csf-note">✋ <b>小建议：这段链表自己敲一遍最划算。</b>哪怕照着抄，也试着一行行理解着抄，抄完把代码盖住、自己默写一遍 <code>push_front</code>。自己亲手把指针接通一次，那种"接指针"的手感才会长在你身上——往后再看链表代码，你一眼就能看出链有没有接断。这门课想帮你练出来的，正是这份"看得出来"。</div>

<details class="csf-fold"><summary>进阶挑战预告：尾插和"打印不出来"<span class="csf-b csf-skip">选学</span></summary>如果你想再进一步，可以试着实现 <code>push_back</code>（在<b>末尾</b>插入）。你会发现它没那么轻松：单链表只攥着 head，想到末尾得先从头走到尾（O(n)），再把最后一个节点的 next 接上新节点。这也解释了为什么很多链表会额外再存一个 tail 指针。<br>另外，新手实现尾插时极容易写出"什么都打印不出来"的 bug——往往是漏了"链表为空时 head 还是 None"这个边界，或者忘了把新节点接上去。遇到了别慌，这就是下面"翻车现场"要讲的。</details>

## 💡 自己复述一遍

合上屏幕，用一句话回答："数组和链表，到底差在哪？"

试着说出这个版本：**数组让数据挨着连续放，所以能算地址、按下标一步取到（O(1)），但开头增删要挪一大片（O(n)）；链表让节点散着放、用指针互相牵着，所以开头增删只改几根指针（O(1)），但查第 i 个得从头数过去（O(n)）。**

说得出来，这一讲的内核就拿到了。

## 🔧 翻车现场

**翻车一：以为 Python 的 `list` 就是链表。** <span class="csf-b csf-key">重点</span>

这是最普遍的误会。Python 的 `list` 名字里有个"list"，但它**不是链表，而是动态数组**——底层是一段连续内存，所以 `arr[i]` 才是 O(1)。真正的链表没有"按下标 O(1)"这个能力。

**为什么要在意？** 因为面试和实战里，"用 list 还是用链表"是个真问题。如果你以为 `list` 就是链表，你会对它的性能产生完全错误的预期（比如以为 `list.insert(0, x)` 很便宜，其实它是 O(n)）。记住：**`list` ≈ 数组，查改快、开头增删慢。** Python 标准库里真正偏链表行为的是 `collections.deque`，两头增删都快。

**翻车二：手写链表时漏接 `next`，断链 / 丢节点 / 打印不出来。** <span class="csf-b csf-core">必读</span>

这是写链表的头号 bug，几乎人人都踩。典型有两种：

```python
# 错误写法：顺序反了，旧链丢失
def push_front(self, val):
    node = Node(val)
    self.head = node        # ❌ 先动了 head，旧链没人牵了
    node.next = self.head   # 此时 self.head 已经是 node 自己，node.next 指向自己！
```

上面这段会让新节点的 `next` 指向它自己，打印时陷入死循环（或只打印一个值）。**正确顺序永远是"先让新节点接住旧链，再移动 head"。**

另一种是遍历时忘了往后走：

```python
# 错误写法：忘了 cur = cur.next
while cur is not None:
    parts.append(str(cur.val))
    # ❌ 漏了 cur = cur.next，cur 永远停在头节点 → 死循环
```

<div class="csf-why">🔍 <b>排查口诀：</b>链表 bug 八成出在指针。打印不出来 / 死循环时，按这个顺序查：①遍历里有没有 <code>cur = cur.next</code> 让指针往前走？②插入时是不是"先接旧链、再移动 head"？③空链表（head 是 None）这个边界处理了吗？把这三条过一遍，多数 bug 当场现形。这种"盯着指针走一遍"的调试功夫，比 AI 直接甩给你正确答案值钱得多。</div>

## ✅ 自检三问

1. 数组"按下标访问是 O(1)"，根本原因是什么？（提示：和"连续"与"算地址"有关，别只背结论。）
2. 在一个有 n 个元素的结构里，"在开头插入一个元素"：数组是什么复杂度？链表是什么复杂度？为什么会反过来？
3. Python 的 `list` 是数组还是链表？据此判断：`list.insert(0, x)` 大概是 O(1) 还是 O(n)？

<details class="csf-fold"><summary>对照参考答案<span class="csf-b csf-skim">细究 · 可跳读</span></summary>1. 因为数组元素连续存放，第 i 个的地址 = 起始地址 + i × 元素大小，是一道乘加法，能直接算出来一步到位，与数组长度无关。<br>2. 数组 O(n)（要把后面所有元素往后挪一格腾位置）；链表 O(1)（只新建节点并改两根指针，谁都不用挪）。差别来自"数组必须连续、链表可以散放"。<br>3. <code>list</code> 是动态数组（不是链表）。所以 <code>insert(0, x)</code> 要把后面所有元素往后挪，是 O(n)；而 <code>append(x)</code> 通常是 O(1)。</details>

## 🚀 挑战

给你的 `LinkedList` 再加一个方法 `find(val)`：从头遍历，找到第一个值等于 `val` 的节点就返回它在第几个位置（从 0 数起），找不到就返回 `-1`。

**要求：自己写**，写完用下面的用例自测；先猜每行会打印什么，再运行核对。

```python
ll = LinkedList()
ll.push_front(30)
ll.push_front(20)
ll.push_front(10)   # 此时链是 10 -> 20 -> 30

print(ll.find(20))  # 先猜：应该返回几？
print(ll.find(99))  # 先猜：找不到返回几？
```

写的时候记住"翻车现场"的口诀：遍历里别忘了 `cur = cur.next`，还要数着走了几步。卡住了，可以让 AI **给你讲思路、帮你看 bug**，但**别让它直接把 `find` 写出来**——这道题的价值，全在你自己把指针走通的那一刻。

<details class="csf-fold"><summary>想验证答案就点开（建议自己先写完再看）<span class="csf-b csf-skip">选学</span></summary>链是 10 -> 20 -> 30，所以 <code>find(20)</code> 返回 <b>1</b>（20 在第 1 位，从 0 数起）；<code>find(99)</code> 返回 <b>-1</b>（不存在）。参考实现：从 head 出发，用一个计数器 idx 从 0 开始，每走一步 idx 加一，<code>cur.val == val</code> 时返回 idx，走到 None 还没找到就返回 -1。</details>

## 📦 复制带走

<div class="csf-card">🎒 <b>这一讲装进口袋的四句话：</b><br>1. <b>数组 = 连续摆放</b>：按下标查 / 改是 O(1)（地址能直接算），但开头增 / 删是 O(n)（要挪一大片）。<br>2. <b>链表 = 散放 + 指针牵手</b>：开头增 / 删是 O(1)（只改几根指针），但按下标查是 O(n)（得从头数过去）。两者快慢正好相反。<br>3. <b>Python 的 list 是动态数组，不是链表</b>：所以 <code>insert(0, x)</code> 是 O(n)，<code>append</code> 通常是 O(1)。这个误会一定要破掉。<br>4. <b>链表 bug 八成在指针</b>：插入"先接旧链、再移动 head"；遍历别忘 <code>cur = cur.next</code>；处理好空链表边界。这套排查手感得自己敲出来，AI 替不了。</div>
