> 承上：上一讲我们搭好了「挑毛病、盯流程」的质检班子；可阿萍很快发现，作坊里返工最多的活，问题往往不在手上，而在更早的一张纸上——图纸。

小磊接了个衣柜的活，柜门和柜体一起下料、一起拼。客人验货时说门关不严，他改了门；一改门，柜体的边框跟着歪，他又改柜体；柜体一动，里头的隔板又卡住，第三回连抽屉都得重做。一件衣柜，他返工了三回，急得满头汗。

老周过来看了一眼，没夸也没骂，就指着小磊那张草图说：「你这毛病不在手艺，在图纸。你看你这门，是直接长在柜体上的——门和柜体连成了一块，改个门就得动整个柜体。」

小磊不服：「那别人家的柜子改门咋就不用动柜体？」老周笑了：「因为人家门和柜体之间是**标准榫接口**。门归门，柜体归柜体，各干各的事；要换门，把榫头一拔一插就行，柜体一根木头都不用动。你这张图，是把『关门』『撑架子』『放隔板』全塞在一处了——一个部件管了太多事，自然牵一发动全身。」

老周又补了一句他常念叨的话：「好家具不是靠手快磨出来的，是**先把图纸画好**画出来的。骨架对了，接口对了，后面下料、拼装、改活都省事；骨架错了，手艺再好也是白返工。」

阿萍在旁边点头：「我验货验多了就明白一个理——一大半返工，其实在画图那一步就埋下了。图纸阶段改一笔，比成品砸了重做便宜太多。」

## 概念揭晓

老周这张「图纸」，在软件里就是**软件设计**——把客人的需求，变成一张能照着干活的「软件骨架图」。

- 小磊那扇「长在柜体上的门」，是**高耦合**：部件之间黏在一起，改一个就得动一片。
- 老周说的「标准榫接口、门归门柜体归柜体」，是**低耦合 + 高内聚**：每个部件只干一件事，部件之间靠规范接口相连，换一个不动其他。
- 「一个部件管了太多事」，对应面向对象设计里的**单一职责原则**被破坏。
- 「先把图纸画好，骨架对了后面省事」，就是这一讲的总纲：**软件设计处于软件工程的技术核心位置**，设计质量决定了后面编码、测试、维护省不省事。

## 软件设计是什么

**软件设计**是把软件需求转换为软件表示的过程，也是将用户需求准确转化为软件系统的**唯一途径**。它分两个阶段，就像老周先画整体骨架、再画每个榫头的细节：

1. **高层次设计（体系结构设计）**：把需求转成数据结构和软件的系统结构，定义子系统以及它们之间的通信/接口。——画衣柜的整体骨架，定好门、柜体、抽屉各是一块，接口怎么对。
2. **详细设计**：对结构细化，得到详细的数据结构和算法，对所有类都详尽描述，给程序员一个清晰的规范说明。——画每个榫头多大、卯眼多深，让下料的人照着做。

## 低耦合、高内聚：这一讲的总指挥棒

软件设计的**基本原则**：始终以质量为目标展开，**设计越简单越好**。它的**指导思想**就两条，正好对应老周的图纸哲学：

- **降低模块耦合度**——部件之间别黏在一起（门别长在柜体上）。
- **提高模块内聚性**——每个部件只干一件事（门只管开关，柜体只管撑架子）。

耦合越低、内聚越高，**模块独立性**就越好，改一处不牵动全身，这就是「图纸画对了后面省事」的本质。

### 耦合性七级（从低到高 = 独立性从高到低，越往后越坏）

| 序 | 耦合类型 | 通俗理解 |
|---|---|---|
| 1 | 非直接耦合 | 两个模块根本不直接打交道（最好） |
| 2 | 数据耦合 | 只通过参数传简单数据 |
| 3 | 特征耦合 | 传了整个数据结构，对方只用其中一部分 |
| 4 | 控制耦合 | 一个模块传「开关标志」去控制另一个模块走哪条路 |
| 5 | 外部耦合 | 多个模块共用外部环境/格式 |
| 6 | 公共环境耦合 | 多个模块共用一块全局数据区 |
| 7 | 内容耦合 | 一个模块直接改另一个模块内部（最坏，像门焊死在柜体上） |

记忆口诀：**非数特控外公内**，越靠后越「黏」，要尽量往前靠。

### 内聚性七级（从低到高 = 独立性从低到高，越往后越好）

| 序 | 内聚类型 | 通俗理解 |
|---|---|---|
| 1 | 偶然内聚 | 一个模块里凑了一堆不相干的事（最差） |
| 2 | 逻辑内聚 | 一类相似的事放一起，靠参数挑着做 |
| 3 | 时间内聚 | 「同一时间要做的」凑一起（如初始化） |
| 4 | 过程内聚 | 按执行顺序组织 |
| 5 | 通信内聚 | 都操作同一份数据 |
| 6 | 信息内聚 | 围绕同一数据结构、各有出入口 |
| 7 | 功能内聚 | 整个模块就干一件完整的事（最好，像门只管开关） |

记忆口诀：**偶逻时过通信功**，越靠后越「专一」，要尽量往后靠。

## 面向对象设计的技术原则

光知道「低耦合高内聚」还不够，前人把它提炼成几条可操作的**设计原则**，就像老师傅传下来的「画图规矩」：

- **开闭原则**：对**扩展开放**、对**修改关闭**。要加新功能就新写组件去扩展，不要去改原来跑得好好的代码。——加个新款门，别去锯柜体。
- **单一职责原则**：一个类只有**一个引起它变化的原因**；如果多于一个动机要改它，就该拆成多个类各管一职。——这正是小磊那扇「又管开关又管撑架」的门犯的错。
- **里氏代换原则**：任何**基类可以出现的地方，子类一定可以出现**；尽量从抽象类继承，而不是从具体类继承。
- **依赖倒置原则**：**抽象不应依赖细节，细节应依赖抽象**；要**针对接口编程，而不是针对实现编程**。——认的是「标准榫口」，不是某一扇具体的门。
- **接口隔离原则**：按客户需求不同，为不同客户端提供不同的服务（接口要细分，别塞一个胖接口）。
- **合成复用原则**：在新对象里用已有对象、通过委派复用其功能，优先用组合而不是继承。
- **迪米特法则（最少知识原则）**：一个对象应当对其他对象**尽可能少地了解**，少打交道、少依赖。

## 软件体系结构：先定整体骨架

**软件体系结构**为系统提供结构、行为和属性的高级抽象，由构件、连接件及其约束组成。它的几种**模型**：

- **结构模型**：以构件、连接件刻画结构，侧重整体结构描述。
- **框架模型**：针对某类特殊问题建结构。
- **动态模型**：是对结构/框架模型的补充，研究系统「大颗粒」的行为（如重新配置）。
- **过程模型**：研究构造系统的步骤和过程。
- **功能模型**：由一组功能构件按层次组成，下层向上层提供服务。

**体系结构分类**（考试常考）：

- **单用户**：整个系统跑在一台机器上，一个用户占全部资源，不共享数据（最早最简单）。
- **C/S（客户机/服务器）**：用户操作模块在客户机，数据存在服务器的数据库里。
- **B/S（浏览器/服务器）**：界面用浏览器实现，少量逻辑在前端，主要逻辑在服务器端。**B/S 是对 C/S 的一种改进**。
- **中间件的多层分布式**：客户端**表示层** + 中间**业务逻辑层** + **数据层**的三层或多层结构；把客户和资源分开，降低服务器负载，不同组件可用不同语言实现。

## 软件设计模式：成套的「做法图谱」

**设计模式**让人更简单方便地复用成功的软件设计和体系结构，帮设计者更快更好地完成系统设计。按目的分**三大类**：

- **创建型模式**（抽象了实例化过程）：抽象工厂、生成器、工厂方法、原型、单件。
- **结构型模式**（用继承组合接口或实现）：适配器、桥接、组合、装饰、外观、享元、代理。
- **行为型模式**（涉及算法与对象间职责分配、通信）：职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者。

## 软件设计优化与典型系统

详细设计落地时要用**结构化设计**：控制结构只用**顺序、选择、循环**三种；用**单入口单出口**；**自顶向下、逐步求精**。常用工具有：流程图、伪码、IPO 图、PAD（问题分析图）、判定表。

典型系统：**J2EE** 是基于 Java 2 平台的多层体系结构（客户层 / Web 层 / 业务逻辑层 / 企业信息系统层）；**.Net** 是 **UI 层 / 业务逻辑层 / 数据层** 三层系统。

## 数据库设计质量与数据字典

数据这块也分三层：**数据层**（数据共享的基础）、**业务层**（负责数据层与表示层之间传输）、**表示层**（客户端，经业务层访问数据库）。

而把数据这件事说清楚的关键工具，是**数据字典**——对**数据项、数据结构、数据流、数据存储、处理逻辑、外部实体**进行定义和描述，目的是对数据流程图中的各个元素做出详细说明。它就是数据这张「图纸」上的标注，标得越准，系统越不容易出岔子。

### 软件设计的目标与两个阶段

> 软件设计是把**软件需求转换为软件表示**的过程，也是将用户需求准确转化为软件系统的**唯一途径**。

两个阶段：
1. **高层次设计（体系结构设计）**：将软件需求转化为数据结构和软件的系统结构，定义子系统及它们之间的通信或接口。
2. **详细设计**：对结构表示细化，得到详细的数据结构和算法，对所有类详尽描述，给程序员清晰的规范说明；即在技术上如何实现已设计好的体系结构。

### 软件设计的基本原则与指导思想

> 设计过程中始终**以质量为目标**展开，**设计越简单越好**。

指导思想：**降低模块耦合度、提高模块内聚性**。

### 耦合性（由低到高 = 模块独立性由高到低）

> **非直接耦合 → 数据耦合 → 特征耦合 → 控制耦合 → 外部耦合 → 公共环境耦合 → 内容耦合**

### 内聚性（由低到高 = 模块独立性由低到高）

> **偶然内聚 → 逻辑内聚 → 时间内聚 → 过程内聚 → 通信内聚 → 信息内聚 → 功能内聚**

### 软件设计的技术原则（面向对象设计原则）

- **开闭原则**：对扩展开放、对修改关闭。「开」指对功能扩展开放，「闭」指对原有代码修改封闭。
- **单一职责原则**：一个类只有一个引起它变化的原因；多于一个动机改变就拆成多个类。
- **里氏代换原则**：任何基类可以出现的地方，子类一定可以出现；尽量从抽象类继承而非具体类。
- **依赖倒置原则**：抽象不应依赖细节，细节应依赖抽象；针对接口编程而非针对实现编程；传参或组合聚合时尽量引用层次高的类。
- **接口隔离原则**：根据客户需求不同，为不同客户端提供不同的服务。
- **合成复用原则**：在新对象里使用已有对象，通过向其委派达到复用已有功能的目的。
- **迪米特法则（最少知识原则）**：一个对象应当对其他对象有尽可能少的了解。

### 软件体系结构的模型与分类

模型：**结构模型、框架模型、动态模型、过程模型、功能模型**。

分类：
- **单用户体系结构**：整个系统运行在一台计算机，一个用户占全部资源，不共享和交换数据。
- **C/S（客户机/服务器）**：用户操作模块在客户机，数据存储在服务器的数据库中。
- **B/S（浏览器/服务器）**：界面通过浏览器实现，少部分逻辑在前端，主要逻辑在服务器端；**B/S 是对 C/S 的一种改进**。
- **中间件的多层分布式**：表示层 + 业务逻辑层 + 数据库服务器的三层或多层；将客户和资源分开，降低服务器负载，不同组件可用不同语言实现。

### 软件设计模式

> 设计模式使人们更简单方便地复用成功的软件设计和体系结构，帮助设计者更快更好地完成系统设计。

三类：
- **创建型**：抽象工厂、生成器、工厂方法、原型、单件。
- **结构型**：适配器、桥接、组合、装饰、外观、享元、代理。
- **行为型**：职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者。

**设计模式的 4 个基本要素**：① 描述模式的问题、解决方案和效果（模式名称/问题）；② 描述应在何时使用模式；③ 描述设计组成部分之间的相互关系、职责和协作方式；④ 描述模式应用的效果及使用模式应权衡的问题。

**UML 的作用**：是一种直观化、明确化、构建和文档化软件系统产物的通用可视化建模语言，可先建模再编码，从一开始保证系统结构合理。

### 软件设计优化

- 模块设计：模块划分合适、模块间有独立性，功能与接口定义正确，数据结构、数据流与控制流定义正确。
- 接口设计：用户接口、硬件接口、软件接口、通信接口设计正确全面，并具有可测试性。
- 详细设计（结构化设计）：控制结构采用**顺序、选择、循环**三种；使用**单入口单出口**；尽量减少 GOTO；用**自顶向下逐步求精**。优点是可读性、可维护性好；缺点是增加存储容量和运行时间（10%-20%）。
- 详细设计工具：**流程图、伪码、IPO 图、PAD（问题分析图）、判定表**。
- 界面设计要求：一致性、自助功能、易懂性、易用性、规范性、帮助设施、美观与协调性、独特性、快捷方式组合、错误保护。

### 典型系统设计

- **J2EE**：基于 Java 2 平台的多层体系结构（客户层、Web 层、业务逻辑层、企业信息系统层）。
- **.Net**：3 层系统——**UI 层、业务逻辑层、数据层**。

### 数据库设计质量与数据字典

三层：**数据层**（数据网络交互共享的基础）、**业务层**（负责数据层与表示层之间的数据传输）、**表示层**（客户端，通过业务层访问数据库）。

> **数据字典**是指对数据的**数据项、数据结构、数据流、数据存储、处理逻辑、外部实体**等进行定义和描述，其目的是对数据流程图中的各个元素做出详细说明。数据字典是数据库设计中数据收集和数据分析所获得的主要成果。
