服务端学习的第一站不是框架，而是 Go 语言本身。框架能帮你注册路由、解析参数、组织中间件，但系统稳定性更多来自语言层面的基本功：值和指针怎么传，错误怎么表达，并发怎么收敛，请求取消后后台任务会不会继续跑。

Go 的好处是语法少，坏处也是语法少。它不会用复杂语法替你隐藏问题，所以写服务端时，每个选择都很直接：一个对象到底能不能被修改，一个 goroutine 有没有退出路径，一个函数返回错误时调用方能不能判断原因。

## 这部分在链路里的位置

Go 基础是后面所有服务端知识的地基。HTTP handler、数据库访问、Redis 缓存、MQ 消费、RPC 调用，本质上都是普通 Go 函数在处理输入、调用依赖、返回结果。

如果 Go 基础不稳，后面会出现很多隐蔽问题：

- 请求已经超时，但下游 goroutine 还在继续查库；
- 错误只返回 `err`，日志里没有业务上下文；
- 并发写 map 导致偶发 panic；
- service 层依赖具体实现，测试时无法替换；
- 数据结构被多个调用方共享修改，状态来源变得混乱。

所以第一阶段的目标不是“会写语法”，而是“能写出可取消、可测试、可排查的服务代码”。

## 必须掌握的知识点

### 值语义和指针语义

Go 里参数默认按值传递。对基础类型、结构体、slice header、map header 的复制行为要特别敏感。

服务端代码里常见的判断方式是：

- 小对象、不可变配置，可以按值传递；
- 需要修改状态，传指针；
- 大结构体频繁传递，传指针减少拷贝；
- map、slice 本身像引用，但 slice append 可能换底层数组，不能靠直觉写共享状态。

### interface 是边界，不是万能抽象

Go 的 interface 最适合用在依赖边界上。比如 service 依赖一个 `UserRepository`，测试时可以换成 fake 实现；业务代码不需要知道底层是 MySQL、内存还是远程 RPC。

不要为了“显得抽象”到处定义 interface。一个好的经验是：由使用方定义 interface，而不是由实现方提前定义一堆可能没人用的接口。

### 错误处理要能帮助排查

服务端错误不是只给机器看的，也是给未来排障的人看的。

推荐习惯：

- 底层错误向上包装，保留上下文；
- 业务错误和系统错误分开；
- 日志里带上 request id、user id、资源 id；
- 不要在每一层都重复打同一个错误日志；
- 对外响应不要暴露内部数据库、缓存、RPC 细节。

一个简单例子：

```go
user, err := repo.FindByID(ctx, userID)
if err != nil {
    return nil, fmt.Errorf("find user %d: %w", userID, err)
}
```

这比只返回 `err` 更容易定位问题。

### goroutine 要有退出路径

Go 写并发很轻松，但轻松不等于安全。每个 goroutine 都应该回答三个问题：

- 谁创建它；
- 它什么时候退出；
- 出错后谁收集结果。

服务端最常见的控制工具是 `context.Context`。请求入口创建 context，下游数据库、RPC、缓存、后台任务都应该感知取消和超时。

```go
select {
case result := <-done:
    return result, nil
case <-ctx.Done():
    return nil, ctx.Err()
}
```

如果一个 goroutine 不监听退出信号，它就可能在请求结束后继续占资源，最终变成泄漏。

### 测试要覆盖边界和失败

Go 的表驱动测试非常适合服务端逻辑。不要只测成功路径，还要测：

- 参数为空；
- 资源不存在；
- 下游超时；
- 重复提交；
- 并发调用；
- 权限不满足。

服务端测试的价值不是追求覆盖率数字，而是锁住业务规则和失败行为。尤其是幂等、事务、状态流转这些逻辑，一旦上线后靠人工验证会很痛。

## 工程取舍

Go 服务端代码最容易走向两个极端：一种是所有逻辑都塞进 handler，另一种是提前设计出很厚的分层和抽象。

更稳的做法是从三层开始：

- handler：只处理协议输入输出；
- service：组织业务流程；
- repository/client：访问数据库、缓存、RPC 等外部依赖。

这样既不会过度设计，也能保证测试和演进空间。

## 练习方式

写一个并发任务执行器：

- 输入一组 URL 或任务 ID；
- 支持最大并发数；
- 每个任务有独立超时；
- 整体支持 context 取消；
- 收集成功结果和失败原因；
- 用表驱动测试覆盖超时、部分失败、全部成功。

这个练习能把 slice、map、interface、error、goroutine、channel、context、测试全部串起来。完成后再进入 HTTP/API，语言能力就会自然落到服务端请求链路里。
