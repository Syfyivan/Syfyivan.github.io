这篇文章整理的是我在大型内容平台实习期间参与和负责过的几类项目：复杂集卡活动页、进度解锁玩法、自动化权益发放、活动服务重构、压测隔离，以及一次事件消费写放大治理。

它不是一份逐字面试稿，也不是内部技术方案的搬运。为了适合公开发布，文中的业务名称、内部系统名称、服务标识和精确数据均已删除或泛化；量级数据也只保留到能说明工程规模的程度。

我想重点回答两个问题：

1. 一个项目为什么难，不能只靠罗列技术名词来证明；
2. 技术动作、工程效果和业务结果之间，怎样建立诚实而有说服力的因果关系。

## 先建立一个项目表达框架

面试里最容易出现的两种问题，一种是只讲页面和接口，听不出业务复杂度；另一种是只报 UV、转化率和 QPS，却没有说明自己做了什么。

我现在更倾向于把项目拆成四层：

```text
技术动作
  -> 直接工程效果
  -> 业务能力效果
  -> 线上业务结果
```

例如，“做了动画降级”只是技术动作；“动画失败时仍能展示服务端已经确定的抽卡结果”是直接工程效果；“低能力设备也能走完抽卡和领奖流程”是业务能力效果；“活动承接了千万级页面访问、数十万参与用户”才是业务结果。

最后一层通常是产品、运营、推荐、客户端、设计、服务端和前端共同作用的结果，不能写成“因为我做了一个降级，所以活动有了千万 UV”。更准确的说法是：

> 我负责的技术方案保障了这条链路在目标规模和多机型环境下能够稳定运行，并支撑了最终的业务结果。

这个边界不会削弱项目，反而说明我知道工程贡献怎样进入真实业务。

## 项目一：一张完整的 Lynx 集卡活动页

### 它不是一个抽卡弹窗

这个项目表面上是一张活动页，实际上承载了一整套连续流程：

```text
做任务获得机会
  -> 单抽或十连抽得到卡片
  -> 查看图鉴与收集进度
  -> 重复卡赠送给好友
  -> 缺失卡向好友求助
  -> 集齐后获得抽奖资格
  -> 抽奖、查看记录并领奖
```

页面中还有十多个任务。任务虽然都展示为“完成后领取机会”，规则却不相同：有的按天刷新，有的整个活动期只能完成一次；有的跳转站内页面，有的依赖互动行为回流；有的奖励可以补发，有的在内容删除后需要撤销。

卡片也不是普通展示数据。赠卡、求卡和领取都要围绕具体卡片实例流转，既要避免一张卡被重复送出，也要处理分享过期、领取失败和状态刷新。集齐后的抽奖又是另一条业务链，需要校验资格、记录抽奖状态，并继续衔接实物或虚拟奖品的领取。

所以我的前端工作不是“把几个模块放到页面上”，而是把任务、资产流转、动画展示、弹窗编排和领奖链路组织成一套可验证的页面状态。

### 第一个原则：服务端结果和动画进度解耦

抽卡最重要的业务事实，是用户抽到了什么由服务端决定。

十连抽可以简化为下面几个阶段：

```text
idle
  -> submitting
  -> result-saved
  -> overview
  -> exit
  -> carousel
```

用户点击抽卡以后，前端先进入提交状态并阻止重复提交。接口返回后，前端第一时间保存十张卡的真实结果，再进入动画展示。后续无论动画是否完整播放，这十张卡都已经是确定的业务结果。

代码层面，我把状态分成四类：

1. 业务结果：页面数据、抽卡结果、集齐抽奖结果；
2. 展示状态：当前弹窗、选中的 Tab、卡片正反面；
3. 流程状态：总览、退出、横滑接管等有限阶段；
4. 瞬时控制：提交锁、请求编号、计时器和只执行一次的保护位。

业务和展示数据适合放在响应式状态里；同步锁、请求编号和计时器句柄更适合放在不会触发渲染的引用中。这样既不会因为闭包拿到旧值，也能避免为了一个互斥锁触发额外渲染。

这里不需要为了“看起来专业”引入完整状态机框架。TypeScript 联合类型、受控的状态迁移、一次性保护和统一清理，已经足以把流程表达清楚。真正重要的是不允许任意组件随意跳转状态。

### 单抽：真实节点从动画开始就存在

单抽最初的直觉方案，是先播放一段完整动画，播放结束后再替换成真实卡片组件。但真机上两套节点的尺寸、位置和最后一帧很难完全一致，只要有轻微偏差，切换时就会闪烁或跳动。

最终的结构是：从动画开始时就渲染真实业务卡片，让同一个节点完成整段入场。

```text
真实卡片节点
  + 服务端卡图、名称、稀有度、新卡标记
  + 位移、缩放、透明度和多轴旋转关键帧
  + 动画结束后的点击和翻面交互
```

同一节点贯穿动画前后，消除了“动画资源最后一帧切真实组件”的交接问题，也让动态数据从一开始就处于真实业务组件中。

### 翻面：从完整 3D 降级为稳定的 2.5D

翻面最初使用的是 Web 中常见的双面结构：正反两个节点叠放，背面预先旋转 180 度，再由外层节点执行 Y 轴旋转。

真机验证发现，单节点旋转本身可以工作，问题主要出现在双子节点、背面隐藏、透视和三维层级组合以后。部分目标机型会在中间角度出现闪烁、两个面同时露出或层级错乱。

最终我采用了一个单节点的 2.5D 方案：

```text
scaleX: 1 -> 接近 0
  -> 在卡面几乎不可见时切换正反面内容
  -> scaleX: 接近 0 -> 1
```

视觉上仍然是卡片转到侧面以后翻出另一面，但实现不再依赖完整的双面三维层级。这个方案的价值不在于代码更少，而在于目标机型上的结果更可控。

这里也体现了我使用 AI 的一个基本原则：AI 可以快速生成标准 3D 翻卡和多种候选方案，但最终选择不能由“代码看起来是否优雅”决定，必须由真实运行证据决定。

### 十连抽：动态卡面进入固定时间线

十连抽和单抽的运行时特点不同。

十张卡虽然来自服务端，但动画开始前，卡片数量、具体结果、位置和播放顺序已经确定；出现、停留和退出又是一段相对固定的一次性视觉过程。因此，这部分适合由 Lottie 时间线承载，再通过跨端动画播放器执行。

接口返回以后，前端会：

1. 保存十张卡的业务结果；
2. 把真实卡面地址映射到动画数据预留的资源槽位；
3. 生成本次播放数据；
4. 播放十卡出现、停留和退出；
5. 由真实横滑组件接管后续交互。

横滑组件不会等十卡完全消失以后才挂载。退出阶段开始时，它已经准备好，并与十卡动画发生短暂的淡入、缩放重叠。这样可以避免“动画先结束，页面空一下，再突然出现结果组件”。

整个方案不是把技术统一成一种，而是按照运行时职责分层：

| 内容 | 承载方式 | 原因 |
| --- | --- | --- |
| 动态卡图、名称、稀有度、按钮 | 真实 Lynx 节点 | 来自业务数据，播放后仍要交互 |
| 单卡位移、旋转、缩放 | 节点动画 | 需要与真实卡片保持同一节点 |
| 固定背景、光效 | 动画资源 | 主要是预设视觉时间线 |
| 十卡总览 | 动态注入后的 Lottie | 播放前输入已确定，过程一次性 |
| 横滑结果 | 真实组件 | 需要持续响应滑动和点击 |

### 动画失败时，业务仍然必须完成

动画不是业务提交凭证，也不能决定用户有没有得到卡片。

正常情况下，动画完成事件推进到下一个展示阶段；如果资源加载失败、动态图片注入失败或播放异常，页面会直接进入简化的真实节点结果展示。若实现中存在最长等待时间，还可以通过超时保护避免页面永远停留在动画阶段。

降级只影响视觉表现，不重新请求抽卡，也不改变服务端已经返回的结果。重新请求不仅可能造成重复消耗，还会让“展示失败”错误地演变成“业务重做”。

### Lynx 页面为什么会出现“模板是新的，图片却是旧的”

端内页面的调试链路不能只看组件代码。

页面代码会编译为客户端能够加载的模板，再通过 Schema 拉起端内容器；模板、图片和动画资源又可能经过不同的加载或离线分发链路。

因此，本地模板加载成功并不代表静态图片也来自本地。图片地址可能仍被改写到离线资源平台或 CDN；如果资源没有发布，即使模板是最新的，真机仍然会请求失败。

我后来把排查顺序固定为：

```text
客户端实际加载的模板
  -> 图片最终请求地址
  -> 对应资源发布状态
  -> 组件尺寸与可见性
  -> 动画资源注入
  -> 业务状态是否提前卸载节点
```

这比围绕“是不是样式写错了”反复修改更有效，因为它把模板、资源、组件和状态四个层次拆开了。

### 我怎样使用 Coding Agent 进入陌生技术栈

这个项目开始前，我主要熟悉 React 和 H5，没有完整交付过一张 Lynx 活动页。AI 在这个项目里不是“替我把页面生成出来”，而是进入了工程调查、局部实现、验证和回归定位的完整闭环。

第一步，我先给 Agent 接入 Lynx 专项知识和约束，让它遇到组件、布局、动画和平台限制时，优先使用 Lynx 语境，不直接套用浏览器方案。

第二步，我定义不会让步的业务边界：

- 主流程必须完整走通；
- 抽卡结果以服务端为准；
- 动画可以降级，结果和领奖不能被阻断；
- 接口和端能力优先复用已有封装；
- 结论需要有当前代码或生产案例作为证据。

第三步，我没有让 Agent 从空白生成整张页面，而是先让它调查真实仓库：页面入口、构建方式、接口和端能力封装、已上线的同类页面，以及相应的验证手段。我会检查它的结论是否能指向具体代码事实，再把需求拆成范围清楚的局部任务。

第四步，每完成一个阶段，我都会构建并在真机上验证，再把截图、日志、请求地址和具体现象作为下一轮输入。问题不再是“动画不对”，而是“出现阶段正常，停留到退出的状态没有进入”；也不再是“页面透明”，而是“固定图片能显示、真实卡图请求成功，但动画资源替换后不可见”。

第五步，如果一个效果以前正常、后来失效，我会让 Agent 比较最后一个正常版本与当前代码，重点追踪组件挂载、状态切换和动画触发，而不是重新生成一套实现。

在这套协作里，Agent 承担大范围代码检索、候选实现、历史比较和重复修改；我负责定义业务事实、检查证据、选择结构、设计最小实验、审查改动并完成真机验收。

这比“所有问题都问 AI”更准确。面对代码事实就查代码，面对运行问题就做实验，面对没有记录在代码里的团队经验或上游资源约束，就找对应协作者确认。

### 业务结果怎样讲

这张活动页最终承接了千万级成功进入页面的用户、数十万活动参与者、数百万次抽卡请求和千万级卡片发放。

这些数字证明的是活动整体规模，不是单个前端方案的独立收益。我的贡献应当表述为：

> 我独立负责整张 Lynx 活动页的前端交付，通过业务结果与动画状态解耦、真实节点与动画资源分层、多机型降级和端内资源链路排查，保障了复杂抽卡、集卡和领奖流程能够在目标规模下完成交付。

## 项目二：把节点活动做成可复用的全栈能力

第二类项目是进度解锁活动。用户通过阅读、互动、签到等任务贡献积分，全站总积分达到阶段阈值后解锁图片、长图、视频或跳转内容；活动中还包含随机掉落和多次抽奖。

它比普通活动页更适合讲全栈所有权，因为一条需求会同时涉及：

- 运营后台的配置；
- C 端查询和交互接口；
- 领域服务的规则与状态；
- 离线聚合任务；
- 前端展示和多版本兼容。

### 不把素材和阈值写死

一次性活动最容易把每个阶段写成代码分支：达到第一个阈值显示图片，达到第二个阈值播放视频。这样当前需求上线很快，但下一次活动更换素材、阈值或跳转形式就需要重新开发。

我把阶段能力抽象成配置：

```text
stage
  - threshold
  - materialType
  - image / video / longImage
  - schema
  - unlockText
  - fallback
```

前端只按照配置渲染当前阶段；服务端负责校验配置、返回当前总分和已解锁状态；运营可以通过后台调整活动内容。

这里的收益不是“少写了几个 if”，而是把一次需求沉淀成后续活动可以继续复用的能力。

### 全体积分为什么不能在页面请求时实时计算

全站总积分可能来自海量用户的任务记录。如果每次打开页面都实时扫描或聚合明细，页面流量会直接放大成数据库压力，延迟也会随着活动规模增长。

更合理的方式是：离线任务周期性聚合活动总分并保存快照，C 端读取快照；用户个人任务仍然走实时链路。

```text
用户行为
  -> 个人任务积分实时更新
  -> 明细进入聚合链路
  -> 离线任务周期性计算总分
  -> 写入总分快照
  -> C 端查询快照并计算解锁阶段
```

这会带来短暂的最终一致性，但换来了稳定的页面查询成本。产品层需要明确刷新频率和展示文案，工程层则需要监控聚合延迟与失败补偿。

### 随机掉落不是“再弹一个奖品弹窗”

随机掉落和主抽奖的触发时机、概率、幂等和记录入口都可能不同。它可能发生在任务完成以后，也可能与某次抽奖伴随发生；即使主流程已经提交成功，掉落权益的发放仍需要独立重试和查询。

所以它应该有独立的结果标识、履约状态和展示逻辑，不能只复用前端弹窗而忽略服务端语义。

### 多抽不能等价成前端循环单抽

如果用户一次抽多次，而前端循环调用单抽接口，会出现部分成功、部分失败、扣减次数不一致、动画结果难以对齐等问题。

服务端应该明确接收本次抽取次数，在同一个业务边界内校验机会、生成全部结果、记录流水，再一次性返回。前端只负责展示这次已经确定的结果集合。

### 结果怎样归因

这类能力上线后支撑了多个节点活动，相关活动合计达到千万级曝光和数十万任务参与。它们是多角色共同完成的业务结果。

我可以明确说明的是：通过配置化阶段、离线聚合、统一任务接入和兼容性设计，同类活动不再需要从零开发整条链路，运营配置和研发交付的重复成本显著下降。

## 项目三：自动化徽章发放

第三个项目是把“达到活动条件以后发徽章”和“运营批量导入名单发徽章”统一成一套服务能力。

这个需求表面上只是调用一次权益接口，真正的难点却在幂等、有效期、批量容错和运营可操作性。

### 两条入口，一套领域规则

自动发放和批量发放的用户来源不同：

```text
自动路径：
离线任务筛选达标用户
  -> 统一徽章发放能力
  -> 下游权益服务

批量路径：
运营上传名单
  -> 后台解析与校验
  -> 统一徽章发放能力
  -> 下游权益服务
```

如果两条路径分别实现，会逐渐产生不同的幂等、有效期和错误处理。更稳妥的设计是把用户筛选、文件解析留在入口层，把发放规则收敛到统一领域能力中。

### 为什么要按徽章和有效期分组

一批用户可能领取不同徽章，或者同一徽章有不同有效期。下游批量接口的参数通常以一组一致权益为单位，因此不能把所有用户无条件塞进一次请求。

我会先按照“徽章类型 + 有效期”分组，再分别调用下游批量能力。这样既减少请求次数，也避免同一批用户被错误地使用相同参数。

### 幂等不能只看用户 ID

同一个用户可能在不同活动中获得同一种徽章，也可能需要续期。幂等键至少要表达活动、用户和徽章三者关系；下游权益层还需要根据产品定义处理已有权益、到期时间和续期。

“重复执行不报错”不等于幂等。真正的幂等是重复执行不会重复产生业务副作用，而且结果可以被查询和解释。

### 批量文件不能一行错、整批失败

运营上传的文件可能出现空用户、格式错误、重复行、非法权益标识等问题。系统应该在执行前完成结构和配置校验；执行时保留每一行的失败原因，允许正确行继续处理，并为失败行生成可下载的结果。

这会把一个开发接口变成运营真正能使用的工具：运营不需要因为一条坏数据重新制作整份名单，也能知道需要修正什么。

### 业务价值

该能力完成首次活动验证后，承接了数十万量级的权益入口用户，并被后续活动继续复用。

技术贡献与业务结果之间更准确的关系是：统一发放能力降低了重复开发和人工操作成本，幂等、批量容错与有效期语义保障了权益可靠到达；活动转化仍然由权益设计、资源位、内容和运营共同决定。

## 项目四：多仓活动服务重构

随着活动能力增长，代码被分散在多个仓库和多个模块中：C 端接口、运营后台、领域逻辑、离线任务、事件积分和公共模型彼此交叉。

旧架构的典型问题不是“文件太长”这么简单，而是能力归属与运行边界不一致：

- 公共仓里混入具体业务规则；
- 一个入口同时处理鉴权、协议、业务编排、数据库、缓存和异步消息；
- 两条产品线的相似玩法写在一起，修改一端可能影响另一端；
- 代码复用边界与独立服务的发布边界冲突。

### 先定义能力归属

重构的目标不是换一套目录名称，而是回答每类能力应该由谁负责：

| 层次 | 主要职责 |
| --- | --- |
| C 端 API | 登录、参数、协议与入口编排 |
| 运营 BFF | 后台配置聚合和展示转换 |
| 领域服务 | 核心业务规则、事务和状态 |
| 离线任务 | 周期计算、补偿和大批量处理 |
| 事件函数 | 消费行为事件并计算积分 |
| 公共层 | 稳定模型、基础设施与无业务方向的工具 |

模块内部再把协议、业务编排、策略、持久化和异步收尾拆开。这样做的价值是，让依赖方向、发布责任和故障边界彼此一致。

### 迁移不能一次切断旧链路

活动服务通常已有多条线上调用链。一次性替换所有旧接口，会把协议兼容、数据副作用和回滚风险叠到同一时刻。

更稳妥的迁移路径是：

```text
建立能力归属和唯一事实源
  -> 新旧版本并存
  -> 逐模块迁移调用方
  -> 比较接口、错误码、数据库、缓存和异步副作用
  -> 小流量灰度
  -> 保留快速回滚
  -> 稳定后移除旧路径
```

验证重构不能只看单元测试。还要确认外部协议、错误码、数据库写入、缓存、消息和补偿任务是否保持等价。

### 一次有价值的返工

重构初期，一个容易出现的思路是：既然领域逻辑应该归到领域服务，就让其他仓库直接引用它的内部代码。

问题在于，代码目录看起来可以复用，不代表运行时允许直接依赖。如果领域能力是独立部署的远程服务，跨仓调用必须通过稳定协议，不能把它当作普通 library 链接。

这次返工让我更明确了一件事：架构边界不仅是代码组织，还必须同时匹配部署、发布、依赖和故障边界。

### 所有权怎样讲

这类团队重构不应说成“我独立重构了所有仓库”。更准确的表达是：

> 我参与了多仓活动服务重构，并负责其中若干业务模块的迁移、跨仓协议调整和新旧链路验证；团队共同完成整体架构收敛。

边界清楚以后，面试官仍然可以继续追问我实际迁移的模块、遇到的协议问题和验证方法。

## 项目五：高流量活动的压测隔离

压测不是把接口打到一个很高的 QPS，然后看有没有 500。

对于带报名、任务、答题、抽奖和发奖的活动，最大的风险是压力流量在某一层丢失标记，悄悄进入正式数据或触发真实权益。

### 隔离必须贯穿整条链路

```text
压测请求标记
  -> 独立流量泳道
  -> 影子数据库表
  -> 隔离缓存命名空间
  -> 测试消息通道
  -> 发奖和通知 Mock / 拦截
```

影子表只解决了数据库写入目标，并不自动保证完整隔离。如果缓存仍使用正式 key，消息仍进入正式主题，或者下游发奖不识别压测标记，系统依然有真实副作用。

因此每一层都要明确标记如何传播、如何路由，以及识别失败时采取什么动作。对真实权益而言，识别不清应当默认停止，而不是尝试继续。

### HTTP 200 不等于业务成功

压测中曾出现网关返回成功，但响应体表示参数不合法，实际请求没有进入领域服务；也出现过上游接受压力流量，下游服务却按安全策略拒绝压测标记的情况。

如果只看 HTTP 状态和 QPS 图，这两种情况都会被误判为“接口抗住了”。

所以每个场景都需要业务断言：

- 报名后能否查询到报名状态；
- 完成任务后进度是否变化；
- 答题结果是否写入正确的影子数据；
- 抽奖次数是否扣减；
- 抽奖记录是否能够查询；
- 副作用是否只进入测试通道。

### 流量模型来自业务路径

活动目标 UV 不能直接等价成某个接口的 QPS。需要结合资源位曝光曲线、页面打开率、首屏接口数、任务参与率、抽奖次数和峰值集中度进行换算。

压测也不应该一开始就把所有接口混在一起。可以先验证读取接口，再验证写入接口，再覆盖异步链路和混合场景；每一阶段都观察成功率、延迟、错误、数据库、缓存热点、消息堆积和下游限流。

这次压测最终获得了多个核心接口数百 QPS 下的延迟和成功率数据，同时发现了“传输成功但业务失败”和“下游不接受压测流量”两类真实问题。它没有证明系统拥有无限容量，但帮助团队在上线前补齐了隔离和链路准入。

## 项目六：事件消费写放大治理

还有一次更适合作为稳定性追问的案例：活动已经结束，但历史社区内容事件因为延迟或重放，仍然进入活动分发、缓存锁、报名查询和大对象详情写入，形成无效写放大。

问题根因不是消息队列本身“多发了一条”，而是消费者没有在足够早的位置判断活动当前是否仍有效。

修复包括：

1. 在进入大规模分发前检查活动时间和状态；
2. 在具体处理器中再次保护，避免绕过入口；
3. 对无效详情做确定性采样，只保留排障所需信息；
4. 裁剪不必要的大字段，降低存储放大；
5. 补充无效事件、拦截量和异常分布的可观测性。

为什么不能只让运营删除配置？因为配置清理有时间差，历史消息仍可能重放，而且依赖人工操作不能作为系统稳定性的唯一防线。消费者应该对活动生命周期拥有自己的判断。

这个案例没有精确的资源下降数据，所以不能编造“节省了多少机器”。可以确认的直接效果是：过期活动事件不再继续进入后续锁、远程调用和详情写入，系统拥有了更明确的生命周期边界。

## AI 协作怎样讲，才不会显得项目是 AI 做的

面试里强调 AI 能力，不等于把所有关键动作的主语都换成 Agent。

如果连续说“Agent 找到、Agent 分析、Agent 修改、Agent 定位”，面试官自然会怀疑：业务事实、技术取舍和最终验收到底是谁负责的？

我更推荐用下面的职责划分：

```text
我：
  定义业务事实与不可破坏的边界
  决定调查问题和验收标准
  审查代码证据与候选方案
  设计最小实验
  完成集成、真机验证和交付判断

Agent：
  扩大代码和历史检索范围
  整理调用链和生产案例
  生成局部候选实现
  比较版本差异
  执行可自动化的构建和测试
```

一段适合口述的回答是：

> 我不是把整张页面一次性交给 AI 生成，而是先让它进入真实仓库调查，再把复杂需求拆成可以调查、实现和验证的局部任务。每一轮我都会用代码、构建、日志、资源请求或真机现象检查结论，把失败收敛成更具体的问题再继续。AI 降低了检索、候选实现和回归比较的成本；业务状态怎么组织、采用哪种动画方案、代码能否合入以及真机表现能否交付，最终由我判断和负责。

这段话的重点不是证明我会写提示词，而是说明我能建立可靠的人机闭环。

## 面试时怎样选择项目

不需要在一个回答里讲完所有项目。不同问题选择最能提供证据的案例：

| 面试官想听什么 | 主案例 | 可以补充 |
| --- | --- | --- |
| 完整前端交付 | Lynx 集卡活动 | 真机资源链路、复杂状态 |
| AI 协作 | Lynx 集卡活动 | 代码调查、最小实验、历史回归 |
| 全栈能力 | 进度解锁活动 | 配置化、离线聚合、多抽 |
| 可复用服务 | 自动化徽章发放 | 幂等、批量容错、有效期 |
| 架构与重构 | 多仓活动服务重构 | 运行边界、灰度迁移 |
| 稳定性和容量 | 压测隔离 | 业务断言、全链路标记 |
| 线上问题治理 | 事件消费写放大 | 生命周期、入口与处理器双层保护 |

主回答控制在两到三分钟：背景和规模约二十秒，核心难点约三十秒，方案一分多钟，结果和边界约二十秒。细节留给面试官追问。

## 几个高频追问

### 为什么动画失败不能重新请求抽卡

因为服务端已经确定结果，动画只是展示层。重新请求可能重复扣减机会或产生新结果。正确做法是保存原结果并降级展示，而不是把视觉故障变成业务重做。

### 用户快速点击两次怎么办

前端用同步提交锁阻止重复交互；服务端通过请求幂等保证最终副作用只发生一次。前端锁改善体验，服务端幂等保证正确性，两者不能互相替代。

### 为什么不全部使用 Lottie

固定光效和一次性时间线适合动画资源；动态业务内容和播放后仍需交互的组件适合真实节点。选择依据是运行时职责，不是代码量。

### 为什么不用完整 3D

目标不是证明使用了某个 API，而是稳定交付视觉效果。完整双面三维结构在部分目标机型上有层级和闪烁问题，单节点 2.5D 在保留视觉语义的同时更稳定。

### 离线聚合有延迟怎么办

首先和产品明确这是最终一致性指标，并定义刷新周期；服务端记录快照时间和任务状态，监控聚合延迟，失败时可重跑；前端避免把短暂延迟解释成用户操作失败。

### 定时发放任务重复执行怎么办

入口重复执行是正常假设。领域层使用能表达活动、用户和权益关系的幂等键，下游也要支持幂等或最终状态查询；重试前后都可以核对结果。

### 如何证明重构没有改变行为

不能只说单测通过。需要比较协议、错误码、数据库、缓存、异步消息和补偿副作用，结合契约测试、请求回放、小流量灰度和回滚能力验证。

### 为什么压测不能只看 QPS

因为 QPS 只说明请求到达或返回的速度，不证明业务路径执行成功，也不证明压力数据与真实副作用完全隔离。必须同时检查业务断言、延迟、错误、资源和下游链路。

## 最后：把“我做了什么”与“项目取得什么结果”都讲清楚

一个好的项目回答，不需要把所有工作都包装成独立完成，也不需要为了显得谦虚而把个人动作全部藏掉。

可以明确说“我独立负责”的，是整张 Lynx 活动页的前端交付；可以说“我负责端到端能力”的，是自己确实覆盖了配置、接口、领域逻辑、离线任务和前端的项目；涉及多仓重构和压测执行，则应该说清楚自己负责的模块与团队共同完成的部分。

最终我希望面试官听到的不是一串 Lynx、Lottie、RPC、消息队列和压测名词，而是下面这条逻辑：

> 我能把复杂业务拆成明确的状态、边界和交付链路；能使用 AI 快速进入陌生工程，但不会把技术判断外包给 AI；能用代码事实、运行证据和业务结果验证方案；也知道个人技术动作与团队业务成果之间应该怎样诚实归因。

这才是这些项目真正可以复用的部分。
