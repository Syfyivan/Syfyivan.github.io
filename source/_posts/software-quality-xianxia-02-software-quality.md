## 一、故事正文

入门第二日，青萝信心满满。她在山门外见过宗门的炼器房：师兄们铸一柄飞剑，先开一个剑模，铁水浇进去，冷却成形，坏了就照同一个模子再铸一柄。她想，**软件**想必也是这样——画一张图，照着浇一批，哪个坏了照模重铸便是。

长老听完她的设想，摇头把她带进藏经阁深处一间空屋。屋里没有炉火，没有铁砧，只有一面会流动的水镜，镜中影像随人念头变幻。

「你说的是**硬件**。」长老指着水镜，「飞剑是**有形**的，铸成便**固化、稳定**，需求**相对清楚**，要多重多长一称便知，能**度量**，能走**流水线、工序**。可软件不在你手里——它**虚拟、动态**，看不见摸不着，像这镜中之影。」

青萝伸手去碰水镜，影像便散了。她愣住。

「更要命的是，」长老继续说，「铸剑前你知道客户要一柄三尺青锋；可做软件，客户一开始**需求就不确定**。他说要一个『好用的查账法阵』，可什么叫好用？查得快算好用，还是看得清算好用？他自己都没想明白。等你照他第一句话做完，他又改了主意。软件的需求是会变的，逻辑关系**复杂**，接口**复杂**，**度量非常困难**。」

她不服气：「那等他想清楚了再做不就好了？」

长老笑：「问题就在这里。有人统计过——软件里 **54% 到 56% 的质量缺陷，来自需求不清楚**；还有 **25% 来自设计和编程**。也就是说，大多数**软件缺陷**根本不是写错代码造成的，而是在『需求分析』和『设计』这两步就已经种下了。你把代码写得再漂亮，地基歪了，楼还是塌。」

青萝沉默了。她原以为炼软件的真功夫在「编程」，原来一炉好软件，胜负早在动手写代码之前就分了大半。

长老在水镜旁的石壁上写下五个词：**需求分析、设计、编程、测试、维护**。「这是**软件开发的基本过程**。记住次序，也记住一件事——软件不像硬件那样维护时只是修旧补漏，软件**可以不断打补丁**，不仅解决老问题，还会**增加新特性、加强新功能**。它是活的。」

「软件无形，缺陷难察，」长老收笔，「所以我们这一脉，要先学会『辨软』——看清软件到底是个什么东西，它的质量到底指什么。」

## 三、概念正解

### 3.1 软硬件特征比较（七项对照，必背表）

| 特征 | 软件 | 硬件 |
| --- | --- | --- |
| 存在形式 | **虚拟、动态** | 固化、稳定 |
| 客户需求 | **不确定性** | 相对清楚 |
| 度量性 | **非常困难** | 正常 |
| 生产过程 | **逻辑性强** | 流水线、工序 |
| 逻辑关系 | 复杂 | 清楚 |
| 接口 | 复杂 | 多数简单、适中 |
| 维护 | 可以不断打补丁（增加新需求、新功能） | 一般没有新的需求 |

口诀：软件「虚、变、难量、靠逻辑、关系杂、接口杂、补不完」；硬件正好相反。

### 3.2 软硬件开发过程比较（关键数字）

软件开发与硬件生产的过程也不同，最关键的是**缺陷来源的分布**：

- **54%~56% 的质量缺陷来自需求不清楚**（需求分析阶段是质量控制的主要阶段之一）；
- **25% 的质量缺陷来自设计和编程**（设计阶段是质量控制的主要阶段之一）；
- 硬件生产的主要过程是制造、检验，质量控制重点在生产；软件的「拷贝」不是质量管理的主要阶段。
- 软件的**维护**不仅支持原有功能、解决以前就存在的问题，**还会增加新特性、加强新功能**；硬件的维修只是支持原功能、解决运行中的问题，一般比较容易预测。

结论：**多数软件缺陷来自需求与设计，而非编码。**

### 3.3 软件开发的基本过程（五步，按序）

1. **需求分析**：了解客户需求中的功能、特性、性能、界面、规格，分析确定软件产品所能达到的目标。
2. **设计**：考虑如何在逻辑、程序上实现已定义的功能，分为概要设计与详细设计（也可分数据结构、体系结构、接口、模块、界面设计）。
3. **编程**：将设计转换成计算机可读的形式。
4. **测试**：对设计、编程进行**验证**和用户需求**确认**的过程。
5. **维护**：维持软件运行，修改软件缺陷、增强已有功能、增加新功能、升级等。

### 3.4 软件开发过程模型（列举）

常见模型：**瀑布模型、原型模型、螺旋模型、并发模型、改进的 V 模型、构件组装模型、快速应用开发（RAD）模型、Rational 统一过程模型和 UML、形式描述技术、测试驱动型、V 模型、敏捷方法—极限编程模型、增量模型和迭代模型**。

### 3.5 V 模型的完整诠释（重点）

V 模型把开发与测试一一对应，左边下行是开发，右边上行是测试：

| 左侧（开发，含静态测试） | 右侧（测试，含动态测试） | 对应关系 |
| --- | --- | --- |
| 需求分析/定义（客户、市场、产品人员） | **验收测试** | 需求 ↔ 验收 |
| 系统、结构设计（设计和环境） | **系统测试**（灰盒方法） | 系统设计 ↔ 系统测试 |
| 详细或程序设计（工程师、技术人员） | **集成/功能测试**（黑盒方法、用例设计） | 详细设计 ↔ 集成/功能测试 |
| 编码 | **单元测试**（白盒方法） | 编码 ↔ 单元测试 |

要点：
- 左侧的「分析/设计/复审」属于**静态测试**；右侧的「检验」属于**动态测试**。
- 测试不是写完代码才开始——**测试计划与测试目标在需求、设计阶段就要定**。
- 最关键的对应：**需求对验收测试**（最上面那一对）。

### 3.6 敏捷方法之极限编程（XP）

**极限编程理念——四个「胜过」：**

| 胜过 |
| --- |
| 个体和交互 **胜过** 过程和工具 |
| 可以工作的软件 **胜过** 面面俱到的文档 |
| 客户合作 **胜过** 合同谈判 |
| 响应变化 **胜过** 遵循计划 |

- 核心信条：**最简单的可能就是最有效的**。
- **格言：「沟通、简化、反馈、勇气」**。
- 极限编程**适用场景**：**小团队（2~10 人）**、**快速变化或不稳定的需求**、**「高风险」**、**强调可测试性**。

### 3.7 软件缺陷（IEEE 729）

**定义（IEEE 1983 的 729 标准）：**
- 从产品**内部**看，软件缺陷是软件产品开发或维护过程中所存在的**错误、毛病等各种问题**；
- 从**外部**看，软件缺陷是系统所需要实现的某种功能的**失效或违背**。

**软件缺陷的表现形式：** 功能/特性没有实现或部分实现；设计不合理、存在缺陷；实际结果与预期结果不一致；运行出错（中断、崩溃、界面混乱）；数据结果不正确、精度不够；用户不能接受的其他问题（如存取时间过长、界面不美观）。

> **软件错误**是缺陷的一种，属于**内部缺陷**，往往是软件本身的问题（如初始化/赋值错误、算法/语法错误、精度问题、接口参数不匹配等）。

**软件缺陷的产生原因：** 项目期限的压力、产品的复杂度、沟通不良、开发人员疲劳/压力/受干扰、缺乏足够的知识技能经验、不了解客户需求、缺乏动力。归纳为三类：**技术问题、团队工作、软件本身**。

**软件缺陷的构成（饼图，必背数字）：**

| 来源 | 占比 |
| --- | --- |
| **规格说明书** | **54%** |
| **设计** | **25%** |
| **代码** | **15%** |
| **其他** | **5%** |

记忆：54 + 25 + 15 + 5 = 100。最大头永远是**规格说明书（需求）**。

### 3.8 软件质量的定义（ANSI/IEEE STD729）

> **软件质量：软件产品满足规定的和隐含的与需求能力有关的全部特征和特性。**

可从四个角度理解：软件产品质量满足用户要求的程度；软件各种属性的组合程度；用户对软件产品的综合反映程度；软件在使用过程中满足用户要求的程度。

它**包含三个方面**：软件**产品**的质量（满足使用要求的程度）、软件**开发过程**的质量（能否满足成本、时间和风险等要求）、软件在其**商业环境**中所表现的质量。

### 3.9 软件质量的三套特性（重点对比）

**3A 特性：**

| 3A | 中文 | 含义 |
| --- | --- | --- |
| **Accountability** | 可说明性 | 用户可基于产品/服务的描述和定义进行使用（如市场需求说明书、功能设计说明书） |
| **Availability** | 有效性 | 产品/服务对 99.999% 客户总是有效的（如性能测试、恢复测试） |
| **Accessibility** | 易用性 | 产品/服务非常容易使用且功能有用（如确认测试、用户可用性测试） |

**3 维特性：** **功能性（Functionality）、可靠性（Reliability）、性能（Performance）**。其中健壮性和有效性有时可看成可靠性的一部分。

**ISO9126 定义的六大特性：** **功能、可靠、易用、效率、可维护、可移植**——每个特性下还分若干子特征。

### 3.10 软件质量的内容（三部分）

软件不仅指软件产品，还包括开发过程及软件的运行/服务。软件质量由 **3 部分**构成：

1. **软件产品质量**：满足使用要求的程度（功能性、可用性、可靠性、性能、容量、可测量性、可维护性、兼容性、可扩展性……）。
2. **软件过程质量**：按一定流程执行开发过程可更有效达到目标，形成方法体系与工程规范——对应 **CMM（软件能力成熟度模型）、PSP（个人软件过程）和 TSP（团队软件过程）、ISO 9000（国际标准过程模型）、SPICE（软件过程改进和能力决断）**。
3. **软件商业环境质量**：软件最终要投入市场，其质量表现要在商业环境中体现；好软件不一定获得好市场，商业表现不一定与产品质量、过程质量同步。

## 五、考点卡

- **判断题抓手**：
  - 「软件大多数缺陷来自编码。」——**错**。规格说明书占 54%，设计 25%，代码只占 15%。
  - 「软件和硬件一样可以度量，需求一开始就清楚。」——**错**。软件度量非常困难、客户需求具有不确定性。
  - 「V 模型中需求分析对应验收测试。」——**对**。这是 V 模型最关键的对应关系。
  - 「软件维护只是修旧补漏，不会有新需求。」——**错**。那是硬件；软件维护还会增加新特性、加强新功能。
- **选择题抓手**：
  - 见「虚拟、动态 / 不确定性 / 非常困难」→ 软硬件特征比较中的「软件」。
  - 见「沟通、简化、反馈、勇气」「四个胜过」「2~10 人小团队 / 需求快变 / 高风险 / 可测试性」→ **极限编程**。
  - 见「54% / 25% / 15% / 5%」→ **软件缺陷的构成**。
  - 见「Accountability / Availability / Accessibility」→ **3A 特性**；见「功能/可靠/易用/效率/可维护/可移植」→ **ISO9126 六特性**。
- **填空题抓手**：
  - 软件缺陷构成中，规格说明书占 **54%**、设计占 **25%**、代码占 **15%**、其他占 **5%**。
  - 软件开发基本过程：需求分析、设计、编程、测试、**维护**。
  - 软件质量（ANSI/IEEE STD729）：软件产品满足**规定的和隐含的**与需求能力有关的全部特征和特性。
- **简答题答题骨架**（软硬件区别）：① 存在形式（虚拟动态 vs 固化稳定）② 客户需求（不确定 vs 相对清楚）③ 度量性（困难 vs 正常）④ 生产过程⑤ 逻辑关系⑥ 接口⑦ 维护，七项对照逐条答。
- **设计题答题骨架**（画/解释 V 模型）：① 左侧开发四阶段：需求→系统设计→详细设计→编码（左侧含静态测试）② 右侧测试四阶段：单元→集成/功能→系统→验收（右侧含动态测试）③ 一一对应，强调需求↔验收④ 指出测试计划在开发早期就启动。

## 六、小试炼

**题 1（判断）：** 软件的客户需求一开始就是清楚的，所以缺陷主要来自编码。
参考答案：**错**。软件客户需求具有不确定性；54%~56% 缺陷来自需求不清楚，代码缺陷只占 15%。

**题 2（选择）：** 极限编程的格言是？
A. 计划、执行、检查、改进　B. 沟通、简化、反馈、勇气　C. 需求、设计、编程、测试　D. 初始、可重复、已定义、优化
参考答案：**B**。「沟通、简化、反馈、勇气」是极限编程格言。

**题 3（填空）：** 软件缺陷的构成中，______ 占 54%，是最大的来源。
参考答案：**规格说明书（需求）**。

**题 4（简答）：** 简述 V 模型左右两侧的对应关系。
参考答案要点：左侧自上而下是需求分析、系统设计、详细设计、编码（含静态测试）；右侧自下而上是单元测试、集成/功能测试、系统测试、验收测试（含动态测试）；两两对应，需求对应验收测试、系统设计对应系统测试、详细设计对应集成测试、编码对应单元测试；测试计划在开发早期同步制定。

**题 5（设计/简答）：** 某团队只有 5 人，客户需求频繁变化且项目高风险，强调可测试性，应优先考虑哪种开发方法？为什么？
参考答案：优先考虑**极限编程**。因为极限编程适用于小团队（2~10 人）、快速变化或不稳定的需求、「高风险」、强调可测试性的场景，理念是「可以工作的软件胜过面面俱到的文档」「响应变化胜过遵循计划」，能快速反馈、拥抱变化。

## 七、易错点

- 把「软件缺陷构成（规格 54% / 设计 25% / 代码 15% / 其他 5%）」和「开发过程缺陷来源（需求 54%~56% / 设计编程 25%）」记混——两者数字相近、含义相通，但前者是缺陷**构成饼图**，后者是**开发过程比较**里的说法，答题按题干用词作答。
- 把 **3A 特性**（可说明性/有效性/易用性）和 **3 维特性**（功能性/可靠性/性能）、**ISO9126 六特性**（功能/可靠/易用/效率/可维护/可移植）混为一谈——三套是不同体系，分别记。
- V 模型只记「左开发右测试」，忘了**具体对应**和「需求↔验收」这一最关键配对，也忘了左侧静态测试、右侧动态测试。
- 只背故事里的「水镜」「飞剑」，答题却不写「虚拟、动态」「客户需求不确定性」「度量非常困难」这些课件原词——故事只帮记忆，得分靠术语。
- 误以为软件维护和硬件维修一样「只修不增」——软件维护会**增加新特性、加强新功能**。
