这次集卡需求，表面上是做一个活动页：用户做任务拿抽卡机会，抽卡收集图鉴，重复卡可以送好友，缺卡可以求好友，集齐以后还能抽奖。

但真正做下来，它不是一个单纯的“照着设计稿写页面”。它更像一个小型活动系统的前端外壳：

```text
H5 参考实现
  -> Lynx RL3 页面迁移
  -> 服务端活动接口和组件接口接入
  -> 任务、抽卡、转赠、求卡、记录、集齐抽奖闭环
  -> 真机调试、视觉还原、低端机降级
  -> 动效和可交互结果页之间的状态机
```

这篇不重点讲 Lottie 透明、CDP/eval 上下文、保存图片这些单点坑。那些问题已经更适合单独成文。这里想把完整需求的思考过程整理下来：一个复杂活动页，怎么从“先跑起来”推进到“能联调、能验证、能承接变化”。

## 先定原则：不要重新设计，先继承业务语义

这个需求一开始最重要的判断，不是用什么动画，也不是某个布局细节，而是：

> H5 分支是业务语义的源头，RL3 页面的第一目标是迁移和承接，不是重新发明一套集卡玩法。

这句话决定了很多后续选择。

如果把它当成纯新页面，前端很容易从视觉开始搭：先画头图、任务区、图鉴区、抽卡弹窗，再慢慢补接口。这样看起来进度快，但风险是业务链路会散。等服务端接进来时，会发现“页面能看”和“活动能跑”之间隔着很多隐性契约：

```text
卡牌是平铺还是按稀有度分组？
任务来自卡牌信息接口，还是来自活动组件接口？
记录页按什么 source 查？
抽卡掉落奖品是整次抽卡一个，还是能绑定到某张卡？
集齐抽奖返回的是奖品，还是只返回抽奖机会变化？
分享口令进入页面时，要先登录、先展示卡，还是直接领取？
```

所以最稳的路线是：先让 RL3 页面继承 H5 的业务语义，再在 Lynx 约束下重建交互和视觉。迁移不是复制 DOM，而是复制“这件事为什么这么做”。

第一批提交也基本按这个思路推进：先让页面可调试、可 mock、可本地构建；再把 collect-card 流程搬进 RL3；随后再补视觉 parity 和真机验证。这个顺序比“等最终设计稿和接口都稳定再动手”更适合活动页，因为活动页的接口、素材和动效往往就是一起变的。

## 页面不是一个 tab，而是一条连续任务线

这个页面最容易误解的一点，是把它拆成几个独立 tab：

```text
任务 tab
图鉴 tab
奖品 tab
```

但实际体验更像一条连续任务线：

```text
先看到活动头图和规则
  -> 做任务拿机会
  -> 看到图鉴进度
  -> 抽卡或求卡补齐图鉴
  -> 集齐后进入奖品抽奖
```

所以实现里没有把三块内容做成互斥面板，而是做成连续 section，再用顶部 tab / 吸顶 tab 去滚动定位。这个取舍很重要。

互斥 tab 的好处是状态简单，但它割裂了活动节奏。用户做任务、看图鉴、看奖品之间会像切页面。连续 section 的好处是活动感更强：所有信息在同一条长页面上，只是通过 tab 快速定位。

代价是前端要自己维护一套滚动同步：

```text
点击主 tab
  -> scrollIntoView 或按测量 offset 滚到 section

用户手动滚动
  -> 根据 scrollTop 反推当前 active tab
  -> 到图鉴区后再反推 active rarity

底部固定抽卡栏
  -> 页面未滚到底时固定在底部
  -> 滚到内联底部栏附近时隐藏固定层，避免两个底栏重叠
```

这里的设计取向是：页面结构服务业务流程，而不是为了代码状态简单把体验拆碎。

## app.tsx 只做编排，复杂性往两边收

这类活动页最怕最后长成一个巨大的 `app.tsx`：所有接口、弹窗、任务点击、滚动、分享、图鉴、动画都塞在一个文件里。短期能跑，长期不可改。

这次拆分的方向比较清晰：

```text
app.tsx
  负责页面级状态、登录、请求、事件编排、滚动同步

service.ts
  负责接口调用、字段兼容、数据归一化

components/sections.tsx
  负责任务区、图鉴区、奖品区这些页面 section

components/modals.tsx
  负责卡片结果、横滑、分享、掉落、登录引导等弹层

components/records-page.tsx
  负责记录页自己的分页、tab、返回和刷新

fallback-provider
  负责低端机图片降级策略
```

这个拆分不是为了“看起来架构化”，而是为了把变化隔离开。

服务端字段变了，应该主要改 `service.ts`；视觉微调，应该主要改 section / modal / less；低端机资源策略，应该不污染业务代码；记录页变成独立页面，也不应该复制一份记录 UI。

这个原则在后面非常救命。因为这个需求并不是一次性写完的，中间不断发生变化：

- 任务来源从本地 mock 变成活动组件接口。
- 记录页从内联视图变成可独立部署的 RL3 entry。
- 更多福利链接需要由后端配置下发。
- 图鉴横滑从 swiper 退回 scroll-view。
- 单抽结果从 Lottie 改成 DOM 卡片。
- 十抽动效在 overview 和 carousel 之间反复调整。

如果这些都集中在一个大文件里，每一次变化都会互相踩。

## 数据归一化层是活动页的稳定器

集卡页最核心的工程点，其实不是页面，而是 `service.ts` 里的归一化层。

活动页接口有一个典型特点：字段不会在第一天就完全稳定，而且不同链路给的数据形态不一样。前端如果把接口响应直接传给组件，组件会充满这种判断：

```text
raw.card_id || raw.cardId || raw.id
raw.card_list || raw.cardList || raw.cards
raw.owned_count || raw.ownedCount || raw.count
```

这样写一两处还行，一旦散到全页面，后面调接口就是灾难。

所以这次先把页面需要的领域模型收敛出来：

```text
PageData
  activityId
  activityStatus
  remainingDrawCount
  collectedCount / totalCardCount
  cardPools: SP / SSR / SR / R
  tasks
  links
  completeLotteryPrizes
  shareEntry
  feature switches

CardItem
  cardId
  cardInstanceId
  name
  rarity
  ownedCount
  image / drawImage / lockImage
  canGift / canRequest
  owner snapshot
  dropPrize

TaskItem
  taskId
  status
  progress / target
  rewardDrawCount
  actionType / actionUrl / actionPayload
  scoreTaskType
```

组件只消费这些稳定结构。至于服务端到底给的是 snake_case、camelCase、JSON string、组件配置、嵌套 data，统一在 service 里消化。

这带来一个很实际的收益：需求推进时可以先用 mock 或候选字段跑通，后端字段稳定后只替换适配层，不需要全页面找字段。

## 卡牌分组：服务端没分组，前端就按领域规则分

图鉴展示是按稀有度分组的：SP、SSR、SR、R。直觉上会去问服务端有没有“分组接口”。但当时实际链路里，卡牌信息更接近平铺列表，每张卡带 rarity / card_level / cardLevel 一类字段。

这里前端做了一个很实用的兼容：

```text
如果服务端给 rarity_groups / card_pools
  -> 尊重服务端分组

否则如果服务端给 cards / card_list
  -> 前端按 rarity 聚合成 SP / SSR / SR / R

再否则
  -> 兼容已有 mock / 本地结构
```

这不是“前端抢服务端职责”，而是活动页展示模型和接口模型之间的转换。服务端负责事实：有哪些卡、每张卡属于什么稀有度、用户拥有几张。前端负责展示：图鉴按什么顺序、每组怎么排、点击后怎么横滑。

把这层想清楚，就不会卡在“没有分组接口是不是不能做”。

## 任务不是按钮列表，而是任务系统适配

任务区一开始看起来只是几行任务：

```text
去阅读
去评论
去分享
去关注
```

但接入后会发现，它不是普通按钮列表，而是一个任务系统适配问题。

有的任务可以直接跳 schema，有的任务要打开阅读器，有的任务要打开评论页，有的任务要拉分享面板，有的任务要内联提交完成。更麻烦的是，任务配置不一定在卡牌主信息接口里，而是来自活动组件链路。

所以任务点击最终做成了三层：

```text
第一层：如果后端下发了明确 actionUrl / schema，优先执行

第二层：如果没有明确跳转，按 scoreTaskType 映射内建动作
  阅读 / 评论 / 话题 / 分享 / 签到 / 答题 ...

第三层：如果是求卡/赠卡类任务
  滚到图鉴区，引导用户选择具体卡片
```

这里有一个重要原则：不要把所有任务都当成“提交任务”。有些任务必须跳到宿主原生场景里完成，前端点击只是入口。提交接口只适合少数内联任务，比如签到、分享上报、答题这类明确可以由活动页直接完成的动作。

这也是活动页经常踩的坑：UI 上都叫“去完成”，但工程上不是同一种动作。

## 抽卡结果：请求完成，不等于交互结束

抽卡链路看起来简单：

```text
点击抽卡
  -> 请求接口
  -> 展示结果
```

但页面上真正需要维护的是一个更长的状态变化：

```text
点击抽卡
  -> 校验活动是否结束
  -> 校验登录
  -> 校验抽卡机会
  -> 请求 draw
  -> 用页面已有卡牌信息补全抽到的卡
  -> 展示单抽或十抽结果
  -> 更新剩余次数
  -> 合并 ownedCount
  -> 如果掉落奖品，还要接到翻卡 / 记录 / 地址入口
```

这里有两个细节值得记。

第一，抽卡返回的卡不一定带足展示字段。页面已有图鉴里已经有完整卡面、稀有度、名称等信息，所以抽卡结果会用当前 pageData 做一次 enrich。这样可以避免接口只返回 id 时结果弹窗缺图缺文案。

第二，更新图鉴不能只把抽到的卡 append 到末尾。正确做法是按 cardId 合并 ownedCount，已有卡数量加一，新卡才补进去，然后重新计算 collectedCount。这样图鉴和抽卡结果才能在一次交互后保持一致。

这就是为什么 `mergeDrawnCards` 这种小函数很关键。它不是工具函数，而是抽卡页状态一致性的边界。

## 求卡和赠卡：它们不是分享按钮，是转赠状态机

求卡 / 赠卡是这个需求里比较容易被低估的部分。

从 UI 看，它们只是两个按钮：

```text
未获得：去求卡
重复拥有：送好友
```

但实际链路更像这样：

```text
用户 A 选择一张卡
  -> 创建 gift / request transfer
  -> 得到 shareToken / shareUrl / shareImage
  -> 展示分享面板
  -> 用户 B 从口令或链接进入
  -> 登录校验
  -> 查询 transfer 状态
  -> gift 场景展示卡并领取
  -> request 场景允许赠送
  -> 状态过期 / 已领取 / 卡不足时给明确反馈
```

所以这块不能写成“点击按钮调分享面板”。分享只是中间一步，核心是 transfer 状态。

前端的关键职责有三个：

1. 创建口令时，把当前卡片和服务端返回的 transfer 信息合成一个 shareEntry。
2. 从分享入口进来时，先用 shareToken 查询状态，不直接假设可领取。
3. 对登录做专门引导，因为分享入口经常来自站外或冷启动。

这也是为什么页面里有 `shareEntry`、`ShareCardsModal`、`LoginGuideModal` 这些状态，而不是一个普通 toast。

## 记录页：先复用 UI，再支持独立入口

记录页一开始可以内联在主页面里打开，但活动上线后更合理的是独立页面：用户可以从“我的记录”直接进入，也可以从抽奖结果、实体奖地址入口回来后刷新。

这次处理方式是：

```text
先把 RecordsPage 做成独立组件
  -> 主页面没有 schema 时，内联渲染
  -> 如果下发 record_page_schema 或能从 template_url 推导，就打开独立 RL3 页面
```

这样有两个好处：

1. 不阻塞上线：schema 没注册前主页面还能用内联记录页。
2. 不复制代码：独立页面和内联页面都复用同一个 RecordsPage。

记录页内部也有几个活动页常见细节：

- 每个 tab 自己维护分页 cursor 和 loading 状态。
- 请求 id 防止旧请求回写新 tab。
- 实体奖品点击后跳地址页，页面重新可见时刷新当前 tab。
- actionUrl 需要做安全校验，不能让后端配置绕过基本协议限制。

这部分看起来不像主视觉那么显眼，但它决定了活动闭环能不能收口。用户抽到奖品之后，最终还是要回到记录和地址状态。

## 更多福利链接：不要混进任务系统

中间还接了一个“更多福利”模块。它和任务很像：都有标题、描述、按钮、跳转。但实现上没有把它塞进 TaskList。

原因很简单：任务是可完成、可领取、可给抽卡机会的；福利链接是被动配置入口。它们长得像，但语义不同。

如果把链接混进任务列表，短期少写一个组件，长期会污染任务模型：

```text
任务需要 status / progress / rewardDrawCount
链接只需要 title / desc / target
任务点击可能提交或跳转
链接点击只做导航
```

所以最终做成 `LinksPanel`：它只负责渲染后端配置的链接，点击复用安全跳转逻辑。这样语义清楚，后面运营加入口也不会影响任务系统。

## 横滑卡：从组件能力退回确定性控制

图鉴和十抽结果都需要横滑大卡。最开始很自然会想到用 swiper，毕竟它就是做分页横滑的。

但在真实宿主 Lynx 版本里，带边距的 swiper 模式出现了布局异常：卡片会被均分成容器宽度的一部分，首尾居中和卡片比例都不稳定。于是后面退回到更可控的实现：

```text
水平 scroll-view
  -> 首尾加 pad，保证第一张和最后一张能居中
  -> scroll / scrollend 记录 scrollLeft
  -> 手指松开时按 15% 阈值判断去上一张、下一张或回弹
  -> JS 驱动 8 帧 ease-out 吸附
```

这个方案没有 swiper 优雅，但它确定。

更关键的是，卡片本体、To 信息、编号、下载按钮、翻卡按钮必须作为一个整体随卡片滑动。之前如果用 z-index 或外部操作区，很容易在 iOS Lynx 上出现“卡在滑，文字和按钮不跟着滑”的图层问题。最后的原则是：

> 每张卡是一个不可拆的滑动单元，卡面、meta、按钮都属于这张卡。

这个结论比“用哪个组件”更重要。

## 集齐抽奖：接口结果和动画结果要解耦

集齐之后的九宫格抽奖，是另一个容易写错的状态机。

错误写法是：请求一回来就弹中奖弹窗，同时转盘动画自己跑。这会导致用户感知上很奇怪：格子还没停，结果已经出来了；或者结果弹窗和机会弹窗混在一起。

最终做法是两段式：

```text
点击中心按钮
  -> 九宫格开始跑马灯
  -> 调 drawCompleteLottery
  -> 接口返回后只暂存结果
  -> 把中奖 prizeId 映射成九宫格目标格
  -> 动画减速并停到目标格
  -> settleDelay 后再弹中奖结果
  -> 刷新页面数据
```

这里的核心是：接口结果和用户可见结果不是同一个时刻。

接口返回代表“服务端已经决定结果”；转盘停稳代表“用户已经看完抽奖过程”。前端要把这两个时刻桥起来，而不是让后端速度决定动效节奏。

这也是活动页常见思路：业务事实可以先发生，用户叙事要按动画和操作节奏呈现。

## 低端机降级不是性能优化，是需求完整性

这个页面用了很多大图：头图、卡面、卡背、抽卡结果、掉落弹窗、分享图、九宫格奖品图。视觉活动页很容易把“图越清楚越好”推到极致，但 Lynx 宿主和低端机内存会给现实约束。

所以后面补了一个本地 fallback provider：

```text
读取设备分数和 32 位信息
  -> 分 high / medium / low
  -> medium / low 开启 downsampling
  -> low 用 RGB_565
  -> 对带图片处理参数的 URL 按比例降低尺寸和质量
```

这件事不是可有可无的“性能优化”。对活动页来说，低端机如果因为大图加载慢、内存压力或渲染失败导致按钮空白、卡面闪烁，那就是需求没完成。

同时它必须做成透明能力：业务组件还是写 `src={image}`，只是通过 `getAdapterDeviceImage` 和 image-config 适配。否则每个组件都要知道设备分级，性能策略就会散掉。

## 安全跳转：后端可配置不等于前端可盲开

任务、链接、记录页都会打开后端下发的目标。这个能力很灵活，但也意味着前端不能盲目 `open(scheme)`。

这次至少做了基础目标校验：

```text
http / https
  -> 走 WebView 容器

schema
  -> 走宿主 open

javascript: / data: / file:
  -> 拒绝
```

这不是完整安全体系，但它是活动页配置化跳转的底线。尤其是记录页这种“领奖 / 填地址 / 查看详情”的入口，actionUrl 由后端返回，前端不能因为它来自服务端就完全信任。

## 真机验证：工具输出只能证明它那一层

这个需求里很多判断都必须回到真机。原因是 Lynx 页面在桌面或构建层看起来正常，不代表宿主里正常：

```text
template.js 本地 200，不代表图片资源也走本地。
lint 通过，不代表 scroll-view 在宿主版本里布局正确。
截图里容器存在，不代表 Lottie 内部 asset 渲染成功。
CDP reload 返回空对象，不代表 session 列表里的 URL 会同步更新。
```

所以提交里反复出现几类验证：

- scoped lint，保证基础代码质量；
- `git diff --check`，避免 whitespace 和补丁问题；
- Lynx 构建，保证目标页面能出包；
- DevTool screenshot / console，验证真机渲染和无明显错误；
- mock 数据，让抽卡次数、掉落、分享入口可重复。

我觉得这次最大的工程经验之一，就是不要把某个工具的输出当成全局真相。每个证据都有边界：

```text
lint 证明语法和规则；
build 证明能打包；
screenshot 证明某一刻视觉；
console 证明当前 session 没报这些错误；
真机点击证明宿主能力和业务动作真的接上。
```

活动页交付要把这些证据拼起来，而不是只看其中一个。

## 提交历史背后的推进节奏

如果把这条分支的提交按阶段看，大概是这样：

```text
第一阶段：可运行
  新增 RL3 页面、mock service、基础组件拆分、本地构建和调试入口

第二阶段：可还原
  迁移 H5 业务流，补视觉资产，按 390 基准还原头图、任务、图鉴、抽卡结果

第三阶段：可交互
  任务点击、抽卡、求卡、赠卡、记录页、横滑、分享入口逐步闭环

第四阶段：可接后端
  活动组件任务、记录 source、配置链接、集齐抽奖组件、feature switches 进入归一化层

第五阶段：可在设备上跑
  修 scroll-view 吸附、图层提升、资源降级、按钮切图兜底、Lynx 宿主差异

第六阶段：可被接手
  DEV_HANDOFF 记录调试链路、当前架构、已知坑和关键 commit
```

这个节奏里有一个反复出现的原则：先让问题可复现，再让实现漂亮。

例如本地 mock、可重复抽卡次数、加载即显示动画、截图 contact sheet、交接文档，看起来都不是最终功能，但它们让问题能被定位和传递。没有这些，复杂活动页会变成“我手机上好像不对，你再看看”的黑盒。

## 我以后会复用的几个判断

**第一，活动页要先收领域模型，再写视觉细节。**

如果一开始没有 PageData / CardItem / TaskItem / Record 这些稳定结构，后面接口一变，所有组件都会被拖下水。

**第二，H5 迁移不是复制代码，而是继承业务语义。**

RL3 和 H5 的 DOM、样式能力、桥接能力都不一样，但“为什么这样展示、为什么这样跳转、为什么这样更新状态”应该继承。

**第三，配置化入口一定要有安全边界。**

任务、福利链接、记录动作都可能来自后端配置。前端要支持灵活，但不能放弃基本协议检查和 action 类型分流。

**第四，动效要服从可交互状态机。**

抽卡不是播放动画，抽卡是一次业务状态变化。动画只是把状态变化讲给用户看。任何动效方案如果会破坏结果页可交互性、重挂旧层、导致按钮不可点，就应该让位。

**第五，低端机和本地资源链路要尽早进场。**

活动页大图多、素材多、宿主差异多。等最后才看低端机，往往不是“优化一下”那么简单，而是会推翻资源和布局策略。

**第六，交接文档不是收尾装饰。**

这次 DEV_HANDOFF 里记录了页面坐标、dev URL、真机拉页方式、reload、截图、eval 限制、架构和已知坑。对这种多阶段活动页来说，这类文档就是后续继续迭代的入口。

## 最后总结

这次集卡需求对我最大的提醒是：复杂活动页不是“视觉 + 接口”的简单相加。

它真正要做的是把几条不稳定的线编成一个稳定体验：

```text
设计稿在变
接口契约在变
素材链路在变
宿主能力有差异
真机表现和桌面直觉不一致
用户却只看到一次连续的活动体验
```

前端的价值就在这里：不是把每个字段显示出来，也不是把每张图摆到设计位置，而是把任务、抽卡、图鉴、分享、记录、抽奖、降级和调试验证收成一个能运行、能解释、能继续改的系统。

这也是为什么这条分支的提交看起来很多：它不是在反复“改样式”，而是在一步步把活动页从静态页面推进到可联调、可验证、可交接的状态。
