> 承上：第六讲讲了 Agent 怎么在循环里自己绕圈办事。可你交给它的活，是“凭感觉边做边改”，还是“先定规格再施工”？这一讲来到一片工地，看两种截然不同的盖法。新来的学徒阿砖，先学最轻快的那种。

阿砖脑子里有个亭子的模样，却说不清尺寸。老工头没让他去画图纸，递给他几根竹竿：“别想太多，先在地上搭个草棚，把你脑子里那个样子立起来看看。”

阿砖手忙脚乱搭起来，立马发现问题：从这个角度看，顶太矮了；挪两步，又觉得柱子太密。他随手拆了挪、挪了改，半天功夫，那个模糊的念头越来越清楚。

“这就是草棚的好处，”老工头说，“快、便宜、随手改，帮你把‘说不清的感觉’试成‘看得见的样子’。”可他随即叮嘱：“但草棚就是草棚——别真让人搬进去住。要长住的正房，得另起一套讲究。”

## 概念揭晓

这种“先搭草棚试手感”的做法，对应 AI 编程里的 **vibe coding（氛围编程）**：不先写严谨规格，而是凭感觉用自然语言驱动 AI 快速把东西做出来、边看边改。这个说法 2025 年由 Andrej Karpathy 提出，迅速流行。

它的价值，正是草棚的几个好处：

- **探索**：把模糊的想法快速变成能看、能用的东西。
- **快速反馈**：立刻看到效果，立刻调整，循环很短。
- **原型**：低成本验证“这个方向行不行”，不行就丢。

它的边界，也正是“草棚不能当正房”：vibe coding 适合探索和原型，不等于可以不理解代码、直接把它当生产系统。

## vibe coding 改变了什么

过去把一个想法变成能跑的东西，门槛在“你得会写代码、会搭环境”。AI 编程把这道门槛大幅拉低：你用自然语言描述想要什么，AI 把它生成出来，你看效果、再用自然语言让它改。

于是“想—做—看”的循环变得极快、极便宜。对探索性的工作，这是质变：你可以一晚上试十个方向，而不是为一个方向写一周代码。这种“快速试错”的能力，本身就很有价值。

## 最适合的三种场合

- **探索想法**：方向还不确定，先做个能玩的版本找感觉。
- **快速原型 / demo**：给自己或别人看“大概长这样、大概能这样用”。
- **一次性的小工具**：用完即弃的脚本、临时的数据处理，不必大动干戈。

这些场合的共同点是：**改起来便宜、错了代价小、不要求长期维护**。草棚最适合搭在这种地方。

## 边界：草棚不能当正房

vibe coding 的风险，全藏在“把草棚当正房”里：

- 凭感觉拼出来的东西，可能能跑，但你不真懂它为什么跑、哪里会塌。
- 没有规格、没有测试，它在边界情况、并发、安全上很容易出问题。
- 一旦要长期维护、要可靠、要多人协作，“说不清结构”就成了大麻烦。

所以严肃、要长期可靠的系统，需要的是另一套讲究——也就是 07.2 要讲的 SDD（先定规格再施工）。vibe coding 和 SDD 不是对错之争，是“探索阶段”和“施工阶段”的分工。

## vibe coding 不等于不用懂

有个流行的误解：vibe coding = 不看代码、全交给 AI。

更稳妥的理解是：在探索阶段可以“凭感觉快做”，但当你要把它变成认真用的东西时，你（或某个把关的人）仍然得理解它在干什么。原始提出者和不少实践者都强调：把它当探索和原型的利器，而不是“可以永远不懂代码”的借口。懂与不懂的分界，往往就是草棚和正房的分界。

## 常见误区

第一，把 vibe coding 当成万能生产方式，用它直接交付要长期可靠的系统。

第二，把它当成“再也不用理解代码”。探索可以快，交付仍需懂。

第三，把它和 SDD 对立起来。它们是不同阶段的工具，常常先探索、后规格。

## 小练习

下面三件事，判断哪些适合先 vibe coding：

1. “周末想试试一个新点子，做个能玩的小网页。”
2. “给公司核心支付系统加一个新功能。”
3. “临时写个脚本，把一批文件批量改个名。”
