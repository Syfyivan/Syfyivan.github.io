前面十篇分别写了 bridge、桌宠 UI、会话分享、开源调研、勿扰、主题、打包、任务详情、气泡边界和全屏窗口。这一篇像一本踩坑账本，把这次做 Kodama 时最容易误判的点集中写下来。

它们有一个共同点：从代码角度看都不大，但从用户体验角度看都很关键。

## 坑 1：把桌宠当成 bridge 的一部分

最开始很容易想：既然飞书机器人要带桌宠，那桌宠是不是也应该懂飞书事件、知道 bot app、甚至自己连飞书？

后来证明这条路不对。

Bridge 已经负责飞书事件订阅、消息过滤、owner 确认、Codex/Claude 后端调用、发送飞书回复。如果桌宠再监听一遍，就会出现两个消费者、两套判断、两套状态。

正确边界是：

```text
bridge 做事
Kodama 展示和回到现场
```

桌宠只需要从 bridge 拉统一事件，不要自己判断飞书消息该不该执行。

## 坑 2：把原始事件当成用户状态

SSE `error` 不等于系统离线。网络重连、bridge 短暂重启、EventSource 自身重试都会触发 error。如果 UI 立刻显示“Bridge 离线”，用户会看到状态反复跳。

所以要做二次确认：

```text
SSE error
  -> 延迟探测 /pet/state 或 /healthz
  -> 仍失败才显示离线
```

用户状态不应该直接等于底层事件。底层事件是事实，用户状态是解释。

## 坑 3：气泡自动消失

普通通知几秒后消失没问题，但 Agent 交互不行。

如果气泡写着“需要你确认权限”，它自动消失就是失败。用户错过以后，任务卡住，系统也没有解释。

所以 Agent 相关气泡要常驻，直到：

- 用户点击跳转处理。
- 用户点击忽略。
- 任务状态变成完成、失败或取消。

这类气泡不是 toast，而是 lightweight inbox。

## 坑 4：点击气泡打开 JSONL

本地 Agent transcript 通常是 JSONL。开发者看 JSONL 能排错，但用户点击气泡时想要的不是 JSONL。

用户想要的是：

- 打开正在运行的 Codex 会话。
- 打开 Claude Code 所在终端。
- 打开飞书原会话。
- 打开可阅读的分享页面。

所以 transcriptPath 只能作为证据字段，不能作为默认跳转目标。打开 JSONL 会让用户觉得功能“跳转错了”。

## 坑 5：任务分享和会话分享混在一起

任务是一次执行，会话是多轮上下文。

用户说“把这轮联调分享出来”时，可能指的是菌子和另一个机器人在一个群里来回联调的整段过程，而不是某一条 bridge task。

所以分享模型要分清：

```text
task share      单次任务执行记录
session share   多轮会话过程
transcript view 本地原始记录的可读渲染
```

如果只分享任务页，别人可能看不到完整上下文。如果只打开 transcript，别人又看不到飞书里发生了什么。

## 坑 6：机器人消息和 Agent 交互混在一个提示里

飞书消息和本地 Agent 事件都是“通知”，但它们的紧急程度不同。

- 飞书机器人收到消息：提醒用户有对话。
- Agent 等待确认：需要用户操作。
- Agent 完成：可以稍后查看。
- Agent 失败：需要排查。

如果都用同一种气泡，用户无法判断优先级。后来拆成不同类型、不同颜色和不同 tab，才像一个可用 inbox。

## 坑 7：气泡盖住宠物

气泡一多，最容易盖住桌宠本体。技术上这只是一个绝对定位问题，但体验上很糟糕：用户看到的是通知卡片，不是桌宠。

布局算法必须把宠物可见区域当成 exclusion zone。气泡可以贴近宠物，但不能盖住宠物主体。

尤其当宠物半出屏时，要避让“屏幕内可见的那部分宠物”，而不是完整图片矩形。

## 坑 8：桌宠半出屏，气泡也半出屏

宠物允许停靠到屏幕边缘，甚至只露半个。但气泡不能跟着跑出屏幕。

这里要分开两个约束：

- 宠物位置：允许贴边和半隐藏。
- 信息位置：必须完整可见。

如果为了保证气泡可见而限制宠物不能靠边，用户就没法把它放到角落。正确做法是让气泡在屏幕内自适应到左上、左下、右上或右下。

## 坑 9：点击范围比图案大

透明窗口不代表不可点击区域自动穿透。Electron 窗口矩形仍然可能接收鼠标。

用户会感觉“我明明没点到它，它怎么动了”。这会直接影响日常操作。

解决思路是：

- 空白区域窗口级穿透。
- 图案内部再做较小 hitbox。
- 设置里暴露点击范围。
- 支持右键触发，左键尽量穿透。

桌宠越透明，越应该少拦截鼠标。

## 坑 10：隐藏后找不到恢复入口

隐藏桌宠是必要功能，但隐藏必须有恢复路径。

菜单栏入口不够，因为菜单栏可能被系统挤掉，也可能被隐藏工具折叠。更稳的是：

- 菜单栏 `Kodama` 入口。
- 全局快捷键。
- 开发态本地命令或 health endpoint。

隐藏功能必须回答“我怎么把它叫回来”。

## 坑 11：把菜单栏当成绝对可靠入口

macOS 菜单栏空间有限。图标多的时候，用户看不到 Kodama 不一定是程序没启动，而是被系统或菜单栏管理工具藏起来了。

所以文档和 UI 都不能只写“去菜单栏点图标”。要同时提示快捷键，必要时在 README 里写清楚开发态恢复命令。

## 坑 12：全屏置顶以为 `alwaysOnTop` 就够

Electron 的 `alwaysOnTop` 在普通桌面有效，但 macOS 全屏 Space 是另一套窗口规则。

需要组合：

```text
setVisibleOnAllWorkspaces
visibleOnFullScreen
screen-saver level
moveTop
reassert
```

如果还不稳定，就要接 NSPanel。全屏问题不能用网页思维解决。

## 坑 13：面板缩小时让文字硬挤

设置面板窄的时候，tab 文案会竖排或溢出。只缩小字体不是根治。

更好的做法是响应式切换：

- 宽：完整文字。
- 中：短文字。
- 窄：两行 grid 或图标。

桌宠面板不是普通大屏 dashboard，它经常被用户缩到很小。

## 坑 14：Bridge 离线状态让用户误会

有时桌宠显示 “Bridge 离线/重连中”，但 bridge 可能只是重启瞬间、SSE 断开、或者端口配置不一致。

状态文案要具体：

```text
Bridge 已连接 · Hook 127.0.0.1:7766
Bridge 重连中 · Hook 127.0.0.1:7766
Bridge 未探测到 · 检查 127.0.0.1:8787
```

把 bridge 和 local hook 分开显示，用户才能知道是哪一段断了。

## 坑 15：Keychain 错误被误判成 secret 错

本机 CLI 有过：

```text
keychain unavailable: context deadline exceeded
```

这不一定是飞书 app secret 错。它可能是 CLI 想把 secret 写入 macOS Keychain，但当前环境拿不到钥匙串。

这类错误要在文档里写清楚：认证失败、secret 错、Keychain 不可用是三类问题。不要看到登录失败就让用户去改 secret。

## 坑 16：机器人互相回复被误接管

联调时出现过一个问题：本地桥还在轮询旧群，review follow-up 逻辑又过宽，于是另一个机器人“知微”的回复被菌子误判成 reviewer follow-up，菌子用自己的身份发了 owner 确认卡。

这个问题的教训是：

- 群轮询必须收敛到明确白名单。
- reviewer follow-up 必须有明确 reviewer 白名单。
- “已知机器人”的回复不能默认当成人类 reviewer。
- owner 确认卡要展示请求人、来源群和风险类型。

自动化越强，触发边界越要窄。

## 坑 17：联调轮数只写死数量

机器人互相联调时，不能只靠固定轮数。固定轮数只能做兜底。

更合理的终止条件是：

- 对话语义收敛。
- 明确出现完成标记。
- 重复内容超过阈值。
- 达到最大轮数兜底。

这类 bot-to-bot relay 应该像任务协议，不应该像盲目 ping-pong。

## 坑 18：只做宠物，不做控制面

如果桌宠只负责显示形象和几个气泡，它很快会变成“好看的通知条”。

真正有用的是控制面：

- 待交互。
- 已完成。
- 会话。
- 最近事件。
- Bridge 任务详情。
- 分享。
- 跳转。
- 勿扰。
- 设置。

这些能力让桌宠成为 Agent 工作流入口，而不是桌面挂件。

## 坑 19：开源桌宠能力不能直接照搬

开源桌宠项目常见能力有：

- 拖拽。
- 贴边。
- 动作动画。
- 表情。
- 主题。
- 托盘菜单。
- 喂食/成长。
- 定时提醒。
- 插件。

这些值得学习，但 Kodama 的核心不是宠物养成，而是 Agent 工作流。所以能力排序不同：

```text
Agent 事件 > 跳转现场 > 分享会话 > 不打扰 > 桌宠养成
```

桌宠生态能力可以补趣味性，但不能压过任务控制面。

## 坑 20：打包成功不等于发布完成

`pnpm run dist:mac` 能产出 DMG，只说明本机能打包。真正发布还要考虑：

- 签名。
- notarization。
- 自动更新。
- Windows/Linux 置顶和托盘差异。
- 开机自启权限。
- 第一次启动引导。
- 崩溃日志。

开发态可用和公开发布是两个阶段。文档里要把它们分开写，不能说“已经完全发布完成”。

## 我现在会怎么重新设计

如果从头再做一次，我会先画三条主线：

第一条是事件主线：

```text
bridge / local hook -> normalized event -> inbox -> bubble / panel / task detail
```

第二条是跳转主线：

```text
event target -> Feishu chat / Codex session / Claude terminal / task page / session share
```

第三条是窗口主线：

```text
pet rect -> visible pet rect -> bubble exclusion -> panel placement -> hitbox -> fullscreen fallback
```

这三条主线先稳定，再做主题、配饰、成长、番茄钟和插件。

## 下一步值得继续做的事

这套系统已经能形成可用闭环，但还有几个方向值得继续补：

- Bridge 任务详情页继续补完整触发判定和失败原因。
- 会话分享要从“单任务”扩展到“多轮联调过程”。
- 全屏场景接 NSPanel，解决 Electron best-effort 不稳定。
- Windows/Linux 单独验证置顶、托盘和点击穿透。
- Token 进账要用真实飞书任务长期验证。
- 配饰和形象要做主题包，而不是写死坐标。
- 番茄钟和久坐提醒要完整 UI 配置。
- 构建、测试、Git 操作等 Agent 细颗粒度事件要继续铺开。

桌宠项目最有意思的地方在于，它不是一个纯前端组件，也不是一个纯机器人。它处在操作系统、IM、Agent runtime 和用户注意力之间。

这也是它最容易踩坑的地方：每一个“小气泡”背后，其实都是一个工作流入口。
