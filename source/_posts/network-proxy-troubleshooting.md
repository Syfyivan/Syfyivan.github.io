代理网络排障最怕“连续换配置”。看起来很努力，实际上每次都改了太多变量，最后无法知道是哪一处生效。

更稳的办法是按层验证：DNS、入口、规则、策略、出口、TLS、UDP/QUIC、目标服务。每一层只证明一件事。

## 先画路径

不要先改配置，先画实际路径：

```text
应用
  -> DNS 解析
  -> 代理入口：系统代理 / 本地端口 / TUN / 透明代理
  -> 规则引擎
  -> 策略组
  -> 真实出口
  -> 目标服务
```

然后在每个箭头上写证据：

- 哪个 DNS 返回了什么结果；
- 代理日志有没有看到连接；
- 命中了哪条规则；
- 策略组选中了哪个出口；
- 出口连接目标时失败在哪里；
- TLS 有没有证书错误；
- UDP/QUIC 是否可用。

证据不够时，不要下结论。

## 第一步：确认 DNS

先问：

```text
这个域名是谁解析的？
解析到了 A 还是 AAAA？
有没有 CNAME？
结果是否来自缓存？
代理节点域名和目标站点域名是否分开解析？
```

本机可以用这些命令做基础观察：

```bash
dig example.com
dig AAAA example.com
nslookup example.com
```

macOS 上还可以看系统 DNS 状态：

```bash
scutil --dns
```

如果浏览器启用了自己的 DoH，它可能不完全遵守系统 DNS。排障时要把浏览器、系统、代理客户端三者的 DNS 设置分开看。

判断标准不是“能解析就行”，而是“解析结果是否被后续连接和规则使用”。

## 第二步：确认流量进了代理

代理客户端日志里没有请求，优先怀疑入口。

系统代理模式下检查：

- 应用是否遵守系统代理；
- 应用是否用了自己的代理设置；
- 命令行是否需要 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`；
- 本地端口有没有填错；
- HTTP 代理和 SOCKS 代理类型有没有选错。

TUN 模式下检查：

- 虚拟网卡是否创建成功；
- 路由表是否把目标流量导入 TUN；
- DNS 是否也被接管；
- IPv6 是否漏走；
- 代理自身连接是否被排除，避免回环；
- Docker、虚拟机、局域网路由是否冲突。

透明代理模式下检查：

- 客户端网关是否指向路由器；
- 防火墙规则是否命中；
- NAT 和策略路由是否正确；
- DNS 是否在网关侧统一处理；
- IPv6 是否和 IPv4 走了不同路径。

这一层的目标很简单：先让日志里出现请求。

## 第三步：确认规则命中

请求进入代理后，看命中的第一条规则。

要记录：

```text
目标域名 / IP / 端口
入口类型
网络类型：TCP / UDP
命中规则
规则动作
策略组
真实出口
```

常见问题：

- 兜底规则太靠前；
- 外部规则集顺序不符合预期；
- 域名规则拿不到域名上下文；
- IP 规则覆盖了域名规则；
- REJECT 误伤；
- 进程规则在路由器透明代理场景根本拿不到进程名。

不要只看配置文件。要看运行时日志里实际命中的规则。

## 第四步：确认策略组

如果规则动作是策略组，不要停在“命中了 PROXY”。

继续看：

- 策略组当前选中哪个节点或出口；
- 这个选择是手动、测速、故障转移还是负载均衡；
- 测速 URL 是否只代表测速目标；
- 失败后有没有切换；
- 切换后旧连接是否仍然复用旧出口。

长连接和连接复用会让切换不立即生效。很多工具切换策略后，新连接走新出口，老连接要等关闭后才变。

## 第五步：确认出口可达

入口和规则都对，不代表出口可达。

可以分开测：

```bash
curl -v https://example.com/
curl -I https://example.com/
curl --http1.1 -I https://example.com/
curl --http2 -I https://example.com/
```

如果工具支持指定代理端口，也可以让 curl 直接走本地代理，排除浏览器因素：

```bash
curl -x http://127.0.0.1:7890 -v https://example.com/
curl --socks5-hostname 127.0.0.1:7891 -v https://example.com/
```

这里的重点不是记住命令，而是分离变量：同一个目标，用同一个入口，观察连接建立、TLS 握手、HTTP 状态码分别在哪里失败。

## 第六步：区分 TLS 错误和 HTTP 错误

TLS 失败和 HTTP 失败不是一回事。

TLS 阶段失败，常见表现是：

- 证书不受信任；
- 证书域名不匹配；
- 握手超时；
- 协议版本或加密套件不兼容；
- MITM 证书没有正确安装；
- App 做了证书固定，拒绝被调试。

HTTP 阶段失败，常见表现是：

- 301/302 重定向；
- 401/403 权限问题；
- 404 路径问题；
- 429 限流；
- 500/502/503 服务端或网关问题；
- 业务层返回错误 JSON。

如果 curl 已经显示 HTTP 状态码，说明 TLS 至少已经建立成功。不要把所有 403 都归因于代理连不上。

## 第七步：单独看 UDP 和 QUIC

HTTP/3 走 QUIC，QUIC 走 UDP。很多“网页偶发慢”可能和 UDP 路径有关。

排查思路：

- 临时让客户端禁用 HTTP/3，看问题是否消失；
- 对比 HTTP/2 和 HTTP/3；
- 看代理入口和出口是否支持 UDP；
- 看网络环境是否限制 UDP；
- 看 DNS 是否返回了触发 HTTP/3 的记录或 Alt-Svc；
- 看日志里是否有 UDP 连接和失败原因。

不要用 TCP 443 正常，直接证明 UDP 443 也正常。它们不是同一条传输路径。

## 第八步：检查安全边界

网络工具越强，越要检查边界。

MITM：

- 是否只对需要的域名启用；
- 本地 CA 是否仍然被系统信任；
- 敏感应用是否被误纳入；
- 调试结束是否关闭。

局域网共享：

- 本地代理端口是否允许 LAN 访问；
- 是否设置认证；
- 是否只绑定本机 `127.0.0.1`；
- 是否暴露到不可信网络。

透明代理：

- 是否影响家里其他设备；
- 是否影响公司或学校网络要求；
- 日志里是否收集了不必要的信息。

排障不是只追求连通，还要知道自己扩大了哪些信任范围。

## 最后再改配置

每次只改一个变量：

- 只换 DNS；
- 只换入口模式；
- 只改一条规则；
- 只切一个策略组；
- 只关 HTTP/3；
- 只测试 IPv4 或 IPv6。

改完写下结果。能复现、能解释、能回滚，才算真正排障。

## 一个可复用模板

以后遇到问题，可以照这个模板记录：

```text
目标：
现象：
入口模式：
DNS 结果：
是否进入代理日志：
命中规则：
策略组和真实出口：
TLS 阶段：
HTTP 状态：
UDP/QUIC：
IPv4/IPv6：
本次只改了什么：
结论：
```

这份记录比“试了很多配置”更有价值。它能让下一次问题更快收敛。
