> 承上：上一章阿器学全了借工具的规矩。这一章，工具行火了——架上从十几件堆到几百件，本以为越多越强，没想到新麻烦来了。

工具行生意兴隆，老掌柜进了越来越多的工具，结果阿器反而抱怨：“东西太多了，我找半天找不着该用的那件，还老拿错相近的。”

老掌柜带他重新整理。先**分门别类**：量的归量的、切的归切的、动账的归动账的，贴上区，别一锅堆。再设个**取用台**：阿器要干某类活，先到取用台报一声，台子按这次的活，只把相关的几件递到他手边，而不是把整架推过来。最后清**新旧**：同一件工具出了新版，旧版要么下架、要么标清楚“别再用”，免得有人拿着过期的去干活、出岔子。

“工具不是越多越好，”老掌柜说，“是越好找、越拿得对越好。几百件摆在那儿没人会用，等于没有。”

> 所属路径：AI 与 Agent 大寓言课 / 第 05 讲：会借工具的学徒 / 05.6 工具生态设计

## 概念揭晓

老掌柜重整工具行，对应 Agent **工具生态的设计与治理**——当工具从几件长到几十上百件时，新的工程问题就来了。

“工具太多找不着、拿错”，是**工具过载**：一股脑把上百个工具定义全塞进上下文，既撑爆窗口（第三、四讲的预算），又让模型在相似工具间挑花眼、选错。

“按这次的活只递相关的几件”，是**工具召回 / 动态加载**：根据当前任务，先检索出可能相关的少数工具再交给模型，而不是一次暴露全部。这和第三、四讲“按需检索、精选上下文”是同一思路。

“分门别类、贴区”，是**分组 / 命名空间**：按领域、按风险给工具归类，既好找，也便于按组管权限。

“清新旧、标过期”，是**版本治理**：工具会升级、会废弃，要有版本管理和淘汰机制，别让 Agent 拿着过期定义干活。

## 工具不是越多越好

直觉上“工具越多，Agent 越能干”。但实践相反：工具一多，几件事同时变糟——

- 上百个工具定义占满上下文，挤掉真正的任务信息。
- 功能相近的工具让模型难以抉择，选错概率上升。
- 维护、权限、安全的复杂度成倍上涨。

所以成熟的做法不是“尽量多挂工具”，而是“让 Agent 在每一步只看到与当前任务相关的少数工具”。质量和可发现性，比数量重要。

## 工具召回：按需暴露

解法和 RAG 异曲同工：把工具也当成“可检索的资源”。

根据当前任务，先用检索/分组的办法挑出可能相关的少数工具，只把这些交给模型；其余的暂不暴露。需要别的，再动态加载。这样既省上下文，又减少误选。这也呼应了 05.3 Skill 的渐进式披露——能力可以很多，但一次只摊开该用的。

举个具体的：一个 Agent 挂了 200 个工具，这一步的任务是"订一张机票"。召回层先按语义挑出航班查询、日历、支付这几类、约莫八九个相关工具交给模型，其余一百九十多个根本不进上下文。模型既不会被一堆无关工具占满窗口，也不会在"订机票工具"和"订酒店工具"之间挑花眼。

## 分组与命名：好找、好管权限

给工具分组、起清晰一致的名字，有双重好处：

- **可发现**：模型（和人）更容易找到对的工具。
- **可治理**：按组授权——比如“只读组”默认放开，“写入组”默认从严（呼应 05.5），整组管比逐个管省事也更不易出错。

命名一致、边界清楚的工具集，本身就是一种降低出错率的设计。

## 版本治理：工具也会过期

工具会升级参数、改语义、被替代或废弃。如果没有版本管理，Agent 可能：

- 拿着旧定义调用，参数对不上而失败；
- 用了已废弃的工具，行为和预期不符。

所以要像管软件依赖一样管工具：标清版本、提供迁移路径、及时下架过期项、变更要通知到依赖它的 Agent。这和第十二讲“产品化里的版本治理”是同一件事的不同层面。
