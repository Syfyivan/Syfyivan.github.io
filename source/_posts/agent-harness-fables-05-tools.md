铁匠铺有三把锤子。

第一把只写着“锤”。第二把写着“敲钉子用，别去砸陶罐”。第三把还写了重量、握柄长度、适用材料和出错时怎么处理。

学徒第一次进铺子，当然更容易拿错第一把。

师傅没有骂他笨，只是把标签重写了一遍。

后来学徒很少拿错。不是他突然开窍了，是铺子里的说明变清楚了。

## 概念揭晓

这篇章要揭开的，是第 06 讲里“工具”这件事的真相：**工具不是能力本体，工具定义也不是给人看的注释，而是一份写给模型看的契约**。

故事里的锤子，对应可以被调用的外部能力；标签，对应工具名、使用时机、参数结构、返回值形状。模型看到的是说明书，真正执行的是外面的系统。

所以这章不是在说“模型突然长出了手”，而是在说：**模型会不会稳稳地使用外部能力，关键取决于契约写得好不好，外壳执行得稳不稳。**

## Tool 不是能力本体

源文最想纠正的误解就是：**Tool 不是模型本身的超能力**。

能力本体在外部世界里，可能是搜索引擎、数据库、本地文件、终端命令、业务接口。模型拿到的只是一个入口说明，知道哪里可以叫门、门后大概有什么、该怎么带参数。

这也是为什么“会不会调用 Tool”不是单纯的模型聪明不聪明，而是模型有没有拿到一份能读懂的说明书。

## Tool definition 是契约

一份好的工具契约，至少要把几件事写清楚：

- 名字是什么。
- 什么时候该用。
- 什么时候不该用。
- 参数怎么填。
- 返回结果意味着什么。

这五件事里，最容易被低估的是“什么时候该用”和“什么时候不该用”。很多工具名本身不差，但描述太像注释，模型只知道它“能做什么”，却不知道它“该在什么边界里做”。

可以把它理解成：`name` 是索引，`description` 是决策证据，`schema` 是边界，`result` 是下一轮能不能读懂的回执。

```json
{
  "name": "get_weather_forecast",
  "description": "Use this when the user asks for current or future weather for one city. Do not use it for historical climate, traffic, or travel advice by itself.",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" },
      "date": { "type": "string" }
    },
    "required": ["city"],
    "additionalProperties": false
  },
  "strict": true
}
```

这类结构不是为了让模型变成确定性程序，而是为了让它在概率性的选择里少走歪路。

## 没有结构化接口以前，大家怎么靠 Prompt 跑

源文回看了 2023 年以前的玩法：那时很多团队没有结构化工具接口，只能把工具清单和调用格式写进 Prompt，再靠应用侧解析文本。

这套方法当年能跑，不是因为它优雅，而是因为模型擅长模仿格式。只要示例足够清楚，模型往往就能学会按 `Action`、`Observation` 这样的文本协议出牌。

但它的问题也很明显：格式一旦稍微漂一点，解析器就开始受罪。所以后来需要结构化接口，把原本写在 Prompt 里的“请按这个格式输出”搬到协议层。

这是个很重要的历史背景：**今天的工具协议，不是凭空发明出来的，而是把旧时代手工约定正式化了。**

## 模型如何发现并决定调用

模型并不是在某个神秘时刻“看见了函数实现”。它看到的是当前上下文里那张工具菜单：工具名、说明、参数、限制，再加上用户问题和系统指令。

它据此做的是一种匹配判断：

- 当前问题是不是缺外部信息。
- 哪把工具的契约最能补齐这部分信息。
- 这把工具是不是现在就该用。

所以 `description` 不是给人看的注释，而是模型选择工具时的重要依据。契约写得越清楚，模型越容易出对牌；写得越含糊，它越容易摇摆。

```text
用户提问 -> 模型判断需要外部信息 -> 输出 tool_call -> 外壳执行 -> 结果回填 -> 模型继续回答
```

## 一次调用、并行调用、多轮调用

源文用天气预报把三种调用形态讲得很清楚，我这里把它们再压一遍。

**一次调用**：模型只需要补一个实时事实，比如“东京现在天气怎样”。它判断要查，然后交给外壳执行。

**并行调用**：同一轮里可以产出多个调用意图，比如同时查北京、上海、广州。模型不负责并发，**并发发生在外壳侧**。

**多轮调用**：答案依赖上一步结果，比如先查天气，再查空气质量，再查路程，直到拼出可用结论。

这三种形态说明的不是“模型会不会玩花活”，而是：**工具调用真正的价值，不是拿到一个事实，而是让模型能边看边改行动。**

## 工程上真正要调的是契约质量

源文里最实用的一句其实是：很多“模型不会用工具”的问题，根子在契约写得太差。

常见坏契约通常有这些特征：

- 名字太泛。
- 描述只写功能，不写边界。
- 参数太宽，什么都能塞。
- 返回值太散，下一轮读不懂。
- 多个工具职责重叠。

所以真正该调的，不是“再给模型一句提醒”，而是把契约本身写清楚、写窄、写成可执行规则。

这也是为什么工具调优更像接口设计，而不是玄学。

## 用 transcript 调试 Tool

调工具最好的材料，不是脑补，而是 transcript。

你要看的不是最后那个回答，而是整个过程：

- 用户原话是什么。
- 模型看到了哪些工具。
- 它为什么选这个工具。
- 它传了什么参数。
- 工具返回了什么。
- 下一轮有没有被结果纠正。

只要 transcript 打开，很多“模型笨”的问题会自动变成普通工程问题：可能是名字没起好，可能是边界没写清，可能是返回值不适合下一轮阅读。
