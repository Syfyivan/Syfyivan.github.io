> 承上：上一讲小磊弄懂了行规和「几星作坊」的招牌等级，正好瞥见自家几位老师傅围着一只快出货的柜子转来转去挑毛病——这就是「出货前的会审」。

一只给城东大户人家定做的顶箱大柜，眼看就要装车送货。阿萍却把它拦下了：「出货前先开个会审。」她叫来老周、还有两位做了二三十年的老师傅，又拿出当初客人定下的图纸和一张写得密密麻麻的检查单，几个人围着柜子，一处一处地对、一处一处地挑。

小磊在边上直嘀咕：「都做完了，眼看就送出去了，还挑啥？耽误工夫。」他伸手推了推柜门，「你看，不挺好的嘛。」

阿萍没理他，蹲下身,指着柜子右下角一道门缝：「这儿,缝不严,差了小半指。」老周凑过去眯眼一看，点头：「真是。现在挑出来，拿刨子修一修、垫一垫，几分钟的事。」他转头跟小磊说：「你要是图省事不挑，等送到客人家、跟旁边的条案、博古架一拼，人家一眼看出这道缝，咋办？得拆下来、装回车、拉回作坊返工，再赔一句不是、折一回信誉。同样一道缝，**现在改是几分钟，到了客人家就是几天，还搭上脸面**。」

小磊愣住了：「越往后，改起来越贵。」阿萍接话：「不光贵。你这柜子的尺寸要是从画图那会儿就错了，下料、拼装全跟着错，越往后错得越多、越缠在一起。所以每一道关口都得有人停下来对一对图纸——这叫**评审**。把毛病摁在它最便宜的时候。」老周补一句：「会审分好几样、好几种开法。最较真、最一处不放过的那种，叫**审查**，也最管用。」

## 概念揭晓

故事里这场「出货前的会审」，对应的正式概念就是 **软件评审（Software Review）**：在软件交付之前，由若干人对照需求、图纸（设计/文档）和一份检查单，逐处挑出其中的缺陷。

- 阿萍那句「越往后改越贵」，是评审的第一条理由——**缺陷发现得越晚，纠正费用越高**。
- 「尺寸从画图那会儿就错了，下料拼装全跟着错」，对应技术上的理由——**前一阶段的错误会传到后一阶段并不断累积**。
- 老周说的几种「开法」，对应 **五种评审方法**（从随便看看到最较真的审查）。
- 那张写得密密麻麻的检查单，就是评审技术里的 **缺陷检查表**。
- 而最较真、一处不放过的那种「审查（Inspection）」，正是 **最正式、最严格、最有效** 的评审方法。

## 为什么要评审

**从成本上：** 同一个缺陷，发现得越晚，改起来越贵。课件给出的相对成本大致是：需求阶段发现是 1 倍，到设计是 3-6 倍，到编码是 10 倍，到测试是 15-40 倍，等产品发布出去再发现，会高到 40-1000 倍。所以评审的重要目的，就是尽早把缺陷从产品里挑出来，避免大量后期返工——就像那道门缝，趁早改是几分钟，送到客户家是几天。

**从技术上：** 软件是一道道工序接力做出来的。前一道工序的错误，会原封不动地传给后一道，并且越滚越多——错误的需求规格说明会导出错误的设计，错误的设计会导出错误的编码，最后留下大量潜伏的错误，变成一个不完善的软件产品。评审就是在每道关口设一个「拦截点」，不让错误往下游漂。

**从效率上：** 评审对各种角色都有好处：

| 角色 | 好处 |
|---|---|
| 开发工程师 | 减少修订缺陷的时间，提高编程效率；减少测试和调试时间 |
| 项目负责人 | 缩短开发周期；减少维护费用；项目风险和质量问题得到很好控制 |
| 测试工程师 | 可以把更多精力放到测试用例设计上，提高测试效率 |
| 维护人员 | 维护工作减少；产品的可维护性增强 |

## 评审的内容

评审按对象分四类：

- **管理评审**：由最高管理者发起，要求各部门对管理体系当前状况（适宜性、有效性、充分性）进行评审，对质量体系进行回顾和总结，确保其适宜、有效、充分。
- **技术评审**：对产品及各阶段的输出内容进行评估，目的是确保需求说明、设计说明书与最初的说明书保持一致，并按计划进行了正确的开发，产出《技术评审报告》。
- **文档评审**：对各类文档进行检查。评审文档分四类：需求评审（市场/产品需求说明书、功能说明书）、设计评审（总体/详细设计说明书）、代码评审（代码）、质量验证评审（测试计划、测试用例）。
- **过程评审**：对软件开发过程的评审，通过监控流程，保证 SQA 定义的软件过程在项目中得到遵守，质量方针得到更快更好执行。

文档评审有一张固定的 **检查列表**（十个角度）：正确性、完整性、一致性、可行性、有效性、模块化、清晰性、可靠性、易测性、可追溯性。

## 评审的方法：五个台阶

按正式程度从低到高，评审方法有五种——越往上越较真、越费工夫，但也越管用：

1. **临时评审（Ad hoc review）**——最不正式，随手看看。
2. **轮查（Pass-round）**——把材料发给几个人各自看、给意见。
3. **走查（Walkthrough）**——作者带着大家走一遍。
4. **小组评审（Group Review）**——有组长、有准备、有会议。
5. **审查（Inspection）**——最正式、最严格、最有效。

**怎么选？** 一句话：**风险越高，用越正式的方法**。核心代码一旦失效后果严重，应当用审查或小组评审；一般代码用临时评审、同桌评审这类随意方法就够了。

审查、小组评审、走查三者的异同，是常考点，记这张表：

| 比较项 | 审查 | 小组评审 | 走查 |
|---|---|---|---|
| 主持者 | 评审组长 | 评审组长或作者 | 作者 |
| 检查表 | 有 | 可能有 | 无 |
| 专门的评审角色 | 有 | 有 | 无 |
| 准备 | 有 | 有 | 无 |
| 会议 | 有 | 有 | 有 |
| 修正 | 有 | 有 | 有 |
| 确认 | 有 | 有 | 无 |

## 评审的技术

- **缺陷检查表**：列出容易出现的典型错误，是评审的重要组成部分（故事里那张密密麻麻的检查单）。
- **规则集**：类似缺陷检查表，是业界通用规范或企业自定义规则的集合。
- **评审工具**：合理利用工具，如 NASA 开发的 **ARM（自动需求度量）**。
- **从不同角色理解**：不同角色对产品/文档的理解不一样，从多角色看能发现更多问题。
- **场景**：按用户使用场景去评审产品/文档。

## 评审会议怎么开

**准备阶段：** 制定评审计划和时间（含评审时间、方式、组成人员，并据此定评审检查点）→ 组建评审组（选好评审组长很关键，组长要和作者一起策划组织）→ 准备评审材料 → 发送审查包（被审查产品、前期文档、相关标准、各种表格、缺陷检查表等工具、测试文档）→ 制定活动进程表（安排房间，通知活动、日期、次数、地点）。

**召开阶段：** ①由评审员/作者演示说明 → ②评审员就疑惑处与作者沟通 → ③协调人或记录员清楚简明地完成会议记录（含缺陷分类）。

**评审结果有四种**（高频考点）：

- **接受**：不存在大缺陷，可以通过。
- **有条件接受**：不存在大缺陷，修订一些小缺陷后可以通过。
- **不能接受**：缺陷较多，作者修改后需重新评审。
- **评审未完成**：因某种原因未能完成，需后续会议。

**注意事项**：避免人身攻击（对事不对人）、避免无休止争论（争不下的记下来交作者定）、避免偏离会议中心、鼓励所有人发言（如按座位轮流发言）。

## 如何把评审做成功

- **主观因素**：对所有工程师做评审培训，让评审深入人心；预防个人冲突，避免有人身攻击倾向的人入组；把评审纳入项目计划并分配足够资源；收集以前的评审数据，了解哪种方法最有效；把评审列入个人时间表，保证有充分时间准备和参加。
- **客观因素**：采用异步评审（如共享文档、邮件评审）与分布式评审（如视频会议）。

一句话收尾：**评审过程越正式，效率越高；审查是评审方法中最正式、最严格、最有效的一种。**

### 考点一：为什么需要评审

**从成本上：缺陷发现得越晚，纠正费用越高。** 软件评审的重要目的，就是通过评审尽早发现产品中的缺陷，减少大量的后期返工。消除一个缺陷的相对成本：

> 需求分析 **1 倍** → 设计 **3-6 倍** → 编码 **10 倍** → 系统测试 **15-40 倍** → 实际测试约 30-70 倍 → 发布后 **40-1000 倍**。

**从技术上：** 前一阶段的错误会导致后一阶段的工作结果中有相应的错误，而且错误会逐渐累积、越来越多（错误的规格说明 → 错误的设计 → 错误的编码 → 潜伏的错误 → 不完善的软件产品）。

**从效率上：** 开发工程师——减少修订缺陷时间、提高编程效率，减少测试和调试时间；项目负责人——缩短开发周期、减少维护费用、项目风险和质量问题得到很好控制；测试工程师——可将更多精力放到测试用例设计上，提高测试效率；维护人员——维护工作减少、产品可维护性增强。

### 考点二：评审的内容（四类）

- **管理评审**：由最高管理者发起；要求各部门对管理体系当前状况进行评审；状况包括适宜性、有效性、充分性。其目的是对质量体系进行回顾和总结并确保其适宜性、有效性和充分性。
- **技术评审**：对产品以及各个阶段的输出内容进行评估。目的是确保需求说明、设计说明书与最初的说明书保持一致，并按照计划对软件进行了正确的开发；输出《技术评审报告》。
- **文档评审**：评审文档分为需求评审（《市场需求说明书》《产品需求说明书》《功能说明书》）、设计评审（《总体设计说明书》《详细设计说明书》）、代码评审（代码）、质量验证评审（《测试计划》《测试用例》）。**文档评审检查列表**：正确性、完整性、一致性、可行性、有效性、模块化、清晰性、可靠性、易测性、可追溯性。
- **过程评审**：对软件开发过程的评审，主要任务是通过对流程的监控，保证 SQA 组织定义的软件过程在项目中得到遵守，同时保证质量方针能得到更快更好地执行。

### 考点三：评审的方法（五种，由低到高）

> **临时评审（Ad hoc）→ 轮查（Pass-round）→ 走查（Walkthrough）→ 小组评审（Group Review）→ 审查（Inspection）**，从最不正式到最正式。

**审查、小组评审、走查异同比较：**

| 项目 | 审查 | 小组评审 | 走查 |
|---|---|---|---|
| 主持者 | 评审组长 | 评审组长或作者 | 作者 |
| 检查表 | 是（有） | 可能 | 否 |
| 专门评审角色 | 是 | 是 | 否 |
| 准备 | 有 | 有 | 无 |
| 会议 | 有 | 有 | 有 |
| 修正 | 有 | 有 | 有 |
| 确认 | 有 | 有 | 无 |

**如何选择评审方法**：最有效的标准是——对于最可能产生风险的工作成果，要采用最正式的评审方法。例如核心代码失效后果严重，应采用审查或小组评审；一般代码可采用临时评审、同桌评审等比较随意的方法。

### 考点四：评审的技术

缺陷检查表（列出典型错误，是评审重要组成部分）、规则集（业界通用规范或企业自定义规则集合）、评审工具的使用（如 NASA 开发的 **ARM 自动需求度量**）、从不同角色理解、场景（按用户使用场景评审）。

### 考点五：评审会议

**准备评审会议**：①制定评审计划和评审时间（含评审时间、方式、组成人员，并制定评审检查点）；②组建评审组（选定评审组长非常重要，组长需和作者一起策划组织整个评审）；③准备评审材料；④发送审查包；⑤制定活动进程表（安排房间，通知活动、日期、次数和地点）。

**召开评审会议**：①由评审员/作者进行演示或说明；②评审员就不清楚或疑惑之处与作者沟通；③协调人或记录员清楚、简明地完成会议记录（含缺陷分类）。

**评审结果（四种）**：

> **接受**——评审内容不存在大的缺陷，可以通过；**有条件接受**——不存在大的缺陷，修订其中一些小缺陷后可以通过；**不能接受**——缺陷较多，作者需修改后重新进行评审；**评审未完成**——由于某种原因未能完成，还需后续会议。

**注意事项**：避免人身攻击（矛盾集中于评审内容本身）、避免无休止争论（争不下的记录下来交作者决定）、避免偏离会议中心、鼓励所有人发言（如按座位顺序轮流发表意见）。

### 考点六：如何实施成功的评审

- **主观因素**：对所有工程师进行评审培训，使评审深入人心；预防个人冲突，避免有人身攻击倾向者加入评审小组；将评审活动加入项目计划并分配足够资源；收集以前的评审数据，了解哪种评审方法最有效；将评审列入个人时间表，确保评审员有充分时间准备和参加。
- **客观因素**：异步评审（如共享文档、邮件评审）、分布式评审（如视频会议）。

### 考点七：小结（点题）

> 对于软件评审，**评审过程越正式则评审的效率越高，审查是评审方法中最正式、最严格、最有效的评审方法。**
