这篇文章单独讲多仓活动服务重构。

重构规模约六个仓库、八类玩法或基础模块、数万行代码。它不是我一个人独立完成的；我参与团队重构，并负责过推荐互动、同人内容、免费活动类型、表单、徽章等具体模块的拆分、接线、灰度和验证。

公开版本保留真实的四周演进顺序，但删除内部仓库、配置键和环境名称。

## 一、十五秒怎么介绍

> 我参与过一次六仓活动服务重构，目标是把公共仓中的业务逻辑迁回正确领域，并把抽奖、任务、表单、徽章等模块拆成清晰的 handler、workflow、repository 和灰度路由。我的工作不是一次改完全部代码，而是负责多个模块的 v1/v2 并存迁移、结果对比和回滚验证，确保重构不改变接口、错误码和异步副作用。

## 二、为什么要重构

旧系统长期迭代后形成三类问题。

### 公共仓混入业务规则

所有仓库都依赖公共仓。把作者互动、任务规则和业务配置放进去，会导致一个业务改动触发多个仓库升级。

### 单入口职责过载

一个函数可能同时处理：

```text
参数校验
鉴权
规则选择
RPC
数据库
缓存
消息
发奖后置
错误兜底
```

任何修改都可能影响隐藏副作用。

### 多产品线逻辑耦合

两个产品的相似玩法放在同一个大 if/else 中，一端新增字段可能改变另一端默认值。

## 三、目标不是“目录好看”

六类运行职责：

```text
C 端 API：HTTP 协议、登录、参数、入口编排
运营 BFF：后台聚合、展示转换、文件入口
领域服务：规则、事务、状态机、运行时配置
离线任务：周期计算、批量和补偿
事件函数：行为事件消费与积分
公共层：模型、表和无业务方向基础设施
```

八个模块：

```text
lottery / signup / ranking / vote
task / form / badge / config
```

重构完成的标准不是文件移动，而是新增业务能落在明确模块，依赖方向与运行边界一致。

## 四、真实四周时间线

### 第一周：3 月中旬，先建架构基线和能力归属

团队先梳理：

- 哪些代码是真公共能力；
- 哪些是领域规则；
- 哪些只能通过 RPC 复用；
- 六个仓库各自的发布和故障边界；
- 八个模块当前入口、存储和异步动作。

这一步产出架构基线和模块迁移 spec，而不是立刻批量移动文件。

### 第二周：3 月 26—30 日，推荐互动作为第一条试点

时间顺序：

```text
3 月 26 日
  拆推荐互动的执行器和加载器
  调整为与其他互动模块一致的结构

3 月 27 日
  接入领域 handler
  恢复 v1 方法
  增加 v1/v2 灰度开关

3 月 30 日
  增加路由日志和结果对比日志
  抽出通用进度服务
  补单元测试
```

为什么第一条试点没有直接删除 v1？因为需要先证明新路径能运行、能比较、能回滚。

### 第三周：4 月 2—3 日，免费活动类型与同人模块验证可复制迁移方式

免费活动类型模块先创建独立 service、handler、feature flag 和 spec，再接入容器与入口路由。

验证顺序很具体：

1. 新路径 mode=1；
2. 日志证明请求进入 v2；
3. mode=0 回滚；
4. 日志证明完整回到 v1；
5. 删除临时 trace marker，只保留请求级路径日志。

期间有一个无效方案：尝试在返回值中增加测试标记，但上层在 nil error 时丢弃该字段，无法证明路径。随后撤回，改用明确日志。

同人模块沿同一周完成迁移，验证这套方式不是只适用于单一玩法。

### 第四周前半：4 月 7 日，表单模块完整迁移

表单模块按 Phase 1/2/3：

```text
Phase 1：定义类型和模块边界
Phase 2：抽 workflow / repository
Phase 3：容器装配、handler 路由、热更新开关
```

随后补：

- FeatureFlag 单测；
- 新旧错误消息对齐；
- 热更新；
- 路径 trace；
- 隔离测试环境验证；
- v1 回滚验证；
- 查询结果对比。

### 第四周后半：4 月 8—9 日，徽章模块和收口

徽章模块先抽 repository/workflow，再接入模块容器与 v1/v2 路由，补单测和隔离测试环境验证。

验证中发现状态枚举映射错误：FAILED 和 DUPLICATE 在新旧模型间被交换。这个问题编译和普通成功用例都发现不了，必须用逐状态对比测试。

4 月 9 日继续收口免费活动类型和同人模块，并修复环境判断和下游调用兼容。

## 五、模块内部如何分层

```text
handler
  参数校验、协议转换，不写重业务

service
  装配依赖、查找策略、调用 use case

strategy / business
  按产品线或活动类型选择实现

workflow
  编排业务步骤和事务边界

repository
  数据库、缓存的持久化接口

post
  事务提交后的消息、发奖和通知

router
  v1/v2 灰度与回滚
```

### 为什么 service 不能继续变成大文件

如果 service 同时写 SQL、发 MQ 和选择业务线，换目录也只是新泥球。service 应该像装配层，复杂流程进入 workflow，存储进入 repository。

## 六、一次关键返工：领域服务不是公共 library

早期想法：既然业务能力应该归领域层，就把公共仓的业务代码搬进领域仓，然后其他仓库直接 import。

问题：领域仓是独立部署的 RPC 服务，不是普通 Go library。

跨仓直接 import 会带来：

- 编译期强耦合；
- 发布顺序绑定；
- 内部依赖被外部使用；
- 领域服务的故障和权限边界失效。

最终原则：

```text
跨进程复用 -> RPC 契约
调用方编排 -> 留在调用方
稳定模型/基础设施 -> 公共层
领域规则 -> 领域服务内部
```

这是面试里最值得讲的失败，因为它不是语法错误，而是对运行边界的认识修正。

## 七、为什么不一次性重写

一次重写会把风险叠加：

- 多个接口同时变化；
- 新旧数据结构无法对比；
- 缓存和消息副作用容易遗漏；
- 出问题无法快速定位模块；
- 回滚需要整体回滚。

分模块迁移可以把风险切成可验证单元。

## 八、v1/v2 路由

推荐集中路由：

```text
mode = 0 -> 全部 v1
mode = 1 -> 指定活动类型走 v2
activity_overrides -> 单活动或类型覆盖
```

请求只在入口选择一次路径，不能中途一半 v1、一半 v2。

### 开关为什么需要热更新

发布代码和放量应该分开。代码先部署但默认 v1，确认依赖和日志后再动态切 v2；异常时不用重新发布即可回滚。

## 九、对比日志怎么设计

只记录“进入 v2”不够，还要记录结果摘要：

```text
request_id
module
selected_version
activity_type
result_count
status_counter
error_code
side_effect_summary
```

影子对比如果会产生写副作用，不能同时执行 v1/v2。可以对读路径双算，对写路径使用回放、测试数据或单路径执行后离线比较。

## 十、兼容契约

每个模块迁移 spec 都应明确：

### API fields

字段名、类型、默认值、空列表、顺序。

### error code / message

客户端可能按错误码决定重试或弹窗，不能只保证成功结果一致。

### DB side effects

表、事务、写入条数、唯一键、审计流水。

### cache

key、TTL、缓存穿透、回源、失效。

### MQ / external RPC

发送时机、payload、幂等键、调用次数。

### rollback

关闭开关是否完整回到 v1，v2 写的数据是否兼容 v1 读取。

## 十一、表单模块为什么适合验证完整迁移

表单有提交、查询和导出三条路径，既包含写也包含读。

迁移时重点：

- handler 保持协议；
- workflow 负责编排；
- repository 负责表单持久化；
- 查询缓存行为不变；
- 导出错误消息与 v1 对齐；
- mode=0/1 均有证据。

它比纯读模块更能验证架构是否真的承接业务。

## 十二、徽章模块暴露的状态映射问题

新旧模型可能分别定义：

```text
0 SUCCESS
1 DUPLICATE
2 FAILED
```

如果手工 cast 或顺序记错，FAILED 和 DUPLICATE 会交换。成功用例仍然通过。

测试必须对所有枚举值逐一断言，不能只测 SUCCESS。

## 十三、免费活动类型模块的回滚演练

回滚不是文档写“关闭开关”就算完成。

真实演练：

1. mode=1 发请求；
2. 通过路径日志确认 v2；
3. mode=0；
4. 再发请求；
5. 确认 v1；
6. 比较返回和副作用；
7. 删除临时测试标记。

这能回答面试官“你怎么证明可以回滚”。

## 十四、为什么临时返回字段不是好验证方式

测试字段可能：

- 被上层丢弃；
- 污染对外协议；
- 被缓存；
- 让客户端依赖；
- 合入后忘记删除。

更好的证据是 request_id 关联日志、trace、明确版本字段（如果正式契约允许）和数据副作用检查。

## 十五、如何拆迁移 Phase

### Phase 0：盘点

入口、调用方、存储、缓存、消息、外部 RPC、配置。

### Phase 1：契约与骨架

types、接口、依赖方向，不接流量。

### Phase 2：最小主链路

选择一条低风险读或写路径进入 workflow/repository。

### Phase 3：装配

service、handler、container、router。

### Phase 4：验证

单测、构建、隔离测试环境、结果对比、回滚。

### Phase 5：灰度和清理

小流量、全量、稳定观察、删除 v1。

## 十六、为什么每个模块稳定后就删 v1

如果等八个模块全部完成再统一清理：

- 双份代码长期并存；
- 新需求可能同时修改 v1/v2；
- 测试矩阵翻倍；
- 开发者不知道事实源。

每个模块全量稳定一周后单独删除更可控。

## 十七、重构中不能被忽略的副作用

```text
主数据库写入
缓存更新/删除
MQ 任务通知
中奖发奖
站内信
异步补偿
埋点和审计
```

面试官问“重构最大风险”，优先回答隐藏副作用，而不是“代码冲突很多”。

## 十八、个人所有权

可以说：

- 我参与团队多仓重构；
- 负责推荐互动、免费活动类型、同人、表单、徽章等模块；
- 编写或维护迁移 spec；
- 接入 router 和热更新开关；
- 做新旧结果对比与隔离测试环境验证；
- 实际演练 mode=0 回滚；
- 修复状态映射和环境兼容问题。

不能说：

- 我独立重构全部六仓；
- 所有八个模块都是我完成；
- 没有工程指标却声称性能提升百分比。

## 十九、工程结果怎么量化

没有统一业务指标时，可以看：

- 公共仓业务代码是否减少；
- 新功能需要修改的仓库数；
- legacy 大文件行数；
- v1/v2 差异数；
- 灰度回滚耗时；
- 模块单测覆盖；
- 新活动接入周期。

## 二十、两到三分钟口述版

> 我参与过一次六仓、八模块的活动服务重构。旧系统的问题不是单纯文件大，而是公共仓混入业务规则、入口同时负责协议和数据库消息、多产品线逻辑互相影响。团队先建立能力归属：C 端 API 做协议，BFF 做后台聚合，领域服务承载规则和事务，离线任务做批量，事件函数做行为积分，公共层只留模型和基础设施。
>
> 我负责过推荐互动、免费活动类型、同人、表单和徽章等模块。迁移不是一次切换，而是先建 spec 和 v2 骨架，再抽最小主链路，接入统一 router，通过开关让 v1/v2 并存。读路径可以做结果对比，写路径重点比较数据库、缓存、消息和外部 RPC 副作用。
>
> 时间上，3 月下旬先用推荐互动试点，补 v1/v2 路由和结果日志；4 月初迁移免费活动类型和同人模块，并实际验证 mode=1 和 mode=0 回滚；随后完成表单的 workflow/repository、热更新和隔离测试环境验证；最后迁移徽章，并通过测试发现 FAILED 与 DUPLICATE 枚举映射错误。
>
> 过程中有一次重要返工：最开始想让其他仓直接 import 领域仓代码，后来确认领域仓是独立 RPC 服务，代码目录边界必须服从部署和发布边界，跨仓能力应该走协议。这次重构让我理解，架构演进的核心不是换目录，而是能力归属、兼容契约、灰度证据和可回滚性。

## 二十一、高频追问

### 为什么不是工厂模式解决大 if/else

工厂只解决对象创建，不解决仓库职责、事务、发布和副作用边界。

### 为什么不新建 v2 仓库

会复制基础设施和发布链路，迁移范围更大。现有领域仓内部模块化更容易灰度。

### 为什么保留 v1

提供结果对比和快速回滚，但稳定后要及时删除。

### 如何证明行为一致

比较字段、错误码、DB、缓存、消息、外部 RPC 和异步后置，不只比较 JSON。

### 什么时候可以清理旧代码

目标模块全量、稳定观察、无差异告警、回滚窗口结束以后。

### 你遇到的最大返工是什么

把独立 RPC 领域服务误认为可直接 import 的 library，后来按运行和发布边界改为 RPC 契约。

### AI 在重构里做什么

Agent 可以建立调用图、找跨仓引用、生成 spec 草案和比较历史；能力归属、灰度策略、兼容契约和最终验收由人负责。

## 二十二、公开边界

- 时间线来自 3 月中旬到 4 月上旬的真实提交；内部仓库名、配置键和环境已泛化。
- 六仓八模块是团队范围，个人所有权只覆盖其中若干模块。
- 没有直接业务收益数字时，只陈述工程结果，不编造性能提升。
