## AI 观察

### 1. 模型小队的价值，不在“谁最强”，而在“谁负责哪一段”

今天群里对 `Sol / Luna / Terra` 的讨论很像一个多模型小队：有人偏好高档位模型做复杂推理，有人让模型负责已经写好的框架，有人把多个模型放进一个小队里各司其职。这是一个有用的群内信号，但它不是模型能力排行榜，也不能独立证明某种组合在所有仓库都更好。

真正值得抽象的是职责，而不是昵称。一个可复用的模型小队至少要回答四个问题：谁负责拆解目标，谁负责修改代码，谁负责运行验证，谁有权宣布交付？如果只是把多个模型接到同一个对话里，最后仍然会出现重复劳动、上下文污染和“每个人都以为别人会验收”的问题。

可以把角色先写成一张小表：

| 角色 | 主要责任 | 交付物 |
| --- | --- | --- |
| 总控 | 目标、范围、任务拆分和验收标准 | 任务卡、基线、完成条件 |
| 执行 | 在边界内改代码、生成资产或调用工具 | diff、生成物、命令结果 |
| 复核 | 检查事实、视觉/代码质量和风险 | 复核意见、未决项 |
| 交付 | 绑定发布渠道、版本和回滚点 | 可追踪的交付记录 |

在这个结构里，切换模型是实现细节；责任边界和证据链才是系统能力。模型可以替换，验收契约不能跟着模型一起漂移。

### 2. Skill 正在从提示词片段变成一条可复现的生产线

今天日报挑出的 `guizang-social-card-skill` 很适合作为观察样本。它的公开仓库自述支持 Claude Code / Codex，提供 Editorial 与 Swiss 两套视觉系统、多个画板尺寸和一套从内容输入到 HTML 渲染、PNG 输出的流程；仓库还提供基于真实 DOM 测量的版式校验脚本。这些是项目 README 的公开自述，应当作为试用线索，不应直接当作独立质量评测。

这个例子说明，Skill 的核心不是“让模型记住一种风格”，而是把隐含经验拆成可执行阶段：输入素材、选择风格、挑选版式、准备图源、渲染、校验、交付和迭代。每一阶段都应能回答“输入是什么、产物在哪里、失败如何处理、谁来确认”。

一条好的 Skill 工作流至少要留下四类证据：

1. `Input`：原文、截图、素材清单和脱敏范围。
2. `Plan`：目标平台、版式、模型/角色和允许的外部资源。
3. `Validation`：数字、来源、版权、尺寸、溢出和可读性检查。
4. `Delivery`：最终文件、生成时间、版本、来源说明和人工确认点。

这也是日报建议“先校验数字、来源和版权，再看三张卡是否更容易被读完”的原因：视觉产出不能把事实检查藏在审美判断后面。

### 3. “长文变成视觉套装”其实是一次内容编译

从文章、截图或产品笔记生成多种尺寸的卡片，不应理解成简单的摘要加配图。它更像一次内容编译：先从原始材料提取事实和结构，再把同一组事实编译成不同平台的布局和信息密度，最后通过渲染与校验得到发布资产。

编译过程里有三种容易丢失的东西：原始出处、数字上下文和目标平台的阅读约束。比如一张适合公众号的宽图，不一定适合手机端的竖向卡片；一段适合文章的限定语，也不能为了标题冲击力被删掉。生成系统应该把“事实层”和“表现层”分开，允许换版式，不允许静默改写事实。

对 agent 来说，这种分层也能降低上下文压力：总控保存结构化事实表，执行角色只接收当前版式需要的字段，复核角色再回看原文和来源。这样既能并行，也能在单张卡出现错误时定位是抽取、编译还是渲染阶段出了问题。

### 4. 工具兼容性是能力边界，不是模型偏好

群里关于 `Codex + DeepSeek`、`Claude Code + DeepSeek` 的比较，最有价值的部分不是谁“更丝滑”，而是暴露出一个常被忽略的事实：模型切换不等于工具链兼容。工具描述、参数约束、补丁格式、子代理协议、上下文管理和错误恢复都可能由客户端或运行时决定。

因此，评估一个模型配置时，应该把“模型质量”和“工具协议适配”拆成两个维度。至少记录：

- 同一个任务是否能稳定调用文件读写、补丁、搜索、测试和子代理工具；
- 失败时是模型不会用工具、客户端没有暴露工具，还是工具返回格式不兼容；
- 任务完成后能否留下可复现的 diff、日志和测试结果；
- 换回原配置是否能恢复，是否产生额外的额度或状态副作用。

没有这张兼容性矩阵，所谓“某模型更好”常常只是某条工具链更顺手。

## 前端 / 服务端 / 客户端工程观察

### 前端：把内容编译过程做成可检查的任务界面

内容生产前端不应只显示一张“生成中”的卡片。对今天这种多阶段 Skill，界面至少应展示：当前输入、已选版式、事实与来源检查、渲染进度、校验结果、需要人工确认的字段，以及最终导出尺寸。

一个轻量任务卡可以这样组织：

| 区域 | 应展示的内容 | 用户动作 |
| --- | --- | --- |
| 输入 | 原文、截图、素材和脱敏状态 | 补充或移除素材 |
| 结构 | 事实、数字、来源和目标平台 | 标记需保留的限定语 |
| 生成 | 当前角色、模型、版式、输出尺寸 | 暂停、重跑单个阶段 |
| 校验 | 溢出、可读性、来源、版权和数字检查 | 查看证据、要求修正 |
| 交付 | PNG/HTML/源文件、版本和发布状态 | 下载、确认或退回 |

前端最重要的交互不是“再生成一次”，而是“从哪个阶段继续”。如果只是渲染失败，就不应重新抽取事实；如果来源缺失，就不应让用户误以为换个颜色能解决问题。

### 服务端：为生成流水线建立阶段状态、来源账本和幂等键

服务端可以把一次生成建模为：

`created → scoped → extracted → composed → rendered → validated → reviewed → delivered`

每次状态迁移都绑定 `task_id`、输入版本、角色/模型、模板版本、图源、输出文件、校验结果和时间戳。外部取图、渲染、上传和发布都应有幂等键；网络超时后要区分“尚未执行”“已执行但回执丢失”和“明确失败”，不能把三者都当作可以安全重试。

来源账本尤其重要。日报推荐的 Skill 自述包含图源优先级、落地本地和写入 `SOURCES.md` 的做法；无论是否采用同一实现，服务端都应保留素材来源、授权状态、抓取时间和最终使用位置。这样内容被改版或复用时，来源不会随着一张图片的替换而消失。

### 客户端：桌面、CLI、IDE 和移动端共享同一份交付事实

OpenAI 的公开 Codex 页面把插件、Sites 和 annotations 描述为扩展 Codex 工作方式的能力，官方仓库则将 Codex 定义为运行在终端中的 coding agent。无论入口是桌面、终端还是浏览器，客户端都不应各自维护一份“生成完成”的本地判断。

跨端至少要共享：`task_id`、输入版本、当前阶段、生成物版本、来源账本、校验结果、人工批准记录和恢复点。移动端可以查看或批准下一步，但界面要明确这次批准对应的是哪一份事实和哪一版输出；桌面端重跑后，移动端看到的也应是同一条任务状态，而不是旧缓存。

如果模型配置可以由用户切换，客户端还要显示工具能力差异：哪些工具可用、哪些工具被禁用、是否支持子代理、失败能否恢复。把模型名称放在下拉框里很容易，把它和运行时能力、预算及回滚点绑定，才是真正可用的配置体验。

### 共同边界：公开项目自述、群内经验与生产承诺不是同一层证据

今天的材料正好有三层：飞书日报对 Skill 和协作方法的编辑判断，群友对模型组合与额度的个人体验，公开仓库和厂商页面对能力的产品/项目自述。它们都可以帮助选题，但证明力不同。

写成工程决策时，最好把结论改写成可验证的实验：固定任务、输入、仓库、工具权限和验收条件，只改变模型或 Skill；记录工具调用成功率、返工次数、验证覆盖、耗时、成本和恢复成本。这样“更顺手”才有机会变成可复查的数据，而不是下一轮口耳相传的配置建议。

## 值得跟进的动作

1. 选一个真实的内容或代码任务，试跑“总控—执行—复核—交付”四角色流程；固定输入和验收条件，只比较返工次数、验证覆盖和恢复成本。
2. 给每个 Skill 增加最小元数据：允许访问的目录、网络域名、外部副作用、来源要求、校验命令、失败恢复方式和最终产物。
3. 建一张模型/工具兼容性矩阵，分别记录文件读写、补丁、搜索、测试、子代理、长上下文和错误恢复，不用一句“体感更好”代替证据。
4. 为内容生成任务增加事实账本与 `SOURCES.md` 等来源记录，保留原文、数字、图源、授权状态和最终投放位置。
5. 前端提供“从失败阶段重跑”和“查看证据”两个动作；服务端用 `task_id + input_version + stage` 做幂等约束，避免重复抓图、重复渲染或重复发布。
6. 对今天日报推荐的第三方 Skill 做隔离试用：先检查代码、权限、依赖、图源策略和校验脚本，再用脱敏周报生成三张卡，暂不直接自动发布。
