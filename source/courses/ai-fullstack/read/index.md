理解 AI 全栈，可以始终追踪两件事：**信息怎样流动，下一步由谁决定。**

用户提出目标，应用收集信息，模型产生回答或操作请求，程序执行操作，再把结果交回来。Agent、CLI、MCP、Skill、Harness 都可以放进这条过程里理解。

这套课程面向 AI 全栈学习与面试准备。先建立能够运行的最小系统，再处理获取资料、执行动作、多步决策、恢复任务和用户交互。这些能力有些存在先后依赖，有些是针对不同需求的可选扩展，不必在每个应用中全部采用。第一遍先沿着任务运行读通，内部算法和接口细节留待深入。

## 1. 用户提出目标，应用把它交给模型

用户在界面里输入一个目标，最先收到它的是应用程序。应用把用户输入、任务要求和必要的历史消息组织起来，发送给模型。模型根据这些内容生成结果，再由应用展示给用户。

这里先分清两个参与者：**应用负责组织任务，模型负责处理提供给它的信息。** 用户身份、历史记录和业务资料通常掌握在应用手里，需要由应用选择并提供。

从模型内部看，它利用训练得到的能力处理输入，并逐步生成输出。我们暂时不用展开网络结构，只需要知道：训练形成已有能力，这次输入决定模型当前能利用哪些信息。

因此，用户说“继续刚才的任务”时，应用需要把相关历史带上，模型才能知道继续什么。这些进入本次模型调用的信息，就是上下文。

模型返回后，如果结果只是供人阅读，应用可以直接展示；如果结果还要决定程序下一步做什么，双方就需要约定一种程序能理解的表达方式。

## 2. 应用从模型回答中取得下一步所需的信息

程序需要从模型输出中准确取出结论，而不只是收到一段文字。应用可以要求模型把判断、目标对象和缺失信息分别返回，这就是结构化输出的作用。

模型收到任务要求，按照约定组织结果；应用读取结果，再决定继续处理还是请用户补充信息。Prompt 在这里承担说明任务和输出要求的作用。

应用还需要把模型结果与真实情况核对。例如，输出中包含一个文档编号，格式检查可以确认它是合法字符串，但文档是否存在、用户是否有权读取，需要应用查询自己的数据。

这样，双方形成了协作：模型从自然语言中整理出候选结果，程序结合真实事实判断怎样使用它。

不过，模型能否给出有依据的结果，还取决于应用提供了什么。如果判断需要参考大量资料，应用首先要从中选出当前任务需要的内容。

## 3. 应用先找到资料，再让模型利用资料

资料较少时，应用可以直接把它们放进上下文。资料很多时，可以先把当前问题交给检索模块，让它返回相关内容及来源，再把这些内容连同问题一起交给模型。

这就是 RAG 所连接的过程：**程序负责找资料，模型负责利用找到的资料生成结果。**

为了让资料可以被找到，系统通常会提前提取文件内容，分成适合检索的片段，并保存来源和版本。查询到来后，检索模块从中选出候选内容，应用再把适用的部分放进上下文。

这时模型看到的已经不只是用户的一句话，还包括支持判断的材料。回答出现问题时，也可以区分：是没有找到必要资料，还是模型没有正确使用已经提供的资料。

历史消息、检索资料和后续操作结果都会进入上下文。应用需要持续选择当前有用的部分，避免无关内容不断累积。

应用已经能根据资料生成回答，但要真正完成操作，还需要把模型的输出交给实际执行的程序。

## 4. 模型提出操作，程序负责执行

应用先告诉模型有哪些可用操作，以及每个操作能做什么。模型判断需要使用某项能力时，返回操作名称和所需信息，应用据此调用真实程序。

这个交接过程就是工具调用：

```text
模型提出操作请求
→ 应用检查请求并执行
→ 实际结果返回应用
→ 应用把结果交回模型
```

负责接收请求并运行对应程序的部分，可以称为工具执行器。

例如，模型决定读取一份资料，执行器完成读取后返回内容。应用把内容加入下一次请求，模型才能基于真实读到的信息继续判断。

所以，工具调用把一次模型生成延伸成了与外部环境的往返。模型选择操作，程序产生实际变化，再把变化结果提供给模型。

执行器要完成这些操作，还需要接入已经存在的程序和服务；CLI 和 MCP 可以在这一层发挥作用。

## 5. CLI 和 MCP 怎样接上实际能力

如果某项能力已经有命令行程序，执行器可以启动它、传入操作信息，再读取结果。这里的 CLI 就是执行器使用外部能力的一种入口，例如搜索文件、运行检查或操作代码仓库。

于是，前面的过程可以继续展开：

```text
模型提出工具请求
→ 执行器调用 CLI
→ CLI 完成操作并返回结果
→ 应用把结果交给模型
```

直接调用服务 API，也可以完成类似连接。

当不同 AI 应用都要接入外部能力时，可以通过 MCP 约定统一的发现和调用方式。应用中的 MCP Client 向 Server 获取能力描述，应用把相关能力提供给模型；模型提出请求后，再由 Client 发送给 Server 执行。

Server 内部仍然可以调用 CLI 或 API。因此，Tool Calling、MCP 和 CLI 可以出现在同一次操作中：模型表达调用意图，应用通过约定的连接方式送出请求，具体程序完成操作。

实际系统可以直接接工具，也可以选择 MCP，取决于接入和复用需求。无论采用哪条路径，执行结果都会回到应用，而应用还要决定如何继续任务。

## 6. 结果返回后，由谁决定下一步

如果任务步骤比较明确，应用可以用代码安排顺序：读取信息，交给模型处理，检查结果，再保存。这种由程序预先安排步骤和分支的方式，就是 Workflow。

另一种情况是，下一步需要根据刚获得的信息判断。应用便把工具结果重新交给模型，让模型决定继续查找、执行另一项操作、询问用户，还是结束。

这样就形成 Agent 的运行循环：

```text
获得当前信息
→ 模型选择下一步
→ 程序执行
→ 结果成为新的信息
→ 模型再次判断
```

区别发生在控制流上：Workflow 主要由代码决定路径，Agent 把一部分路径选择交给模型。两者可以结合，例如程序固定主要阶段，在其中某个阶段允许模型灵活选择操作。

如果任务较长，模型还可以形成计划，把阶段目标带入后续判断，并根据执行结果调整。

现在系统能够连续工作了，但每轮之间还需要有人保存进度、组织输入，并判断是否允许继续。这些工作由承载整个过程的运行程序完成。

## 7. Harness 把多轮执行组织成一个任务

这个运行程序通常称为 Agent Harness。不同实现的职责边界会有所差异，这里沿着刚才的循环理解它。

任务开始时，Harness 保存目标和当前进度。每轮调用前，它取出相关资料、已有结果和可用工具，组织模型输入。模型返回操作请求后，它把请求交给执行器；执行结束后，再保存结果，为下一轮准备信息。

因此，各轮调用能够接起来，是因为程序在它们之间持续传递和保存事实：

```text
当前任务记录
→ 本轮模型输入
→ 模型提出动作
→ 实际执行结果
→ 更新后的任务记录
```

Harness 也在这条过程中检查任务是否应该等待、停止或结束。模型提出“完成”以后，程序还可以核对实际结果是否满足目标。

Workflow 和 Agent 都能运行在这套机制中：它们决定步骤的方式不同，但都需要执行、记录和控制。

运行过程已经建立，同一类任务还会反复使用相似方法。把这些方法保存下来，任务开始时再按需提供，就不必每次重新解释。

## 8. Skill 把做事方法带入当前任务

Skill 用来组织可复用的任务方法，例如应该先读取哪些资料、遵循哪些约定、怎样检查结果，以及使用什么模板或脚本。

应用先根据任务找到相关 Skill，再把其中的方法提供给模型。模型利用这些方法安排操作，具体操作仍然通过已有工具执行。

它与前面几个概念在同一过程中协作：**Harness 组织运行，Skill 提供方法，模型据此选择动作，执行器完成动作。** 如果部分步骤已经写进 Workflow，程序也可以直接安排这些步骤。

Skill 通常可以按需加载：先让应用或模型知道有哪些方法，选中以后再读取详细内容。这样既能复用经验，也不必把所有说明放进每次上下文。

方法可以反复使用，但“当前任务已经做到哪里”需要另外保存；当任务跨越多次调用甚至跨天执行时，这种信息区分就变得必要。

## 9. 状态和记忆怎样重新进入上下文

上下文是模型本轮看到的信息，任务状态则记录执行进度。两者通过应用连接：程序从保存的状态和结果中选择内容，组成新的上下文。

如果任务中断，恢复时可以先读取上次停下的位置和已经完成的操作，再把继续所需的信息交给模型。模型由此接着处理，程序也保留了独立的执行记录。

长期记忆保存的是后续可能有用的信息，例如稳定偏好。它同样需要在相关时被取出，才能进入当前判断。Skill 保存方法，状态保存进度，记忆保存可复用信息，它们最终都可能成为上下文的来源。

恢复任务时，还要核对已经发生的外部操作。外部系统可能已执行成功，只是本地尚未记录；直接重新操作可能造成重复。因此，程序需要查询实际结果，或利用能够识别同一次请求的机制避免重复执行。

任务能够在后台持续运行以后，用户界面也需要与这份任务状态连接，才能展示真实进度并接收用户控制。

## 10. 前端通过任务事件连接用户与后台

模型生成的文本可以逐步展示，但任务进度应当来自程序实际发生的事件。

工具开始执行时，后端发送开始事件；执行结束后发送结果；需要用户补充信息时，将任务置于等待状态。前端根据这些信息展示进度和可用操作。

这样，界面同时呈现两类内容：模型用于解释的文字，以及程序确认的执行状态。

用户补充材料后，前端把内容交给后端，后端保存并触发任务继续。用户取消时，后端记录取消请求，再控制后续执行。连接断开后，前端可以根据任务编号重新获取状态，恢复同一个任务的展示。

前端因此成为用户参与执行过程的入口。用户看见进度并不等于任务已经正确完成，系统还需要根据目标检查最终结果。

## 11. 用实际结果判断完成，用执行记录定位问题

如果任务要求生成文件，就检查文件及其内容；如果要求改变外部状态，就读取对应系统中的结果。应用依据这些事实判断目标是否达成，再向用户说明。

当结果不符合要求时，需要沿执行记录寻找原因：必要资料有没有获得，模型选择是否合理，操作是否成功，结果是否满足目标。

把同一次任务里的检索、模型调用、工具执行和状态变化关联起来，就形成了可追踪的执行过程，通常称为 Trace。

固定的一组任务还可以用于评估系统修改前后的表现。这样，调整 Prompt、Skill 或工具以后，能够检查质量是否真正改善。

权限控制也落在实际执行过程中：即使模型提出了某个操作，程序仍根据用户身份和资源权限判断能否执行。

系统能够检查正确性之后，多人使用带来的等待、资源消耗和成本，也可以沿着同一条执行链分析。

## 12. 根据整条执行链维持服务稳定

任务进入后，需要模型和工具逐步处理。如果接收速度长期超过处理速度，等待任务就会累积，因此系统需要控制并发和接收量。

耗时任务可以交给后台 Worker 执行，队列负责分发，任务记录负责保存进度。前端继续通过状态和事件观察它，执行不必依赖一个始终连接的页面。

出现性能问题时，可以查看时间花在哪里：是等待处理、模型生成，还是工具执行。再根据实际位置，选择减少无关输入、复用已有结果、并行独立操作，或减少不必要的模型往返。

每次调整都需要重新检查任务质量，并记录相关版本，才能知道速度、成本和结果为什么发生变化。

至此，一次任务从用户输入出发，经由应用组织信息、模型选择或生成、程序实际执行、状态保存和界面反馈，最终到达可核对的结果。**各个概念都服务于这条过程中的具体交接；理解这些交接，就能沿着任何一次任务解释整套系统怎样运行。**
